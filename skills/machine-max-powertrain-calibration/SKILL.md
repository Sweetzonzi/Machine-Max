# Machine-Max 动力系统标定

标定做两件事：把需求换成参数，确认这组参数没有互相打架。

核心检查是动力源曲线、传动比、轮端力矩上限、附着和行驶阻力是否相容。离线脚本给静态估算；轮端实际输出和动态手感需在游戏内验证。

本技能只处理**静态包线**——给定参数下最多能输出多少力、能跑多快、能爬多陡。动态手感（换挡冲击、断流顿挫、档位振荡、油门跟随）由控制逻辑决定，标定阶段用观测量记录，不建模。

## 何时使用

- 新载具首次配动力链，或从别的载具复制参数后调整。
- 症状：极速明显低于预期、起步或加速发肉、爬坡无力、驱动轮空转、刹车感远强于加速感、HUD 标称马力与实际观感不符。
- 内容包改动了 `*_engine.json`、`*_motor.json`、`*_gearbox.json`、`*_transmission.json`、`*_wheel_driver.json`、`*_track_drive.json`、部件质量或轮胎材质之后。

换挡顿挫、高低档来回跳和油门响应迟滞先查控制逻辑。松油门拖拽感还可能涉及动力源内阻参数，需结合滑行测试判断。

## 需求：设计时给目标，诊断时读现状

作者手上的输入差别很大，但它们不是几条互斥的路，而是同一组约束里给多给少：

| 输入 | 地位 | 钉住什么 | 没给时怎么补 |
|---|---|---|---|
| 期望极速 `v*` | 目标设计时给定 | 最高档总传动比 `i_top`（配红线转速） | 只报告当前参数的估算极速 |
| 额定功率 `P_rated` @ `n_p` | 可选 | `max_power`，以及极速可达性的下界 | 由 `v*` 处阻力反推 |
| 最大扭矩 `τ_max` @ `n_τ` | 可选 | 一档传动比与档数 | 由 `P_rated` 与转速形状反推 |
| 怠速 / 红线转速 | 可选 | 曲线转速轴与 `i_top` 的取值 | 按发动机族取 |
| `0→x` 加速时间 | 可选 | 比功率下界 | 由 `P_rated` 反算得到时间 |
| 最大爬坡度 | 可选 | 一档总传动比 `i_1` | 按附着利用率 0.85~0.95 反推 |
| 档数 / 巡航转速 | 可选 | 级比与换挡落点 | 用相邻档总传动比差 ≥15% 试算，再核对曲线 |
| 制动距离或减速度 | 可选 | `max_brake_force` | 按 0.8 g 反推 |

设计目标车速时，`v*` 可用于反推最高档总传动比。纯诊断可以不提供任何目标，脚本会读当前参数并估算性能。其余给定指标用于生成可检验的约束；缺少硬件参数时，建议值需要明确标为假设。

三种典型粒度，中间的任意子集同样成立：

- **只给极速**：自由度最大；极速给出最高档传动比和功率下界，扭矩与档数仍需另作选择。
- **极速 + 实车硬件**（还原向：功率、扭矩、转速，乃至档数）：硬件固定，极速退化成一条要校验的不等式。
- **全部都给**：约束数超过未知数，先判可行性，再谈怎么填。

可行性是这一节唯一要回答的问题：所有不等式同时成立才算可行。有一条破了就是不可行——报出破的是哪条、差多少、放松哪个代价最小，不允许悄悄挪动参数把残差吃掉。残差的算法见 [工程模型 §七](references/engineering-model.md)。

## 求解前先量出来的量

需求之外还有一组量。它们不是作者的选择，而是装配体与模型的事实，必须先从内容包里量出来：

| 量 | 来源 | 影响 |
|---|---|---|
| 整备质量 `M_0`、运行质量 `M` | 各部件 `mass` 之和；`M = M_0 +` 乘员质量 | 加速、爬坡、附着极限、功重比 |
| 轮半径 `r` | **模型**：`type: "wheel"` 的 cube 在 y 向尺寸的一半；履带车取**主动轮**那颗球 | `i_top`、牵引力换算、`max_drive_force` 折成牛顿 |
| 驱动轮数 `N` | 接在传动上的轮；履带车是左右两个驱动端 | 单轮力矩分配 |
| 传动箱减速比 `r_trans` | 传动箱 `power_outputs` 里该端的分值 | `i_top`；漏算会把极速算低 |
| 前向阻力面积 `Cd·A` | 各子零件 `hydrodynamics` 的前向二阶系数 × 前向投影面积，求和 | 极速处的气动阻力 |
| `C_rr` | 轮胎材质的 `rolling_friction`；履带车读履带配件的材质 | 滚阻、滑行减速 |
| `μ` | 轮胎材质 `friction` × 地面方块 `friction`；履带车同上换材质 | 附着上限 `μg` |

`Cd·A` 不能只按模型量：每个子零件都有一个气动点，`hydrodynamics` 没写时按默认系数 `[0.1, 1.0]` 计，所以「车壳 + 轮子 + 车门各算一遍」才是游戏里的阻力口径。写了系数的零件按自己的值替换，遮挡会把实际阻力再压低一档，脚本不复现遮挡，给出的 `Cd·A` 因此是上界。

`r` 没有对应的 JSON 字段，只能从模型读：轮子的碰撞球半径就是模型 cube 的 y 尺寸一半。轮子画大一圈，`i_top` 与 `max_drive_force` 的换算会一起变，所以改模型之后必须重算 `i_top`，并在报告中记录新的 `r`。

履带车的 `r` 取主动轮那颗球，不取最大的负重轮：`TrackDriveSubsystem.radius()` 读的是被驱动子零件的碰撞球，负重轮再大也只承重不换算车速。主动轮在模板里没有显式指向，脚本按 `track_drive` 的 `connector` 名去掉前缀去匹配子零件名（`hull_left_sprocket` → `left_sprocket`），因此主动轮子零件要按这个名字命。

履带的滚阻与附着走的是另一份材质：`CollisionHandler.setupFriction` 对履带成员（主动轮、负重轮、诱导轮，**有没有轮驱子系统都算**）统一换成履带配件的材质，所以 `C_rr` 与 `μ` 要顺着 `track_type` → `fittings` 的 `material` 去读，读轮面碰撞箱上的 `off_road_tire` 会差一倍。滚阻合力仍是 `C_rr·M·g`，与接地轮有几个、半径多大无关。

`r_trans` 同样不在变速箱里：它在部件的 `subsystem_data` 下，是传动箱子系统自己的一张「输出端 → 减速比」表，键是子系统名，值是减速比。单速车（只有电机、没有变速箱）全靠这张表，`r_trans = 1` 时动力源转速就等于轮速换算值。

**单人标定口径**：整备质量只含部件；加速、滚阻、爬坡、附着与功重比用上车后的运行质量。默认加一名 60 kg 乘员，空车分析可传 `--occupant-mass 0`。已知乘员质量时用实际值覆盖默认值；货物等额外载荷当前未自动读取，报告中需注明。60 kg 默认值的实现依据见[工程模型 §七](references/engineering-model.md)。

## 求解顺序

1. **目标极速 → 最高档传动比**：让目标车速落在红线之前，并计入挡位、终传比与传动箱输出端。纯诊断时跳过反推，直接读取当前传动比。
2. **目标极速处的阻力 → 功率下界**：用气动、滚阻和内阻估算所需功率。0.85 是设计余量假设，并非脚本算出的传动效率。
3. **给定功率与转速 → 动力源曲线**：检查峰值扭矩、峰值功率、转速区间与 `max_power` 是否相容。
4. **爬坡或附着目标 → 一档传动比**：按驱动轮载荷估算附着上限，再检查轮端力矩限幅；实际载荷分配需游戏内验证。
5. **一档到最高档的跨度 → 档数**：相邻档传动比差可作初筛；换挡收益还须结合两档转速对应的扭矩曲线。
6. **回填验算**：逐档标注动力源、轮端限幅或附着中先到的约束。档位表加速度尚未扣行驶阻力。

反推方程、残差定义与默认值见[工程模型 §七](references/engineering-model.md)。

## 参数与模型速查

- 内燃机的 `max_power`（W）会限制实际扭矩；它应与限幅后曲线的峰值功率相符。电机的 `max_power`（W）与 `max_torque`（N·m）共同决定基速，`red_line_power_ratio` 决定高转功率衰减。曲线形状、端点与转速换算见[工程模型 §六](references/engineering-model.md)。
- `max_drive_force`、`max_brake_force` 是轮端力矩（N·m），牵引力还要除以模型轮半径。传动比包含挡位、终传比和传动箱输出端；两驱车的附着上限只计驱动轮载荷。完整驱动力链与单位表见[工程模型 §一、§二与单位速查](references/engineering-model.md)。
- 履带车读的是 `max_drive_torque`、`max_brake_torque` 与 `max_speed`：前两者同样是轴端力矩，`max_speed` 是主动轮角速度上限（rad/s），乘主动轮半径后是一条独立的极速上限。两条履带都驱动，附着按全车重量计。
- 气动、滚阻和动力源内阻分别建模；`Cd·A` 由各子零件的前向二阶系数与投影面积求和，未复现游戏内遮挡。阻力公式与默认值见[工程模型 §三](references/engineering-model.md)。

## 验收阈值

下表是设计参考阈值；没有给目标时应标明采用了哪些假设。离线结果只验静态参数，游戏内实测用于验收动态表现。

| 指标 | 阈值 | 不达标时的第一嫌疑 |
|---|---|---|
| 动力源净功率比 `P_net,peak / P_curve,peak` | ≥ 0.85（参考） | 动力源内阻过大；此项不含传动与轮端夹紧 |
| 一档附着利用率 `F / F_grip,driven` | 0.85 ~ 0.95（参考） | 过低查一档传动比或扭矩；过高查打滑风险 |
| 相邻档总传动比差 | ≥ 15%（参考） | 档位过密；实际换挡收益须按两档曲线另算 |
| `max_power` 与曲线偏差 | ≤ 1% | 参数填错 |
| 驱动加速度 / 制动减速度的比值 | 0.7 ~ 1.0（参考） | 两者严重不对称时查轮端力矩限幅 |
| 极速 | 相对目标 ±5% | 最高档总传动比，其次 `Cd·A` |
| `0→x` 加速时间 | 相对目标 ±10% | 比功率不足，或一档之后的级比过大 |

平地加速受驱动轮附着限制；两驱车不能按全车四轮的附着量设加速目标。均分载荷下的估算公式见[工程模型 §四](references/engineering-model.md)。

## 动态项的处理

静态方法覆盖不了起步扭矩爬升、换挡断流、档位振荡与轮胎滑移等过程。这些要在游戏内观测记录：

- 换挡断流可粗估为 `t_0→X ≈ t_静态 + n_次换挡 × switch_time`，实际时间仍要量测。
- 起步、振荡和滑移在游戏内记录，不写入静态结论。记录前按工程模型 §十 的口径：以物理步计时、先确认轮子在滚而不是在滑。

不要为动态性能另写一套积分模型：一旦脚本与游戏物理不一致，排查成本会超过收益，而且无法判断哪一方错。

## 完成后的自检

- 有设计目标时，需求表列出给定约束与试算假设；纯诊断无需补造目标。
- 每个上限都写清了它绑定在哪一档、哪个速度点。
- 残差表没有负项；有负项时写明了放松的是哪条软约束。
- 报告里的面积、整备质量、传动比与实际 JSON 一致；乘员质量假设单独列明。
- `max_power` 等于曲线峰值：它是硬上限，不是一个独立数字。
- 结论中的阻力三项各自有来源，没有合并成单一系数。

## 脚本

`scripts/` 下的工具直接读内容包 JSON，把上面这些量算出来。只要 Python 3.9+，无第三方依赖，不需要游戏。

四个入口各管一个侧面。按需只跑其中一个即可，不必为了看曲线而跑整车标定：

| 入口 | 回答什么 | 什么时候用 |
|---|---|---|
| `calibrate.py` | 档位表、估算极速、动力源净功率比、约束残差 | 配动力链、检查给定需求 |
| `curve.py` | 扭矩/功率曲线的形状：峰值落点、功率带宽度、`max_power` 削不削扭矩 | 只调引擎或电机，不看车 |
| `drag.py` | 逐子零件前向面积、阻力系数与 `Cd·A`，各速度点的阻力与所需功率 | 极速不够、判断哪块最吃风 |
| `gears.py` | 挡位 × 终传比 × 传动箱减速比，以及各档红线车速 | 只调传动，动力源还没定 |

```bash
python scripts/calibrate.py --list                          # 有哪些包与模板
python scripts/calibrate.py --pack Machine-Max_K17          # 整车标定，输出 Markdown
python scripts/curve.py --pack Machine-Max_K17              # 该车动力源的曲线
python scripts/curve.py --pack Machine-Max_K17 --csv        # 逐 rpm 全表，可直接画图
python scripts/drag.py --pack Machine-Max_K17 --speeds 30,60,90
python scripts/gears.py --pack Machine-Max_Civilian --template mini_ev
```

Windows 上 `python` 有时是应用商店的占位程序（直接退出、无输出），改用 `py -3` 或 `python3`。

`curve.py` 也能不经过整车，直接点名一个定义：`--subsystem machine_max:k17_engine`。它给出两个值得单看的形状指标：

- **功率带**：功率不低于峰值 90% 的转速区间。区间窄说明换挡落差不能过大，否则换完档可能掉出功率带。
- **`max_power` 削扭矩起点**：功率上限真的开始压制折线扭矩的转速。有起点就说明高转段调 `max_torque` 已经无效，只有 `max_power` 管用。

`calibrate.py` 带需求时追加参数，会多输出一张残差表：

```bash
python scripts/calibrate.py --pack Machine-Max_K17 \
    --top-speed 60 --power "500 PS" --accel 50:3.0 --grade 33 --gears 7
```

| 参数 | 含义 |
|---|---|
| `--pack` / `--pack-root` | 包目录名或包 id；包根目录缺省按脚本位置推断 |
| `--template` | 模板名；包内有多个模板时必填（`--list` 可见） |
| `--top-speed` | 目标极速 km/h，给出推荐 `i_top` 与极速处功率下界 |
| `--power` | 给定功率，`500 PS` / `368 kW` / `500hp` 都认 |
| `--accel` | `50:3.0` 表示 0→50 km/h 用 3 秒 |
| `--grade` / `--gears` | 最大爬坡度（度）、给定档位数 |
| `--cd-area` | 直接指定前向 `Cd·A`（m²），覆盖包内气动点 |
| `--occupant-mass` | 单名乘员质量，默认 60 kg；空车用 0 |
| `--json` / `--strict` | 输出 JSON；有残差为负时退出码 1（可进 CI） |

`drag.py` 与 `calibrate.py` 都认 `--cd-area`，`drag.py` 另有 `--speeds` 给速度点，`--occupant-mass` 与整车标定同口径；`curve.py` 的 `--points` 控制采样点数、`--step` 控制 CSV 的转速步长。四个入口都认 `--json` 与 `--list`。

JSON 的 `power_source.power_util` 是 `peak_net_power / peak_curve_power`，只衡量动力源内阻；它不代表轮端功率利用率或传动效率。

脚本算与不算的边界：

| 会算 | 不会算 |
|---|---|
| 整车质量、驱动轮数、轮半径、轮胎材质 | 动态手感（换挡、油门跟随） |
| 前向 `Cd·A`（各子零件气动点求和）、逐零件分解 | 游戏内遮挡折减：求和结果不含遮蔽，是阻力的上界 |
| 逐档 `τ_w`、牵引力、加速度、绑定约束 | 游戏内实测 |
| 极速（红线 + 功率平衡）、动力源净功率比 | 轮端峰值功率及真实传动效率 |
| 内燃机与电机两种曲线、功率带、削扭矩起点 | 混动：两者同时存在时只取内燃机 |
| 轮式与履带两种驱动端：车轮按占比折附着，履带按全车重量 | 履带接地压力分布与滑转：牵引力按均分估算 |
| 变速箱挡位 × 终传比 × 传动箱减速比，以及没有变速箱的单速车 | 各输出端减速比不一致时的转速/扭矩分化：按均值折算并点名 |

自检：`python scripts/test_scripts.py`，用 K17、2S38、MTLB 与 mini_ev 的真实数据做回归基线。

整车报告默认直接输出到对话。先给摘要：估算极速与绑定约束、曲线峰值功率、整备质量、单人运行质量、运行质量口径的功重比；再给约束残差、主要瓶颈和必要的明细。只有作者要把参数作为长期回归基线、交付内容包说明或团队协作记录时，才把完整标定卡片保存为文档；[标定卡片](references/calibration-card.md) 是可选模板。
