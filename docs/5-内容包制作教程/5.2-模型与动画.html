    5.2 模型与动画¶

    MachineMax 的零件模型使用基岩版 minecraft:geometry 格式（即 .geo.json 文件）。本章面向内容包作者，介绍模型从制作到在零件定义中引用的完整流程，不涉及代码实现细节。

    事前需要准备¶

    开始制作零件模型前，需要准备以下内容：

    • Blockbench（推荐）：用于创建和导出基岩版实体模型的建模工具，可从 blockbench.net 获取。
    • 基岩版实体模型（.geo.json 文件）：MachineMax 使用 Minecraft 基岩版的 minecraft:geometry 格式存储模型几何数据，格式版本至少需要 1.12.0。
    • 贴图文件（.png）：模型使用的纹理贴图资源，最终放入内容包的 textures/ 模块目录下。

    模型文件和贴图文件分别放入内容包的 models/ 和 textures/ 模块目录。在零件 JSON 中通过 model 和 textures 字段以 namespace:path 格式引用，详见 5.3 零件定义。

    比例与单位¶

    MachineMax 的模型坐标系统与基岩版实体模型保持一致。

    项目 对应关系
    1 格（block） 16 bb 单位（Blockbench 单位）
    X 轴 东—西/左—右方向（正值向东/右）
    Y 轴 上—下方向（正值向上）
    Z 轴 南—北/前—后方向（正值向南/后）
    原点 (0,0,0) 模型的几何中心，通常也是模型空间的原点

    游戏内 1 格等效于 1 米。但由于 Minecraft 玩家模型的实际高度约为 1.8 格，直接按 1:1 比例（现实 1 米 = 16 bb 单位）制作载具模型会在视觉上偏小。建议采用以下推荐比例：


    		 换算关系
    推荐比例 现实载具 1 米 ≈ 20 bb 单位
    内部单位统一 零件 JSON 中所有以米（m）、毫米（mm）为单位的参数仍以游戏内 1 格 = 1 米为基准

    使用推荐比例时，一辆现实约 4.3 米长的小型轿车在模型中约为 86 bb 单位（约 5.4 格），视觉上更符合玩家体型。

    推荐比例仅影响模型的视觉尺寸——零件 JSON 中的 mass（kg）、thickness（mm）、collision_height（m）、projected_area（m²）等物理参数仍按照游戏内 1 格 = 1 米的尺度填写。

    命名规范¶

    模型中的骨骼组（Bone）和定位器（Locator）的名称会被零件 JSON 或代码直接引用，因此推荐遵循统一的命名规范。

    元素 规范 示例
    骨骼组 大驼峰命名法 AllChassis、LeftSeatInteract
    定位器 蛇形命名法 mass_center、hull_mass_center 、left_front_wheel、chassis_left_door_axis

    模型的层次结构¶

    一个典型的零件模型采用以下骨骼层级：

    root / Root                  ← 根骨骼（pivot 在原点）
├── AllHull                  ← 主体结构骨骼，包含车壳、底盘等渲染用方块
│   ├── Hull                 ← 车壳渲染骨骼
│   ├── Chassis              ← 底盘渲染骨骼
│   │   └── locators:        ← 连接点/功能定位器（如 left_front_wheel）
│   ├── HullHitBoxes         ← 碰撞箱父骨骼（集中管理所有 HitBox 骨骼）
│   │   ├── HullHitBox       ← 车壳碰撞箱（空 UV 方块）
│   │   ├── EngineHitBox     ← 发动机碰撞箱
│   │   └── FrontGlass       ← 挡风玻璃碰撞箱
│   ├── HullInteract         ← 交互判定区父骨骼
│   │   ├── LeftSeatInteract ← 左座交互区
│   │   ├── RightSeatInteract← 右座交互区
│   │   ├── GloveBoxInteract ← 手套箱交互区
│   │   └── TrunkInteract    ← 后备箱交互区
│   └── locators:            ← 质心/属性定位器（如 hull_mass_center）
├── DoorLeft                 ← 左车门骨骼（可独立动画）
├── DoorRight                ← 右车门骨骼（可独立动画）
└── LeftFrontWheel           ← 左前轮骨骼（可独立旋转）

    这种层级并非强制要求，但将碰撞、交互和外观分离到不同骨骼组有利于维护。官方内容包中的模型均遵循此结构。

    模型必须包含的内容¶

    渲染用骨骼¶

    至少需要一组包含方块（Cube）的骨骼，用于零件的外观渲染。实际上，有方块且有 UV 贴图的骨骼即为渲染骨骼。所有未挂载子系统的骨骼默认参与渲染。

    碰撞箱骨骼（HitBox）¶

    每个子零件（SubPart）在 JSON 中的 hit_boxes 字段至少需要一个条目。hit_boxes 的键名必须与模型中的同名骨骼匹配，模组会读取该骨骼下的方块来生成碰撞形状。

    碰撞箱骨骼的方块需要满足以下要求：

    • 删除 UV 数据：在 Blockbench 中选中 Cube 后按 Alt + X（"删除 UV"操作），使该方块的 uv 字段为 {}。这样既能生成正确的碰撞体积，又能避免不必要的 UV 映射对渲染造成干扰。
    • 仅使用立方体：当前碰撞形状类型 box、sphere、cylinder、capsule 均基于方块（Cube）生成。其中 box 类型最稳定，推荐初次制作时优先使用。

    一个简单的碰撞箱骨骼在 .geo.json 中的示例：

    {
  "name": "HullHitBox",
  "parent": "HullHitBoxes",
  "pivot": [0, 0, 0],
  "cubes": [
    {
      "origin": [-20, -3, -28],
      "size": [40, 3, 56],
      "uv": {}
    },
    {
      "origin": [-17, 0, 24],
      "size": [34, 14, 17],
      "uv": {}
    }
  ]
}

    碰撞箱骨骼中的多个方块会组合成一个复合碰撞形状。方块的数量不宜过多——方块越多物理计算开销越大。建议用尽量少的方块覆盖零件的主要碰撞轮廓即可。

    碰撞箱骨骼下也可以放置定位器（Locator），用于标记碰撞发生时需要生成视觉特效的位置。

    模型的可选内容¶

    连接点定位器¶

    连接点（Connector）是零件与零件之间对接的接口。在模型中，每个对外连接点都需要一个定位器来标记它的位置和朝向。

    定位器的位置决定了连接点的世界坐标，定位器的旋转决定了连接点的初始朝向（两个对接的连接点的定位器朝向会在拼装时用于确定零件的安装姿态）。定位器名称需要与零件 JSON 中 connectors 条目下的 locator 字段匹配。

    以 kluo 车壳为例，其连接点定位器包含：

    定位器名 用途
    left_front_wheel 左前轮连接点
    right_front_wheel 右前轮连接点
    left_back_wheel 左后轮连接点
    right_back_wheel 右后轮连接点
    hull_front_bumper_left 前保险杠左连接点
    hull_front_bumper_right 前保险杠右连接点
    hull_left_door_axis 左车门铰链连接点（旋转轴）
    hull_left_door_lock 左车门锁扣连接点（固定）
    hull_trunk_door_axis 后备箱门铰链连接点
    hull_trunk_door_lock 后备箱门锁扣连接点
    hull_hood_axis 引擎盖铰链连接点
    hull_hood_lock 引擎盖锁扣连接点

    连接点定位器遵循蛇形命名，顺序为 先左右 → 再所属部件 → 再连接部件 → 再具体细节（如 hull_left_door_axis）。axis 类定位器标记铰链接口、lock 类定位器标记锁止接口。

    交互判定区骨骼（InteractBox）¶

    交互判定区用于定义玩家可以交互的区域，例如上车检测区、车门开关触发区、储物箱打开区等。交互区对应模型中的骨骼，模组会以该骨骼下方块（Cube）的包围盒作为交互判定体积。

    交互区骨骼通常放在一个统一的父骨骼下（如 HullInteract），并采用 <功能>Interact 的大驼峰命名：

    骨骼名 用途
    LeftSeatInteract 左座上车交互区
    RightSeatInteract 右座上车交互区
    GloveBoxInteract 手套箱（副驾储物）交互区
    TrunkInteract 后备箱交互区
    HullInteract 车壳交互区（父骨骼）

    交互区骨骼也需要方块，建议使用简单的立方体覆盖目标交互范围。在零件 JSON 中通过 interact_boxes 字段配置交互区的行为和信号路由。

    质心定位器¶

    质心定位器用于指定子零件的质量中心位置。模型中的定位器名与子零件 JSON 中的 mass_center 字段对应。支持以下方式：

    1. 在每个碰撞箱骨骼或定位器容器骨骼下放置 mass_center 定位器——该子零件的质心将取自此处。
    2. 在模型顶层（如 root 骨骼的 locators 对象中）放置 mass_center 定位器——作为整个零件的默认质心。
    3. 不放置任何 mass_center 定位器——此时模组会以子零件所有碰撞体积的形心（几何中心）作为质心。

    如果零件由多个子零件组成，建议为每个子零件分别指定质心定位器。常见模式是在 root 骨骼下声明一个基准 mass_center，然后在各部件的骨骼下以带前缀的形式声明（如 hull_mass_center、chassis_mass_center），并在零件 JSON 的 mass_center 字段中按需引用。

    各子系统所需的定位点¶

    部分子系统需要在模型中有对应的定位器来标记功能生效的位置。常见的有：

    子系统类型 所需定位点 用途
    seat 座位位置点（如 LeftFrontSeatPoint） 玩家乘坐时被传送到的位置
    lighting 灯光子系统所绑定的 HitBox 骨骼中的定位器 灯光发光的定位参考点
    气动计算（hydrodynamics） 不指定时使用质心；如需指定可填写任意已有定位器名 流体动力计算点，留空则使用质心

    子系统定位点的具体用法取决于对应子系统型号的定义。制作时可以参考官方内容包中已有零件的模型结构和子系统配置。

    多子零件模型的组织¶

    当一个零件包含多个子零件（如底盘 + 保险杠 + 车灯），建议将不同子零件的相关骨骼分组到各自的骨骼层级下。在零件 JSON 中通过 start_bone 和 end_bones 字段指定每个子零件对应的骨骼范围，详见 5.3 零件定义 中关于 sub_parts 的说明。

    动画¶

    MachineMax 支持基岩版骨骼动画（.animation.json）和动画控制器（.animation_controllers.json）。动画文件同样放置在内容包的 animations/ 和 animation_controllers/ 模块目录中。

    在零件 JSON 的 variants 中通过 animations 字段指定动画路径：

    "variants": {
  "model": "machine_max:kluo.geo",
  "animations": "machine_max:kluo",
  ...
}

    动画目标骨骼的名称必须与模型中的骨骼名称一致。关于动画资源和 Molang 表达式的详细内容将在 5.10 Molang表达式 中进一步展开。

    检查清单¶

    完成模型制作后，可以对照以下清单自查：

    • [ ] 模型格式为基岩版 minecraft:geometry，format_version ≥ 1.12.0
    • [ ] 骨骼组名称使用大驼峰，定位器统一使用蛇形命名
    • [ ] 至少有一组碰撞箱骨骼，其方块已删除 UV（uv: {}）
    • [ ] 碰撞箱骨骼的名称与零件 JSON 中 hit_boxes 的键名一致
    • [ ] 连接点的定位器名称与零件 JSON 中 connectors 的 locator 字段一致
    • [ ] 交互区的骨骼名称与零件 JSON 中 interact_boxes 的 bone 字段一致
    • [ ] （可选）已在对应骨骼下放置 mass_center 或其他子系统定位器
    • [ ] 贴图文件已放入 textures/ 目录并在零件 JSON 中正确引用
