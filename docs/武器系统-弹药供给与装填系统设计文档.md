# Machine-Max 弹药供给与装填系统 — 设计文档

> 状态：设计阶段
> 创建时间：2026-06-07
> 依赖：WeaponControllerSubsystem、LauncherSubsystem、ItemStorageSubsystem、EnergyGrid

---

## 一、背景与问题

Machine-Max 现有的武器系统已具备三个核心子系统——`WeaponControllerSubsystem` 负责目标跟踪与火控解算、`TurretDriverSubsystem` 驱动炮塔伺服机构、`LauncherSubsystem` 执行发射——形成了完整的观瞄-火控-发射链路。然而当前的 `LauncherSubsystem` 在发射时直接从静态属性 `projectile_type` 读取投射物类型并创建，没有膛内弹药状态，也没有弹药消耗与补充机制。这意味着每门炮拥有无限的、类型固定的弹药，无法模拟真实载具作战中的弹药管理与弹药选择行为。

同时，`AmmoLoaderSubsystem` 的类框架已于早期搭建，定义了 `magazineCapacity`（弹仓容量）、`roundByRound`（逐发压入 / 整体换弹匣双模式）、`reloadTimeTicks`（装填耗时）以及四个信号频道名，但完整的装填状态机、与 `LauncherSubsystem` 的交互逻辑、弹药消费与补充均未实现。

此外，并非所有武器都采用物理弹药。激光器、爆能束等能量武器直接从载具能量网格获取电能以"生成"光束弹药；某些街机风格的游戏设计中，导弹发射后可经过冷却时间凭空再生。当前设计中缺乏处理此类非物理弹药供给的抽象。

更进一步的复杂性来自弹药选择。一辆载具内可能安装多个弹药架（装弹机），各自容纳不同弹种（如 AP、HE），玩家应能在战斗中切换下一发使用的弹种——这要求武器控制器介入供弹路径的选择。

## 二、设计目标

本设计旨在完成弹药供给与装填系统的全面建模，达成以下目标：

1. **膛内弹药建模**：为 `LauncherSubsystem` 增加膛内弹药状态（`chamberedType`），发射、退弹、装填均围绕此状态展开，使发射器具备真实枪炮的闭锁-击发-退壳语义
2. **物理弹药供给**：实现 `AmmoLoaderSubsystem` 的完整装填状态机，支持逐发压入（火炮）与整体换弹匣（机炮）两种模式，与 `ItemStorageSubsystem` 联动读取弹药物品
3. **非物理弹药供给**：统一能量武器与再生武器为 `RegenLoaderSubsystem`，支持从 `EnergyGrid` 消耗电能生成弹药、或纯冷却时间驱动的免费再生
4. **弹药选择**：在 `WeaponControllerSubsystem` 中增加弹药选择能力，允许玩家切换供弹来源以改变下一发使用的弹种
5. **弹药链串联**：支持装弹机之间相互供给（如车体主弹仓 → 自动装弹机 → 发射器），通过 `IAmmoSupplier` 与 `IAmmoConsumer` 接口抽象完成多层次弹药输送
6. **接口驱动的松耦合**：发射器仅依赖接口，不关心供给来自物理弹药仓、再生电容还是其他装弹机，实现供给来源的可替换性

## 三、架构概览

### 3.1 核心接口

系统引入两个核心接口，构成弹药供应链的契约层：

```java
public interface IAmmoSupplier {
    // 查询
    boolean hasAmmo();
    int getRemainingCount();              // -1 = 无计数概念
    ProjectileType getSuppliedType();     // 当前将提供的弹药类型，null = 未准备好
    boolean isRoundByRound();
    int getReloadTimeTicks();
    boolean canSupplyMultiple();          // 是否允许多个消费者同时等待
    String getLabel();                    // HUD 弹种标签

    // 供给流程
    boolean requestRound(IAmmoConsumer consumer);
    boolean isRoundReady(IAmmoConsumer consumer);
    @Nullable ProjectileType consumeReadyRound(IAmmoConsumer consumer);
    // 退弹
    boolean canEject();
    void returnRound(ProjectileType type);
}

public interface IAmmoConsumer {
    boolean canAcceptAmmo();
    int getFreeCapacity();
    boolean receiveAmmo(ProjectileType type);
    @Nullable IAmmoSupplier getCurrentSupplier();
    List<IAmmoSupplier> getSuppliers();
    void setCurrentSupplier(int index);
}
```

接口设计中不传递冗余的 `tags` 参数（`ProjectileType` 自身已有 `getTags()`），弹药兼容性校验完全由消费者端在运行时逐发执行（§4.4）。`consumer` 参数存在于 `requestRound` / `isRoundReady` / `consumeReadyRound` 中，以支持单一供给者同时服务多个消费者（如一个电容为多个激光器供电）。

### 3.2 实现角色矩阵

| 类 | IAmmoSupplier | IAmmoConsumer | 说明 |
|---|---|---|---|
| `LauncherSubsystem` | — | ✓ | 膛内消费弹药，多供给者可选 |
| `AmmoLoaderSubsystem` | ✓ | ✓ | 持有 `SimpleContainer`（物理弹仓），可从上游取弹补充自身 |
| `RegenLoaderSubsystem` | ✓ | — | 再生/能量生成弹药，无物理容器，不消费外部弹药 |

### 3.3 类层次

```
BasicSubsystem
├── LauncherSubsystem         implements IAmmoConsumer
├── AmmoLoaderSubsystem       implements IAmmoSupplier, IAmmoConsumer
└── RegenLoaderSubsystem      implements IAmmoSupplier
```

### 3.4 数据流拓扑

以一辆典型战车为例，展示弹药从存储到发射的完整路径：

```
ItemStorageSubsystem (弹药物品)
    │ NBT 读取弹药类型
    ▼
AmmoLoader "车体主弹仓"
    │ IAmmoSupplier + IAmmoConsumer
    │ capacity=40, roundByRound=true, reloadTime=100tick
    │ canSupplyMultiple=false
    │
    ├── requestRound / consumeReadyRound ──→ AmmoLoader "自动装弹机"
    │       IAmmoSupplier + IAmmoConsumer
    │       capacity=5, roundByRound=false, reloadTime=10tick
    │       (自身无容器，弹药来自上游)
    │       │
    │       └── requestRound / consumeReadyRound ──→ LauncherSubsystem
    │               IAmmoConsumer
    │               膛容=1, chamberedType
    │
    └── (也可直接供给) ──→ LauncherSubsystem (跳过自动装弹机)

RegenLoaderSubsystem "激光电容"            RegenLoaderSubsystem "导弹架"
    │ IAmmoSupplier                          │ IAmmoSupplier
    │ energy_cost_per_round=500              │ energy_cost_per_round=0
    │ regen_per_minute=120                   │ regen_per_minute=2
    │ canSupplyMultiple=true                 │ canSupplyMultiple=false
    │                                        │
    ├── Launcher "主炮激光"                  └── Launcher "导弹发射管"
    └── Launcher "副炮激光"
```

## 四、调用上下文与线程安全

### 4.1 接口调用 vs 信号通信的互补关系

本系统引入 `IAmmoSupplier` / `IAmmoConsumer` 直接 Java 接口调用，与现有信号系统（`SignalChannel` / `sendCallbackToListener` / `getAcceptedChannels`）形成互补：

| 通信方式 | 适用场景 | 示例 |
|----------|----------|------|
| 信号频道 | 跨子系统松耦合、同一频道多接收者广播 | WCS 向 Launcher 发开火信号；WCS 向 TurretDriver 发角度信号 |
| 直接接口调用 | 握手后建立的紧耦合、1:N 但方法级精确调用 | Launcher 调用 `supplier.requestRound()`；Launcher 调用 `turret.computeAimAngles()` |

两类调用的共同前提是**握手已建立直接引用**。一旦握手完成，信号频道与直接调用均可使用——选择依据是"是否需要广播/松耦合"。弹药供给是典型的紧耦合场景（一发射器映射一当前供给者），直接接口调用更自然。

这并非混合架构的新问题：`WeaponControllerSubsystem` 已有先例——它通过信号频道下发 RotationSignal 给 TurretDriver，但同时**直接调用** `turret.computeAimAngles(target)` 和 `launcher.isAimedAt(target, tolDeg)`。直接方法调用在子系统间早已存在，本文档将这一模式规范化到弹药域。

### 4.2 线程安全契约

所有弹药接口调用均在**主线程**（20tps `onTick()` 中）发生：

- `LauncherSubsystem.fire()` 在 `onTick()` 中由开火信号触发
- `AmmoLoaderSubsystem` 的装填计时器在 `onTick()` 中推进
- 供给者握手中建立的直引用仅在主线程读写

因此无需 volatile、锁或 ConcurrentHashMap——所有弹药状态修改都是单线程的。

### 4.3 requestRound() 的非阻塞与幂等性

`requestRound(consumer)` 不是立即获得弹药，而是启动一个**非阻塞的装填计时器**。调用方需遵守以下契约：

1. **调用即启动**：调用后弹药进入准备中状态，`isRoundReady(consumer)` 初始返回 false
2. **幂等性**：连续两次调用 `requestRound(consumer)` 不应创建两个计时器。供给者内部维护一个 `reloadingConsumers` 集合，已存在的 consumer 再次调用时直接返回 true（不重复启动）
3. **仅就绪时可消费**：`consumeReadyRound(consumer, tags)` 仅在 `isRoundReady(consumer) == true` 时才能成功取走弹药；否则返回 null

Launcher 侧调用流程：

```
fire():
  if (chamberedType == null):
    supplier = suppliers.get(selectedSupplierIndex)
    if (supplier.isRoundReady(this)):
      ProjectileType offered = supplier.consumeReadyRound(this)
      if (canAccept(offered)):
        chamberedType = offered
      else:
        // 弹药不兼容 → 归还后切换到下一个供给者重新请求（仅一个supplier则继续从同一supplier取下一发）
        if (canEject()) returnRound(offered)
        if (suppliers.size() > 1):
          selectedSupplierIndex = (selectedSupplierIndex + 1) % suppliers.size()
          reloading = false
        supplier.requestRound(this)
        reloading = true
    else if (!reloading):
      supplier.requestRound(this)
      reloading = true
    if (chamberedType == null):
      return
```

`reloading` 标志由 Launcher 内部维护，当 `chamberedType` 被成功填充后清零。

### 4.4 运行时逐发兼容校验

弹药兼容性仅在**发射时逐发校验**，握手阶段不检查（弹药架在连接时可能为空，或后续被玩家替换弹药）。

`consumeReadyRound()` 取到弹药后，Launcher 运行 `canAccept(type)` 检查。若兼容则装膛；若**不兼容**：

- **有多个供给者**：自动切换到下一个供给者，向其 `requestRound()`。当前供给者的不兼容弹药不消耗（不取走，或取走后通过 `returnRound()` 归还）
- **仅有一个供给者**：丢弃不兼容弹药，从同一供给者 `requestRound()` 取下一发（弹仓 FIFO，下一发可能兼容）

供给者不负责兼容性校验——它只提供弹药，校验完全由消费者负责。`consumeReadyRound()` 不携带 `acceptedTags` 参数。

### 5.1 新增状态

`LauncherSubsystem` 新增以下实例字段——注意 `suppliers` 列表由供给者通过握手中的 `addSupplier()` 调用填充，Launcher 自身不发起握手：

```java
/** 膛内当前弹药类型。null = 空膛 */
private ProjectileType chamberedType;

/** 当前选中的供给来源索引（多供给时供 WCS 切换） */
private int selectedSupplierIndex = 0;

/** 由供给者握手中的 addSupplier() 填充的 IAmmoSupplier 列表 */
private final List<IAmmoSupplier> suppliers = new ArrayList<>();
```

### 5.2 发射流程变更

`LauncherSubsystem.fire()` 从现有的"直接读取静态属性"改为"使用膛内弹药"：

```
fire() 被 WeaponController 通过开火信号触发:
  │
  ├─ chamberedType == null?
  │     └─ YES → 尝试从 selectedSupplier 取弹
  │            ├─ isRoundReady() → offered = consumeReadyRound() → canAccept(offered)?
  │            │      YES → chamberedType = offered
  │            │      NO  → 归还弹药，切换到下一个供给者重新请求
  │            │             （仅一个供给者时继续从同一供给者取下一发）
  │            └─ 未在 reload 中 → requestRound() → 设置 reloading
  │
  ├─ chamberedType != null → 使用 chamberedType 创建投射物并发射
  └─ chamberedType = null（发射后清膛）
```

发射间隔仍由 `LauncherSubsystemStaticAttr.fire_rate` 控制（作为 `fireCooldown`），与装填延迟独立生效。

### 5.3 新增方法

```java
/** 判断此发射器是否可以装填指定弹药类型（使用静态属性的 required/acceptable/forbidden tags） */
public boolean canAccept(ProjectileType type);

/** 供 AmmoLoader 调用，装填一发弹药到膛内 */
public boolean loadRound(ProjectileType type);

/** 退膛：返回膛内弹药并清空。若当前供给者可接收退弹则归还，否则生成 ItemEntity 掉落在世界中 */
public ProjectileType ejectRound();
```

### 5.4 退弹行为

退弹时尝试归还给当前供给者：若 `getCurrentSupplier().canEject()` 为真，则调用 `returnRound()` 将弹药返还（AmmoLoader 弹仓+1；RegenLoader 可选择性支持）。若无法归还，则生成物品实体掉落于发射器 locator 的世界位置——当前阶段暂无弹药物品，此项留空。

## 六、AmmoLoaderSubsystem 装填状态机

### 6.1 两种装填模式

AmmoLoader 通过静态属性 `roundByRound` 区分两种工作模式：

**`roundByRound = false`（机炮 / 弹链供弹）：**

- `reloadTimeTicks` 仅在**切换供弹来源**时生效（换弹链延迟）。日常发射中，每发弹药的交付瞬时完成
- 典型场景：M2 勃朗宁的弹链、加特林的旋转供弹——弹链连续，换弹时才需要时间

**`roundByRound = true`（火炮 / 逐发压入）：**

- 每发弹药都需要等待 `reloadTimeTicks` 时间才能就绪
- 典型场景：T-34 的 76mm 炮——自动装弹机或装填手每次压入一发炮弹需要数秒

### 6.2 状态机

AmmoLoader 为每个消费者维护独立的输送计时器（Map<IAmmoConsumer, Integer>），支持 `canSupplyMultiple = true` 时同时向多个消费者输送弹药：

```
状态: IDLE
  │ 收到 Launcher/下游 AmmoLoader 的 requestRound(this)
  │
  ├─ internalAmmo > 0?
  │     ├─ YES → 进入 RELOADING(consumer, reloadTimeTicks)
  │     │
  │     └─ NO → 若有上游 supplier (串联模式):
  │                   requestRound(upstreamSupplier) → 等待上游 isRoundReady → consumeReadyRound → internalAmmo+1 → 然后 RELOADING
  │             若无上游且 roundByRound=false:
  │                   IDLE（机炮无弹即为空）
  │
  └─ RELOADING(consumer, remaining)
        │ 每 tick: remaining--
        │
        ├─ remaining == 0 → 弹药就绪
        │      isRoundReady(consumer) 返回 true
        │      consumeReadyRound(consumer) → internalAmmo-1
        │      回到 IDLE
        │
        └─ remaining > 0 → 继续倒数
```

### 6.3 串联模式

AmmoLoader 同时实现 `IAmmoSupplier` 和 `IAmmoConsumer`，使其既能向下游供弹，也能从上游取弹。串联握手由上游供给者发起——即"车体主弹仓"在握手时发现"自动装弹机"（也是一个 `IAmmoConsumer`），通过 `addSupplier()` 注册自身到下游装弹机。

当下游 AmmoLoader 弹仓容量未满时，可选择是否自动从上游请求补充（此行为由静态属性 `auto_request_upstream` 控制）。自身的 `receiveAmmo()` 方法负责将上游输送来的弹药存入内部容器。

### 6.4 自带弹药容器

AmmoLoader 自身持有 `SimpleContainer`（一维容器，尺寸由 `magazine_capacity` 直接决定，无需行列映射），作为弹药的物理载体。AmmoLoader 不实现 `MenuProvider`，不对玩家开放 GUI 交互——弹药放置通过自动化装填流程管理，而非手动操作。

容器与 ItemStorageSubsystem 的分工如下：

| 子系统 | 用途 | 容器 |
|--------|------|------|
| `AmmoLoaderSubsystem` | 专用于向发射器供弹，容量较小，按 FIFO 弹序输送 | 自身 `SimpleContainer` |
| `ItemStorageSubsystem` | 通用储物，大容量，玩家手动交互放置/取出物品 | 自身 `SimpleContainer` |

若未来需要"从货舱远程输弹到弹药架"的场景，可通过串联模式（§6.3）实现——将 ItemStorage 包装为 `IAmmoSupplier`（通过适配器或让 ItemStorage 直接实现接口），作为 AmmoLoader 的上游供给者。当前阶段暂不实现此联动，弹药直接放入 AmmoLoader 的容器中即可。

容器中的数据持久化（NBT 读写）复用 `SimpleContainer` 的标准序列化模式，与 `ItemStorageSubsystem.loadData()` / `saveData()` 逻辑一致。

## 七、RegenLoaderSubsystem 再生装弹机设计

### 7.1 统一能量与再生模型

能量武器与免费再生武器的本质区别仅在于 `energy_cost_per_round` 是否为 0，因此统一为 `RegenLoaderSubsystem`。

此外引入 `regenRoundByRound` 字段控制再生模式：

| `regenRoundByRound` | 行为 | 典型场景 |
|---|---|---|
| `true` | **随打随产**：弹药被消耗后立即开始再生下一发。`regen_per_minute` 表示每分钟恢复的弹药数量，`energy_cost_per_round` 表示每再生一发从 EnergyGrid 消耗的能量 | 激光电容——每次射击后电容自动充电，持续输出 |
| `false` | **批量产出**：弹仓完全打空后才开始再生，经过整段冷却时间后一次性回满至 `magazine_capacity`。`regen_per_minute` 语义为"每分钟可完成多少次完整装填"，`energy_cost_per_round` 在批量完成时一次性扣除总能量 | 街机导弹架——6 发全打完后冷却，一次性回满 6 发 |

> **注意**：批量产出模式下，只有弹仓**完全打空**（`ammoCount == 0`）才会触发再生。若剩 1 发未打完，永远不会触发。这是有意设计：街机风格的弹药架要求玩家清空弹仓才能获得"满弹奖励"；若希望支持"不满即补"行为，可将 `regenRoundByRound` 设为 `true`（随打随产）。

示例 JSON 配置：

```json
// 随打随产示例：激光电容
{
  "type": "machine_max:regen_loader",
  "definition": "machine_max:laser_capacitor",
  "magazine_capacity": 20,
  "regen_per_minute": 30,
  "regen_round_by_round": true,
  "energy_cost_per_round": 500,
  "projectile_type": "machine_max:laser_beam",
  "reload_time_ticks": 15,
  "can_supply_multiple": true
}

// 批量产出示例：街机导弹架
{
  "type": "machine_max:regen_loader",
  "definition": "machine_max:missile_rack",
  "magazine_capacity": 6,
  "regen_per_minute": 0.2,
  "regen_round_by_round": false,
  "energy_cost_per_round": 0,
  "projectile_type": "machine_max:atgm",
  "reload_time_ticks": 10,
  "can_supply_multiple": false
}
```

### 7.2 场景速查

| 场景 | `regen_per_minute` | `energy_cost_per_round` | `regenRoundByRound` | 行为描述 |
|------|--------------------|------------------------|---------------------|----------|
| 街机导弹 | 0.2 | 0 | false | 6 发打完 → 冷却 5 分钟 → 一次性回满 6 发，不耗能 |
| 激光炮 | 120 | 800 | true | 每秒最多生成 2 发激光弹药，每发从 EnergyGrid 扣 800 能量，随打随产 |
| 纯电容 | 0 | 0 | true | 静态弹仓，无自动再生，依赖外部补充 |

### 7.3 运行逻辑与能量访问

RegenLoader 的能量消耗是一次性的瞬时抽取（每再生一发或每批次完成时扣除），并非持续性电网负载。因此 RegenLoader 不实现 `IEnergyConsumer` 接口，而是直接持有 `EnergyGrid` 引用，调用 `grid.consumeEnergy(amount)` 瞬时抽取。

访问路径：通过 `getOwner().getSubsystemController().getVehicleCore().getEnergyGrid()` 获取 EnergyGrid 实例。

> `EnergyGrid.consumeEnergy(amount)` 为一次性瞬时抽取方法，与 tick 平衡中的持续负载互斥——不影响负载计算，返回值表示实际消耗量（可能小于请求量，当储能不足时）。

随打随产模式（`regenRoundByRound = true`）：

```java
// RegenLoaderSubsystem.onTick():
if (ammoCount < magazineCapacity) {
    regenProgress += regenPerMinute / 1200f;  // 20tick/s × 60s = 1200 ticks/min
    while (regenProgress >= 1.0f && ammoCount < magazineCapacity) {
        if (energyCostPerRound > 0) {
            if (!tryConsumeEnergy(energyCostPerRound)) break;  // 能量不足则暂停
        }
        ammoCount++;
        regenProgress -= 1.0f;
    }
}
```

批量产出模式（`regenRoundByRound = false`）：

```java
// RegenLoaderSubsystem.onTick():
if (ammoCount == 0 && !isBatchReloading) {
    isBatchReloading = true;
    int totalEnergyCost = (int)(magazineCapacity * energyCostPerRound);
    if (energyCostPerRound > 0 && !tryConsumeEnergy(totalEnergyCost)) {
        isBatchReloading = false;  // 能量不够，等下一 tick 再试
        return;
    }
    // 冷却时间 = 弹仓容量 / 每分钟再生次数 × 1200tick
    batchCooldownTicks = (int)(magazineCapacity / regenPerMinute * 1200);
}
if (isBatchReloading) {
    batchCooldownTicks--;
    if (batchCooldownTicks <= 0) {
        isBatchReloading = false;
        ammoCount = magazineCapacity;  // 一次性回满
    }
}
```

`tryConsumeEnergy()` 通过 `EnergyGrid` 消耗能量。若能量不足，再生暂停（progress 累积不丢失），待能量恢复后继续补弹。批量模式下若能量不够整批，等待直至充足后一次性扣除并开始冷却。

### 7.4 多消费者并发

当 `canSupplyMultiple = true` 时，RegenLoader 为每个消费者维护独立的输送计时器。多个发射器可同时从中取弹，共用同一个 `ammoCount` 弹仓。

## 八、弹药选择与 WeaponController 扩展

### 8.1 弹药选择流程

供给者在握手中通过 `addSupplier()` 注册到 Launcher 后，WeaponController 通过其握手中缓存的 `launchers` Map 直接获取 Launcher 引用，无需额外信号频道。当 `launcher.getSuppliers().size() > 1` 时，WCS 读取玩家弹种切换输入（来自 SeatSubsystem 透传的按键信号），直接调用 `launcher.setCurrentSupplier(newIndex)` 切换供弹来源。

若只有一个供弹来源，WCS 无需介入——Launcher 已在 `addSupplier()` 调用时自动选定该唯一来源。

### 8.2 切换时序

- 若旧供给者是 `roundByRound = true`（逐发），等待当前装填周期完成后才切换
- 若旧供给者是 `roundByRound = false`（弹链），立即触发换弹延迟（`reloadTimeTicks`）

切换发生时，如果旧供给者正在为 Launcher 装填中（`requestRound` 已调用但尚未 `consumeReadyRound`），采用**立即取消**策略：

1. Launcher 的 `reloading` 标志清除
2. 旧供给者内部取消该 consumer 的装填计时器（从 `reloadingConsumers` 中移除）
3. 供给者的弹药不减少（未被取走）

此策略简单且语义清晰——弹药尚未进入膛内，取消装填不造成任何损失。下次射击时将使用新供给者提供的弹药类型。

## 九、握手机制

### 9.1 供给者发现消费者

弹药链的握手方向为**供给者主动广播、消费者被动注册**。这与 WeaponController 驱动 TurretDriver/Launcher 的模式在方向上是相反的，原因在于弹药的来源具有高度多样性——弹药仓、电容、再生器、串联装弹机均可能成为供给者，而发射器（消费者）不应预先知晓所有可能的供弹者。

作为载具拼装游戏，玩家可能在载具上任意位置添加新的弹药架、激光电容或导弹再生仓。供给者主动发现消费者的模式使新增弹药来源能够自动找到载具内所有兼容的发射器，无需手动配置连接关系。装上即用。

### 9.2 握手流程与发现频道路由

供给者（AmmoLoader 或 RegenLoader）在 `onAttach` 与 `onVehicleStructureChanged` 时发起握手。消费者（Launcher、下游 AmmoLoader）需将供给者配置的发现频道名列入自身的 `getAcceptedChannels()` 返回值中，以使信号基础设施将发现信号路由到该子系统。

推荐的实践方案是约定一个众所周知的发现频道名（如 `ammo_discovery`），所有实现 `IAmmoConsumer` 的子系统将其加入 `getAcceptedChannels()`，所有 `IAmmoSupplier` 将其作为 `discovery_outputs` 的目标频道。这样新增弹药架时无需修改任何消费者的配置：

```java
// LauncherSubsystem.getAcceptedChannels():
public List<String> getAcceptedChannels() {
    List<String> channels = new ArrayList<>(attr.staticAttribute.getControlInputs());
    channels.add("ammo_discovery");  // 约定弹药发现频道
    return channels;
}
```

握手流程：

```
onAttach / onVehicleStructureChanged:

  AmmoLoader / RegenLoader (IAmmoSupplier):
    handShake() → 发送空信号到 discoveryOutputs 频道
    │
    └─ onSignalUpdated("callback", sender):
         │  基础设施自动回调：sender 即发出响应的子系统
         │
         ├─ sender instanceof LauncherSubsystem?
         │     └─ 直接建立连接：
         │          将 launcher 加入自己的 consumers 列表
         │          同时调用 launcher.addSupplier(this) 注册自身
         │          （若 launcher 此前只有 0 个 supplier → 自动选定本 supplier）
         │          （若 launcher 有多个 supplier → WCS 介入弹种选择）
         │
         │      * 握手时不检查兼容性：连接时弹药架可能为空，或只装了暂不兼容的弹药（玩家后续可能替换）。兼容性校验推迟到运行时逐发执行（§4.4）。
         │
         └─ sender instanceof AmmoLoaderSubsystem（下游串联装弹机）?
               └─ 将下游装弹机加入 consumers 列表
                   同时调用下游装弹机的 setCurrentSupplier(this)
                   下游装弹机也可作为 IAmmoSupplier 继续向下握手
```

### 9.3 Launcher 侧的被动注册

Launcher 不主动发起弹药握手，仅实现 `IAmmoConsumer` 暴露 `canAccept()` / `addSupplier()` 供供给者调用：

```java
// LauncherSubsystem 新增：
private final List<IAmmoSupplier> suppliers = new ArrayList<>();

/** 由供给者在握手中调用，注册自身到发射器的可选弹种列表中 */
public void addSupplier(IAmmoSupplier supplier) {
    suppliers.add(supplier);
    if (suppliers.size() == 1) selectedSupplierIndex = 0;
}

/** 由供给者在握手中调用，检查发射器是否可以装填该供给者的弹药 */
public boolean canAccept(ProjectileType type) {
    return attr.staticAttribute.isAmmoCompatible(type);
}
```

此设计使 Launcher 对弹药来源完全透明——它只知道自己有若干可用的供给者，每个供给者通过 `IAmmoSupplier` 接口提供弹药。无论新增什么类型的弹药架，Launcher 代码无需改动。

### 9.4 与 WeaponController 握手的关系

两套握手并行且互不冲突：

| 握手 | 发起方 | 发现对象 | 触发时机 |
|------|--------|----------|----------|
| WCS 火控握手 | WeaponController | TurretDriver, Launcher | onAttach, onVehicleStructureChanged |
| 弹药链握手 | AmmoLoader, RegenLoader | Launcher, 下游 AmmoLoader | onAttach, onVehicleStructureChanged |

WCS 在弹药域的唯一职责是弹种选择：多供给者时，WCS 通过已有的 `launchers` 直接引用调用 `launcher.setCurrentSupplier(index)` 切换弹种。单一供给者时 WCS 完全不介入。

## 十、JSON Schema 扩展

### 10.1 AmmoLoaderSubsystemStaticAttr 精简

在现有字段基础上移除四个信号频道（已改为 IAmmoSupplier 直接方法调用），保留纯硬件参数与行为配置：

> **破坏性变更**：`ammo_request_channel`、`ammo_response_channel`、`ammo_consumed_channel`、`reload_channel` 四个字段从静态属性中移除。当前处于开发阶段，`AmmoLoaderSubsystem` 尚未被任何内容包实际使用，无向后兼容负担。静禬属性构造器与 CODEC 同步修改。

`getAcceptedChannels()` 返回值也相应调整——AmmoLoader 不再需要监听弹药请求信号频道（弹药通信改为直接接口调用），仅需包含发现频道名：

```java
// AmmoLoaderSubsystem.getAcceptedChannels():
public List<String> getAcceptedChannels() {
    List<String> channels = new ArrayList<>();
    channels.addAll(attr.discoveryOutputs.keySet());  // 握手发现的回调频道名
    return channels;
}
```

```json
{
  "type": "machine_max:ammo_loader",
  "definition": "machine_max:autoloader",
  "round_by_round": false,
  "magazine_capacity": 5,
  "reload_time_ticks": 10,
  "can_supply_multiple": false,
  "auto_request_upstream": true
}
```

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `round_by_round` | bool | `false` | `true`=逐发压入；`false`=弹链供弹 |
| `magazine_capacity` | int | `30` | 弹仓容量 |
| `reload_time_ticks` | int | `200` | 装填耗时（tick）。roundByRound=false 时仅在切换供给来源时生效 |
| `can_supply_multiple` | bool | `false` | 是否允许多消费者同时等待 |
| `auto_request_upstream` | bool | `true` | 弹仓未满时是否自动向上游请求补充 |

已移除的字段：`ammo_request_channel`、`ammo_response_channel`、`ammo_consumed_channel`、`reload_channel`——弹药请求与消耗均改为 `IAmmoSupplier` / `IAmmoConsumer` 接口的直接方法调用，不再走信号频道。

### 10.2 AmmoLoaderSubsystemAttr（动态属性）

只需增加握手发现频道，与 WeaponController 的 `control_outputs` 模式一致：

```json
{
  "type": "machine_max:ammo_loader",
  "definition": "machine_max:autoloader",
  "discovery_outputs": {
    "ammo_discovery": ["subpart"]
  }
}
```

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `discovery_outputs` | `Map<String, List<String>>` | `{}` | 握手发现频道→目标列表。AmmoLoader 向这些频道发送空信号，通过回调发现同载具内的 IAmmoConsumer |

### 10.3 RegenLoaderSubsystemStaticAttr 新增

`RegenLoaderSubsystem` 是全新的子系统类型，需要以下注册条目：

- `SubsystemTypes.REGEN_LOADER` 枚举值
- `RegenLoaderSubsystemStaticAttr` 类（extends `BasicSubsystemStaticAttr`，含本文定义的字段与 CODEC）
- `RegenLoaderSubsystemAttr` 类（extends `BasicSubsystemDynamicAttr`，含 `discoveryOutputs` 字段与 CODEC）
- 在静态/动态属性分发表中注册对应的 CODEC
- `SubsystemType` JSON 常量：`"machine_max:regen_loader"`

| 字段 | 类型 | 默认值 | 说明 |
