## 一、背景与动机

现有投射物系统（阶段一/二）聚焦纯动能弹丸，`ProjectileType` 为单一扁平结构，所有字段由 `RecordCodecBuilder` 平铺定义。随着武器种类的扩展，需要支持：

| 需求 | 说明 |
|------|------|
| **制导弹药** | 导引头（红外/雷达/激光）+ 制导律（比例导引/纯追逐） |
| **引信多样化** | 碰炸 / 定时 / 命中后延时 / 近炸，支持时间装订与保险 |
| **战斗部效果** | 首期实现原版爆炸，后续复用通用 Effect 扩展破片、点燃等效果 |
| **光束武器** | 脉冲激光（瞬时），持续照射激光（连续伤害），距离衰减穿深模型 |
| **数据驱动** | 内容包创作者通过 JSON 定义全部参数，无需 Java 代码 |
| **向后兼容** | 现有 `point` / `rigid` JSON 无需修改 |

核心设计决策：

- **按运动模型分派 Codec（dispatch）**：质点/刚体与光束采用不同类型和管理器。
- **静态 Attr 与运行时实例分离**：Codec 只构建配置，投射物实例持有有状态的引信和 Trigger。
- **直接命中、引信和战斗部解耦**：终点弹道负责穿深/伤害与载体去留，引信负责起爆时机，战斗部是通用 Effect 列表。
- **热路径零分配**：100Hz 物理 tick 不创建临时 Context、集合或向量对象。

## 二、类型体系：Codec Dispatch 分派

### 2.1 顶层设计

`ProjectileType` 从具体类变为 **abstract class**，通过 `Codec.dispatch()` 按 `"type"` 字段分派到子类：

```
ProjectileType (abstract, dispatch on "type")
│
├── KineticProjectileType     ← type: "point" | "rigid"
│   │   运动模型：飞行弹丸
│   │   管理器：ProjectileManager（物理线程 SoA）
│   │   发射器：LauncherSubsystem
│   │   有代理实体 (MMProjectileEntity)
│   │   速度-伤害幂函数模型
│   │
│   └── 可组合的行为组件：
│       seeker? / guidance? / fuze? / warhead[]
│
└── RayProjectileType        ← type: "pulse" | "beam"
    │   运动模型：射线（瞬时或持续照射）
    │   管理器：RayManager（主线程）
    │   发射器：RayLauncherSubsystem
    │   无代理实体
    │   距离衰减穿深/伤害模型
    │
    └── 当前阶段不支持 seeker / guidance / fuze / warhead
```

### 2.2 Codec 实现

```java
public static final Codec<ProjectileType> CODEC = Codec.STRING.dispatch(
    "type",
    ProjectileType::getSerializedName,
    name -> switch (name) {
        case "point", "rigid" -> KineticProjectileType.CODEC;
        case "pulse", "beam"  -> RayProjectileType.CODEC;
        default -> throw new IllegalArgumentException("未知投射物类型: " + name);
    }
);
```

- `point` / `rigid` / `pulse` / `beam` 是 JSON 中的用户可见字符串
- `point` 和 `rigid` 路由到同一个 `KineticProjectileType`（内部 `ProjectileTypeEnum` 区分）
- `pulse` 和 `beam` 路由到同一个 `RayProjectileType`（内部 `RayAttr.durationSeconds` 区分）

### 2.3 共享字段

所有 `ProjectileType` 子类保留这些平级字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `tags` | `List<ResourceLocation>` | 弹药标签，与发射器的 required_tags / acceptable_tags / forbidden_tags 匹配 |
| `maxLifetime` | float | 最大存活时间（秒），对光束为燃料/持续时间上限 |
| `bulletNum` | int | 单发弹丸数 |
| `visual` | VisualProperties (子类化) | 视觉属性 |
| `sounds` | ProjectileSoundAttr (子类化) | 音效属性 |

## 三、KineticProjectileType — 飞行弹丸

### 3.1 字段结构

```java
public class KineticProjectileType extends ProjectileType {
    ProjectileTypeEnum typeEnum;              // POINT / RIGID
    ExternalProperties external;              // 质量、阻力、重力、初速...
    TerminalProperties terminal;              // 速度-穿深/伤害模型
    @Nullable SeekerAttr seeker;              // 导引头
    @Nullable GuidanceAttr guidance;          // 制导律
    FuzeAttr fuze;                            // 引信静态配置；JSON 缺失时解码为默认碰炸
    List<WorldEffect> warhead;                // 战斗部效果列表；空列表表示纯动能
    VisualProperties visual;
    ProjectileSoundAttr sounds;
}
```

### 3.2 ExternalProperties

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `mass` | 必填 | 质量（kg） |
| `gravity_factor` | 1.0 | 重力系数 |
| `drag_factor` | 0 | 空气阻力系数 |
| `radius` | 0.05 | 碰撞半径（m） |
| `base_velocity` | 必填 | 参考速度（m/s） |
| `base_accuracy_mil` | 5.0 | 精度（密位） |
| `restitution` | 0.0 | 恢复系数；质点用于跳弹速度保持，刚体传给 Bullet 刚体 |

`restitution` 对质点和刚体采用同一语义，但执行方式不同：质点手动计算反射速度，刚体调用 `body.setRestitution()`。若未来需要真实滚动，还需为刚体增加非零摩擦系数；本阶段不纳入。

### 3.3 TerminalProperties

| 字段 | 默认值 | 说明 |
|------|--------|------|
| `base_penetration` | 必填 | 参考速度下穿深（mm RHA） |
| `base_damage` | 必填 | 参考速度下伤害 |
| `penetration_velocity_coefficient` | 0 | 穿深速度系数（德马尔≈1.43） |
| `damage_velocity_coefficient` | 0 | 伤害速度系数 |
| `block_damage_factor` | 1.0 | 方块破坏因子 |
| `discard_on_blocked` | true | 无法穿透且引信未接管载体时，是否移除投射物 |

速度-伤害模型：`effective = base × (speed / baseVelocity)^coefficient`（系数为 0 时退化常数）

`discard_on_blocked=false` 时：

- 质点投射物进入 `STOPPED` 状态：停在命中点、速度归零、不再执行射线碰撞，但继续寿命和引信 tick。
- 刚体投射物保留 Bullet 碰撞响应，继续弹跳或运动。
- 若引信已经进入延迟起爆状态，则无论该字段为何值，均由引信保留载体直到起爆。

运行时命中结果不能继续只用 `destroyed + newVelocity` 表达，至少需要区分：

```java
public enum ProjectileMotionResult {
    REMOVE,
    CONTINUE_WITH_VELOCITY,
    STOP,
    KEEP_RIGID_RESPONSE
}
```

## 四、行为组件设计

### 4.1 SeekerAttr — 导引头

决定投射物**如何获取目标位置**。`seeker` 字段缺失 → 纯弹道飞行。

```java
public record SeekerAttr(
    /// 导引头类型
    SeekerType type,
    /// 视场角（度）
    float fovDegrees,
    /// 锁定距离（米）
    float lockRange,
    /// 最大跟踪角速率（度/秒）
    float maxTrackRateDps,
    /// 最小热对比度（仅红外有效）
    float minContrast,
    /// 是否抗诱饵（仅红外有效）
    boolean rejectFlares
) {
    public enum SeekerType {
        INFRARED,            // 被动红外
        RADAR,               // 主动雷达
        SEMI_ACTIVE_LASER,   // 激光半主动（需外部照射）
        TV,                  // 电视（昼间）
        COMMAND,             // 无线电指令（外部指引）
    }
}
```

### 4.2 GuidanceAttr — 制导律

决定**如何根据目标位置修正飞行路径**。`guidance` 缺失 → 无制导。

```java
public record GuidanceAttr(
    /// 制导律类型
    GuidanceLaw law,
    /// 导航增益（比例导引用）
    float navigationGain,
    /// 最大横向加速度（m/s²，0=无限制）
    float maxLateralAcceleration
) {
    public enum GuidanceLaw {
        PROPORTIONAL_NAVIGATION,  // PN（比例导引）
        AUGMENTED_PN,             // APN（增广比例导引）
        PURE_PURSUIT,             // 纯追逐
        LEAD_PURSUIT,             // 前置追逐
    }
}
```

### 4.3 FuzeAttr — 引信

决定**何时解除保险、何时触发、何时真正起爆**。引信不是互斥枚举，而是保险条件与多个 Trigger 的组合：

```java
public record FuzeAttr(
    float timeSafetySeconds,
    List<FuzeTriggerAttr> triggers
) {}
```

对应 JSON：

```json
"fuze": {
  "time_safety": 0.2,
  "triggers": [
    { "type": "delay", "default_delay": 5.0 },
    { "type": "proximity", "radius": 4.0 }
  ]
}
```

保险语义固定如下：

- `time_safety < 0`：不使用时间保险。
- `time_safety >= 0`：根据发射时的绝对物理 tick 计算 `armingPhysicsTick`。
- 当前物理时间到达 `armingPhysicsTick` 后永久解除保险，不会重新上保险。
- 保险不维护逐步累加的 elapsed 字段，只比较绝对截止时间。
- Trigger 的截止时间可以早于保险解除时间，但不得提前起爆；若定时已经到期，则在解除保险的物理步立即触发。

时间保险已经能够覆盖当前防止近距离自伤的需求。距离保险与其职责高度重叠，而且需要额外维护累计路程，首期不实现；未来若出现严格的离膛距离、旋转圈数或加速度保险需求，再单独引入可组合的 ArmingCondition。

多个 Trigger 是 **OR** 关系，任一 Trigger 最终请求起爆即可。首期提供三种 Trigger：

#### 4.3.1 DelayFuzeTrigger — 出膛后定时

```json
{ "type": "delay", "default_delay": 5.0 }
```

- `default_delay` 是没有外部装订时使用的秒数。
- 运行时保存绝对 `detonationPhysicsTick`，不逐物理步累加倒计时。
- 同一个引信允许存在多个 `delay` Trigger；一次装订会修改全部 `delay` Trigger。
- `delay` 从出膛时刻开始计时，不从解除保险时刻开始计时。
- 创建或重新装订时按 `launchPhysicsTick + delaySeconds × physicsTps` 计算截止时间。

#### 4.3.2 HitDelayFuzeTrigger — 命中后延时

```json
{
  "type": "hit_delay",
  "sensitivity_rha": 5.0,
  "delay": 0.03
}
```

- 只有命中目标的有效 RHA 大于等于 `sensitivity_rha` 才触发。
- `delay` 是固定命中后延迟，不接受外部装订。
- 首次符合条件的命中锁存 Trigger，后续命中不重置倒计时。
- `sensitivity_rha=0` 且 `delay=0` 即标准碰炸引信。
- 命中时按 `hitPhysicsTick + delaySeconds × physicsTps` 计算绝对起爆时间。
- Entity 命中的 RHA 可沿用现有 pending 主线程伤害管线；请求中保留原始命中点、速度和 `hitPhysicsTick`，RHA 决议后再调用 `fuze.onHitResolved(...)`。若截止时间已经过去，则立即起爆。

#### 4.3.3 ProximityFuzeTrigger — 近炸

```json
{ "type": "proximity", "radius": 5.0 }
```

- 使用物理世界扫掠查询检测本物理步内进入半径的目标，避免高速弹丸在离散 tick 中穿过目标。
- 首期至少排除投射物自身和已死亡目标；发射者与同载具过滤在 owner/source vehicle 体系补齐后实现。
- 若查询能够给出命中分数，则以最近接近点作为起爆计算起点。

#### 4.3.4 Attr 与运行时 Trigger

沿用项目现有的 Attr → 运行时对象模式：Codec 构建 Attr，Attr 负责分派，运行时 Trigger 构造器直接接受对应 Attr。

```java
public abstract class FuzeTriggerAttr {
    public abstract MapCodec<? extends FuzeTriggerAttr> codec();
    public abstract FuzeTrigger createTrigger();
}

public final class DelayFuzeTriggerAttr extends FuzeTriggerAttr {
    private final float defaultDelay;

    @Override
    public FuzeTrigger createTrigger() {
        return new DelayFuzeTrigger(this);
    }
}

public final class DelayFuzeTrigger extends FuzeTrigger {
    private final DelayFuzeTriggerAttr attr;
    private float configuredDelaySeconds;
    private double detonationPhysicsTick;

    public DelayFuzeTrigger(DelayFuzeTriggerAttr attr) {
        this.attr = attr;
        this.configuredDelaySeconds = attr.getDefaultDelay();
    }
}

public abstract class FuzeTrigger {
    public void physicsTick(FuzePhysicsContext context) {}
    public void mainTick(Level level, IProjectile projectile) {}
    public void onHitResolved(FuzeHitSnapshot hit, float effectiveRha) {}
}
```

`FuzeAttr` 中保存 `List<FuzeTriggerAttr>` 以便 Codec 解码；运行时 `Fuze` 在构造时转换为固定的 `FuzeTrigger[]`，100Hz 热路径使用索引循环，不创建迭代器。

`Fuze` 创建完成后使用 `launchPhysicsTick` 和 `physicsTps` 为每个 `DelayFuzeTrigger` 按其 `default_delay` 初始化绝对截止时间；后续火控装订只重新计算这些截止时间。

#### 4.3.5 Fuze 生命周期与载体销毁

```text
SAFE → ARMED → TRIGGERED → DETONATED
```

- `SAFE`：保险未解除，Trigger 不得起爆。
- `ARMED`：保险解除，Trigger 可以触发。
- `TRIGGERED`：已触发但尚未到起爆时刻；延迟引信在此状态保留载体。
- `DETONATED`：确定精确起爆位置、提交战斗部 Effect、移除投射物。
- 瞬发引信在同一物理步内从 `ARMED` 直接进入 `DETONATED`。
- 引信进入 `TRIGGERED` 后接管载体销毁；尚未触发时，仍由 `discard_on_blocked` 决定载体去留。
- `max_lifetime` 始终保留为硬清理上限，避免哑弹永久存在。

JSON 缺少 `fuze` 时，加载后规范化为 `sensitivity_rha=0, delay=0` 的默认 `HitDelayFuzeTrigger`，即标准碰炸；运行时无需传播 `null`。

`Fuze` 构造时记录 `launchPhysicsTick`，并计算：

```text
armingPhysicsTick = time_safety < 0
    ? launchPhysicsTick
    : launchPhysicsTick + time_safety × physicsTps
```

运行时只比较当前绝对物理时间与 `armingPhysicsTick`，不维护 `elapsedSeconds`。

#### 4.3.6 零分配物理上下文

每个 `Fuze` 构造一次可复用的 `FuzePhysicsContext`。`Level` 和 `IProjectile` 引用在构造时固定，每个物理步只覆写 primitive 字段：

```java
public final class FuzePhysicsContext {
    private final Level level;
    private final IProjectile projectile;

    private PhysicsLevel physicsLevel;
    private double physicsTick;
    private float physicsTps;
    private float px, py, pz;
    private float vx, vy, vz;

    public FuzePhysicsContext(IProjectile projectile) {
        this.projectile = projectile;
        this.level = projectile.getLevel();
    }

    public void reset(PhysicsLevel physicsLevel,
                      double physicsTick, float physicsTps,
                      float px, float py, float pz,
                      float vx, float vy, float vz) {
        this.physicsLevel = physicsLevel;
        this.physicsTick = physicsTick;
        this.physicsTps = physicsTps;
        this.px = px;
        this.py = py;
        this.pz = pz;
        this.vx = vx;
        this.vy = vy;
        this.vz = vz;
    }
}
```

- 物理 tick 不创建 record、数组、集合或 `Vector3f`。
- `FuzePhysicsContext` 仅在物理线程使用，Trigger 不得在调用结束后保留其可变快照。
- 需要主线程处理的数据使用单独的命中/效果快照，不跨线程读取该 Context。
- 引信可以区分 `physicsTick` 与 `mainTick`：绝对时间比较、近炸和精确起爆位置尽量在物理线程完成；Minecraft Entity/Block 世界修改提交主线程。
- `physicsTick` 使用 `double`，整数部分表示物理步编号，小数部分表示步内时间，从而保留短于单步的延迟。

#### 4.3.7 亚步长起爆位置

质点和刚体共享同一线性外推逻辑。100Hz 物理步长内忽略重力和阻力误差：

```text
stepEndTick = physicsTick + 1.0

if detonationPhysicsTick <= stepEndTick:
    offsetTicks = clamp(detonationPhysicsTick - physicsTick, 0.0, 1.0)
    offsetSeconds = offsetTicks / physicsTps
    detonatePos = stepStartPos + stepVelocity × offsetSeconds
```

- 出膛定时只比较 `detonationPhysicsTick` 是否落入当前物理步，不递减剩余时间。
- 截止时间因保险或主线程 pending 已经落后于当前物理步时，`offsetTicks` 钳制为 0，在当前步起点立即起爆。
- 命中后延迟从命中点开始，使用碰撞后速度外推。
- 延迟小于一个物理步时不等待下一 tick，直接使用预测位置起爆。
- 物理线程确定的位置作为不可变快照提交主线程，主线程不得再次从已移除投射物读取位置。

#### 4.3.8 火控时间装订

`FireCommand` 直接携带装订时间，负数表示不装订、使用 JSON `default_delay`：

```java
public record FireCommand(
    @Nullable Vector3f direction,
    float correctionAngleDeg,
    boolean firing,
    float fuzeDelaySeconds        // < 0 = 不装订
) {}
```

装订发生在物理线程真正击发时，而不是主线程将弹药放入 `pendingFires` 时：

```text
WeaponController.onPrePhysicsTick
→ 使用最新物理结果计算/接收 fuzeDelaySeconds
→ 写入 FireCommand
→ LauncherSubsystem.fireSingle 读取最新 FireCommand
→ type.fire() 创建投射物
→ 对本次创建的所有投射物调用 programFuzeDelay(...)
```

```java
public boolean programFuzeDelay(float delaySeconds) {
    boolean changed = false;
    for (int i = 0; i < triggers.length; i++) {
        if (triggers[i] instanceof DelayFuzeTrigger delay) {
            delay.program(delaySeconds, launchPhysicsTick, physicsTps);
            changed = true;
        }
    }
    return changed;
}
```

`type.fire()` 与装订调用位于同一物理线程调用栈中，不会在两者之间插入投射物物理步，因此无需额外同步。

### 4.4 WorldEffect — 通用世界效果

`warhead` 直接是 `List<WorldEffect>`，不再额外包装 `WarheadAttr`，也不使用互斥 `WarheadType`。空列表表示纯动能投射物。

首期仅实现标准原版爆炸：

```json
"warhead": [
  {
    "type": "machine_max:vanilla_explosion",
    "power": 4.0,
    "causes_fire": false,
    "interaction": "block"
  }
]
```

`WorldEffect` 是可注册的 Codec 分派类型，可复用于投射物起爆、油箱/弹药架等子系统摧毁及未来脚本效果：

```java
public interface WorldEffect {
    MapCodec<? extends WorldEffect> codec();
    void apply(EffectContext context);
}
```

不为 Entity、Block、`DestroyableObject` 提供多组 `apply` 重载，也不额外包装 Attribution/Target 层级。当前所需信息直接展平到一个上下文：

```java
public record EffectContext(
    Level level,
    Vec3 origin,
    Vec3 velocity,

    @Nullable Entity directEntity,
    @Nullable Entity ownerEntity,
    @Nullable DestroyableObject sourceObject,

    @Nullable Entity targetEntity,
    @Nullable DestroyableObject targetObject,
    @Nullable BlockPos targetBlockPos
) {}
```

- 空爆时三个 target 字段均为 null。
- Entity 命中设置 `targetEntity`；载具零件等 BF 对象设置 `targetObject`；地形命中设置 `targetBlockPos`，由 `Level + BlockPos` 共同表示目标。
- `directEntity` 对应直接载体，如已创建的 `MMProjectileEntity`；`ownerEntity` 对应射手/操作者，即原版 DamageSource 的 causing entity。
- `sourceObject` 对应触发效果的投射物、油箱、弹药架或其他 `DestroyableObject`。
- 投射物当前尚缺少 owner 实体字段，后续应作为 `PointProjectile` / `RigidProjectile` 构造参数传入，并同步给代理 Entity。
- 首物理步起爆时代理 Entity 可能尚未创建，因此 `directEntity` 必须允许为 null；owner 仍可用于原版伤害归属。
- 原版爆炸、Entity 状态和方块修改必须提交主线程；未来生成 Machine-Max 子投射物的 Effect 可在物理线程执行。
- 不让各 Effect 自行决定线程切换，由统一 Effect 执行器根据效果类型调度，保证位置快照和错误处理集中。

### 4.5 组件运行时架构

```text
ProjectileType（资源重载时构建，共享只读）
├── SeekerAttr?
├── GuidanceAttr?
├── FuzeAttr
│   └── List<FuzeTriggerAttr>
└── List<WorldEffect> warhead

IProjectile（每发弹药实例）
├── Fuze
│   ├── FuzeState
│   ├── FuzeTrigger[]
│   └── FuzePhysicsContext（每发一个，可复用）
└── 位置/速度权威值仍由 ProjectileManager SoA 或 Bullet 刚体维护
```

Seeker/Guidance 的无状态计算仍可使用 static logic；Fuze/Trigger 因包含保险、倒计时和触发状态，必须使用每发弹药独立的运行时实例。

### 4.6 默认行为

| 缺失组件 | 默认行为 |
|----------|----------|
| 无 `seeker` | 纯弹道飞行（不跟踪目标） |
| 无 `guidance` | 无路径修正 |
| 无 `fuze` | 规范化为零延迟碰炸引信 |
| 无 `warhead` / 空列表 | 仅执行直接动能命中，不产生额外世界效果 |

## 五、RayProjectileType 概览

详见配套文档 `武器系统-光束系统详细设计.md`。本节仅列出与 `KineticProjectileType` 的关键区别：

当前阶段光束系统只实现直接射线命中、穿深和伤害模型，**不支持引信和战斗部 Effect**。未来若光束需要点燃或特殊命中逻辑，应另行设计 `beam_hit_effects`，不复用有实体载体语义的 Fuze。

| 维度 | KineticProjectileType | RayProjectileType |
|------|----------------------|-------------------|
| JSON key | `"point"`, `"rigid"` | `"pulse"`, `"beam"` |
| 运动模型 | 飞行弹丸（位置 + 速度矢量） | 线段（起点 + 方向 + 长度） |
| 时间模型 | 瞬时命中 | pulse=瞬时，beam=持续 |
| 终效模型 | 速度-伤害幂函数 | 等效距离线性衰减 |
| 管理器 | `ProjectileManager`（物理线程） | `RayManager`（主线程） |
| 发射器 | `LauncherSubsystem` | `RayLauncherSubsystem` |
| 代理 Entity | 有（`MMProjectileEntity`） | 无 |
| 可用组件 | seeker / guidance / fuze / warhead | 当前无行为组件 |
| 穿深消耗 | 无（残余速度衰减） | 有（穿透 RHA 消耗等效距离预算） |

### 5.1 RayAttr — 射线外弹道属性

射程、精度、半径、持续时间、油耗统一在 `RayAttr` 中。JSON 字段名 `external`，与 kinetic 共用：

```java
public record RayAttr(
    float maxRange,            // 最大射程（米）
    float radius,              // 射线半径（米），用于子采样密度计算
    float nearRange,           // 无衰减区间（米），0 = 立即衰减
    float durationSeconds,     // 0=pulse, >0=burst, -1=continuous
    float ammoPerSecond,       // 连续模式油耗（burst/pulse 无效）
    float baseAccuracyMil,     // 基础精度（密位），0 = 完美精准
    float accuracyDriftTime    // 回归半衰期（秒）
) {
    public boolean isPulse()     { return durationSeconds <= 0; }
    public boolean isBurst()     { return durationSeconds > 0; }
    public boolean isContinuous(){ return durationSeconds < 0; }
}
```

### 5.2 BeamTerminalProperties

JSON 字段名 `terminal`，与 kinetic 共用。Java 类不同，Codec dispatch 分派。

**等效距离——统一能量预算模型：**

```
等效距离 = 实际传播距离 + Σ(已穿透RHA × rhaToDistanceRatio)
穿深/伤害 = nearPenetration/damage → 线性插值 → farPenetration/damage
```

| 字段 | 说明 |
|------|------|
| `near_penetration_mm` | 零距离（nearRange 内）穿深 |
| `far_penetration_mm` | maxRange 处穿深 |
| `near_damage` | 零距离伤害 |
| `far_damage` | maxRange 处伤害 |
| `rha_to_distance_ratio` | 1mm RHA 等效多少米射程 |

## 六、管理器与发射器对应关系

```
ProjectileType 类型
│
├── KineticProjectileType (point / rigid)
│   │
│   ├── 发射器: LauncherSubsystem (现有，实现 IAmmoConsumer)
│   │   └── 膛内弹药 (chamberedType) → pendingFires → 物理线程 fireSingle()
│   │
│   └── 管理器: ProjectileManager (现有，物理线程)
│       └── SoA 数组，半隐式 Euler 积分 + rayTest
│       └── 有 MMProjectileEntity 代理
│       └── 通过 objId 访问 IProjectile 上的 Fuze 运行时实例
│
└── RayProjectileType (pulse / beam)
    │
    ├── 发射器: RayLauncherSubsystem (新增，实现 IAmmoConsumer)
    │   ├── pulse: consumeReadyRound() → 瞬时扫描 → RayManager 处理
    │   ├── burst: consumeReadyRound() → 创建 BeamInstance(durationTicks>1)
    │   └── continuous: consumeReadyRound() → 创建 BeamInstance(continuous)
    │                    → 持续消耗燃料 → 耗尽时 consumeReadyRound() 补充
    │
    └── 管理器: RayManager (新增，主线程)
        └── SoA 管理所有活跃 BeamInstance
        └── 每 tick 扫描 + 穿透判定 + 伤害
        └── 无代理 Entity，直接渲染
```

### 6.1 Kinetic 击发与时间装订

`pendingFires` 仍只负责将待发射弹种从主线程交给物理线程，不保存装订时间。`LauncherSubsystem.fireSingle()` 在物理线程读取当时最新的 `FireCommand`：

```text
主线程：消耗膛内弹药 → pendingFires.add(projectileType)
物理线程：pendingFires.poll()
        → 读取最新 FireCommand.fuzeDelaySeconds
        → 使用最新枪口/平台物理状态创建投射物
        → 若 delay >= 0，对本次创建的全部投射物执行 programFuzeDelay(delay)
```

这保证时间装订使用实际击发时的最新物理结果，而不是主线程上一 tick 的距离或速度快照。

### 6.2 射速与持续时间正交

`RayLauncherSubsystem` 可同时持有多个 `BeamInstance`——射速不受光束持续时间限制：

```
Tick 0:  击发 → Beam#1 (burst, 3s)
Tick 0.05: 再次击发 → Beam#2 (burst, 3s)
          → #1 和 #2 同时在 RayManager 中活跃
Tick 3:  #1 到期
Tick 3.05: #2 到期
```

### 6.3 弹药框架兼容

两者均实现 `IAmmoConsumer`，共享 `AmmoLoaderSubsystem` 弹药供给：

- `LauncherSubsystem`: `consumeReadyRound()` → 1 发 → 1 次 fire
- `RayLauncherSubsystem`: `consumeReadyRound()` → 1 发 → pulse 或 N ticks 燃料
