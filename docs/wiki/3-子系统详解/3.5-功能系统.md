# 3.5 功能系统

功能系统负责补足载具“能开”之外的那部分体验。它们通常不直接决定车辆的加速、转向或抓地力，而是负责人与载具的交互、车内外的视觉反馈、储物能力，以及为内容包扩展预留接口。

与前面的动力系统、传动系统、行驶系统相比，功能系统更像是把一堆“能动的零件”组织成一辆真正可用的车。对深度玩家来说，这一类子系统主要影响上车、视角、交互和使用便利性；对 UGC 作者来说，它们决定座舱如何把输入送到控制链、灯光如何表现、储物空间如何放置，以及哪些位置可以作为扩展入口。

本节主要讨论当前版本中最常用、也最适合面向玩家和内容包作者展开的几类功能子系统：

- **座舱（`seat`）**
- **控制组（`control_group_preset`）** — 座舱的附属配置，决定按键如何映射为信号
- **照明（`lighting`）**
- **物品存储（`item_storage`）**
- **摄像头（`camera`）与瞄准镜（`sight`）**
- **自定义脚本（`javascript`）**

武器相关子系统（`weapon_controller`、`launcher`、`ammo_loader`、`regen_loader`）已独立成章，见 [3.8 武器系统](3.8-武器系统.md)。

像 `joint`、`turret`、`signal_convert` 这类偏专用或仍在扩展中的类型，本节在末尾补充提及，具体字段和配置方式仍以 [5.5 子系统定义](../5-内容包制作教程/5.5-子系统定义.md) 为准。

## 功能系统在整车中的位置

功能系统最常见的职责，可以概括为四类：

- **乘员交互**：决定玩家坐在哪里、能看到什么、按键会发给谁；
- **状态呈现**：决定车灯、HUD、乘员可见性等表现层内容；
- **容器与使用性**：决定载具能否提供手套箱、后备箱等储物空间；
- **扩展接口**：为内容包作者提供视角锚点、脚本钩子和特种机构的挂载位置。

它们和其他系统的关系通常不是“替代”，而是“把别的系统接起来”。例如：

- 座舱本身不负责开车，但它负责把玩家输入发送给车辆控制器；
- 照明本身不提供推进力，但它会决定夜间驾驶时的视觉效果；
- 储物子系统不影响速度，却会直接影响载具在生存模式中的实用性。

## 座舱系统：玩家与载具的主入口

座舱子系统是功能系统里最核心的一类。它不仅提供乘坐位置，还负责把玩家操作变成系统可用的信号。

### 座舱负责什么

从行为上看，一个 `seat` 子系统通常同时承担以下工作：

- 提供一个可进入的乘坐点；
- 维护当前乘客占用状态；
- 让乘客附着在对应子零件实体上；
- 将移动、视角和常规按键输入发送给控制器或其他目标；
- 决定该座位允许哪些视角，以及乘员是否允许继续使用物品。

这意味着座舱不是单纯的“装饰位”。如果驾驶位没有把 `move_outputs` 和 `regular_outputs` 正确连到控制器，即使玩家成功坐进车里，也可能根本无法驾驶。

### 驾驶位与乘客位的区别

在实际内容包中，驾驶位和乘客位通常会共用同一种 `seat` type，但动态连接关系不同。

最常见的差异是：

- **驾驶位**：会配置 `move_outputs`、`regular_outputs`、`aim_outputs`，把输入转发给车辆控制器或经连接点继续转发；
- **乘客位**：通常只保留乘坐和占用状态输出，不接入驾驶控制链。

官方内容包里这两类用法都很典型：

- `default_seat` 常用于驾驶位；
- `default_passenger_seat` 常用于副驾或后排乘客位。

对 UGC 作者来说，最重要的不是“这个模型看起来像驾驶位”，而是它有没有真正接入控制链。

### 视角与乘坐体验

座舱还是当前版本里最直接的视角控制入口。它可以决定：

- 是否启用第一人称；
- 是否启用第三人称；
- 第三人称镜头离车多远；
- 镜头俯仰与偏航的可转动范围；
- 是否跟随载具姿态；
- 是否聚焦载具中心；
- 是否叠加专用 HUD。

对深度玩家来说，这部分直接影响驾驶舒适度。例如：

- 第三人称距离太近，会让大型载具难以观察周边；
- 俯仰限制太紧，会让越野或坡道环境中的视野受限；
- 偏航范围太小，会明显限制“回头看”的能力。

对内容包作者来说，驾驶体验往往不是由单个字段决定，而是由**座位位置、视角偏移、镜头限制、车辆尺寸**共同塑造的。

### 允许使用物品与乘员可见性

`seat` 还会影响两个很容易被忽略的使用层细节：

- `allow_use_items`：决定乘客在乘坐时是否还能进行使用物品、打开物品栏等原版动作；
- `render_passenger` / `passenger_scale`：决定乘员是否显示，以及显示时的缩放方式。

这些选项尤其适合以下场景：

- 需要让玩家在乘坐时操作手持工具、武器或辅助物品；
- 需要隐藏乘员模型，以匹配封闭式驾驶舱、机甲或特殊座舱；
- 需要缩放乘员模型，使其与特殊驾驶位比例更协调。

### 玩家视角下最常见的问题

如果座舱配置不合理，玩家通常会直接感受到以下问题：

- 上车后无法控制车辆；
- 视角过低、过高或被模型遮挡；
- 下车位置别扭，或者在高速移动时体验突兀；
- 某些座位看起来能坐，但实际上只是摆设。

其中前两类问题，往往不是行驶系统本身的问题，而是座舱没有把“人”和“控制链”正确接起来。

## 照明系统：主要负责视觉反馈

照明子系统的定位很明确，它主要负责客户端视觉表现，而不是改变世界中的实际光照规则。

### 照明系统能做什么

当前版本的 `lighting` 更接近“体积光 / 光效节点”，而不是原版意义上的发光方块。它适合用于：

- 前照灯；
- 尾灯、刹车灯；
- 雾灯、辅助灯；
- 仪表或装饰性光源。

对玩家来说，它影响的是“看起来亮不亮、照出来的效果像不像”，而不是直接修改区块亮度。

### 点光与光束

照明子系统支持两种常见光型：

- **`point`**：更适合泛光、尾灯、舱内灯等向周围扩散的光源；
- **`beam`**：更适合前灯、探照灯等具有明确方向性的光束。

这两者的选择，会直接影响玩家对载具用途的感知。即使只是同一个车头模型，若前灯全部改成点光，观感也会很不一样。

### 亮度、范围与耐久的关系

照明系统常见的调节参数包括：

- 光照范围；
- 光照颜色；
- 光照强度；
- 光束角度。

此外，照明子系统仍然有自己的耐久和摧毁状态。这意味着它不仅是视觉节点，也可以作为一个会损坏的功能部位。对玩家来说，这会形成很自然的战损反馈：车还能开，但灯可能已经坏了。

### 对内容包作者的设计建议

灯光系统最容易出现的问题，不是字段写错，而是“节点摆得不对”。通常建议优先检查：

- `locator` 是否准确位于灯具实际位置；
- 左右灯是否成对布置；
- 尾灯、刹车灯、雾灯是否需要拆成不同子系统；
- 某些只是装饰玻璃的部位，是否其实应使用 `basic` 而不是 `lighting`。

如果只是想保留部件损坏差分，而不需要真实光效，也可以像官方部分内容那样，用无功能子系统或低强度灯光节点来表达。

## 物品存储系统：提升生存和长期使用价值

物品存储子系统提供的是标准容器能力。它的作用非常直接，就是把载具的一部分空间变成可交互的物品栏。

### 物品存储的基本行为

`item_storage` 主要有三种玩家能直接感受到的表现：

- 与对应交互区域互动时，可以打开容器界面；
- 容量由行列数决定；
- 当子系统被拆卸或摧毁时，内部物品会掉落出来。

最后这一点很重要，因为它决定了储物空间既方便，也有风险。对生存模式玩家来说，载具不是“绝对安全的跨维度背包”，而是一个会受损、会被拆、会把内容物暴露出来的实体容器。

### 常见用途

在官方内容包里，`item_storage` 常用于：

- 手套箱；
- 后备箱；
- 车内小型储物格。

这些部位通常不会接入复杂信号链，但会明显提升一辆载具的实用性，尤其是长途移动、工程运输或联机协作场景。

### 容量设计的取舍

虽然 `rows` 和 `columns` 很简单，但它们实际对应的是玩法定位：

- 小容量更适合作为手套箱、工具格；
- 中等容量适合作为日常车辆收纳；
- 大容量则更接近运输车、补给车或工程车的玩法定位。

如果容量设计过大，载具很容易变成低风险的大型移动仓库；如果容量过小，则可能让交互成本高于实用收益。这里更适合按“车型定位”来定，而不是机械地追求更大。

## 摄像头系统：炮镜视角、稳定器与变焦

摄像头子系统（`camera`）并非简单的"额外视角挂点"——它是载具实现精密观瞄的基础设施。摄像头挂载在子零件的 locator 位置上，玩家通过按键切换到炮镜视角后，画面从该 locator 位置出发，遵循摄像头自身定义的视场角和视角限制，独立于座舱的驾驶视角运行。

### 三轴稳定模式

摄像头通过两个独立的布尔开关——`verticalStabilized`（垂直稳定）和 `horizontalStabilized`（水平稳定）——组合出四种稳定模式：

| 垂直稳定 | 水平稳定 | 效果 |
|:---:|:---:|------|
| 关 | 关 | **完全无稳**。炮镜固定在零件上，随车体晃动而晃动。二战坦克的潜望镜式体验——车体颠簸，镜中画面跟着跳，瞄准点也随之漂移。 |
| 开 | 关 | **仅垂稳**。俯仰方向自动补偿车体起伏，但水平方向仍随车体偏航。适合仅需稳定纵向瞄线的场景。 |
| 关 | 开 | **仅水平稳**。偏航方向自动补偿车体转向，俯仰方向固定。 |
| 开 | 开 | **双轴稳定**。镜中画面完全独立于车体晃动——现代主战坦克的陀螺稳定器效果。炮手看到的画面始终稳定在瞄准点上，即使车体在崎岖地形上剧烈颠簸。 |

稳定器的工作原理是在客户端每渲染帧执行：从上一帧的世界瞄准点反算当前帧所需的俯仰和偏航角，以补偿 locator 位置与朝向的变化。由于稳定运算在客户端 60fps+ 渲染帧中执行（而非服务端 20tps），画面平滑无跳变。当玩家退出炮镜视角后，双稳模式下的摄像头会持续跟踪最后的世界瞄准点——这意味着下次切回炮镜时，十字线仍指向同一位置。

### 变焦与视场角

摄像头通过三个参数控制放大倍率：

- **`baseFov`**：基准视场角（度），即 1× 变焦时的 FOV。值越小画面越"拉近"（如 10° 对应约 7× 放大）。
- **`baseZoom`**：最小变焦倍率，通常为 1.0。
- **`maxZoom`**：最大变焦倍率，如 8.0 表示可放大至 8 倍。

玩家通过按键一键切换基准倍率与最大倍率，变焦过程采用指数衰减平滑过渡，过渡速度与帧率无关——无论在 20fps 还是 144fps 下，变焦的视觉流畅度一致。若未绑定切换按键，摄像头支持连续缩放模式，适合需要精细调节倍率的观瞄场景。

### 视角限位

摄像头定义了俯仰和偏航方向的转动范围：

- **`minPitch` / `maxPitch`**：俯仰角上下限（度），正值向上、负值向下。典型的坦克炮镜俯仰范围为 ±8°。
- **`yawLimit`**：偏航张角（度），实际范围为 `[center - limit/2, center + limit/2]`。例如设为 10 表示水平方向 ±5° 的观察窗口。

视角限位仅在炮镜模式下生效——它决定了炮手能在多宽的范围内转动视角来搜索和跟踪目标。限位角度越小，炮镜的"隧道视野"感越强，也更接近真实装甲车辆的潜望镜/炮镜体验。

### 目标跟踪模式

目标跟踪（TRACKING）是摄像头的运行时状态，而非静态配置。当外部信号源（雷达、数据链或脚本）向摄像头的 `trackingTargetInputs` 频道写入目标世界坐标后，摄像头自动转入跟踪模式——镜头持续锁定该坐标，等效于双轴稳定加目标追踪。信号消失后，摄像头退回原本的稳定配置。在跟踪模式下，玩家仍可通过鼠标微调瞄准点以叠加提前量偏移。

### 多摄像头切换

一辆载具可以挂载多个摄像头子系统实例——例如车长周视镜和炮手炮镜。玩家通过按键循环遍历所有可用的摄像头（由 `allowCycle` 控制是否参与循环），每个摄像头独立维护自身的稳定设置、变焦状态和视角限位。

### 瞄准镜系统

瞄准镜子系统（`sight`）继承自摄像头子系统，在摄像头全部功能之上增加了炮镜标尺等瞄准辅助特性。它与武器控制器和发射器协同工作，为玩家在瞄准模式下提供距离刻度和弹道参考线。对于需要精密射击的载具，瞄准镜是实现精确火力投射的关键组件。

## 自定义脚本系统：面向 UGC 的高级扩展口

脚本子系统是功能系统里最开放的一类。它允许内容包作者把一段 JavaScript 逻辑挂到载具上，在运行时响应 tick、碰撞、信号更新等事件。

### 它适合解决什么问题

当现成子系统无法覆盖目标行为时，脚本子系统通常可以作为补充。例如：

- 根据多个输入信号组合出特殊逻辑；
- 控制一套自定义状态机；
- 处理某种专用互动规则；
- 在多个脚本子系统之间交换自定义数据。

从实现上看，它几乎可以介入子系统生命周期的多个阶段，因此扩展能力很强；但这也意味着它更适合已经熟悉现有系统边界的内容包作者，而不是一上来就拿它代替标准子系统。

### 什么时候不该先用脚本

如果一个目标已经能用现有子系统清晰表达，通常仍然建议优先用内置类型，例如：

- 乘坐与输入转发，优先用 `seat`；
- 灯光效果，优先用 `lighting`；
- 容器，优先用 `item_storage`；
- 动力和行驶行为，优先用对应的动力链与控制链。

脚本更适合作为“补充”，而不是“先把一切都塞进脚本里”。这样后续维护成本会低得多。

关于脚本字段和 API 入口，仍建议与 [5.10 Molang表达式](../5-内容包制作教程/5.10-Molang表达式.md) 配合阅读。

## 控制组：按键到信号的翻译层

控制组（`control_group_preset`）不是一种独立的子系统 type，而是挂载在座椅子系统上的 JSON 预设配置。它的职责是将玩家的键盘、鼠标和手柄输入翻译为载具内部可用的信号——座舱负责"玩家能坐进去"，控制组负责"坐进去后按键能干什么"。

### 控制组解决什么问题

默认情况下，一个座舱生成后并不知道玩家按下 W 键应该产生什么效果。是前进？是爬升？控制组通过以下机制将按键映射为信号：

- **控制模式（`control_mode`）**：决定按键的基础语义。`ground` 模式下 W/S 对应油门/刹车，A/D 对应转向；`plane` 模式下 W/S 对应俯仰，A/D 对应横滚；`ship` 和 `mech` 各有独立映射。
- **信号路由（`move_targets` / `view_targets` / `regular_targets`）**：决定移动输入、视角输入和常规按键分别发送到哪个频道、哪些目标。
- **离散绑定（`bindings`）**：将特定按键（如鼠标左键、R 键、数字键）映射到自定义信号频道。支持 PRESS（按下发送）、HOLD（按住持续发送）和 TOGGLE（切换状态）三种动作类型。

### 两级控制组与角色切换

每个座位拥有一个始终激活的**基础控制组**（`base_group`）和一组可选的**子控制组**（`groups`）。基础控制组由内容包作者预设，子控制组允许玩家在同一座位上切换不同角色——例如驾驶员可以在"行驶"和"武器操作"模式之间切换，前者将按键映射到油门和转向，后者将鼠标映射到炮塔。

### 对内容包作者的意义

控制组预设定义在内容包的 `control_groups/` 目录下，通过座椅子系统的 `control_group_preset` 字段引用。官方内置了 `default_driver`（驾驶员）、`default_passenger`（乘客）、`default_gunner`（炮手）和 `default_commander`（车长）等预设，内容包作者可以直接使用或参照创建自定义预设。

一个典型的驾驶员控制组预设如下：

```json
{
    "base_group": {
        "name": "base",
        "control_mode": "ground",
        "move_targets": { "move_input_p1": ["global"] },
        "view_targets": {},
        "regular_targets": { "regular_input_p1": ["global"] },
        "bindings": []
    }
}
```

炮手控制组则会将鼠标左键绑定到开火信号：

```json
{
    "base_group": {
        "name": "base",
        "control_mode": "inherit",
        "view_targets": { "aim_input_p1": ["global"] },
        "bindings": [
            {
                "trigger": "key.mouse.left",
                "action": "hold",
                "channel": "fire_input_p1",
                "targets": ["global"]
            }
        ]
    }
}
```

控制组还支持 **GUI 交互元素**（`gui_actions`）——在 AUI 载具控制面板上显示的按钮、开关和滑块。这些元素不占用物理按键，适合配置不常用的功能（如灯光模式切换、差速锁开关等）。三种 GUI 元素类型为：PULSE（点击按钮）、TOGGLE（勾选框）和 SLIDER（滑动条）。

控制组预设的完整配置格式与字段说明见 [5.9 辅助模块](../5-内容包制作教程/5.9-辅助模块.md) 中的控制组预设定义一节。

## 其他功能系统的定位

本章开头列出的功能系统里，还有几类更偏专用用途的子系统：

- **`joint`**：驱动高级连接点的旋转或平移，适合机械结构、舱盖、机构件、炮塔底座等；
- **`turret`**：服务于炮塔与武器控制链的方位-俯仰双轴伺服；
- **`signal_convert`**：用于信号翻译、转名和延迟控制。

这些类型确实属于功能系统的一部分，但其中多数（特别是炮塔类）需要与武器控制器、发射器等子系统配合才能发挥完整效用，对深度玩家的直接上手理解门槛更高，也更依赖具体内容包设计。因此本节不再展开行为细节，后续在撰写武器、特种机构或复杂交互专题时再单独细化会更合适。

## 对深度玩家有用的观察点

如果你主要从使用体验来理解功能系统，可以重点观察下面这些问题：

- 驾驶位是否真正接入了控制链，而不是只有乘坐外观；
- 视角是否符合车辆定位，例如跑车、卡车、摩托、工程车的镜头需求并不一样；
- 灯光节点是否只是装饰，还是会随部件损坏而失效；
- 储物空间是偏便利性，还是带有明确的风险与取舍；
- 载具是否提供了额外视角或特殊互动方式；
- 武器系统是否完整——发射器、装弹机和控制器是否都正确挂载并连通信号。

这些内容不一定像动力链那样决定“能不能开”，但它们往往决定“这辆车用起来像不像一辆完整的车”。

## 对内容包作者有用的组织思路

如果你正在规划一辆可长期使用的载具，功能系统通常建议按下面的顺序考虑：

1. 先确定驾驶位和乘客位分别在哪里，哪些座位需要输出控制信号。
2. 再确定灯光、手套箱、后备箱等功能部位是否要独立成子系统。
3. 如果需要武装，确定武器控制器、发射器、装弹机（或再生装弹机）和瞄准镜的挂载位置与信号链路。
4. 最后再考虑是否需要额外摄像头、脚本或特种机构。

这样做的原因很简单：

- 座舱决定整辆车是否“可操作”；
- 照明和储物决定整辆车是否“好用”；
- 武器系统决定整辆车是否“有战斗力”；
- 摄像头、脚本和特种机构决定整辆车是否“有特色”。

如果一开始就从脚本或特种功能倒推，很容易把基础交互链路做得很乱。

## 与 5.5 的分工

本节主要回答的是：

- 这些功能子系统在玩家视角下分别做什么；
- 它们在整车里通常承担什么角色；
- 内容包作者该如何理解它们的使用边界。

而 [5.5 子系统定义](../5-内容包制作教程/5.5-子系统定义.md) 负责回答的是：

- 每种子系统有哪些静态参数；
- 每种子系统有哪些动态参数；
- 这些参数在 JSON 里该怎么写。

如果你已经知道自己要做驾驶位、尾灯或后备箱，那么本节帮你确认结构思路；接下来真正落地到内容包时，再回到 5.5 对照字段即可。
