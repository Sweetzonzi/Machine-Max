# 5.9 辅助模块

在前几章中，我们已经介绍了零件、子系统、模板、蓝图与配方等核心数据。本章继续说明几类"不直接决定载具结构或物理表现，但会显著影响玩家体验"的辅助模块：物品说明文本、自定义 HUD、色板、语言文件，以及与之配套的图标和贴图资源。

这些模块的共同特点是：它们主要作用于**显示层**。对于 UGC 作者来说，这一层决定了玩家在物品栏、制造台、研究台和驾驶界面中看到什么、如何理解你的内容包，以及能否快速分辨不同零件和整车方案。

> 本章主要面向 UGC 作者实际会接触到的配置与资源组织方式，不展开底层渲染或代码实现细节。

## 本章涉及的模块

| 模块名      | 主要用途                                              | 玩家可见位置                                  |
| ---------- | --------------------------------------------------- | ----------------------------------------- |
| `tooltips` | 为蓝图、装配体以及部分配方提供悬浮说明文本                    | 物品栏悬浮提示、制造台配方详情                     |
| `colors`   | 定义可复用的文本色板，供 `tooltips` 等文本样式引用             | 蓝图/装配体说明文本中的颜色                         |
| `huds`     | 定义驾驶 HUD 的模型、动画、文本与布局                     | 乘坐座椅后的第一人称/第三人称驾驶界面               |
| `control_groups` | 定义控制组预设，决定按键如何映射为载具信号               | 驾驶时玩家的按键响应行为                           |
| `lang`     | 提供名称、本地化描述、HUD 文本、交互提示等翻译内容             | 几乎所有文字显示位置                              |
| `textures` | 提供图标、HUD 贴图等视觉资源                              | 物品图标、HUD 面板、零件贴图等                    |

---

## 辅助模块的协作关系

辅助模块通常不会单独使用，而是和蓝图、装配体、子系统与贴图资源配合工作。

- `blueprints/` 和 `assemblies/` 可以通过 `tooltip` 字段引用 `tooltips/` 中的描述文件，并通过 `icon` 字段引用 `textures/` 中的图标。
- `tooltips/` 中的文本通常不会直接写完整说明，而是引用 `lang/` 中的翻译键，再通过样式标签叠加颜色、字体和强调效果。
- `huds/` 中定义的是 HUD 本体；真正决定它何时显示的是座椅子系统 `views` 中的 `first_person_hud` 和 `third_person_hud` 字段。详见 [5.5 子系统定义](5.5-子系统定义.md)。
- `control_groups/` 中定义的是控制组预设；真正激活它的是座椅子系统的 `control_group_preset` 字段。
- `colors/` 为文本样式提供统一的颜色别名，便于多个说明页面共用同一套视觉规范。

---

## 物品说明文本（tooltips/）

`tooltips/` 模块用于为蓝图物品、装配体物品以及部分配方详情提供说明文本。它最直接影响玩家在物品栏中查看载具内容时获得的信息量。

### 文件位置

```text
spark_modules/
└── my_pack/
    └── my_mod/
        └── tooltips/
            ├── my_sports_car.html
            └── my_truck.html
```

文件名（含扩展名）就是该说明文本的资源路径末尾部分。例如 `tooltips/my_sports_car.html` 会以 `my_mod:my_sports_car.html` 的形式被引用。

### 在蓝图与装配体中引用

蓝图与装配体 JSON 可以通过 `tooltip` 字段引用说明文本：

```json
{
  "$schema": "../docs/zh_cn/schemas/blueprint.schema.json",
  "template": "my_mod:my_sports_car",
  "tooltip": "my_mod:my_sports_car.html",
  "icon": "my_mod:textures/icon/sports_car.png"
}
```

如果不填写 `tooltip`，该物品仍可正常使用，但鼠标悬停时不会显示额外说明。

### 文本格式

`tooltips/` 中的文件虽然扩展名为 `.html`，但并不是浏览器 HTML 页面，而是一种**简化的类 HTML 富文本格式**。每一行会被解析为一条 Minecraft 提示文本，常见写法如下：

```html
<bold><c.9BE868><f.yahei>title.my_mod.blueprint.sports_car</f.yahei></c.9BE868></bold>
<f.yahei>description.my_mod.blueprint.sports_car</f.yahei>

<italic>notes.my_mod.blueprint.example</italic>

<bold>author.my_mod.blueprint.sports_car</bold>
```

上面的示例可以概括为四种常见信息：

- 标题：通常使用加粗和强调色
- 简介：一到两行简要说明该载具或模块的定位
- 备注：可选，用于补充来源、用途或示例说明
- 作者信息：可选，适合注明模型作者、贴图作者等信息

### 支持的常用标签

| 标签              | 作用                                           |
| ----------------- | ---------------------------------------------- |
| `<bold>`          | 加粗                                           |
| `<italic>`        | 斜体                                           |
| `<underline>`     | 下划线                                         |
| `<strike>`        | 删除线                                         |
| `<obfuscated>`    | 混淆文本效果                                   |
| `<br>`            | 换行                                           |
| `<t>`             | 插入缩进                                       |
| `<c.xxxxxx>`      | 直接指定十六进制颜色，例如 `<c.FF8800>`        |
| `<c.palette_key>` | 使用 `colors/` 模块中定义的颜色别名             |
| `<f.font_name>`   | 使用指定字体资源                               |

> 为了保持各页面风格统一，建议优先使用少量固定样式组合，不要在同一份说明中混用过多颜色和字体。

### 与语言文件的关系

`tooltips/` 文件中的正文通常写的是**翻译键**，而不是最终显示的自然语言句子。例如：

```html
<bold>title.my_mod.blueprint.sports_car</bold>
```

对应的实际文本放在 `lang/zh_cn.json` 或 `lang/en_us.json` 中：

```json
{
  "title.my_mod.blueprint.sports_car": "示例运动型小车",
  "description.my_mod.blueprint.sports_car": "一辆用于演示内容包结构的紧凑型载具。",
  "author.my_mod.blueprint.sports_car": "模型作者：YourName"
}
```

这种写法有两个好处：

- 同一份说明结构可以方便地支持多语言
- 文案修改只需要调整语言文件，不必改动富文本结构

### 玩家会在哪里看到这些说明

- 在物品栏中悬停查看内容包蓝图或装配体时
- 在部分制造界面的配方详情区域中
- 在使用同一物品定义生成的创造模式物品时

因此，`tooltips/` 最适合承载的是**简洁的识别信息**，而不是过长的背景故事。建议优先写清楚载具类型、用途、特点与作者来源。

## 色板（colors/）

`colors/` 模块用于定义可复用的颜色方案，主要服务于说明文本等界面元素的样式控制。

### 文件位置

```text
spark_modules/
└── my_pack/
    └── my_mod/
        └── colors/
            └── common.json
```

### 基本结构

色板文件本质上是一个字符串到颜色值的映射表。一个简化示例如下：

```json
{
  "colors": {
    "brand_green": "9BE868",
    "warning_orange": "FF9A3C",
    "author_gray": "AAAAAA"
  }
}
```

随后就可以在 `tooltips/` 中通过 `<c.brand_green>` 这样的标签引用对应颜色。

### 适用场景

- 为整套蓝图说明统一标题颜色
- 为不同类别载具定义固定色调
- 为注意事项、作者信息、实验性提示提供一致的强调样式

### 使用建议

- 色板数量不宜过多，一般一到两份公共色板就足够
- 同一内容包内的标题色、备注色、警告色建议保持固定
- 如果某个颜色只出现一次，直接在标签里写十六进制值即可，不一定需要专门放进色板

`colors/` 只负责文本颜色别名，不影响零件材质、车辆涂装或物理表现。

## 自定义驾驶 HUD（huds/）

`huds/` 模块用于定义驾驶时显示在屏幕上的 HUD 元素，例如速度表、挡位显示、转速表、警告灯和其他自定义信息面板。

对玩家来说，这部分决定了"坐上车之后看到什么"；对 UGC 作者来说，这是最能体现车辆个性化体验的辅助模块之一。

### 文件位置

```text
spark_modules/
└── my_pack/
    └── my_mod/
        └── huds/
            ├── driver_dashboard.json
            └── offroad_hud.json
```

### HUD 资源的组成

一个完整 HUD 通常由以下几部分共同构成：

1. `huds/*.json`：HUD 配置文件，定义模型、动画、贴图、偏移和文本
2. `models/`：HUD 使用的模型文件
3. `animations/`：HUD 的动画文件
4. `textures/`：HUD 的贴图资源
5. `lang/`：HUD 文本用到的翻译键

### 基本结构

一个 HUD JSON 的典型结构如下：

```json
{
  "model": "my_mod:driver_dashboard.geo",
  "animation": "my_mod:driver_dashboard",
  "texture": "my_mod:textures/hud/driver_dashboard.png",
  "offset": [95, 55, -135],
  "rotation": [-25, -30, 0],
  "scale": [15, 15, 15],
  "perspective": true,
  "texts": {
    "speed": {
      "key": "hud.my_mod.dashboard.speed",
      "centered": true,
      "shadow": true,
      "molang_args": [
        "math.floor((math.abs(global.get('vehicle_speed')??0.0)) * 3.6)"
      ]
    }
  }
}
```

### 常用字段

| 字段           | 类型        | 必需 | 说明                                                |
| -------------- | ----------- | ---- | -------------------------------------------------- |
| `model`        | 资源路径    | 是   | HUD 模型资源                                       |
| `animation`    | 资源路径    | 是   | HUD 动画资源                                       |
| `texture`      | 资源路径    | 是   | HUD 贴图资源                                       |
| `offset`       | 三维向量    | 否   | HUD 相对屏幕中心的偏移                             |
| `rotation`     | 三维向量    | 否   | HUD 旋转角度（度）                                 |
| `scale`        | 三维向量    | 否   | HUD 缩放                                           |
| `color`        | RGB 数组    | 否   | 整体着色                                           |
| `alpha`        | 整数        | 否   | 透明度                                             |
| `perspective`  | 布尔值      | 否   | 是否使用透视投影                                   |
| `texts`        | 对象        | 否   | HUD 文本定义                                       |
| `enable_scissor` 等 | 布尔/整数 | 否   | 裁剪区域设置，用于限制显示范围                     |

### 文本显示

`texts` 字段用于在 HUD 中显示动态文本。每个条目对应模型中的一个文本定位器，常用字段包括：

| 字段          | 类型        | 说明                                               |
| ------------- | ----------- | ------------------------------------------------- |
| `key`         | 字符串      | 翻译键                                             |
| `centered`    | 布尔值      | 是否居中显示                                       |
| `shadow`      | 布尔值      | 是否绘制阴影                                       |
| `scale`       | 三维向量    | 文本缩放                                           |
| `color`       | RGB 数组    | 文本颜色                                           |
| `molang_args` | 字符串数组  | 动态参数，用于向翻译键传入运行时数值                |
| `significand` | 整数        | 数值参数保留的小数位数                             |

例如：

```json
"gear": {
  "key": "hud.my_mod.dashboard.gear",
  "centered": true,
  "shadow": true,
  "molang_args": ["global.get('gear')??'N'"]
}
```

这里的 Molang 细节会在 [5.10 Molang表达式](5.10-Molang表达式.md) 中展开。本章只需要知道：HUD 文本可以读取实时车辆状态，因此适合显示速度、挡位、转速和警告信息。

### HUD 如何和座椅绑定

HUD 本身不会自动显示，必须在座椅子系统的 `views` 配置中引用：

```json
{
  "type": "machine_max:seat",
  "views": {
    "enable_first_person": true,
    "first_person_hud": ["my_mod:driver_dashboard"],
    "enable_third_person": true,
    "third_person_hud": ["my_mod:driver_dashboard"]
  }
}
```

这表示：

- 玩家坐上这个座位并切到第一人称时，显示 `my_mod:driver_dashboard`
- 玩家切到第三人称时，也可以显示同一套或另一套 HUD

如果 `first_person_hud` 或 `third_person_hud` 为空，对应视角下就不会叠加自定义 HUD。

### 面向玩家应优先展示哪些信息

对于大多数载具，建议 HUD 先覆盖以下高频信息：

- 车速
- 当前挡位
- 发动机或电机转速
- 关键警告灯（如损坏、刹车、灯光状态）

不建议一开始就做过多装饰性元素。先保证玩家能够读懂核心状态，再逐步增加风格化面板。

## 语言文件（lang/）

`lang/` 模块为内容包中的可见文本提供本地化支持。它不仅负责零件和物品名称，也负责蓝图标题、说明文字、HUD 文本、连接点名称、子系统名称以及交互提示。

### 文件位置

```text
spark_modules/
└── my_pack/
    └── my_mod/
        └── lang/
            ├── zh_cn.json
            └── en_us.json
```

### 常见用途

语言文件通常会包含以下几类键：

- 零件、子系统、连接点的显示名称
- 蓝图和装配体的标题、描述、作者信息
- HUD 中使用的文本模板
- 交互提示文本

示例：

```json
{
  "my_mod.sports_car_chassis": "示例小车底盘",
  "title.my_mod.blueprint.sports_car": "示例运动型小车",
  "description.my_mod.blueprint.sports_car": "一辆用于演示内容包结构的紧凑型载具。",
  "author.my_mod.blueprint.sports_car": "模型作者：YourName",
  "hud.my_mod.dashboard.speed": "%1$s km/h",
  "hud.my_mod.dashboard.gear": "%1$s"
}
```

### HUD 文本中的占位符

对于 HUD 文字，翻译内容经常包含 `%1$s`、`%2$s` 之类的占位符。它们会按顺序填入 `molang_args` 计算得到的结果。

例如：

```json
{
  "hud.my_mod.dashboard.speed": "%1$s km/h"
}
```

配合：

```json
"molang_args": [
  "math.floor((math.abs(global.get('vehicle_speed')??0.0)) * 3.6)"
]
```

最终就能在 HUD 中得到类似 `128 km/h` 的实时显示。

### 编写建议

- 所有需要给玩家看的文字，都尽量放进 `lang/`
- `tooltips/` 和 `huds/` 中优先写翻译键，而不是直接写固定文本
- 至少提供一份 `zh_cn.json`；如果内容包打算公开发布，建议同步提供 `en_us.json`

## 图标与贴图资源（textures/）

严格来说，`textures/` 不是只属于辅助模块的目录，但在本章语境下，它主要承担两类职责：

1. 为蓝图和装配体提供物品图标
2. 为 HUD 提供界面贴图

### 蓝图/装配体图标

在 [5.7 模板、蓝图与装配体](5.7-模板、蓝图与装配体.md) 中提到过，`blueprints/` 和 `assemblies/` 都可以通过 `icon` 字段指定图标：

```json
"icon": "my_mod:textures/icon/sports_car.png"
```

玩家会在以下位置看到这些图标：

- 物品栏 GUI
- 创造模式标签页
- 部分配方或研究成果展示界面

如果没有提供图标，系统通常会退回到 3D 预览，而不是报错；但从识别效率来看，正式发布的内容包仍建议为主要载具准备独立图标。

### HUD 贴图

HUD 的 `texture` 字段通常引用 `textures/hud/` 下的 PNG：

```json
"texture": "my_mod:textures/hud/driver_dashboard.png"
```

这类贴图负责仪表盘底板、刻度、装饰框等静态视觉元素；动态部分则由动画与文字共同完成。

## 控制组预设（control_groups/）

`control_groups/` 模块用于定义控制组预设——JSON 文件描述座舱内按键如何映射为载具信号。预设文件被座椅子系统的 `control_group_preset` 字段引用，决定玩家坐在该座位时，WASD、鼠标和自定义按键分别产生什么效果。

### 文件位置

```text
spark_modules/
└── my_pack/
    └── my_mod/
        └── control_groups/
            ├── default_driver.json
            └── my_gunner.json
```

文件名（不含扩展名）即为预设的注册 ID（如 `my_mod:my_gunner`）。

### 预设 JSON 结构

一个控制组预设 JSON 包含一个 `base_group`（始终激活的基础控制组）和可选的 `groups`（可切换的子控制组列表），以及可选的 `gui_actions`（AUI 面板上的交互控件）。

**顶层字段：**

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `base_group` | ControlGroup | **是** | 基础控制组，始终激活 |
| `groups` | List\<ControlGroup\> | 否 | 可切换的子控制组列表 |
| `gui_actions` | List\<GuiAction\> | 否 | 驾驶界面交互控件 |

**ControlGroup 字段：**

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `name` | 字符串 | **是** | 控制组名称。`base_group` 固定为 `"base"` |
| `control_mode` | 枚举 | 否（默认 `inherit`） | 控制模式。`inherit` 不覆盖基础组；`ground` / `plane` / `ship` / `mech` 各有独立按键语义 |
| `move_targets` | 对象 | 否 | 移动输入路由，格式 `{频道名: [目标列表]}` |
| `view_targets` | 对象 | 否 | 视角输入路由，格式同上 |
| `regular_targets` | 对象 | 否 | 常规按键（离合/换挡等）路由 |
| `bindings` | 列表 | 否 | 离散按键绑定列表 |

**ControlBinding 字段：**

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `trigger` | 字符串 | **是** | 逻辑按键标识，如 `"key.mouse.left"`、`"key.r"`、`"gamepad.button_a"` |
| `action` | 枚举 | **是** | 动作类型：`"press"`（按一次发送）、`"hold"`（按住持续发送）、`"toggle"`（切换状态） |
| `channel` | 字符串 | **是** | 输出信号频道名 |
| `targets` | 字符串列表 | 否（默认 `["global"]`） | 信号目标。常用值：`"global"`（载具总线）、连接器路由名、子系统名 |

**GuiAction 字段：**

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `type` | 枚举 | **是** | `"pulse"`（按钮）、`"toggle"`（开关）、`"slider"`（滑块） |
| `label` | 字符串 | **是** | 控件显示标签（翻译键） |
| `channel` | 字符串 | **是** | 输出信号频道名 |
| `min` / `max` / `step` | 浮点数 | 仅 `slider` | 滑块数值范围与步进 |

### 编写示例

**驾驶员（ground 模式，WASD 控制载具总线）：**

```json
{
    "base_group": {
        "name": "base",
        "control_mode": "ground",
        "move_targets": { "move_input_p1": ["global"] },
        "regular_targets": { "regular_input_p1": ["global"] }
    }
}
```

**炮手（inherit 模式，鼠标控制视角与开火）：**

```json
{
    "base_group": {
        "name": "base",
        "control_mode": "inherit",
        "view_targets": { "aim_input_p1": ["global"] },
        "bindings": [
            {
                "trigger": "key.mouse.left",
                "action": "hold",
                "channel": "fire_input_p1",
                "targets": ["global"]
            }
        ]
    }
}
```

**乘客（全部为空，纯乘坐）：**

```json
{
    "base_group": {
        "name": "base",
        "control_mode": "inherit"
    }
}
```

### 在座椅子系统中引用

控制组预设通过 `control_group_preset` 挂接到具体座椅：

```json
"subsystem.my_mod.driver_seat": {
    "type": "machine_max:seat",
    "definition": "machine_max:default_seat",
    "locator": "DriverSeatPoint",
    "control_group_preset": "my_mod:default_driver"
}
```

### `targets` 路由说明

`targets` 数组中的值决定信号到达何处：

- `"global"` — 走载具总线广播，所有子系统均可接收。
- `"connector.{命名空间}.{名称}"` — 沿指定连接器传播，信号经连接点的 `signal_targets` 和 `signal_translations` 处理后送达对侧零件。
- `"subsystem.{命名空间}.{名称}"` — 直接发送给指定子系统。

### 实践建议

- 驾驶员至少配置 `move_targets`；炮手至少配置 `view_targets` 和一个开火 `binding`。
- 子控制组的 `control_mode` 设为 `"inherit"` 时沿用基础组的按键语义，适合炮手/车长等不改变核心驾驶操作的辅助角色。
- GUI 控件适合放置低频操作（灯光切换、差速锁、辅助系统启停），避免占用物理按键。
- 预设文件名建议使用语义化命名（如 `tank_gunner`、`heli_pilot`），便于在零件 JSON 中辨识。

## 典型工作流

当你准备为一辆内容包载具补全玩家可见信息时，通常可以按下面的顺序处理：

1. 在 `lang/` 中先写好名称、标题、简介和 HUD 文本键。
2. 在 `textures/` 中准备图标和 HUD 贴图。
3. 在 `tooltips/` 中编写蓝图/装配体的悬浮说明，必要时配合 `colors/` 管理统一配色。
4. 在 `blueprints/` 或 `assemblies/` 中引用 `tooltip` 与 `icon`。
5. 在 `control_groups/` 中定义每个座位的按键映射预设。
6. 在 `huds/` 中编写驾驶 HUD。
7. 在座椅子系统的 `views` 和 `control_group_preset` 字段中绑定 HUD 与控制组。

这一流程的核心思路是：先准备文本和资源，再定义交互行为，最后把它们挂接到蓝图、装配体和座椅上。

---

## 实践建议

- 蓝图和装配体的说明文本应以识别信息为主，避免写得过长。
- 同一内容包中的标题、作者说明、提示语最好使用统一的语言键前缀。
- HUD 首先保证可读性，再考虑复杂动画和装饰细节。
- 如果一个内容包内有多种载具，建议统一图标尺寸、说明结构和色板风格。
- 当玩家最常接触的是生存模式流程时，应优先补全蓝图说明、研究成果名称和驾驶 HUD，而不是先做边缘性的视觉资源。
