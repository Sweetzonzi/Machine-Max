# 5.3 零件定义

零件定义 JSON 是内容包中最核心的配置文件，放置在 `parts/` 模块目录下。每个 JSON 文件定义一个零件类型（`PartType`），包括其变体外观、子零件结构、碰撞体积、连接点挂载和子系统配置。

从内容包作者的角度看，零件定义并不只是“把模型挂进游戏”的一步。第四章里提到的很多系统，最终都要在这里找到入口：`hit_boxes` 和 `material` 会决定命中后如何进入 [4.3 装甲与穿甲](../4-物理与战斗机制/4.3-装甲与穿甲.md) 与 [4.4 伤害系统](../4-物理与战斗机制/4.4-伤害系统.md)；`block_collision`、`collision_height` 和 `climb_assist` 会决定部件如何参与 [4.6 地形平滑](../4-物理与战斗机制/4.6-地形平滑.md)；`connectors` 和 `subsystems` 则负责把结构、动力和控制网络真正组织起来。

因此，编写零件定义的过程，本质上是在回答四个问题：

- 这个零件看起来是什么样
- 它由哪些可独立结算的子零件组成
- 它如何与地形、伤害和碰撞系统交互
- 它如何与其他零件和子系统建立结构、信号与动力关系

本章面向 UGC 作者，逐字段解释零件定义 JSON 的完整结构。阅读本章前，建议先完成 [5.2 模型与动画](5.2-模型与动画.md) 的模型准备工作。

## 文件位置

零件定义 JSON 放在内容包对应的命名空间目录下：

```
spark_modules/
└── my_pack/
    └── my_mod/
        └── parts/
            ├── my_chassis.json
            ├── my_wheel.json
            └── my_engine.json
```

每个文件名（不含扩展名）即为该零件的内部 ID。模组加载时，以 `命名空间:文件名` 的格式注册零件类型（如 `my_mod:my_chassis`），后续在配方、蓝图等模块中通过此格式引用。

> `parts/` 目录下的 JSON 文件可以任意嵌套子文件夹来组织（如 `parts/vehicle/ae86/chassis.json`），但注册名仅取文件名（不含扩展名和路径），即 `my_mod:chassis`。嵌套路径仅用于作者自行分类，不影响注册结果。

## 顶层字段

在进入字段表之前，先建立一个简单的阅读顺序会更容易理解整个文件：

1. 顶层字段描述“这个零件整体是什么”。
2. `variants` 描述“它有哪些外观或装配变体”。
3. `sub_parts` 描述“这些变体内部由哪些受力、受击和运动单元组成”。
4. 子零件下的 `hit_boxes`、`connectors`、`subsystems`、`hydrodynamics` 等字段，再分别决定“这个单元会如何参与具体系统”。

也就是说，零件定义是一个由外到内、由静态外观到动态行为逐步展开的结构，而不是一组彼此孤立的配置项。

零件定义 JSON 的顶层包含零件的全局属性。以下按字段列出：

| 字段                              | 类型   | 必需    | 默认值                   | 说明                                                          |
| ------------------------------- | ---- | ----- | --------------------- | ----------------------------------------------------------- |
| `$schema`                       | 字符串  | 否     | —                     | JSON Schema 引用路径，供编辑器提供智能提示和校验。建议保留                         |
| `icon`                          | 资源路径 | 否     | `minecraft:missingno` | 零件在物品栏和 UI 中显示的图标，格式为 `namespace:path`                      |
| `vehicle_durability_rate`       | 浮点数  | 否     | `0.8`                 | 载具耐久贡献系数。零件耐久度按此比例累加到载具总耐久度。例如设为 `1.0` 表示零件的全部耐久度都贡献给载具     |
| `vehicle_damage_rate`           | 浮点数  | 否     | `1.0`                 | 常态伤害传导系数。零件受到伤害时按此比例传导给载具本体。例如设为 `0.5` 表示零件只将 50% 的伤害传递给载具  |
| `vehicle_damage_rate_destroyed` | 浮点数  | 否     | `0.1`                 | 零件被摧毁后的伤害传导系数。通常设为较低值以避免摧毁后继续承受高额伤害                         |
| `functional_threshold`          | 浮点数  | 否     | `0.3`                 | 功能阈值（0\~1）。当零件组装进度达到该值后，子系统可正常工作。也用于控制组装阶段的线框渲染何时自动关闭       |
| `share_durability`              | 布尔值  | 否     | `true`                | 是否共享耐久度。设为 `true` 时零件内所有子零件共享同一耐久度池；设为 `false` 时每个子零件有独立耐久度 |
| `max_stack_size`                | 整数   | 否     | `1`                   | 零件物品的最大堆叠数量（1\~64）。可通过调大此值使零件在物品栏中可堆叠                       |
| `variants`                      | 对象   | **是** | —                     | 零件变体列表，详见下文                                                 |

> `functional_threshold` 的实际生效范围被限制在 0\~1 之间。例如设为 `0.6` 表示组装进度达到 60% 时子系统即可正常工作。

### 关于 `share_durability`

当 `share_durability` 为 `true`（默认）时，零件的所有子零件共享一个耐久度池。任何一个子零件受到伤害都会从总池中扣除，总池归零时所有子零件同时瘫痪。

当设为 `false` 时，每个子零件拥有独立耐久度。这种做法适用于希望不同子零件独立承受伤害的场景，但会增加一份额外的同步开销。

## 变体（variants）

`variants` 字段是零件定义的顶层必需项，它定义零件可用的所有变体。变体机制允许同一个零件类型以不同的外观、贴图甚至不同的子零件结构出现。最常见的用途是区分左右对称零件（如左轮/右轮、左门/右门）。

这里的“变体”不应只理解为换一张贴图。因为变体还可以拥有不同的 `tags` 与 `sub_parts`，所以它也会间接影响后续的连接点匹配、交互方式，甚至结构布局。换句话说，变体既可以只是外观差异，也可以是同一类零件的不同安装版本。

### 单一变体写法

如果零件只有一个变体，可以直接将变体属性写在 `variants` 下，模组会自动为其分配 `"default"` 变体名：

```json
"variants": {
  "model": "machine_max:my_part.geo",
  "textures": "machine_max:textures/part/my_part.png",
  "sub_parts": { ... }
}
```

### 多变体写法

如果零件有多个变体，`variants` 写为一个键值对集合，键为变体名称，值为该变体的属性：

```json
"variants": {
  "left": {
    "model": "machine_max:wheel.geo",
    "textures": "machine_max:textures/part/wheel_left.png",
    "tags": ["machine_max:wheel", "machine_max:left"],
    "sub_parts": { ... }
  },
  "right": {
    "model": "machine_max:wheel.geo",
    "textures": "machine_max:textures/part/wheel_right.png",
    "tags": ["machine_max:wheel", "machine_max:right"],
    "sub_parts": { ... }
  }
}
```

玩家在拼装时可以通过切换零件变体来选择使用左变体或右变体。变体名称可以自由命名（如 `"left"` / `"right"`、`"red"` / `"blue"`）。

### 变体属性字段

每个变体包含以下字段：

| 字段           | 类型         | 必需    | 默认值                   | 说明                                                                                                                         |
| ------------ | ---------- | ----- | --------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| `model`      | 资源路径       | **是** | —                     | 基岩版几何模型路径，格式为 `namespace:name.geo`。例如 `machine_max:my_part.geo` 会在所有内容包的 `models/machine_max/part/` 下搜索 `my_part.geo.json` |
| `textures`   | 资源路径或键值对对象 | 否     | `minecraft:missingno` | 贴图路径。可以是一个字符串（单一贴图，以 `"default"` 作为纹理名），也可以是一个键值对对象，键为纹理名，值为贴图路径                                                           |
| `animations` | 资源路径       | 否     | —                     | 动画路径。例如 `machine_max:my_anim` 会在所有内容包的 `animations/machine_max/part/my_anim/` 下加载动画文件。留空则不播放动画                             |
| `tags`       | 字符串数组      | 否     | `[]`                  | 零件标签列表。标签用于连接点匹配（详见 [5.4 连接点定义](5.4-连接点定义.md)），以及功能分类。格式为 `namespace:tag_name`                                             |
| `sub_parts`  | 对象         | **是** | —                     | 子零件定义，详见下文                                                                                                                 |

#### 贴图（textures）的两种写法

**单一贴图（简写）**：

```json
"textures": "machine_max:textures/part/my_texture.png"
```

等效于 `"textures": {"default": "machine_max:textures/part/my_texture.png"}`。

**多名贴图（完整写法）**：

```json
"textures": {
  "print.machine_max.red": "machine_max:textures/part/red.png",
  "print.machine_max.blue": "machine_max:textures/part/blue.png"
}
```

多个贴图配合涂装系统使用，允许玩家在游戏中通过喷罐切换贴图。贴图名称的命名空间前缀（如 `print.machine_max.`）用于与涂装色彩合集关联，详见 [2.5 涂装系统](../2-载具系统完全指南/2.5-涂装系统.md)。

> 模型路径和动画路径在内部采用非文件夹精确匹配的搜索方式：`machine_max:my_part.geo` 会在 `models/machine_max/part/` 的任意子目录下查找。因此内容包作者无需关心内部子目录结构，只需保证文件名唯一即可。

## 子零件（sub\_parts）

子零件是零件的最小运动单元，也是碰撞、连接点和子系统挂载的基本载体。零件的每个独立可动部分都应当定义为一个子零件。

如果说整个零件定义回答的是“这是什么零件”，那么子零件回答的就是“它内部哪些部分需要被分别看待”。第四章中的许多判定，实际上都不会直接对整份零件 JSON 一次性结算，而是落到某个具体子零件上。例如质量分布、命中受损、组装进度、地形接触、气动受力，最终都需要知道自己在作用哪个子零件。

与变体类似，子零件也支持单一和多个两种写法。只有一个子零件时可简写为直接对象（自动命名为 `sub_part.machine_max.main`），多个子零件时使用键值对。

子零件中的字段说明如下。

### 骨骼范围控制

| 字段           | 类型    | 必需 | 默认值        | 说明                                                       |
| ------------ | ----- | -- | ---------- | -------------------------------------------------------- |
| `start_bone` | 字符串   | 否  | `""`（全部骨骼） | 子零件的起始骨骼名称。此骨骼及其所有子骨骼（递归）会被纳入该子零件的渲染和定义范围                |
| `end_bones`  | 字符串数组 | 否  | `[]`       | 终止骨骼名称列表。配合 `start_bone` 使用，指定的骨骼及其子骨骼会被**排除**在渲染和定义范围之外 |

`start_bone` 和 `end_bones` 配合使用的场景：当多个子零件共用同一个模型文件时，通过骨骼范围将模型的不同部分划分给不同的子零件。例如一个车体模型同时包含车轮骨骼，但车轮由单独的子零件承载：

```json
"sub_part.machine_max.main": {
  "start_bone": "AllHull",
  "end_bones": ["LeftFrontWheel", "RightFrontWheel", "LeftBackWheel", "RightBackWheel"],
  ...
}
```

若不指定 `start_bone` 和 `end_bones`，则模型中的所有骨骼都归属于该子零件。

### 基本物理属性

这一组字段决定的是子零件作为物理对象的基本轮廓。它们虽然看起来只是一些数值，但后续的重量转移、碰撞响应、空气阻力和受损表现都建立在这些基线之上。

| 字段               | 类型   | 必需 | 默认值                   | 说明                                                                       |
| ---------------- | ---- | -- | --------------------- | ------------------------------------------------------------------------ |
| `durability`     | 浮点数  | 否  | `20.0`                | 子零件基础生命值。降至 0 时该子零件的所有子系统瘫痪。若顶层 `share_durability` 为 `true`，此值为共享池的一部分   |
| `mass`           | 浮点数  | 否  | `25.0`                | 子零件质量（kg），用于物理模拟。应填写真实或接近真实的质量值                                          |
| `mass_center`    | 字符串  | 否  | `"mass_center"`       | 质心定位器名称。模型中的同名定位器将作为该子零件的质量中心。若未找到则使用碰撞体积的几何中心                           |
| `projected_area` | 三维向量 | 否  | `{"x":0,"y":0,"z":0}` | 子零件在三个轴向上的投影面积（m²），参与空气阻力计算。格式如 `[1.5, 0.8, 3.2]`。留空时模组会根据子零件的整体尺寸自动粗略计算 |

### 地形碰撞

这一组字段和第四章中的接地逻辑直接对应。尤其是在轮胎、履带、滑撬和底盘下缘这类会持续接触地面的子零件上，`block_collision`、`collision_height` 与 `climb_assist` 的组合，往往比单纯调整碰撞箱尺寸更能决定实际驾驶手感。

| 字段                 | 类型  | 必需 | 默认值      | 说明                                                                                 |
| ------------------ | --- | -- | -------- | ---------------------------------------------------------------------------------- |
| `block_collision`  | 字符串 | 否  | `"true"` | 地形碰撞模式。可选值：`"true"`（与所有方块碰撞）、`"ground"`（仅与子零件下方的地面方块碰撞）、`"false"`（不与任何方块碰撞）        |
| `collision_height` | 浮点数 | 否  | `-1.0`   | 碰撞检测高度（m）。仅当 `block_collision` 为 `"ground"` 时生效。高度低于此值的障碍将被忽略。默认值 `-1.0` 表示不忽略任何障碍 |
| `climb_assist`     | 布尔值 | 否  | `false`  | 是否启用攀爬辅助。开启后使用高度场修正碰撞法线，使车轮能平滑地爬上台阶和不规则地形，而非直接撞击垂直棱边。建议轮胎类子零件开启                    |

> `"ground"` 模式适用于车轮等需要与地面交互但不应穿透墙壁的零件。`"true"` 模式适用于保险杠、车壳等需要与所有方块碰撞的零件。

如果需要更具体地理解这三个字段的实际效果，建议结合 [4.6 地形平滑](../4-物理与战斗机制/4.6-地形平滑.md) 一起阅读。对内容包作者来说，可以把它们简单理解成三层控制：

- `block_collision` 决定这个子零件走哪类地形碰撞路径
- `collision_height` 决定它愿意接受多高的局部台阶
- `climb_assist` 决定它是否按更接近轮式滚动的方式修正接触

## 碰撞箱（hit\_boxes）

`hit_boxes` 是子零件的**唯一必需子字段**。它定义子零件的物理碰撞体积。模组读取模型文件中与键名匹配的骨骼，根据骨骼下方块的几何数据生成碰撞形状。

从系统职责上看，`hit_boxes` 同时承担三件事：

- 定义“这块东西在物理世界里占多大体积”
- 定义“攻击命中时究竟命中了哪里”
- 定义“这次命中应该套用什么材料、厚度和子系统关联”

这也是为什么 `hit_boxes` 会成为零件定义里最不能省略的一部分。没有它，零件不只是“缺少碰撞”，而是无法正确进入伤害、装甲、穿透和局部功能受损这整条链路。

### 基本用法

```json
"hit_boxes": {
  "HullHitBox": {
    "type": "box",
    "material": "machine_max:structural_steel",
    "thickness": 3
  }
}
```

键名（如 `HullHitBox`）必须与模型中的骨骼名称精确匹配。值对象为碰撞箱属性。

### 碰撞箱属性

| 字段          | 类型   | 必需 | 默认值                     | 说明                                                                                                                                               |
| ----------- | ---- | -- | ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `id`        | 字符串  | 否  | `"part"`                | 碰撞形状 ID。同 ID 的碰撞体积不会被同一次攻击重复命中，避免穿甲弹等穿透效果重复判定                                                                                                    |
| `type`      | 字符串  | 否  | `"box"`                 | 碰撞形状类型。可选值：`"box"`（长方体）、`"sphere"`（球体，取方块 Y 半长作为半径）、`"cylinder"`（圆柱体，Z 轴为轴向）、`"capsule"`（胶囊体，Y 轴为轴向）、`"wheel"`（特殊球体，见下方说明）                       |
| `subsystem` | 字符串  | 否  | `""`                    | 关联的子系统名称。当此碰撞箱受到伤害时，关联的子系统会受到等量伤害。常用于将窗玻璃、引擎等部件与对应的子系统关联                                                                                         |
| `material`  | 资源路径 | 否  | `"machine_max:default"` | 材料注册 ID。决定碰撞箱的摩擦系数、减伤属性、音效等物理表现。引用 `materials/` 模块中定义的材料                                                                                         |
| `thickness` | 浮点数  | 否  | `1.0`                   | 厚度（mm）。决定碰撞箱的防护能力，参与伤害减免和穿甲计算                                                                                                                    |
| `condition` | 字符串  | 否  | —                       | 条件表达式。使用 Molang 语法，当表达式计算结果为 `false` 时此碰撞箱不生效。常用于使被摧毁后不再提供防护，如 `"!subpart.subsystem_destroyed('subsystem.machine_max.front_glass')"`（玻璃未被摧毁时才生效） |
| `overwrite` | 对象   | 否  | —                       | 材质属性覆写。允许按需覆写 `material` 中引用的材料的任意字段，如摩擦系数、恢复系数、伤害修正等。覆写条目仅为所需修改的字段，其余字段仍继承材质定义                                                                  |

其中 `material`、`thickness` 与 `overwrite` 三个字段需要放在一起理解。`material` 提供一套可复用的共用基线，`thickness` 决定当前这块命中箱自身有多厚，而 `overwrite` 则用于在不新建整份材料定义的前提下，对某个局部命中箱做少量特化。这种分工和 [5.6 材料定义](5.6-材料定义.md) 中的思路是一致的。

#### wheel 类型的特殊说明

`type` 设为 `"wheel"` 时，碰撞形状为特殊球体（半径取自方块 Y 半长，宽度取自方块 X 尺寸）。其行为特点：

- 碰撞检测时若碰撞点的 X 偏移超出轮胎半宽，则忽略此次碰撞。
- 会根据方块尺寸以圆柱体转动惯量公式调整整个刚体的转动惯量，模拟车轮的旋转特性。

> 建议单个子零件仅包含**一个**类型为 `wheel` 的碰撞箱，且该碰撞箱对应的骨骼下仅包含一个方块。

#### condition 表达式的典型用法

条件表达式目前常用于玻璃类碰撞箱——玻璃被摧毁后其碰撞箱不应继续提供防护：

```json
"FrontGlass": {
  "type": "box",
  "material": "machine_max:glass",
  "thickness": 1,
  "subsystem": "subsystem.machine_max.front_glass",
  "condition": "!subpart.subsystem_destroyed('subsystem.machine_max.front_glass')"
}
```

> 关于 Molang 表达式的更多用法，参见 [5.10 Molang表达式](5.10-Molang表达式.md)。

### 碰撞箱与模型的对应关系

1. 模组首先按 `hit_boxes` 的键名查找模型中的同名骨骼。
2. 读取该骨骼下的所有方块（Cube），根据 `type` 参数生成对应的碰撞形状。
3. 该骨骼下的定位器（Locator）也会被读取，供相关子系统使用（如灯光子系统的发光定位点）。
4. 模型中方块的 UV 数据不参与碰撞计算——因此碰撞骨骼的方块应删除 UV（`"uv": {}`），参见 [5.2 模型与动画](5.2-模型与动画.md) 中的说明。

## 交互判定区（interact\_boxes）

`interact_boxes` 定义玩家可以交互的区域，如上车检测区、车门开关触发区、储物箱打开区等。这是可选字段。

它和 `hit_boxes` 的区别在于：前者回答“玩家能不能在这里触发交互”，后者回答“物理或伤害能不能命中这里”。两者都可能引用模型中的骨骼，但服务的系统完全不同，不建议混为一谈。

### 基本用法

```json
"interact_boxes": {
  "interact.machine_max.left_seat": {
    "bone": "LeftSeatInteract",
    "signal_targets": {
      "left_seat_interact": ["subsystem.machine_max.driver_seat"]
    },
    "interact_mode": "accurate"
  }
}
```

键名（如 `interact.machine_max.left_seat`）为交互区的唯一标识符，用于信号路由引用。值对象为交互区属性。

### 交互区属性

| 字段               | 类型  | 必需    | 默认值      | 说明                                                                                       |
| ---------------- | --- | ----- | -------- | ---------------------------------------------------------------------------------------- |
| `bone`           | 字符串 | **是** | —        | 交互区对应的骨骼名称。模组以该骨骼下方块的包围盒作为交互判定体积                                                         |
| `signal_targets` | 对象  | **是** | —        | 信号传输目标。键为信号频道名，值为目标列表（目标可以是子系统名称、连接点名称、`"subpart"`、`"part"` 或 `"vehicle"`）               |
| `interact_mode`  | 字符串 | 否     | `"fast"` | 交互模式。`"fast"`：玩家碰撞箱与交互区相交时按下交互键触发；`"accurate"`：玩家准星瞄准交互区时按下交互键触发                         |
| `condition`      | 字符串 | 否     | `"NOR"`  | 交互区的可用条件逻辑。可选值：`"AND"`（所有输入信号均不为 0）、`"OR"`（任意输入信号不为 0）、`"NAND"`、`"NOR"`、`"XOR"`、`"XNOR"` |

> `"fast"` 模式适合上车等需要宽松判定的场景；`"accurate"` 模式适合需要精确瞄准的开关或按钮类交互。

## 连接点（connectors）

`connectors` 字段定义子零件用于与其他零件连接的接口。每个连接点关联模型中的一个定位器，定位器的位置和朝向决定了连接点的位姿。这是可选字段（无连接互动的独立零件可不填写）。

在编写零件定义时，可以把 `connectors` 理解为“零件对外提供的结构接口与线路接口”。它不只决定拼装时能不能接上，还会决定动力、信号和断裂后果如何沿这条接口传播。因此它和第四章中的结构断裂逻辑，以及下一节 [5.4 连接点定义](5.4-连接点定义.md) 的静态参数，是前后衔接的一整套系统。

### 基本用法

```json
"connectors": {
  "connector.machine_max.left_front_wheel": {
    "locator": "LeftFrontWheel",
    "definition": "machine_max:ae86_left_front_wheel",
    "signal_targets": {
      "move_input": ["subsystem.machine_max.car_controller"]
    }
  }
}
```

键名（如 `connector.machine_max.left_front_wheel`）为连接点在零件内的唯一标识符，供子系统引用（如 `wheel_driver` 的 `connector` 字段）。值对象为连接点配置。

### 连接点配置字段

| 字段                    | 类型   | 必需    | 默认值     | 说明                                                                                                                   |
| --------------------- | ---- | ----- | ------- | -------------------------------------------------------------------------------------------------------------------- |
| `locator`             | 字符串  | **是** | —       | 模型中的定位器名称。定位器的世界坐标决定连接点位置，定位器的旋转决定连接点初始朝向                                                                            |
| `definition`          | 资源路径 | **是** | —       | 连接点静态属性定义 ID。引用 `connectors/` 模块中定义的连接点，格式为 `namespace:connector_name`                                               |
| `power_target`        | 字符串  | 否     | `""`    | 对侧连接器传入的机械能在本零件内的接收目标（子系统名或连接点名）。设置后该连接点可作为机械能传输通道，将对侧传入的机械能转发至本零件内的目标，如 `"subsystem.machine_max.my_gearbox"`        |
| `overwrite`           | 对象   | 否     | —       | 覆写连接点的静态属性。按需覆写 `definition` 引用中定义的字段，如 `integrity`（结构完整性）、`required_tags`（匹配标签要求）等。未覆写的字段继承原定义                      |
| `signal_targets`      | 对象   | 否     | —       | 信号转发目标。键为信号频道名，值为目标列表。通过此连接点传输的信号将被转发到指定的子系统、其他连接点或载具                                                                |
| `signal_translations` | 对象   | 否     | —       | 信号频道转换。键为原始频道名，值为目标频道名。用于将来自不同来源的信号统一到同一频道。例如将 `"interact_left_door"` 和 `"interact_right_door"` 都转换为 `"interact"` 频道 |
| `internal`            | 布尔值  | 否     | `false` | 是否为零件内部连接点。设为 `true` 时仅用于同一零件内部子零件间的自动连接，不参与对外拼装                                                                     |

连接点静态属性（`definition` 指向的内容）定义连接点的类型（简单/高级）、关节属性、结构完整性、冲击处理参数和标签匹配规则等，详见 [5.4 连接点定义](5.4-连接点定义.md)。

### 覆写（overwrite）示例

覆写允许在零件级别调整连接点的特定参数，无需重复定义整个连接点属性：

```json
"connector.machine_max.left_door_lock": {
  "locator": "hull_left_door_lock",
  "definition": "machine_max:fixed_up",
  "overwrite": {
    "integrity": 5
  }
}
```

此处将车门锁扣的连接点结构完整性覆写为 `5`（原定义值被替换），其余属性（如方向、冲击参数）仍沿用 `machine_max:fixed_up` 的定义。

## 子系统（subsystems）

`subsystems` 字段为子零件挂载子系统配置。子系统赋予零件具体的功能行为（如引擎、座椅、储物箱、车辆控制器等）。这是可选字段。

如果说 `hit_boxes` 提供的是“受击入口”，`connectors` 提供的是“结构与传输接口”，那么 `subsystems` 提供的就是“这个零件真正能做什么”。大多数玩家能直接感知到的功能，例如发电、驱动、转向、乘坐、照明和储物，最终都是通过这里挂载到具体子零件上的。

### 基本用法

```json
"subsystems": {
  "subsystem.machine_max.my_seat": {
    "type": "machine_max:seat",
    "definition": "machine_max:default_seat",
    "locator": "SeatPoint",
    "move_outputs": {
      "move_input": ["connector.machine_max.chassis_connection"]
    }
  }
}
```

键名（如 `subsystem.machine_max.my_seat`）为子系统在零件内的唯一标识符，供碰撞箱关联（`subsystem` 字段）和信号路由引用。值对象为子系统动态配置。

### 子系统通用字段

所有子系统类型共享以下通用字段：

| 字段           | 类型   | 必需    | 默认值 | 说明                                                                     |
| ------------ | ---- | ----- | --- | ---------------------------------------------------------------------- |
| `type`       | 资源路径 | **是** | —   | 子系统类型。可选类型见下表                                                          |
| `definition` | 资源路径 | **是** | —   | 子系统型号定义 ID。引用 `subsystems/` 模块中定义的子系统型号，格式为 `namespace:subsystem_name` |
| `locator`    | 字符串  | 视类型而定 | —   | 功能定位器名称。部分子系统类型需要（如 `seat` 需要座位定位点、`lighting` 需要灯光定位点）                 |

### 子系统类型一览

| 类型标识                               | 功能                                     | 特有字段                                                                                                       |
| ---------------------------------- | -------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| `machine_max:engine`               | 内燃机。将燃料化学能转换为机械功率                      | `power_output`（功率输出目标，填子系统名或 `"part"` / `"vehicle"`）、`speed_outputs`（转速信号输出）                               |
| `machine_max:motor`                | 电动机。低速下恒扭矩，高速下恒功率                      | 同 `engine`                                                                                                 |
| `machine_max:gearbox`              | 变速器。改变转速和扭矩                            | `power_output`（功率输出目标）、`gear_outputs`（挡位信号输出）                                                              |
| `machine_max:transmission`         | 传动/差速器。将功率分配至多个输出端                     | `power_outputs`（功率输出目标及其减速比键值对）                                                                            |
| `machine_max:wheel_driver`         | 轮胎驱动。驱动连接点上的零件滚动和转向                    | `connector`（控制的连接点名称）                                                                                      |
| `machine_max:car_controller`       | 车辆控制器。将玩家输入转换为各子系统控制信号                 | `engine_outputs`、`wheel_outputs`、`gearbox_outputs`、`speed_outputs` 等多种信号输出配置                               |
| `machine_max:motorbike_controller` | 摩托车控制器。类似 `car_controller` 但适配摩托车的操控逻辑 | 同上                                                                                                         |
| `machine_max:joint_driver`         | 关节驱动。直接驱动 Advanced 连接点的关节              | `connector`（控制的连接点名称）                                                                                      |
| `machine_max:seat`                 | 座位。允许玩家乘坐                              | `locator`（座位定位点，必需）、`move_outputs`、`regular_outputs`、`aim_outputs`（控制信号输出）、`passenger_num_outputs`（乘坐状态输出） |
| `machine_max:battery`              | 电池。为能量网供电                              | （参见 [5.5 子系统定义](5.5-子系统定义.md)）                                                                             |
| `machine_max:lighting`             | 灯光。渲染光照效果                              | `locator`（灯光定位点）                                                                                           |
| `machine_max:item_storage`         | 物品存储。提供可交互的存储容器                        | （无需特有字段，功能由 `definition` 决定）                                                                               |
| `machine_max:basic`                | 基础子系统。无特殊功能，仅用于表示是否被摧毁                 | （无需特有字段）                                                                                                   |

> `machine_max:basic` 类型的子系统本身不提供任何主动功能。它的存在仅用于碰撞箱的条件判断——如玻璃碰撞箱关联 `basic` 子系统后，可通过 `condition` 表达式检测玻璃是否被摧毁以决定碰撞箱是否生效。

### 信号输出配置的通用格式

许多子系统具有信号输出配置字段（如 `*_outputs`），其格式统一为键值对：

- **键**：信号频道名（如 `"engine_speed"`、`"throttle"`、`"gear"`）
- **值**：信号目标列表，目标可以是：
  - 其他子系统名称（如 `"subsystem.machine_max.gearbox"`）
  - 连接点名称（如 `"connector.machine_max.hull"`）
  - `"subpart"`——向当前子零件广播
  - `"vehicle"`——向整个载具广播

关于子系统信号传输、能量传递的详细机制，参见 [5.5 子系统定义](5.5-子系统定义.md)和 [3.6 信号系统](../3-子系统详解/3.6-信号系统.md)。

## 流体动力（hydrodynamics）

`hydrodynamics` 定义子零件在空气和水中的流体动力特性，包括阻力、升力等。这是可选字段。

这一部分与 [4.2 流体动力学与气动](../4-物理与战斗机制/4.2-流体动力学与气动.md) 相对应。并不是所有零件都需要精细编写它，但对车壳、翼面、浮筒、整流罩或高速外露部件来说，这里会直接影响高速稳定性、阻力和升力表现。

### 基本用法

```json
"hydrodynamics": {
  "": {
    "front_drag": [0.1, 1.0],
    "back_drag": [0.1, 1.0],
    "y_lift": 0.3
  }
}
```

键名遵循两阶段查找规则：先尝试匹配模型中的**骨骼名**，若命中则使用该骨骼下的**所有定位器**作为气动计算点；若未命中骨骼名，则视为**定位器名**直接使用。空字符串 `""` 表示以子零件质心作为计算点。

### 计算点属性

每个计算点支持以下字段：

| 字段                    | 类型         | 必需 | 默认值          | 说明                                                  |
| --------------------- | ---------- | -- | ------------ | --------------------------------------------------- |
| `scale`               | 浮点数        | 否  | `1.0`        | 整体缩放系数，用于统一调整此计算点的流体动力效果                            |
| `effective_range`     | 浮点数        | 否  | `1.0`        | 有效计算范围（m）。在来流方向上此距离内检测到遮挡时，会降低实际阻力系数，以模拟车壳遮挡带来的减阻效果 |
| `transonic_amplifier` | 浮点数        | 否  | `5.0`        | 跨音速放大系数。速度接近音速时阻力急剧增加的放大倍率                          |
| `front_drag`          | `[一阶, 二阶]` | 否  | `[0.1, 1.0]` | 前向阻力系数。一阶系数用于低速粘性阻力，二阶系数用于高速压差阻力                    |
| `back_drag`           | `[一阶, 二阶]` | 否  | `[0.1, 1.0]` | 后向阻力系数                                              |
| `left_drag`           | `[一阶, 二阶]` | 否  | `[0.1, 1.0]` | 左向阻力系数                                              |
| `right_drag`          | `[一阶, 二阶]` | 否  | `[0.1, 1.0]` | 右向阻力系数                                              |
| `up_drag`             | `[一阶, 二阶]` | 否  | `[0.1, 1.0]` | 上向阻力系数                                              |
| `down_drag`           | `[一阶, 二阶]` | 否  | `[0.1, 1.0]` | 下向阻力系数                                              |
| `x_lift`              | 浮点数        | 否  | `0.0`        | X 轴升力系数                                             |
| `y_lift`              | 浮点数        | 否  | `0.0`        | Y 轴升力系数（正值为上抬升力）                                    |
| `z_lift`              | 浮点数        | 否  | `0.0`        | Z 轴升力系数                                             |
| `advanced`            | 布尔值        | 否  | `false`      | 是否启用高级气动模式（目前为 WIP，尚不稳定）                            |

### 空气阻力优先级

子零件还有一个顶层字段 `hydro_priority`（整数，默认 `0`），用于控制子零件之间的遮挡关系：

> 优先级较高的子零件不会被优先级较低或相等的子零件阻挡。例如将车壳设为 `hydro_priority: 1`、底盘设为 `hydro_priority: 0`，则车壳不会因底盘的气动遮挡而降低阻力系数，但底盘可能因车壳的遮挡而减阻。

## 完整示例

如果你是第一次编写零件定义，推荐按下面的顺序落地，而不是一开始就把所有字段同时填满：

1. 先确认 `model`、`textures` 和 `sub_parts` 的基本骨架能被正确加载。
2. 先让每个子零件拥有最小可用的 `hit_boxes`，确保碰撞和受击正常。
3. 再补 `connectors` 和 `subsystems`，让结构和功能工作起来。
4. 最后再微调 `block_collision`、`hydrodynamics`、材料覆写和交互细节。

这样做的好处是，出现问题时更容易判断错误到底来自模型命名、碰撞结构、连接关系，还是更后面的功能细节。

以下为一个简化但完整的零件定义示例，展示一个自带储物功能的简易容器零件：

```json
{
  "$schema": "../../docs/zh_cn/schemas/part_definition_schema.json",
  "icon": "machine_max:textures/icon/my_container_icon.png",
  "vehicle_durability_rate": 0.0,
  "vehicle_damage_rate": 0.0,
  "vehicle_damage_rate_destroyed": 0.0,
  "max_stack_size": 8,
  "variants": {
    "model": "machine_max:my_container.geo",
    "textures": "machine_max:textures/part/my_container.png",
    "animations": "machine_max:empty",
    "tags": ["machine_max:storage"],
    "sub_parts": {
      "sub_part.machine_max.main": {
        "durability": 100.0,
        "mass": 30.0,
        "block_collision": "true",
        "hit_boxes": {
          "Shape": {
            "type": "box",
            "material": "machine_max:structural_steel",
            "thickness": 5
          }
        },
        "interact_boxes": {
          "interact.machine_max.container": {
            "bone": "Interact",
            "signal_targets": {
              "container_interact": ["subsystem.machine_max.storage"]
            },
            "interact_mode": "accurate"
          }
        },
        "subsystems": {
          "subsystem.machine_max.storage": {
            "type": "machine_max:item_storage",
            "definition": "machine_max:container_16x16x8"
          }
        },
        "connectors": {
          "connector.machine_max.up": {
            "locator": "up",
            "definition": "machine_max:fixed_up"
          },
          "connector.machine_max.down": {
            "locator": "down",
            "definition": "machine_max:fixed_down"
          }
        }
      }
    }
  }
}
```

## 检查清单

完成零件定义后，可对照以下清单自查：

- [ ] `$schema` 引用路径正确，JSON 编辑器无语法错误提示
- [ ] `variants` 已填写，至少包含 `model` 和 `sub_parts`
- [ ] 模型路径指向的文件确实存在于 `models/` 模块下，且为基岩版 `minecraft:geometry` 格式
- [ ] 每个子零件的 `hit_boxes` 至少有一个条目，其键名与模型骨骼名一致
- [ ] 碰撞箱对应的模型骨骼下确实包含方块，且碰撞用方块的 UV 已删除
- [ ] 若使用 `start_bone` / `end_bones`，骨骼名称在模型中存在
- [ ] 连接点的 `locator` 名称与模型定位器名一致，`definition` 引用的连接点存在于 `connectors/` 模块中
- [ ] 子系统的 `type` 和 `definition` 分别在正确的命名空间下引用
- [ ] 信号输出目标（`*_outputs`）中引用的子系统名、连接点名或关键字（`"subpart"`/`"part"`/`"vehicle"`）拼写无误
- [ ] 若有气动需求，`hydrodynamics` 计算点定位器名与模型中一致，或留空使用质心
- [ ] 语言文件（`lang/`）中已为零件添加显示名称和物品描述
