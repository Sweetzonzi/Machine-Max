# 5.8 研发与制造配方

配方（Recipe）是 MachineMax 生存模式流程的支柱。第2.6章已经介绍了玩家视角下的蓝图系统：获取研发点、在研究台解锁蓝图、抄录制造蓝图并完成组装。本章面向内容包作者，解释如何在 JSON 中定义这些配方，使自定义零件能够接入研发—制造—组装的完整链路。

MachineMax 的配方分为两类：**制造配方**（`machine_max:fabricating` 与 `machine_max:part_fabricating`）用于制造台自动加工，其中零件配方还参与手动焊枪组装/拆卸；**研究配方**（`machine_max:blueprint_research` / `machine_max:research`）用于研究台解锁技术与蓝图。此外，装配体和载具蓝图物品的合成仍使用原版工作台配方（`minecraft:crafting_shapeless`）。

> 配方文件全部放在内容包的 `recipe/` 模块目录下。**零件配方必须放在 `recipe/part_fabricating/` 下**，通用制造配方的目录不限。推荐蓝图研发配方放在 `recipe/research/` 子目录，装配体合成放在 `recipe/assembly/`，载具蓝图合成放在 `recipe/blueprint/`。

## 制造配方

制造配方描述「一组原料 → 一个产物 + 耗时」。产物是不是零件，决定了它属于哪一类：

| 配方类型    | `type`                        | 产物来源        | 目录                          | 参与手动组装/拆卸 |
| ------- | ----------------------------- | ----------- | --------------------------- | --------- |
| 通用制造配方  | `machine_max:fabricating`     | 由 `result` 完整声明 | 不限                          | 否         |
| 零件配方    | `machine_max:part_fabricating` | 由文件名推导      | `recipe/part_fabricating/`  | 是         |

两类配方都服务于**制造台（Fabricator）自动加工**；零件配方额外服务于**手动焊枪组装**与**手动焊枪拆卸**：

- **手动焊枪组装**：手持焊枪对未组装部件推进组装进度，每次推进按组装清单消耗材料。
- **手动焊枪拆卸**：对已组装部件拆卸，每次拆卸按拆卸清单返还材料。

### 通用制造配方

通用制造配方只在制造台中加工，不参与手动装配。产物由 `result` 完整声明（物品注册名、数量与数据组件）。

```json
{
  "$schema": "../docs/zh_cn/schemas/recipe/fabricating_recipe.schema.json",
  "type": "machine_max:fabricating",
  "ingredients": [
    {
      "ingredient": { "item": "minecraft:iron_ingot" },
      "count": 4
    }
  ],
  "result": {
    "id": "machine_max:structural_component_1",
    "count": 1
  },
  "time": 100,
  "description": "recipe.machine_max.structural_component_1.desc"
}
```

| 字段            | 类型  | 必需    | 默认值   | 说明                                                                                       |
| ------------- | --- | ----- | ----- | ---------------------------------------------------------------------------------------- |
| `$schema`     | 字符串 | 否     | —     | JSON Schema 引用路径，供编辑器提供智能提示和校验                                                           |
| `type`        | 字符串 | **是** | —     | 固定为 `"machine_max:fabricating"`                                                          |
| `ingredients` | 数组  | **是** | —     | 原料列表，每项为原料-数量对                                                                           |
| `result`      | 对象  | **是** | —     | 产出物品，包含 `id`（物品注册名）、`count`（数量，1\~99）、`components`（可选，数据组件）                              |
| `time`        | 整数  | 否     | `100` | 制造台加工耗时，单位为 tick（1 秒 = 20 tick）                                                          |
| `description` | 字符串 | 否     | `""`  | 配方描述文本。通常是在语言文件中定义翻译键（如 `"research.machine_max.ae86_chassis_blueprint.desc"`），此处填写对应的翻译键 |

### 原料选择器

`ingredients` 数组中每项的 `ingredient` 字段支持三种写法：

**1. 物品 ID（简写）**

```json
"ingredient": {
  "item": "minecraft:iron_ingot"
}
```

**2. 标签**

```json
"ingredient": {
  "tag": "c:empty_blueprint"
}
```

**3. NeoForge 数据组件匹配**

```json
"ingredient": {
  "type": "neoforge:components",
  "items": ["machine_max:part"],
  "components": {
    "machine_max:part_type": "machine_max:container_16x16x8"
  },
  "strict": false
}
```

数据组件匹配用于精确筛选具有特定属性的物品，例如要求原料必须是某个特定零件类型的零件物品。

### 零件配方

零件配方的 `type` 为 `machine_max:part_fabricating`。产物零件由文件名推导，因此 JSON 只声明产物数量。

#### 目录与命名约定

| 约定       | 内容                                                        |
| -------- | --------------------------------------------------------- |
| 目录       | 文件必须位于内容包的 `recipe/part_fabricating/` 下，允许再分子目录            |
| 文件名      | 不含扩展名的文件名（只取最后一段，忽略子目录）等于零件 id 的 path                    |
| namespace | 文件所在的 namespace 等于零件 id 的 namespace                      |
| 配方 id    | `<namespace>:part_fabricating/[子目录/]<文件名>`                 |
| 产物声明     | JSON 只写 `result.count`，产物由文件名推导                           |

内容包支持在同一包内放置多个 namespace 的内容，"配方与其零件同 namespace"是对作者的硬约束，不构成组织上的限制。同一 namespace 下两个不同子目录里的同名零件文件会落到同一个零件 id（后加载者覆盖前者），并共享同一条零件配方，因此需要避免同名零件文件。

```
spark_modules/
└── my_pack/
    └── my_mod/
        └── recipe/
            └── part_fabricating/
                ├── my_chassis.json
                ├── my_wheel.json
                └── my_engine.json
```

上例中的 `my_chassis.json` 产物即 `machine_max:part` 加数据组件 `machine_max:part_type = <namespace>:my_chassis`（namespace 取自本包），配方 id 为 `<namespace>:part_fabricating/my_chassis`。`part_type` 不写进 JSON。

#### 顶层字段

| 字段            | 类型  | 必需    | 默认值              | 说明                                                                   |
| ------------- | --- | ----- | ---------------- | -------------------------------------------------------------------- |
| `$schema`     | 字符串 | 否     | —                | JSON Schema 引用路径                                                     |
| `type`        | 字符串 | **是** | —                | 固定为 `"machine_max:part_fabricating"`                                  |
| `ingredients` | 数组  | **是** | —                | 原料列表，每项为原料-数量对（写法同"原料选择器"）                                           |
| `manual`      | 布尔  | 否     | `true`           | 是否用原料装配；为 `false` 时装配材料是本配方的产物整件                                     |
| `result`      | 对象  | 否     | `{"count": 1}`   | 只声明 `count`，即制造台单次产出数量，取值 1\~该零件的堆叠上限                                |
| `time`        | 整数  | 否     | `100`            | 制造台加工或手动组装的耗时，单位为 tick（1 秒 = 20 tick）。手动组装/拆卸的推进速度也会参考此值                |
| `description` | 字符串 | 否     | `""`             | 配方描述文本                                                               |

#### 手动装配材料与折算

`manual` 为 `true`（缺省）时，装配材料取自 `ingredients`，并按 `result.count` 折算成两份清单：

- **组装清单**：每种原料重复 `ceil(原料数量 / result.count)` 次。
- **拆卸清单**：每种原料重复 `floor(原料数量 / result.count)` 次（折算为 0 的条目不返还）。

以 `result.count` 为 1 的典型情况为例，组装一次消耗配方声明的全部原料数，拆卸一次返还全部原料数；`result.count` 大于 1 时二者按比例缩放，使多次推进的总消耗/总返还与配方一致。

`manual` 为 `false` 时，装配材料是本配方的产物整件（`machine_max:part` 加 `part_type` 组件），清单长度恒为 1，与 `result.count` 无关；此时 `result.count` 只影响制造台的产出数量。焊枪会消耗背包中的成品零件填满材料进度，再用焊接时间把组装进度推到 1。

> 制造台自动加工不涉及折算规则——每次加工直接消耗 `ingredients` 声明的完整数量，并按 `result.count` 产出。

#### 完整范例

`manual: true`（缺省）的零件配方：

```json
{
  "$schema": "../../docs/zh_cn/schemas/recipe/part_fabricating_recipe.schema.json",
  "type": "machine_max:part_fabricating",
  "manual": true,
  "ingredients": [
    {
      "ingredient": { "item": "machine_max:structural_component_1" },
      "count": 8
    },
    {
      "ingredient": { "item": "machine_max:power_component_1" },
      "count": 2
    }
  ],
  "result": { "count": 1 },
  "time": 75
}
```

`manual: false` 的零件配方：

```json
{
  "$schema": "../../docs/zh_cn/schemas/recipe/part_fabricating_recipe.schema.json",
  "type": "machine_max:part_fabricating",
  "manual": false,
  "ingredients": [
    {
      "ingredient": { "item": "minecraft:netherite_ingot" },
      "count": 4
    }
  ],
  "result": { "count": 1 },
  "time": 400
}
```

#### 装载期校验

零件配方在装载时会做五项校验，任一失败都会记入错误列表并提示玩家，同时该配方不进入配方列表：它不会出现在制造台配方列表与 JEI 中，改造过的客户端提交该配方 id 也无法建任务。

| 校验       | 失败条件                                                        |
| -------- | ----------------------------------------------------------- |
| 目录归属     | `type` 为 `machine_max:part_fabricating` 但配方 id 的 path 不以 `part_fabricating/` 开头 |
| 类型归属     | 配方 id 的 path 以 `part_fabricating/` 开头但 `type` 不是 `machine_max:part_fabricating` |
| 零件存在性    | 由 namespace 与文件名（最后一段）拼出的零件 id 没有对应已注册零件                    |
| 装配侧唯一性   | 同一个零件 id 出现第二条零件配方                                          |
| 产物数量     | `result.count` 小于 1 或超过该零件的堆叠上限                              |

## 蓝图研发配方

蓝图研发配方（BlueprintResearchRecipe）的 `type` 为 `machine_max:blueprint_research`。它定义研究台中的蓝图研发项目——完成一个研发项目只做三件事：消耗研发材料、扣除研发点、把该项目登记为已完成，本身不产出任何物品。玩家可以在已完成的条目上抄录出 `unlock_recipe` 所指制造配方的制造蓝图（见"抄录蓝图"一节）。

与研究台中的研发项目体验直接对应（参见 [2.6 蓝图系统](../2-载具系统完全指南/2.6-蓝图系统.md)），蓝图研发配方的核心作用是建立"从研发到蓝图解锁"的映射关系。

### 文件位置

```
spark_modules/
└── my_pack/
    └── my_mod/
        └── recipe/
            └── research/
                ├── my_chassis.json
                └── my_wheel.json
```

### 条目显示名

研究台界面里条目的名字取**条目自身注册名**的语言键：把注册名里的 `:` 与 `/` 都换成 `.`。文件放在 `recipe/research/my_chassis.json` 时注册名为 `machine_max:research/my_chassis`，对应语言键：

```json
"machine_max.research.my_chassis": "我的车架"
```

语言键缺失时界面回退显示注册名原文。这个键取的是研发项目自己的名字，与产物名（零件名）无关——同一零件的两个名字可以不同，也可以直接沿用零件名文案。

### 顶层字段

| 字段                     | 类型    | 必需    | 默认值  | 说明                                                         |
| ---------------------- | ----- | ----- | ---- | ---------------------------------------------------------- |
| `$schema`              | 字符串   | 否     | —    | JSON Schema 引用路径                                           |
| `type`                 | 字符串   | **是** | —    | 固定为 `"machine_max:blueprint_research"`                     |
| `research_cost`        | 整数    | **是** | —    | 所需研发点（RP）。不得小于 0                                           |
| `research_ingredients` | 数组    | 否     | `[]` | 研发材料列表，每项为原料-数量对。默认留空，此时完成研发只消耗研发点。只有以既有零件作为研发前提的条目才在此列出该零件（例如强化储物箱列出储物箱 1 个）；空白蓝图属于抄录时的消耗，不写入研发材料 |
| `prerequisites`        | 字符串数组 | 否     | `[]` | 前置项目列表。每项为另一条研发配方的**完整配方 id**（含其所在目录，如 `machine_max:research/ae86_chassis`）。全部前置均已完成时该项目才可研发 |
| `groups`               | 资源路径数组 | 否     | `[]` | 归属组列表，一个条目可同时属于多个组。缺省时归入杂项组（见"`groups`：条目分组"一节）           |
| `icon`                 | 资源路径  | 否     | —    | 项目图标路径，在研究台列表中显示。格式为 `namespace:path`                      |
| `description`          | 字符串   | 否     | `""` | 项目描述文本。通常填写翻译键（如 `"research.machine_max.my_chassis.desc"`） |
| `unlock_recipe`        | 资源路径  | **是** | —    | 抄录该条目时产出的制造蓝图所指的制造配方，写**完整配方 id**                          |

### 前置项目

`prerequisites` 字段用于建立研发树中的依赖关系。每个前置项写另一条研发配方的**完整配方 id**，即该配方文件在 `recipe/` 下的相对路径（见"配方文件命名注意事项"一节），指向另一个蓝图研发配方或通用研究配方。研发配方通常放在 `recipe/research/` 下，因此前置通常写作 `machine_max:research/<名字>`。

```json
"prerequisites": [
  "machine_max:research/ae86_chassis",
  "machine_max:research/basic_engine_tech"
]
```

前置 id 必须能对应到一条已注册的研发配方。直接照抄本条配方的文件名、或漏掉 `research/` 这类目录前缀（例如误写 `machine_max:ae86_chassis`），前置都会永远无法完成，装载期会把该条目记为「前置引用了未注册的研发 id」并判为不可研发。

只有在所有前置项目均已完成的情况下，当前项目才会在研究台界面中显示为可研发。如果某个项目始终不可见或不可用，优先检查其前置项是否已完成。未配置前置则该项目默认可以直接研发。

装载期会校验前置引用并记录错误：前置指向不存在的研发 id、依赖成环（含条目指向自身的自环）、以及依赖环下游的条目都会被判为不可达成——界面标注为「不可研发」，同时在装载期记入错误列表。

### `groups`：条目分组

`groups` 是资源路径数组，声明该条目归属的组。一个条目可以同时属于多个组（例如 `["machine_max:kluo", "machine_max:kluo_gt"]`），它会在每个组的树中各出现一次。

组没有独立的定义文件：组因被配方引用而存在，配方里写了哪些 id 就存在哪些组。组的显示名取组 id 的语言键 `<namespace>.<path>`，例如组 id `machine_max:ae86` 取语言键 `machine_max.ae86`（内容包已有载具名条目时可直接复用该键）；语言键缺失时回退显示组 id。

未声明 `groups` 的条目归入「杂项」组，组 id 为 `machine_max:misc`。

### `unlock_recipe` 的关联机制

`unlock_recipe` 是蓝图研发配方区别于通用研究配方的最重要字段。它指向一条制造配方的**完整配方 id**：零件配方写作 `<namespace>:part_fabricating/<零件名>`，通用制造配方写作它在 `recipe/` 下的注册名。玩家在该条目上抄录时，研究台按 `unlock_recipe` 现场产出对应类型的制造蓝图：

- `unlock_recipe` 指向零件配方 → 产出**零件制造蓝图**（可放置为线框零件并参与装配）；
- `unlock_recipe` 指向通用制造配方 → 产出**通用制造蓝图**（只有凭证与展示语义）。

因此，设计流程上推荐的顺序是：**先定义制造配方，再定义蓝图研发配方，并在后者中通过** **`unlock_recipe`** **指向前者**。

### 完整范例

```json
{
  "$schema": "../../docs/zh_cn/schemas/recipe/blueprint_research_recipe.schema.json",
  "type": "machine_max:blueprint_research",
  "groups": ["machine_max:ae86"],
  "research_cost": 120,
  "prerequisites": ["machine_max:research/ae86_chassis"],
  "icon": "machine_max:textures/icon/ae86/ae86_chassis_icon.png",
  "description": "research.machine_max.ae86_wheel_blueprint.desc",
  "unlock_recipe": "machine_max:part_fabricating/ae86_wheel"
}
```

该配方归入 `machine_max:ae86` 组，在完成 `machine_max:research/ae86_chassis` 的前置研发后可用，消耗 120 研发点（`research_ingredients` 未声明，即不消耗任何物品），完成后可在该条目上抄录 `machine_max:part_fabricating/ae86_wheel` 的零件制造蓝图，每次抄录消耗 1 张空白蓝图。

### 抄录蓝图

在研发标签页中选中一个已完成的蓝图研发条目，点击行内的「取出」按钮（下箭头图标）即可产出该条目 `unlock_recipe` 对应的制造蓝图。取出会抄录一份蓝图并消耗 1 张空白蓝图（`machine_max:empty_blueprint`，标签 `c:empty_blueprint`），产出的蓝图直接进入玩家背包；背包放不下时掉落在玩家脚下。

取出可以反复进行，每次各消耗 1 张空白蓝图，因此蓝图不能免费无限复制。背包里没有空白蓝图时，该按钮为禁用状态。该动作是研究台的内建行为，内容包作者不需要额外配置。

## 通用研究配方

通用研究配方（ResearchRecipe）的 `type` 为 `machine_max:research`。它与蓝图研发配方的区别在于**没有 `unlock_recipe`**——也就是说，通用研究项目不产出任何制造蓝图，界面里也没有取出动作。

通用研究配方的典型用途是作为前置节点出现在研发树中。例如，可以通过一个通用研究作为"基础载具技术"节点，将其设为其他蓝图研发配方的前置条件。

### 顶层字段

| 字段                     | 类型    | 必需    | 默认值  | 说明                           |
| ---------------------- | ----- | ----- | ---- | ---------------------------- |
| `$schema`              | 字符串   | 否     | —    | JSON Schema 引用路径             |
| `type`                 | 字符串   | **是** | —    | 固定为 `"machine_max:research"` |
| `research_cost`        | 整数    | **是** | —    | 所需研发点（RP）。不得小于 0             |
| `research_ingredients` | 数组    | 否     | `[]` | 研发材料列表。每项为原料-数量对             |
| `prerequisites`        | 字符串数组 | 否     | `[]` | 前置项目列表                       |
| `groups`               | 资源路径数组 | 否     | `[]` | 归属组列表，含义同蓝图研发配方              |
| `icon`                 | 资源路径  | 否     | —    | 项目图标路径                       |
| `description`          | 字符串   | 否     | `""` | 项目描述文本                       |

与蓝图研发配方相比，通用研究配方缺少 `unlock_recipe` 字段，其余字段含义相同（包括前置、分组与条目显示名的语言键 `machine_max.research.<名字>`）。

## 装配体与载具蓝图的合成配方

### 装配体合成配方

装配体合成配方是标准的 `minecraft:crafting_shapeless` 配方，用于将多个成品零件在工作台中合成为一个装配体物品。配方文件放在 `recipe/assembly/` 下。

```json
{
  "type": "minecraft:crafting_shapeless",
  "ingredients": [
    {
      "type": "neoforge:components",
      "items": ["machine_max:part"],
      "components": {
        "machine_max:part_type": "machine_max:my_hull"
      },
      "strict": false
    },
    {
      "type": "neoforge:components",
      "items": ["machine_max:part"],
      "components": {
        "machine_max:part_type": "machine_max:my_chassis"
      },
      "strict": false
    }
  ],
  "result": {
    "id": "machine_max:assembly",
    "count": 1,
    "components": {
      "machine_max:assembly_path": "machine_max:my_vehicle"
    }
  }
}
```

`machine_max:assembly_path` 数据组件的值指向 `assemblies/` 模块中的装配体数据（见 [5.7 模板、蓝图与装配体](5.7-模板、蓝图与装配体.md)）。

### 载具蓝图合成配方

载具蓝图合成配方同样使用 `minecraft:crafting_shapeless` 类型，用于将多个零件制造蓝图在工作台中合成为一个载具蓝图物品。配方文件放在 `recipe/blueprint/` 下。

```json
{
  "type": "minecraft:crafting_shapeless",
  "ingredients": [
    {
      "type": "neoforge:components",
      "items": ["machine_max:part_fabricating_blueprint"],
      "components": {
        "machine_max:part_type": "machine_max:my_hull"
      },
      "strict": false
    },
    {
      "type": "neoforge:components",
      "items": ["machine_max:part_fabricating_blueprint"],
      "components": {
        "machine_max:part_type": "machine_max:my_chassis"
      },
      "strict": false
    }
  ],
  "result": {
    "id": "machine_max:vehicle_blueprint",
    "count": 1,
    "components": {
      "machine_max:vehicle_blueprint_path": "machine_max:my_vehicle"
    }
  }
}
```

`machine_max:vehicle_blueprint_path` 数据组件的值指向 `blueprints/` 模块中的蓝图数据（见 [5.7 模板、蓝图与装配体](5.7-模板、蓝图与装配体.md)）。

## 配方在研发树中的串联

对于一个完整的自定义零件，推荐按以下顺序建立配方链路：

```
通用研究（可选前置节点）
    │
    ▼
蓝图研发配方 ──unlock_recipe──→ 零件配方（machine_max:part_fabricating）
    │                                    │
    │ 完成研发后                          │ 制造台 / 手动焊枪
    │ 抄录零件制造蓝图                    │ 产出成品零件
    ▼                                    ▼
零件制造蓝图 ──放置──→ 未组装零件 ──焊枪组装──→ 成品零件
```

对于非零件物品（如合成材料），链路可以更简单——只需要一个通用制造配方（`machine_max:fabricating`），无需接入蓝图研发流程。

## 配方文件命名注意事项

- 配方文件在 `recipe/` 下的相对路径（去掉扩展名）即为配方的注册名，格式为 `namespace:relative_path`。
- 零件配方的文件名决定产物零件：文件名（最后一段）必须等于零件 id 的 path，且必须放在 `recipe/part_fabricating/` 下。
- 通用制造配方的产物完全由 `result` 声明，文件名不参与产物推导。
- `recipe/` 目录内的文件可以任意嵌套子目录（如 `recipe/research/`、`recipe/assembly/`、`recipe/blueprint/`），注册名包含子目录路径。
- `blueprint_research` 配方的注册名不要求与 `unlock_recipe` 指向的制造配方同名——它们是两个独立的配方条目。
