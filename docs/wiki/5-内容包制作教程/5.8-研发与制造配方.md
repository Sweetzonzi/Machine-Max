# 5.8 研发与制造配方

配方（Recipe）是 MachineMax 生存模式流程的支柱。第2.6章已经介绍了玩家视角下的蓝图系统：获取研发点、在研究台解锁蓝图、领取制造蓝图并完成组装。本章面向内容包作者，解释如何在 JSON 中定义这些配方，使自定义零件能够接入研发—制造—组装的完整链路。

MachineMax 的配方分为两类：**制造配方**（`machine_max:fabricating`）用于制造台自动加工和手动焊枪组装/拆卸，**研究配方**（`machine_max:blueprint_research` / `machine_max:research`）用于研究台解锁技术与蓝图。此外，装配体和载具蓝图物品的合成仍使用原版工作台配方（`minecraft:crafting_shapeless`）。

> 配方文件全部放在内容包的 `recipe/` 模块目录下。制造配方必须放在 `recipe/` 根目录，其他可随意。推荐蓝图研发配方放在 `recipe/research/` 子目录，装配体合成放在 `recipe/assembly/`，载具蓝图合成放在 `recipe/blueprint/`。

## 制造配方

制造配方（FabricatingRecipe）的 `type` 为 `machine_max:fabricating`。它同时服务于三种场景：

1. **制造台（Fabricator）自动加工**：放入原料后自动产出零件。但制造台尚未实装。
2. **手动焊枪组装**：手持焊枪对未组装部件推进组装进度，每次推进消耗等比例缩放的原料。
3. **手动焊枪拆卸**：对已组装部件拆卸，每次拆卸按比例返还原料。

### 自动关联

当制造配方文件的文件名（不含扩展名）与某个零件类型（PartType）的注册名匹配时，该配方会自动成为该零件的手动组装/拆卸配方。例如 `ae86_chassis.json` 会与 `machine_max:ae86_chassis` 零件关联。

对于非零件物品的制造配方（如合成材料），文件名不受此限制——它只影响自动关联，不阻止配方在制造台中使用。

### 文件位置

```
spark_modules/
└── my_pack/
    └── my_mod/
        └── recipe/
            ├── my_chassis.json
            ├── my_wheel.json
            └── my_engine.json
```

### 顶层字段

| 字段            | 类型  | 必需    | 默认值   | 说明                                                                                       |
| ------------- | --- | ----- | ----- | ---------------------------------------------------------------------------------------- |
| `$schema`     | 字符串 | 否     | —     | JSON Schema 引用路径，供编辑器提供智能提示和校验                                                           |
| `type`        | 字符串 | **是** | —     | 固定为 `"machine_max:fabricating"`                                                          |
| `ingredients` | 数组  | **是** | —     | 原料列表，每项为原料-数量对                                                                           |
| `result`      | 对象  | **是** | —     | 产出物品，包含 `id`（物品注册名）、`count`（数量，1\~99）、`components`（可选，数据组件）                              |
| `time`        | 整数  | 否     | `100` | 制造台加工或手动组装的耗时，单位为 tick（1 秒 = 20 tick）。手动组装/拆卸的推进速度也会参考此值                                 |
| `description` | 字符串 | 否     | `""`  | 配方描述文本。通常是在语言文件中定义翻译键（如 `"research.machine_max.ae86_chassis_blueprint.desc"`），此处填写对应的翻译键 |

### 原料选择器

`ingredients` 数组中每项的 `ingredient` 字段支持三种写法：

**1. 物品 ID（简写）**

```json
"ingredient": {
  "item": "minecraft:iron_ingot"
}
```

**2. 标签**

```json
"ingredient": {
  "tag": "c:empty_blueprint"
}
```

**3. NeoForge 数据组件匹配**

```json
"ingredient": {
  "type": "neoforge:components",
  "items": ["machine_max:part"],
  "components": {
    "machine_max:part_type": "machine_max:container_16x16x8"
  },
  "strict": false
}
```

数据组件匹配用于精确筛选具有特定属性的物品，例如要求原料必须是某个特定零件类型的零件物品。

### 产出（result）

`result` 的 `id` 指定产出的物品注册名。对于零件，固定为 `"machine_max:part"` 并通过 `components` 中的 `machine_max:part_type` 指定具体的零件类型：

```json
"result": {
  "id": "machine_max:part",
  "count": 1,
  "components": {
    "machine_max:part_type": "machine_max:my_chassis"
  }
}
```

对于非零件物品（如合成材料），`id` 直接填写该物品的注册名，`components` 可以省略。

### 手动组装与拆卸的原料折算

手动组装的原料消耗和手动拆卸的返还并非简单地 1:1 对应配方中的原料数量。模组按以下规则自动折算：

- **手动组装**：每次推进消耗 `ceil(原料数量 / result.count)` 份各原料。
- **手动拆卸**：每次推进返还 `floor(原料数量 / result.count)` 份各原料（返还数为 0 的条目不返还）。

以 `result.count` 为 1 的典型情况为例，组装一次就消耗配方声明的全部原料数；拆卸一次则返还全部原料数。当 `result.count` 大于 1 时，二者均按比例缩放，使多次推进的总消耗/总返还与配方一致。

> 制造台自动加工不涉及此折算规则——每次加工直接消耗并产出配方声明的完整数量。

### 完整范例

一个包含多原料的零件制造配方：

```json
{
  "$schema": "../docs/zh_cn/schemas/recipe/fabricating_recipe.schema.json",
  "type": "machine_max:fabricating",
  "ingredients": [
    {
      "ingredient": {
        "item": "machine_max:structural_component_1"
      },
      "count": 8
    },
    {
      "ingredient": {
        "item": "machine_max:power_component_1"
      },
      "count": 2
    },
    {
      "ingredient": {
        "tag": "minecraft:wool"
      },
      "count": 2
    }
  ],
  "result": {
    "id": "machine_max:part",
    "count": 1,
    "components": {
      "machine_max:part_type": "machine_max:ae86_back_seat"
    }
  },
  "time": 75
}
```

## 蓝图研发配方

蓝图研发配方（BlueprintResearchRecipe）的 `type` 为 `machine_max:blueprint_research`。它定义研究台中的蓝图研发项目——完成研发后，玩家可获得对应制造配方的制造蓝图。

与研究台中的研发项目体验直接对应（参见 [2.6 蓝图系统](../2-载具系统完全指南/2.6-蓝图系统.md)），蓝图研发配方的核心作用是建立"从研发到蓝图解锁"的映射关系。

### 文件位置

```
spark_modules/
└── my_pack/
    └── my_mod/
        └── recipe/
            └── research/
                ├── my_chassis.json
                └── my_wheel.json
```

### 顶层字段

| 字段                     | 类型    | 必需    | 默认值  | 说明                                                         |
| ---------------------- | ----- | ----- | ---- | ---------------------------------------------------------- |
| `$schema`              | 字符串   | 否     | —    | JSON Schema 引用路径                                           |
| `type`                 | 字符串   | **是** | —    | 固定为 `"machine_max:blueprint_research"`                     |
| `research_cost`        | 整数    | **是** | —    | 所需研发点（RP）。不得小于 0                                           |
| `research_ingredients` | 数组    | 否     | `[]` | 研发材料列表。每项为原料-数量对。默认为空，此时仅消耗研发点。通常至少包含一张空白蓝图                |
| `prerequisites`        | 字符串数组 | 否     | `[]` | 前置项目列表。每项为研究配方的注册名。该项目只需要所有前置均完成才可研发                       |
| `icon`                 | 资源路径  | 否     | —    | 项目图标路径，在研究台列表中显示。格式为 `namespace:path`                      |
| `description`          | 字符串   | 否     | `""` | 项目描述文本。通常填写翻译键（如 `"research.machine_max.my_chassis.desc"`） |
| `unlock_recipe`        | 资源路径  | **是** | —    | 解锁的制造配方注册名。格式为 `namespace:recipe_name`。完成后该制造配方的蓝图即可领取     |

### 前置项目

`prerequisites` 字段用于建立研发树中的依赖关系。每个前置项的格式为 `namespace:recipe_name`，指向另一个蓝图研发配方或通用研究配方。

```json
"prerequisites": [
  "machine_max:ae86_chassis",
  "machine_max:basic_engine_tech"
]
```

只有在所有前置项目均已完成的情况下，当前项目才会在研究台界面中显示为可研发。如果某个项目始终不可见或不可用，优先检查其前置项是否已完成。未配置前置则该项目默认可以直接研发。

### `unlock_recipe` 的关联机制

`unlock_recipe` 是蓝图研发配方区别于通用研究配方的最重要字段。它指向一个制造配方的注册名——完成研发后，该制造配方对应的制造蓝图会进入研究成果暂存，供玩家领取。

因此，设计流程上推荐的顺序是：**先定义制造配方，再定义蓝图研发配方，并在后者中通过** **`unlock_recipe`** **指向前者**。

### 完整范例

```json
{
  "$schema": "../../docs/zh_cn/schemas/recipe/blueprint_research_recipe.schema.json",
  "type": "machine_max:blueprint_research",
  "research_cost": 120,
  "research_ingredients": [
    {
      "ingredient": {
        "item": "machine_max:structural_component_1"
      },
      "count": 6
    },
    {
      "ingredient": {
        "tag": "c:empty_blueprint"
      },
      "count": 1
    }
  ],
  "prerequisites": ["machine_max:ae86_chassis"],
  "icon": "machine_max:textures/icon/ae86/ae86_chassis_icon.png",
  "description": "research.machine_max.ae86_wheel_blueprint.desc",
  "unlock_recipe": "machine_max:ae86_wheel"
}
```

该配方在完成 `machine_max:ae86_chassis` 的前置研发后可用，消耗 120 研发点和 6 个结构组件 Lv1 + 1 张空白蓝图，完成后解锁 `machine_max:ae86_wheel` 制造配方的蓝图。

### 重新获取

当某个项目已研发完成、成果暂存已清空但蓝图丢失时，玩家可以在研究台重新获取该项目成果。前提是该项目的研发已完成且没有尚未领取的成果（参见 [2.6 蓝图系统](../2-载具系统完全指南/2.6-蓝图系统.md) 中"蓝图重新获取"一节）。内容包作者不需要对此机制进行额外配置，它是研究台的内建行为。

## 通用研究配方

通用研究配方（ResearchRecipe）的 `type` 为 `machine_max:research`。它与蓝图研发配方的区别在于**不产出制造蓝图**——也就是说，完成通用研究后，成果不会出现在研究台的暂存栏中。

通用研究配方的典型用途是作为前置节点出现在研发树中。例如，可以通过一个通用研究作为"基础载具技术"节点，将其设为其他蓝图研发配方的前置条件。

### 顶层字段

| 字段                     | 类型    | 必需    | 默认值  | 说明                           |
| ---------------------- | ----- | ----- | ---- | ---------------------------- |
| `$schema`              | 字符串   | 否     | —    | JSON Schema 引用路径             |
| `type`                 | 字符串   | **是** | —    | 固定为 `"machine_max:research"` |
| `research_cost`        | 整数    | **是** | —    | 所需研发点（RP）。不得小于 0             |
| `research_ingredients` | 数组    | 否     | `[]` | 研发材料列表。每项为原料-数量对             |
| `prerequisites`        | 字符串数组 | 否     | `[]` | 前置项目列表                       |
| `icon`                 | 资源路径  | 否     | —    | 项目图标路径                       |
| `description`          | 字符串   | 否     | `""` | 项目描述文本                       |

与蓝图研发配方相比，通用研究配方缺少 `unlock_recipe` 字段，其余字段含义相同。

## 装配体与载具蓝图的合成配方

### 装配体合成配方

装配体合成配方是标准的 `minecraft:crafting_shapeless` 配方，用于将多个成品零件在工作台中合成为一个装配体物品。配方文件放在 `recipe/assembly/` 下。

```json
{
  "type": "minecraft:crafting_shapeless",
  "ingredients": [
    {
      "type": "neoforge:components",
      "items": ["machine_max:part"],
      "components": {
        "machine_max:part_type": "machine_max:my_hull"
      },
      "strict": false
    },
    {
      "type": "neoforge:components",
      "items": ["machine_max:part"],
      "components": {
        "machine_max:part_type": "machine_max:my_chassis"
      },
      "strict": false
    }
  ],
  "result": {
    "id": "machine_max:assembly",
    "count": 1,
    "components": {
      "machine_max:assembly_path": "machine_max:my_vehicle"
    }
  }
}
```

`machine_max:assembly_path` 数据组件的值指向 `assemblies/` 模块中的装配体数据（见 [5.7 模板、蓝图与装配体](5.7-模板、蓝图与装配体.md)）。

### 载具蓝图合成配方

载具蓝图合成配方同样使用 `minecraft:crafting_shapeless` 类型，用于将多个制造蓝图在工作台中合成为一个载具蓝图物品。配方文件放在 `recipe/blueprint/` 下。

```json
{
  "type": "minecraft:crafting_shapeless",
  "ingredients": [
    {
      "type": "neoforge:components",
      "items": ["machine_max:fabricating_blueprint"],
      "components": {
        "machine_max:part_type": "machine_max:my_hull"
      },
      "strict": false
    },
    {
      "type": "neoforge:components",
      "items": ["machine_max:fabricating_blueprint"],
      "components": {
        "machine_max:part_type": "machine_max:my_chassis"
      },
      "strict": false
    }
  ],
  "result": {
    "id": "machine_max:vehicle_blueprint",
    "count": 1,
    "components": {
      "machine_max:vehicle_blueprint_path": "machine_max:my_vehicle"
    }
  }
}
```

`machine_max:vehicle_blueprint_path` 数据组件的值指向 `blueprints/` 模块中的蓝图数据（见 [5.7 模板、蓝图与装配体](5.7-模板、蓝图与装配体.md)）。

## 配方在研发树中的串联

对于一个完整的自定义零件，推荐按以下顺序建立配方链路：

```
通用研究（可选前置节点）
    │
    ▼
蓝图研发配方 ──unlock_recipe──→ 制造配方（machine_max:fabricating）
    │                                    │
    │ 完成研发后                          │ 制造台/手动焊枪
    │ 领取制造蓝图                        │ 产出成品零件
    ▼                                    ▼
制造蓝图物品 ──放置──→ 未组装部件 ──焊枪组装──→ 成品零件
```

对于非零件物品（如合成材料），链路可以更简单——只需要一个制造配方，无需接入蓝图研发流程。

## 配方文件命名注意事项

- `recipe/` 目录下的文件名（不含扩展名）即为配方的注册名，格式为 `namespace:filename`。
- 与零件同名的制造配方会自动与该零件关联（用于手动组装/拆卸）。
- `recipe/` 目录内的文件可以任意嵌套子目录（如 `recipe/research/`、`recipe/assembly/`、`recipe/blueprint/`），但注册名仅取文件名本身，不含路径。
- `blueprint_research` 配方的注册名不要求与 `unlock_recipe` 指向的制造配方同名——它们是两个独立的配方条目。
