# 部件公共基础接入

本文说明 Machine-Max 的公共机械部件 API、普通部件边界和扩展接入方式。源码坐标相对于 Machine-Max 仓库根；ARMS-Core 的身体玩法由扩展模组实现。

## 类型和职责

| 对象 | 职责 |
| --- | --- |
| `AbstractPart<T extends AbstractPartType>` | 身份、SubPart、连接点、子系统、共享耐久、模型、动画和信号 |
| `RegularPart` | 普通机械部件的材料、组装、制造配方、线框、载具伤害传递和 HP 贡献 |
| `AbstractPartType` / `RegularPartType` | 公共结构定义 / 普通部件专属参数 |
| `AbstractPartData` / `RegularPartData` | 公共保存状态 / 普通部件保存状态 |
| `PartKind<T,D>` | 一种类型的定义 Codec、保存 Codec、新建工厂、恢复工厂和校验器 |

实现位置：`src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/AbstractPart.java#AbstractPart`、`src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/RegularPart.java#RegularPart`、`src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/PartKind.java#PartKind`。

VehicleCore 的容器和拓扑图只接受 RegularPart。可驾驶机甲可以继承 VehicleCore，通过控制子系统接入运动控制器。混合身体与装备的装配体实现 IPartAssembly；身体核心、默认肢体、身体生命值及姿态驱动由该扩展定义。

## 内容作者的普通定义

`parts` 中省略 `type` 或填写 `"type": "regular"` 都使用 RegularPartType。普通字段、默认值、变体简写及保存字段保持兼容，不需要给普通内容批量添加 type。

显式的未知类型、null、空字符串、非字符串都会解码失败。已识别扩展类型的专属字段错误也会失败。定义分派不会把这些输入解释为普通部件。

MM 的零件物品、零件创造栏、PDA 装配入口仅使用 Regular 定义；制造蓝图创造栏还要求存在有效制造配方。扩展类型使用扩展自己的物品、配方和 Schema。

入口：`src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/PartKinds.java#CODEC`、`src/main/kotlin/io/github/sweetzonzi/machine_max/common/registry/MMCreativeTabs.kt#fabricatingParts`。

## 扩展模组的注册和构造

1. 定义 AbstractPartType 子类，提供命名空间类型 ID，例如 `arms_core:body`；其 Codec 只描述数据。
2. 按实际字段需要定义 AbstractPartData 子类及 Codec。顶层保存 `registry_key`，用于选择已发布定义和保存 Codec。
3. 在模组初始化、内容包读取开始前调用 `PartKinds.register`，交出 PartKind 的各项实现。类型描述的重复 ID 会被拒绝。
4. 实例继承 AbstractPart，并在自己的字段初始化完成后调用 `initializeStructure()`。模型构造、模型事件、连接和子系统构建在这个阶段执行。
5. 如需专属 MoLang 查询，在 `initializeStructure()` 前调用 `bindMolangContext()`，传入 MechMolangContext 子类。每个部件只有一套动画控制器和共享姿态。
6. 恢复构造在结构初始化后调用 `restoreState(data, mode)`；后续专属恢复如果失败，调用 `abortConstruction()` 并抛出错误。该清理不产生库存掉落。

`save()` 返回该类型的状态对象。公共物理代码通过 `permitsSubsystemWork`、`durabilityLimitRatio`、`repairLimitRatio`、`permitsRepair`、`assemblyDamage` 和耐久变化通知调用类型行为，不要求身体对象存在材料进度。

完整接入样例在 `src/main/java/io/github/sweetzonzi/machine_max/common/gametest/PartFoundationGameTest.java#ProbeType`、`src/main/java/io/github/sweetzonzi/machine_max/common/gametest/PartFoundationGameTest.java#ProbeData`、`src/main/java/io/github/sweetzonzi/machine_max/common/gametest/PartFoundationGameTest.java#ProbePart`。这些类型仅由 GameTest 用例注册，不代表正式身体玩法。

工厂入口为 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/PartFactory.java#create` 和 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/PartFactory.java#restore`；保存 Codec 的逻辑侧选择通过 `decodeData` / `encodeData` 显式传入。工厂和公共构造均检查定义对象属于当前发布的一代。

## 完整恢复和骨架恢复

| 策略 | 使用入口 | 状态规则 |
| --- | --- | --- |
| `FULL_STATE` | 存档、客户端重建、收纳物品 | 恢复材料、组装、耐久、涂装、连接器和子系统保存状态 |
| `STRUCTURE_ONLY` | 载具蓝图 | 保留身份引用、SubPart、位姿和连接结构；Regular 使用材料 0、组装 0、线框和默认涂装，不导入保存的库存、电量或装填资源 |

骨架的初始耐久及子系统初值由构造规则决定，并不意味着所有资源数值必须为 0。扩展工厂必须遵守传入策略，不支持某策略时应明确拒绝。

`VehicleData.normalized()` 处理坐标和整车 HP 等归一化，部件动态字段保存在结果中。是否应用这些状态由恢复策略决定，不能用 normalized 代替该判断。恢复不能修改输入 DTO。

实际物品入口：`src/main/java/io/github/sweetzonzi/machine_max/common/item/prop/BaseVehicleItem.java#createVehicle`、`src/main/java/io/github/sweetzonzi/machine_max/common/item/prop/AssemblyItem.java#restoreMode`、`src/main/java/io/github/sweetzonzi/machine_max/common/item/prop/VehicleBlueprintItem.java#restoreMode`。VehicleCore 在分配部件前对整批类型、变体、身份和连接引用预校验，见 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java#validateSavedConnector`。

RegularPartData 的 JSON 字段和二进制字段布局采用普通部件保存契约。公共 Java 类型提取没有增加线上分派字段，因此本轮载荷协议版本保持现有值。验证位于 `src/test/java/io/github/sweetzonzi/machine_max/part/RegularPartDataContractTest.java#jsonAndBinaryPreserveAllStateWithoutChangingWireLayout`。

## 定义的发布和重载

PartModule 的读取结果进入本轮暂存区。读取开始时，本逻辑侧的已发布集合为空，制造和研发缓存同步失效。全部候选就绪后，校验器检查本类型规则，并通过 PartValidationContext 声明必需依赖。

`require(id)` 声明必需部件依赖；`requireConnector(id, variant, subPart, connector)` 同时检查默认连接目标。依赖目标的验证失败时，其所有必需依赖者也不能发布。类型校验器负责自己所声明关系中的循环合法性。

PartDefinitions 一次发布有效集合的只读快照。运行时查找、普通视图和工厂不能取得暂存定义。上一代对象也无法绕过工厂的身份校验。未处理的发布前异常使本轮维持空集合。Spark 的 onFinish 异常捕获用于报告问题，定义安全性由这套发布流程保证。

解码完成之后，`PartModule.read` 调用 `partType.validate()` 做装载期跨引用检查。检查按层分派：`AbstractPartType#validate`（`final`，各 kind 共用）只遍历变体；`VariantAttr#validate` 检查子部件非空并逐个分派；`SubPartAttr#validate` 再分派到连接点、命中框、交互框与子系统。规则依赖模型与子部件区间，不能写在属性构造器里：子系统属性与命中框、交互框都在变体解码过程中构造，此时同级 `model` 尚未解码，`start_bone`/`end_bones` 区间也未计算。检查项包括：变体必须声明至少一个子部件；连接点的 `locator` 必须落在宿主子部件区间内，类型名必须是 `simple` 或 `advanced`，`joint_attrs` 的轴名只能是 `X`/`Y`/`Z`/`XR`/`YR`/`ZR`，`power_target` 与 `signal_targets` 的目标必须能在本子部件内解析为子系统、交互区或连接点（`local` 与 `global` 两个保留地址除外）；相机、炮镜、座位、发射器与照明引用的定位器必须落在区间内，其中照明只在型号的 `range` 与 `intensity` 均大于 0 时才要求定位器；轮驱、炮塔驱动、履带驱动与关节驱动受控的连接点必须存在且为高级连接点；命中框引用的子系统必须存在；交互框的骨骼必须落在区间内且 `interact_mode` 受支持。座位声明的下车定位器缺失与 `hydrodynamics` 计算点无法解析只记录警告，前者下车流程会跳过该候选点，后者运行时退回刚体原点；简单连接点上声明 `joint_attrs` 也只记录警告，关节属性只作用于高级连接点。首个错误以 `PackContentException` 抛出，文件帧由 Spark 补齐（报出形如 `[parts] machine_max:parts/...json @ machine_max:builtin → …` 的模块、文件路径与内容包），该部件不进入暂存区。诊断文案通过 `MMLanguageRegistry#component` 以 `en_us` 为兜底：装载发生在语言表加载之前，纯 `translatable` 在日志里只会渲染出键名并把参数丢光，兜底之后才能读到模型、子部件与名字。

各类型自己的规则由 `ConnectorAttr#validate`、`AbstractSubsystemAttr#validate`、`HitBoxAttr#validate`、`InteractBoxAttr#validate` 提供，签名均为「变体 + 子部件名 + 自身名称」。分层入口：`src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/AbstractPartType.java#validate`、`src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/VariantAttr.java#validate`、`src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/SubPartAttr.java#validate`。

制造索引通过发布就绪状态区分“正在校验”和“已经发布空集合”。校验期间保存配方数据源并推迟重建；发布后严格检查有效 Regular 定义。客户端退出服务器时同时清理配方数据源引用，避免下一次连接复用上一个服务器的数据源。

该规则限制定义查询和新建／恢复，不主动销毁已经存活的实例。实例在内容重载期间的迁移属于装配体生命周期策略。

实现：`src/main/kotlin/io/github/sweetzonzi/machine_max/common/resource/modules/PartModule.kt#onFinish`、`src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/PartDefinitions.java#validateAndPublish`、`src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/PartValidationContext.java#requireConnector`。

## 工具和宿主代理

`PartCreationContext.crowbarRemovable` 决定实例的撬棍许可。普通上下文为 true；身体或不可撬卸装备的构造与恢复上下文可以为 false。这是不可变的构造许可，保存数据不重复记录它；扩展必须在新建和恢复时传递一致的上下文规则。

撬棍先检查许可和 Regular 类型，再执行断连、冲击、摘下和物品产出。焊枪的材料操作只针对 Regular，并在工具损耗前检查类型。维修行为由公共维修许可独立决定。撬棍许可不表达战斗无敌。

装配体通过 `usesMMPartEntities()` 决定自动代理。VehicleCore 使用 MMPartEntity，宿主装配体可以使用自己的渲染和交互代理；该选择同时覆盖身体和 Regular 装备。装配体负责每个部件的主线程动画发布及物理步混合各执行一次。

外部装配体实现 `findPart(UUID)`，并通过 PartAssemblyLookup 注册客户端查找适配器，即可接收 Regular 的材料状态同步。该适配不要求向载具注册表写入对象。涂装同步通过已有 SubPart ID 查询进入公共部件。

入口：`src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/IPartAssembly.java#usesMMPartEntities`、`src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/PartAssemblyLookup.java#register`、`src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/SubPart.java#refreshPartEntity`。

## 验证方式

使用 Java 21 与仓库包装器，命令全部离线：

```powershell
.\gradlew --offline test
.\gradlew --offline build
.\gradlew --offline runGameTestServer
.\gradlew --offline checkSchemas
```

JUnit 的 `PartDefinitionContractTest` 覆盖类型错误、扩展字段往返、依赖失败传播及多代重载；`RegularPartDataContractTest` 覆盖普通保存布局和归一化保真。GameTest 的 `fullStateAndBlueprintSkeleton` 经收纳物品和蓝图入口比较同一份含库存、涂装和损伤的数据；`externalFactoryAndVehicleBoundary` 检查扩展 Codec／工厂、查询上下文、载具拒绝、宿主代理和工具门禁。

GameTest 的模板为 `src/main/resources/data/machine_max/structure/part_foundation.nbt`，批次名为 `mmPartFoundation`。测试部件不加入物理世界，因此这些用例验证构造与状态契约，不测关节动力学或客户端画面。

客户端玩法验收应进入测试世界，依次检查普通部件装配和连接、焊枪维修与材料拆解、喷漆、收纳放置、蓝图放置、进出区块和重连，并核对共享动画及 UI。自动化探针不替代这组画面与交互验收。
