# 武器系统：双端装填预测与同步校正实施方案

**状态：计划中。** 本文定义的客户端自主受理、预测资源记账及成组校正尚待实现。

**代码核对日期：2026-11-17。** 适用仓库为 Machine-Max；下游兼容检查包括 ARMS-Core。本文可作为编码 agent 的独立实施输入。路径均相对 Machine-Max 根目录；Java 源码的公共前缀为 src/main/java/io/github/sweetzonzi/machine_max/。

## 1. 目标、用户决策与交付边界

目标是在已加载武器上，由两端执行相同的装填受理、资源竞争、阶段推进、交付和耗弹规则。客户端使用本地结果播放表现，服务端创建真实投射物、施加真实后坐力并决定最终游戏状态。

用户已经确认：

1. 多管争用采用固定顺序优先，本轮没有公平轮换。
2. 客户端覆盖所有已加载武器，包括观察其他玩家的武器。
3. 射速计时错误与装填预测一起修复，纳入连射验收。
4. nextJobId 进入现有状态同步，客户端在 postTick 统一处理。
5. 预测一致时保留本地先行；确认分叉时重建相关状态。本轮不做历史输入回放或物理回滚。
6. 无需能源的弹药再生与已装 Belt 回充在两端预测。需要付费的产出由服务端决定，客户端没有能源支出预测。
7. 付费产出若在服务端同一 tick 生成并射出，本轮只保证状态正确，允许缺少对应客户端射击表现；本轮没有权威射击补播机制。
8. 零时长的单发装填支持同 tick 多次受理和交付。射速决定射击预算，装填不附加“一 tick 最多一份”的限制。
9. 共享资源的固定优先级采用内容声明序与零件安装顺序；该顺序贯穿保存、恢复、合并和拆分，不以运行时对象地址或全局创建编号决定优先级。

本轮使用 RegenAmmoRackSubsystem、AmmoLoaderSubsystem、LauncherSubsystem、LoaderRoster 和 SeatSubsystem。AmmoRackSubsystem 的物品供弹是 WIP，不扩展它的产品功能。资源定义与存档中的武器语义维持现有契约：单发装填、整份换装、部分份额、人工转机械、暂停超时、普通 Belt 与可回充 Belt 都要覆盖。ARMS-Core 本轮只检查公共 API 与编译兼容，不接管其角色控制或尚未驱动的子系统生命周期。

本文不要求两端整个 Minecraft 世界或 Bullet 世界确定性一致。预测输入是已知的输入、拓扑、人员及资源状态；未知的损伤、上下座、供能与控制权变化通过权威校正收敛。

## 3. 必须成立的不变量

1. 同一有序装配数据、同一已知状态和同一有效输入，受理结果及资源分配一致。安装顺序属于状态，不能把不同安装历史仅因成员集合相同而视作相同输入。
2. 每个提供者满足 0 ≤ R = 各作业预留份额之和 ≤ N；取得预留不扣 N，兑现恰好扣一次，终止恰好释放一次。
3. 一个独占机械槽只归一份活跃作业；同一人物只能推进一份人工工作。并行机械运输按现有 can_supply_multiple 契约执行。
4. 每根 Launcher 的 jobId 为正 int；0 表示无作业。nextJobId 仅在成功受理时推进。失败尝试不耗号。
5. 客户端资源账本属于预测运行态，不能写服务器、背包、伤害、世界投射物或真实能量存储。
6. 同一个射击序号在同一客户端最多触发一次音效、火光、抛壳及开火动画。新加入的客户端只建立当前基线，不播放历史射击。
7. 单次射击可产生多颗投射物；射击序号按射击次数计，不按弹丸数计。
8. 一轮同步只能作为完整的权威采样边界参与校正。一个资源域中的新库存、旧作业和新槽位拥有者不得拼成一份可执行状态。
9. 同一作业的正常确认不能把本地进度、已交付弹药或已消费弹链恢复到较早状态。
10. 暂停、失败、路线失效、人员变化及拓扑迁移都有明确的释放与校正路径。

## 4. 固定顺序与生命周期

### 4.1 两层有序集合

AbstractPart.getAllSubsystems 返回按 SubPart 声明顺序、子系统声明顺序构造的 LinkedHashSet，维持 Set 返回契约与对象去重语义。

SubsystemController 的完整执行序为零件安装顺序，零件内按 SubPart 声明顺序、子系统声明顺序展开。现有 CopyOnWriteArraySet 的安全遍历语义需要保留：控制器持有 volatile 的只读有序 Set 快照，成员变化时在主线程创建保留成员顺序的 LinkedHashSet，一次发布新快照；遍历方捕获当前快照。发布后集合不接受原地修改。不得用 clear 加 addAll 暴露构建中的空集合。

集合的直接写入口统一落在 addSubsystems 与 removeSubsystems；结构变更处理只重建订阅、调用两阶段钩子并重整能源索引，不增删成员、不重排。编码前检索项目与 ARMS-Core 的 allSubsystems 直接访问，维持现有只读查询调用。所有业务、物理遍历及初始化遍历使用同一已发布顺序。成员追加前先检查是否已经存在，不能因重复注册把既有成员移动到队尾。HashSet 可用于成员查重，不能用它的迭代结果生成执行序。

已确认 ObjectManager.removeVehicle 直接调用 allSubsystems.clear；它以及控制器 destroy、discardUninitialized 必须经统一清理入口发布空快照并清理预测状态。DebugCommand.kt 与 ScriptablePayload 的公开集合读取需保持兼容或同步调整。不得只处理 addSubsystems 而遗漏销毁路径。

共享地址继续用于身份和同步寻址，不参与执行优先级排序。结构恢复期间先安装成员；共享 ID、声明序及完整基线就绪后才允许武器预测。有序容器本身不要求先同步 ID。

顺序是装配数据的一部分，具体落点如下：

| 路径 | 顺序契约与实现落点 |
| --- | --- |
| 新建和单件安装 | 按安装事件追加部件；零件内保持内容声明序；重复安装不改变位置 |
| getPartData | 使用 LinkedHashMap，按 partNet.nodes 的节点序构造；节点序只由按序 addNode 建立，不从无序集合批量初始化 |
| RegularPartData.MAP_STREAM_CODEC | 编解码保留线上条目序；decode 使用 LinkedHashMap |
| VehicleData.CODEC／世界附件／物品保存 | 写入明确的 part_order UUID 列表；不能依赖 JSON/NBT Map 的键遍历顺序 |
| VehicleData.rebased | 按输入顺序构造 LinkedHashMap，重定位不改变零件相对顺序 |
| VehicleData.normalized 与 withNewName／withNewUUID／withMeta | 拷贝时透传零件顺序；顺序不能只由 parts 的键序隐含承载 |
| 恢复与创建包 | 校验顺序列表，再按它构造部件和控制器成员；动态 SubPart 状态按名字查找，不能覆盖内容声明序 |
| 合并 | 保留接收方节点序，然后按被吸收方的节点序追加；不得从 donorVehicle.partMap.values 取得优先级 |
| 拆分 | 用旧节点序过滤出每个连通分量；分量按各自最早成员在旧节点序中的位置排列；先按顺序加入该分量所有节点，再添加边，避免 addEdge 隐式加入端点改变节点序；发给客户端的参考部件取该分量的最早成员 |

part_order 只保存部件 UUID 顺序，parts 保持键值查找职责。网络 Map 线上已有条目顺序，可由有序 decode 生成 DTO 的顺序；持久化 Codec 必须显式保存顺序字段。完整、骨架恢复和模板／蓝图路径共用归一化方法。顺序字段存在时必须与 parts 键集合严格相同，重复、缺项和多余项在输入边界拒绝。

旧数据没有 part_order 时，按 UUID 字符串全序建立一次确定性基线；该规则兼容旧数据，但无法恢复没有被保存的历史安装顺序。新编码写出明确顺序。该回退只服务旧格式入口，运行时没有第二条隐式按 UUID 重排的路径。内容包模板就是序列化的 VehicleData，part_order 在其中是可选字段，落点见 §12。

拆分算法中的 HashSet 可以只承担访问标记和成员判定；分量的节点生成不能按该集合迭代。若质量相同的分量需要决胜，按各分量最早成员在旧节点序中的位置决胜；维持既有按质量优先保留载具身份的规则。

所有增删结束后，控制器成员序应等于当前节点序展开的子系统序。这是宿主调用纪律的后置条件，不是控制器执行的重排操作：控制器只持有 level，不持有零件图，也不应知道它。控制器一侧只有三条义务——容器保序、成员追加不移动既有成员、销毁路径经统一入口发布空快照。合并与拆分路径按节点序调用 addSubsystems，后置条件即成立，由 §14.2 的保存→恢复比较断言。

子零件数据里的 connectorData／subsystemData 不参与顺序：恢复按名字查找，子系统安装序来自 partType 声明，有序化不扩散到这两个容器。

零件序与座位序是两套口径：getAllSeats 以部件 UUID 升序为规范序，服务的是座位编号在同一载具生命周期内稳定；武器受理优先级以安装序为规范序，服务的是争用结果可复现。两套都成立，不合并。

### 4.2 固定顺序是资源竞争规则

Launcher 依次受理，成功者即时占资源，后续请求读取更新后的账本。此行为就是用户确认的固定优先级，不引入轮换或新的请求调度框架。

WeaponController 的 Launcher 顺序从控制器已发布的成员序过滤取得，与资源受理优先级一致；不能仅按名字排序，也不另建按全局创建编号的竞争优先级。地址用于区分同名成员。选路继续按预计耗时、运输者地址、提供者地址决胜；选人继续按耗时、座位地址、人物 UUID 决胜。回收旧 Belt 的提供者询问顺序为首选目标，然后按提供者共享地址，去重后逐个询问。

### 4.3 每轮边界

控制器业务轮具有以下顺序：

1. 主线程读取当前有效输入；服务端采样装填候选人员信息，客户端使用已确认候选信息。
2. 按固定集合顺序执行各子系统 onTick，包含免费再生、选路、受理、推进、交付与开火计划。生产者与消费者的相对顺序由上述安装／声明序决定，不另设隐含的端别顺序。
3. 各子系统 postTick 完成业务收尾。
4. 服务端在该边界冻结并发送本轮脏同步批次；客户端在该边界应用待处理权威批次，并完成一次域级校正。

模拟状态、计时、预留与人员认领均由主线程拥有。物理线程消费服务端 pendingFires，创建投射物和施加后坐；客户端表现消费本地已成功射击记录。同步校正不得将历史射击重新入 pendingFires。

公共控制器支持同一生命周期，不允许在公共代码中强转 VehicleCore。VehicleCore 已成对调用 tick 和 postTick。当前核对的 ARMS-Core 只持有 SubsystemController，没有注册成员和驱动 tick/postTick 的运行入口；本轮不能把这一宿主能力误报为现成功能。使用最小非载具 IPartAssembly 夹具验证公共寻址与生命周期，ARMS-Core 做编译兼容检查。

## 5. 运行态与权威基线

客户端需要区分两类已有领域数据的用途：

| 数据 | 所有者 | 用途 |
| --- | --- | --- |
| 当前作业、nextJobId、弹膛、已装 Belt、冷却、预测库存、预留、机械及人员认领 | 原领域对象 | 执行本端本轮规则；HUD 默认读取这份运行态 |
| 收到的同步字段及完整批次元信息 | SubsystemController 的权威基线缓存 | 确认预测、校正、完整重建；不得被客户端模拟消费 |
| 尚未确认的作业收据 | LauncherSubsystem | 记住已受理或本地已结束的作业，用于匹配滞后的权威结果；不保存历史输入或物理状态 |

同步包先进入待应用队列。回调不得直接清空当前作业或把权威弹药写进预测运行态。权威字段在批次完整落地后才供校正读取。普通同步回调和武器校正的职责需在代码中分清，不能同时有两条路径写同一份预测弹药。

收据只保存实际匹配所需的数据：jobId、运输者与提供者地址、冻结规格和 q、请求来源、人工倍率／阶段记录、当前或终态、是否本地交付。终态收据保留到权威确认；每 Launcher 的未确认记录默认最多 256 条，超限采用 §9 的全量重建，不静默丢掉最早身份。此记录不是第二份可执行作业，也不参与推进或再次交付。

实现以现有类的方法与字段为主。跨网络冻结的 record 是允许的；不要建立只有一个实现的预测接口、通用事务引擎或第二套装填状态机。

零时长路径在单轮产生多份收据时使用有序列表，不能只有一个 lastLocalDeliveryId 或最近终态槽。

## 6. 客户端自主受理与资源规则

### 6.1 统一业务入口

两端均从 Launcher.onTick 调用同一个 tickReload 业务流程。该流程在缺少作业且需要弹药或换装时调用 acceptNewJob，执行认领、预留、建作业，并在本轮按现有规则立即推进。普通 Belt 补膛与成功射击消费也共用规则。

端别判断集中在权威发布、真实能源付费、物品／世界副作用和投射物创建边界。客户端不能停留在“收到作业后才开始 tickClientReload”的入口形态。

每轮先做一次常规装填维护；成功射击后立即准备下一发。准备顺序为：从已装 Belt 补膛；若需要取得一份供给，则受理或使用当前作业；零时长作业可以即时交付并回到本轮射击预算循环。正时长作业在常规维护阶段最多获得一次推进，射击循环内新建的正时长作业只受理，首次推进在下一业务轮。射击循环不得重复调用正时长阶段的整 tick 推进。

每轮初始准备与每次成功射击最多各驱动一次新受理；失败尝试、交付拒收或没有获得可射击内容时结束本轮重试。完成最后一发预算后允许准备下一发或启动下一份正时长工作，但不继续射击。零时长请求数量受本轮实际射击数加一次准备约束，不会在零时间失败路径中自旋。一次人工转机械也不能因同轮多发给两个正时长阶段各完整推进一次。

客户端同样执行 WeaponController 的选路。首次完整基线提供选中规格和当前路；后续按本地状态、共同排序和有效选择输入决策。权威路由仅用于匹配或分叉重建，不在每次同步时无条件覆盖预测路。

### 6.2 数字弹药架

RegenAmmoRackSubsystem 持有本端运行态 N 与 reservations。客户端的 reserve、deliverReserved、releaseReservation、holdsReservation 和 returnBelt 与服务端遵循相同数量和身份规则；客户端交付创建独立 AmmoBelt，不产生真实物品。

getAmmoCount、getReservedTotal、getAvailableCount 读取运行态；发布同步值由服务端完成。库存不能在客户端模拟时直接从即刻更新的 SynchedEntityData 读取。

免费再生及其 delay、逐发或整批模式在两端运行；付费分支等待权威产出，不调用客户端 EnergyGrid 扣费。已装 Belt 的免费回充也在两端运行，付费回充只接受权威产出。

为了接收权威 N 时保留本地已发生的交付，架上维护本轮运行期累计数量：producedRounds、returnedRounds、deliveredRounds。成功产出、实际收回、成功兑现分别推进各自累计数；数值使用非负 long。初始库存作为基线，不计作 producedRounds。强制损失、装载外部库存或殉爆等非预测业务改变库存时提升 stockEpoch，并要求相关域重建。

同一 stockEpoch、作业收据均匹配且权威累计数没有越过本地累计数时：

    预测 N = 权威 N
           + 未确认的本地产出数量
           + 未确认的本地收回数量
           - 未确认的本地交付数量

每项未确认数量是本地累计数减去权威累计数；这些累计数按数量计，不能按调用次数计。运行态预留表由本地当前活跃作业持有，不把权威 R 再加一遍。若投影后违反 0 ≤ R ≤ N，或累计数／收据无法对应，走重建。

同步快照还必须带免费再生进度、整批标记及进度、剩余延迟，以便完整重建。正常匹配确认保留本地先行的连续进度；付费产出到达导致权威越过本地时，可直接使用重建路径。生产序列使用 producedRounds 的连续范围，批量数量决定范围长度，不另建同义计数器。确认范围之前必须校验对应的免费／付费模式及已匹配的作业收据；累计数量公式不是跳过业务匹配的理由。

### 6.3 机械槽

AmmoLoaderSubsystem 两端维护 claimedJobs。独占与并行的差别只由 can_supply_multiple 决定。claim 不能在客户端恒成功；getAdvanceTicks、holdsCommitment 与 isClaimedByOther 都读本端账本。正常完成只释放对应 key。

同步的槽位状态是权威基线，不能在正常确认中撤掉客户端较晚作业占有的槽。全量重建时从权威活跃作业重建占用：机械阶段占机械资源；人工阶段按现有规则占人员。重建后的槽位拥有者必须与权威槽位字段相容，矛盾表示批次或基线不完整。

### 6.4 人员候选与认领

SeatSubsystem 提供一个不可变装填候选快照：人物 UUID、是否可作为存活执行者、个人时间倍率。座位及宿主的启用／损坏、安装表中的岗位倍率沿用已有数据。服务端每轮业务采样；人物或倍率变化时发布。客户端候选读取不依赖 passenger 引用，也不能仅凭 occupied 推断存在一个倍率为 1 的装填手。

LoaderRoster 共用同一候选过滤、耗时计算和 ReloadCrewSelection 比较。服务端人物认领沿用 CrewReloadAttachment 的身份契约；客户端按人物 UUID 维护预测认领，作用域为客户端 Level，使跨装配体换座期间同一 UUID 也不会同时被两份预测作业取得。该表可由 ObjectManager 承载并在 Level 卸载时清理；不需要新的服务接口。只在读取、保存实体认领的边界区分端别，业务条件必须等价。

人工推进为 1 的前提是本端这条作业确有有效认领。选不到人时推进为 0；换人时共用剩余时间折算。服务端暂停／恢复、阶段切换与倍率变化都发布当前进度、时长和运行标记。客户端已越过这项权威决策时，按 §9 判分叉，而非靠人工段继续空跑来等待超时结果。

域重建或换座时，人员预测表只按 UUID 与原 jobKey 同时匹配释放；不能清除该 UUID 已在另一装配体取得的新认领。

人员认领必须能从完整权威样本恢复到具体 UUID 和 jobKey；只恢复“这个座位有人”不足以重建资源。不要在客户端创建假的 LivingEntity 或虚构 passenger。

### 6.5 已装 Belt 与独立膛内弹

供弹实例身份取同步代次与交付 jobId；初始存档中的实例用该代次的初始标记 0。Belt 不需要额外随机 UUID。普通补膛会从 Belt 移出一发，空膛开火直接消费可回充 Belt 的额度，两种路径都只能记一次消费；独立膛内弹的射击不能重复扣当前 Belt。

Launcher 对当前实例记录 beltTakenRounds 与 beltRechargedRounds，分别累计从 Belt 移出的数量和成功回充的数量。普通补膛在移出时记账，不能等射击时又记一次。同步样本携带实例身份和两项计数。

同实例且业务前缀匹配时，剩余量按“权威剩余 + 本地未确认回充 - 本地未确认移出”合并，范围必须在 0 到 length 之间；回充延迟和零碎进度保留合法的本地先行。付费回充使权威计数超过本地时采用重建。客户端已按匹配收据换入后续实例时，旧实例样本只确认对应历史，不覆盖新实例。无法匹配或数量越界时重建。

整份换装保留现有独立膛内弹契约，直到该发射出；其来源身份与已装新 Belt 身份分别保存。换装提交时向数字架返还旧 Belt 的数量参与 returnedRounds，不能用当前新 Belt 的数量或一次较早的余量样本代替。

## 7. nextJobId、请求因果与收据

### 7.1 编号分配与同步

nextJobId 保持每 Launcher 的正 int，初值为 1。两端在执行资源和预留均取得成功后建作业，使用该值为 jobId，然后递增。失败路径释放已取得资源，不递增。

Launcher 的同步字段表追加 NEXT_JOB_ID；服务端 nextJobId 是权威计数，客户端另有执行本地受理的运行值。字段只在编号改变和全量基线时发送，postTick 与作业、结果共同处理。

相同输入和状态下两个计数会相同，但网络确认不是逐字段强制相等。客户端已经完成 k、开始 k+1 时，服务端可能才确认 k。此时不能把本地 nextJobId 从 k+2 写回 k+1。也不能把 max(local, remote) 当作所有情形的修复：真实分叉时，错误占用和作业身份也要一起处理。

### 7.2 足以核对编号的权威事实

除活动 ReloadJobSync 外，每 Launcher 提供：

| 字段 | 语义 |
| --- | --- |
| NEXT_JOB_ID | 服务端下一个成功受理使用的编号 |
| 最近受理判定 | 候选编号、请求来源、是否实际尝试、成功／未受理及原因 |
| 本批有序终态收据 | 每份的完整冻结分配、jobId、交付成功或终止；同 tick 多次即时交付全部保留 |
| 成功射击累计序号 | 服务端实际提交的射击计划序号，用于因果、校正和表现去重 |
| 冷却样本 | 以 §11 的整数子 tick 单位表示的剩余量 cooldownU；相位及连射状态仅作匹配和重建，不传两端 tickCount 原点 |

“请求来源”必须能区分旧状态与客户端未来需求。使用成功射击累计序号和有效弹种选择输入的身份，另记请求种类（首次装入／补充／整份换装）。输入身份包含来源 UUID、控制代次和该来源序号，不能只比较不同玩家各自的裸序号。自动补充记录导致缺弹的射击序号；整份换装记录选中规格的输入身份；初始装入使用初始基线代次。等待资源时保持同一来源，不每 tick 虚构一次新请求。

这些字段描述已存在的业务因果，不产生一条装填请求网络 RPC。接收“未受理”时，只有服务端已经评估同一个请求来源，才可否决本地预测作业。服务端尚未执行导致该需求的射击或选择输入时，较小的 NEXT_JOB_ID 只是较早确认。

### 7.3 编号匹配表

| 收到的权威事实 | 客户端处理 |
| --- | --- |
| 活动作业 k 与当前或未确认收据 k 的来源、分配一致 | 确认前缀；保留本地进度、已交付／消费内容及后续作业 |
| 成功终态 k 与本地成功交付收据 k 一致 | 确认该收据；不再次交付，不恢复曾经射掉的弹 |
| 服务端尚未到本地请求来源 | 保留待确认预测；不回退 nextJobId |
| 服务端对同来源、同候选编号明确未受理 | 该预测分叉；重建资源域 |
| 同编号的来源、运输者、提供者、冻结规格、份额或终态不同 | 该预测分叉；重建资源域 |
| 权威状态已越过本地且没有可验证收据 | 使用完整权威基线重建，不猜测缺失历史 |
| 初次加载或记录超限 | 全量基线重建，不补播历史表现 |

正常确认完成后，本地 nextJobId 保留本地未确认尾部的合法值；不存在本地尾部时才与权威值对齐。分叉重建时直接采用权威 nextJobId，并清除本域的预测尾部及其资源承诺。

同一 jobId 内的阶段或倍率变化是权威业务决策。普通先行进度不构成分叉；明确暂停、不同人员选择、不同阶段分配或时长变化需要校准。零时长作业可以没有活动快照，必须靠终态收据完成匹配。

同批收据按受理顺序逐份确认，最后才处理最终活动作业与 nextJobId。所有中间即时交付都要能与本地收据对应。同一候选编号的重复未受理样本不消耗编号；本轮最后一次未受理保留其请求来源和原因。重复收到已经确认的收据不再次合并库存。

终态列表的序列化器可在列表内部复用相同冻结分配模板，条目以小整数引用模板并携带 jobId、请求来源和结果，避免即时多次交付重复编码整份弹药模式。该字典只用于一份列表的编码与解码，不产生第二套运行时弹药定义或逐发射击载荷。

编号不得溢出为 0 或负数。接近 int 上界时由服务端开启新的同步代次并发送完整域基线，然后从 1 分配；代次之间的预测记录和迟到包不得混用。此边界用参数化的小编号上限验证，不运行数十亿次测试。

## 8. 现有同步机制的成组边界

继续使用 SynchedEntityData、各类 EntityDataAccessor 和已登记的字段序列化器。字段编号在末尾追加，禁止在类层次中重新排列已有访问器。网络协议组按实际修改提升版本；当前基线为 input:3.0.0、sync:11.0.0，实施时以工作树实际值为准。

将现有 SubsystemSyncPayload 的发送单元定义为同一个 SubsystemController 的一轮批次。每个条目继续使用 (subPartId, subsystemIndex, DataValue 列表)，外层包含装配体身份、同步代次、递增批次序号、服务端采样步和 full 标记。复用现有编解码，不为每个武器另建一条射击事件通道。

服务端 AbstractSubsystem.onTick 执行业务与基类逻辑；脏字段的打包由控制器 postTick 统一完成。每次业务离散变化采样同一时刻的相关字段，尤其 nextJobId、活动作业、终态、弹膛／Belt、库存累计量及资源占用。正常推进的进度只在阶段、暂停／恢复、时长变化等离散点发送；全量样本含精确当前进度。

这是公共基类同步相位的改动，影响全部 AbstractSubsystem 实现及下游扩展，不能只验武器。不能概括成“整体晚一个业务步”：业务入口前已经写入的值从本轮开头发到本轮末尾；onTick 内业务产生的值则可在本轮末尾发出，免去原发送位置带来的一轮等待。客户端统一 postTick 落地也有自己的消费边界。

非武器同步的目标契约是：采样前已提交的变化进入该完整批次，客户端在收齐后的首个可应用 postTick 落地；业务 onPostTick 写入的值也必须被该轮第二遍采样看到。不得额外等待一个服务端或客户端业务轮，字段回调不得重复。座位占用、工作／毁坏状态和发动机工况反馈分别做回归；这些测试固定的是完整采样边界与最终行为，不要求复制基类开头发送的具体时刻。

客户端先将完整批次排队，postTick 按批次顺序更新权威缓存并校正。不能用几个 pending 布尔覆盖掉同一客户端 tick 收到的多轮作业终态；零时长作业与快速先后两份作业都必须保留顺序。网络大包如需分片，应在完整重组后提交，分片不是可应用的状态。

冻结与发送采用两遍：先完成所有子系统本轮业务收尾，再按受影响资源闭包采样动态字段，最后统一 packDirty。不能在逐个执行 onPostTick 的同时立即打包该子系统，因为后面的收尾可能改变同一份资源。

参与一份武器批次的闭包内，当前进度、冷却、再生、库存和占用都应采样到本轮边界。未变化的冻结规格可从上次完整基线引用；开工时保留的 elapsed=0 不能冒充当前进度参与重建。可将常变的作业进度样本与冻结规格分开编码：动态样本带 jobId 和阶段身份，必须对应同批权威缓存中的静态作业。闭包没有离散变化时不为推进进度而每 tick 广播。

| 所有者 | 必须能够冻结或恢复的状态 |
| --- | --- |
| Launcher | 既有路由、膛内弹、Belt 及各自来源；Belt 的移出／回充累计量；nextJobId；活动作业的冻结分配与动态进度；本批终态列表；最近受理判定及来源；shotSequence；相对冷却 |
| 数字架 | N 与 R；stockEpoch；三项累计数量；免费再生状态；付费产出确认 |
| 机械运输者 | 独占槽的权威拥有者；并行占用可由本批所有机械阶段活动作业导出；人工阶段的具体认领 |
| Launcher 的人力运输者 | 认领的座位地址、人物 UUID 及 jobKey；阶段倍率 |
| 座位 | 装填候选 UUID、存活可用标记及个人倍率 |
| 武器控制器 | 选中规格、选择输入身份及已认可的控制来源／有效扳机门 |

完整恢复时，按所有活动作业的 provider 与 q 导出预留表，以权威 R 校验，不必再下发一份内容相同的预留表。资源账本的构造必须等待完整闭包，而不是在第一个作业回调时立即开始竞争。

pushAllTo 在统一采样边界生成只读全量样本，不修改全局脏标记或把特定玩家需要的进度写回广播基线。首次基线完成前不受理预测作业；现有可信弹膛的表现可按初始化契约处理，但不得凭空推导库存。

完整基线请求使用只读的 SubsystemBaselineRequestPayload，参数只含装配体身份、可解析的成员地址及客户端已知代次。服务端验证所在 Level、对象归属和同步资格，按玩家／装配体限流；请求不能携带库存、作业或反向写状态。每域只保留一个在途请求，重复故障不会每 tick 发送。已有创建补发继续调用 pushAllTo，共用完整样本生成路径。

域通过条目宿主的 ISubsystemHost.getSubsystemController 与 IPartAssembly.getAssemblyId 定位，不能只查询 VehicleCore。结构迁移使同步代次失效；新代次首包为完整基线。缺少成员时整批等待结构就绪，不能只应用一半资源；同域 FIFO 等待有界，超限清理该域队列并请求最新全量样本。

## 9. 校正范围与无回放重建

### 9.1 哪些状态需要一起重建

域的最小单位是共享装填资源的闭包：发射器、其候选运输者和提供者、共享装填手，以及这些资源服务的其他发射器。第一版允许直接使用所在 SubsystemController 的全部弹药相关状态作为闭包，避免漏掉竞争者。车体位姿、Bullet 状态和其他子系统业务不参与回滚。

分叉时先停用本域本地作业的提交，按 key 释放预测预留、机械槽及人员认领，再从完整权威缓存恢复：路由与所选规格、活动作业、nextJobId、弹膛、Belt、库存和再生状态、累计数量、槽位、人员、冷却及成功射击序号。恢复完毕检查 §3 的资源不变量，再允许下一业务轮自主受理。

这里不会重新执行过去的 tick，不重放历史按键，不把权威的历史射击送进物理队列。校正时保留当前实际按住的本地输入，等待下一轮按已恢复状态重新求值；权威已明确拒绝的控制来源不得自动恢复。

冷却同步使用采样边界的相对剩余量，以整数子 tick 单位下发，不把服务端 tickCount 直接赋给客户端时钟。分叉或首次基线恢复时采用权威 cooldownU，连射相位置于待初始化状态，下一实际业务 tick 按 §11 播种；这种无回放重建可能带来一次额外等待。正常匹配确认保持本地相位和进度，不能借恢复函数每次重启计时。收到的采样步用于版本与诊断，不等同于本机刚完成的 tick。

### 9.2 确认时的数量合并

匹配作业收据后，先推进权威确认边界，再依据 §6.2 的累计数量计算本地尾部。该过程不再次调用 deliverReserved 或 returnBelt。装弹机及人物继续保有属于本地后续作业的预测认领；旧作业 k 的释放不能删除 k+1 的占用。

完整比对使用字段值，不能以对象引用或一个未经校验的 hash 相等当作成功。Belt 的冻结规格比对必须涵盖影响交付的容器身份、模式、长度及回充配置；已有 AmmoBelt.compareSpec 没有比较全部回充数值，不能直接充当收据的完整一致性判据。

明确失败或暂停与本地结果矛盾时重建；仅因权威进度小于客户端进度不能重建。免费生产序列、外部 stockEpoch、来源和人员相容性也参与判定，防止只看 nextJobId 就接受一份内容不同的预测。

### 9.3 迟到与付费边界

批次序号去重，旧代次直接丢弃。TCP 已提供连接内有序可靠传输；这里的队列、序号服务于业务采样与身份核对，不另做逐发 ACK 或 UDP 重发协议。

付费产出确认可让权威库存或成功射击序号超过本地。使用重建收敛；客户端没有预支付费额度，也没有用序号差补射击表现。已经发出的预测声音不能撤销，这属于用户接受的分叉表现纠正边界。正常免费资源分支不得依赖这个例外掩盖系统性漏表现。

## 10. 输入镜像

所有已加载武器运行相同装填规则，不等于把本地玩家输入套给所有武器。每条输入保持原控制来源、宿主地址与路由。

通用主副武器按键在 RawInputHandler 中同时投递本地对应方法和上行包；自定义 ControlBinding 保持本地即时投递。服务端校验控制权与地址，认可后把同一语义事件发送给相关客户端，包含旁观者。

两条输入路径共用每玩家单调递增的输入序号，载荷保留按键或 bindingIndex、按下／松开语义和原控制地址。服务端与客户端按来源、控制代次和序号去重。本地玩家收到自己的认可回声时只确认，不再执行一次 toggle、切弹或 hold 边沿；旁观者执行一次。拒绝或控制权变化通过状态同步使本地输入来源失效。

晚到的旧座位事件不能影响新座位。AI 与服务器产生的信号没有本地玩家序号时，以服务端发布的来源代次和事件序号镜像。有效扳机门若在物理线程改变，沿用跨线程事件队列发布到主线程，按顺序保留开／关边沿，再进入输入镜像批次。只镜像影响选弹／装填／射击的有效控制事实及必要目标数据，不广播伤害归属 Entity 引用。

本轮不扩展物理瞄准回滚；武器朝向、能否瞄准等外部判定短暂不同可以导致预测分叉，但完整数据下的装填状态机不得依赖物理线程遍历的对象 hash。

## 11. 射速与成功射击序号

### 11.1 相位与防连点状态

调度只依赖实际执行的业务 tick，不使用墙钟、System.nanoTime、Level.gameTime 或子系统创建时的 tickCount 原点。每 tick 有 U = 1,000,000 个子 tick 单位，intervalU = round(1200 × U / RPM)。

phaseU 表示本次连射累计的相对相位；cooldownU 表示上一业务边界距下一发的剩余量，用于跨松键、失效和换装的防连点约束。另有原始 triggerHeld、本次连射 burstActive 和本轮实际 firedCount，不能让 wasFiring 同时表达这些含义。

phaseU、cooldownU 和 intervalU 使用 long，但它们都是有界相对计数，不是绝对时间。RPM 必须正且有限；计算结果要能在 long 中容纳 intervalU 加 U，且 intervalU 至少为 1，边界在 BreechModuleAttr 解码／构造入口验证。现有 Codec.FLOAT 没有 RPM ≥ 1 的约束，例如 0.1 RPM 的 intervalU 约为 1.2×10^10，不能声称 int 普遍足够。没有额外的“最低 1 RPM”产品限制。

### 11.2 每业务 tick 的精确规则

完整暂停时没有业务 tick：相位、冷却和装填进度均不推进，恢复不补墙钟经过的时间。多人游戏只打开菜单但世界未暂停时，按实际业务 tick 正常推进。

    若本轮武器不可用、换装锁定，或 triggerHeld 为 false：
        phaseU = 0
        burstActive = false
        cooldownU = max(cooldownU - U, 0)
        firedCount = 0
    否则：
        firedCount = 0
        若 burstActive 为 false：
            phaseU = clamp(intervalU - cooldownU, 0, intervalU)
            burstActive = true
        phaseU += U
        while phaseU > intervalU：
            若按 §6.1 准备后依然没有可射击内容：
                phaseU = intervalU
                break
            成功消费并提交一发
            phaseU -= intervalU
            firedCount += 1
            按 §6.1 准备下一发
        cooldownU = intervalU - phaseU

循环使用严格大于：恰好落在本业务步右端的发射留给下一业务步。初始状态 phaseU=0、cooldownU=0、burstActive=false，第一次按下播种为 intervalU，因而立即有首发；高射速也能消费本业务步内的其余预算。每次只扣成功发出的数量。

正常连射必须完整保留除法余量，不能每 tick 把相位截到 max(intervalU, U)。只有已经到发射点却确实缺弹时，才把逾期量收敛为“当前已就绪”的 intervalU，避免蓄积历史欠发。缺弹不清零相位或扳机事实，下一步可发数量只来自该步预算与就绪的一发；能否连续多发还取决于本地真实供弹。

结束一次连射时 phaseU 归零，cooldownU 保留并按实际业务 tick 递减，因此快速连按不能重置低射速武器的间隔。刚好到期即能发射，不添加一个完整新间隔。失效／换装也不能通过归零冷却绕过该约束。

intervalU 随模块受损或升级改变时，按新周期结算当前轮：先把 cooldownU 夹到 [0, intervalU]，再按上式推进；换周期那一轮的相位不超过 intervalU + U，避免一次换型号在单个业务步里补发历史预算。缺少这两条夹紧时，冷却大于新周期会让播种相位为负，周期变小则会让相位远超新间隔。

120 RPM 在 0 发射、9 tick 装填完成时，下一发在 10；6000 RPM 连续供弹每个完整业务 tick 为 5 发。900、4000 RPM 等非整 tick 周期保留相位余量，按量化后的 intervalU 验证长期发数及逐发间隔；首发和右端归属引起的有限窗口差异最多一发，不能接受固定降档。period 舍入误差与每 tick 丢余量是两件事，测试必须区分。

同步只传该边界的相对 cooldownU 等状态。正常确认保持本地相位，硬重建按 §9 初始化；客户端比服务端晚创建、单人暂停或两端 tickCount 数值不同，不需要时钟原点换算。

### 11.3 射击与表现事实

每次成功消费并提交本端射击计划时推进 shotSequence。音效和火光从这一步的本地事实产生，不通过“弹膛同步从有到空”推断。重建后 shotSequence 可采用较小的权威值，但本客户端已播放水位不回退，避免同序号重复表现。水位按同步代次隔离；正常确认不清零。

表现次数的测试针对成功射击事实的调度和去重。自动武器可以使用连续循环音效、合并光源或同轮动画更新，不要求每一发创建独立声音实例；这些持续表现的启动、维持和结束必须由本地真实成功射击及停火状态驱动。

付费产出、首次基线或真实分叉造成的序号缺口不触发补播。这个序号同时为 §7 的补充请求提供因果身份。

本轮不承诺把主线程同 tick 的多发分散到多个 Bullet 子步。pendingFires 的物理消费架构维持现有形态；高射速验收分别检查逻辑发数与实际弹丸数，不能把网络批量正确等同于子 tick 物理时刻精确。

### 14.2 GameTest 与下游

复用现有 Ammo 路由、人物与结构用例，检查服务端权威受理、恢复、共享资源与同步全量快照。测试类保留在 common/gametest，普通 JUnit 保留在 src/test；发布产物排除规则继续生效。

至少一条保存→恢复 GameTest 比较实际 allSubsystems 的成员身份序列；另覆盖含共享资源的合并／拆分，再比较各目标的执行序。序列比较按持久成员身份和声明位置进行，不能因一次恢复分配了新运行 ID 就误报优先级改变。

至少检查 VehicleCore 和一个最小非载具 IPartAssembly 夹具的控制器注册、tick/postTick、全量同步定位；ARMS-Core 需要能够编译并运行其适用回归。本文不要求为 ARMS-Core 接入完整子系统驱动，也不让它的角色运动状态机参与武器预测。

### 14.3 双客户端实机

本地操作者与独立旁观客户端同时观察：人力单发、机械单发、整带供弹、高射速、多管共享资源、切弹、上下座、损伤／恢复及载具合并拆分。先测零额外延迟，再测人工增加的稳定延迟和抖动；不得用单人整合服务端替代全部联网验收。

日志至少包含：端别、同步代次及批次、输入来源序号、shotSequence、请求来源、jobId 与 nextJobId、完整共享地址、N/R、受理成功／未受理原因、推进前后进度、人员 UUID、结果匹配／分叉原因、重建域范围、表现去重水位。

正常免费资源场景核对服务端成功射击数、客户端预测射击数与表现次数；同 tick 多发按次数比对。状态基线初始化、真实分叉及付费例外单独计数，不能混进正常循环的通过率。记录同步包数、编码后应用字节数、活跃武器和接收人数，验证没有逐发独立开火包或每 tick 完整历史广播。

## 15. 执行命令与最终交付

所有 Gradle 命令带 --offline，使用仓库 wrapper 和 Java 21。本机缓存路径需要显式指定时，仅为命令配置正确的 Gradle user home，不改仓库的通用构建配置。

    .\gradlew --offline test
    .\gradlew --offline runGameTestServer
    .\gradlew --offline checkContent checkSchemas
    .\gradlew --offline build

ARMS-Core 的适用回归在其仓库执行。schema 与内容 JSON 若本轮没有变化，不进行无关迁移；如确有字段扩展，依仓库规则同步 schema。

编码 agent 最终报告应列出已完成阶段、行为变化、完整测试结果、双客户端实测证据、网络量级、付费产出例外和其他未覆盖边界。文档中的计划状态按真实代码交付更新；不能仅凭编译通过或单次正常点射宣布预测闭环完成。

本节记录本方案的具体审阅决策，比较基线完整列在表内。所有决策只修改计划，生产代码尚未实施。

| 编号 | 审阅意见或原方案基线 | 复核与处理 |
