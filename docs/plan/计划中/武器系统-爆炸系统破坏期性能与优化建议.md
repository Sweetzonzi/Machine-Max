## 一、本文要解决的问题

`武器系统-爆炸系统详细设计.md` §十五「性能预算」为爆炸系统建立了成本模型，覆盖两个通道：DDA 体素遍历（纯数学，随 `rayCount × advancePerStep` 增长）与快照 `contactTest` / `rayTest`（native 调用，靠粗筛压到「确实靠近刚体的射线」）。**该章没有覆盖第三个通道：方块被摧毁之后发生的事。** 这个通道的成本随**被摧毁的方块数**增长，而不是随射线步数增长；在现有模型里它是零。

本文补上这一通道，给出：

1. 完整的破坏期成本模型与调用链（§二）；
2. 一个与既有设计表述**不冲突**的边界说明——既有文档 §3.2 写「为一次爆炸唤起地形构建不划算」，读者可能据此认为破坏期没有地形开销，本文说明那句话的适用范围（§三）；
3. 可执行的测量口径（§四）；
4. 按风险与收益排序的优化候选，区分「严格等价」与「需要设计裁定」（§五、§六）；
5. 一条硬约束（§七）。

## 二、破坏期成本模型

### 2.1 完整调用链

一次爆炸的方块摧毁路径（`common/mech/explosion/ExplosionInstance.java#execute` 起）：

```text
ExplosionInstance.execute()
  └─ level.removeBlock(pos, false)
       └─ Level#removeBlock → setBlock(pos, fluidstate.createLegacyBlock(), 3)          // flags = 3
            └─ LevelChunkSection#setBlockState(...)                                     // 真正的数据写入
            └─ Level#markAndNotifyBlock
                 ├─ (flags & 2) sendBlockUpdated  → ClientboundBlockUpdatePacket      // 每方块一个包
                 ├─ (flags & 1) blockUpdated      → 邻居更新                            // 每方块
                 └─ Level#onBlockStateChange(...)                                        // 无条件的
                      └─ ServerLevelMixin#onBlockStateChange                             // Spark-Core
                           └─ PhysicsChunkManager#onBlockUpdated(Set.of(pos))
                                ├─ markDirtySections(sectionPos)                         // 每方块
                                ├─ chunkHeightIndex.updateSection(...)                   // 每方块
                                └─ submitDeduplicatedTask("terrain_update_activate_" + blockPos.toShortString(), …)  // 每方块
                                     └─ contactTest(activator)                           // native，每方块
```

**关键事实：`Level#onBlockStateChange` 不在任何 flag 分支里**，它是 `Level#markAndNotifyBlock` 里与各个 flag 分支并列的无条件调用。`Level#removeBlock` 的第二个参数只影响 `flags` 是否含 64（`| (p_46624_ ? 64 : 0)`），**不影响地形同步**。因此：只要破坏走 `level.removeBlock` / `Level#setBlock`，Spark-Core 的地形脏标记与激活就**逐方块**发生。

### 2.2 完整成本表

在既有 §15.1 四行之上补入标记为 **◆** 的行：

| 通道 | 单位成本 | 每 tick 次数 | 与地形有关 |
| --- | --- | --- | --- |
| DDA 体素遍历 | 纯数学，极低 | `rayCount × advancePerStep` | 是 |
| 快照 `contactTest`（粗筛） | 1 次 native 查询 + narrow phase | 1（每爆炸每 tick 一次） | **否** |
| 快照 `rayTest`（粗筛后） | native 调用 | 仅「本 tick 够得到的刚体附近」的射线 | **否** |
| 逐射线 AABB 粗筛 | 纯 Java 算术 | `rayCount × 候选刚体数` | 否 |
| ◆ `settleBlock` 判定 | 每**去重键每 tick一次**：`getBlockState` + `getMaxBlockDurability` | 被命中且尚未摧毁的方块数 | 是 |
| ◆ `execute()` 摧毁 | 每**被摧毁方块一次**：`getBlockState` + `setBlock` 全套 flags + `onBlockStateChange` | 本 tick 被摧毁方块数 | 是 |
| ◆ `onBlockUpdated` 记账 | 每方块：`SectionPos`/`ChunkPos` 构造、字符串拼接、任务表写入 | 本 tick 被摧毁方块数 | **在 Spark-Core** |
| ◆ `chunkHeightIndex.updateSection` | 每方块：区间表扫描 + `sectionHasSolidBlock` 最坏 4096 次逐格读 | 本 tick 被摧毁方块数 | **在 Spark-Core** |
| ◆ 脏 section 碰撞体重建 | 每**脏 section 每物理步一次**（已按 section 去重）：4096 格快照 + 逐格 `getCollisionShape` | 本 tick 被触及的 section 数 | **在 Spark-Core** |
| ◆ 逐方块光照与客户端同步 | 每方块：`sendBlockUpdated` 包 | 本 tick 被摧毁方块数 | 是 |

### 2.3 量级估算

用 §15.1 自己的参数（`rayCount = 1024`、`front_speed = 20 m/s`，即 `advancePerStep = 1 m`）与 `BlastRayGenerator.adaptiveRayCount` 的公式 `rayCount = clamp(126 × near_radius², 64, 4096)`：

- `near_radius = 3.0` → `rayCount = clamp(1134) = 1134`；
- 每 tick 约 1134 个体素步，其中命中实体方块的约占 1/4~1/3 → **每 tick 约 300 次 `settleBlock`**；
- 一次 30 m 量级爆炸（`max_radius` 30、`front_speed` 20 → 寿命约 1.5 s ≈ 30 tick）总摧毁量在 10⁴ 量级，波及的 section 在 10² 量级；
- 于是 **`chunkHeightIndex.updateSection` + 脏 section 重建这两项，每 tick 的逐格读取次数在 10⁵ 量级**，而 DDA 是 10³ 量级。

**结论**：破坏期两行的量级盖过 DDA 之前的所有行。§15.1 的算术没有错，只是它衡量的不是瓶颈。真正需要监控的量不是 `rayTest` 次数，而是**本 tick 摧毁方块数**与**本 tick 脏 section 数**。

> **估算不是实测。** §二的量级是按公式折算的，没有跑过。§四给出把它变成实测的口径——**在动 §五的代码之前应先跑它**，否则无法判断哪一项真的在耗时。

## 三、与既有文档的边界（此处是澄清，不是修订）

`武器系统-爆炸系统详细设计.md` §3.2 的介质交互表写：

> **方块（地形）** | 主线程 **3D DDA** 读区块数据 | 地形刚体**不在快照里**，且为一次爆炸唤起地形构建不划算

这句话成立，且与本文不冲突，但它的适用范围需要写清楚，否则容易读成「破坏期没有地形开销」：

- **它说的是判定通道**：爆炸**不把地形刚体纳入 `WorldSnapshot`**，不靠物理引擎做地形判定，而是在主线程用 DDA 直接读区块数据。这是「怎么知道炸到了什么」的问题，结论正确——为了一次爆炸去唤起整片地形的物理形状构建，确实不划算。
- **本文说的是破坏之后的同步通道**：一旦方块真的被摧毁，**Spark-Core 自己**会因为 `Level#onBlockStateChange` 而把受影响的 section 标脏并在随后的物理步重建碰撞体。这不是爆炸系统主动唤起的，也不需要爆炸系统主动唤起；它是引擎侧为了保持地形刚体与现实一致而必须做的工作。

两者是同一件事的两端：**判定走 DDA（廉价、按射线路径），同步走引擎脏标记（昂贵、按被摧毁方块数）**。既要保留前者，也无法绕过后者——绕过它就是 §七那条硬约束。

## 四、测量口径（先做这一步）

在优化之前，先在既有框架内取数。三个量都只需要临时代码与日志，不需要改结构：

| 量 | 位置 | 口径 |
| --- | --- | --- |
| 每 tick 摧毁方块数 | `ExplosionInstance#execute` | 进入时取 `pendingDestroy.size()`，并计时整个循环 |
| `execute` 单次耗时 | 同上 | `System.nanoTime()` 包住循环，只在超过阈值（如 2 ms）时打日志 |
| 每 tick 脏 section 数 | `PhysicsChunkManager#updateDirtySections` | `sectionsToUpdate.size()`（Spark-Core 侧，见另一份文档） |
| 单次 section 重建耗时 | `PhysicsChunkSection#startAsyncUpdate` | 包住 `buildCollisionShapeAsync(...).await()`（Spark-Core 侧） |
| `settleBlock` 总耗时 | `ExplosionInstance#settle` | 在 `settle()` 内累计 `settleBlock` 分支耗时，随上面的日志一起打 |

判据：**如果「每 tick 摧毁方块数 × 单方块代价」与「每 tick 脏 section 数 × 单 section 重建代价」之和超过 tick 预算的可见比例（例如 5 ms / 50 ms），则 §五的 P0 与 §六的 S0/S1 应当实施；否则本文的全部内容可以推迟。**

## 五、Machine-Max 侧候选

### 5.1 严格等价项（不改变任何可观测行为）

**M1 — 消除 `execute()` 中的重复 `getBlockState`**

`settleBlock` 在同一 tick 内已经读过 `pos` 的 `BlockState` 并据此判定过阈值，`execute` 却为同一个 `pos` 再读一次：

```java
// ExplosionInstance#execute
BlockState state = level.getBlockState(pos);   // settleBlock 已经读过
if (state.isAir()) continue;
```

把 `pendingDestroy` 从 `Set<BlockPos>` 改为 `Map<BlockPos, BlockState>`（或维护一张并行的状态表），执行期直接用缓存值。省下的是**每被摧毁方块一次区块读取**。

**M2 — 去重「形状体积因子」的重复构建**

`DamageUtil.getMaxBlockDurability` 的末行：

```java
// util/mechanic/DamageUtil.java
AABB aabb = blockState.getCollisionShape(level, blockPos).bounds();
blockDurability *= (float) (0.25f + 0.75f * aabb.getXsize() * aabb.getYsize() * aabb.getZsize());
```

同一颗方块在这次爆炸里已经被判过「是不是实心」——`VoxelRayWalker#addIfSolid` 刚为它构建过一次 `getCollisionShape(level, pos)`：

```java
// util/mechanic/VoxelRayWalker#addIfSolid
if (state.getCollisionShape(level, pos).isEmpty()) return;
```

`getCollisionShape` 会构造形状（可能分配 `AABB` / `VoxelShape`）。**同一命中里构建了两次。**

可行口径：按 `BlockState` 身份缓存「体积因子」。`BlockState` 是单例，且 `BlockBehaviour.BlockStateBase` 未覆写 `equals`/`hashCode`，因此 `IdentityHashMap<BlockState, Float>` 是合适的键类型。缓存的量是

```text
volumeFactor(state) = clamp(0.25 + 0.75 * X * Y * Z, …)   // 由该 state 在空世界下的 getCollisionShape 求得
```

**注意范围**：该 state 的形状可能依赖位置（`getCollisionShape(level, pos)` 的 `pos` 参数），因此缓存必须以「与位置无关」为前提。对绝大多数方块成立；对依赖上下文的方块（栅栏、墙、楼梯）不成立。**建议的落地口径是：只缓存 `BlockState#getShape` 等价于常量形状的情形，或用一次 `getCollisionShape(EmptyBlockGetter.INSTANCE, BlockPos.ZERO)` 探测，探测结果与带 `level, pos` 的调用不一致时退回原路径。** 这一条需要一次形状等价性测试才能算严格等价，否则会静默改变高爆炸抗性方块（§9.2 的阈值判定）的摧毁判据。

若不愿承担该测试成本，**M2 可以只做一半**：把 `bounds()` 的 `AABB` 分配换成直接读 `VoxelShape` 的 `min/max`（`getXsize()` 等三个调用各做一次边界查询），这在语义上完全不变，收益是省掉一个 `AABB` 对象。

**M3 — `settleBlock` 对已标记方块的早退**

`accum` 每 tick 清理（`settle()` 末尾 `accum.clear()`），因此**同一个方块在相邻两个 tick 上会各走一遍完整阈值链**，直到它真的被摧毁（或被射线放过）。在被持续照射的方块上这是重复劳动。

在 `settleBlock` 开头加一句早退：

```java
if (pendingDestroy.contains(pos)) return;   // 本 tick 已判过且已通过阈值
```

语义等价（本 tick 内该方块的结果已经确定），省下的是「同一 tick 内多射线命中同一方块」的重复判定。

### 5.2 需要设计裁定的项

**M4 — 破坏执行按 chunk 收敛（光照与网络部分）**

把 `execute()` 的逐方块 `level.removeBlock(pos, false)` 改为：

1. 按 `ChunkPos` 分组 `pendingDestroy`；
2. 每组取一次 `level.getChunk(...)`、一次 `LevelChunkSection` 数组；
3. 逐方块 `LevelChunkSection#setBlockState(lx, ly, lz, AIR, false)`；
4. 每个受影响的 section 一次 `ThreadedLevelLightEngine#updateSectionStatus`；
5. 每个 chunk 一次 `Heightmap.primeHeightmaps` + `initializeLightSources` + `propagateLightSources`；
6. 每个 chunk 向该 chunk 的玩家各发一个 `ClientboundLevelChunkWithLightPacket`。

**为什么这条路保得住地形同步**：`Level#setBlock` 的方块数据写入终点就是 `LevelChunkSection#setBlockState`，而 `Level#onBlockStateChange` 是在其后的 `Level#markAndNotifyBlock` 里被调用的（无条件，不在任何 flag 分支内）。第 3 步保留 `LevelChunkSection#setBlockState` 作为写入终点，因此地形侧的脏标记与激活照常发生，不受第 4~6 步改动的影响。

**收益**：省掉逐方块的 `sendBlockUpdated`（每方块一个 `ClientboundBlockUpdatePacket`）与逐方块的方块更新通知；把光照更新从逐方块变成分节/分块。

**代价与风险**：
- 丢掉逐方块邻居更新（`flags & 1`）。爆炸是否依赖邻居更新？**当前爆炸不依赖**——它不做掉落、不做流体回流（`destroyBlocks` 与 `dropItems` 是两个独立开关，掉落走 `Block.dropResources` 不依赖邻居更新）。但如果将来要支持「爆炸后沙子塌落」「水流入坑」，这条就变成了行为变更。
- `ClientboundLevelChunkWithLightPacket` 的构造与序列化比逐方块包贵得多。必须**按 chunk 计数并设每 tick 上限**，否则大当量爆炸会把主线程耗在包序列化上。
- 需要与 §十一 的地形破坏开关、`dropItems` 分支保持一致的处理顺序。

**建议**：先做 M1–M3（严格等价、风险为零），把 M4 作为独立阶段，并附上「每 tick 发包数上限」与「关闭开关时回退到逐方块路径」两个护栏。

## 六、Spark-Core 侧候选（登记在此，实施见另一份文档）

破坏期的两项大头落在 Spark-Core：`ChunkHeightIndex#updateSection` 的逐方块重扫，与 `PhysicsChunkManager#onBlockUpdated` 的逐方块记账。它们不是爆炸系统能单方面修复的。**候选清单、改动口径与量级见 `Spark-Core/docs/地形方块变更热路径优化建议.md`。**

其中与本系统直接相关的一条**必须**在此登记，因为它约束 Machine-Max 能做什么：

> `PhysicsChunkManager#onBlockUpdated` 的签名已经是 `Set<BlockPos>`，但 `ServerLevelMixin` 只传 `Set.of(pos)`（一次一个）。爆炸侧知道自己的完整摧毁集合，却拿不到从「方块变更」到「地形脏标记」这条链的控制权。要让爆炸把整批摧毁一次性提交给地形侧，需要 Spark-Core 提供一个批量入口。

***

## 七、硬约束：不要用整节替换，也不要调小 flags

破坏执行**必须**经由会触发 `Level#onBlockStateChange` 的路径。两条禁止事项：

**① 禁止把 `removeBlock(pos, false)` 的 flags 调小以求省事。**
既然 `onBlockStateChange` 是无条件调用，把 `setBlock(pos, AIR, 2)` 之类换成更小的 flags **不会**省下地形同步，只会丢掉邻居更新与客户端方块包——纯粹的行为损失，没有任何收益。（`removeBlock` 内部固定传 `3`；`flags` 的 64 位只由第二个参数控制。）

**② 禁止绕过 `LevelChunkSection#setBlockState` 直接换掉 section 对象。**
即禁止这种形态：

```java
// 反面示例：整体替换 section，不产生任何方块状态变更
sections[i] = new LevelChunkSection(
        new PalettedContainer<>(Block.BLOCK_STATE_REGISTRY, AIR, Strategy.SECTION_STATES),
        section.getBiomes());
```

这样做在方块数据上是正确的、在内存上极省（空 section 共享同一个缓存实例），**但一个方块状态变更都不会发生**：`Level#onBlockStateChange` 不触发 → Spark-Core 的 `markDirtySections` 不触发 → **该 section 的地形碰撞体停留在旧形状上**。后果是炸出一个深坑而物理上仍是平地，载具与角色悬空，且不报错、不崩溃，只在物理行为上表现出来。

若将来确实需要整节替换的吞吐（例如引入无条件的大范围地形重塑类技能），前提是**自己为受影响的 section 补齐地形侧同步**：按 `SectionPos` 调 `PhysicsChunkManager#markDirtySections`，并保证随后的 `updateDirtySections` 能取到正确的 `LevelChunk`。Spark-Core 侧两个现读来源都是 `LevelChunk`——`SectionSnapshot#snapshotFromChunk` 与 `ChunkHeightIndex#computeIntervals`——因此这条路在原理上接得上；但它是 Spark-Core 的改动，需要对方配合。

> **这条约束的来源**：整节替换这种写法在第三方模组中是存在的（`mods/the-shooting-star-demo-1.3.0-neoforge.jar` 的 `dev.aek.shootingstardemo.mc1211.star.Carving#cut` 用它实现单次 10⁴~10⁶ 量级的无条件地形破坏），在那套代码里它没有问题——那个模组不驱动 Bullet 地形刚体，方块数据的一致性就是全部。本项目引入了 Spark-Core 的地形同步链，同一种写法在这里会静默破坏物理一致性。**它在这两处的前提不同，结论因此相反。**
