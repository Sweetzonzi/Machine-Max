## 一、现状

投射物的推进段由两个独立的类型各表达一次，中间是一次一对一折算：

| 位置 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
| 内容包 | `BallisticProjectileType.ExternalProperties.ThrustProperties` | `force` / `duration` / `ignition_delay` | 作者侧形态，`spark_modules/**/projectiles/*.json` 的 `external.thrust` |
| 弹道库 | `io.github.sweetzonzi.ballistics_framework.api.trajectory.ThrustProfile` | `force` / `startSeconds` / `endSeconds` | 求解器与积分器读的形态；窗口 `[start, end)` |

折算在 `BallisticProjectileType#getThrustProfile()`：`start = ignition_delay`、`end = ignition_delay + duration`，结果按弹种惰性缓存一次。

三个消费方共用同一条积分式 `TrajectoryStep#step`（服务端趟一、客户端外推、地形预载视界行走），因此"预测与模拟同式"由构造保证。仓库内 15 个弹种定义里只有 `9m133_kornet.json` 配了 `thrust`：

```json
"thrust": { "force": 2600.0, "duration": 2.5, "ignition_delay": 0.1 }
```

推力沿**速度矢量**施加，只增速率、不改方向；质量取 `BallisticConfig.mass()`，燃烧期恒定。`HudBallisticTable` 对 `hasThrust()` 的弹种返回空表，即带推力的弹种不出弹道标定分划。

## 二、缺口

### 2.1 只能点火一次

双脉冲（第二脉冲在飞行中段点火）、火箭增程弹、筒式发射弹的"弹射 + 续航"两段，都需要不止一个燃烧窗口。当前形态用一个 `force` 与一个窗口表达，能表达的只有"一次恒力点火 + 出膛速度"这一种组合。

### 2.2 燃烧期质量恒定

推进剂烧掉后质量不变，于是段内加速度恒为 `F/m₀`，而真实加速度随质量下降单调上升。以 9M133 的配置做量级参考（26 kg、2600 N、2.5 s，取排气速度 2354 m/s 即 Isp 240 s，反推装药 2.76 kg 占总质量 10.6%，用同一条半隐式欧拉、dt = 0.01 s）：

| 场景 | 燃尽速度 | 45° 射程 | 10° 射程 |
| --- | --- | --- | --- |
| 常质量（当前形态） | 283.7 m/s | 8530 m | 1402 m |
| 变质量 | 297.9 m/s | 9352 m（+9.6%） | 1476 m（+5.2%） |
| 变质量且把 `force` 反标定到 2473 N | 284.4 m/s | 8544 m（+0.2%） | 1373 m（−2.1%） |

读法有三条：

- **速度增量改变**。总冲不变而分母变小，`Δv` 从 250 m/s 升到 264 m/s（+5.7%）。
- **单点反标定只能对上一种射击**。把 `force` 调到 2473 N 能让 45° 复原，10° 反而短 2%——变质量把加速后置（段初加速度低、段末高），浅角射击对速度形状更敏感。
- **阻力项使结论偏乐观**。上表用 9M133 的 `drag_factor = 0.0025`，300 m/s 时阻力加速度只有 0.08 m/s²，因此差别几乎全是纯火箭效应；阻力若按真实量级取值，燃尽后质量更低会使减速度更大，抵消一部分增益。

积分误差不是问题：同样的比对在 dt = 10 ms 下，常质量与变质量相对各自 0.2 ms 参考解的位置差都是米级（1.6 m 与 1.4 m，O(dt) 同阶），质量流失不劣化误差阶。

### 2.3 本文不承担的部分

- **推力曲线 / 任意函数**：固体发动机的实际剖面是"平台 + 尾段爬升"，2~4 个分段点足够；采样曲线没有消费方，且给内容作者增加无收益的负担。
- **分级分离**：真正的多级有级间分离、质量跳变与迎风面积跳变。段表给的是"多次点火"，不含分离事件。
- **推力方向**：沿速度矢量是质点模型下的既定近似，制导转弯由指令加速度承担。

## 三、目标形态：段表

`external.thrust` 是一个段数组，缺省或空数组表示无推力：

```json
"thrust": [
  { "force": 2600.0, "start": 0.1, "duration": 2.5 },
  { "force": 1800.0, "start": 8.0, "duration": 1.2, "propellant_mass": 0.9 }
]
```

| 字段 | 类型 | 缺省 | 语义 |
| --- | --- | --- | --- |
| `force` | number > 0 | 必填 | 推力（N） |
| `start` | number ≥ 0 | 必填 | 点火时刻（s），自发射瞬间起算 |
| `duration` | number > 0 | 必填 | 燃烧时长（s）；窗口 `[start, start + duration)` |
| `propellant_mass` | number ≥ 0 | `0` | 本段全程烧掉的推进剂（kg）；0 = 本段质量恒定 |

**装药按段记录，不设剖面级总量。** 每段自带推进剂，于是每段有自己的排气速度（助推药柱与续航药柱本就不是同一配方），也不必强行为全剖面假设一个 Isp。质量按段内匀速消耗：

```text
mdot_i        = propellant_mass_i / duration_i              （kg/s）
consumed_i(t) = clamp(t − start_i, 0, duration_i) · mdot_i   （kg）
m(t)          = max(m₀ − Σ consumed_i(t), ε)
```

排气速度 `ve_i = force_i / mdot_i` 是派生量，不进 JSON，也不作为作者参数。

**校验**（在内容包加载期报错，带文件路径）：

- `force > 0`、`duration > 0`、`start ≥ 0`；
- 段之间不得重叠（允许空隙，空隙即无推力滑行）；
- `Σ propellant_mass < external.mass`。

## 四、BallisticsFramework 侧

目标版本 `1.0.0.alpha.15`。

### 4.1 `ThrustProfile`

```java
public record ThrustProfile(List<Segment> segments) {
    public record Segment(float force, float startSeconds, float endSeconds, float propellantMassKg) {}

    public static final ThrustProfile NONE = new ThrustProfile(List.of());
    public static ThrustProfile of(float force, float start, float end);   // 单段恒质量的规范写法

    public boolean isActive();                 // 至少一段有效
    public float forceAt(float seconds);       // 段内返回 force，段外与空隙返回 0
    public float endSeconds();                 // 末段熄火时刻，NONE 为 0
    public float burnDuration();               // Σ 段时长
    public float massAt(float seconds, float launchMass); // 无装药时逐位返回 launchMass
    public ThrustProfile remainingSince(float elapsedSeconds); // 供求解起点晚于发射点的消费方
}
```

构造器负责规范化：过滤无效段 → 按 `startSeconds` 排序 → 拒绝重叠（抛 `IllegalArgumentException`）。`startSeconds` 允许为负，沿用"负值表示全程"的既有语义。

调用方不必自己平移时间原点：`forceAt` / `massAt` 以调用方给出的时刻为唯一时基，而 `remainingSince(elapsed)` 把以发射瞬间为原点的段表裁剪到"求解起点晚于发射点"的调用方所需的新原点（整体减去 `elapsed`、丢弃已燃尽段、裁剪正在燃烧的段）。Machine-Max 的三处消费都以发射瞬间为原点，不调用它。

### 4.2 `RealisticTrajectory` 接线

| 位置 | 当前写法 | 目标写法 |
| --- | --- | --- |
| `forwardSolve` 分派（L93） | `thrust.isActive()` | 不变；空隙由 `forceAt = 0` 跳过 |
| `thrustAppliedAtStep`（L219–222） | 比较 `start` / `end` | 删除；三个推力积分器改问 `thrust.forceAt(stepStart) > 0` |
| 三个积分器的 `aT`（L235、L262、L302） | 提到循环外除以 `config.mass()` | 移进循环，按该步步初时刻取 `force` 与 `massAt` |
| `halfRhoRef`（L263、L303） | 含 `/config.mass()` | 移进循环，除数为该步的 `massAt` |
| `estimateSpeed`（L800–802） | `0.5 · aT · (end − start)` | 有装药时用 `ve · ln(m₀/m_f)`，否则对段求和 |
| 非推力路径的 `config.mass()`（L149、L186） | 常量 | 不动 |

### 4.3 不变式

- **只要剖面含有效段，就走进推力积分器**，包括段间空隙。于是非推力退化路径永远见不到变质量，它们继续用常量 `config.mass()`；代价是空隙步走的是推力积分器，收益是分派门禁只需要判"段表是否为空"这一条静态条件，不必按步分派。
- **单段剖面与单窗口等价**：`forceAt` 在窗口内返回同一个 `float`，`massAt` 无装药时返回 `launchMass` 本身，因此 `aT` 与除质量的算术与单窗口形态逐位一致。
- **窗口判定取步初时刻**，左闭右开，与既有积分器一致。

### 4.4 测试

现有 `RealisticTrajectoryInvariantTest` 的 T1–T9 原样保留，5 处 `new ThrustProfile(...)` 改用 `ThrustProfile.of(...)`。新增：

| 编号 | 断言 |
| --- | --- |
| T10 | 单段 `of(f, s, e)` 与 T5 的参考解一致 |
| T11 | 双段 + 空隙：段外不施加推力，等效于依次施加两个窗口 |

| T15 | `propellantMassKg = 0` 时与不带该字段的结果逐位相同 |

## 五、Machine-Max 侧

### 5.1 数据形态

`ExternalProperties` 的 `thrust` 字段是 `List<ThrustSegment>`，不保留包装 record：

```java
public record ThrustSegment(float force, float start, float duration, float propellantMass) {}
```

`CODEC` 为 `Codec.list(ThrustSegment.CODEC).optionalFieldOf("thrust", List.of())`，不做形态分派。`ExternalProperties` 的整组 codec 套一层 `flatXmap` 承接跨字段校验（装药总和小于质量），失败返回 `DataResult.error`，使错误带上内容包路径而不是堆栈。

### 5.2 折算

`getThrustProfile()` 把段表逐项折算（`endSeconds = start + duration`），按弹种惰性缓存一次；`hasThrust()` 的判据是"列表非空"。

### 5.3 积分

`TrajectoryStep#step` 的两处除数是该步质量 `thrust.massAt(burnTime, cfg.mass())`，推力大小由 `forceAt` 取。函数签名不变，三个消费方零改动。

### 5.4 内容包

`9m133_kornet.json` 的推进段写成一段的数组，不写 `propellant_mass`（保持常质量，弹道与当前逐位一致）：

```json
"thrust": [ { "force": 2600.0, "start": 0.1, "duration": 2.5 } ]
```

### 5.5 schema 与同步

`projectile.schema.json` 的 `thrust` 是 `array`，元素 `additionalProperties: false`，不含对象形态。改完 schema 后执行 `./gradlew syncSchemas`，把九个第一方包的副本、技能快照与 `bundle-manifest.json` 放在同一个提交。

### 5.6 不改动的部分

| 组件 | 原因 |
| --- | --- |
| `HudBallisticTable` | 带推力的弹种继续返回空表；分划表的前提（射程上界取初速、飞行时间上限）对助推弹不成立 |
| `ProjectilesSpawnPayload`、`sync` 协议版本 | 推进段全部是弹种常量，无需逐发同步 |
| `ProjectileManager` 的 SoA 数组 | 质量由 `burnTime` 与段表解析得到，不需要新状态 |
| `getThrustProfile()` 的按弹种缓存 | 段表仍是弹种常量，缓存继续成立 |

落地时同步更新三处：`common/mech/projectile/AGENTS.md` 与 `docs/wiki/4-物理与战斗机制/4.7-投射物.md` 的推力段落写到段表口径；`docs/plan/已实现/武器系统-制导组件实现备忘.md` §十四 的指针按实现状态改判，本文移入 `docs/plan/已实现/` 并更新索引。

## 六、验收

**回归门槛**（三条全绿才算"行为保持"）：

1. `9m133_kornet.json` 未写 `propellant_mass`、只有一段 ⇒ 服务端积分的逐位结果与当前一致；
2. BallisticsFramework 的 T1 旧签名逐位兼容、T2–T9 全绿；
3. `src/test/.../mech/trajectory/TrajectoryStepTest.java` 的四条用例全绿（其中"燃烧窗口在视界之外时逐位相同"改造成段表形态后仍为逐位断言）。

**新增用例**：§4.4 的 T10–T15；Machine-Max 侧补三条编解码用例（数组解码、空数组、装药超质量报错）与一条段重叠报错用例。

**命令**：`./gradlew --offline test`、`./gradlew checkSchemas`；实机用 `runClient` 发射一发 9M133 确认弹道与画面无变化。

## 七、明确不做

- **指令触发（飞行中点火）**。它的引入方式是在段上加一个可选的 `ignition` 枚举（`timed` / `commanded`）；数组元素增加可选属性属于兼容的 schema 变更，不产生迁移成本。届时才需要引入"每发解析后的剖面"与一条点火同步载荷，而当前没有消费方（没有火控会下发这个指令），因此不进本期。
- **对象形态不保留**。`external.thrust` 只接受数组：仓库内只有 9M133 一处，随本文一并改为数组。第三方包若沿用了对象写法，会在加载期以"期望列表"失败，属于响亮的失败而非静默降级。
- 推力曲线、分级分离、推力方向，见 §2.3。

## 八、风险

| 风险 | 处置 |
| --- | --- |
| 段间空隙使推力积分器承接了"无推力滑行"的步 | 由 §4.3 的不变式保证等价，T11 与 T12 钉住 |
| 重叠段/无序段被内容作者写出 | 构造期规范化 + 加载期报错，不做隐式覆盖 |
| schema 破坏性变更影响第三方内容包 | 仅一处仓库内配置受影响；错误信息明确 |
| 变质量移动既有弹道 | 只在写了 `propellant_mass` 时发生；9M133 不写，现有弹道不变 |
| 两个仓库的提交顺序 | BallisticsFramework 先合入并升到 `alpha.15`；Machine-Max 的 `gradle.properties` 在同一次提交里跟上，否则复合构建会解析到旧版本 |
