# 武器系统 — 弹药三角色接口拆分计划

**状态**：计划中，未实施。本文把弹药一侧的接口拆成三个角色——接收者、提供者、运输者——并给出各自的契约、受理与阶段顺序、同步字段与实施步骤。基线是 `sync:7.0.0` 时的实现：装填作业与作业身份、实际架预留与两端本地推进、人工段与座位装填频道、人力直取路径都已落地（见[人工与机械装填及操作员接入计划](武器系统-人工与机械装填及操作员接入计划.md) §10.1 的 S18—S22）。

**核对日期**：2026-11-15。

## 1. 现状与问题

`IAmmoSupplier` 现在同时回答三件事：库存与预留（再生架的本职）、运输的时间与占用（装弹机的本职）、用人（人工段的座位发现与认领）。两个实现的意义并不相同：

| 实现 | 持有库存 | 机械动作 | 独占槽位 | 用人 |
| --- | --- | --- | --- | --- |
| `AmmoLoaderSubsystem` | 否——`getDeliverySpec`／`returnBelt`／`getLabel`／`getCapacity` 全部转调上游架 | 是，`reload_time` | 按 `can_supply_multiple` | 可选准备段，`human_reload_time` |
| `RegenAmmoRackSubsystem` | 是——`N`／`R` 与整张预留表 | 否，`getReloadTimeTicks` 为 0 | 否，`canSupplyMultiple` 恒真、`isClaimedByOther` 恒假 | 否，人工段的六个方法全部沿用默认实现 |

装弹机因此以"供给者"的身份登记在发射器的供给者表里，尽管它既不持有库存也不决定库存；再生架则以"供给者"的身份承担交付，尽管它没有任何机械过程。两类对象在消费者眼里是同一种东西，靠一排恒为真／恒为假的默认实现区分。

人工段的归属在运行时判定：`LauncherSubsystem#ownsHumanStage` 看"交付方有没有声明 `human_reload_time`"，没有就由发射器自己用人。为此发射器对同五个人工段操作各保留一份转发（`claimOperator`／`holdsOperator`／`releaseOperator`／`operatorTimeScale`／`humanStageAdvance`），客户端还要用同一个判据决定谁播人工段音效。一条作业的人工段因此有两个可能的主人与两个必须保持一致的条件。

路由单位是一台机器：作业用两个同类型引用（`deliveryTarget`／`upstreamOrigin`）表达"谁交给我"与"弹从哪来"，它们的含义随路径变化——人力直取时是同一台架，机构路径时是机构与上游架。再生架报 `getReloadTimeTicks() == 0`，于是人力直取的作业在人工段之后还有一个 1 tick 的机械段（作业时长下限 1），它不表达任何机械动作。

路由单位选错对象还有一处可见的症状：发射器上有五处各自读"当前供给者"的地方——退膛、当前弹种、换装判定、换装提交、旧份交还。它们都假定"这条路只有一台机器，找到它就等于找到了整条路"，而换装旧份那里已经长出"先问本次来源、再问当前指认、最后按发现顺序扫其余供给者"的三级兜底，说明一台机器承担不了路这个角色。

还有两处现状决定了下面的取舍。其一，`WeaponControllerSubsystem#findSupplier` 已经把被别的作业占着的独占机器排除在候选之外（候选条件含 `!isClaimedByOther(launcher)`），"忙的机器是要等的候选"这条口径没有对应实现，本计划按代码现状收敛（D11）。其二，弹药池条目的 `channel` 字段只在 `refreshAmmoPoolCounts` 里被原样复制，没有读取点，池内排序只看与消费者无关的 `reloadTimeTicks`——频道今天是一段死数据，因此不再作为路的一部分引入（D12）。

## 2. 三个角色

| 角色 | 接口 | 实现 | 拥有 | 不拥有 |
| --- | --- | --- | --- | --- |
| 接收者 | `IAmmoConsumer` | `LauncherSubsystem` | 作业与进度、发现结果与路由、膛内弹与已装 Belt | 库存、时间基准、选人、弹链实例 |
| 提供者 | `IAmmoSupplier` | `RegenAmmoRackSubsystem`；物品架 `AmmoRackSubsystem` 随物品往返接入 | 实际库存 `N`、可分配 `N − R`、预留表、交付规格、兑现出的弹链、退弹接收、再生阶段 | 任何时间基准、机械槽位、装填人员、接收者身份 |
| 运输者 | `IAmmoTransporter` | `AmmoLoaderSubsystem`（机械）、`LoaderRoster`（人力） | 本段时长、占用（机械槽或一名乘员）、本 tick 推进量 | 库存与预留（向提供者取）、弹链实例的制造 |

接收者向两个角色各问一件事：

```text
接收者 ──向运输者要──▶ 本段时长、执行资源（槽位或乘员）、本 tick 能推进多少
接收者 ──向提供者要──▶ 整次作业的预留；走完后兑现成一份弹链
```

一条装填作业对应**一条路**：一个运输者加一个提供者。路是路由与同步的单位，不是状态对象（§3.3）。

## 3. 接口契约

### 3.1 提供者 `IAmmoSupplier`

```java
enum ReloadPhase { IDLE, LOADING, REGENERATING, REFILLING }   // 嵌套在 IAmmoSupplier 内
record Grant(AmmoBelt spec, int reservedCount) {}             // 同上

boolean isSupplyOperational();             // 自身可工作：启用、未摧毁（含 30% 恢复锁存）、供能条件
int getRemainingCount();                   // 可申请数量 N−R；-1 = 无计数概念
default boolean hasAmmo() {                // 便捷读法，无独立语义
    int count = getRemainingCount();
    return count < 0 || count > 0;
}
@Nullable ProjectileType getSuppliedType();
@Nullable AmmoBelt getDeliverySpec();      // 下一份的满额规格，只读模板
int getCapacity();                         // -1 = 无容量概念
@Nullable Grant reserve(ReloadJobKey key); // 整次作业预留，q = min(N−R, 规格长度)，q > 0
@Nullable AmmoBelt deliverReserved(ReloadJobKey key); // 按身份扣 N、交出独立实例、一次兑现
void releaseReservation(ReloadJobKey key); // 只减承诺，不补弹
boolean holdsReservation(ReloadJobKey key, int reservedCount);
boolean returnBelt(AmmoBelt belt);         // 全收或全拒，由提供者自己判
String getLabel();                         // 仅显示
ReloadPhase getRefillPhase();
float getRefillProgress();
int getRefillRemainingTicks();
```

**提供者不认识接收者。** 预留、兑现与撤销只按作业身份记账，参数里没有消费者。"哪根管占着这一份"由身份里的宿主 SubPart ID 与发射器名表达，提供者不需要反向握住接收者；接收者因此也不必担心提供者持有自己的引用跨作业残留。作业身份在本会话内唯一（`ReloadJobKey` = 宿主 SubPart ID ＋ 发射器名 ＋ 作业号），一次预留对应一次兑现。

**`holdsReservation` 的第二个参数是客户端的保守判据。** 服务端读预留表（该身份是否还有份额），忽略 `reservedCount`；客户端没有整张预留表（§5），只能按"实际库存不少于本作业份额"回答，`reservedCount` 就是那个份额。两端问的是同一个问题——"你手上还有这一份吗"——只是证据不同。

**`Grant` 只有规格与预留量两个字段。** 来源由调用方指名的那台提供者给出，消费方把它写成 `AmmoRef.ofProvider(provider)`，不需要第三个字段。预留语义沿主计划 §3.4：整次作业一次预留、`0 ≤ Σq ≤ N`、按身份撤销与兑现、不足一份按剩余发数受理。

落点：`ReloadPhase` 与 `Grant` 保持为 `IAmmoSupplier` 的嵌套类型，`IAmmoSupplier.java` 是唯一文件。

### 3.2 运输者 `IAmmoTransporter`

```java
boolean isHuman();                              // 人力运输者：整条运输由乘员完成
boolean isOperational();                        // 本机可工作（启用、未摧毁、供能/条件满足）；人力运输者恒 true
boolean canServeMultipleConsumers();            // 能否同时为多条作业运输
int getHumanReloadTimeTicks();                  // 人工段基准 tick；0 = 没有人工段（人力运输者为 0 时不进路由）
int getReloadTimeTicks();                       // 机械段基准 tick；0 = 没有机械段
List<IAmmoSupplier> getFeedSources();           // 喂弹线；人力运输者为空表
default @Nullable IAmmoSupplier findProvider(AmmoRef ref) { /* 按 getFeedSources() 匹配 */ }
boolean claim(IAmmoConsumer consumer, ReloadJobKey key);          // 取得/维持本阶段执行资源
default boolean claimForMachineStage(IAmmoConsumer consumer, ReloadJobKey key) { return true; }
int getAdvanceTicks(IAmmoConsumer consumer);     // 本 tick 推进量
boolean holdsCommitment(IAmmoConsumer consumer);
boolean isClaimedByOther(IAmmoConsumer consumer);
void releaseClaim(IAmmoConsumer consumer, ReloadJobKey key);
double getOperatorTimeScale(IAmmoConsumer consumer);
int estimateTicks(IAmmoConsumer consumer, IAmmoSupplier provider);
default void tickStageSounds(IAmmoConsumer consumer, float progress) {}
```

**`isHuman()` 的定义与不变量。** 人力运输者是"由一名乘员完成整条运输"的对象：没有机械段、没有喂弹线、不占机械槽。`isHuman()` 由类型决定——roster 恒为真、装弹机恒为假——是构造时就成立的事实，不是从时长推断出来的；另外两条是它的派生读法，分别服务阶段规划与喂弹线解析，三者在内容解码期做一次一致性校验：

```text
isHuman()  ⇒ getReloadTimeTicks() == 0 && getFeedSources().isEmpty()
!isHuman() ⇒ getReloadTimeTicks() > 0
两段都为 0 的运输者在内容解码期即被拒绝（运输者必须有一段时长）
```

人力运输者多一条前置：它只有在基准时长 > 0 时才进入路由。`LoaderRoster#discover(standardTicks)` 收到 0 时清空基准时长并停止登记，§4.1 也不为发射器合成人力路，因此"被选中的运输者有人工段"在运行期恒成立，不需要断言兜底。机械运输者的喂弹线可以为空——那是结构变化后的短暂窗口，此时它没有可用的路，不是配置错误。

**`canServeMultipleConsumers()`** 是唯一的产能声明。`false` 的运输者一次只推进一条作业：别的作业这一 tick 拿到 0，路由不把已被占用的它放进候选；`true` 允许并行。人力运输者恒为 `false`——一名乘员一次只推进一段人工装填。提供者没有产能声明：同一份库存的独占性由预留表保证，与运输者的槽位无关。

**受理分两步，都由接收者发起。** 接收者先向运输者取执行资源，再向提供者取预留：

| 运输者 | `claim` 取得 | `claimForMachineStage` |
| --- | --- | --- |
| 人力运输者 | 认领一名乘员 | 不会被调用（机械段为 0） |
| 机械运输者，无人工段 | 机械槽（`!canServeMultipleConsumers()` 时） | 不会被调用（受理即机械段） |
| 机械运输者，有人工段 | 认领一名乘员 | 人工段结束时补齐机械槽 |

`claim` 是**可重入且幂等**的：同一身份重复调用只补齐本阶段的资源、并按当前候选换人，不追加预留、不重置进度。人工段每 tick 调它一次，因此"换不换人"与"还有没有人"是同一个入口。两步任一步失败——`claim` 返回 false，或随后的 `reserve` 返回 null——都撤销本次已取得的资源（`reserve` 失败时调 `releaseClaim`），接收者因此不建作业、不开始计时。资源来自两个对象，取得顺序固定为运输者在前、提供者在后，撤销只涉及先取得的那一份。

**预留由接收者向提供者取得，不由运输者代办。** 一次作业只有一份预留，取得它只需要作业身份与规格，而规格是提供者的属性；运输者代办会让它多背一个不属于自己的状态。提供者因此不出现在运输者的受理与推进签名里；除下一段的失效清理外，它只在两个只读处出现：`getFeedSources()` 交出喂弹线，`estimateTicks` 按指名的那台估价。

**撤销也归接收者，只有一个例外。** 正常收尾由接收者按身份撤销：先释放运输者的乘员与机械槽，再撤销提供者的预留。运输者的 `releaseClaim` 只释放自己的资源，不碰提供者的预留表——那张表只有一个常规写者。例外是失效清理：消费者已被摧毁或停用、再没有机会走收尾时，运输者在剔除自己的失效占用时按身份撤销对应预留，否则那份预留会永久占住库存。触发条件与理由写在实现处的注释里；它是"消费者已无机会收尾"的补救，不是常规路径。

**推进与承诺。** `getAdvanceTicks` 是唯一的放行入口，返回值 ∈ `{0, 1}`：`1` 表示这一 tick 前进一格，`0` 表示推不动（本机不可工作、槽位被别的作业占着、乘员离场、作业的预留已撤销）并计一次暂停。人工段的时长已把岗位倍率 `P` 与个人倍率 `A` 折进去，人员变化由 `ReloadJob#retimeHuman` 换算剩余量，因此人工段不需要按秒数算推进量。

`holdsCommitment` 区分"承诺整体消失"与"这一 tick 推不动"，只有前者让接收者立刻按失效收尾，不等暂停上限。承诺消失只有三个来源：预留已被撤销或已兑现（`holdsReservation` 为假）、运输者的占用被按身份摘掉（身份匹配的释放，或失效清理）、消费者自己已摧毁／停用／指认不再指向本运输者。**换人不属于承诺消失**：`claim` 每 tick 可以换乘员，换的是执行者，不是这条作业的预留与占用，换人保留进度。占用也不会被抢占——占用只由身份匹配的释放与失效清理删除，独占运输者在受理时就拒绝别的消费者。

**代价 `estimateTicks`。** 运输者回答"沿这条路，接收者还要多久拿到下一份交付"，各类加成由它自己折算。这是路由排序与换人比较的唯一代价，接收者与武器控制器都只读这一个值：

```text
!isOperational()（运输者自己不可工作）              → Integer.MAX_VALUE
提供者为空或 !provider.isSupplyOperational()        → Integer.MAX_VALUE
作业已在这条路上（作业上的运输者与提供者都对得上）
    人工段 → 本阶段剩余（时长已含 P×A）+ 机械段
    机械段 → 本阶段剩余
作业不在这条路上
    提供者的可分配库存为 0（-1 表示无计数概念，按有货） → Integer.MAX_VALUE
    人力段选不到任何候选乘员                          → Integer.MAX_VALUE
    其余                                             → 人工段标准剩余 × P × A + 机械段
```

已在路上的作业只看自己的剩余量：那一份已按身份预留，`N − R` 归零不影响它。已经在路上的作业也不重算换人收益：换不换由 `claim` 每 tick 用同一批候选判定，本方法只报这条作业按现状还要多久。缺弹等待只按"这一 tick 有没有可分配库存"判定，因此可分配为 0 的提供者在这条路上等价于不可达；再生时间的折算不在本次范围（§10、D11）。

估价本身是一次只读的选人，所以**同一次选路内同一个 `(consumer, provider)` 只算一次**：结果放进调用方的局部表，随调用丢弃，不跨 tick 保留，也不写回发现表或弹药池。`LauncherSubsystem#ticksToNextRound(AmmoPath)` 因此只剩一次转发，武器的候选比较与换人判定都读这个值（§4.2）。

**人力的读口。** `getOperatorTimeScale` 报已认领乘员的 `P × A`，接收者每 tick 现读并用于换人重定时；`estimateTicks` 在尚未受理时用同一批候选与倍率给出预计（只读——不认领、不改预留），因此人力运输者需要一份"只选不认"的估计入口，与 `claim` 共用同一批候选与同一个比较纯函数（`ReloadCrewSelection`）。基准时长由运输者在发现阶段持有一次（`discover` 时传入），`claim` 与 `estimateTicks` 的签名里因此没有它。`tickStageSounds` 只在客户端调用，由运输者按自己的游标播本段音效（人工段的声音定位在接收者，机械段在运输者）。

落点：`IAmmoTransporter.java`（新文件）、`AmmoRef.java`（新文件）、`AmmoPath.java`（新文件）。`LoaderRoster` 是包内类，实现本接口后仍是包内可见。

### 3.3 一条路与弹药端身份

```java
record AmmoPath(IAmmoTransporter transporter, IAmmoSupplier provider) {}
```

`AmmoPath` 是路由单位，不是状态对象：它由两张发现表按需合成，不在发现阶段缓存（见 §4.1 的原因）。`IAmmoSupplier.SupplierRef` 提为顶层类型 `AmmoRef`，编码不变（宿主 SubPart ID ＋ 子系统名），`NONE`／`compareTo`／`STREAM_CODEC` 随文件移动；它指向两种角色之一，名字取弹药端而非提供者。两个具名工厂代替单一 `of`：

```java
AmmoRef.ofProvider(IAmmoSupplier provider)    // 必须是子系统
AmmoRef.ofTransporter(IAmmoTransporter transporter)
```

两个工厂各自断言自己的那一侧：`ofTransporter` 要求"`isHuman()` 为真当且仅当结果是 `NONE`"，`ofProvider` 要求实现是子系统。同一台对象不会同时实现这两个接口（§7 的 M1 一次切换，没有同时持有两个身份的类），具名工厂把这条约束写在名字与断言上，不依赖重载解析。

`NONE` 在运输者位上有唯一含义：**人力运输者**。`LoaderRoster` 不是子系统，`ofTransporter(roster)` 给出 `NONE`；非子系统的机械运输者是编码错误，`ofTransporter` 记一条警告并同样给出 `NONE`，接收者据此按人力处理——这类对象在内容里不存在，断言只防回归。`NONE` 在提供者位上只有一个含义：**没有提供者**（没有路由、或作业已收尾）。

### 3.4 人工段的主人是类型决定的

半自动流程仍存在：机械运输者可以同时声明准备段与机械段（`human_reload_time > 0 && reload_time > 0`），准备段由它自己的座位发现选人，机械段由它自己放行。人力运输者只有一个段，走完即交付。

一条路只有一个运输者，人工段归运输者，不存在两个候选主人，也不需要客户端再判一次谁播放人工段音效。"交付方声明了人工段就由它用人，否则由发射器用人"这条优先级规则与它服务的场景一起消失：发射器不再为任何作业"借"自己的用人能力给别的对象。`LauncherSubsystem` 的五个人工段转发方法与 `humanStageStandardTicks`／`humanStageAdvance` 一并去掉，`ownsHumanStage` 没有读者。

发射器型号的 `human_reload_time` 因此只有一个含义：本型号有一条完整人力路（运输者是自己的 roster，提供者是发现到的架）。它不再被"交付方也声明了人工段"截断。§6 记录这条语义变化对第三方内容的后果。

## 4. 流程

### 4.1 发现

接收者按 `ammo_discovery_targets` 做只读发现，把命中对象分成两张表：

| 命中对象 | 登记为 | 合成的路 |
| --- | --- | --- |
| `IAmmoTransporter`（装弹机） | 运输者，按到达频道分组 | 该运输者 × 它 `getFeedSources()` 里的每一台架；喂弹线为空则该运输者这一轮没有路 |
| `IAmmoSupplier`（再生架／物品架） | 提供者，按到达频道分组 | 仅当本型号声明了完整人力流程（`human_reload_time > 0`）时参与合成：`(本管的 roster, 该架)` |

配对在**路由时**做，不在发现时做：结构变化分清理与重建两个相位，同一个集合里各子系统的重建顺序不确定，装弹机的喂弹线可能比发射器的发现晚一拍就绪；把配对固定成表会把空来源留在表里。

`IAmmoConsumer` 暴露两张登记入口与一个按需合成的视图：

```java
@Nullable AmmoPath getCurrentRoute();
void setCurrentRoute(@Nullable AmmoPath route);
List<AmmoPath> getRoutes();                          // 运输者 × 喂弹线，加人力路；现算，同一对对象只出一条
void addTransporter(IAmmoTransporter transporter, String channel);
void addProvider(IAmmoSupplier provider, String channel);
@Nullable IAmmoSupplier resolveProvider(AmmoRef ref); // 见 §4.4
```

其余成员（`getReloadJob`／`canAccept`）不变。

**频道只是发现表的登记键，不是路的属性。** `resolveTargets(channel)` 按频道分组返回结果，两张表因此按到达频道建；路本身不带频道，也没有读者——弹药池不按频道排序，HUD 不显示它，路由判定不看它。今天的 `LoaderEntry.channel` 就是这样一段死数据（§1）；拆分只保留登记键，不引入按频道分组的视图（D12）。

**评价频次。** `getRoutes()` 每 tick 由路由现算：它是两张表的嵌套遍历（运输者 × 喂弹线，加人力路），同一对对象只出一条，没有缓存也没有跨 tick 状态——结构变化因此立即生效。唯一的成本在 `estimateTicks`：人力路要跑一次只读的选人（座位枚举加读附件），所以它在一次选路内按 `(consumer, provider)` 复用一次（§3.2），候选被比较多少次都只算一遍。弹药池与这两件事无关，它是"HUD 弹链选项卡与数量"的数据源：条目只存一条路、它的交付规格与实时数量，不存任何逐消费者的量（§7 ⑤）。

### 4.2 路由

武器控制器为每根管选一条路。候选必须同时满足四个硬条件，缺一不是"更差的候选"而是"不是候选"：

1. 运输者可工作：`path.transporter().isOperational()`；
2. 提供者可工作：`path.provider().isSupplyOperational()`；
3. 本管炮闩接受提供者的交付规格：`LauncherSubsystem#canAcceptBelt(provider.getDeliverySpec())`，规格为 null 时同样不接受；
4. 运输者没被别人的作业占着：`!path.transporter().isClaimedByOther(launcher)`。

条件 1 与条件 4 由运输者自己回答，条件 2 是提供者的，条件 3 由接收者判定——炮闩兼容性是接收者的属性，运输者不参与。硬条件与代价分工固定：条件决定"能不能选"，代价只决定"选哪条"。条件 2、3 与今天 `WeaponControllerSubsystem#supplyTypeAccepted` 的两次判定同义，条件 4 与 `findSupplier` 里的 `isClaimedByOther` 过滤同义；M1 把它们写成循环里的两个 `if`，不再保留 `canSupplyTo`／`supplyTypeAccepted` 两个私有判据（§7 ⑤）。

排序键与换人判据是同一个值：

```text
路径代价 = path.transporter().estimateTicks(launcher, path.provider())
```

`LauncherSubsystem#ticksToNextRound(AmmoPath)` 是对它的转发，供 `WeaponControllerSubsystem#isWorthKeeping` 与 `findSupplier` 的排序使用。倍率只由运输者折算：同一台弹药架换用倍率更低的乘员，这条路立刻变短。代价每 tick 现读，不取自弹药池——池里的数量是显示用的快照，`getRemainingCount()` 才是实时值。

比较规则是候选必须**严格更早**拿到下一份才换，相等或更慢保持；代价相同时按路的身份决胜（`AmmoRef` 的宿主 SubPart ID → 子系统名），同一份载具状态下每次摊派的结果因此一致。换人的收尾走统一收尾，旧作业的预留与占用按身份释放。

**当前路的有效性每 tick 单独判一次**，判据是"运输者仍在本管的发现表里、提供者仍能解析到、两者都可工作"。任一项不成立就按统一收尾结束旧作业并丢掉指认——不带着已经不可达的提供者继续取弹，也不在同一作业里换架。重选在下一个 tick 由控制器做，可能换运输者，也可能换架。

### 4.3 受理、阶段与交付

| 场景 | 受理 | 阶段 | 交付 |
| --- | --- | --- | --- |
| 人力直取（弹药架＋roster） | `transporter.claim`（认领乘员）→ `provider.reserve` | 只有人工段，时长为 `H × P × A` | 人工段走完直接 `provider.deliverReserved` |
| 全自动机构 | `transporter.claim`（机械槽）→ `provider.reserve` | 只有机械段，时长为 `M` | 机械段走完 `provider.deliverReserved` |
| 半自动机构 | `transporter.claim`（认领乘员）→ `provider.reserve` | 人工段 → `claimForMachineStage` → 机械段 | 机械段走完 `provider.deliverReserved` |

人力直取没有"机械段只有一个 tick"的空段：作业在人工段完成时交付，机械段只在机械运输者上存在。交付实例永远由提供者制造，运输者不在交付路径上。

收尾仍是统一入口：按身份释放运输者的乘员与机械槽、提供者的预留，再发布带原 `jobId` 的已交付／未交付结果。运输者的 `releaseClaim` 不代撤销预留（§3.2 的撤销归属）；人员离场只释放认领并暂停，暂停满 200 tick 才走收尾；结构变化后座位不再出现在发现结果里时同样按不可用处理。

**退弹、换装与当前弹种都只认这条路的提供者。** 这三个入口共用一份去处规则，直接对提供者说话，不经过运输者转发：

```text
退膛的一发、换装换下的旧份、换装被拒退回的新份
    当前路的提供者收下              → 结束
    否则按 getRoutes() 逐台询问其它提供者，每台一次 → 结束
    都不收                          → 记一条警告并丢弃（弹药不入库）
```

两级去处就是全部：第一级是本次交付的来源，第二级是本装配体里其它能收下它的架。这里没有第三级，也不按运输者的发现顺序扫一遍机器——弹链只有提供者能收，问运输者等于多绕一跳。没有当前路时（管上还没有指认）直接丢弃并记警告。

当前弹种（`LauncherSubsystem#getCurrentAmmoType`）的兜底读当前路提供者的 `getSuppliedType()`，与退弹读同一个对象。

### 4.4 客户端

客户端按同一份路由与作业推进自己的一份：人工段每 tick 推进 1（时长已折入倍率，人员状态只由服务端判定），机械段向运输者要推进量；走完即用作业上冻结的规格与份额本地交付、本地扣弹与补膛，不建真实预留、不扣实际库存、不生成投射物。音效按运输者归属：人力运输者没有对象可定位，人工段用接收者自己的音效表；机械运输者（含它的准备段）用运输者自己的游标。

客户端把同步来的两个 `AmmoRef` 解析成实例，**整对解析、整对替换**：

```text
运输者：ref 为 NONE → 本管的 roster；否则在运输者发现表里按身份找
提供者：先问运输者 findProvider(ref)，再查本管的提供者发现表
任一步落空 → 保留上一帧的整对，不替换，也不因此收尾作业
```

机械路的提供者不在发射器的发现表里（它由装弹机自己发现），因此第一步不能省；人力路的提供者就在发射器的表里，因此第二步兜住。逐字段替换会把新运输者与旧提供者拼成一条服务端从未指认的路：今天靠 `LauncherSubsystem#deliverySupplier` 校验"指认与作业上的目标一致"挡住同类问题，拆分后这条校验的形状从"一个供给者"变成"一对引用"——两段都解析成功、且与作业上冻结的那一对相符，才算当前路。作业是权威：作业上的一对与解析出的路不一致时，按作业推进与交付，路只是指认。

## 5. 同步与协议

| 字段 | 形状 | 内容 |
| --- | --- | --- |
| `ROUTE_TRANSPORTER` | `AmmoRef` | 当前路由的运输者；`NONE` = 人力运输者 |
| `ROUTE_PROVIDER` | `AmmoRef` | 当前路由的提供者；`NONE` = 没有路由 |
| `JOB_ID`／`JOB_SPEC`／`JOB_RESERVED`／`JOB_TOTAL`／`JOB_ELAPSED`／`JOB_STAGE`／`JOB_RESULT`／`JOB_RESULT_DELIVERED` | 作业部分整包（`ReloadJobSync`），结束结果两项在包外 | 作业身份、冻结分配、本阶段时长与基线、阶段；结束结果仍只描述已经结束的那一条 |
| `JOB_TARGET` | `AmmoRef` | 本作业的运输者；`NONE` = 人力运输者 |
| `JOB_ORIGIN` | `AmmoRef` | 本作业的提供者；`NONE` = 没有作业 |
| `SLOT_OWNER` | 作业身份 | 仅 `canServeMultipleConsumers() == false` 的机械运输者下发 |
| `AMMO_COUNT`／`RESERVED` | 不变 | 提供者的实际库存与预留总量 |

客户端按 `JOB_TARGET` 是否为空与 `JOB_STAGE` 得到完整描述：`NONE` ＋ 人工段 ＝ 人力运输，推进 1、用本管音效表、走完即交付；非空 ＝ 机械运输者，机械段向它要推进量、音效用它的游标、准备段由它播。作业字段整包下发，因此"有没有作业"由快照本身表达（`Optional.empty()`），不需要在编号里留一个哨兵；快照存在时其中的运输者引用与阶段总是同时可读。

路由指认由两个引用表达：`ROUTE_TRANSPORTER`（`NONE` = 人力运输者）与 `ROUTE_PROVIDER`（`NONE` = 没有路由）。两个字段是一对量，客户端按整对解析与替换（§4.4），单个字段先到不构成一条路。两个作业字段的含义固定：`JOB_TARGET` 恒为运输者，`JOB_ORIGIN` 恒为提供者。字段表已变，协议组要提升到 `sync:9.0.0`——`8.0.0` 已被"装填作业改为一包快照"占用，本次是在那之上的又一次字段表改写（实际值以 `network/MMPayloadRegistry.java#register` 为准）。作业、占用与预留都不持久化，存档格式不变。

## 6. 内容与存档

字段集合与结构不变，三处键名统一为"装填手"（`loader`；装弹机的类型 id 是 `ammo_loader`，两者不会混）。下表左侧是内容里现有的写法，右侧是本次之后生效的写法，作者需要按它改自己的型号与座位实例：

| 现名 | 新名 | 落在 |
| --- | --- | --- |
| `reload_operator_discovery_targets` | `loader_discovery_targets` | 机构型号、发射器型号的安装属性 |
| `reload_operator_time_multipliers` | `loader_time_multipliers` | 同上 |
| `reload_operator_discovery_inputs` | `loader_discovery_inputs` | 座位实例 |

改名是一次纯机械迁移，作为 M0 单独提交（§7），不等待本次拆分：三个 codec 键与对应的 getter、全部第一方内容实例、builtin schema 与其余包的副本、技能快照、测试夹具一起改，`grep -rn reload_operator src` 清零。其余字段（`ammo_discovery_targets`／`ammo_discovery_inputs`／`human_reload_time`／`reload_time`／`can_supply_multiple`）不变，第一方内容除了这三处键名不需要其他迁移。语义有两处变化，都要随本次落到作者可见的地方：

**一、发射器 `human_reload_time` 的说明。** 它现在只表示"本型号有一条完整人力路"。builtin 的 `launcher_static_attr.schema.json` 里该字段的描述需要整段重写（两种语言），它今天同时说错两件事：一是"省略或写 0 表示不支持该路径，这根管只经自动装弹机装填"——拆掉"交付方用人"的优先级之后，没有人力路的管走的是机构路（装弹机经自己的喂弹线取弹），不再有"只经自动装弹机"这层限定；二是"交付方自己声明了人工段时由它负责用人，本字段不参与"——这条优先级规则被取消（§3.4）。重写后同一段要写清三件事：0 表示没有人力路、弹药由机械运输者经喂弹线取得；人工段时长是基准秒数乘岗位倍率与个人倍率；两条已知的配置失误各有一次启动告警（座位没声明频道、没发现到任何弹药架）。因此跑 `./gradlew syncSchemas` 把其余第一方包的副本与技能快照一起更新；`checkSchemas` 校验的是副本与 builtin 一致，不是"没有变更"。字段集合与结构不变。

**二、第三方内容的组合语义。** 同时写"发射器 `human_reload_time`"与"只配了 `reload_time` 的机构"的型号，人工段在机构路上不会发生：机构那条路没有人工段，人力那条路要发现到架才存在。发现不到架时人力路根本不存在（发现阶段打一次警告，文案指明检查 `ammo_discovery_targets` 与弹药架的接线）；能发现到架时两条路按代价竞争，作业不会把两段拼成一条。第一方内容不受影响——`120mm_m256` 与 `50mm_kwk39` 声明了 `human_reload_time`，它们的机构在 S22 已拆掉，走的是人力路。

存档格式不变：作业、机构占用、架预留都不入档，读档后按发现结果重新受理。

## 8. 验收

```bash
./gradlew --offline classes
./gradlew --offline test
./gradlew --offline runGameTestServer
./gradlew checkContent       # 内容引用不变，应无输出
./gradlew syncSchemas        # 写出 builtin 的文案变更、其余第一方包的副本与技能快照
./gradlew checkSchemas       # 副本与 builtin 一致
```

本机存在 `../ARMS-Core` 兄弟目录时，复合构建会一起编译；`IAmmoSupplier`、`IAmmoTransporter`、`IAmmoConsumer` 与 `AmmoRef`／`AmmoPath` 是公共 API，那里的编译过关才算接口收敛。

验收点：

- 受理的两侧可分别观察：提供者的可分配数量只减少 `q`、实际库存 `N` 不变；运输者的槽位（或乘员认领）只属于该作业。收尾后两侧同时释放，旧身份的回调摘不掉新作业。
- 人力直取：走完人工段即交付，没有多余的机械段；乘员离座后作业暂停、满 200 tick 未交付收尾，换人保留进度。
- 全自动机构：受理即进入机械段；独占运输者对别的管表现为已占用（因此不是候选），对自己不算。
- 可工作性：运输者被打坏或断能时路由当场改选，不靠"暂停满 200 tick 再收尾"兜底；提供者被打坏时当前路当场收尾。这两条各由一侧回答，任一侧失效都不必等对面。
- 半自动机构：准备段只占人、不占槽，准备段结束后才补槽位，预留自始至终只有一份。
- 承诺判定：换人（人工段换乘员）不触发收尾，作业、预留与进度都保持不变；预留被撤销或已兑现、占用被身份匹配的释放摘掉、消费者停用这三种情形才当场收尾。
- 撤销只有一个常规写者：正常收尾只有接收者在写提供者的预留表；运输者的 `releaseClaim` 过后预留仍在，只有失效清理会代撤销。
- 路径有效性：拆下装弹机后这条路由失效并按统一收尾；喂弹线在结构变化后的空窗里，已在推进的作业按承诺继续、不换架；不可达的路先收尾，重选时重建。
- 代价含加成：同一台弹药架在换用倍率更低的乘员后，这条路的预计时间随之变短并被路由改选；两条路的比较、换人判定与候选排序读同一个值，没有第二处按基准时长推算的排序键，也没有把逐消费者代价存进弹药池。
- 退弹去处：膛内那一发与换装换下的旧份都先交给当前路的提供者；它拒收时按路由询问本装配体里其它提供者，仍无人接收才丢弃并记警告。没有当前路时直接丢弃。
- 两端解析：同一份作业在服务端与客户端解析出同一对 (运输者, 提供者)；只有一个字段先到时客户端保留上一帧的整对，不产生"新运输者 + 旧提供者"的混合路；机械路的提供者不经发射器发现表也能解析到时，客户端不因发现顺序晚一拍而收尾；客户端判断"预留还在"只问作业上的那一台提供者，不退回别的架。
- schema：`checkSchemas` 通过，其余第一方包的副本与技能快照随 builtin 一起更新，`checkContent` 无新增输出。

**不宣称已验**：半自动准备段的端到端行为需要一份配置了 `human_reload_time` 的机构型号与真实乘员，第一方内容没有这种型号，只能在实机上用临时内容标定；FMOD 装填事件仍未接线；多人场景下的 HUD 与音效未做实测。

## 9. 决策记录

| 编号 | 结论 |
| --- | --- |
| D1 | 提供者由**接收者指名**。机械运输者的喂弹线由它自己发现并以 `getFeedSources()` 交出，接收者把它作为本次指名的提供者；人力运输者没有喂弹线，提供者取接收者自己发现到的架。指名体现在两个动作上：接收者对那台提供者调 `reserve`，以及把它写进作业——此后 `getAdvanceTicks` 与交付都只认作业上的那一台 |
| D2 | `isHuman()` 显式回答"是不是人力"，由类型决定，不由时长推断，是唯一权威；另两个读法是它的派生，三者在解码期做一次一致性校验。人力运输者的基准时长为 0 时不进入路由（§3.2） |
| D3 | `canServeMultipleConsumers()` 是唯一的产能声明：产能只由运输者回答，提供者没有产能声明 |
| D4 | 人力运输者没有机械段：人工段走完即交付，作业不保留空机械段 |
| D5 | 半自动准备段的能力保留在机械运输者上（`human_reload_time` 与 `reload_time` 同时存在），第一方暂无这种型号 |
| D6 | 路由代价含全部加成，由运输者的 `estimateTicks(consumer, provider)` 统一回答：人工段乘 `P × A`、机械段按基准，接收者与武器控制器只读这一个值。缺弹等待仍只按这一 tick 的可分配库存判定，再生时间的折算另议 |
| D7 | 提供者不认识接收者：预留、兑现与撤销只按作业身份记账，运输者也不出现在提供者的任何签名里。一次作业一份预留，取它只需要身份与规格，而规格是提供者的属性 |
| D8 | 退弹与换装旧份的去处只有两级：当前路的提供者，其次本装配体里其它提供者；两级都不收就丢弃并记警告。弹链只有提供者能收，因此去处不经运输者转发，也不按运输者的发现顺序扫机器 |
| D9 | 发射器 `human_reload_time` 的 schema 描述整段重写，`syncSchemas` 产生的副本变更属于本次交付；`checkSchemas` 的判据是副本与 builtin 一致 |
| D10 | 接口与调用方一次切换：`IAmmoSupplier` 的收缩与 `IAmmoTransporter` 的引入落在同一次提交里，两个接口之间没有"同时实现"的中间态，`AmmoRef` 因此不需要靠重载解析区分角色 |
| D11 | 被别的作业占着的独占运输者**不是候选**，不折算成等待代价；缺弹等待只按本 tick 的可分配库存判定（0 即等价于不可达），再生时间的折算另议。这条与 `findSupplier` 的现状一致，主计划 §9 第 1 条的等待口径随之改写 |
| D12 | 路不带频道：频道只是发现表的登记键（`resolveTargets` 按频道分组），没有读者，因此不提供按频道分组的视图，也不把频道写进池条目 |
| D13 | 撤销归接收者：`releaseClaim` 只释放运输者自己的资源，提供者的预留表只有一个常规写者；唯一例外是运输者的失效清理——消费者已无机会收尾时按身份代撤销，否则预留会永久占住库存 |
| D14 | 客户端按整对解析与替换路由：两个 `AmmoRef` 任一解析失败就保留上一帧的整对，不产生混合路；作业上冻结的那一对是权威 |
| D15 | 装填手相关的键与类型改名为 `loader_*`／`LoaderRoster`，作为独立的机械提交（M0）先落地，不与接口切换混在一起 |
