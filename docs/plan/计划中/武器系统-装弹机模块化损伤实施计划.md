## 2. 范围与交付边界

### 2.1 第一期必须完成

1. 再生装弹机继承 `ModularSubsystem`，具有 `feed` 和 `magazine` 两个内部模块。

8. 纯逻辑测试、真实子系统接线测试与运行期验收清单。
9. 模块化子系统在 `pass_damage=false` 时仍吸收伤害（§3.5），第一方发射器的模块耐久随命中下降。

## 3. 模块模型与状态契约

### 3.1 两个固定模块

| 模块名 | 静态属性类型 | `critical` | 业务职责 |
| --- | --- | --- | --- |
| `feed` | `FeedModuleAttr` | 硬编码 `false` | 输送与交付能力；不拥有库存 |
| `magazine` | `MagazineModuleAttr` | 硬编码 `true` | 可用的储存结构；损坏时停止存入、再生和供给，满足条件时库存殉爆 |

两个类型均放在 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/attr/static_attr/module/`，继承现有 `AbstractModuleAttr`，只承载本期实际使用的 `durability_weight` 和固定的关键性。属性形态参考 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/attr/static_attr/module/BreechModuleAttr.java#BreechModuleAttr`。

`RegenLoaderSubsystem#defineModules` 按 `feed`、`magazine` 的固定顺序声明两个模块。模块名是内容包及存档契约，不能由实例任意改名。

静态 definition 的顶层字段为 `feed` 和 `magazine`，与发射器的显式模块字段组织一致。两个字段均提供默认实例，保证已有 definition 可以解码。默认耐久权重均为 `1.0`；单模块最大耐久为：

```text
moduleMax = basic_durability × moduleWeight / (feedWeight + magazineWeight)
```

例如总耐久 20、权重各为 1 时，两个模块各为 10。这个默认值是迁移起点，不是已经完成玩法标定的参数。定点击毁某个模块所需伤害可能低于整机 20 点，内容作者须按 §11 记录标定。

Codec 在装弹机属性边界校验：`basic_durability` 和两个权重必须为有限正数，权重合计也必须有限且为正。不要把这项验证扩散为所有子系统的无关重构。`critical` 不开放 JSON 配置，schema 也不列出它。

校验结果以 Codec 的 `DataResult` 错误表达，不靠构造器抛异常；`BasicAttr` 的共享编解码器本任务不改动，装弹机边界自行复核它的取值。内容包加载按文件隔离：`SparkPackLoader` 逐文件捕获解码失败并记一条 ERROR，该定义不注册，其余文件与后续包继续加载。两条路都不影响别的实例，差别只在诊断文案——`DataResult` 走 `PackCodec` 的 `spark_core.pack.*` 文案与字段名，抛异常只留下异常消息。

### 3.2 三种判定分别读取什么

| 判定 | 含义 | 读取来源 |
| --- | --- | --- |
| 实际库存 | 还存着多少发 | `AMMO_COUNT_ID`；不因机构故障写成 0 |
| 供给工作能力 | 当前机构、弹仓和宿主是否允许交付 | §4 的 `isSupplyOperational`；不包含库存是否非空 |
| 整机摧毁 | 关键储存结构失效及其修复锁存 | 弹仓模块的 `destroyed`，汇总到基类 `DATA_DESTROYED_ID` |

`hasAmmo`、`getRemainingCount` 和 `getCapacity` 保持物理库存/容量语义。空仓但健康的再生装弹机可以有工作能力；有 50 发但机构损坏的装弹机可以没有工作能力。

### 3.3 状态结果

下表假设宿主有效、子系统启用；膛内已有弹药是发射器自己的状态。

| 情形 | 后续交付 | 再生 | 库存 | 整机摧毁标志 |
| --- | --- | --- | --- | --- |
| 两模块健康 | 可按请求→就绪→取弹流程进行 | 可进行 | 正常增减 | false |
| `feed` 归零，弹仓健康 | 立即阻断 | 可继续至满仓 | 保留 | false |
| `feed` 修复至 0%—30% 之间 | 仍阻断 | 可进行 | 保留 | false |
| `feed` 修复至至少 30%，模块已脱离摧毁 | 从新的请求重新计时 | 可进行 | 保留 | false |
| `magazine` 归零，尚未进入判毁 tick | 立即阻断 | 立即停止 | 等待判毁时按贡献处理 | 当下可能尚为 false，不能只检查它 |
| 弹仓已判毁 | 阻断 | 停止 | 殉爆贡献非零时清空；零贡献时保留 | true |
| 弹仓已判毁，修复至 0%—30% 之间 | 阻断 | 停止 | 不因修复凭空增加 | true |
| 弹仓修复至至少 30% 且框架完成恢复 | 取决于 `feed` 是否可用 | 可进行 | 保留现值，再生按正常计费开始 | false |

两个模块共用同一条恢复规则：归零即摧毁，修到自身最大耐久的 30% 才脱离摧毁，0%—30% 之间保持摧毁。两者的差别只在整机判据上——整机摧毁由关键模块决定，任一关键模块摧毁即整机摧毁；非关键模块摧毁只让该模块不可用，不改变整机摧毁位。因此机构修到 20% 时交付仍被阻断，但整机既不报摧毁也不触发库存殉爆。两条都要有测试覆盖。

### 3.4 为什么只有弹仓是关键模块

整机 `onDestroyed` 只在进入摧毁状态时调用一次。如果把机构也标为关键，机构先坏会占用整机摧毁边沿，弹仓后坏时可能漏掉殉爆。两个模块都关键的方案不符合本计划。

本期的唯一关键模块就是弹仓，因此可以使用既有整机回调执行弹仓判毁。`onDestroyed` 的库存处理入口还须显式核对弹仓确实损坏，不能把任意外部直接调用的整机回调等同于弹药被击毁。未来添加其他关键模块时，必须同时重审这条前提；那时需要弹仓自身的判毁边沿，不能只向 `defineModules` 增加一行。

### 3.5 模块伤害必须能落地：`pass_damage` 的两条路径

模块化子系统的伤害入口按 `pass_damage` 分两条路（C17）：

1. `pass_damage=false`：取消事件在前，模块路由在后。事件被取消，零件与载具不扣耐久；随后照常执行 `limitDamage` 与 `routeDamage`，伤害由模块吸收。
2. `pass_damage=true`：事件不取消，模块先按相同金额扣耐久，该金额再按既有规则传给零件。

非模块化基类的同一字段表达的是“取消向下传递、伤害由子系统自己承担”——`BasicSubsystem#onHurt` 取消事件后仍扣自身耐久，wiki《子系统概述》也把它写成“伤害完全由子系统自身吸收”。第一条路径与这个口径一致。

第一方在用的发射器定义与全部再生装弹机定义都写 `pass_damage=false`（builtin 的 `basic_launcher` 是没有实例引用的模板，取默认值 true）。模块伤害只在“取消之后仍继续路由”时下降，因此 §3.3 的状态表、§6 的殉爆入口、§11 的 T02/T07/T13/T22 都以这条口径为前提。

影响面与验收：

- 唯一继承 `ModularSubsystem` 的是 `LauncherSubsystem`。第一方火炮的 `barrel`/`breech`/`capacitor` 耐久随命中下降，炮管散布与初速衰减、炮闩射速与弹药兼容性随之生效。这是本期要接受的玩法变化；发射器的模块损伤、修复与加载回归与数值标定一起做（§10 已要求这三类回归）。
- 装弹机沿用 `pass_damage=false`：`feed`/`magazine` 可损，命中伤害不传到零件。希望伤害同时伤及车体的内容把它写成 `pass_damage=true`，此时模块先扣耐久。
- 事件被取消时 `SubPart` 不产生零件耐久记账与载具伤害（C16），因此“只伤子系统”的验收要同时断言三条：模块耐久下降、零件耐久不变、载具伤害为零。
- 本契约不改变事件的取消标志、`limitDamage` 口径与伤害管线其余环节。

## 4. 供给接口、路由与交付入口

### 4.1 供给能力查询

在现有 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/IAmmoSupplier.java#IAmmoSupplier` 中声明：

```java
boolean isSupplyOperational();
```

这是工作能力查询，不启动计时、不修改库存，不要求有弹。两个现有实现都必须实现它：

- 再生装弹机：基类 `isActive()` 为真，且 `feed`、`magazine` 都未处于摧毁状态。模块修到 0%—30% 之间仍算摧毁，因此这段区间也判为无工作能力。基类 `isActive` 已包含整机恢复锁存、宿主状态与组装许可，因此不要覆盖它来表达机构故障。
- 普通装弹机：返回现有整机 `isActive()` 的结果，保留非模块化形态。

接口至少有两个真实实现；不要为此增加新供给者接口、适配器或故障状态 record。模块是固定必需项，构造和解码保证存在，不为内部模块查询叠加多层默认值。

### 4.2 路由必须使用实时能力

`WeaponControllerSubsystem#supplyTypeAccepted` 使用 `isSupplyOperational` 判断供给者能力，再执行既有弹种兼容检查。所有依赖该方法的候选、保留和回退路径一起核对，重点是 `findSupplier`、`isWorthKeeping`、`canSupplyTo`。

不要仅在每 10 tick 的弹药池重建/刷新时过滤坏机构；选定、保留当前供给者必须读取实时能力。机构坏后可切换另一台健康供给者；没有可用供给者时清除指认，膛内弹药照常保留，沿用 C9。

弹药池是拓扑与库存的显示源。`rebuildAmmoPool` 在机构故障期间保留弹链条目，`refreshAmmoPoolCounts` 继续读取真实剩余数。修复机构无需重新握手才被发现，已有拓扑引用即可恢复参与路由。

### 4.3 三个交付方法都要检查

| 方法 | 无工作能力时的结果 | 必须避免的旁路 |
| --- | --- | --- |
| `requestRound` | false；不创建计时器或就绪位 | 重复请求、瞬时交付 |
| `isRoundReady` | false；不自动为坏机构重新请求 | 已有就绪位、隐式重试 |
| `consumeReadyRound` | null；不扣库存、不推进指针 | 不经过控制器的直接取弹、同 tick 伤害后的取弹 |

在已有就绪/幂等分支的入口先执行门控。`reload_time=0` 同样需要健康机构，“没有计时延迟”不代表绕过机构。

`getStatus` 对无工作能力的供给者返回 `SupplierStatus.EMPTY`，`getReloadProgress` 对其返回 0。本期保留三个枚举值；把 `EMPTY` 的接口注释写清楚为“该消费者当前无可交付弹药”，不要用它反向推断库存为零。膛内有弹时，HUD 的发射管状态仍由膛内弹优先报告 READY。

### 4.4 交付承诺的失效

机构或弹仓从正耐久降到 0 的当次主线程伤害应用中，释放所有尚未取走的交付：

- 清空 `deliveryLoadedTicks`、`readyConsumers` 和 `lastPlayedProgressKeys`。
- 不补回弹药，不推进 `BELT_INDEX`。C2 的库存扣减发生在实际取走时，因此承诺阶段没有已扣出的弹药。
- 机构修复后新请求从 0 tick 开始；受损前的输送进度不自动接续。
- 已进入发射器 `chamberedType` 的弹不受这次释放影响，已提交的发射也不撤回。

在 `RegenLoaderSubsystem` 内提取一个无额外状态的交付清理方法，供损坏处理、殉爆消耗和相关客户端表现清理调用即可。不要建立消费者等待队列。

`routeDamage` 是模块伤害的公共入口。损坏后的交付清理必须覆盖通过它直接施加的伤害，不能只放在 `onHurt` 事件路径里。使用前后耐久比较识别本次进入零耐久的模块，正常启停的暂停规则与这条破坏规则分别处理。

## 5. 再生、退弹与计费

### 5.1 拆开 tick 的工作门控

`RegenLoaderSubsystem#onTick` 首先调用 `super.onTick()` 维护生命周期和同步。业务推进至少按下列语义组织：

1. 清理失效消费者和表现遗留，不能让整机停机导致无主交付长期占用。
2. 弹仓损坏或整机恢复锁存未解除时，禁止输送与再生。
3. 宿主不允许工作或子系统未启用时，按现有停摆语义暂停计时。
4. 机构健康才推进交付计时；机构损坏时没有可推进的交付承诺。
5. 弹仓可工作且整机允许工作时推进再生延迟及逐发/批量再生，独立于机构状态。
6. 客户端只播放当前真实推进过程的进度音效；机构损坏时不得继续播输送音效。

服务端是库存、弹链和实际能量结算的权威端。客户端根据同步状态维护表现；本期不要把模块损伤判定放进物理线程，也不要在物理线程读写弹药计数或进度集合。伤害入口与业务消费的相位依据见 C16 及子系统目录的 `AGENTS.md`。

### 5.2 弹仓损坏时的再生状态

弹仓首次降到零时，清除 `regenProgress`、`batchElapsedTicks`、`isBatchReloading`、`regenDelayRemainingTicks` 和批量进度音效标记。它们表示储存单元内进行中的产出，不能在修复后立刻完成受损前那一批。清理点是子系统摧毁回调（`RegenLoaderSubsystem#onDestroyed`）——弹仓是唯一关键模块，该回调等价于"弹仓归零"；读档不补发摧毁回调，因此载入边界在 `isDestroyed()` 为真时再清一次（§7.3）。

批量模式已预扣的能量不退款；修复后从新批次开始，并按既有批量启动规则支付新批次能量。机构损坏只清理输送承诺，保留以上再生状态，也不额外扣除或退还能量。

零贡献弹药在弹仓损坏时可保留计数，但储存结构修复前不能被取走、接收退弹或继续再生。这是“库存未被殉爆消耗”和“弹仓可工作”两个不同事实。

### 5.3 `returnRound` 的明确口径

退弹按“已被取走的一发重新记入储备”处理，本期不模拟逆向输弹机械。机构损坏而弹仓可储存时允许退还；弹仓损坏或处于整机恢复锁存时拒绝退还。启停开关不单独禁止退还，既有弹链成员与容量检查继续生效。

不得借退弹入口向损坏弹仓灌入弹药；也不得把承诺释放错误实现成一次退弹。

## 6. 殉爆入口与弹仓受击定位

### 6.1 执行相位与触发条件

继续在服务端主线程的 `onTick → onDestroyed` 执行库存快照、贡献合成和爆炸提交，不在 `onHurt` 内立即调用爆炸服务。入口条件为：

```text
服务端
且 magazine 当前为摧毁状态
且实际库存非空
且 CookoffComposition 非空
```

**不检查宿主状态**：已摧毁零件留下的残骸仍可被攻击并引爆弹药架，这是有意的玩法设计。宿主零件被摧毁时子系统只是 `setActive(false)`（`SubPart#setDestroyed`），子系统继续 tick，因此残骸上的弹仓归零照常走判毁边沿并起爆；零件整体移除后子系统不再 tick，自然不会起爆。前两条由判毁边沿本身保证（`isModularDestroyed` 即弹仓摧毁），后两条在 `detonateStoredAmmo` 内判断。

客户端 `onDestroyed` 只执行基类表现。机构损坏、正常停用、卸载、脱离和从存档恢复一个已坏弹仓，均不构成一次新的库存殉爆事件。

本期采用既有 tick 判毁模型：整机判毁读的是关键模块的摧毁状态（`isModularDestroyed`），不是弹仓耐久是否为零。因此判毁相位开始时即使弹仓刚被修到正耐久，只要它还在 0%—30% 的恢复锁存里，这次整机摧毁照样成立；若它在判毁相位之前就修过了 30%、模块已脱离摧毁，本次判毁不成立。不要同时实现一条“受击时先起爆”的并行路径；伤害与修复同 tick 的测试须固定这条规则。

### 6.2 弹仓自己的受击来源

整机的最近有效受击不能作为弹仓爆点来源。例如同一结算批次中：

```text
A 命中弹仓并使其归零
B 随后打伤仍健康的机构
下一次子系统 tick 判定弹仓摧毁
```

整机的最近受击可能已经是 B，用它定位会把弹仓殉爆放到机构的命中箱上。

做法是把最近有效受击下沉到模块：`SubModule` 保存自己最近一次有效受击的定稿事件，`ModularSubsystem#routeDamage` 只在某个模块的耐久确实下降时更新它。于是：

1. 定向命中只更新被指名的模块；比例分摊命中更新所有真的掉了耐久的模块。
2. 打伤机构、零伤害、被拦下的伤害都不会碰到弹仓的记录。
3. 已摧毁模块的 `applyDamage` 返回 0，零耐久的追加命中不会覆盖它，记录冻结在打穿它的那一击。
4. 模块脱离摧毁时清空记录（`SubModule#normalizeDestroyed` 的出口），因此修复到恢复门槛、读档、整机恢复之后都从零开始，下一次生命周期不会沿用旧爆点。
5. 记录不进 NBT、不进同步：新实例与客户端恒为 `null`，只有服务端起爆读它。

位置与豁免键必须依据同一个命中箱，所以两者只共用一处来源：`AbstractSubsystem#getLastHitBox` 给出"最近一次有效受击指认的那个命中箱"，`getLastDamageOrigin` 与 `getCookoffIgnoredKeys` 都由它派生。基类读子系统级的记录；再生装弹机覆写这一个方法，改读弹仓模块的记录。来源为 `null` 时起爆点回退宿主质心、**不豁免任何命中箱**——不知道爆点落在哪个命中箱里就一个都不放行，不放行宿主的全部命中箱。

命中箱不存对象引用：`AbstractSubsystem#resolveHitBox` 从事件里的命中箱名回宿主查当前那一个实例，因此结构变化替换命中箱之后不会指到旧几何；名字在宿主上已不存在时返回 `null`，按无来源处理。

### 6.3 库存合成与消耗

复用 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/explosion/CookoffComposition.java#addStoredRound` 和现有装弹机的弹链统计。

- 统计范围是一台装弹机的实际库存，按当前弹链指针解析构成；不按 `magazine_capacity` 假定满仓。
- 纯能量弹、惰性弹或未配置贡献的弹种不会仅因使用再生装弹机就获得爆炸贡献。
- 合成为空时不起爆、不清空库存，弹仓保持失效。
- 合成非空时，先将当前库存归零并清理交付，再向普通爆炸服务提交一次；其中零贡献弹种也随该库存单元一起消耗。
- 修复只恢复结构与能力，不恢复已经消耗的弹药。后续再生按 §5 开始。

爆炸参数、贡献计算和连锁传播继续遵循第 1 节引用的殉爆机制设计 §3、§4。本任务不修改其伤害/冲量公式，不增加额外冷却和整车去重。

## 7. 持久化、迁移与同步

### 7.1 再生装弹机的存档内容

已有库存、弹链与再生字段继续保存：`ammo_count`、`belt_index`、`regen_progress`、`batch_elapsed`、`is_batch_reloading`、`regen_delay_remaining`。现有 `batch_cooldown` 的兼容读取沿用 `RegenLoaderSubsystem#loadData`。

模块沿用 `ModularSubsystem#saveData` 的形式：

```text
modules:
  feed:     { durability: <绝对值>, destroyed: <布尔值> }
  magazine: { durability: <绝对值>, destroyed: <布尔值> }
```

存档里没有整机摧毁键。整机摧毁状态是“任一关键模块 `destroyed`”的汇总，`modules` 已经完整表达它；模块自己带着 0%—30% 的恢复锁存（§3.3），所以整机锁存也跟着模块一起往返，不需要第二个键，也不会出现与模块分叉的整机标志。`ModularSubsystem#saveData` 因此删掉父类写出的整机 `destroyed` 键，`durability_ratio` 继续保留供 §7.2 的旧存档映射使用。

交付计时与消费者对象引用不持久化。载入时交付从空开始，发射器中已保存的膛内弹仍由发射器恢复。

### 7.2 单一耐久存档的映射

映射不需要单独的迁移分支：基类 `AbstractSubsystem#loadData` 把 `durability_ratio × getMaxDurability()` 写进 `setDurability`，而 `ModularSubsystem#setDurability` 把这一笔在模块之间分摊。旧存档的两个模块从满耐久出发，按缺失容量分到同一比例，结果就是：

```text
moduleDurability = oldRatio × currentModuleMax
moduleDestroyed  = moduleDurability <= 0
```

旧 40% 耐久因此恢复为两个 40% 模块，聚合仍为 40%，而不是两个满耐久模块。比例缺失时基类取 1；比例非有限时基类记一条诊断并按 1 处理，NaN 不会写进模块。

已有 `modules` 数据优先：模块条目在分摊之后逐项覆盖，已经存在的条目保留自己的绝对耐久与摧毁标志。必需模块条目缺失时，该模块保留分摊出来的耐久，并记一条警告说明用的是整机比例。不要因缺一项而覆盖另一项已保存的损伤。

带模块的存档按模块绝对耐久加载，并按当前最大耐久钳位，沿用 C12。`durability` 与 `destroyed` 不一致的外部数据在加载边界归一（`SubModule#load`）：零耐久必须为摧毁；耐久已到恢复门槛必须为未摧毁；两者之间沿用存档值，于是修复到 0%—30% 之间的恢复锁存能跨存档保留。归一结果只落在模块标志上，整机摧毁状态在模块读入后由 `ModularSubsystem#restoreDestroyed` 汇总得出。

### 7.3 恢复锁存且不重放殉爆

模块读入后，整机同步摧毁位按模块汇总，不读任何整机存档键：

```text
任一关键模块 destroyed → true
其余                   → false
```

关键模块的 `destroyed` 已经带上了 0%—30% 的恢复锁存（§7.2 的归一），所以“弹仓修到 10% 仍是摧毁”在读档后直接成立，不需要额外字段。

旧存档没有 `modules` 标签，只能按 §7.2 的唯一比例映射出两个模块，映射出的 `destroyed` 由零/正耐久决定。旧存档无法表达历史上是否处于锁存，因此“弹仓修过但不到 30%”这一状态在第一次往返后会回落为未摧毁；这条兼容限制须在迁移说明中明确。

加载属于恢复历史状态，不能通过调用 `onDestroyed` 初始化它，也不能让首次 `onTick` 把历史零耐久重新识别成一次受击殉爆。已保存库存无论是否非空，都按恢复后的库存保留；其后必须经历真实修复和新的损坏才能形成新生命周期事件。

加载同时清空交付、弹仓受击来源和进度音效追踪。若弹仓仍处于恢复锁存，按 §5.2 清除进行中的再生状态；机构单独受损不清除已保存的再生进度。禁止把加载阶段的任意状态清理当作一次库存扣减。

迁移实现在再生装弹机加载边界内完成；C12 的通用迁移缺口要被覆盖，但本任务不擅自改变发射器及所有模块化子系统的存档契约。

### 7.4 同步必须覆盖模块初值与继承链变化

1. 再生装弹机的 `defineSynchedData` 先调用 `super`，再定义库存和弹链项，确保 `ModularSubsystem#DATA_MODULES_ID` 已注册。
2. 模块状态通过现有 `CompoundTag` 访问器同步，只使用通用模块同步通道。
3. 构造时在本类 `attr` 已赋值后，才允许初始化模块并发布模块快照；加载、迁移结束也必须把最终模块状态写入该快照。不要在父构造器中访问尚未赋值的子类属性。
4. 不能只等待 `routeDamage/routeRepair` 标脏。载入一个损坏状态保持恒定的装弹机，也必须经 C14 的全量补推收到正确模块初值。
5. 客户端接收模块快照后清理已失效的交付表现，但不修改权威库存，不调用服务端殉爆或实际能量结算。模块数据和整机摧毁位的到达顺序不能造成一次瞬时取弹。
6. 全量补推继续只读获取同步值，不强制把全局同步表标脏。

继承链加入 `ModularSubsystem` 会改变再生装弹机后续访问器的编号。即使 `SubsystemSyncPayload` 的字段列表未变，客户端与服务端也必须使用相同的访问器布局，因此 `src/main/java/io/github/sweetzonzi/machine_max/network/MMPayloadRegistry.java#register` 的世界同步协议已随 P1 从 `sync:2.7.0` 提升到 `sync:2.8.0`，`src/main/java/io/github/sweetzonzi/machine_max/network/AGENTS.md` 与 `docs/部件公共基础接入.md` 的协议说明同步更新。之后再改动子系统访问器布局时，同样在改动提交里提升该组版本并使用当时版本的下一档，不覆盖其他任务的版本更新。

## 8. 内容包与 schema

### 8.1 静态 definition 示例

以下字段属于装弹机 definition 顶层；`projectile_types` 和 `discovery_outputs` 仍属于部件中的实例配置：

```json
{
  "type": "machine_max:regen_loader",
  "basic_durability": 20,
  "feed": { "durability_weight": 1.0 },
  "magazine": { "durability_weight": 1.0 },
  "magazine_capacity": 74,
  "regen_per_minute": 120,
  "regen_round_by_round": true,
  "energy_cost_per_round": 0,
  "reload_time": 0.45,
  "can_supply_multiple": false,
  "regen_delay": 0.3
}
```

该示例省略音效，仅展示完整可解码的字段组合。两个模块属性只有权重，不把再生速率、库存计数或弹种复制到模块属性里。

### 8.2 命中箱必须按物理含义标注

已有 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/HitBoxAttr.java#module` 可直接使用。相同子系统下，弹药区域指向 `magazine`，机构区域指向 `feed`：

```json
{
  "subsystem": "subsystem.machine_max.2a90_ap_loader",
  "module": "magazine"
}
```

这是向既有命中箱条目添加字段的局部示例，其形状、材质、厚度和骨骼引用由原条目提供；它不是一份独立可载入的命中箱定义。机构命中箱同理使用 `"module": "feed"`。

`subsystem` 必须属于同一 SubPart；不能为了共享机构而把名称指到另一个 SubPart。独立机构和弹仓命中箱使用不同 `id`，避免同一次攻击的命中去重把两个部位当作一个。机构命中箱必须有真实模型几何，不能靠覆盖整个炮塔的箱体假装精确损伤。

未写 `module` 的外部内容继续使用 C4 的按最大耐久比例分摊，既可能损伤机构，也可能损伤弹仓。未知模块名继续使用通用框架的警告和分摊规则；本任务不改变全体子系统路由。因而“只伤机构不伤弹药”的保证只对实际指向 `feed` 的命中成立；不应声称空模块名也具有该保证。

当前 2S38 的 AP/HE 使用不同装弹机实例（同一 JSON 的 `subsystem.machine_max.2a90_ap_loader` 与 `subsystem.machine_max.2a90_he_loader`）。本计划只隔离每个实例内部的机构和弹仓，不声称两个实例已经共享同一机构。若模型表明一台机构为两仓服务，实施报告应注明该建模限制，不能复制一个重叠机构箱给两个实例来制造共享损伤假象。

完成条件包含一条真实“只命中机构”的可复现路径。若现有第一方模型没有相应几何，需提供一件最小的测试资源或真实模型部位，并明确资源用途；仅给现有弹药箱补 `magazine` 字段只能算弹仓接线完成。

## 9. 普通装弹机的适配边界

本期只要求 `AmmoLoaderSubsystem` 实现 `isSupplyOperational`，保持容器、WIP 物品映射和现有殉爆流程。不要因为该类的注释也叫“装弹机”，就在同一提交里补齐物流系统。

普通装弹机正式模块化时应复用本计划的这些契约：

- `feed` 非关键、`magazine` 唯一关键；机构损坏保留物品容器。
- 实际取弹才扣物品；释放交付承诺不补物品。
- 殉爆读取实际物品堆栈，沿用当前 `CookoffComposition`，不拿容器格数当弹药发数。
- 容器物品与再生计数分别属于各自子系统，不增加同时保存两套库存的通用包装。
- 复用两种模块属性和接口，按同一套序列测试校验。

这些是后续接入约束，不应在完成第一期后把普通装弹机标记为已模块化。

## 11. 验收矩阵与验证命令

### 11.1 必须覆盖的业务契约

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| T01 | 省略两个模块字段 / 显式不同比重 / 非正或非有限权重 | 默认存在；最大耐久按比例分配；非法输入在属性边界拒绝 |
| T02 | 满仓，仅 `feed` 被打至 0 | 弹仓耐久、库存、弹链指针不变；无殉爆；无后续交付 |
| T03 | `reload_time=0`，直接重复请求与直接取弹 | 机构损坏时三入口均拒绝；库存不减 |
| T04 | 机构在输送中和已就绪待取两种时点损坏 | 所有承诺释放；不补弹；修复后重新计时 |
| T05 | 消费者已压入一发，再打坏机构 | 膛内那发可发射；下一发被阻断；无隐式退膛 |
| T06 | 机构先坏，下一 tick 再打坏有非零贡献库存的弹仓 | 仍能产生一次库存殉爆；库存归零；机构先坏没有占用判毁边沿 |
| T07 | 弹仓先坏，机构后坏；同批次两种命中顺序 | 每个弹仓生命周期至多提交一次；后续机构命中不更改弹仓起爆定位 |
| T08 | 空仓 / 全零贡献库存 / 混装且含零贡献弹种 | 前两者不生成爆炸；全零贡献计数保留但不可用；混装按现有合成处理并消耗整份库存 |
| T09 | 普通受击来源、直接 `routeDamage`、命中箱失效 | 正确弹仓命中箱定位，或明确宿主质心回退；豁免键与来源一致 |
| T10 | 客户端回调、宿主已摧毁/退场、正常脱离 | 不提交库存爆炸，不凭空扣库存 |
| T11 | 机构坏且弹仓健康，逐发/批量再生 | 产出继续到容量；计费次数正确；没有输送进度音效 |
| T12 | 弹仓在已预付能量的批量再生中损坏，再修复 | 中断批次清理；不退款、不免费完成；新批次重新支付能量 |
| T13 | 机构与弹仓分别从 0 修到 10% 再修到 30% | 修到 10% 时两者都仍处于摧毁：交付与再生被阻断、整机按关键模块判摧毁；越过 30% 才恢复；已消耗弹药不被结构修复补回 |
| T14 | 机构坏时退弹 / 弹仓坏时退弹 / 满仓退弹 | 分别按 §5.3 和既有容量、弹链规则处理 |
| T15 | 旧存档比例为 1、0.4、0；部分模块标签；非法比例 | 按 §7 唯一映射规则恢复；健康度不凭空变满；非法输入有诊断 |
| T16 | 弹仓 10% 且锁存中的新存档往返 | 模块 `destroyed` 保持锁存，整机随之仍为摧毁；修至 30% 才恢复 |
| T17 | 加载零耐久弹仓且库存非空 | 首个 tick 不重放殉爆；修复后再受损才有新事件 |
| T18 | 损坏模块加载后没有再变化，客户端首次收到全量快照 | 客户端正确拒绝交付；库存和模块一致；无强制全局标脏 |
| T19 | 两台供给者，一台机构损坏；以及全坏 | 健康供给者接管；全坏清除指认但保留膛内弹；库存选项不因故障消失 |
| T20 | 多消费者、释放一位消费者的交付、停用后再启用 | 无主承诺不占线；正常暂停与损坏清理互不混淆；不重复扣弹 |

| T22 | 第一方精确命中机构、弹仓；连锁爆炸 | 命中模块与模型对应；各库存独立处理；机构单独命中不触发其库存爆炸 |
| T23 | `pass_damage=false` 的模块化子系统被命中；同型写 `pass_damage=true` | 前者取消事件、模块耐久按 `module` 或比例下降，零件耐久与载具伤害不变；后者模块先扣，同一金额按既有规则传导给零件 |
