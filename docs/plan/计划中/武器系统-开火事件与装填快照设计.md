# 武器系统：开火事件与装填快照设计

**状态：计划中（设计稿，未实施）。** 代码核对日期：2026-11-17。适用仓库为 Machine-Max；路径均相对仓库根，Java 源码公共前缀为 `src/main/java/io/github/sweetzonzi/machine_max/`。

本文自包含：只读本文即可实施，不要求先读其它计划文档，也不要求读过本文的任何早期版本。落地后，《武器系统-双端装填预测与同步校正实施方案》与《武器系统-AmmoBelt 与发射器装填第一阶段重构计划》所述的双端预测模型整体退役，`common/mech/subsystem/AGENTS.md`、`network/AGENTS.md`、`common/mech/projectile/AGENTS.md` 中与之对应的条目按 §9 改写。

## 1. 目标与非目标

**目标**：把武器侧的"客户端也是一个模拟器"降为"客户端是一个回放器"。

- 服务端是唯一模拟者：受理装填、推进阶段、兑现交付、决定开火。
- 客户端只做两件事：按事件播表现，按快照画 HUD。它不判断"能不能开火"，不推算"还剩几发"，也不推导"装填进行到哪"。
- 快照一份形状三处用：进服补推、重连、读档存档。
- 装填进度随快照落盘，读档后未完成的装填继续。

**非目标**：

- 不改投射物物理、SoA 结构、命中与伤害归属（`common/mech/projectile/` 只增加一个随生成包发出的射击记录队列，见 §4.4）。
- 不改内容包格式与字段语义。
- 不做输入回显预测：按键仍经回声回到本端，本端不立即执行（见 §2 第 1 条）。
- 不改载具同步的总模型：`SubsystemSyncPayload` 仍是"一 tick 一批的值表"，事件另开一条通道，因为值表不是事件流。

**由此得到的三条事实**：

1. 射手自己的第一声枪响已经落后一个往返：按键上行、服务端处理、回声下行。旁观者同样落后一个往返。
2. 客户端当前跑的是"服务端那套状态机的第二份实例"，不是"提前量"。账本、预留与认领的双端同步存在的理由，是让这份第二实例的结论与服务端逐发一致。
3. 因此把表现改为事件驱动，时间基准从"回声抵达"挪到"事件抵达"，两者同属服务端时钟的回程，差最多一个业务 tick。

## 3. 设计总览

```
服务端（唯一模拟者）
  物理线程 fireSingle（读刚体位姿、建投射物、记后坐力）
      → 入队本 tick 的开火记录：每个发射器一条，其内按弹种分桶
  主线程 tickReload（受理/推进/交付/收尾）
      → 状态跃迁记账：reload-start / reload-stage / reload-end
  主线程 postTick
      → 投射物生成包（既有 ProjectilesSpawnPayload，主体改成开火记录列表，开火记录与条目同包；本 tick 结束连射的地址同批写在包尾）
      → 装填事件包（新 ReloadEventPayload，只在装填跃迁时发）
      → 值表同步（既有 SubsystemSyncPayload，携带当前作业快照与库存）

客户端（回放器）
  收生成包的组 → 反查 (子零件 ID, 声明序序号) → 交给该发射器播表现
  收生成包的 ends → 收循环、播尾音
  收生成包的条目 → 创建本地投射物，与组无配对关系
  收 ReloadEventPayload → 建、改、收显示条
  收子零件建好 → 现有 pushAllTo 全量补推即快照 → HUD 显示
  收事件与快照 → 不产生任何游戏状态，只产生显示状态

存档
  saveData：当前作业 + 当前弹药内容（既有的膛内与整份）+ 库存与再生状态
  loadData：结构建好后解析引用，重新取得承诺，失败即放弃作业
```

**不变式**：

1. 服务端之外没有第二份弹药账本：客户端不持有预留、不持有机械槽、不持有乘员认领。
2. 每一次装填跃迁都有一条事件；短作业（含 `reload_time: 0` 的瞬时作业）只靠事件可见，不靠采样撞上。
3. 事件按（发射器地址，轮次）幂等：同一轮次的重复结束事件不改变显示状态。
4. 快照描述"此刻是什么"，事件描述"发生过什么"。客户端只在前者上做插值，不在后者上做推断。
5. 表现的时间基准是包抵达时刻。客户端不按本端相位推算应当开几枪，也不按"多久没收到开火"推算连射何时结束——结束由服务端下发。
6. 存档里的引用按名字写；读档时先重建结构再解析，解析失败等于没有这条作业。
7. 读档重建的作业必须重新取得运输者执行资源与提供者预留；取不到就放弃，不留半份承诺。

## 4. 事件

### 4.1 两类事件与所属通道

| 事件 | 何时产生 | 走哪条通道 |
| --- | --- | --- |
| 开火（`FIRE`） | 服务端 `fireSingle` 决定开火并创建投射物 | 并入投射物生成包（`ProjectilesSpawnPayload` 的开火记录列表） |
| 连射结束（`FIRE_END`） | 服务端收尾，或相位在发射点饿停；每段连射一条 | 并入同一份投射物生成包（`ends` 列表） |
| `RELOAD_START` / `RELOAD_STAGE` / `RELOAD_END` | 受理、换段、收尾 | 独立的 `ReloadEventPayload` |

开火与投射物同源：一次开火的直接后果就是那几颗弹丸，两者同包、同刻抵达，客户端不需要把两份数据配起来。连射结束与开火同源但不同刻：收尾发生在最后一发之后的某一个 tick，那一刻可能一发都没打（打空），也可能只结束了循环而没有弹丸；它因此是包里的一串地址，不是某条开火记录的字段。装填跃迁与任何一帧的弹丸无关，频率是"每次跃迁一条"，独立成包不增加每 tick 的包数。

### 4.2 开火随投射物包

生成包的主体从"一串条目"改成"一串开火记录"，每个在本 tick 开过火的发射器一条，记录内部按弹种分桶：

```
Firing {                          // 每个开火的发射器一条
  origin:  (子零件 ID, 声明序序号)   // 非发射器创建的弹丸省略这一项
  buckets: [                      // 本 tick 打过的弹种，各带自己的条目
    { typeKey, entries: [ {objId, pos, vel} … ] }
  ]
}

ends: [ origin … ]                // 本 tick 结束连射的发射器，本 tick 没开火也照发
```

- **记录的语义是"本 tick 这个发射器打过哪些弹种"**，不携带发数：同一 tick 内的表现在同一帧里叠着发生，客户端每个桶播一次（首发播单发声并起循环、此后维持循环，一次火光、一次粒子、一次后坐动画、一声抛壳），多发与一发不可分辨。
- **同一发射器一 tick 内换型不另起记录**：混装弹序让连发在同一 tick 里换型时，第二个弹种是同一记录里的第二个桶，地址只出现一次。
- **桶之间不保序**：同一 tick 内的表现落在同一帧、叠在一起，顺序不可辨。
- **枪口坐标不单独传**：每个桶里第一条 entry 的位置就是该型的枪口，散布是厘米级、火光半径是米级。
- **条目数不等于发数**：一发可以产生多颗弹（`bullet_num`），那只是同一个桶里的多条条目。
- **客户端一次分发**：按 `origin` 找到发射器，逐桶播一次表现，并把各桶条目创建成本地投射物；没有 `origin` 的桶只创建弹丸，不播表现。

**`ends` 表达的是"连射结束"，不是"最后一发"**：实现里没有点射计数，`FirePhase` 只有"扳机按着就按射速打"一条规则，所以"最后一发"无从命名——能命名的是"本次连射结束"。它在服务端有两个产生点，与客户端现在收尾的两处一一对应：`ceaseBurst`（`LauncherSubsystem.java:1236`，覆盖松扳机、失活或摧毁、换装锁定）与 `advanceFirePhase` 的饿停分支（`LauncherSubsystem.java:1311-1316`）。两端各持一位：服务端记"本段连射已下发结束"，打出任何一发就清掉、收尾时置上；客户端记"这个发射器现在有没有在响"。没有服务端那一位，饿停之后继续按着扳机时相位每个 tick 仍然饿停，会每秒发出二十条结束。按了扳机却一发没打（膛与弹链全空）的连射同样会得到一条，客户端落在"没在响"的分支里，不产生声音。

- **这四类收尾里只有饿停推不出来**。松扳机、失活、换装都是客户端手里的本地事实；饿停要求"相位到了发射点且膛里没弹"，而回放模型的客户端既没有相位也没有弹药内容。只补饿停这一条会让客户端留着两条收尾路径，因此四类统一由服务端下发。
- **也不能用"多久没收到组"顶替**。首方 15 个发射器的 `fire_rate` 从 6 到 800 发/分（`spark_modules/*/subsystems/**/*launcher.json`），周期从 200 个业务 tick 到 1.5 个，相差 133 倍：单一门限在 550 发/分上余量充足，在 120 发/分（2A90，10 tick）上会把连射切碎，在 6 发/分（100mm，200 tick）上会把尾音压后十秒。
- **顺序：先组后 `ends`**。今天最快的 800 发/分对应 1.5 tick 的周期，相位循环"先发射再相减"，减完已不满足 `phaseU > intervalU`，因此饿停必然出现在本 tick 没有组的那一包上；射速一旦跨过 1200 发/分（一 tick 打两发）就能与最后一发同 tick，这条顺序让那种情形下客户端仍先播这一发、再收循环播尾音。
- **成本**：每条 `ends` 是一个地址（两个 varint，3 字节以内）加列表长度，出现频率是"每段连射一次"；打空后一直按住的那段也只发一条。

**为什么不做成逐颗投射物打"已发"标记**：标记表达不了"三颗弹属于同一枪"，要么把地址重复三份，要么再补一个射击序号；而客户端要做的是"每个弹种播一次"，那正好是每个（发射器，弹种）一个桶。

**带宽**（550 发/分、每发 1 颗弹、9.2 发/秒）：

| 方案 | 每发成本 | 每秒 |
| --- | --- | --- |
| 现状：每条目自带弹种 | 78 字节（objId 2 + 弹种 28 + 6×double 48） | 718 B/s |
| 逐发一条记录 | 78 + 44 | 1.1 KB/s |
| 按发射器记录、按弹种分桶 | 3 + 29 + 50 = 82 字节 | 754 B/s |

多弹丸射击是净省：每发 3 颗时现状 234 字节，分组后 182 字节。换型只多一个桶（29 字节），不会多出一条发射器记录。桶头里弹种 key 占 28 字节，若成为瓶颈可在包内做一次性的弹种表 + varint 下标，条目与桶都受益。

### 4.3 装填事件包

新增 `ReloadEventPayload`，注册在 `sync` 组（`playToClient`），头部是装配体 UUID，主体是一串有序事件。生成包的布局同时改变，协议版本 `sync:19.0.0 → 20.0.0`。

| 事件 | 字段 | 客户端动作 |
| --- | --- | --- |
| `RELOAD_START` | 地址、轮次、阶段、本阶段时长、已走 tick、冻结规格摘要、预留份额、运输者与提供者身份 | 建显示条：总长与起点由事件给出 |
| `RELOAD_STAGE` | 地址、轮次、阶段、本阶段时长、已走 tick | 重设显示条，不倒退 |
| `RELOAD_END` | 地址、轮次、是否已交付 | 收显示条；未交付按中止表现 |

- **必须是事件流而不是值表**：零时长作业在同一 tick 内受理并交付，两条样本写同一个字段，值表只会留下最后一条。
- 没有跃迁的 tick 完全不发；一次装填的生命周期只有两三条事件。
- 事件按（地址，轮次）幂等。

**循环音效与尾音由组与 `ends` 驱动**：客户端按"该发射器现在有没有在响"这份纯显示状态决定首发的单发声与随后的循环——第一次收到某发射器的组时播 `0.0` 键的单发声并启动循环，此后每组只维持循环（RPM 跨档位时交叉淡入）；收到该发射器的 `ends` 时收掉循环，并按 `cease` 音效表播一次尾音。尾音的弹种取该发射器上一个组的弹种（本端记一位）：回放模型的客户端没有弹药内容，而且松开扳机前切过弹种时，按真正打出去的那一型播尾音才对。没有在响的发射器收到 `ends` 不播任何声音——晚加入的客户端可能没听过整段连射。收尾路径只有这一条：与"按扳机推导停火"并列会让同一次连射收尾两次。

### 4.4 线程与排队

- 枪口位姿只有物理线程读得到（`fireSingle` 的 `computeMuzzleState`），而发包只能主线程。因此记录在 `fireSingle` 里**先于**创建弹丸入队 `ProjectileManager` 的 `pendingVolleys`，由既有的 `flushProjectileEntities` 一次取走，正常情形下记录与它的条目必在同一包里。同一 tick 内同一个发射器的多次 `fireSingle` 并入同一条记录，条目按弹种进各自的桶。
- `RELOAD_*` 在主线程 `tickReload` 内入队，由 `SubsystemController#flushSync` 同一次调用发出。
- `ends` 与组走同一个批次：`ceaseBurst` 只在主线程把地址记进本 tick 的待发列表，由 `flushProjectileEntities` 与组一起写出（组在前）。`ceaseBurst` 若晚于本 tick 的那次 flush，这条结束随下一 tick 的包走，顺序照样成立，只晚一个业务 tick。

## 5. 快照

### 5.1 三个消费者，一份形状

快照复用既有的同步值（`JOB_SPEC_ID`／`JOB_PROGRESS_ID`／`BELT_ID`／`CHAMBERED_ID`／`ROUTE_*`／库存与再生状态），不新增"快照载荷"：`SubsystemController#pushAllTo` 的全量补推本来就是快照通道。改动只在语义与落盘：

| 消费者 | 时机 | 走哪条路 |
| --- | --- | --- |
| 进服补推 | 载具在客户端建好，`ObjectManager#pushVehicleRuntimeState` | `pushAllTo`，既有 |
| 重连／分裂重建 | 载具在客户端重建完成 | 同一条 `pushAllTo` 全量补推 |
| 存档 | `saveData` | NBT，字段与值表同一份 DTO |

### 5.2 发射器快照的字段

| 字段 | 用途 | 端 |
| --- | --- | --- |
| 轮次 | 与事件配对、幂等 | 两端 |
| 阶段、本阶段时长、已走 tick | 显示条 | 两端 |
| 冻结规格（交付内容与长度） | HUD 显示"在装什么" | 两端 |
| 预留份额 | 显示与排查 | 两端 |
| 运输者与提供者身份 | 显示与排查 | 两端 |
| 膛内弹种、已装整份 | HUD 与开火表现 | 两端 |
| 当前路（`ROUTE_*`） | 显示 | 两端 |

客户端拿到快照后**不建作业对象**：显示侧只需要一个 `ReloadDisplay { round, stage, total, elapsedAtSample, sampledTick }`，每 tick 自增到 `total` 为止。HUD 改读新增的 `LauncherSubsystem#getReloadDisplay()`；`IAmmoConsumer#getReloadJob()` 的签名与语义保持给服务端内部用，不改成显示类型。

### 5.3 备弹的可分配口径

弹药池条目的"实时数量"在服务端是"库存 − 其他作业的预留和"。客户端不持有预留表，因此**同步值里必须直接带可分配量**（`RegenAmmoRackSubsystem` 的库存字段旁边新增一个"可分配"值，或在同一记录里同时给库存与预留和）。只给库存会让 HUD 显示的备弹多于实际能用的数量。

## 6. 存档

### 6.1 存什么

发射器的 `saveData` 增加一个 `reload_job` 复合标签：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `round` | int | 本管第几次受理 |
| `stage` | string | `human` / `machine` |
| `total` | int | 本阶段时长（tick，0 合法） |
| `elapsed` | int | 进度坐标 |
| `reserved` | int | 整次作业的预留份额 |
| `spec` | compound | 冻结的交付规格，沿用 `AmmoBelt#save()` 的布局 |
| `transporter_host` / `transporter_sub` | string | 机械运输者所在的子零件名 + 子系统名；人力运输者时两字段都写空 |
| `provider_host` / `provider_sub` | string | 提供者所在子零件名 + 子系统名 |
| `crew` | uuid, 可选 | 人工段必须落盘的乘员身份；缺失或该人不在线则读档放弃本作业 |

架的 `saveData` 不增加任何字段：预留与累计量继续不落盘（`RegenAmmoRackSubsystem.java:830` 的现有约定保留）。

### 6.2 引用按名字，不按 ID

`DestroyableObject` 的对象 ID 来自进程内计数器（`DestroyableObject.java:71`），跨存档不保证相同；`AmmoRef` 的第一段正是这个 ID，因此**不能直接写进 NBT**。存档里写 `(子零件名, 子系统名)`，两者本来就是存档键与日志身份；读档时在结构重建完成之后解析成 `AmmoRef`。

### 6.3 读档重建顺序

1. 载具结构、子系统与静态属性先恢复（既有路径）。
2. 发射器的 `loadData` 解析引用；任一解析失败 → 丢弃这条作业，记一条 `reload-restore-skip`，按"没有作业"继续。
3. 解析成功后**不直接建作业**，而是走与服务端受理同一条路的"恢复受理"：向提供者取整次预留（用存档的 `spec` 与 `reserved`，不做份额折算），向运输者取执行资源（机械槽或乘员认领；人工段用 `crew` 指定的那个人，认不到就放弃）。
4. 两笔承诺都取到，才按存档的轮次、阶段、时长与进度建作业，并把本管受理计数推到该轮次。
5. 任一步失败：撤销已取到的那一笔，丢弃作业，记日志。不缩份额、不换人、不降级成半份承诺。

### 6.4 与内容的关系

- 阶段时长以存档里的 `total` 为准，不重算：读档时乘员倍率与机构状态都可能与存档时不同，重算会得到另一条时间线。
- 人工段换人重定时仍按 `ReloadJob#retimeHuman` 换算比例，读档不触发换算。
- `reload_time: 0` 的机构不会存出"进行中"的作业：它在受理那一 tick 内走完并交付。

### 6.5 旧存档

缺 `reload_job` 标签即"没有作业"。这一类存档读出来与服务端刚受理之前的状态等价：本管下一 tick 按 `needsBelt` 重新受理。不需要版本号迁移。

## 8. 表现、手感与验收口径

### 8.1 时延

| 环节 | 现状 | 本设计 |
| --- | --- | --- |
| 按键 → 服务端处理 | 半个往返 | 不变 |
| 服务端开火 → 本端表现 | 回声，半个往返 | 与投射物同包，同刻抵达 |
| 投射物出现在画面 | 半个往返 | 不变 |
| 火光与投射物是否同刻 | 否：火光早、投射物晚 | 是：两者同 tick 发出 |
| 松扳机或打空 → 循环停、尾音起 | 本端相位自己收尾，落后一个往返 | 服务端在收尾那一 tick 记一条 `ends` 随生成包下行：松扳机仍是"一个往返 + 一个业务 tick"，打空不晚于现在（判据从本端投影的弹药内容挪到服务端那一次判定） |

### 8.2 显示的正确性

- 膛内、弹链、备弹、装填进度都按权威值显示，差异窗口是"一个单程 + tick 量化"。
- 短装填（`reload_time: 0.45` 秒、9 tick）由 `RELOAD_START` 与 `RELOAD_END` 两条事件保证可见；`reload_time: 0` 的作业在同一 tick 内开始与结束，客户端按"两条事件都到、显示条存在 0 tick"处理，不绘制。
- 客户端的表现只由事件产生，不存在"本端少一发/多一发"的形态。

### 8.3 验收

**GameTest（`runGameTestServer`，纯服务端契约）**：

1. `firingRecordCarriesLauncherAddressAndTypeBuckets`：一发产生多颗弹时只有一条记录、一个桶、多条条目；同一 tick 打两发同型弹时仍是一条记录一个桶。
2. `sameTickDifferentAmmoTypesMakeSeparateBuckets`：混装弹序在一 tick 内换型时，同一条记录里出现两个桶，各自的条目齐全，地址只出现一次。
3. `firingRecordAndItsEntriesTravelInTheSamePacket`：一次 `fireSingle` 产生的记录与它的条目出现在同一个生成包里。
4. `reloadStartPrecedesFireInTheSameTick`：零时长作业在同一 tick 内交付并开火，装填事件序列是 `RELOAD_START` → `RELOAD_END`，同一 tick 的生成包里带着开火的组。
5. `reloadEventsAreIdempotent`：重复的 `RELOAD_END` 不改变显示状态。
6. `reloadJobSurvivesSaveAndLoad`：存读档后剩余 tick、阶段、路由、规格与预留份额一致。
7. `reloadJobIsDroppedWhenReservationCannotBeRestored`：存档期间库存被改少到不足预留份额，读档后作业被丢弃并留下日志，不建半份作业。
8. `reloadJobIsDroppedWhenCrewIsGone`：人工段存档里的乘员不在线，读档后作业被丢弃。
9. `restoredJobKeepsItsFrozenDuration`：读档后阶段时长取存档值，不按当时的乘员倍率重算。
10. `burstEndIsEmittedOncePerBurst`：按住打到打空，饿停那一 tick 得到一条结束记录；继续按住若干 tick 与随后松开都不再产生（同一段连射）；补弹后再打一段，得到新的一条。

**单测（`src/test`，不依赖内容包数值）**：

1. `reloadDisplayAdvancesFromSnapshotOnly`：`ReloadDisplay` 只由快照与经过的 tick 决定，与任何作业对象无关。
2. `eventFieldSetIsCoveredBySnapshot`：事件里出现的每个字段都能在快照里读到，晚加入的客户端不依赖历史事件。

**双客户端手测**（`runClient` 两个实例，含 `--latency` 或外置延迟档）：

- 射手与旁观者同时看到火光、听到枪声、看到后坐动画。
- 550 发/分的机枪连射：循环音由组维持，松扳机后一个往返加一个业务 tick 内停并播尾音。
- 2A90（120 发/分，周期 10 tick）按住扳机连打：循环不被切碎，抛壳音连续，中间不出现尾音。
- 100mm（6 发/分，周期 200 tick）打一发即松手：尾音在松手后立刻响，不拖到下一个发射点。
- 按住扳机把弹链打空：循环收掉、尾音只响一次，此后不再有循环音；补上弹后再次连射是新的一个首发单发声加新循环。
- 2A90 的 0.45 秒装填进度条完整可见。
- 装填途中存档、退出、重进：进度条从剩余处继续，不从头开始。
- 装填途中摧毁弹药架：显示条按中止收掉，不留悬挂的进度。
