## 1. 结论摘要

- **症状**：已加入碰撞世界的刚体被切成运动学模式后，若它被约束（关节）连接，多线程构建下**一次步进即崩**，崩在物理线程，`hs_err` 指向 `bulletjme.dll` 的 `EXCEPTION_ACCESS_VIOLATION`。稳定复现，与关节数量、接触数、刚体总数无关。
- **根因**：岛屿划分阶段，`btGetConstraintIslandId1()` 返回 `-1`（两端刚体都没有有效 island tag），而 `btSimulationIslandManagerMt::addConstraintsToIslands()` 在 release 下没有下界检查，直接把 `-1` 用于索引 `m_lookupIslandFromId`（元素 8 字节 → 故障地址 `-8`）。
- **为什么运动学体会没有 island tag**：归岛用的并查集按定义跳过静态/运动学刚体，并把它们的 tag 写成 `-1`——源码级默认开启的优化，见 §2.2。
- **为什么只有多线程构建会崩**：崩点所在的那次"把约束散进各岛"只有多线程管理器在做——`addConstraintsToIslands()` 是 `btSimulationIslandManagerMt` 才有的成员，单线程的 `btSimulationIslandManager` 里没有对应函数。多线程管理器必须把约束与流形散进各岛才能分派给求解线程池，因此**只有"无岛可归"的约束在这里成了问题**；单线程路径把零散片段攒进队列一次解掉，从不需要回答"这条约束属于哪个岛"。详见 §2.3。
- **release 下无任何保护**：`getIsland()`、`btGetConstraintIslandId1()`、调用点三处的 `btAssert` 全部被编掉（`btSimulationIslandManagerMt.cpp:72 / 175 / 176 / 460`；`btAssert` 在未定义 `BT_DEBUG` 时展开为空，见 `btScalar.h:71-73 / 144-154`）。Debug 构建会先撞 `:72` 那条断言——**它就是被违反的不变量本身**。
- 查表缓冲区非空时，同一缺陷表现为读越界垃圾指针并继续解引用（可发展成越界写），比读到空指针更严重。
- 该函数在 bullet3 master 上仍未修。

## 2. Issue 草稿（可整节复制到上游）

### 标题

**已入世的运动学刚体被关节连接时，多线程构建步进即崩（物理线程越界访问）**

### 环境

- libbulletjme **23.1.0**，Windows x86_64
- 原生库：**DpMt**（双精度 + 多线程），2 个求解线程，`btDiscreteDynamicsWorldMt` + `btConstraintSolverPoolMt`，运行时 `threadSafe:true, doublePrecision:true`
- **Release 构建**（`btAssert` 已被编掉）
- 对照：同一份树内源码、只去掉 `BT_THREADSAFE` 的单线程构建**不崩**

### 背景

我们有以下几类需求，要求刚体**留在约束图里、但本步不被推进**：

- 动画 / 关键帧驱动的布娃娃：姿态来自动画与 IK，但刚体仍需参与关节约束；
- 暂时冻结的多体系统：系统暂停 / 编辑 / 摆放期间保持不动，之后从同一状态恢复；
- 服务器权威姿态：客户端接收服务器下发的位姿。

运动学模式是我们用来表达"在图中但不被推进"的手段，于是产生了"关节两端都是运动学刚体"的配置。

### 症状

多线程构建上，以下配置**稳定**复现崩溃，首次步进即崩：

1. 两个刚体都**已加入碰撞世界**；
2. 用一条约束（`btTypedConstraint`，例如 `New6Dof`）把两者连接，并把约束加入世界；
3. 把**两端都**设为运动学模式（`setKinematic(true)`）；
4. 执行一次 `stepSimulation`。

与关节数量、接触流形数量、刚体总数均无关。单线程构建则无此问题。

### 最小复现

```java
PhysicsSpace space = new PhysicsSpace();
space.createSpace(min, max, /*broadphase*/ 0, /*numSolvers*/ 2, configId); // btDiscreteDynamicsWorldMt + btConstraintSolverPoolMt(2)

PhysicsRigidBody bodyA = new PhysicsRigidBody(1f, boxShape);
PhysicsRigidBody bodyB = new PhysicsRigidBody(1f, boxShape);
PhysicsSpace.addRigidBody(spaceId, bodyA.nativeId(), 1, -1);
PhysicsSpace.addRigidBody(spaceId, bodyB.nativeId(), 1, -1);
PhysicsSpace.addConstraintC(spaceId, jointId, true);   // New6Dof，两端指向上面两个体
bodyA.setKinematic(true);
bodyB.setKinematic(true);
PhysicsSpace.stepSimulation(spaceId, 1f / 60f, 4, 1f / 60f, 0); // <-- 崩
```

### 崩溃点归属

```
# Problematic frame:
# C  [bulletjme.dll+0x366ab]

siginfo: EXCEPTION_ACCESS_VIOLATION (0xc0000005), reading address 0xfffffffffffffff8

RAX = 0x0000000000000000
R9  = 0xffffffffffffffff
```

崩溃线程是步进物理的那条线程，Java 栈顶为 `com.jme3.bullet.PhysicsSpace.stepSimulation`。读地址 `0xfffffffffffffff8` 即 `0 + (-1) * 8`——拿 `-1` 当索引去读一个空的指针查找表。

`0x366ab` 落在 PE 的 `.pdata` 叶子函数 `[0x3664b, 0x367ea)` 内。该函数与 `btSimulationIslandManagerMt::addConstraintsToIslands()`（`btSimulationIslandManagerMt.cpp:450-468`）逐步对应：

```asm
mov    r15, rdx                       ; r15 = &constraints
cmp    dword ptr [rdx + 4], ebp       ; constraints.m_size（btAlignedObjectArray：m_size 在 +4）
mov    rax, qword ptr [r15 + 0x10]    ; constraints.m_data（+0x10）
mov    r14, qword ptr [rax + rcx*8]   ; r14 = constraints[i]
cmp    byte ptr [r14 + 0x20], 0       ; constraint->m_isEnabled
mov    rax, qword ptr [r14 + 0x28]    ; m_rbA
movsxd rax, dword ptr [rax + 0x1a4]   ; m_rbA->m_islandTag1
sar    rax, 0x3f
and    eax, 8                         ; tagA >= 0 ? 取 m_rbA(+0x28) : 取 m_rbB(+0x30)
mov    rax, qword ptr [rax + r14 + 0x28]
movsxd r9, dword ptr [rax + 0x1a4]    ; islandId = 选中端的 m_islandTag1
mov    rax, qword ptr [r13 + 0xe0]    ; this->m_lookupIslandFromId.m_data（+0xe0）
mov    rbx, qword ptr [rax + r9*8]    ; <== fault：table[-1]，rax = 0，r9 = -1
```

其后还有 `cmp dword ptr [rdx + 0x60], r9d`（`m_activeIslands[i]->id == islandId`）、三处 `call`（内联的 `btAlignedObjectArray::resize()` 的 malloc / memcpy / free）、末尾的 `mov byte ptr [rbx + 0x58], r12b`（`m_ownsMemory`）与 `mov qword ptr [rax + rcx*8], r14`（`island->constraintArray.push_back(constraint)`），与 `:462-465` 的 `if (Island* island = getIsland(islandId)) island->constraintArray.push_back(constraint);` 完全吻合。

### 根因

`btSimulationIslandManagerMt::getIsland()`（`btSimulationIslandManagerMt.cpp:173-192`）：

```cpp
btSimulationIslandManagerMt::Island* btSimulationIslandManagerMt::getIsland(int id)
{
    // btSimulationIslandManagerMt.cpp:175-176
    btAssert(id >= 0);
    btAssert(id < m_lookupIslandFromId.size());
    Island* island = m_lookupIslandFromId[id];   // id == -1 -> 越界读
    ...
}
```

调用点 `:459-462` 与 `btGetConstraintIslandId1()`（`:68-75`）各有一条 `btAssert`，同样在 release 下被编掉：

```cpp
SIMD_FORCE_INLINE int btGetConstraintIslandId1(const btTypedConstraint* lhs)
{
    const btCollisionObject& rcolObj0 = lhs->getRigidBodyA();
    const btCollisionObject& rcolObj1 = lhs->getRigidBodyB();
    btAssert(rcolObj0.getIslandTag() >= 0 || rcolObj1.getIslandTag() >= 0); // stephengold added 2023-02-14
    int islandId = rcolObj0.getIslandTag() >= 0 ? rcolObj0.getIslandTag() : rcolObj1.getIslandTag();
    return islandId;
}
```

`m_lookupIslandFromId` 是 `btAlignedObjectArray<Island*>`：空表时 `m_data == NULL`，`table[-1]` 读到 `0 - 8`，即 `0xfffffffffffffff8`。若表缓冲区非空（同一 solve 内已分配过岛），同一次越界读会取到一块垃圾内存并当作 `Island*` 继续解引用，`+0x367be` 处的现场即为此形态，后果是越界读 + 越界写。

**为什么会存在"两端 tag 均为负"**：岛屿构建按定义跳过静态与运动学刚体。`btUnionFind.h:24` 有 `#define STATIC_SIMULATION_ISLAND_OPTIMIZATION 1`，该分支下：

```cpp
// btSimulationIslandManager.cpp:98-114（storeIslandActivationState）
if (!collisionObject->isStaticOrKinematicObject())
{
    collisionObject->setIslandTag(m_unionFind.find(index));
    collisionObject->setCompanionId(-1);
    index++;
}
else
{
    collisionObject->setIslandTag(-1);   // 静态 / 运动学体一律 tag = -1
    collisionObject->setCompanionId(-2);
}
```

也就是说：**运动学刚体即使已在碰撞世界中，其 island tag 也按设计为 `-1`**。于是"两端都是运动学"必然让 `btGetConstraintIslandId1()` 落到返回 `-1` 的那条路。

#### 为什么只有多线程构建会崩

同一个碰撞世界、同一份源码，去掉多线程后不崩。原因是**"把约束散进各岛"这一步只有多线程管理器在做**。

`addConstraintsToIslands()` 是 `btSimulationIslandManagerMt` 独有的成员（声明见 `btSimulationIslandManagerMt.h:79`）；单线程的 `btSimulationIslandManager` 里没有任何对应函数。单线程路径逐岛迭代，但**不在岛屿管理器里做任何散列**，只把约束按岛排序后整体交给回调：

```cpp
// btDiscreteDynamicsWorld.cpp:686-703（btDiscreteDynamicsWorld::solveConstraints，节选）
m_sortedConstraints.quickSort(btSortConstraintOnIslandPredicate());  // 只排序，不散进岛
m_solverIslandCallback->setup(&solverInfo, constraintsPtr, m_sortedConstraints.size(), getDebugDrawer());
m_islandManager->buildAndProcessIslands(dispatcher, getCollisionWorld(), m_solverIslandCallback);
```

求解在回调里发生，`islandId` 只是参数。回调对负 id 专门留了一条分支（`m_splitIslands` 为 `false` 时整世界就带着 `islandId = -1` 从这条分支进来）：

```cpp
// btDiscreteDynamicsWorld.cpp:123-176（InplaceSolverIslandCallback::processIsland，节选）
if (islandId < 0)
{
    ///we don't split islands, so all constraints/contact manifolds/bodies are passed into the solver regardless the island id
    m_solver->solveGroup(bodies, numBodies, manifolds, numManifolds, &m_sortedConstraints[0], m_numConstraints, *m_solverInfo, m_debugDrawer, m_dispatcher);
}
else
{
    //also add all non-contact constraints/joints for this island
    btTypedConstraint** startConstraint = 0;
    int numCurConstraints = 0;
    // 遍历所有约束，按 btGetConstraintIslandId(...) == islandId 挑出属本岛的起点与条数
    //（两段循环：先找第一条，再数条数，此处略）
    if (m_solverInfo->m_minimumSolverBatchSize <= 1)
    {
        m_solver->solveGroup(bodies, numBodies, manifolds, numManifolds, startConstraint, numCurConstraints, ...);
    }
    else
    {
        // 否则把这批刚体/流形/约束攒进 m_bodies / m_manifolds / m_constraints
        for (i = 0; i < numCurConstraints; i++) m_constraints.push_back(startConstraint[i]);
        if ((m_constraints.size() + m_manifolds.size()) > m_solverInfo->m_minimumSolverBatchSize)
        {
            processConstraints();   // 队列够大了，合并求解一次并清空
        }
    }
}
// btDiscreteDynamicsWorld.cpp:705：解算末尾再冲一次队列
// m_solverIslandCallback->processConstraints();
```

关键在于**这条路径允许"攒起来一起解"**：`processConstraints()`（`:178-187`）把 `m_bodies / m_manifolds / m_constraints` 三个队列一次性交给求解器并清空，而 `solveConstraints()` 在解算末尾还会无条件再冲一次队列（`:705`）。于是任何"零散、不成岛"的片段都会被这一趟兜住——这条路径不需要知道某条约束属于哪个岛。

这也说明：单线程路径对"无岛约束"并非无能为力，它只是**从未需要回答"这条约束属于哪个岛"这个问题**。

多线程构建走的则是完全不同的结构：每个岛要分派给线程池里的求解器，所以先建岛、再把流形与约束**散进对应的岛**，然后按岛并行求解：

```cpp
// btDiscreteDynamicsWorldMt.cpp:187
im->buildAndProcessIslands(dispatcher, getCollisionWorld(), m_constraints, solverParams);

// btSimulationIslandManagerMt.cpp:681-697（同函数内的散列与派发）
initIslandPools();
addBodiesToIslands(collisionWorld);
addManifoldsToIslands(dispatcher);
addConstraintsToIslands(constraints);   // <-- 崩点在这里
mergeIslands();
m_islandDispatch(&m_activeIslands, solverParams);
```

这一步没有"整世界兜底"可退：散不进任何岛的约束，线程池就没有它的批次可执行。

**缺陷因此可以一言概括**：`addConstraintsToIslands()` 的隐含前提是"每条启用中的约束都归属于某个岛"——对该函数所在的构建而言这不是可选项，而是它完成散列的必要条件。但岛由并查集定义，而并查集按设计跳过静态与运动学刚体；当一条约束的两端都被跳过时，它不属于任何岛，这个前提被违反——**没有岛的约束，没有可归的批次**。

### 其他可能触发路径

以下路径在我们的实测之外，机制上会走到同一个中间量，但**我们没有逐一验证，列出仅供排查参考**：

- **两端都是静态刚体**：`isStaticOrKinematicObject()` 对静态体同样为真，tag 同样为 `-1`。约束以静态体为端点不是常规用法，未实测。
- **刚体从未加入碰撞世界**：这类刚体不在 `m_collisionObjects` 里，`storeIslandActivationState()` 的 tag 赋值循环遍历不到它，其 tag 保持构造时的值。它们会把 `-1` 带进 `btGetConstraintIslandId1()`。
- **刚体加入后被移出**：`btCollisionWorld::removeCollisionObject()`（`btCollisionWorld.cpp:273`）只把 `m_worldArrayIndex` 打回 `-1`，**不改 `m_islandTag1`**。因此这条路径是否会命中，取决于该体此前是否已被岛屿构建赋过非负 tag——我们**没有闭合这条**，判别数据在此自相矛盾（见 §3.2 的 `removed` 行）。
- **其它非动态碰撞对象**（例如 multibody link 的碰撞体）：`btGetConstraintIslandId1()` 的 `else` 分支对非刚体同样可能返回负 tag，未实测。

### 建议

#### 1.在岛屿管理器里补齐 release 也生效的下界检查

`getIsland()` 入口对 `id < 0` 返回 `NULL`（语义就是"没有岛"），或让调用方在 `id < 0` 时跳过：

```cpp
btSimulationIslandManagerMt::Island* btSimulationIslandManagerMt::getIsland(int id)
{
    if (id < 0 || id >= m_lookupIslandFromId.size()) {
        return NULL;   // 无岛：调用方已用 `if (Island* island = ...)` 承接
    }
    ...
}
```

两个调用点本就用 `if (Island* island = getIsland(islandId))` 承接空返回（`:441`、`:462`），所以这个改法不改变正常路径行为。`addManifoldsToIslands()` 的 `getIslandId()`（`:60-66`，连 Debug 断言都没有）同理。

#### 2.显式文档化

若判定"约束两端都不参与动力学求解"不在支持范围，请在 `btTypedConstraint` / `New6Dof` 上明确写清：**当约束两端的 island tag 均为负（例如两端都是运动学或静态刚体）时，多线程构建会在岛屿划分阶段越界访问**；并给出规避手段（不要用运动学模式冻结参与关节的刚体，改用平动/转动系数归零；或在窗口期内 `removeConstraint`）。

| `noadd` | 两端均未加入世界、都切运动学 | **崩 @ `+0x366ab`**，`reading address 0xfffffffffffffff8` |
| `removed` | 两端入世界、都切运动学，步进前把 B 移出 | **崩 @ `+0x366ab`**，`reading address 0xfffffffffffffff8` |
| `normal_plus_dyn` | 同 `normal`，但世界内另有动力学体 | **崩 @ `+0x367be`**，`reading address 0xffffffffffffffff` |
| `noadd_plus_dyn` | 同 `noadd`，但世界内另有动力学体 | 存活 |

（现场文件：`.verify/repro_run/auth_*/hs_err_*.log` 与 `.verify/repro_run/hs_err_*.log`。）

这张表的读法与遗留矛盾：

- **`normal` 是本项目实际形态的等价复现**（两端都已入世、都切成运动学），对应 §1 的症状，与机制完全一致。
- **`onekine` 的作用**是说明"入世与否"不是判据：其 `bodyB` 是动态体但从未入世（`Repro.java:81` 只在 `normal`/`dyn`/`removed` 下加 B），两端同样都取不到 tag。
- **`removed` 与本中间量的解释不符，尚未闭合**：`btCollisionWorld::removeCollisionObject()` 只清 `m_worldArrayIndex`、不清 `m_islandTag1`，按机制推断 B 应保留入世时被写入的非负 tag，从而让 `btGetConstraintIslandId1()` 返回非负值、**不该崩**——但实测崩在同一地址。这条矛盾未解决，故本文不把它当作支持证据，只作为"还有其他路径"的一个待查项（§2.4）。
- **`noadd_plus_dyn` 存活 / `normal_plus_dyn` 崩在另一处且读地址不同**（`0xffffffffffffffff` 即 `-1`，而不是 `-8`）说明查表缓冲区的有无会改变故障形态：表为空时直接读到 `-8`；表非空时越界读出的是垃圾 `Island*`，程序以它为基址继续解引用，故障点因此前移到 `+0x367be`。**这一支后果更重（越界读 + 越界写）。**

### 3.3 未复核项（如实标注）

- **SpMt 一侧未复核**：工作区内既无 SpMt 库，也没有构建 SpMt 的脚本（只有 `scripts/build_dp_dll.bat`、`build_dpmt_dll.bat`、`build_dpmt_dll_debug.bat`），`scripts/objsp`、`scripts/obj2sp` 为空目录。因此"SpMt 崩于 `+0x35e68`"这一条**未经本轮核验**，引用时请注明。
- `scripts/repro/` 下的三个 `hs_err_pid*.log` 是**另一类崩溃**（`msvcp140.dll+0x13080`，发生在 `CollisionConfiguration.createNative` / `countThreads` 的搭台阶段），不能作为 3.2 表的证据。

### 3.4 历史记录

本崩溃在项目内**早已出现过并被记录过**，只是当时没有做过反汇编与判别实验：

- Spark-Core 早期在 Windows / Linux 上实际加载的是 **SpMt**（当时仓库里的 `natives/bullet/` 是**非** Mt 的 `SpRelease`，加载器先试主库即命中它，Mt 构件不在加载路径上）——细节见 Spark-Core 的 `docs/libbulletjme-double-precision-evaluation.md` §2.2。
- 项目 `AGENTS.md` 曾以"运动学刚体 + 关节约束"记录过这类物理线程崩溃，并由此产生了"顺序 `addToLevel`"这一历史临时对策。**那条记录的症状描述与本文一致，方向是对的**；后续之所以一度被写成别的机制（求解器对未来碰撞世界刚体查表），是因为只读了崩溃现场而没有做判别实验。
- **这次能把根因落到岛屿划分，靠的是判别实验**（3.2 表）：崩溃现场的机器码本身不足以区分"求解器查表"与"岛屿划分"，只有"哪些场景崩、哪些不崩"这组对照能把两者分开。
