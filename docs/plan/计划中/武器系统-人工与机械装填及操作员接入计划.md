## 2. 基准秒数与修正倍率

### 2.1 数据归属

| 位置 | 目标数据 | 含义 |
| --- | --- | --- |
| Launcher 型号定义 | 完整人力装填流程 | 标准人员通过纯人工路径完成一次装填的基准秒数及音效；没有该流程表示不支持此路径 |
| 装弹机型号定义 | 机构辅助装填流程 | 人工准备、机械运行各自的基准秒数及音效，都是该类型顶层字段；机械段 `M` 用顶层 `reload_time`，全自动流程没有人工段 |
| 容器型号定义 | `reload_time_penalty` | 容器附加秒数，默认 0；用于大弹匣、重弹箱等供弹具差异 |
| 装填需求方的安装实例 | 每个发现频道的岗位时间倍率 | 该位置的乘员为当前武器／机构操作时的便利程度；例如装填手 1.0、炮手 2.0。它只是 §4.3 预计完成时间里的一个因子，不单独决定选人 |
| 实际乘员 | 个人装填时间倍率 | 人员能力；1 为标准，小于 1 用时较短，大于 1 用时较长。它属于乘员自己的装填能力对象，不写进座位或武器 |

C1 的秒数与秒单位直接沿用，键随 `feed` 块解包落到机构型号顶层：迁移前 2S38 写 `feed.reload_time: 0.45`，迁移后是机构型号的 `reload_time: 0.45`。人工段是另外的可选顶层配置。现有内容等价迁移时默认无人工段（`H = 0`），不自动增加岗位／人员耗时或容器惩罚；旧总交付时间整体进入 `M`，不再叠加一次原交付计时，因此 2S38 的总装填时间保持 0.45 秒。需要人工段的型号由内容作者明确配置并单独标定；本轮不引入同义的 `machine_seconds` 字段。迁移逐项核对见 §7.1。

AmmoBelt 不保存容器装填时间惩罚；物品路线通过容器型号查询，再生交付路线不应用该惩罚。容器定义与实际物品读取依赖前置计划 §10 的 F5，本文不要求为计时单独制作物品系统。

同一门炮可以具有完整人力 8 秒、半自动准备 2 秒加机械 4 秒、全自动机械 6 秒的不同路径。三个示例是独立的标定值，不能从某个完整人力时间推导所有机构的准备时间。

### 2.2 计算规则

设 `H` 为当前流程人工段的基准秒数，`M` 为机械段基准秒数，`C` 为容器附加秒数，`P` 为选中发现关系的岗位倍率，`A` 为实际乘员的个人倍率：

```text
完整人力或半自动的人工段：T_human = (H + C) × P × A
半自动的机械段：          T_machine = M
全自动的机械段：          T_machine = M + C
顺序执行总时间：          T_total = T_human + T_machine
```

每次装填只应用一次容器惩罚：存在人工段时加在人工段，全自动流程加在机械段。再生路线中 `C = 0`。多个发现频道是候选关系，只有实际选中关系的倍率进入公式。

装弹机型号直接配置机械秒数，不配置与该秒数重复表达标称快慢的固定时间倍率。需要模拟选弹定位时，由机构根据状态提供额外机械秒数；没有储位／转盘状态的型号使用固定周期。再生库存没有物理弹位信息，不能据其计数或 AmmoBelt 配弹序列推导转盘距离。

弹匣容量与更换时间没有线性换算关系。向容器逐发补弹属于另一项操作，不属于本次换装时间公式。待发与后备位置的取用差异由各自配置的装填流程表达。

## 3. 共用流程与唯一执行状态

### 3.1 固定人工段与机械段

Launcher 的人力备份配置和装弹机配置使用同形的具体装填数据：可选人工段、可选机械段，每段包含基准秒数和进度音效。固定按“人工准备 → 机械运行”执行；纯人工仅有人工段，全自动仅有机械段。两段都为空的配置不能表达有效装填路径。

不建立任意阶段脚本、动作解释器、通用工作流接口或阶段提交框架。共用的是实际由 Launcher 消费的时间／音效数据及执行逻辑，具体 Java 类型名在编解码实施时确定。

| 路径示例 | 人工段 | 机械段 |
| --- | --- | --- |
| 人力备份 | 8 秒；开闩、装弹、手动关闩的进度音效 | 无 |
| 半自动机构 | 2 秒；取弹、放上托盘的进度音效 | 4 秒；推弹、自动关闩的进度音效 |
| 全自动机构 | 无 | 6 秒；定位、输弹、关闩的进度音效 |

### 3.2 执行与库存

装填状态按三个量分开归属，任何一方都不复制另一方的量：

| 量 | 归属 | 内容 |
| --- | --- | --- |
| 作业进度 | Launcher 的当前作业 | 选定流程来源、当前人工／机械段、段内进度、实际人工执行者；一台管只有一个作业，因此各是一个值。音效游标不属于这一行，见下方说明 |
| 产能与共享机械状态 | 装弹机构 | 流程定义（机械段 `M` 与可选人工段）、健康／供能条件、同时服务的槽、本 tick 可推进量、转盘／机械臂／待发托盘与供能锁定 |
| 占用 | 被占用的执行者 | 一个人工段占用一名乘员、一个机械段占用机构的一个槽；占用是认领，不是计时 |

Launcher 每 tick 向执行者索取放行条件与本 tick 可推进量，不自行判断机构能否工作；机构也不运行一份针对同次操作的阶段计时。这是本地运行状态的归属，不要求把累计进度或推进量逐 tick 下发：服务端决定分配与运行条件，两端各自推进所属 Launcher 的作业（§5）。保留 S12 的 `ReloadJob`；调整同步方式不以把计时搬回机构或人力附件为前提。

首轮产能采用布尔规则：`can_supply_multiple=false` 的机构一次只为一个作业分配槽位（独占且满速），`true` 的机构不限槽位、各作业分别满速。并发能力不增加库存：每个开始计时的作业都必须先取得自己的弹药预留（§3.4）。整数槽位与推进额度分摊不在本轮。

机构只维护一份实际占用记录：`Map<IAmmoConsumer, Integer>`，键是消费者引用，值是它占用本机的作业 `jobId`。独占机构最多一项，并发机构可有多项；网络下发的槽位拥有者是该记录的编码表示，不是另一份独立判定的运行状态。客户端据权威归属建立本地镜像，不同时维护一张可自行分配的认领表。记录只在受理点写入（`claimFor`），由消费者按编号释放（`releaseClaim`）。

`currentSupplier` 表达路由指认／亲和，未受理的指认不进入占用记录、不阻挡别的作业。路由候选过滤与执行者放行都查询同一份实际占用；控制器不能在“选中机构”时直接向记录加消费者，占用记录对普通读取方只读，受理与带 `jobId` 的释放由执行者处理。首阶段需同时取得本次作业的库存预留与首阶段执行者；机构占用记录只在进入机械段且取得槽位时登记，人工段只认领人员、保留整作业预留；受理失败撤销本次取得的资源，保留路由提示也不算占用。半自动流程尚在人工准备或等待机械槽时，不占机械槽。实际切换正在执行的路径须走作业终止／重建，不能只改路由引用后遗留旧占用。

服务端主线程读取占用或受理请求前，按同一份记录检查持有者：消费者或宿主已摧毁／失活、已移除或脱离合法拓扑、当前作业为空、`jobId` 不匹配、该阶段已不再占用本执行者的条目，按无占用处理并惰性清理。能定位作业时调用 §3.6 的按身份收尾，不能只删槽位而遗留库存预留；作业已不可定位时各资源所有者清理自己的无效条目，实际架也在可分配数量查询／预留前清理无效预留。仍合法且未超时的暂停作业保持已获占用，不能按“当前未推进”当作失效。清理只释放承诺、不增加实际库存，并更新相应镜像；其他线程只读发布状态，客户端缺少尚未创建的对象时等待指认就绪，不自行抢占。§3.6 六类入口负责及时收尾，惰性清理是遗漏后的兜底，不替代生命周期接线。

C2 的两个记录各有落点：`deliveryLoadedTicks` 对应 Launcher 当前作业的一份累计进度，机构只保留“槽位给了谁”；`lastPlayedProgressKeys` 对应各客户端的已播游标，它既不下行也不存档。客户端按权威分配和运行条件推进作业，tick 末应用新收到的分配变化与权威结果，平稳装填不依赖服务端逐 tick 提供进度（§3.3、§5.1）。机构提供音效配置与播放位置；S12 已实现的逐消费者音效游标记录见 §10.1。

“弹药架 → 人力准备 → 装弹机 → Launcher”属于同一次武器装填：人工与机械依次执行，人工段结束后释放人员占用。这里的机构入口只是作业交接位置，不形成第二份可查询库存，也不拆为一次弹药架补货作业。机构不缓存 AmmoBelt 实例：交付时把上游 `consumeReadyBelt` 返回的实例直接交给下游，扣减与写入在同一个主线程提交点完成；链上任一跳失败时不扣上游库存、不提交下游交付，按作业身份释放已取得的来源库存预留及人员／机构占用。完成时从选定来源向 Launcher 提交完整交付。

人工段仅在有可用执行者时推进，机械段按机构自身可工作条件与该作业的有效预留推进。某阶段的完成只表达计时过程，弹药库存按 §3.4 与前置计划 §5.1 的完整交接契约提交，不产生“已装弹头”“已放药包”等中间弹药库存。已有预留的作业不以公共可分配数量作为继续推进的条件。

人工段的推进量按标准人力秒累计（`Σ dt ÷ (P × A)`），该值单调不减，段完成条件是它达到 `H`；已完成比例由 `该值 ÷ H` 换算，不单独保存。人员或倍率变化只改变后续推进速度，因此不存在比例倒退需要特判。换人、失去全部乘员和路径切换的规则见 §9 第 3 条，不依 tick 顺序隐式决定。

整份换装、单发入膛和膛内弹保留按前置计划 §4 区分。完成装填前的射击门控、旧 Belt 保持与退回失败处理沿用该计划 §4.3、§5.1；不能因为本流程具有两个计时段而在人工段结束时提前提交一次库存交换。

有效新交付提交时，旧 Belt 可以交给当前合法且接受它的提供者；无人接收或拒收则丢弃，不要求原路退回，不为历史来源建立持久化关系。未完成装填首轮不存档，读档后由服务端重新选择来源与人员并发起装填；膛内弹、实际已装 Belt 和源库存按各自实际持有状态恢复。

### 3.3 进度音效

各路径独立提供音效配置。人力备份的关闩声、半自动托盘声与自动机构声允许不同；同一声音资源可以被多个配置引用。音效标记按所属人工／机械段的 0—1 进度触发，人员倍率只拉伸人工段的时间。

每次推进应处理跨过的全部标记，不能只播放最大阈值，避免一次推进越过多个标记时遗漏声音。阶段开始的 0、完成的 1 以及零秒阶段的标记处理见 §9 第 4 条。已完成阶段不因后续机械计时或人员变化重播。已播标记是客户端自己的量：每个客户端按本地模拟的进度推进游标，tick 末校准把进度往回拉时不倒退重播，往前跳时也不补播中间标记。默认人工音效定位在 Launcher，机械音效定位在实际装弹机。

客户端根据服务端分配的来源、流程、阶段实际时长与运行状态，自行推进装填、取弹、扣弹、音效与 HUD；同步回调缓存分配变化和权威结果，在主线程 postTick 应用。首次进入或重新建立模拟基线时可一次性提供阶段进度，正常装填期间不持续同步进度。服务端负责真实库存、选人、占用和完成判定，客户端不重做来源与人员竞争。不得使用客户端座位显示状态作为装填能力的权威输入。完整初值只建立模拟基线，校准不触发枪声或装填标记，不重播历史流程。详细边界见本文 §5.1—§5.3。

C3 的传统进度音效与 FMOD 路径都需要核对。本文不要求建立第二套与装填进度无关的定长音频计时器；两种音频后端的触发选择及停止／恢复接线见 §9 第 4 条。

### 3.4 开工预留、并发与交付

实际库存所有者维护预留。再生架记录实际库存 `N` 和各作业预留量 `q`，可分配库存为 `N - Σq`；任意时刻满足 `0 ≤ Σq ≤ N`。预留键使用 Launcher 的宿主 SubPart ID、子系统名和 `jobId`（§5.2），同一实际架即使经多台机构或多条线路被发现，也只有这一份库存与预留表。机构不缓存 AmmoBelt，也不另建一份库存承诺。

弹药预留按整次作业取得一次，必须早于首个有效阶段计时；不是每段重新预留，也不等到机械段才申请。服务端在同一个主线程受理点取得该份库存预留和首阶段执行者占用，任一项失败都释放本次取得的资源并等待，不推进、不播放开始音。执行者才按阶段切换：半自动人工段需人员与已预留弹药，不占机械槽；人工段结束释放人员，再等待／取得机械槽，期间原库存预留保持。纯人工同样在人工段前预留，全自动在机械段前预留。等待重试按 `(subPartId, subsystemName)` 稳定顺序处理，不建队列、不抢占已受理作业。

人工段包含取弹、放上托盘等处理实弹的动作，不能无弹空跑。若某半自动作业已受理并预留最后一发，另一全自动作业必须等弹，这属于既有承诺；不为让后来者更快完成而抢走它的预留。本轮不引入可在无弹时先做完的独立准备阶段。

不足一份仍可开工：数字库存的本次预留量固定为 `q = min(可分配库存, belt_definition.length)`，`q = 0` 时等待供弹，`q > 0` 才受理。选定交付规格与 `q` 一并进入作业；例如 30 发规格只有 5 发可分配时，预留 5 发并开始装填，交付仍保留 30 发规格、实际 `remaining = 5`。装填期间再生出的数量供后续作业申请，不自动加入已受理作业；物品路线未来预留具体物品／槽位，不拆开同一弹匣重复承诺，物品往返仍属 WIP。

| 时机 | 实际架与作业的行为 |
| --- | --- |
| 开工 | 实际库存 `N` 不减，可分配数量立即减少 `q`；作业绑定来源、规格和份额 |
| 推进／短暂暂停 | 检查本作业预留及来源是否仍有效；其他作业即使把可分配库存耗到 0，也不影响已取得预留的作业；暂停保留与超时释放沿用 §9 第 3 条 |
| 成功交付 | 校验作业身份、预留与兼容性，从实际库存精确扣除预留的 `q`，消费该预留并向 Launcher 写入独立 Belt；扣减与写入在同一主线程提交点完成。同一身份最多兑现一次，重复兑现不改库存；客户端同一 `jobId` 的交付也只模拟一次 |
| 取消／重建／换架 | 释放旧作业预留与占用，按新作业重新申请；没有交付就没有实际库存扣减。重复释放无效果，旧 `jobId` 的清理不能释放新作业的预留 |
| 来源摧毁／失效 | 作业不能继续凭无效预留交付，服务端释放或清理预留并按 §9 重建；仍在架内的弹药按实际库存参与该架的损伤／殉爆，只计一次 |

非交付原因减少实际库存时也须维护 `R ≤ N`。可拒绝的正常取物／移出只允许操作未预留部分；强制损失若能定位具体物品，先撤销绑定该物品的预留；不能定位到具体份额的数字减少，在同一主线程处理点将预留键 `(subPartId, launcherName, jobId)` 按元组字典序升序排列（宿主 ID 与作业 ID 按整数数值升序，名称按 `String.compareTo` 升序），再从末尾即键值最大者开始，按从大到小的方向整笔撤销，直到剩余预留总量不大于新的实际库存。撤销对象只由服务端选定，客户端跟随结束结果与预留新值，不另选撤销顺序。受影响作业以未交付结束，释放其他资源并下发校准；其后重新申请才可取得新份额。保留的预留 `q` 不变，不把旧作业静默缩成较小交付，不补发、不向实际库存加回缺口。物品／部分损失入口接入时落实该规则，物品往返仍为 WIP。

K17 四管共用 `can_supply_multiple=true` 的机构、可分配库存仅 1 且期间没有新增库存时，只允许一管取得 1 发预留并开始计时，另外三管等待供弹。取得预留与扣实际库存是两个时点；不能让四管同时计时，再在完成时争抢最后一发。多个机构共用一架时同样适用。

预留仍属于架内库存：计入容量与殉爆，既不提前腾出再生空间，也不触发交付后的 `regen_delay`。再生按包含预留的实际库存 `N` 计算，成功交付才按现有交付规则更新延迟。存档只保存实际库存和再生状态，预留、作业与占用不保存；加载后预留为空，未完成装填重新申请，不会因开工预扣而丢弹或补回两份。

预留总量记为 `R = Σq`，已经包含本作业份额。Launcher 的 `reservedCount` 是该作业交付的依据，不是可分配库存计算中的额外扣项；显示统一使用 `N - R`，不再减一次自己的 `q`。客户端本地交付只提交消费者一侧：把冻结规格与份额变成一份弹药内容并标记该作业已交付；`N` 与 `R` 跟随权威值——一次交付让两者同时减少 `q`，`N - R` 前后不变，因此本地不改这两个数也不会让可分配数量失真，而预改会留下隐患：服务端的 `N` 只在真实扣减时变化，`R` 却在撤销时也会变化，若本地预先也减了 `N`，一条被撤销的作业就会让本机的库存永久低于权威值（那个旧值不会再被推送一次）。新分配跟随服务端已授予的预留，不重新申请，也不把 `reservedCount` 再加进已同步的 `R`。权威值按 §5.1 在 postTick 覆盖，允许此前存在短暂预测差异。

**已落地的预留表（S19）**：`RegenAmmoRackSubsystem` 持有 `Map<ReloadJobKey, Integer>` 与同步值 `R`（`RESERVED_ID`），可分配库存是实际库存减 `R`；受理点 `AmmoLoaderSubsystem#claimFor` 在同一次调用里取得机构槽位与该架预留，`q = min(可分配库存, 交付规格长度)`，并把来源、规格与份额作为 `Grant(origin, spec, q)` 交给消费者写进作业；`consumeReadyBelt` 落到 `deliverReserved`（按身份扣实际库存、交出实例、一次兑现），释放、失效清理与强制损失都按身份调用 `releaseReservation`。`trimReservationsToStock` 按 `(subPartId, launcherName, jobId)` 元组升序排列预留键、从最大键起整笔撤销，维持 `R ≤ N`。路由、显示与 HUD 的"储备"读可分配数量。物品架（`AmmoRackSubsystem`）的预留随物品往返一起做，本轮不涉及。

### 3.5 机构条件与来源可用性

P4 明确拆开三个判断：机构自身可工作（启用、未摧毁及供能条件）、选定来源可工作且路径有效、该请求能取得库存或该作业已有有效预留。`AmmoLoaderSubsystem.isSupplyOperational()` 表达第一项；实际架沿用自己的 `isOperational()`，库存分配与继续推进按 §3.4 判定。纯人工路径没有机构项。

尚未受理的请求使用可分配数量，缺弹等待显示为等待供弹；已受理作业使用自己的预留，不能因为可分配数量为 0 就暂停。机构损坏／断能、来源失效、缺少未预留弹药和执行者忙碌分别提供状态原因，HUD 与 §4.3 的预计完成时间使用相应原因，不把缺弹显示成机械故障。S12 的 `isSupplyOperational()` 还要求 `upstream() != null`，且 `upstream()` 会回退到健康空架，因此现代码混入的是上游可工作性，并非直接要求上游有弹；P4 按本节拆分这些读取点。

### 3.6 ReloadJob 读口与资源释放

`IAmmoConsumer#getReloadJob()` 是这份作业的只读口：由 Launcher 返回当前作业，无作业时为 null。装弹机的 `consumeReadyBelt(consumer)`、执行者放行与 `CrewReloadAttachment` 都通过这一口读取同一份作业，不强转 Launcher，也不各自保存一份分配记录。

`ReloadJob` 是每台 Launcher 在本端持有的唯一运行期作业对象：身份与受理后固定的分配包含 `jobId`、交付目标、实际来源、冻结规格、份额和流程来源；当前阶段、段内累计量、实际时长、运行／暂停态属于该对象的执行状态。路径重建创建新作业；同路径换人及阶段推进更新同一作业。个人能力变化后的时长更新沿用 §5.1，保持已完成进度。读口是主线程内对当前对象的只读访问，不承诺不可变快照，不为每次查询复制对象或新造分配类型；推进、阶段切换与结束由 Launcher 控制，外部执行者不能修改作业字段。

`ReloadJob` 不直接充当网络／跨线程快照。下行仍是 §5.3 的字段值及待应用缓存，客户端在 postTick 将这些值应用于自己的作业；冻结规格／Belt 按已有可变副本规则处理，不能把一端的活作业对象当成另一端的状态。占用映射只记录消费者引用与 `jobId`，不复制完整作业；释放必须匹配该身份，旧作业的回调不能摘掉新作业。

资源结束使用统一收尾入口：先保留待结束作业的身份与来源，按身份释放人物占用、机构占用和实际架预留，再清空作业。成功交付先兑现预留并发布已交付结束；其他终止统一发布带原 `jobId` 的未交付结束，包括显式取消、200 tick 暂停超时、库存撤销和失效清理，不存在只释放资源而不通知客户端的超时特例。随后收尾剩余占用；重复收尾无效果，释放只减少预留量，不向实际库存加弹。六类入口与核对场景如下；这些是 P3b／P4 的行为核对要求，不增加 AmmoBelt 第一阶段的验收任务。

| 释放入口 | 必须处理的内容 | 对应核对场景 |
| --- | --- | --- |
| 成功交付 | 预留只兑现一次；释放人物／机构占用并结束作业 | 正常装填完成后，下一作业可取得槽位，库存只扣一次 |
| 显式取消、切弹／切源／路径重建、暂停超时 | 在清空／替换旧作业前释放旧身份资源；新作业独立申请 | 取消及 200 tick 超时后原份额立即可用；旧回调不释放新作业 |
| Launcher 或宿主 Part 摧毁、Launcher 停用 | `onDestroyed`／停用收尾不能只清进度；解除该消费者全部占用与预留 | 持有预留时摧毁或停用 Launcher，其余健康消费者能申请该份额，释放不凭空补弹 |
| 来源或机构失效 | 清理受影响作业及资源，按合法路径重建；来源殉爆按实际库存结算 | 机构摧毁只停工并释放承诺；来源摧毁不把预留再加回被销毁库存 |
| 子系统／Part 拆卸、拓扑变化或跨载具转移 | 清理阶段先解除旧路径再丢引用；即使转移分支跳过 `onDetach`，也须经结构清理释放 | 将仍持有预留的 Part 拆成另一装配体，两边没有旧认领或预留，重新握手后才能开工 |
| 载具销毁／注销／维度卸载及恢复边界 | 在对象注销前清理可达资源；加载只恢复实际库存，预留与占用为空 | 带未完成作业卸载、保存再载入，库存不增不减，其他对象不留下悬空占用 |

`LauncherSubsystem#onDestroyed` 走统一收尾（先按身份释放机构占用，再清作业）后结算已装库存殉爆；换指认、停用与结构变化后发现结果里已没有该供给者时同样经这一口收尾（`#isStillDiscovered` 判定路径是否还在本装配体内）。`SubsystemController#removeSubsystem` 的转移分支会跳过 `onDetach`，`#destroy` 会统一调用 `onDetach`，因此拓扑转移不能只依赖拆卸回调，实际入口是发现结果与失效占用清理。表中剩余的资源只有人物占用，它随 §9 第 2 条的乘员能力附件接入；统一收尾入口本身不为它另开分支（S18 已接入机构占用，S19 已接入实际架预留，S20 已接入带原 `jobId` 的结束结果）。

## 4. 操作员、岗位与发现

### 4.1 需求方发现座位

Launcher 为完整人力路径主动发现座位；装弹机为自身流程的人工段主动发现座位。座位声明可被发现的频道并提供当前乘员，个人能力从乘员取得。岗位倍率属于“装填需求方 → 座位”的发现关系，不是座位全局能力。

人力运输／装填能力属于实际人物，由绑定该人物的能力附件持有：与 `LivingEntityEyesightAttachment` 同形的带逻辑附件，持有人在里面认领作业、报出本次能推进多少，而不是只存一个数字。这个能力与装弹机构实现同一个执行者接口——放行条件、本 tick 可推进量、占用归属，Launcher 只按该接口询问，不区分对面是乘员还是机构（§3.2）。座位不实现该能力，也不是独立子系统。不同武器经座位取得同一个人的能力与占用状态，不能为每个发现者复制一份独立劳力。

同一个炮手座位服务主炮可以是 2.0 倍，服务旁边机枪可以是 1.0 倍；同一人换座后个人倍率保持由其自身能力决定。装填执行者不能直接复用 C6 的开火操作员，后者可能因松开扳机被清空。

座位安装实例新增 `reload_operator_discovery_inputs`，默认空列表；它与型号级 `interact_inputs`（C20 的 `SeatSubsystemStaticAttr#interactInputs`）在 C5 的 `SeatSubsystem#getAcceptedChannels` 中取并集。型号的交互输入从 `attr.staticAttribute` 读取，实例只提供装填发现频道，不假定存在实例级 `interact_inputs`。广播按合并结果筛选；发现操作只读，不向座位发送交互事件。

这些装填发现频道只用于发现握手，不承载装填指令或其他业务信号。并入接收声明后，真实广播也可能被信号总线写入座位输入槽；这不构成新的业务协议，实际装填调用握手取得的引用方法。

下列 JSON 固定需求方安装实例的发现字段及岗位倍率；发现使用 `*_discovery_targets`，不使用表达业务输出的 `*_outputs`：

```json
{
  "reload_operator_discovery_targets": {
    "crew.reload.loader": ["local"],
    "crew.reload.gunner": ["local"]
  },
  "reload_operator_time_multipliers": {
    "crew.reload.loader": 1.0,
    "crew.reload.gunner": 2.0
  }
}
```

装填手座位实例声明 `reload_operator_discovery_inputs: ["crew.reload.loader"]`；炮手座位实例声明 `reload_operator_discovery_inputs: ["crew.reload.gunner"]`。发现配置和座位频道属于安装实例，便于同型号安装在不同车辆或位置时设置岗位关系。岗位倍率继续使用 `reload_operator_time_multipliers`，其键与需求方发现频道对应。

倍率绑定发起查询的配置条目。连接器可以转译到达频道，但不会使倍率改为从另一个同名条目读取；每个条目的查询结果携带其关系代价供选人使用。

### 4.2 推荐范围：Part 内广播

推荐 `local` 作为常规发现范围，覆盖当前 Part 的全部 SubPart。两个独立炮塔 Part 可以复用相同频道而互相隔离。`global` 仅用于作者明确允许全装配体共享人员的情形；炮身和座位分属不同 Part 时通过连接器接线限定范围。

`local` 的边界是 Part，不是任意空间距离。两个炮塔被做在同一 Part 内时，需要频道或明确接线区分；座位和武器在不同 Part 内时，单独的 `local` 不会自动跨件发现。

C8 的 Part 总线是已实现的前置能力。具体契约及验证记录见 [Part 信号总线实施计划](../已实现/信号系统-Part信号总线实施计划.md) §3—§7：独立 local 订阅、Part 内广播与同范围只读发现，覆盖存储、端口接收和生命周期。装填代码复用该范围解析，不专门遍历全车座位。

### 4.3 选最快完成装填的实际执行者

候选是有效座位的存活乘员连同其可走的路径，必须满足当前流程可达关系，并且未参与另一项人工装填。选择用的唯一代价是**预计完成本次装填的时间**，不是岗位倍率本身，也不是频道顺序：

```text
预计完成时间 = 该候选执行下的剩余人工段 + 机械段等待与执行
剩余人工段 = (H + C) × P × A × 该阶段尚未完成的比例
机械段     = M（全自动另加 C）+ 机构当前无法开始工作的等待 + 缺弹等待
```

服务端对每个候选算出这个值，取最小者。机构不可工作或路径不可达的候选直接排除；弹药架为空但会自身再生的，把预计再生时间计入缺弹等待，不排除。候选是“执行者 × 其可走路径”的组合：同一路径下机械段是共同项，比较退化为剩余人工段；跨路径（纯人工、半自动、不同机构）比较时机械等待与缺弹等待才参与决定。`P × A` 只是估计里的因子，不单独决定选人。这里只做单武器内的局部比较，不引入全局最优调度或多人合作加速。

同一个人通过多条发现线路出现时，只采用其最有利的有效关系；这些关系的倍率不互相相乘。预计完成时间相同时保持当前执行者，其他平局以稳定身份顺序处理，不能依赖散列表顺序。换人是否划算同样用这个估计；换人保留已完成的进度，规则见 §9 第 3 条。

同一实际乘员一次只能推进一个人工装填段。多个武器同时需要人时的认领时机和稳定处理顺序见 §9 第 3 条；不引入全局最优调度或多人合作加速。全自动流程没有人工占用，半自动人工段结束后释放人员，机械部分继续受机构状态约束。

结构变化时按 C9 的两个相位重建候选座位引用。乘员上下座和个人能力变化在运行时检查，不以“发现到一个座位”替代“存在实际可用乘员”。已移除或已离开当前拓扑的对象不能保留为有效执行者。

### 4.4 供弹握手与装填请求

供弹发现由有输入需求的对象发起：Launcher 查询可用机构或直接弹药架，机构查询自己的上游来源。统一采用“需求方 `<域>_discovery_targets` → 提供方 `<域>_discovery_inputs`”命名，字段层级固定如下：

| 域 | 需求侧安装实例 | 提供侧安装实例 |
| --- | --- | --- |
| 供弹 | Launcher／机构的 `ammo_discovery_targets`：频道到目标列表 | 弹药架／机构的 `ammo_discovery_inputs`：接收频道列表 |
| 装填人员 | Launcher／机构的 `reload_operator_discovery_targets`：频道到目标列表 | 座位的 `reload_operator_discovery_inputs`：接收频道列表 |

例如 Launcher 写 `ammo_discovery_targets: {"ammo_120mm": ["local"]}`，可提供该服务的弹药架／机构声明 `ammo_discovery_inputs: ["ammo_120mm"]`。机构同时是下游的提供方和上游的需求方，可以具有这两个字段。发现目标并入 C7 的首跳解析表，提供方频道并入其 `getAcceptedChannels`；实际发现只调用 `resolveTargets`，不发送装填业务信号。不配置完整路径数组，不改动相机／瞄具现有的 `discovery_inputs` 或座位 `camera_discovery_targets`。

同一频道上的边由对象角色决定，不为上游另起一套频道名。机构在该频道上既声明输入端（找上游）又声明需求端（供下游管）；它的**上游查询只接受库存持有者**——库存归弹药架（§3.2），机构不持有，因此机构之间不互认上游，机械链不会成环。Launcher 在同一个频道上会同时发现机构与弹药架，其中“直接向弹药架取弹”属于人力直取路径，只有该型号定义了人工段（`H > 0`）时才作为候选进入 §4.3 的代价比较；没有人工段的管只经机构装填。

C19 的 `discovery_outputs` 是迁移前供给者主动发现 Launcher 的配置，`ammo_inputs` 是迁移前 Launcher 型号的发现输入；迁移目标明确反转这条边。须按旧实际可达关系生成“Launcher → 新机构 → 新弹药架”（或明确的人力直取路径）的配置，不能把旧目标表原样改名后挂到另一端。第一方 25 处里有 6 个实例的广播频道不在其管的 `ammo_inputs` 内（`LauncherSubsystem#addSupplier` 拒绝登记），这些边的供弹今天不成立，新配置按管声明的服务类别重写，旧频道名不进入任何新配置。已有信号端口的目标与频道转译也须核对反向可达性。第一方配置完成迁移后，供弹 Codec／schema 移除旧 `discovery_outputs` 与 Launcher 型号 `ammo_inputs`，不并行维护两种发现方向；Launcher 的接收与广播筛选按其实际控制输入等频道更新。清单与迁移验收见 §7.1、§8 与[拆分迁移清单](武器系统-装弹机与弹药架拆分迁移清单.md)。

移除 `ammo_inputs` 时，`LauncherSubsystem` 的代码落点必须一起处理：

| 当前入口 | 新架构的明确规则 |
| --- | --- |
| `getAcceptedChannels` | 退出 `ammo_inputs` 合并，接收声明由 `control_inputs` 等实际输入组成；供弹需求发现配置属于发送侧查询表 |
| `acceptAllRoutingInput`、`acceptAllBroadcastInput` | 控制频道的宽接收仅由 `control_inputs.isEmpty()` 决定，广播跟随同一规则；移除 `control_inputs.isEmpty()` 与 `ammo_inputs.isEmpty()` 相或的供弹分支，不能因已经退出的供弹字段为空而永久宽收 |
| 带频道的 `addSupplier` 及其调用方 | 退出供给者反向登记和基于 Launcher `ammo_inputs` 的校验；需求方按自己的查询结果建立合法上游引用，弹种／Belt 兼容性继续在实际交付入口校验 |

这包含一项明确的接收语义调整：控制列表非空、旧供弹列表为空时，控制频道将按所列频道筛选；空控制列表才表示接受任意路由／广播。当前 builtin `basic_launcher` 模板的控制列表为 `["weapon_control"]`、未声明 `ammo_inputs`，因此迁移后只声明该控制频道；若内容作者需要宽接收，显式填写 `control_inputs: []`。15 份 Launcher 定义中，14 份在用型号的 `control_inputs` 与 `ammo_inputs` 均非空，移除供弹字段不改变其宽接收判定；唯一翻转的是无实例的 builtin 模板。第一方在用型号与默认模板都按 §7.1 清单核对，不能把旧供弹空列表造成的控制宽接收当作新接口的隐式约定。

频道用于握手发现，`ammo_120mm` 仅表达服务类别。握手调用 C7 的只读终端查询，保存直接上游对象引用和对应线路信息；机构保留自己的上游关系，Launcher 不把全部最终弹药架展平为可任意选用的来源。发现结果按对象身份过滤查询者自身，机械链有环时该路径无效。

实际装填在服务端通过缓存引用调用对象方法，传递选中规格并完成查询、预留和交付，不向所有提供者广播实际取弹请求。弹药兼容性依据 Launcher 的弹种／供弹具规则，不能从发现频道名称推导。

武器控制器从受控 Launcher 的合法连接汇总弹药资源池，按实际库存所有者去重计数；机构提供的多条路径不产生多份库存。弹药架为空时，武器可以等待该架自身再生或选择另一条已配置来源路径。来源与机构的选择用与 §4.3 相同的代价：预计完成本次装填的时间（含机构何时能开始、路径是否可达），不按频道顺序、库存大小或型号排序。

## 5. 新架构的同步、持久化与退回契约

本节按拆分后的状态所有者组织实现：弹药架持有库存与再生，机构提供流程和可工作条件，Launcher 持有装填作业与已装弹药，火控持有选择和资源池。各对象的本地推进、权威校准和保存范围随职责拆分共同实现，不为迁移前的混合对象建立第二套长期运行状态。

### 5.1 客户端模拟与 postTick 校准

1. 服务端分配本次装填使用的机构／弹药架、流程与阶段，发布实际阶段时长、受理与运行状态。客户端跟随分配，不自行选择来源、争抢槽位或认领人员。分配的最小完备性见 §5.2、§5.3。
2. 同步回调只缓存本次收到的武器运行字段，不在模拟中途覆盖膛室、Belt 或作业。每个缓存项区分“未收到更新”和“收到空值”；同一字段多次到达时保留最新值，未到达字段不参与本次覆盖。相关作业字段在统一应用边界组成一致状态，不逐字段重建正在运行的作业。
3. 客户端业务 tick 沿指定路径正常推进装填、取弹、补膛、Belt 消费与回充，并从本地射击循环生成枪声、弹壳、尾焰、火光和动画。必须接通这些步骤当前的服务端专用分支，不能只停止发送 `JOB_ELAPSED_ID`。客户端修改自己的状态副本，不向服务端回写库存，不建立真实预留，不生成真实投射物，不执行真实能源扣费或世界伤害。
4. 本轮武器模拟结束后，在客户端主线程 `postTick` 一次应用待处理的分配变化与权威结果；这里不是物理线程的 `postPhysicsTick`。Launcher、弹药架及机构在同一校准边界应用新值，由主线程 tick 结束入口统一接线。机构按权威受理、占用与运行条件回答本地推进量，客户端不重新运行竞争分配；作业进度仍归 Launcher（§3.2）。
5. 校准只覆盖状态，不触发射击、装填标记或完成音效；库存覆盖本身不无条件重置射速累积、连射状态和声音实例。暂停、恢复、换人、换路径、作业完成或取消时更新相应状态，客户端按其语义处理声音实例与后续推进，不借校准补播跨过的音效。
6. 应用后清除本次待处理标记。没有新值时继续模拟，不把上一份缓存反复覆盖回去。Belt 的消费与回充使用独立可变实例，不能原地修改同步基线。

同步的常规内容是分配、条件变化与结果，稳定运行的阶段由两端自行累计进度。完整补推可携带当前阶段及进度以建立初值；暂停／恢复、换人或换路径等离散变化需要重建时，也可携带一次性进度基准。不得将该初值或基准每 tick 更新来替代本地推进。阶段实际时长由服务端解析；人员或倍率变化影响后续速度时，随该变化发布新的时长与必要基准，保持已完成进度。

两种到达顺序都按 `jobId` 处理：

| 到达顺序 | 客户端处理 |
| --- | --- |
| 本地先完成、权威结果后到 | 本地只交付一次；结果到达后覆盖弹药／库存／预留值，同一身份不再交付、不重播标记 |
| 权威已交付结束先到、本地尚未完成 | postTick 将该 `jobId` 标记为已由权威交付，停止并结束对应本地作业，应用结果值；后续 tick 不再为它执行 `N -= q`、`R -= q` 或再次写入 Belt |
| 权威未交付结束／取消先到 | 结束身份匹配的本地作业并应用校准，不从“作业已空”推断曾成功交付；更早预测出的错误弹药由权威结果覆盖 |
| 旧结束结果到达时，本地已有另一 `jobId` | 库存／预留字段仍按收到的最新绝对值校准，但不结束或替换当前新作业、不重置其阶段进度，也不释放新身份的占用与预留 |

交付结果须携带结束的 `jobId` 及已交付／未交付结论，并与本次相关的源 `N/R` 和 Launcher 弹药结果关联消费。作业终态的副作用必须校验完整身份 `(subPartId, launcherName, jobId)`：只有与当前本地作业相同才结束它或跳过其后交付；身份不匹配时只做所收库存／预留值的正常校准，不能用旧作业结束结果清掉新作业。客户端不能仅根据 `N/R` 变化猜哪个作业已完成，也不能先覆盖该次交付库存、仍让同一作业随后本地扣一次。底层即使分为多个子系统更新，P4 的结果缓存与应用也须维持这组关联，在同一 postTick 应用边界先处理权威终态、再覆盖相关结果。只保留当前／最近一次结束身份以识别重复，不建立逐发确认或作业历史日志；完整补推的终态只建基线，不补播历史表现。

本轮接受网络延迟内的短暂模拟差异，以实际到达的权威新值持续校准。不建立输入历史、状态回滚、预测重推、永久射击日志或逐发确认协议；不为一次射击的声音、粒子、火光分别发送表现包。`chamberedType` 可以正常同步，它不承担逐发事件编码，也不需要按“正在开火”暂停同步。

现有 `packDirty()` 选择发生变化的字段，每个 `DataValue` 携带该字段的最新绝对值，不是数值增减量。比如库存 10 变为 8，接收的是 8，postTick 使用覆盖而不是再执行减 2。客户端可以正常模拟库存扣减、交付和预留释放，收到新值后在统一边界覆盖自己的状态，不另建差量累加协议。

例如本地 `N=10`、`R=4`，其中本作业 `q=2`：交付后变为 `N=8`、`R=2`，可分配数量前后均为 6；随后收到权威 `N=8`、`R=2`，只覆盖，不重复扣减。`R` 和本作业的 `reservedCount` 是总量与份额两个视角，不能相加后再扣一次。

未变化字段不一定有新包；只应用本次收到的字段，不能假定下一 tick 有全量覆盖。完成、取消或重建的权威结果要确保本地已预测修改的相关库存／预留字段能够校准，即使服务端该值没有数值变化，也可能需要在相应结果中显式携带，复用现有状态载荷即可。校准遗漏不能靠反复应用旧缓存掩盖，不扩展为每 tick 全量同步、回滚或重推。

**已实现的边界（S20）**：六条全部落地。服务端发布分配与运行状态，客户端的同步回调只记"哪几项变了"（`LauncherSubsystem#onSyncedDataUpdated`），在 `AbstractSubsystem#onPostTick()`（`SubsystemController#postTick()` 在 `VehicleCore#preTick()` 末尾统一调用）里按"指认 → 作业 → 膛内弹／已装 Belt"的顺序落地；`JOB_ELAPSED_ID` 只在作业开始、离散重建与全量补推时写。第 3 条的完整业务链已经接通：客户端按执行者给的推进量走完作业后，用作业上冻结的规格与份额生成本地交付，交给首次装填或整份换装，并按同一份模式本地扣弹、补膛、跑射击循环（音效、枪口焰与动画）；它不建立真实预留、不扣实际库存、不生成投射物、不扣能源。回充不由客户端推进——余量与零碎进度都在已装同步值里，服务端补出一发的那一刻就推了新余量，本地再算一遍会与取电脱节。因此上表两种到达顺序都已可发生：本地先交付时只交一次，权威结果到达后按同一份内容收口；权威结果先到时结束身份匹配的本地作业并跳过其后本地交付，弹药内容以权威的 `BELT_ID`／`CHAMBERED_ID` 为准（它们与结果可能落在相邻的两个包里，收口按最新到达的值）。

### 5.2 服务端选择与运行期引用

装弹机、弹药架和当前作业的来源由服务端决定并下发。客户端可以模拟选定作业的计时与弹药消费，但不重新选择最快来源、抢占机构或认领人员。共用机构的请求是否已获受理也跟随服务端，不能仅靠两端自行遍历请求获得相同结果。

拆分库存与机构后，同步本次作业用到的引用即可，不下发完整发现图。两个引用是同一个 `SupplierRef` 类型担当的两个角色，不是两种地址：`deliveryTarget` 指本次把弹药交到手上的对象，机构路径下是机构，纯人工直取路径下是弹药架；`upstreamOrigin` 指机构为这次作业挑中的上游弹药架，只有机构路径非空。作业不保存第三个“来源”字段，也不把上游架塞进机构上的全局字段。

机构路径在申请库存时由服务端选架，取得 §3.4 的预留后把来源写入该作业的 `upstreamOrigin`。申请前或新作业可重新选架；已取得预留的作业完成交付时使用该份预留，换架须先释放旧预留并取得新预留，按 §9 的路径重建规则处理。`AmmoLoaderSubsystem#consumeReadyBelt(consumer)` 读取消费者当前作业，按身份在发现到的上游架里找到握着该预留的那台并从它兑现相同份额；纯人工路径从 `deliveryTarget` 所指架兑现。签名里不重复传入 origin，该方法也不允许临时另选第一个有货的架。逐作业绑定保存在 Launcher 的作业和实际架的预留表中，机构的候选上游列表只是发现缓存，不是某个作业的来源绑定。

Launcher 内用递增 `int jobId` 标识已公布的作业，0 只表示尚无已公布作业；新建／重建时分配新值，等待重试、暂停／恢复、同路径换人及正常阶段切换保持该值（等待重试不消耗编号：编号在受理成功后自增）。结束状态保留最近一次结束的 `jobId` 与结果（已交付／未交付）随结束结果一起接入，不能只清为 0 或空目标而丢失结果身份；没有活跃作业时 `getReloadJob()` 仍返回 null。新作业替代最近终态，不建立历史结果集合。身份使用 `(subPartId, launcherName, jobId)`，不引入全局作业注册表，也不持久化。分配字段同时包含冻结的紧凑交付规格与 `reservedCount`，客户端不能在完成时从变化后的供给预览重新推导本次弹药内容或份额。

仅独占机构同步一个槽位拥有者，形状为 `(int launcherSubPartId, String launcherName, int jobId)`，空拥有者对应无占用；地址沿用“宿主 ID ＋ 子系统名”编码，不用人物身份或历史 Part UUID。`can_supply_multiple=true` 没有独占槽位，不下发拥有者字段，各消费者跟随自己的作业受理状态。服务端只维护 §3.2 的一份实际占用映射，独占拥有者从其中编码；原始映射不整体下发。客户端收到拥有者值后更新本地占用镜像，不运行第二套抢占判定。该运行归属随变化发布，不持久化。

纯人工执行者的能力与占用属于人物附件，不塞进 `SupplierRef`；客户端按服务端发布的实际时长与运行状态推进人工段，不依赖自行读取个人倍率。

运行期子系统引用统一使用“宿主 SubPart ID ＋ 子系统名”，与 C14 的普通子系统更新寻址形状一致。供给指认无需 Part UUID 或 SubPart 名，不引入额外的子系统整数注册表。双方使用服务端创建数据中的宿主 ID；不能各自分配后假定一致。

`IAmmoSupplier.SupplierRef` 的形状是 `(int subPartId, String subsystemName)`，包括 `NONE`、`of`、比较规则、`STREAM_CODEC`、同步序列化器及解析调用方。来源关系不持久化，因此存档不保存这个短地址：Launcher 不保存已装内容的来源身份，换装时旧的一份交给当前合法且接受它的机器（无人接收则丢弃）。引用编码变化计入本轮世界同步协议组提升。

对象定位后检查它是否仍属于当前合法发现关系、是否已失效。指认目标尚未就绪时暂存等待，不自行改选，也不沿旧来源继续取弹；已在膛内或已装 Belt 中的弹药依其自身状态使用。运行期 ID 和对象引用都不进入子系统关系存档。

### 5.3 下行状态与带宽

| 所有者 | 下行数据 | 客户端用途 |
| --- | --- | --- |
| Launcher | 分配及变化：`jobId`、`deliveryTarget`、`upstreamOrigin`、冻结的交付规格与 `reservedCount`、流程、阶段实际时长、受理／运行／暂停状态、阶段切换与带 `jobId` 的结束结果（已交付／未交付，关联该次源库存／预留校准）；结果：膛内弹、已装 Belt 的内容与余量／回充状态。完整补推或离散重建时可附当前阶段进度基准 | 自行推进作业、本地供弹与射击，生成装填音效与 HUD；tick 末应用分配变化和权威结果 |
| 弹药架 | 实际数量 `N`、已预留总量 `R` 与可工作状态的最新值；再生配置及阶段变化，完整补推或重新建立基线所需的再生进度／剩余延迟。不下发完整预留表 | `R` 已含本作业份额，显示只算 `N-R`；本地交付同时减少 `N` 和 `R`，postTick 用收到的新值覆盖，不重复累加份额或扣减 |
| 装弹机构 | 自身可工作条件／故障原因；仅独占机构从唯一实际占用记录编码槽位拥有者 `(launcherSubPartId, launcherName, jobId)` 的最新值，并发机构没有该字段 | 跟随服务端受理和占用，按本作业有效预留计算本地放行与推进量；不逐 tick 同步推进量，不另持作业进度 |
| 武器控制器 | 选中的交付规格及既有开火控制状态 | 保持弹药选择一致；核对多管轮射和瞄准门控的双端差异 |

已实现的下行字段（S20）：Launcher 的 `JOB_ID`／`JOB_TARGET`／`JOB_ORIGIN`／`JOB_SPEC`／`JOB_RESERVED`／`JOB_TOTAL`／`JOB_ELAPSED`（基线），以及最近一次结束的作业编号 `JOB_RESULT` 与已交付结论 `JOB_RESULT_DELIVERED`；独占装弹机的 `SLOT_OWNER`（作业身份，并发机构不下发），再生架的 `AMMO_COUNT` 与 `RESERVED`。`JOB_SPEC` 复用可空 Belt 序列化器，`SLOT_OWNER` 复用作业身份序列化器，结束结果是同一编号空间里的一个 `int` 加一个布尔——编号在本管范围内唯一，因此不必把宿主 ID 与子系统名再编码一遍。结束结果只在收尾时写一次，新作业开始时不覆盖它，客户端据"编号是否与当前作业或刚才本地交付的那一条相同"决定是否结束本地作业。

固定的 label、pattern、length、容器 ID 与回充配置在安装、更换和完整补推时发送，不把 3000 发弹链展开。稳定装填不持续下发阶段进度或本 tick 推进量；库存／已装弹药仍按真实变化校准，不能把减少装填计时同步理解为停止同步权威弹药结果。再生与回充的进度、延迟同样由本地推进，完整初值与阶段／条件变化按需提供基准。推进装填所需的实际时长由服务端发布，不为显示重新计算人物能力。“每 tick 检查脏字段”不等于“每 tick 写入进度字段”，也不扩展为全量广播。

首次进入和对象恢复时，保持“创建对象 → 全量补推”的顺序。完整初值建立本地模拟基线，不播放历史枪声或历史装填标记。多人旁观同样跟随权威来源，不依赖自己是否持有该武器的输入。

同步字段或引用编码改变时，读取 `network/MMPayloadRegistry.java#register` 的实际版本后递增相关协议组，不预写固定的新版本号。

### 5.4 子系统持久化与恢复

本表列本次弹药业务状态；耐久与损伤状态的拆分迁移另见 §5.6。

| 子系统 | 保存自身数据 | 不保存的运行关系 |
| --- | --- | --- |
| Launcher | 独立膛内弹、完整紧凑 Belt（含 label、实际弹序、余量与回充运行态）、需要延续的剩余射击冷却 | 当前供给者、装弹机／弹药架路径、历史退回来源、发现表和网络引用 |
| 弹药架／再生来源 | 实际物品或数字库存、自身逐发或批量再生进度与剩余延迟 | 消费者认领、交付预留、机构关系和客户端显示缓存 |
| 武器控制器 | 玩家选中的弹药规格；恢复后对合法来源重新匹配 | 聚合资源池、已选来源引用及派生路由 |
| 装弹机构／当前装填 | 首轮不保存未完成装填作业，读档后重新发起 | 人员认领、机构占用、作业路径、阶段进度与音效播放记录 |

预留不从保存的实际库存中预扣，已预留数量仍包含在实际库存里；恢复时预留表与已预留总量清零，由新作业重新申请。`jobId` 与独占槽位拥有者也不保存。

结构、接线配置和连接拓扑由现有载具／部件层恢复，不在上述子系统存档里重复保存。服务端恢复实际库存与玩家选择后，握手发现、选择来源、建立运行关系，再向客户端同步。没有关系存档时也不能为 Launcher 播种满额 Belt。

剩余冷却、延迟和再生进度表达游戏内尚未完成的量，不绑定客户端出生后的 tick。卸下或未加载的 Belt 暂停回充，不计算现实时间恢复。客户端预测状态、待应用缓存、声音实例和已播标记不存档；服务端使用自己的实际状态保存。

首轮恢复不承诺从人工／机械段中途续装。未来确实需要跨存档续装或分装弹检查点时，再明确所需作业信息和恢复政策，不为当前范围保存历史路径。

### 5.5 退回与丢弃

已装 Belt 不要求退回原提供者。退回时可尝试当前合法且接受该份内容的提供者；本轮不实现跨多个接收方拆分回收。无人接收或整份拒收时允许直接丢弃，正常卸弹／换装不因此受阻，也不要求生成掉落物。

接收方接口保持全收／全拒：成功时按类型回收完整实例或增加数字数量；拒收时不改库存、不修改传入 Belt。调用方在拒收后执行丢弃并清理自身对应内容，不能把丢弃报告为提供者成功接收。数量核对将这笔计为明确的丢弃损耗。

新交付不合法或交付失败时，不应提交新装填；这与“有效新交付已取得、旧 Belt 回收失败后丢弃”分别处理。战术换弹保留膛内弹，换掉的是已装 Belt。子系统无需 `loadedBeltSource` 这类历史来源追踪，也无需为重启后原路退回持久化引用。

### 5.6 耐久、存档与命中箱交接

[装弹机模块化损伤实施计划](../进行中/武器系统-装弹机模块化损伤实施计划.md) §3.1、§7、§8.2 是合一 `RegenLoaderSubsystem` 作为模块化子系统的模块、存档及命中箱基线。拆分后弹药架与机构都是普通子系统，不再有模型内模块：型号里没有 `feed`／`magazine` 块，没有 `durability_weight`，存档里没有 `modules.*` 键，命中箱不写 `module`。迁移只搬数值与职责，不搬模块结构。

| 合一实现中的内容 | 拆分后的所有者与目标形状 |
| --- | --- |
| 型号 `magazine` 块及其字段（`capacity`、`regen_per_minute`、`regen_round_by_round`、`energy_cost_per_round`、`regen_delay`、`durability_weight`） | 解包为弹药架型号的顶层字段，`durability_weight` 删除；再生架 `regen_ammo_rack` 保留 `regen_*`，物品架 `ammo_rack` 保留物品容器与容量 |
| 型号 `feed` 块及其字段（`reload_time`、`can_supply_multiple`、`durability_weight`） | 搬进机构型号已经平坦的顶层字段：`reload_time` 即 §2.1 的机械段 `M`，`can_supply_multiple` 即 §3.2 的布尔产能，`durability_weight` 不搬 |
| 型号 `basic_durability`、`pass_damage`、`sounds`（进度音效与 FMOD） | 耐久按下方公式折算；`pass_damage` 保持 `false`（取消事件、伤害落自己）；`sounds` 跟着机械段搬到机构，人工段的音效配置在 Launcher 的流程定义里 |
| 实例 `belt_definition`、实际库存与自身再生字段 | 弹药架持有：物品架保存实际物品，再生架保存实际数字与生产进度 |
| 并发服务限制、共享机械状态（转盘／托盘／供能锁定） | 机构持有；并发服务沿用 §3.2 的布尔语义 |
| 旧合一子系统实例名与类型 id | 同 SubPart 的新弹药架沿用旧实例名，存档按实例名投递，因此类型 id 从 `regen_loader` 改成 `regen_ammo_rack` 不影响读档；新机构用 P0 迁移表固定的无冲突实例名，类型 id 用 `ammo_loader` |
| 存档 `modules.magazine.{durability,destroyed}` | 只进入弹药架：绝对耐久按下方公式折算，`destroyed` 成为该架自己的摧毁状态 |
| 存档 `modules.feed.{durability,destroyed}` | 只进入机构：折算方式相同；机构判毁只停工，不动弹药架库存、不触发库存殉爆 |

拆出来的两个宿主（再生架与机构）的 `basic_durability` 分别等于旧模块已分配的最大耐久：设旧整机上限为 `B`、旧权重为 `w_feed` 与 `w_magazine`，则机构为 `B × w_feed ÷ (w_feed + w_magazine)`，弹药架为 `B × w_magazine ÷ (w_feed + w_magazine)`。这两个值只在迁移时算一次，之后就是两个新类型的普通 `basic_durability`；权重字段与模块定义从 schema 和型号定义里删除，不能把 `B` 同时赋给两个宿主。

判毁与恢复沿用 `AbstractSubsystem` 的同一门槛：`shouldDestroy` 是耐久 ≤ 0，`shouldRecover` 是耐久 ≥ `RECOVERY_RATIO`（0.3）倍上限，两个新类型各用一份，与今天不分模块时的语义相同。`critical` 随模块一起消失——普通子系统的判毁只看自己那份耐久。殉爆归属随 `magazine` 落到弹药架：弹药架耐久归零的摧毁边沿触发自身库存殉爆，机构耐久归零只停工。旧实现里“`feed` 非关键所以机构损坏不使弹仓失效”的效果，由两个宿主天然分开来保证，不再需要关键模块布尔。

存档一拆二的入口位于 C22 的部件恢复边界，在向新子系统调用 `loadData` 前处理 `SubPartData.subsystemData`。迁移表以 Part 型号、SubPart 名、旧子系统名定位新弹药架与机构；该表属于本次内容迁移，不是需要另行保存的运行关系。旧记录的库存／再生写进沿用旧名的弹药架，`modules.feed` 的耐久折算后写进机构；更早的单一 `durability_ratio` 格式按关联损伤计划 §7.2 先归一为旧模块状态再折算。新记录没有 `modules` 键，识别为新格式的记录不重复折算；已经存在的新记录不得被历史记录覆盖。加载不重放殉爆，不重复扣库存或重新生成满架弹药。

第一方机构保持与原合一子系统相同的 SubPart。命中箱的 `subsystem` 逐项指向弹药架或机构，`module` 字段从这些箱体上删除：拆开后同一个子系统里没有第二个模块可以按耐久比例分摊，漏标 `module` 不再有兜底路径。现有 4 个带 `module` 的箱体都在 2S38 炮塔，标 `magazine` 的指向沿用旧名的弹药架，标 `feed` 的指向新机构；其余指向旧供给实例的箱体按物理含义逐个确定宿主，不能静默全部归到弹药架，也不能把 `subsystem` 指向另一 SubPart。命中箱 `id`、骨骼、几何、材质和厚度随清单核对，不复制箱体制造两次伤害。模型缺少机构几何时记录缺口，不把存档迁移完成当作精确分离命中已实现。

上述配置、存档键、命中箱、耐久折算与载入初值随 P2／P4 同批交付；关联损伤计划描述合一实现的边界，本文定义拆分目标。物品弹药架 `ammo_rack` 的物品往返尚无真实实现，那部分维持明确 WIP（§9 第 1 条），不据其接口可编译声称完成物品迁移。

## 6. 分装弹与检查点的范围

分装弹相关表达限于人工／机械计时和进度音效，不实现物理分装弹、可选药包量、部分入膛库存、独立弹头／发射药物品或任意阶段检查点。

未来确有分装弹需求时，允许在弹药定义增加一个分装装填布尔，采用简化进度保留：人工段不足 50% 时从 0 恢复，达到 50% 后从 50% 恢复。该规则只作用于单发装填的人工段，不作用于弹匣／弹链更换，也不改变弹道或装药量。检查点属于本次具体装填，换弹种或终止本次装填时清除。

这个布尔和半程恢复不属于本计划的首轮交付；没有消费方时不预建字段。首轮未完成作业读档后重新发起，不保存检查点。未来需要跨存档保留检查点时，所存进度必须与本次弹药和流程身份绑定，不能仅保存一个可套用到另一发弹药的百分比。

## 8. 验收与本次文档交付

首轮构建验收从 Machine-Max 仓库根执行 `.\gradlew --offline classes`。物品往返、实际音频、乘员接替和多人同步的玩法验证不能由编译成功推断，验证结果需按实施范围另记。本计划不把新的 JUnit／GameTest 或客户端启动纳入 AmmoBelt 第一阶段验收。

新架构运行核对至少覆盖：2S38 按住多发和点射；导弹单管、齐射和轮射；其他乘员／旁观者；射击中加入；缺弹后再生；充能 Belt；混装弹序和战术换弹；同 tick 多次同步、空值更新、无更新时继续模拟；来源变更／失效；退回拒收丢弃；读档后的实际库存、冷却与重新装填。校准不能重播音效，丢弃不能制造回收库存。

外审边界核对包括：两种交付到达顺序下同一 `jobId` 都只消费一次；旧 `jobId` 结果到达时新作业继续推进且不释放新预留；多个预留键按明确升序排列后从大到小撤销；200 tick 超时与库存撤销都下发相同种类的未交付结束结果；半自动人工段开始前已预留、人工到机械切换不重复预留；强制库存损失撤销整笔受影响预留、保留份额不缩小、不补弹；有意漏掉一次正常释放后，下一次读取／受理能剔除失效占用及预留，而合法暂停作业不被误清。

并发库存核对至少包括：K17 四管、单发交付、库存仅 1 且暂停再生时，只有一管开始装填；其余管在取得各自新预留后才从阶段起点推进。还包括多个机构共享同一架、重复请求不重复预留、已预留作业在可分配数量为 0 时继续、取消／超时／来源失效后释放、旧 `jobId` 清理不释放新预留、装填中再生不扩大既定份额、30 发规格只预留 5 发时最终准确交付 5 发，以及读档重启无弹药增减。

§3.6 的六类释放入口逐行核对，覆盖 Launcher／宿主摧毁与停用、Part 拆卸、跨载具转移及整车卸载；不能只测换弹成功。另核对路由指向但未受理的管不占槽、受理失败后其他管能取得机构、拥有者镜像与实际占用一致，以及 `N=10/R=4/q=2` 的本地交付和权威覆盖均保持可分配量为 6。其中受理、占用归属、开工预留与结束结果已由 `common/gametest/AmmoJobClaimGameTest`（批次 `mmAmmoJobClaim`）固定：受理后作业带编号、来源与份额，预留只减少可分配库存而不动实际库存，独占机构对别的管表现为已占用而对自己不算，身份不匹配的释放不摘占用，预留被撤销时作业按失效收尾且不留承诺并下发带原编号的未交付结论，没有可分配库存时不建作业也不占槽；成功交付那条用例覆盖"按份额扣一次实际库存、膛内得到那一发、机器重新可用、结束结果带原编号与已交付结论"。本地交付与权威覆盖的另一半（客户端那一侧的状态机）没有自动化形式：它要求客户端 `Level`，现有 GameTest 只在服务端跑，验收走 `runClient` 的画面与音效核对。

P4 还须核对同步契约本身：稳定装填期间客户端在没有阶段进度更新时持续推进 HUD 和音效，服务端不因计时经过而逐 tick 标脏进度或推进量；暂停／恢复、换人、换路径与完成／取消能及时改变本地作业；同一机构连接多个架时，两端只从权威作业绑定的架取弹。完整补推能从当前阶段建立基线且不补播历史标记。S20 已把这条链路做成当前实现：分配与来源一次性下发、进度只作基线、客户端按执行者给的推进量自行累计并在走完时本地交付与扣弹、结束结果按编号结束匹配的本地作业。其中"服务端不逐 tick 标脏进度"与"暂停／恢复、换人、完成／取消改变本地作业"两条有自动化形式（后者见 `mmAmmoJobClaim` 的结束结果断言）；本地交付的两种到达顺序、校准不重播标记与投影表现仍只由 `runClient` 的画面与音效核对，不宣称已验。

1. 类型与定义形状，以及代价各项的取值口径。
   已定：三种类型各司其职。`ammo_loader` 是自动装弹机，沿用现有 id：迁移前的该类型已是平坦的普通子系统，`reload_time`、`can_supply_multiple`、`sounds` 就在顶层，迁移删掉 `magazine_capacity`（库存归架）、`round_by_round` 与 `auto_request_upstream`（输弹粒度归 Launcher 的 `single_round_loading`，上游来源改由需求方发现），补上 §3.2 的槽位与共享机械状态以及可选人工段。`regen_ammo_rack` 是再生弹药架，现 `regen_loader` 改名：删掉 `feed` 块，把 `magazine` 块解包成顶层 `capacity`、`regen_per_minute`、`regen_round_by_round`、`energy_cost_per_round`、`regen_delay`，并从模块化子系统改为普通子系统。`ammo_rack` 是物品弹药架：承载迁移前 `AmmoLoaderSubsystem` 里的物品容器，定义从它已经平坦的 `magazine_capacity` 起步，物品往返仍 WIP，本轮只保证类型、容量与拒收语义成立。三种类型因此都没有 `feed`／`magazine` 块、没有权重、存档没有 `modules.*`，`FeedModuleAttr` 与 `MagazineModuleAttr` 随之下线（§5.6）。内容侧：25 个实例的 `type` 改成 `machine_max:regen_ammo_rack`，14 份型号定义文件跟着改名，另需为每个供给实例补一个机构实例、并把三套 schema 的文件名与内容一起改。
   代价口径（整数 tick 比较）：机构等待在机构可工作且没有别的作业占着槽位时为 0；`can_supply_multiple=false` 且槽位被占时等于该作业机械段的剩余 tick（读服务端当前作业的本阶段实际时长与进度，不重算基准）加 1 tick 交接；机构摧毁或供能不满足是排除候选，不折算成等待。缺弹等待按未受理请求的可分配库存计算，已有有效预留的作业没有这项等待；前者读来源自报的「交出第一个可分配单元还需多久」（再生延迟剩余加本轮或本批产出时间）；有可分配库存即为 0（允许不足一份交付）；既无可分配库存又无后续可分配产出时排除。不可达是排除。选人方只读各方已发布的估计值，不按 `regen_per_minute` 等速率重算，也不跨 tick 缓存等待值。
2. 乘员能力的载体与读取入口。
   已定：与 `LivingEntityEyesightAttachment` 同形的带逻辑附件 `CrewReloadAttachment`（`common/attachment/`，在 `MMAttachments.kt` 注册 factory），持有人身上保存能力本身与当前认领：个人倍率（默认 1.0，钳位 [0.25, 4.0]，非有限值按 1.0 并记警告）、正在推进的作业，以及本 tick 能推进多少的判定；只有倍率需要持久化，用 codec 存。它与装弹机构实现同一个执行者接口——放行条件、本 tick 可推进量、占用归属（§3.2、§4.1），Launcher 只按接口询问，不按对面是实体还是子系统分支。玩家、NPC、机娘共用这一条路径，不为宿主类型另写分支。客户端不读该倍率，实际时长由服务端发布（§5.3）。附件通过 §3.6 的 `IAmmoConsumer#getReloadJob()` 读取 Launcher 当前作业；读口与 `ReloadJob` 字段扩展在 P3b 附件接入前完成，不复制分配记录或外部修改作业。
3. 人工中断、直接换人、路径切换的进度规则，以及单人占用的认领与释放时机。
   已定：同一路径内换人保留人工进度，同一 tick 内释放旧认领并认领新人，不重播已越过的音效标记。当前乘员离座、死亡或实体移除时立即释放其个人认领；无替补时作业暂停（进度冻结，已取得的机构槽位与上游预留保留），暂停超过 200 tick 即终止并释放全部资源。人物认领的释放不清除本次已完成的人工进度，也不能把离座者继续锁在旧作业上。路径切换（机构摧毁、供能不满足、供弹中断）重建作业：人工段按 §3.2 的标准人力秒继续并按新 `H` 截断（超过则人工段直接完成），机械段从 0 重新计时，槽位与上游预留重新申请；机械动作不跨机构换算。认领在人工段开始前的同一 tick 完成，段完成或作业终止时释放；多台武器争同一乘员按 `(subPartId, subsystemName)` 稳定序每 tick 重试，不建全局等待队列，也不允许抢占。
4. 零秒段、起止标记，以及 FMOD 事件怎样跟随暂停和阶段切换。
   已定：长度 ≤ 0 的段在解码期按未配置处理（显式 0 跳过，负值报解码错误），两段都不存在仍是非法配置。段内进度 p ∈ [0,1)，越过阈值即触发；一次推进跨过多个标记时按阈值升序逐个播放。阈值 0 是段开始音、阈值 1 是提交时的完成音，两者不进越过循环。阶段切换先冲刷上一段的剩余标记再启动新段。人工段暂停或机械段受阻时对 FMOD 事件 `pause`，恢复时 `resume`，跨段与作业终止时 `stop` 并释放句柄，完成音允许自然收尾。§5.1 的校准只纠正状态，不触发标记与事件，也不补播。
5. 真实状态的字段编码、协议与 HUD 呈现，以及结构变化后的流程重建。
   已定：复用 `SynchedEntityData` 与现有脏包，常规下行表达装填分配、条件变化和权威结果。分配字段包含 Launcher 内的 `int jobId`、`deliveryTarget` 与 `upstreamOrigin` 两个 `SupplierRef`、冻结的紧凑交付规格、`int reservedCount`、流程来源、阶段、本阶段实际时长、受理及运行／暂停状态，以及带原 `jobId` 的已交付／未交付结束结果；阶段切换、结束或重建时更新。终态与相关库存结果关联应用，两种到达顺序见 §5.1，不能把结束身份只清空而让旧作业再本地提交。完整补推及需要重新建立阶段基线的离散变化可携带一次性进度，稳定运行不按时间经过更新进度字段。`JOB_ELAPSED_ID` 是只在作业开始、离散重建与全量补推时写入的进度基线（`LauncherSubsystem#refreshSyncBaseline` 在 `pushAllTo` 前刷新），稳定装填期间不标脏；本 tick 可推进量由本地执行者按权威运行条件计算，不逐 tick 下发。已下发的字段是 `JOB_ID`／`JOB_TARGET`／`JOB_ORIGIN`／`JOB_SPEC`／`JOB_RESERVED`／`JOB_TOTAL`／`JOB_ELAPSED`，加上结束结果 `JOB_RESULT`／`JOB_RESULT_DELIVERED`（只在收尾时写，新作业不覆盖）；流程来源、阶段与运行／暂停状态尚未随字段下发，客户端按同一份运行条件自行推导。机构同步自身条件／故障；仅独占机构从同一份实际占用记录同步 `(launcherSubPartId, launcherName, jobId)` 形状的槽位拥有者（`SLOT_OWNER`），并发机构不下发该项；未受理的路由指认不算占用（§3.2）。实际架维护服务端预留表，按变化下发已预留总量（`RESERVED`）供可分配库存显示，`R` 已含本作业 `q`，不重复扣份额，不把整张预留表下发。通路发送字段最新绝对值；客户端正常模拟后由 tick 收尾覆盖，不累加网络差量（§3.4、§5.1—§5.3）。音效游标是客户端本地量，不下行、不存档（§3.2、§3.3）。相关字段在 §5.1 的收尾边界统一应用，作业开始／重建须可与上一作业区分，不能只比较长期供给者是否相同，也不建立逐发事件或历史作业日志。字段编码复用现有通路，不预设位打包层。
   协议组当前是 `sync:6.0.0`，对应本节字段表与 `SupplierRef` 的宿主 ID ＋ 名称编码；此后每次修改字段表或引用编码，重读 `network/MMPayloadRegistry.java#register` 并递增实际版本。HUD 从本地作业读进度，分配与时长跟随服务端。结构变化时清理相位丢弃失效的来源、机构与乘员引用；作业引用失效即按第 3 条重建，不跨 tick 保留悬空引用；客户端收到作业清空或重建时停止旧声音实例，不重播历史标记。

这些结论限定实施选择，不表示要先完成药包系统、任意阶段流程或全部物品功能。
