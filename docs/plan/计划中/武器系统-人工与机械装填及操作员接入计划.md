首轮弹药架不作为主动提出弹药需求的接收端，不发现其他弹药架，不发起架间补货或搬运；再生功能只增长自己的数字库存。其职责限于库存／再生、可供规格与数量查询、装填预留、交付及退回接受。退回已交付 Belt 按提供者的回收策略处理，不构成架间补货任务；regen 按计数回收，物品路线的完整实例回收随物品实现接入。

首轮不配置补货层级，不建立后台搬运任务、武器／补货优先级或抢占调度。接收端限于 Launcher，人力和机构共同完成武器装填；弹药架之间的主动接收、容量预留和转运协议由前置计划 §10 的 F4 另行细化。

`ammo_loader`、`regen_loader` 当前都混有储存和输弹职责。本文的“装弹机”专指参与实际装填动作的机构；不能把再生库存生产时间直接当作该机构的机械时间。两类储存子系统的最终名称及机械机构类的落点与前置计划 §10 的 F1 一起确定。

## 2. 基准秒数与修正倍率

### 2.1 数据归属

| 位置 | 目标数据 | 含义 |
| --- | --- | --- |
| Launcher 型号定义 | 完整人力装填流程 | 标准人员通过纯人工路径完成一次装填的基准秒数及音效；没有该流程表示不支持此路径 |
| 装弹机型号定义 | 机构辅助装填流程 | 人工准备、机械运行各自的基准秒数及音效；全自动流程没有人工段 |
| 容器型号定义 | `reload_time_penalty` | 容器附加秒数，默认 0；用于大弹匣、重弹箱等供弹具差异 |
| 装填需求方的安装实例 | 每个发现频道的岗位时间倍率 | 该位置的乘员为当前武器／机构操作时的便利程度；例如装填手 1.0、炮手 2.0 |
| 实际乘员 | 个人装填时间倍率 | 人员能力；1 为标准，小于 1 用时较短，大于 1 用时较长 |

AmmoBelt 不保存容器装填时间惩罚；物品路线通过容器型号查询，再生交付路线不应用该惩罚。容器定义与实际物品读取依赖前置计划 §10 的 F5，本文不要求为计时单独制作物品系统。

同一门炮可以具有完整人力 8 秒、半自动准备 2 秒加机械 4 秒、全自动机械 6 秒的不同路径。三个示例是独立的标定值，不能从某个完整人力时间推导所有机构的准备时间。

### 2.2 计算规则

设 `H` 为当前流程人工段的基准秒数，`M` 为机械段基准秒数，`C` 为容器附加秒数，`P` 为选中发现关系的岗位倍率，`A` 为实际乘员的个人倍率：

```text
完整人力或半自动的人工段：T_human = (H + C) × P × A
半自动的机械段：          T_machine = M
全自动的机械段：          T_machine = M + C
顺序执行总时间：          T_total = T_human + T_machine
```

每次装填只应用一次容器惩罚：存在人工段时加在人工段，全自动流程加在机械段。再生路线中 `C = 0`。多个发现频道是候选关系，只有实际选中关系的倍率进入公式。

装弹机型号直接配置机械秒数，不配置与该秒数重复表达标称快慢的固定时间倍率。需要模拟选弹定位时，由机构根据状态提供额外机械秒数；没有储位／转盘状态的型号使用固定周期。再生库存没有物理弹位信息，不能据其计数或 AmmoBelt 配弹序列推导转盘距离。

弹匣容量与更换时间没有线性换算关系。向容器逐发补弹属于另一项操作，不属于本次换装时间公式。待发架和后备架在首轮是互不转运的独立来源，是否能为武器供弹取决于库存与配置的装填路径。架间搬运成本和自动补货策略由前置计划 §10 的 F4 细化。

## 3. 共用流程与唯一执行状态

### 3.1 固定人工段与机械段

Launcher 的人力备份配置和装弹机配置使用同形的具体装填数据：可选人工段、可选机械段，每段包含基准秒数和进度音效。固定按“人工准备 → 机械运行”执行；纯人工仅有人工段，全自动仅有机械段。两段都为空的配置不能表达有效装填路径。

不建立任意阶段脚本、动作解释器、通用工作流接口或阶段提交框架。共用的是实际由 Launcher 消费的时间／音效数据及执行逻辑，具体 Java 类型名在编解码实施时确定。

| 路径示例 | 人工段 | 机械段 |
| --- | --- | --- |
| 人力备份 | 8 秒；开闩、装弹、手动关闩的进度音效 | 无 |
| 半自动机构 | 2 秒；取弹、放上托盘的进度音效 | 4 秒；推弹、自动关闩的进度音效 |
| 全自动机构 | 无 | 6 秒；定位、输弹、关闩的进度音效 |

### 3.2 执行与库存

Launcher 持有本武器唯一的装填运行状态：选定流程来源、当前人工／机械段、段内进度、实际人工执行者和必要的音效事件进度。装弹机提供流程定义、健康／供能条件和占用信息，不自行运行一份针对同次操作的独立计时器。

“弹药架 → 人力准备 → 装弹机 → Launcher”属于同一次武器装填：人工与机械依次执行，人工段结束后释放人员占用。这里的机构入口只是作业交接位置，不形成第二份可查询库存，也不拆为一次弹药架补货作业。完成时从选定来源向 Launcher 提交完整交付。

人工段仅在有可用执行者时推进，机械段按机构可工作条件推进。某阶段的完成只表达计时过程，弹药库存按前置计划 §5.1 的完整交接契约提交，不产生“已装弹头”“已放药包”等中间弹药库存。

人工进度使用归一化的已完成比例；人员或倍率变化时更新后续推进速度，不能通过重算总时长让已完成比例倒退。换人时是否构成中断、失去全部人员时重置到段起点还是保留当前进度、路径故障后怎样进入人力备份，均须在实施前按 §8 明确，不能由 tick 顺序隐式决定。

整份换装、单发入膛和膛内弹保留按前置计划 §4 区分。完成装填前的射击门控、旧 Belt 保持与退回失败处理沿用该计划 §4.3、§5.1；不能因为本流程具有两个计时段而在人工段结束时提前提交一次库存交换。

有效新交付提交时，旧 Belt 可以交给当前合法且接受它的提供者；无人接收或拒收则丢弃，不要求原路退回，不为历史来源建立持久化关系。未完成装填首轮不存档，读档后由服务端重新选择来源与人员并发起装填；膛内弹、实际已装 Belt 和源库存按各自实际持有状态恢复。

### 3.3 进度音效

各路径独立提供音效配置。人力备份的关闩声、半自动托盘声与自动机构声允许不同；同一声音资源可以被多个配置引用。音效标记按所属人工／机械段的 0—1 进度触发，人员倍率只拉伸人工段的时间。

每次推进应处理跨过的全部标记，不能只播放最大阈值，避免一次推进越过多个标记时遗漏声音。阶段开始的 0、完成的 1，以及零秒阶段的标记处理在实施时形成明确规则。已完成阶段不因后续机械计时或人员变化重播。默认人工音效定位在 Launcher，机械音效定位在实际装弹机。

客户端根据服务端选定的流程来源、阶段和进度，正常模拟装填、取弹、扣弹、音效与 HUD；同步回调缓存新值，在主线程 postTick 校准。服务端负责真实库存、选人、占用和完成判定，客户端不重做来源与人员竞争。不得使用客户端座位显示状态作为装填能力的权威输入。完整初值只建立模拟基线，校准不触发枪声或装填标记，不重播历史流程。详细边界见关联同步计划 §2—§4。

C3 的传统进度音效与 FMOD 路径都需要核对。本文不要求建立第二套与装填进度无关的定长音频计时器；两种音频后端的触发选择及停止／恢复接线按 §8 细化。

## 4. 操作员、岗位与发现

### 4.1 需求方发现座位

Launcher 为完整人力路径主动发现座位；装弹机为自身流程的人工段主动发现座位。座位声明可被发现的频道并提供当前乘员，个人能力从乘员取得。岗位倍率属于“装填需求方 → 座位”的发现关系，不是座位全局能力。

人力运输／装填能力属于实际人物，使用绑定该人物的能力对象或组件，不是独立子系统；座位不实现人力运输接口。不同武器经座位取得同一个人的能力与占用状态，不能为每个发现者复制一份独立劳力。

同一个炮手座位服务主炮可以是 2.0 倍，服务旁边机枪可以是 1.0 倍；同一人换座后个人倍率保持由其自身能力决定。装填执行者不能直接复用 C6 的开火操作员，后者可能因松开扳机被清空。

座位安装实例提供 `reload_operator_inputs`，默认空列表。其频道与交互输入合并到 `getAcceptedChannels` 的接收声明，广播据此筛选；发现操作只读，不向座位发送交互事件。

下列 JSON 仅固定数据关系，字段拼写在实施时结合现有目标表构建代码确认：

```json
{
  "reload_operator_outputs": {
    "crew.reload.loader": ["local"],
    "crew.reload.gunner": ["local"]
  },
  "reload_operator_time_multipliers": {
    "crew.reload.loader": 1.0,
    "crew.reload.gunner": 2.0
  }
}
```

装填手座位声明 `reload_operator_inputs: ["crew.reload.loader"]`；炮手座位声明 `reload_operator_inputs: ["crew.reload.gunner"]`。发现配置和座位频道属于安装实例，便于同型号安装在不同车辆或位置时设置岗位关系。

倍率绑定发起查询的配置条目。连接器可以转译到达频道，但不会使倍率改为从另一个同名条目读取；每个条目的查询结果携带其关系代价供选人使用。

### 4.2 推荐范围：Part 内广播

推荐 `local` 作为常规发现范围，覆盖当前 Part 的全部 SubPart。两个独立炮塔 Part 可以复用相同频道而互相隔离。`global` 仅用于作者明确允许全装配体共享人员的情形；炮身和座位分属不同 Part 时通过连接器接线限定范围。

`local` 的边界是 Part，不是任意空间距离。两个炮塔被做在同一 Part 内时，需要频道或明确接线区分；座位和武器在不同 Part 内时，单独的 `local` 不会自动跨件发现。

C8 的 Part 当前没有广播能力。信号系统前置工作见 [Part 信号总线实施计划](信号系统-Part信号总线实施计划.md) §3—§7：实现独立 local 订阅、Part 内广播与同范围只读发现，覆盖存储、端口接收和生命周期。装填代码不专门遍历全车座位来代替信号系统的范围解析。

### 4.3 选耗时最短的实际执行者

候选必须是有效座位的存活乘员，满足当前流程可达关系，并且未参与另一项人工装填。服务端计算各候选的 `P × A`，选当前人工段实际耗时最短者；没有固定“装填手优先”规则，也不依赖频道顺序表达岗位优先级。

同一个人通过多条发现线路出现时，只采用其最有利的有效关系；这些关系的倍率不互相相乘。耗时相同时保持当前执行者，其他平局以稳定身份顺序处理，不能依赖散列表顺序。

同一实际乘员一次只能推进一个人工装填段。多个武器同时需要人时的认领时机和稳定处理顺序按 §8 固定；不引入全局最优调度或多人合作加速。全自动流程没有人工占用，半自动人工段结束后释放人员，机械部分继续受机构状态约束。

结构变化时按 C9 的两个相位重建候选座位引用。乘员上下座和个人能力变化在运行时检查，不以“发现到一个座位”替代“存在实际可用乘员”。已移除或已离开当前拓扑的对象不能保留为有效执行者。

### 4.4 供弹握手与装填请求

供弹发现由有输入需求的对象发起：Launcher 查询可用机构或直接弹药架，机构查询自己的上游来源；弹药架只提供库存和回收能力，不查询其他弹药架。接线使用项目的“频道 → 目标列表”形状，例如 `ammo_discovery_targets: {"ammo_120mm": ["local"]}`，提供方声明相应 `discovery_inputs`。不配置完整路径数组。

频道用于握手发现，`ammo_120mm` 仅表达服务类别。握手调用 C7 的只读终端查询，保存直接上游对象引用和对应线路信息；机构保留自己的上游关系，Launcher 不把全部最终弹药架展平为可任意选用的来源。发现结果按对象身份过滤查询者自身，机械链有环时该路径无效。

实际装填在服务端通过缓存引用调用对象方法，传递选中规格并完成查询、预留和交付，不向所有提供者广播实际取弹请求。弹药兼容性依据 Launcher 的弹种／供弹具规则，不能从发现频道名称推导。

武器控制器从受控 Launcher 的合法连接汇总弹药资源池，按实际库存所有者去重计数；机构提供的多条路径不产生多份库存。弹药架为空时，武器可以等待该架自身再生或选择另一条已配置来源路径，不自动把后备架弹药搬入待发架。

## 5. 分装弹与检查点的范围

当前目标只包含人工／机械计时和进度音效，不实现物理分装弹、可选药包量、部分入膛库存、独立弹头／发射药物品或任意阶段检查点。

未来确有分装弹需求时，允许在弹药定义增加一个分装装填布尔，采用简化进度保留：人工段不足 50% 时从 0 恢复，达到 50% 后从 50% 恢复。该规则只作用于单发装填的人工段，不作用于弹匣／弹链更换，也不改变弹道或装药量。检查点属于本次具体装填，换弹种或终止本次装填时清除。

这个布尔和半程恢复不属于本计划的首轮交付；没有消费方时不预建字段。首轮未完成作业读档后重新发起，不保存检查点。未来需要跨存档保留检查点时，所存进度必须与本次弹药和流程身份绑定，不能仅保存一个可套用到另一发弹药的百分比。

## 6. 实施顺序

| 步骤 | 内容 | 完成边界 |
| --- | --- | --- |
| P0 | 拆分机械／储存职责及供弹关系 | 先明确并拆分库存、运输执行和 Launcher 作业状态；弹药架只作提供者，供弹握手保存直接上游引用，资源池保持路径可达性与库存去重；AmmoBelt 第一阶段独立验收 |
| P1 | Part 总线前置 | 按 Part 信号总线实施计划交付 `local` 的真实广播和只读发现，同一 Part 覆盖全部 SubPart；全车 `global` 保持其范围 |
| P2 | 时间与音效配置 | 纯人工和机构流程读取同形配置；人工／机械分开计时；移植现有进度音效并核对 FMOD 接入 |
| P3 | 座位发现与个人能力 | 接收频道、发现关系倍率、实际人员能力读取、最快候选及单人占用进入人工段 |
| P4 | 状态、同步与迁移 | 单一运行状态、合法中断、库存整份提交、首次快照和客户端 postTick 校准；运行关系重建，未完成作业不存档，拒收允许丢弃；同步字段变化按实际协议版本提升 |
| P5 | 第一方标定与编译 | 核对各型号纯人力、半自动、自动路线及岗位关系；编译通过，行为验证另行记录 |

首轮实施不依赖弹药物品和容器模型已经完成；容器惩罚随容器资源接入，regen 路线不为此构造占位容器。内容 schema 手改 builtin 的中英源，再按仓库根 `AGENTS.md` 的“内容包 schema 同步”执行副本同步。

## 7. 验收与本次文档交付

首轮构建验收从 Machine-Max 仓库根执行 `.\gradlew --offline classes`。物品往返、实际音频、乘员接替和多人同步的玩法验证不能由编译成功推断，验证结果需按实施范围另记。本计划不把新的 JUnit／GameTest 或客户端启动纳入 AmmoBelt 第一阶段验收。

本文交付装填设计与实施顺序，Part 总线的独立实现及验证由关联计划负责。文档交付检查链接、源码符号、自包含性与 diff，不运行编译或游戏。弹药架主动补货、架间转运及其任务优先级不属于首轮验收。

## 8. 实施前待细化项

1. 装弹机构与物品／再生弹药架的具体类型拆分，以及不同来源的取用成本与人力备份路径选择。
2. 乘员能力的注册及读取入口；玩家、NPC、机娘宿主采用同一时间倍率语义，能力取值要有限且为正。
3. 人工中断、直接换人、路径切换的进度规则，以及单人占用的认领／释放时机；最快选择规则必须保留。
4. 零秒段、起止标记，以及 FMOD 事件怎样跟随暂停和阶段切换；同步应用遵循关联同步计划 §2—§4，不引入回滚重推。
5. 真实状态的字段编码、协议与 HUD 呈现，以及结构变化后的流程重建；首轮未完成作业读档后重启，来源关系、人员认领与机构占用不持久化，结构和接线由载具／部件层恢复。

这些待定项限定实施选择，不表示要先完成药包系统、任意阶段流程或全部物品功能。
