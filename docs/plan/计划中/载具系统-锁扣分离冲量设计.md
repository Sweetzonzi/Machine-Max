# 载具系统：锁扣分离冲量设计

> **状态**：P0–P2 已实现（四个字段、两条触发路径、施加方法、单测与 GameTest）；P3 的桑塔纳标定与 §9 的 G1–G2 人工验收待做。
> **日期**：2026-11-25
> **范围**：`machine_max:coupler` 型号静态属性新增四个平铺字段；锁扣在解扣与意外脱锁两条路径上各施加一次零件冲量；桑塔纳六处可开合件的标定。
> **依赖**：现成的 `SubPartImpulse` / `ObjectManager` 冲量批次、`AbstractConnector#detach` 的 `PPhase.ALL` 摘关节、`DestroyableRigidObject.updateLock` 的位姿同步。不需要新的网络载荷、事件、求解器能力或连接点字段。

## 1. 目标与非目标

**目标**

1. 分离这一瞬间给离开的那一件一个可标定的初速度。今日解扣只解除约束、不写速度，因此“几发打脱锁”与“主动解扣”在画面上都缺少结果（§2 第 1、4 行）。
2. 主动解扣与意外脱锁可以分别选择是否施加，由一个布尔表达（`separation_command_only`）。
3. 施加点可以选在分离点或质心，分别服务“带铰链的件要初始自转”与“自由件要纯平移”两类需求（`separation_apply_on_center`）。
4. 走已有的零件冲量管线，不新增同步字段、事件、载荷或物理任务排序。

**非目标**

- 不向基座施加反作用力（§10.5）。
- 不做分离时的粒子或专属特效；可见的结果就是运动本身（§10.6）。
- 不给 `ConnectorAttr` 加任何字段：连接点层分不清“被拆除”与“被打脱”，且会命中陈旧边清理与销毁路径（§10.2）。
- 不做持续推力、不做 `release` 信号频道、不做按分离原因分档的第三档（§10.4）。
- 不改 `integrity` / `impact_reduction` / `impact_absorption` 那套结构冲击语义，锁扣的“几发即脱锁”标定仍按 [5.14 连接点标定](../../wiki/5-内容包制作教程/5.14-连接点标定.md) 的口径。

## 3. 内容契约

### 3.1 字段

四个字段都平铺在锁扣型号的静态属性里，与 `capture_distance`、`max_lock_speed` 同级。

| 字段 | 类型 | 默认 | 校验 | 语义 |
| --- | --- | --- | --- | --- |
| `separation_impulse` | float，N·s | `8` | 有限且 `>= 0` | 分离时施加的冲量大小；`0` 关闭 |
| `separation_direction` | `Axis` | 省略 = 自动 | 复用 `Axis.CODEC` | 分离方向，宿主子零件局部帧的 `xp` / `xn` / `yp` / `yn` / `zp` / `zn`；省略时取“宿主质心指向分离点” |
| `separation_command_only` | bool | `false` | — | `true` = 只有锁扣自己解开的那一次施加；`false` = 任何分离都施加 |
| `separation_apply_on_center` | bool | `false` | — | `false` = 施在分离点（有力臂，产生初始自转）；`true` = 施在质心（纯平移） |

`Axis` 是 [`util/data/Axis.java`](../../../src/main/java/io/github/sweetzonzi/machine_max/util/data/Axis.java#L9) 里连接点方向用的同一个枚举，不新增枚举类型。

### 3.2 为什么是平铺而不是一个 `separation` 块

1. **型号静态属性里没有“行为组”对象。** 嵌套的只有两类：跨类型复用的音效记录（`sounds`，十几种类型各自包一层、字段集合相同），与真正按轴、按可视模式、按模块拆开的子配置（`roll`、`steering`、`yaw`、`pitch`、`views`、`barrel`、`breech`、`capacitor`）。四个描述同一件事的标量不在这两类里。
2. **带前缀的平铺字段族是既有写法。** [`CarControllerSubsystemStaticAttr`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/attr/static_attr/CarControllerSubsystemStaticAttr.java#L106) 的 `drift_assist` / `drift_front_outer_brake_gain` / `drift_rear_inner_brake_gain`，[`TrackControllerSubsystemStaticAttr`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/attr/static_attr/TrackControllerSubsystemStaticAttr.java#L104) 的 `pivot_yaw_rate` / `pivot_speed_threshold`，[`TransmissionSubsystemStaticAttr`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/attr/static_attr/TransmissionSubsystemStaticAttr.java#L29) 的 `diff_lock*`，都是平铺加前缀，没有包成对象。
3. **两个布尔离开前缀就读不通。** 顶层裸写 `apply_on_center` 要问“中心是什么的中心”，裸写 `command_only` 要问“只有命令时做什么”。带上 `separation_` 前缀即自解释。
4. **建块要多一个只有一处构造的记录。** 一个 `SeparationAttr` 要一条 CODEC、一个 `DEFAULT` 常量、一次 `optionalFieldOf("separation", …)`，而它只装两个 float、两个 bool，没有跨类型复用也没有第二个调用方，正落在“中间对象只在跨边界冻结数据时出现”要挡的那一类。若将来 Java 侧需要类型而 JSON 侧仍要平铺，`BasicAttr` 那种 `MapCodec.forGetter` 内联写法（[`BasicSubsystemStaticAttr`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/attr/static_attr/BasicSubsystemStaticAttr.java#L24)）是现成的做法，四个字段暂无必要。

代价：锁扣型号的顶层键从七个涨到十一个，`separation_direction` 与 `capture_distance` 同屏，读者需要靠前缀分清“接近方向”与“离开方向”。

### 3.3 schema 与检查

- 为四个 `separation_*` 字段改 builtin 的 `coupler_static_attr.schema.json` 两份（`zh_cn`、`en_us`），写清单位、默认值与 `additionalProperties: false` 下的四个新属性，然后跑 `./gradlew syncSchemas`。schema 不做同步时内容包 JSON 会因为未知属性解析失败。
- `content-check.gradle` 不需要改：那张表只登记信号频道，锁扣一行是 `always: ['interact']`（[第 1206 行](../../../content-check.gradle#L1206)），与型号静态字段无关。
- 型号属性不进存档，四个新字段不涉及存档兼容。

## 4. 触发

### 4.1 哪些入口施加

| 入口 | 是否施加 | 依据 |
| --- | --- | --- |
| 交互区点击解扣成功（`onInteract` 返回 `CONSUME` 之前） | 施加 | 这是“主动分离”，也是 `separation_command_only = true` 唯一放行的时机 |
| 配对引用消失、`connected` 由真翻假（`reconcileConnected` 的意外消失分支） | `separation_command_only = false` 时施加 | 这一支只在 `isConnected()` 为真、两端引用都已不成立、且不是本锁扣发起的时候进入，覆盖打脱锁与其他系统摘除两条来源 |
| 关节失效收尾（`disconnectUnified`） | 不施加 | 这是“引用与图都在、物理约束已失效”的巡检修复，不是一次真实分离 |
| 陈旧边删除（`dropStaleGraphEdge`） | 不施加 | 这时双端引用早已不成立，只剩一条图边待清，没有分离事实；清理陈旧边不能让零件飞出去 |
| 同件恢复失败（`tryRestoreSamePartConnection` 把标记清成假） | 不施加 | 读档时的状态对账，没有分离事实 |
| 锁扣停用或宿主已摧毁 | 不施加（显式 `isActive()` 判定） | 意外消失那一支跑在 `onTick` 的 `isActive()` 门之前，需要自带这一条 |

### 4.2 一次分离只施一次

两处调用都挂在“这次配对刚刚结束”的边沿上：交互路径是解扣返回成功之后，巡检路径是 `isConnected()` 从真翻假的那一 tick。`setConnected(false)` 会立刻把标记改掉，因此同一对连接不会在后续 tick 重复进入。

### 4.3 打脱锁的时序

巡检要晚一个服务端 tick 才看见打脱，因此这一条的冲量比分离晚 50 ms 落地。此时关节已经被摘掉、零件已经开始各自运动，冲量是叠加在这个既成状态上的——与“子弹把门推开”的实际顺序一致。

## 5. 施加

### 5.1 目标

冲量施加在**对侧**（`SimpleConnector`）所在的子零件，也就是离开的那一件；锁扣所在的一侧不动。内容因此要把锁扣装在基座侧，桑塔纳六处已经是这样。装在可动侧的锁扣会把对侧推走，按内容错误处理，不额外防护。

### 5.2 方向

- 写了 `separation_direction`：取该轴在宿主子零件局部帧的方向，换算到世界。
- 省略：取宿主子零件刚体原点（即其质心）指向分离点的方向。车门在两侧得到向外，引擎盖在上方得到向上，后备箱盖在后上方得到向后上，这些都不需要作者写；弹射座椅坐在车体中部、径向水平，需要显式写 `yp`。
- 两点距离小于 `1e-4 m` 时不施加并记一条 DEBUG：零向量定不出方向，不猜。

方向绝不从连接点法线推导。法线只保证两端相反，四个锁扣的实际取值是手调的：桑塔纳车体的 `hood_lock` 是 `yp`（指向上方），而右前门锁是 `xn`（指向车内）。按“宿主法线朝外”推，引擎盖对、四扇车门全反。

### 5.3 作用点

- `separation_apply_on_center = false`（默认）：用分离点的世界坐标，由连接点的 `offsetFromMassCenter` 与宿主刚体的位姿快照换算，与 [`CouplerSubsystem#endpoint`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/CouplerSubsystem.java#L654) 同一口径（读 `transform` 与服务端刚体已发布的位姿，不读动画 locator，也不读校正后的 `actualTransform`）。力臂带来初始自转，车门需要这个。
- `separation_apply_on_center = true`：用目标子零件的刚体原点，纯平移，无初始自转。弹射座椅这类一离轨就不该翻的件用这一档。

### 5.4 施加前必须唤醒

登记冲量前调用 `assembly.activatePhysics()`。休眠刚体不唤醒时，`applyImpulse` 改的是速度而不是位移，零件看起来不动——命中冲量那条路径同样在登记前做了这一步。

### 5.5 不施加反作用

冲量只给离开的那一件，基座不受反作用力。既有的后坐力同样只作用在发射平台上，不向弹丸反推。反作用会让一次抛放踢到整车，两个目标用途都不需要它。

### 5.6 顺序与端别

- **顺序**：服务端 `onTick` 里的登记早于本 tick 的 `publishImpulses`，因此冲量在同一 tick 的 `PPhase.PRE` 批次里；摘关节的 `PPhase.ALL` 已先于它执行（§2 第 2 行）。打脱锁那一支更是晚了一个 tick，关节必然已经不在。
- **端别**：纯服务端。客户端刚体按同步位姿摆放，分离后的运动由位姿同步承载，不需要载荷携带冲量。

## 6. 标定

### 6.1 尺子

配置注释里已有的锚点都是对 24 kg / 30 耐久车门而言的：

| 冲击 | 冲量 | 该门上的速度 |
| --- | --- | --- |
| 手枪一发 | `1 N·s` | `0.04 m/s` |
| 空手一击 | `2.6 N·s` | `0.11 m/s` |
| 铁剑一击 | `14 N·s` | `0.58 m/s` |
| 暴击斧一击 | `43 N·s` | `1.79 m/s` |
| 125 mm 一发 | `20 N·s` | `0.83 m/s` |

### 6.2 默认值 `8 N·s`

落在空手与铁剑之间：在 24 kg 车门上约 `0.33 m/s`，按注释里“暴击斧 43 N·s 约 11°”线性折算约 2°。看得出动了一下，不像被踹开；想更明显取 12，想几乎不可见取 4。

冲量对质量是盲的：同一个 `8 N·s` 在 500 kg 的炮塔上是 `0.016 m/s`，等于没有。默认值只对轻件有意义，重件必须自己给——这一条要写进作者文档，否则会被当成默认值失效。

**默认非零是有意的全局行为变更**：桑塔纳六处锁扣与第三方包里的每个锁扣，一行 JSON 都不改就会开始弹。这是为了避免“没写就不生效”这种静默坑，但必须进提交信息与 [锁扣实施计划](载具系统-锁扣子系统实施计划.md) 的迁移说明。

### 6.3 按哪个场景标定

- 停着的车被打脱锁：此时开、关片段早已走完，门与盖的驱动器已松手（§2 最后一行），冲量不受阻挡。**默认值按这个场景调。**
- 点开门：同一 tick 里伺服正以最高 `180°/s` 把门往开的方向驱动，冲量只是叠加，主要靠伺服。也就是说 `separation_command_only = false` 的价值集中在“没人命令的分离”与没有作动器的件上。
- 舱盖与后备箱盖的 `_open` 是循环片段，撑开之后由伺服持续顶住开度；这一档没有新的分离可触发，冲量不会与它相争。

### 6.4 各用途起点

| 用途 | `separation_impulse` | 备注 |
| --- | --- | --- |
| 车门被打脱锁 | `6`–`12` | 有铰链，冲量转成摆角 |
| 引擎盖、后备箱盖 | `8`–`20` | 铰链是限位轴，弹起后靠重力回落 |
| 货箱、挂载物脱落 | `30`–`80` | 无铰链，纯平动 |
| 弹射座椅的弹出段 | `150`–`400`（配 `separation_apply_on_center = true`） | 5 m/s 只换约 1.2 m 弹起高度；持续上升见 §10.4 |

这些是起点而非定值，最终以 §9 的人工验收为准。

## 7. 影响面与回归

- 默认非零使全部既有锁扣的行为改变，回归面主要在 GameTest 里那几处现成夹具：[`CouplerGameTest`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/CouplerGameTest.java#L189) 的两处 `detachConnections`、[`CouplerSamePartGameTest`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/CouplerSamePartGameTest.java#L152) 的同件解扣。配重与同件对侧现在会被推开，涉及“解扣后端点距离”“重扣门控”“分裂后引用分量”的断言都要重看；确实需要静止语义的夹具显式写 `separation_impulse = 0`。
- 同件自环解扣会把冲量施加到同一 `Part` 的另一个 `SubPart` 上。内部连接仍在，件不会飞走，但这是既有夹具里最容易被推动的一处。
- 新增四个字段后，builtin 的两份 schema 与各包副本要一起提交（`syncSchemas`），否则 `checkSchemas` 让 `check` 失败。
- 作者的字段说明进 schema；标定方法进 [5.14](../../wiki/5-内容包制作教程/5.14-连接点标定.md)；字段契约进 [锁扣实施计划](载具系统-锁扣子系统实施计划.md) §3 的表。

| P0 ✅ | 四个字段进 `CouplerSubsystemStaticAttr`（CODEC 一行加四个 `optionalFieldOf`、构造期校验），builtin 两份 schema，跑 `syncSchemas` |

| P2 ✅ | 单测：默认值、边界校验、方向与作用点解析 |
| P3 | 桑塔纳六处按 §6.4 起步标定，走 §9 的人工验收，再决定是否写进型号 JSON |

T1–T4 的观察对象是「解扣那一刻某个刚体获得了多少速度」，因此由 §9 的 G1–G2 在游戏内验收，不进 GameTest：GameTest 的快速 tick 让物理线程长期落后于服务端 tick，关节入世、地形等待的钉住与解扣那一步的重力重写都落在同一个观察窗口里，夹具自身的不确定性大于被测行为。诊断期实测到的速度变化与 `J / m` 逐位相符（24 kg 门上 `8 N·s` 得到 `0.3333 m/s`），可作为 §5 施加口径已落地的证据；`command_only`、`separation_apply_on_center` 与 `separation_impulse = 0` 三档的差异由 §3.1 的解码测试覆盖字段语义，实际手感留待游戏内验收。

## 10. 决策记录

1. **单位取 N·s，不取 m/s。** 冲量是作者能直接对标的量：配置注释里的锚点给出的就是 N·s。按速度写就要读零件质量折算，多一次主线程取数、多一条“质量与型号解耦后不准”的隐患；按冲量写，四个字段的施加完全由常量与方向决定。代价是质量盲（§6.2），接受。
2. **不进 `ConnectorAttr`。** 连接点层没有“主动解扣”这个动词，只有“被摘掉”；写在那一层会让任何一对被拆开的螺栓都弹射，包括陈旧边清理与 `detach(true)` 的销毁路径。锁扣已经负责“分离时的声音”，也负责唯一一种主动解扣，把冲量放在这里才是同一件事的力学版本。
3. **不建 `separation` 块。** 理由见 §3.2。
4. **不给 `ConnectorDetachEvent` 加分离原因。** 加一个枚举能精确区分“打脱”与“拆除”，但目前只有锁扣一个消费方，而且锁扣靠自己的两条路径已经能分开这两件事；按“没有消费方的类型不写”，等真的出现“拆解不该弹”的需求再加。
5. **不施加反作用力。** 基座是载具其余部分的锚，反作用会把一次抛放变成整车的踢击；这一档没有消费方。
6. **不做分离粒子。** 粒子要新的内容字段、客户端生成与 `content-check` 的引用检查，而“明显的视觉效果”这一项已经由运动本身兑现。日后要加，落点是客户端已经存在的连接状态边沿（`tickClientSounds` 那个位置）。
7. **不做持续推力、不做 `release` 信号频道。** 完整弹射需要“分离冲量 + 沿方向持续推刚体的部件”两件事，后者是独立特性：`LauncherSubsystem` 只生成投射物，`JointDriverSubsystem` 只驱动关节，都没有这条能力。主动释放可以复用门的“交互区 → 连接点 → 锁扣 `onInteract`”接线，不需要新频道；要脚本化顺序释放时再加。
