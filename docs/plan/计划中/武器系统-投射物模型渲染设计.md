## 二、模型是怎么被找到的（路径约定）

模型的加载与寻址都在 Spark-Core 侧，规则如下（依据见附录 A）：

1. **模型文件**：`spark_modules/<包>/<命名空间>/models/<类别>/<名字>.json`，由 `ModelModule` 读取，注册为 `ModelIndex(类别, <命名空间>:<文件名去掉 .json>)`。
   - `<类别>` 就是目录名，也是 `ModelIndex.type`。零件用 `part`、方块用 `block`、物品用 `item`，投射物因此是 **`projectile`**。
   - 文件名去掉的只有 `.json` 一层，所以 Blockbench 导出的 `9m133.geo.json` 注册出来是 `<命名空间>:9m133.geo`，**带 `.geo` 后缀**。仓库内零件模型一律保留这个后缀（`k17.geo.json` → `machine_max:k17.geo`，JSON 里写 `"model": "machine_max:k17.geo"`）。
2. **贴图**：`ModelInstance` 的默认贴图路径是 `<命名空间>:textures/<类别>/<模型键路径>.png`。零件不用这个默认值——它们的 `variant.textures` 显式给出 `machine_max:textures/part/k17/k17.png`，由 `ModelController.setTextureLocation()` 覆盖。
3. **贴图必须是** `textures/` **下的真实资源**：`TextureModule` 把 `spark_modules/**/textures/**/*.png` 注册进客户端资源包，路径就是 `textures/<各层目录>/<文件名>`。
4. **模型数据来自服务端**：`ModelModule` 只在 `fromServer` 时读文件，客户端拿到的是服务端发来的同一份 `OModel`。因此模型放内容包里、不用放客户端专属资源。

**由此得到本方案的目录约定**（与用户要求的"projectile 类别"一致）：

```text
spark_modules/sdkfz/machine_max/models/projectile/9m133.geo.json     -> ModelIndex("projectile", machine_max:9m133.geo)
spark_modules/sdkfz/machine_max/textures/projectile/9m133.png         -> machine_max:textures/projectile/9m133.png
```

## 三、资源就位情况与两个实测发现

已放置（源文件取自 `D:\Files\Project_Blockbench\载具\相关物品`）：

| 文件 | 大小 | 说明 |
| --- | --- | --- |
| `models/projectile/9m133.geo.json` | 30265 B | `format_version 1.12.0`，**1 根骨骼 `bone`**（`pivot [0,0,-0.84589]`、`rotation [0,-90,0]`），**93 个 cube**，无 mesh、无 locator |
| `textures/projectile/9m133.png` | 1553 B | 64×64 RGBA，61 种颜色 |

让这个弹种渲染出模型的接法是显式配置 `model`：`9m133_kornet` 注册在 `machine_max:9m133_kornet` 上，而模型注册出的索引是 `machine_max:9m133.geo`，两者不相等；若只依赖缺省回退（按弹种注册键查找同名模型），`OModel.getOrEmpty` 会取到空模型（0 骨骼）、骨骼循环一次都不执行。§4 的 B 方案正是为这类名字对不上的情况而选。

两个在核对资源时量出来的事实，都会影响观感，列在这里而不是留到实现时才发现：

**（1）贴图声明与文件不一致，但两者是自洽的，预判可以直接用。**
`description.texture_width/height` 声明 **32×32**，而 PNG 实际 **64×64**。UV 归一化用的是声明值（`u / textureWidth`），所以正常化后 UV 落在 64px 贴图的**上半分辨率**位置。把两边的包围盒对一下就能确认这不是错误：

| 量 | 值 | 换算 |
| --- | --- | --- |
| UV 最大延展（171 个面） | `(u,v) = (27.5, 27.5)` | 32 空间 |
| 64px 贴图里非透明像素的包围盒 | `x ∈ [0,54]`、`y ∈ [0,57]` | 64 空间 |
| 二者关系 | `27.5 / 32` = `55 / 64`、`28.5 / 32` ≈ `57 / 64` | — |

即贴图是同一套 32 空间版式的 2 倍分辨率重绘，`u/32` 与 `u·2/64` 指向同一片像素。**结论：不必改声明，也不必缩贴图**。仍列入 §12 的验收项（贴图是否正确只有在画面上能确认）。

**（2）模型比真弹小，长约 0.80 米。**
忽略每个 cube 自身的旋转，93 个 cube 的长轴是 Blockbench 的 **X** 轴，延展 12.748 单位；经 `ModelModule` 的转换后长轴落到模型空间 ±Z（推导见 §5）。`ModelModule` 把坐标除以 16，故模型长 **12.748 / 16 = 0.797 格（米）**。9M133 实弹长 1.2 m，两者比 **0.66**。最长截面只有 0.87 单位、展向 3.98 单位，与该弹细长比量级一致，说明**形状对、比例对，整体偏小**。

要按真实尺寸出观感，需要 **≈1.5 倍缩放**。缩放是逐弹种可配的量（§4），因为不同内容包的建模比例不会统一。

## 四、绑定方式：三选一，推荐 B

| 方案 | 做法 | 代价 | 能表达什么 |
| --- | --- | --- | --- |
| **A** 零代码，文件名对齐注册键 | 把模型存成 `models/projectile/9m133_kornet.json`，索引自然等于注册键 | 无代码改动 | 只能"一弹种一模型"，名字必须等于弹种注册键；无法共享、无法关闭、无法改朝向/缩放 |
| **B** 显式字段 + 保留注册键回退 | `ProjectileType.VisualProperties` 增加可选 `model` / `texture`（已落地），朝向与缩放另需 `model_rotation` / `model_scale` / `model_lod_distance`（未实现）；`getDefaultModelIndex()` 优先取 `visual.model`，为空时退回注册键 | `VisualProperties` 加可选字段 + `getDefaultModelIndex()` 与 `getModelController()` 各改几行（`model`/`texture` 已完成）；`ProjectileEntityRenderer` 应用缩放/旋转（未做） | 已实现别名、多弹种共享一个模型、显式贴图、显式关闭（不配即不渲染）；朝向修正与缩放待实现 |
| **C** 完全走 `ModelIndex` 编解码 | 让 JSON 直接写 `ModelIndex`（含 `type`） | 内容包要写 `"type": "projectile"`，且把 Spark 的内部类型泄漏到弹种 JSON | 同 B，但契约更啰嗦 |

**推荐 B**，理由三条：

1. **它是 A 的超集**，且**缺省行为与今天逐字相同**：`visual.model` 不写就仍然按注册键找模型，内容包依旧可以"把文件命名成弹种名"零配置接入。A 与 B 的差别只在内容包多写一行。
2. **朝向与缩放必须能逐弹种配**：§3 已经量出模型偏小 0.66 倍，而"鼻子朝哪"在建模阶段无法强制——把这两个量做成 JSON 字段，就不用为了改朝向去重新导出模型。
3. **避免把 Spark 的 `ModelIndex` 泄漏进弹种 JSON**：`type` 对投射物恒为 `"projectile"`，让内容包写它是纯粹的噪声。

## 五、姿态与朝向

### 5.1 契约：模型的局部 `-Z` 就是飞行方向

投射物的 `transform` 旋转分量由 `ProjectileManager` 每 tick 写成"局部 `-Z` 对齐速度方向"的四元数，与载具的 `getFrontVector()` 同一约定。渲染侧 `ProjectileEntityRenderer` 直接把 `getWorldPositionMatrix(partialTick)` 乘进 `PoseStack`，所以**模型的局部 `-Z` 必须指向弹头**。

配套的既有行为：平移取 lerp、旋转取 slerp，因此制导弹大幅改向时模型与曳光是同一套帧间平滑，不会逐 tick 跳。

### 5.2 9m133 的朝向推导（结论：长轴落在 ±Z，需实测确认哪端是弹头）

模型只有一根根骨骼 `bone`，它带着 `rotation [0,-90,0]` 与 `pivot [0,0,-0.84589]`——说明作者是按 Blockbench 的 X 轴建模、再整体转 90° 对齐。`ModelModule` 的换算会镜像 X 并取反骨骼旋转的 X/Y 分量，逐步算下来：

- cube 的内坐标 x 区间是 `[-origin.x - size.x, -origin.x]`，即 Blockbench `+X` 端映射到内坐标 `-X` 端；
- 骨骼旋转变成 `+90°` 绕 Y（绕枢轴），作用后内坐标 `-X` 端落到模型空间 `+Z`。

实测的 cube 分布印证长轴落在 Z 上：`origin.x` 在 `[3,7]` 区间有 35 个 cube、在 `[-6,-4]` 区间有 47 个，两端各有一组薄板构成的外形（前者薄板长边沿 Z、对称分布在轴线两侧，是该弹的尾翼/格栅翼），中间是弹体。

**因此本方案不把朝向当作已知正确**，而是把朝向做成可配项（§5.3），并在 §12 验收里用一条明确的判据确认：*朝飞行方向看，若翼面在弹头一端、锥面在尾端，则需要补 180° 偏航。*`model_rotation` 字段未实现，因此这一改当前只能落到模型上（重导时把弹头转向 `-Z`），或先落地该字段。

### 5.3 应用点：客户端渲染器，不进 SoA

朝向与缩放**不写进 `transform`、也不进 SoA 热路径**，只在 `ProjectileEntityRenderer` 里应用一次（两个字段未实现，下面三行是它们落地时的形态）：

```text
poseStack.mulPose(worldMatrix)                  // 世界 → 模型空间（已含插值姿态）
poseStack.mulPose(模型旋转 model_rotation)       // 绕模型原点，ZYX 欧拉，单位度
poseStack.scale(model_scale, ...)               // 各向同性
```

理由：这两个量是**模型的属性**而不是弹道属性。放进 `velocityAttitude()` 会让物理线程每 tick 多做一次旋转合成，并且会把"某个内容包的模型建歪了"变成全局物理量。

## 六、动画：静态模型不需要，动画模型需要两个驱动点

**关键事实：没有任何地方在 tick 投射物的 `AnimController`。** `AnimApplier` 只对 `IEntityAnimatable` 实体工作（`MMProjectileEntity` 不是，它只是把 `getModelController()` 转发给投射物）；零件的 tick 由 `VehicleCore` 驱动，投射物不在那条链上。

这**对静态模型没有影响**：`BonePose` 的 `oLocalTransform / localTransform` 初值都是 `KeyAnimData()`（位移 0、旋转 0、缩放 1），不 tick 就一直是单位变换，模型按原样渲染。所以**第一期不做动画也是完整的**。

需要动画（展开舵面、发动机火焰、折叠尾翼）时才要驱动，两个点：

| 驱动 | 线程 | 建议挂点 | 代价 |
| --- | --- | --- | --- |
| `AnimController.tick()` | 主线程 | `ProjectileManager` 的主线程遍历（`tickAndPreTick()`，与 `preTick()` 同一趟） | 发布共享 pose（`setChanged`）；无动画时是几次空遍历 |
| `AnimController.physTick()` | 物理线程 | `ProjectileManager.prePhysicsTick()` 的遍历（两端都会跑：客户端也有 `PhysicsLevelTickEvent`，证据是客户端专属的 `ClientProjectileRenderer.physTick()` 就在这条事件上） | 无动画时 `isPlayingAnim == false` 立即返回 |

配套三点：

1. **`getRenderPosition()` 要覆写**。`IAnimatable` 的默认实现会为了取 LOD 判断用的位置而构造一个完整 `Matrix4f`（每 tick 每投射物一次分配），`physTick` 里会调它。投射物已经有缓存的 `getPosition()`，覆写成直读即可。零件侧已有同样做法可参照。
2. **LOD 只影响动画混合频率，不影响渲染几何**。`AnimController.physTick` 按 `ModelIndex.fullDetailDistance` 分 LOD 档、跳帧做骨骼混合；骨骼该不该画、画多细，渲染侧不看 LOD。投射物是 0.8 米量级的小物体，默认 24 m 太大，建议用 `model_lod_distance` 给到 8 m 上下。
3. **动画集也要放对目录**：`animations/<类别>/<名字>/<动画名>.json`，类别同样是 `projectile`；`OAnimationSet` 按 `ModelIndex` 索引，与模型同一把钥匙。

## 七、渲染路径：沿用实体渲染器

模型继续由 `ProjectileEntityRenderer`（`MMProjectileEntity` 的 `EntityRenderer`）画，不新开渲染器。理由与代价：

- **代价为零**：每个投射物都有且只有一个 `MMProjectileEntity`（服务端 `flushProjectileEntities()` 生成、客户端按 objId 反绑），模型只是复用它已有的渲染入口，不新增实体、不新增网络字段。
- **位姿同源**：渲染器用 `projectile.getWorldPositionMatrix(partialTick)` 定位与定向，与曳光渲染器逐字相同，画面上模型与曳光线不可能分离。
- **光照贴图取自代理实体所在方块**（`getBlockLightLevel`/`getSkyLightLevel`），无需自算。
- **材质**：`RenderType.entityTranslucent(texture)`，写深度（这一点在 §9.3 有后果）。
- **已知不对称**：命中即毁的那一发靠 `deadRetained` 多留一帧给曳光，但它的代理实体已经被摘除，因此**那一帧没有模型、只有曳光**。视觉上可接受，记在这里以免被当成 bug。

需要动的三处（都在客户端；第三处已落地，前两处未做）：

1. **空模型提前返回**（未做）：取到 `ModelInstance` 后先看 `getOrigin().getBones().isEmpty()`，为空直接 return——把光照查询、位姿矩阵、`pushPose` 全部省掉。绝大多数弹种（没配模型）走的都是这条路，所以它是一处纯优化，不影响可见结果。
2. **应用 `model_rotation` / `model_scale`**（未做，§5.3）。
3. **贴图覆盖**（已落地）：`texture` 非空时 `setTextureLocation()`，否则沿用默认推导路径。这一句在 `BallisticProjectile.getModelController()` 的懒初始化里，只执行一次。

## 八、字段契约

全部挂在既有 `visual` 块下，**全部可选**。`ProjectileType.VisualProperties` 是 record + `RecordCodecBuilder`，加字段就是加 `optionalFieldOf`；"未配置"用 `Optional<ResourceLocation>` 承载，与 `HitBoxAttr.PhysicsOverwriteAttr` 的写法一致。

| 字段 | 类型 | 缺省 | 语义 | 状态 |
| --- | --- | --- | --- | --- |
| `model` | `ResourceLocation` | 无 → 退回 `<弹种注册键>` | 模型名（`models/projectile/` 下的文件名去掉 `.json`），例 `machine_max:9m133.geo` | 已实现 |
| `texture` | `ResourceLocation` | 无 → `textures/projectile/<model 路径>.png` | 贴图全路径，例 `machine_max:textures/projectile/9m133.png` | 已实现 |
| `model_scale` | `double` | `1.0` | 各向同性缩放 | 未实现 |
| `model_rotation` | `Vec3`（度，`Vec3.CODEC`） | `[0,0,0]` | 模型空间欧拉角，绕模型原点；与 `HudElement` 的 `rotation`/`scale` 同一种用法 | 未实现 |
| `model_lod_distance` | `double` | `8.0` | 传给 `ModelIndex.fullDetailDistance`，决定动画按 LOD 降频的距离 | 未实现 |

已落地的取值逻辑（`BallisticProjectile`，见附录 A 第 2、4 条）：

```text
getDefaultModelIndex():
    model = visual.model().orElse(null)
    if model == null: model = <弹种注册键>     // 回退：模型文件命名成弹种名即可零配置接入
    return ModelIndex("projectile", model)

getModelController():                          // 仍是懒加载
    if controller == null:
        controller = new ModelController(this) // 构造即读 getDefaultModelIndex()
        visual.texture().ifPresent(controller::setTextureLocation)
    return controller
```

`model_lod_distance` 落地时进上面 `ModelIndex` 构造的第 3 个参数；`model_rotation` / `model_scale` 只在 `ProjectileEntityRenderer` 里作用于 `PoseStack`（§5.3）。

**9m133 的落定写法**（`projectiles/9m133_kornet.json` 的 `visual` 块，已成文）：

```json
"visual": {
  "tracer_color": [255, 170, 60],
  "tracer_alpha": 255,
  "tracer_length": 1.05,
  "model": "machine_max:9m133.geo",
  "texture": "machine_max:textures/projectile/9m133.png"
}
```

## 九、与曳光、与光照的关系

### 9.1 曳光线与模型会同时出现

曳光线画在 `AFTER_TRANSLUCENT_BLOCKS`，长度 = 当前速率 × `tracer_length`（9m133 是 1.05）。带上模型后，画面上是"一个 3D 弹体 + 一条从弹体位置向后的长线"。

三选一，取舍留给实现者（推荐第三个）：

| 处理 | 效果 |
| --- | --- |
| 都保留 | 线像发动机尾焰/烟迹；但 1.05 × 速度的线在初速 50 m/s 时也有 52 m，远长于 1.2 m 的弹体 |
| 有模型时关掉曳光 | 弹体清晰，但远距离只剩一个小点，丢失"弹道可见性" | 
| **有模型时保留曳光、由内容包把 `tracer_length` 调到 0.1 量级** | 线退化成弹体后方一小段尾迹，弹道可见性与弹体辨识度都在；不改代码，纯内容包调参 |

### 9.2 自遮挡容差：投射物一旦有模型就会进入曳光光照的陷阱区

`docs/plan/计划中/武器系统-投射物曳光光照设计.md` §9.3 记录了一个陷阱：投射物模型自己写深度缓冲，若曳光光照的遮挡容差太小，光源会被自己的模型剔掉、光照凭空消失。该文档把"这条陷阱是否触发"与**该弹种是否解析到带骨骼的模型**绑定。§3 的资源与 §8 的 `model` 字段落地后，触发条件对 9M133 成立：它解析到 93 个 cube 的模型，因此写深度、自遮挡陷阱对它生效；其余弹种没有 `model`、也没有与注册键同名的模型，解析到空模型、不写深度。

那份文档的四处状态描述与两处字段计数已按当前事实改写（§11 列出具体位置）。要点是：判据是"该弹种是否解析到带骨骼的模型"，不是"仓库里有没有模型资源"——因此 9M133 一旦配上 `model` 就进入陷阱区，而不是等到所有弹种都有模型。

9M133 按口径折算的容差是 `0.20 m + 2 mm × 152 = 0.504 m`，与模型半长（0.797 m 的一半）同量级，说明**这份容差是按"带模型的弹体厚度"设计的**：模型一上线正好用上。这也是为什么**不要**用"缩小模型"去回避容差问题——容差与口径挂钩，与渲染缩放无关。

**P1 — 让 9m133 出现模型（本方案的主体，客户端 + 弹种 JSON）**

6. **已完成**：同步更新受影响的文档（§11）。

**P2 — 动画（可选，只有内容包要用动画时才做）**

1. `BallisticProjectile` 覆写 `getRenderPosition()` 为直读位置，避免 LOD 计算里每 tick 构造矩阵。
2. `ProjectileManager` 主线程遍历加 `getAnimController().tick()`，物理线程遍历加 `physTick()`；两处都按"该弹种有动画集"门控。
3. 若内容包要循环动画，参照零件侧 `autoPlayLoopAnimations()` 的做法：只自动播 `loop:true` 的动画，一次性动画由命中/发射事件触发。

| 不做 | 理由 |
| --- | --- |
| 把姿态或缩放写进 `transform`/`velocityAttitude()` | 模型属性不进物理热路径（§5.3） |

| 替换 `ProjectileEntityRenderer` 为视觉特效渲染器 | 已有实体渲染器可用，见 §7 |
| 服务端做任何模型相关的事 | 模型数据是 `fromServer` 发下来的，服务端只提供资源（§2） |
