# 第一部分 · 决策与依据

## 一、目标与范围

### 1.1 要做什么

| 阶段 | 内容 | 载体 |
| --- | --- | --- |
| **S1** | **逐像素光照**：以投射物为球心，按世界空间距离衰减，把光加到已画好的画面上 | 全屏后处理 pass |
| **S2** | **光源级遮挡剔除**：光源整体落到几何体之后时，本帧不参与光照 | CPU 装配 + shader 各一处判断 |
| **S3** | **屏幕空间遮挡步进**：部分遮挡与自投影（车体挡住曳光的投影） | 同上，可选 |
| **S4** | **法线响应**：从深度导数重建法线，做出"朝向光的一侧更亮"的材质感 | 同上，可选 |
| **F1** | **修复爆炸波前折射的遮挡通路**：让它的深度剔除真正生效（修复前：原版会话下它读到的深度恒为远平面、判据从不生效；光影会话下深度未被抹平、判据本就生效） | 与 S1 同一份深度副本 |

S1 独立可用：只有 S1 时，光斑的位置、大小、衰减形状与世界空间一致，被前景挡住的部分不会穿透——这已经是"曳光在照亮周围"的完整观感。S2 修掉的是光源自身被遮挡时的穿透，S3/S4 是观感增强。

F1 是既有特性的缺陷修复，与 S1 共用同一套深度机制（§6.7）：两者都必须在深度还有效的时刻取走它，因此合并为一次改造，而不是各自再写一遍。F1 与 S1–S4 相互独立，可单独提交。

### 1.2 不做什么

| 不做 | 理由 |
| --- | --- |
| 修改世界光照数据 | §1.3：本效果是逐帧图像运算，不产生任何持久状态 |
| 光源累积缓冲（延迟式光照） | §3.3：可见光源数量有界且很小，该架构徒增 FBO、深度拷贝与一条合成链 |
| 阴影贴图 | 需要一条独立的世界几何渲染通道，成本与收益不成比例；遮挡由 S2/S3 的屏幕空间手段承担 |
| 体积光 / 光轴 | 需要沿视线多次采样做 ray march，逐像素成本比本文方案高一到两个数量级 |
| 世界内加法几何光晕 | §2.1：它拿不到世界空间衰减、遮挡与法线响应，正是本文要替代的方案 |
| 光照影响云 | 云写入深度缓冲，会被一并照亮；天气（雨雪）不写深度，不受影响（附录 C19）。已知且接受（§13 风险表第 6 条） |
| 新增投射物弹道/终端字段 | 只读既有的 `visual` 块与 `external.caliber`（口径，用于折算照射半径，§11.1），不触碰外弹道解算、终端效应与命中判定 |

### 1.3 与"不动世界光照数据"的关系

本效果不写入光照引擎的任何状态。逐项对照如下，用于在实现期与验收期排除越界改动：

| 关注的量 | 本效果是否触碰 | 说明 |
| --- | --- | --- |
| 方块亮度（block light） | 否 | 不调用 `LevelLightEngine`，不触发区块重光照 |
| 天空亮度（sky light） | 否 | 同上 |
| `LightTexture.pack(block, sky)` | 否 | 每个渲染器的光照贴图坐标不由本效果参与计算 |
| `BlockState.getLightEmission()` | 否 | 不注册任何光源方块 |
| 服务端 → 客户端的同步 | 否 | 无新增网络载荷；光源列表在客户端由既有 SoC 数组现算 |
| 持久状态 | 无 | 全部数据是每帧重建的临时量，退出世界即丢弃 |

因此本效果与其它模组的光照修改、以及原版的昼夜/天气光照演化互不干扰；世界在任何时刻的光照查询结果与未安装本效果时一致。

## 二、为什么必须走屏幕空间后处理

### 2.1 世界内加法几何买不到的三样东西

Minecraft 走前向渲染，没有 G-Buffer：光照已经烘进每个像素的最终颜色里。世界内加法几何（面向相机的广告牌）能做的只是"往已画好的像素上加颜色"，它买不到下面三样。这一路在项目内的实例是照明子系统的车灯光晕（`LightSourceRenderer` 以径向光晕/光锥绘制，附录 C1b），其配置只需"范围/颜色/强度"三个量即可成立，正因为下面三样它都拿不到：

| 缺什么 | 后果 |
| --- | --- |
| **世界空间距离** | 广告牌的衰减只能在平面内插值，等于拿**屏幕距离**当**世界距离**的代理。§2.2 |
| **遮挡** | 几何自身进深度缓冲后会被遮挡，但它无法知道"光源是否被别的几何体挡住" |
| **法线** | 无法区分朝向光的一面与背对光的一面，只能整片加同样的量 |

第一项是几何方案与本文方案在**正确性**上的分界，不是画质偏好。

### 2.2 两个"远"必须分开

"越远越淡"里混着两个独立的量：

| 量 | 定义 | 决定 |
| --- | --- | --- |
| **世界距离** $d = \lVert P - C \rVert$ | 光心 $C$ 到**被照表面点** $P$ 的米制距离 | 照亮范围与强度 |
| **相机距离** $z_c = -C_z$ | 光心到相机的视空间前向深度 | 光斑在屏幕上的大小（透视缩放） |

世界内广告牌的正确做法是：屏幕半径按 $z_c$ 算（近大远小），但 alpha 只能在四边形平面内插值——于是它实际用的是屏幕距离。这两者在**被照表面与光心深度接近**时几乎一致（曳光贴着车体飞），在**深度差很大**时明显不一致。

典型失效场景：投射物低空掠过地面、相机从斜上方俯视。地面上的光斑在世界空间里是圆，在屏幕上应是椭圆（透视压缩）；屏幕距离代理会把它画成正圆。曳光高速掠过时不易察觉，悬停的火箭弹或慢速导弹上会露陷。

本文方案逐像素重建 $P$（§6.5），$d$ 是真实米制距离，因此光斑形状、以及"光心在相机背后 / 光心在近平面以内"这些退化情形全部自然正确。

### 2.3 遮挡天然成立

逐像素方案只照亮**可见表面**：像素存在，说明它没被任何东西挡住，于是它收到的光必然来自"光心到它之间没有遮挡物"的情形——除非光心自己在别的几何体之后（§9）。

这一条为"照亮车体"这个核心用例提供了正确基线：车体背面的光不会漏到正面。

## 三、为什么用逐像素枚举而不是光源累积缓冲

### 3.1 并发量估算

判断架构的分水岭是"同屏可见光源有多少"。曳光在弹道上按 $v / (RPM/60)$ 均匀排布，因此弹距为

$$s = \frac{60v}{RPM}$$

以仓库内已配置的投射物实测数据为输入（`base_velocity` 与 `max_lifetime`，见附录 C15）：

| 弹种 | $v$ (m/s) | 寿命 (s) | 750 RPM 下弹距 $s$ (m) |
| --- | --- | --- | --- |
| 7.62mm 曳光 | 855 | 2.5 | 68 |
| 7.92mm 曳光 | 740 | 2.0 | 59 |
| 20mm AP | 600 | 3.0 | 48 |
| 30mm AP | 960 | 5.0 | 77 |
| 50mm PzGr39 | 835 | 5.0 | 67 |
| 120mm APFSDS | 1650 | 10.0 | 132 |
| 155mm HE | 600 | 20.0 | 48 |
| 9M133 导弹 | 50（推力加速） | 25.0 | 单发 |

### 3.2 屏幕半径剔除

光源在屏幕上的投影半径约为

$$r_{px} \approx \frac{f \cdot R}{d}$$

$f$ 为像素焦距（附录 A.3），$R$ 为光源世界半径。取 $R = 1.5$ m、$f \approx 770$ px（1080p、FOV 70°），则剔除阈值 $r_{px} < r_{\min}$ 等价于只处理

$$d < d_{\max} = \frac{f R}{r_{\min}}$$

| $r_{\min}$ | $d_{\max}$ | 说明 |
| --- | --- | --- |
| 2 px | 578 m | 8 位色深下 2px 半径的贡献已接近不可见 |
| 4 px | 289 m | 保守取值，观感上无损失 |

按 4px 阈值、$d_{\max} = 289$ m、750 RPM 的弹距：7.62mm 约 4 发、30mm 约 4 发、120mm 约 2 发同时在列。**可见光源数量是个位数。**

> 上表按参考半径 $R = 1.5$ m 给出量级。落地后 $R$ 随口径折算（§11.1，1.58 m–3.05 m），$d_{\max} = fR/r_{\min}$ 相应落在 304–587 m，同屏发数只会更少、不会更多。

再叠加"按屏幕半径降序取前 $N$ 槽位"，超限时替换最弱的一个（与爆炸波前折射的装配策略同构），最坏情形也只是丢掉贡献最小的那几个。

### 3.3 结论

采用**逐像素枚举（每像素遍历光源数组）**，不采用光源累积缓冲。理由：

- 可见光源数量有界且很小（§3.2），枚举的每像素循环体只是一次约 8 条指令的视线-球剔除；
- 累积缓冲要把每光源成本降到"正比于屏幕投影面积"，只有在光源成百上千时才有意义——被剔除阈值挡在门外的那些光源本来就贡献不了可见亮度；
- 累积缓冲需要额外 FBO、把主目标深度拷进该 FBO（项目内 `OffscreenFbo.copyMainDepth` 是既有先例），以及一条合成链，是纯负债。

**触发重新评估的条件**：若将来出现千发级射速的武器（如 CIWS）或破片战斗部一次生成大量独立光源，再回到本节重算 §3.2 的数量级。

# 第二部分 · 契约与通道

## 四、客户端手上的数据

### 4.1 投射物 SoA 的既有成员

`ProjectileManager` 用结构数组（SoA）保存投射物状态，客户端每帧可直接索引（附录 C2、C17）：

| 成员 | 用途 |
| --- | --- |
| `count` | 有效条目数，循环上界 |
| `posX[i]` / `posY[i]` / `posZ[i]` | 位置（客户端为外推值） |
| `velX[i]` / `velY[i]` / `velZ[i]` | 速度 |
| `lifetime[i]` | 剩余寿命，用于与曳光同步淡出（§4.4） |
| `objId[i]` | 取 `DestroyableObject`，进而取插值位姿 |
| `typeIndex[i]` | 索引到投射物类型，取 `visual` 配置 |
| `alive[i]` | 条目是否仍参与模拟。**不是渲染判据**——见 §4.3 第 1 条 |
| `deadRetained[i]` | 死条目多留一次清理扫描，供渲染画出命中闪光（附录 C25） |

`ObjectManager.levelProjectileManagers` 按维度给出管理器，与 `ClientProjectileRenderer` 的取法一致。

### 4.2 位置必须与曳光同源

光源位置取 `DestroyableObject.getWorldPositionMatrix(partialTick)` 的平移分量——**与 `ClientProjectileRenderer` 逐字相同的调用**（附录 C2）。

理由：800 m/s 量级的弹一 tick 位移约 40 m，客户端在 `ProjectileManager.clientExtrapolate()` 中以 5 个子步外推，位置在 tick 内是平滑的。光源与曳光若取不同来源，快速弹上会出现光斑与曳光线分离。**同源比绝对平滑更重要**。

### 4.3 候选列表的装配与剔除

每帧在 CPU 侧装配候选光源，顺序与判据如下（对应爆炸波前折射的 `assemble()` 骨架）：

1. **用与渲染器相同的门禁筛条目**：`getProjectileTypeByIndex(i)` 取到类型后，跳过曳光不可见的弹种（`tracer_alpha <= 0`），跳过 `pm.getProjectile(i)` 取不到对象的条目；
2. 计算世界位置 → 视空间（附录 A.1）；
3. 剔除：光心在相机后方（$z_c \le 0$，此时屏幕投影方向会翻转）。更近的光源不在 CPU 侧重复剔除——它们由着色器的 `NEAR_Z` 判据兜住，见 §6.5；
4. 剔除：屏幕投影半径 $r_{px} < r_{\min}$（§3.2）；
5. 剔除：$d > $ 视距；
6. 按 $r_{px}$ 降序取前 $N = 16$ 个；超限时替换当前贡献最弱的一个；
7. 把该发的视空间光心、半径、颜色、强度写入自持的装配数组（§6.6），供 uniform 全量上传。

**第 1 条是整节的门禁，不能改用 `alive` / `lifetime`。** `ClientProjectileRenderer` 刻意不检查 `alive`（`ClientProjectileRenderer.java:60-62` 的注释写明：死条目由 `deadRetained` 在数组里多留一次清理扫描，这一帧仍要画出来，否则"出膛即命中销毁"的投射物完全没有曳光）。若光源按 `alive` 早退，那一发就只剩曳光线、没有光，违反 §4.2 立下的"光斑与曳光同源"标准；`deadRetained` 保留的那一帧也会同样错位。因此本文与渲染器取同一组门禁：**类型的曳光配置 + 对象可取到**。

**候选列表直接遍历 SoA，不构造快照 List。** `ExplosionManager.visuals()` 返回 `Collections.unmodifiableList` 的活视图（附录 C16），那是爆炸侧的合适做法；但 `ProjectileManager` 的 SoA 结构正是为"无每帧分配"而设计的，每帧构造 `List<TracerLightVisual>` 会违背它的设计前提。中间量放在 §6.6 的自持数组里，不产生每帧对象。

### 4.4 强度与曳光的同步

光源强度不是独立的一条曲线，而是跟随曳光自身已有的两条调制，否则两者会在末尾分离（曳光渐暗、光斑不暗，读作"光先走、线还在"）：

| 调制 | 曳光侧 | 光源侧 |
| --- | --- | --- |
| 弹种透明度 | `tracer_alpha / 255` | 乘进每槽强度 |
| 超时淡出 | `lifetime < 20` 时乘 `lifetime / 20` | 同一条包络 |

每槽强度 = `tracer_light_intensity` × 客户端全局倍率 × 上表两条。**颜色**直接取 `tracer_color`（§11.1）：光是曳光自己发的，不做分色，因此默认情况下光斑与曳光线同色。

两者的混合方式不同（曳光走加法混合，光斑走 screen 混合，§9.2），因此"同强度"不等于"同亮度"，这是已知且接受的取舍。

## 五、通道选型

### 5.1 挂载点

挂在 `RenderLevelStageEvent` 的 `AFTER_LEVEL` 阶段（NeoForge 阶段事件，触发于 `GameRenderer.renderLevel` 内、`LevelRenderer.renderLevel` 返回之后），由 `PostProcessingManager` 统一管理生命周期。

该事件携带本文需要的全部量：`getModelViewMatrix()`（纯旋转）、`getProjectionMatrix()`、`getCamera()`、`getPartialTick()`（`DeltaTracker`）。项目内已有两个效果在该阶段工作（`LightSourceRenderer` 的体积光、`DistantVehicleRenderer` 的远程载具），取用方式可直接参照。

选择该时机的三条理由：

| 理由 | 说明 |
| --- | --- |
| 深度缓冲已完整 | 所有世界几何（含实体、方块实体、粒子、云）均已写入，遮挡判据可用 |
| 在第一人称手部之前 | 光照只作用于世界画面，不影响手部物品、HUD 与屏幕 |
| 不受视角模式影响 | 第一/第三人称都能触达 |

**深度必须在本阶段立即取走，不能等到更晚的时机。** 同一个 `renderLevel` 在手部渲染之前会执行一次 `RenderSystem.clear(GL_DEPTH_BUFFER_BIT)`（`GameRenderer.java:1282`）。这一步是否真的抹平深度，取决于执行那一刻的深度写掩码：**原版会话里掩码为真，主目标深度被整体写成远平面；光影（Iris）会话里掩码为假，清除是空操作、深度原样留下**（附录 C27 的两次采集）。此外，任何以 `minecraft:main` 为输出目标的 pass 在绘制前也会清空该目标（`PostPass.process` → `RenderTarget.clear`），本项目每条链末尾的 `blit → main` 都在此列。因此：

- 本文的深度**不能**声明为指向主目标的 auxtarget（`{"id":"minecraft:main:depth"}`）。在 `AFTER_LEVEL` 之后再读它，原版会话里的读数是恒为 1.0 的空深度，逐像素都会命中 §6.5 的天空早退、光斑不出现；光影会话里却看起来正常——这个差异随光影开关变化，不可依赖；
- 正确做法是在本阶段把主目标深度**拷进链内临时目标**，着色器从副本采样。项目内 `OffscreenFbo.copyMainDepth` 就是这个模式，其注释"AFTER_LEVEL 调用，此时深度完整"即本节结论的既有记录（附录 C22）；
- **副本目标的深度格式必须与主目标逐位相同**：`glBlitFrameBuffer` 的深度位在两侧深度格式不一致时按规范非法（`GL_INVALID_OPERATION`，副本里只剩清屏值）。本项目主目标的深度是 `GL_DEPTH32F_STENCIL8`（带 stencil），而 `new TextureTarget(w, h, true, ...)` 默认给的是 `GL_DEPTH_COMPONENT`。**链 JSON 里声明的目标不在此列**：NeoForge 给 `PostChain.addTempTarget` 加了"镜像主目标 stencil"的补丁（附录 C28），因此声明式目标无需额外处理；手工建的目标则必须自己 `enableStencil()`；
- blit 前后要**还原两处状态**：`RenderTarget.copyDepthFrom` 结束时把 FBO 0 绑在 DRAW 上，必须重新 `bindWrite(true)` 主目标；blit 本身受深度写掩码影响，应在拷贝前置真、拷贝后还原（附录 C28）。

### 5.2 与既有后处理链的次序

本文效果排在**最前**，次序为：

```text
曳光光照  →  爆炸波前折射  →  过载黑视  →  失色
```

两条理由：

1. **折射是对最终画面的屏幕空间扭曲**。任何在它之后加入的内容都不会被扭曲，爆炸发生时那部分会显得"贴上去"。光照放在它之前，光斑会被折射一并扭曲，这是期望行为。
2. **过载黑视与失色是全屏滤镜**，语义上应作用在**已被照亮**的画面上。

本效果只做加法、不做扭曲，因此它相对折射的次序在数学上无影响；上面取的是"被折射扭曲"这一条一致性的收益。

**次序只有在"每条链都从副本读深度"的前提下才是自由的。** 反例是实测到的：任一以 `minecraft:main` 为输出目标的 pass（每条链末尾的 `blit → main`）在原版会话里会把主目标深度写成常量 0.12 m，于是**排在它后面的任何对 `main:depth` 的采样都会全像素判为被遮挡**——折射链若挂在曳光链之后且直读 `main:depth`，爆炸环会整屏消失（附录 C27）。所以"次序自由"不是从"加法与扭曲可交换"推出来的，而是靠下面这条不变量买来的：

> 每帧只在 §5.1 那个时刻取一份深度副本；所有需要深度的 pass 都从副本采样，谁都不读 `minecraft:main:depth`。

在这条不变量下，链的先后才只影响观感（即本节前述两条理由）。**副本的所有权定为"每条链各声明并拷贝一份"**：链 JSON 的目标表逐链独立，因此"一份副本被两条链共用"要么靠共享目标注入（在 `PostChain` 构造前把外部目标放进目标表，需改 `PostChain` 的目标表且要额外定所有权与销毁时机），要么把两个效果并入同一条链（§5.3 的合并选项）。两条路的收益都只是省一次 blit，而各拷一份与 F1 现有形态完全一致、两个效果可独立开关与回退，因此取各拷一份：同帧既有爆炸又有曳光候选时两次深度 blit（§5.4 的成本表按一次计），无候选的链各自为 0 次。若实测带宽吃紧，再按 §5.3 的合并链收敛。

这条选择的**硬约束**是两份快照都必须在本帧第一个深度消费者之前取完：曳光链自己的 pass 与所有以 `minecraft:main` 为输出目标的 pass 一样会清空主目标深度，因此 `PostProcessingManager` 里两个 `capture*` 都排在曳光 `render()` 之前（§十五）。

落地时需同步更新 `PostProcessingManager` 内的次序注释，以及 `已实现/武器系统-爆炸波前视觉设计.md` 中把它自己记为"最先"的三处表述（该文档 §5.1、风险表第 6 条、文件清单）。

### 5.3 一条链的固定成本

既有的每条 `PostChain` 都是"`pass → swap`"加"`blit → main`"，即**两次全屏读写**。世界渲染阶段的链有三条（折射、过载、失色），合计每帧 6 次；本文增加一条后为 8 次。CRT 滤镜挂在 GUI 阶段、默认关闭，不计入世界渲染成本。

| 分辨率 | 单次全屏读写（RGBA8） | 8 次/帧 @60fps |
| --- | --- | --- |
| 1920×1080 | 约 16.6 MB | 约 8 GB/s |
| 3840×2160 | 约 66.4 MB | 约 32 GB/s |

独显无感，核显需实测。若实测帧时间不可接受，有两条路，取舍不同：

| 方案 | 收益 | 代价 |
| --- | --- | --- |
| 保持独立链 | 架构一致：一条链一个特性、独立开关、关闭时零开销 | 多 2 次全屏读写 |
| 并入 `blast_distortion` 的同一条链 | 省掉一整轮读写，两条 pass 各自用 count uniform 自禁用（附录 C13） | 两个特性共用一条链，因此不能独立开关；两条 pass 都必须从 §5.1 的同一份深度副本采样 |

**默认按独立链实现**，先保证架构一致与可独立回退；实测后再决定是否合并。

### 5.4 深度副本的成本

§5.1 的深度副本是**一次 GPU→GPU 的 blit**，不是一遍渲染：

- 目标不重复分配：链内临时目标在链加载时按窗口尺寸建一次（`PostChain.getTempTarget`，附录 C23），每帧只做搬运，无每帧分配；
- 无 CPU 回读、无 `glReadPixels`、无同步等待；
- 深度附件是与主目标**同格式**的深度-模板纹理（本仓库基线为 `GL_DEPTH32F_STENCIL8`，附录 C28），即 **8 字节/像素**，与一次全屏 pass（读颜色 + 写颜色 = 8 字节/像素）相当。不用 4 字节/像素的纯深度格式，是因为深度位 blit 要求两侧格式逐位相同（§5.1）：主目标带 stencil，副本就必须带。

| 分辨率 | 单次深度 blit | 占单次全屏 pass 的比例 | @60fps | @144fps | @240fps |
| --- | --- | --- | --- | --- | --- |
| 1920×1080 | 约 16.6 MB | 100% | 约 1.0 GB/s | 约 2.4 GB/s | 约 4.0 GB/s |
| 2560×1440 | 约 29.5 MB | 100% | 约 1.8 GB/s | 约 4.2 GB/s | 约 7.1 GB/s |
| 3840×2160 | 约 66.4 MB | 100% | 约 4.0 GB/s | 约 9.6 GB/s | 约 15.9 GB/s |

换算成链成本：一次深度 blit 的搬运量与一次全屏 pass 相当，在 §5.3 的 8 次链内读写之上再加约 1/8 的搬运量。真正的压力点不是带宽而是**同步**——它插在"世界刚画完"与"第一次采样"之间，强制一次显存往返，会把 GPU 流水线截断一次；帧率越高，这一泡的相对占比越大。因此：

- **无候选光源的帧不拷贝**：拷贝必须放在 §6.1 的"候选数为 0 → CPU 侧提前返回"分支**之内**，而不是放在每帧无条件执行的路径上。绝大多数帧没有曳光，这些帧的拷贝成本因此为 0；
- 折射链在同一时刻也取自己的快照（§6.7 的 F1），两条链按 §5.2 的决定**各声明并拷贝一份**：同帧既有爆炸又有曳光候选时是 2 次 blit，任一侧没有候选时那一侧为 0 次；
- 实测不达标时的退路按优先级：先试半分辨率（光斑是低频信号，降采样几乎无损，拷贝与 pass 成本同时降到 1/4），再考虑合并链。

# 第三部分 · 着色器设计

## 六、后处理通道详细设计

### 6.1 生命周期

与 `BlastDistortionEffect` 同构（附录 C8、C9、C12、C13），但挂载在 `AFTER_LEVEL`（§5.1）：

| 时机 | 动作 |
| --- | --- |
| 首次有活跃光源 | 懒加载 `PostChain`，取出数组 uniform 的 `Uniform` 引用与深度副本临时目标 |
| 窗口尺寸变化 | `chain.resize(w, h)`；公式全部按像素与米计算，无需其他改动 |
| 每帧（有候选） | 装配候选列表 → **把主目标深度拷进链内临时目标** → 写 uniform → `chain.process(partialTick)` → `mc.getMainRenderTarget().bindWrite(true)` |
| 候选数为 0 | CPU 侧提前返回：**pass 不提交，深度副本也不执行**，零渲染开销 |
| 退出世界 | `chain.close()`，清空 uniform 引用、深度副本引用与尺寸缓存 |

**深度副本必须在 `AFTER_LEVEL` 完成，且不晚于本帧第一个深度消费者**（§5.1）：副本之后主目标深度可能被任何以 `main` 为输出目标的 pass 清空，晚一帧取就只能拿到远平面。副本与"消费它的 `process()`"是否在同一次调用内并无要求——F1 的落地形态就是副本在 `AFTER_LEVEL` 取、折射在同一帧的 `RenderLevelLastEvent` 才处理（§七）。

| --- | --- |
| `shaders/post/tracer_light.json` | 链：`pass(main → swap)` + `blit(swap → main)`；声明一个深度副本临时目标，供 pass 采样 |
| `shaders/program/tracer_light.json` | 程序：声明两个 sampler 与全部 uniform（含数组） |

### 6.3 每帧的数据装配（Java 侧）

纯 CPU 标量运算，无分支依赖 GPU 状态。每帧写入三类 uniform：

| 类别 | 内容 | 写入路径 |
| --- | --- | --- |
| 视空间光心与半径 | 每槽 4 个 float：`Cx, Cy, Cz, R` | 数组 uniform，需 `PostPass` 引用（附录 C8） |
| 颜色与强度 | 每槽 4 个 float：`r, g, b, intensity` | 同上 |
| 遮挡容差 | 每槽 1 个 float：容差的绝对分量（m，由口径折算，§9.3） | 同上 |
| 标量 | `FocalPx`、`DepthA`、`DepthB`、`LightCount`、`OcclusionTolRel` | `chain.setUniform(String, float)`（附录 C9） |

标量一律用**独立的单分量 uniform**，不打包成 `vec2`/`vec3`/小数组：写标量那条路径一次只写第 0 个分量（附录 C9），打包后其余分量只能取到 JSON 默认值里的垃圾（附录 C14）。`OcclusionTolRel` 因此自成一项。

遮挡容差按槽上传而不是取一个全局常量，是因为它的绝对分量由**该发自己的口径**折算（§9.3）：一个常量在两端各失效一次——大口径弹的近处自遮挡与步枪弹的远处漏光无法用同一个米制值同时满足。

`LightCount` **必须是 float**：int uniform 在该写入路径上不可用（附录 C9）。

数组 uniform 的 JSON 默认值只写前若干个分量，其余是未初始化内存，因此**每帧全量 `set(float[])`**，且与 `process()` 处在同一条无分支的代码路径上。

### 6.4 Uniform 契约

```text
sampler2D DiffuseSampler    上一 pass 的画面
sampler2D MCDepthSampler    链内深度副本（§5.1 在本帧 AFTER_LEVEL 从主目标拷入）

vec2  OutSize               输出尺寸（px），由 PostPass 逐 pass 写入
float FocalPx               像素焦距 f
float DepthA, DepthB        深度线性化系数
float LightCount            有效光源数（float，见 §6.3）
float OcclusionTolRel       遮挡判据的相对容差（§9.2）
float LightView[64]         每 4 个：视空间光心 xyz、世界半径 R
float LightColor[64]        每 4 个：颜色 rgb、强度
float LightTol[16]          每槽 1 个：遮挡容差的绝对分量（m，按口径折算，§9.3）
```

`LightView` / `LightColor` 的长度 $4N = 64$ 对应 $N = 16$（§3.2）。**每个光源占 4 个槽位而不是 3 个**：float 数组 uniform 的分量写入路径以 4 为组（附录 C14），按 4 对齐可以避免跨槽读取的边界问题。`LightTol` 是每槽一个 float 的独立数组（不需要按 4 对齐：它是单独一次 `set(float[])`，不与别的量共享分量）。

### 6.5 片元着色器本体

```glsl
#version 150

uniform sampler2D DiffuseSampler;
uniform sampler2D MCDepthSampler;
uniform vec2  OutSize;
uniform float FocalPx;
uniform float DepthA;
uniform float DepthB;
uniform float LightCount;
uniform float LightView[64];
uniform float LightColor[64];
uniform float LightTol[16];        // 每槽：遮挡容差的绝对分量（m，按口径折算，§9.3）
uniform float OcclusionTolRel;

in  vec2 texCoord;
out vec4 fragColor;

const float NEAR_Z = 0.05;          // 原版近平面（m）

void main() {
    vec4 src = texture(DiffuseSampler, texCoord);
    if (int(LightCount) <= 0) { fragColor = vec4(src.rgb, 1.0); return; }
    vec2 px  = texCoord * OutSize;

    // 本像素的视空间视线方向（未归一化时 z 分量为 -1）
    vec2  q   = vec2((px.x - OutSize.x * 0.5) / FocalPx,
                     (OutSize.y * 0.5 - px.y) / FocalPx);
    float L   = sqrt(1.0 + dot(q, q));
    vec3  dir = vec3(q, -1.0) / L;

    // 深度纹理 → 前向深度（米）。采样的是链内深度副本（§5.1）
    float zBuf = texture(MCDepthSampler, texCoord).r;
    // 天空/远平面：两个端点都判，不假设深度方向（§8.3）
    if (zBuf >= 1.0 || zBuf <= 0.0) { fragColor = vec4(src.rgb, 1.0); return; }
    float zfwd = DepthB / (zBuf + DepthA);
    if (zfwd <= NEAR_Z) { fragColor = vec4(src.rgb, 1.0); return; }

    // 本像素的视空间表面点：沿射线 t·vec3(q,-1)，前向深度恰为 t
    vec3 P = vec3(q, -1.0) * zfwd;

    vec3 light = vec3(0.0);
    for (int i = 0; i < int(LightCount); i++) {
        vec3  C = vec3(LightView[i*4], LightView[i*4+1], LightView[i*4+2]);
        float R = LightView[i*4+3];
        if (R <= 0.0) continue;

        // 视线-球剔除：精确，屏幕角落同样正确（§8.4）
        float tc    = dot(C, dir);
        float perp2 = max(dot(C, C) - tc * tc, 0.0);
        if (perp2 > R * R) continue;

        // S2 光源级遮挡（§9.2）：在光源自身的屏幕位置取深度副本比对
        float zc = -C.z;
        if (zc > NEAR_Z) {
            vec2 lightPx = vec2(OutSize.x * 0.5 + FocalPx * C.x / zc,
                                OutSize.y * 0.5 - FocalPx * C.y / zc);
            if (all(greaterThanEqual(lightPx, vec2(0.0))) &&
                all(lessThan(lightPx, OutSize))) {                  // 越界按可见处理
                float tol   = max(LightTol[i], zc * OcclusionTolRel);
                float zHere = DepthB / (texture(MCDepthSampler, lightPx / OutSize).r + DepthA);
                if (zHere < zc - tol) continue;                     // 光源在几何体之后
            }
        }

        float d = length(P - C);
        if (d >= R) continue;               // §8.4 补足充分性

        float att = 1.0 - d / R;
        att *= att;                          // §8.1 有限支撑
        light += vec3(LightColor[i*4], LightColor[i*4+1], LightColor[i*4+2])
               * (att * LightColor[i*4+3]);
    }

    light = min(light, vec3(1.0));           // §8.2 防止累加溢出
    fragColor = vec4(src.rgb + light * (1.0 - src.rgb), 1.0);   // §8.2
}
```

**`alpha` 必须强制写 1.0**：链尾的 `blit` 会做 alpha 混合，把 alpha 留给画面内容会把天空清成黑色。这一条与爆炸波前折射的处置相同。

上面的代码把 S2 的判据放在片元里（每光源一次深度采样，与像素数无关）；也可按 §9.2 放在 CPU 侧逐光源剔除，二者的判据与容差相同，取其一即可。本文落地取片元形态：CPU 形态要拿到深度值就得先回读显存，那是一次 GPU→CPU 同步，而它正是 §5.4 指出的真正压力点。`MinRadiusPx` 只用于 CPU 侧的候选筛选（§3.2），着色器不需要它，因此**不进 uniform 契约**——屏幕半径下限只有一个所有者，即 Java 侧的 `MIN_SCREEN_RADIUS_PX` 常量（§11.4）。

### 6.6 自持的装配缓冲

§4.3 要求"不构造快照 List"，但排序与超限替换需要为每个候选保留中间量（$r_{px}$、颜色、强度）。这些中间量放在效果自持的**平行原始数组**里，与 uniform 上传的两组数组同构，全程零分配：

| 缓冲 | 长度 | 内容 |
| --- | --- | --- |
| `lightView` | `4N` | 视空间光心 xyz、世界半径 R（直接对应 `LightView`） |
| `lightColor` | `4N` | 颜色 rgb、强度（直接对应 `LightColor`） |
| `lightTol` | `N` | 遮挡容差的绝对分量（直接对应 `LightTol`） |
| `sortKey` | `N` | 该槽的 $r_{px}$，仅用于排序与"替换最弱一个" |

本帧实际写入的槽数是装配方法的返回值，直接当 `LightCount` 传入，不占缓冲。这样 §4.3 的第 2–7 步全程只写数组下标，`process()` 之前一次性把 `lightView` / `lightColor` / `lightTol` 交给 uniform。超限时替换最弱一个的做法与 `BlastDistortionEffect.assemble()` 同构（附录 C24），区别只是本文的比较键是 $r_{px}$ 而不是屏幕偏移峰值。

### 6.7 爆炸波前折射的遮挡修复（F1）

折射的着色器里有一条深度剔除判据（`zScene < zFront - DEPTH_EPS_M` → 该像素比波前更近、被前景遮挡 → 跳过），它决定"站在墙后看爆炸时墙面是否被扯动"。**把深度直读为 `minecraft:main:depth` 时，这条判据在原版会话里从不成立**，原因是采样时机：折射挂在世界渲染全部结束之后，而主目标的深度在它采样之前已被手部块那次 `clear` 抹成远平面（附录 C21），`zScene` 因此对每个像素都等于远平面。**光影（Iris）会话里同一个清除因深度写掩码为假而不生效、深度幸存，判据本来就正常**——所以这是"随光影开关变化"的缺陷，而不是无条件失效（附录 C27 给出两次采集的对照）。折射的画面色偏与深度无关，它一直"看起来能用"，掩盖了这条判据在原版下的失效。

修法与 §5.1 对本文的要求完全一致，因此与 S1 合并实施：

| 项 | 做法 |
| --- | --- |
| 挂载点 | **不动**，仍是 `RenderLevelLastEvent`（§七 已按此落地）。挪到 `AFTER_LEVEL` 同样可行，但那是独立的观感取舍（见下），不是本修复的必要条件 |
| 深度来源 | 在 `AFTER_LEVEL` 把主目标深度拷进**链内声明的**副本目标，pass 声明的是副本目标而非主目标深度（§5.1、附录 C28） |
| 链与着色器 | `shaders/post/blast_distortion.json` 增加一个全尺寸目标，并把 `auxtargets` 的 `id` 由 `minecraft:main:depth` 改为该目标的 `:depth`；`blast_distortion.fsh` **一行都不用改**（sampler 名不变） |
| 判据与容差 | 沿用折射自己的 `DEPTH_EPS_M`（米制）。它比较的是**同一像素**的场景深度与波前交点深度，两者量纲一致、不受 §9.2 那条"单像素深度分辨度正比于前视深度"的影响，因此**不需要**改成相对形式 |
| 清理 | 折射链里那句把背景视为永不遮挡的守卫（`zScene <= 0.0 → 1e9`）在当前标定系数下取不到（系数由 1 m / 256 m 反解，`zScene` 对任何合法深度都是正值），可一并删除或加注说明，避免后人以为它在起作用 |

**"不挪挂载点"省掉的是一次观感改动，不是一次技术必要。** 挪到 `AFTER_LEVEL` 的输入是等价的（事件携带的投影矩阵是世界相机的、模型视图是纯相机旋转），差别只在于**手部是否被折射扭曲**：挂在 `RenderLevelLastEvent` 时手部已经画进画面、会被环扭到；挪到 `AFTER_LEVEL` 则先折射、后画手部，手部不受影响。两者都可接受，取舍留给实现者；F1 的落地形态取"不动"。

**深度副本天然不含手部与 HUD。** 副本取自手部块之前，因此无论手部是否写入主目标深度，副本里都只有世界几何——这正是遮挡判据该面对的东西。反过来说，若直读 `AFTER_LEVEL` 之后的主目标深度，混进来的手部与 HUD 深度会在环上挖出手形的洞。

**连锁影响**：世界渲染阶段的次序是 曳光光照 → 爆炸波前折射 → 过载黑视 → 失色。`已实现/武器系统-爆炸波前视觉设计.md` 的 §5.1、风险表第 6 条与文件清单，以及 `PostProcessingManager` 内的次序注释，都按这条次序陈述（见 §13 风险 12 与 §14）。

**验收**：站在墙后引爆，墙面不被扯动；爆炸在相机上/下方时近处地面不被扯动；波前越过某个方块时前后画面在交点处正确切换；把相机放进爆炸内部，环平滑消失且画面无破图。这一组判据在 `已实现` 文档的 P2 行里已经写好，但该行**没有勾选栏位**——落地时需先给它补一列结论，或把结论记在本节。已完成的部分见 §七。

## 八、四个必须正确处理的语义点

### 8.1 衰减函数必须有有限支撑

**这是正确性约束而不是审美问题。** 包围球剔除（§8.4）假设"$d > R$ 的像素贡献恒为零"。若使用物理的平方反比 $1/(1 + k d^2)$，它在任何有限距离都不为零，被剔除掉的那部分贡献会在阈值处形成**硬边**——光斑边缘出现可见截断。

因此只考虑在 $R$ 处严格归零的函数：

| 候选 | 形式 | 特点 |
| --- | --- | --- |
| 二次窗 | $(1 - d/R)^2$ | 本文采用；中心平坦、边缘 $C^0$，代价最低 |
| 平滑窗 | `smoothstep(R, 0, d)` | 两端都平滑，边缘更柔，代价多几条指令 |
| 四次窗 | $(1 - d^2/R^2)^2$ | 最平滑，中心更集中 |

若需要近场更亮的观感，可以用二次窗乘一个近场增强项，但**窗口因子本身必须在 $R$ 处归零**。

### 8.2 LDR 帧用 screen 混合而非加法

Minecraft 这一帧是 LDR、已过雾效的，没有 HDR 缓冲可以溢出。纯加法 `src + light` 在雪地、白色车体、明亮天空边缘会直接削顶成一片纯白，失去所有细节。

本文采用逐通道的 **screen 混合**：

$$\text{out} = \text{src} + \text{light}\,(1 - \text{src}) = \text{light} + \text{src}\,(1 - \text{light})$$

它正是 $\text{screen}(a, b) = a + b - ab$。性质恰好是所需的：暗表面（$\text{src} \to 0$）吃到近乎全部贡献，亮表面（$\text{src} \to 1$）几乎不变，且**数学上永不削顶**。代价是一条乘加。

副作用：它不是严格线性的光，两个曳光重叠不会亮到两倍。对曳光场景完全可接受，且远优于削顶。此外累加后对 `light` 做一次 $\min(\cdot, 1)$ 作为保险。

### 8.3 天空像素必须排除

`zBuf` 取到深度端点的值表示该像素是背景/远平面，**必须直接跳过，不参与光照**。否则曳光飞向天际线时会把整片天空染亮。

判据同时检查两个端点（标准深度约定下远平面是 1.0，反向深度约定下是 0.0），因此不假设深度方向；两种约定下可见几何都取不到这两个值——标准约定里 0.0 只出现在近平面上，而那里的几何已被裁剪掉。

这条判据成立的前提是"没有任何几何写过该像素的深度"。原版满足这一点：世界渲染开始时把深度清为远平面（`LevelRenderer.renderLevel` 的 `RenderSystem.clear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT)`），天空在 `depthMask(false)` 下绘制、不写深度，天气与世界边界同样不写深度。因此纯天空像素的深度恰为远平面值，而任何实体、方块、粒子、云都会写入一个更近的值。

前提一旦不成立，判据就会"恒真"而不再区分天空与几何：**如果采样时深度已被整体清空，每个像素都读到远平面，本效果会逐像素早退、完全不生效**。这正是 §5.1 要求把深度拷进链内副本、并在 `AFTER_LEVEL` 当场取走的原因。

注意这一条与爆炸波前折射的语义**方向相反**：折射那边把背景视为"永不遮挡"（`zScene = 1e9`），因为折射没有几何体就不该发生；光照这边背景没有表面，因此不该被照亮。两侧都在各自文档与注释中写明，避免互相照抄。

### 8.4 包围剔除的必要与充分

shader 中用了两条判据，缺一不可：

| 判据 | 含义 | 性质 |
| --- | --- | --- |
| `perp2 > R*R` | 本像素**视线**到光心的垂距超过 $R$ | **必要**：视线完全不穿过球时，球内任何点都不在此视线上 |
| `d >= R` | 本像素**表面点**到光心的距离超过 $R$ | **充分**：真正决定贡献是否为零 |

只有第一条会漏：视线穿过球，但该像素的表面点可能远在球外（例如表面比光心近得多或远得多）。只有第二条会做全量重建后才剔除，失去提前退出的收益。

采用"垂距法"而不是"屏幕圆"还有一个收益：垂距是精确的锥截面判据，**屏幕角落处同样正确**，不需要按 $1/\cos$ 或类似因子放大屏幕半径。这与爆炸波前折射取垂距的理由一致。

## 九、遮挡

### 9.1 为什么遮挡不是可选项

没有遮挡处理时，本文方案会退化得**比世界内加法几何更难看**：曳光从车体背后飞过时，它的光斑会穿透车体、照亮车体正面——而"照亮车体"恰恰是本效果的核心用例，车体自己就是那个遮挡物。

存在一个必须接受的物理限制：**屏幕空间方法无法知道光源与表面点之间是否有遮挡物**。深度缓冲只记录每个像素最近的一个表面，不含沿视线的完整几何。可用的手段只有两条：

- **S2**：判断光源自身是否落在几何体之后（每光源一次深度采样）；
- **S3**：从表面点向光源做屏幕空间步进，逐步比对深度（逐像素多次采样）。

### 9.2 S2 —— 每光源一次深度采样

在光源自身的屏幕位置采一次深度：若该处的前向深度显著小于光源的前向深度，说明光源整体在几何体之后，本帧跳过该光源。

| 项 | 内容 |
| --- | --- |
| 判据 | `zScene(光源屏幕位置) < z_c - max(LightTol, z_c · OcclusionTolRel)` → 跳过该光源；`LightTol` 由该发的口径折算（§9.3） |
| 光源屏幕位置 | `(OutSize.x*0.5 + FocalPx*C.x/z_c, OutSize.y*0.5 - FocalPx*C.y/z_c)`，即 §6.5 中已用到的投影式 |
| 成本 | 片元形态（§6.5 采用）：每像素、每个落入光锥的光源 1 次采样，随像素数与光锥内光源数增长；CPU 形态（放在候选装配里逐光源剔除）：每光源 1 次，与像素数无关，但取值需要回读显存（一次 GPU→CPU 同步，§5.4）。**落地取片元形态** |
| 覆盖 | 曳光完全落到车体、墙、山体之后这个最常见、最刺眼的情形 |
| 不覆盖 | 部分遮挡（曳光被细杆挡去一半）。此时偏保守地"整个光源消失"，观感远优于穿透 |
| 越界处置 | 光源屏幕位置在画面外时不采样，按"可见"处理 |

**容差必须是相对量与绝对量的较大者，不能是一个米制常量。** 判据比较的是沿视线的前向深度，而单像素能分辨的深度差正比于该像素的前向深度：以 1080p、$f \approx 771$ px 为例，相邻像素的深度步长在 20 m 处约 0.3 m，在 300 m 处则不足 0.05 m。同一个常量因此会在两端各失效一次——太小则近处光源被自己的模型剔掉，太大则远处光源被永久判为遮挡而消失。所以判据取

$$\text{tol}(z_c) = \max\bigl(\text{LightTol}(\text{口径}),\ z_c \cdot \text{OcclusionTolRel}\bigr)$$

`OcclusionTolRel` 只负责远距离随深度增长的量化余量（一个全局常量），**绝对分量 `LightTol` 逐发不同**：它由该发的口径折算（§9.3），因为近处真正要盖住的是"这一发自己的模型在视线方向上有多大"，而那个量本身就是口径的函数。两个量都列入 §12 的 S2 验收项。

### 9.3 自遮挡陷阱

**S2 的朴素实现会把每个光源自己剔掉。** 原因链条：

1. 投射物的代理实体由 `RenderType.entityTranslucent(texture)` 渲染（附录 C4）；
2. 该 RenderType 未显式设置 writeMask，`CompositeState` 的缺省是 `COLOR_DEPTH_WRITE`；
3. 于是**投射物模型写入了深度缓冲**，在光源自己的屏幕位置处，采到的深度是模型前表面，比光源中心的深度更近；
4. S2 据此判定"被遮挡"→ 所有光源消失。

**处置**：容差的绝对分量必须盖住"这一发自己的模型在视线方向上有多少厚度"。两个失败模式由同一个量决定——

| 容差取值 | 失败模式 |
| --- | --- |
| 过小 | 光源被自己的模型剔掉，光照凭空消失 |
| 过大 | 光源穿透近处遮挡物，回到 §9.1 的问题 |

该厚度是口径的函数（弹体细长比约 5，半长 ≈ 2.5 × 口径），因此绝对分量按口径线性折算：

$$\text{LightTol}(\text{口径}) = 0.20\,\text{m} + 2\,\text{mm} \times \text{口径(mm)}$$

0.20 m 的常数项吸收模型原点偏移与深度量化，斜率项覆盖越长越粗的弹体；值域 0.215 m（7.62mm）→ 0.51 m（155mm），与 §9.2 的相对分量取较大者。**这两个系数列入 §12 的 S2 验收项**：在近（约 20 m）与远（约 250 m）两个距离上按上表两种失败模式双向确认，而不是拍一个常量了事。

**当前内容包下这条陷阱并不触发**（依据见附录 C30）：投射物的模型索引由弹种注册键给出（`ModelIndex("projectile", <弹种键>)`），而仓库内没有任何 `projectile` 模型资源，`OModel` 因此取到空模型（0 骨骼）、渲染器的骨骼循环一次都不执行——投射物实体不写深度，画面上只有曳光线，而它显式不写深度（附录 C3）。口径折算的容差是给将来带模型的内容包留的余量，不是当前画面所必需。

曳光线本身**不写深度**（其 RenderType 显式设了 `COLOR_WRITE`，附录 C3），因此不构成干扰。

### 9.4 S3 —— 屏幕空间遮挡步进（可选）

从表面点 $P$ 向光心 $C$ 步进 $K$ 步（$K = 8 \sim 16$），每步投影到屏幕采深度比对：若某步的深度显著小于该步射线的前向深度，判定为被遮挡，按步数比例衰减贡献。

| 项 | 内容 |
| --- | --- |
| 收益 | 部分遮挡、以及**车体投出的影**（光源在车体一侧时，车体另一侧的地面处于阴影中） |
| 成本 | 仅对 $att$ 显著的像素执行；数量由光源屏幕投影面积界定，量级与一屏相当 |
| 必须处理 | 采样越界视为无遮挡；容差沿用 §9.2 的相对形式，否则近处表面会与自身比对而出现噪点（acne） |
| 与 S4 的关系 | S3 的观感收益高于 S4（§9.5） |

### 9.5 关于 S4（法线响应）

从深度导数重建法线需要多采 2 次深度并做 2 次重建，且在**深度不连续处（所有轮廓边缘）会产出无效法线**，需要额外的阈值拒绝逻辑，否则车体轮廓上会出现一圈噪点。加上镜面项在 LDR 下还需额外的削顶处理。

**因此 v1 不做 S4。** 判据是："看起来是光"这个观感主要来自**车体投出的影**与光斑的运动，而不是表面明暗梯度——所以 S3 的收益高于 S4。等 S1–S3 落地后若光斑仍读作"贴纸"而非"光"，再上 S4；那时要的其实是镜面高光扫过车体的动态，属另一套调参。

## 十、性能预算

| 项 | 量级 |
| --- | --- |
| 每像素固定成本 | 1 次颜色采样 + 1 次深度采样 + 视线方向重建（约 6 条指令） |
| 每像素每光源 | 剔除约 8 条指令；仅落入光锥的像素才做表面点重建与衰减（约 12 条指令 + 1 次 `sqrt`） |
| 满屏 1920×1080、$N = 16$ | 约 200 万像素 × 约 130 条指令 —— 后处理常规量级 |
| S2 额外成本 | 片元形态：每像素 × 光锥内光源各 1 次采样；CPU 形态：每光源 1 次、与像素数无关（§9.2） |
| S3 额外成本 | 仅对 $att$ 显著像素做 $K$ 次深度采样，量级与一屏相当 |
| 无活跃光源 | 0（pass 与深度副本都不提交） |

# 第四部分 · 落地

## 十一、参数与配置的边界

### 11.1 内容包 JSON：新增一个可选字段；颜色与照射半径都由既有字段决定

在 `ProjectileType.VisualProperties` 上扩展（新增字段为 `optionalFieldOf`，附录 C14）：

| 字段 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `tracer_light_intensity` | double | 1.0 | 强度倍率（再乘曳光自身的透明度与超时淡出，见 §4.4） |

**颜色不设字段**：取 `tracer_color`。光是曳光自己发出来的，曳光什么颜色、照亮什么颜色，分色是"以后真有需要再加"的可选字段（加它是零破坏的），现在就配一个只会多出"两处颜色不一致"的坑。

**强度单独成项**，因为它与 `tracer_alpha` 各自承担不同的量：透明度是曳光线自己的可见度，而强度是它投到周围表面的光。大口径弹种可以用较低的透明度（曳光线更暗、不刺眼）配更高的强度（闪光更强），两者在数据上正交。

**照射半径也不是字段，而是由弹种口径折算**：

$$R = 1.5\,\text{m} + 1\,\text{cm} \times \text{口径(mm)} \quad (\text{上限 } 4\,\text{m})$$

口径是"弹丸有多大"这件事在数据里的唯一载体（`external.caliber`，**单位 mm**；物理半径 = 口径/2000 m、触发体半径与风阻截面积都由它换算），因此照射半径也由它线性折算，不必再新增一个与口径高度相关、还容易配得不一致的字段：

| 弹种 | 口径 (mm) | 照射半径 R (m) |
| --- | --- | --- |
| 7.62mm / 7.92mm 曳光 | 7.62 / 7.92 | 1.58 |
| 20mm AP | 20 | 1.70 |
| 120mm APFSDS | 26（次口径弹芯） | 1.76 |
| 30mm AP / HE | 30 | 1.80 |
| 50mm PzGr39 / Sprgr38 | 50 | 2.00 |
| 9M133 导弹 / 155mm HE | 152 / 155 | 3.02 / 3.05 |

`R` 只决定"够得着多远"，不决定峰值亮度：衰减窗 $(1 - d/R)^2$ 在中心处恒为 1（§8.1）。基准 1.5 m 保证小口径曳光贴地、贴车飞过时有可见光斑，上限避免超大口径变成探照灯。

**发不发光的门禁是既有的 `tracer_alpha`，不是新字段**：只有 `tracer_alpha > 0` 的弹种会照亮（§4.3 第 1 条，与渲染器同一条判据）。要关掉某个弹种的光，把它的 `tracer_alpha` 配成 0 —— 那本来就会让曳光线消失。

**代价**：仓库内现有 11 个 `tracer_alpha > 0` 的弹种在本效果落地后立刻发光，内容包一条 JSON 都不需要改（7.92mm 发烟弹的 `tracer_alpha` 为 0，不发光）。代价是**没有"曳光可见但不发光"的开关**——那需要再加一个字段，落地时判断不值得。

### 11.2 与照明子系统的字段区分

`LightingSubsystemStaticAttr` 已有 `range`（默认 16，车灯照射范围）、`color`（默认白）、`intensity`（`clamp(0,1)`，默认 1）三个语义相近的字段，作用对象是**载具车灯**（由 `LightSourceRenderer` 在世界内画体积光锥）。本文的三个字段作用于**投射物曳光**、由屏幕空间后处理实现，两套配置互不影响：

| 对比项 | 照明子系统 | 本文 |
| --- | --- | --- |
| 载体 | 子系统 JSON | 投射物 `visual` 块 |
| 半径/范围含义 | 车灯照射范围（m） | 光源半径 $R$（m，决定衰减与剔除） |
| 强度取值 | `[0, 1]` | 倍率，可大于 1（全局倍率上限 2.0） |
| 实现 | 世界内加法几何（光锥） | 全屏后处理（screen 混合） |

内容包作者不应把两套字段互相抄用。

### 11.3 客户端配置（`MMClientConfig`）：只放玩家需要改的

| 配置项 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `TRACER_LIGHT_ENABLED` | bool | true | 总开关。关闭后 pass 不加载、不执行 |
| `TRACER_LIGHT_INTENSITY` | double | 1.0 | 全局强度倍率，0.0–2.0 |

命名与语义对齐既有的 `BLAST_DISTORTION_ENABLED` / `BLAST_DISTORTION_INTENSITY`。

### 11.4 代码常量（按所有权分两处）

**Java 侧**（`TracerLightEffect`）—— 数值策略，改它不需要重编着色器：

| 常量 | 符号 | 初值 | 单位 |
| --- | --- | --- | --- |
| `MAX_LIGHTS` | $N$ | 16 | — |
| `MIN_SCREEN_RADIUS_PX` | $r_{\min}$ | 4 | px |
| `LIGHT_RADIUS_BASE_M` | 半径常数项 | 1.5 | m |
| `LIGHT_RADIUS_PER_MM_M` | 半径斜率 | 0.01（每毫米口径 1 cm） | m/mm |
| `LIGHT_RADIUS_MAX_M` | 半径上限 | 4.0 | m |
| `OCCLUSION_TOL_BASE_M` | 容差常数项 | 0.20 | m |
| `OCCLUSION_TOL_PER_MM_M` | 容差斜率 | 0.002 | m/mm |
| `OCCLUSION_TOL_MAX_M` | 容差上限 | 1.0 | m |
| `OCCLUSION_TOL_REL` | 相对分量 | 0.002 | — |
| `FADE_TICKS` | 超时淡出起点 | 20（与曳光淡出包络一致） | tick |
| `CALIB_Z_NEAR` / `CALIB_Z_FAR` | — | 1 / 256 | m（附录 A.2 的两点标定深度） |

最大距离不设常量：取 `GameRenderer.getRenderDistance()`（§4.3 第 5 步），它随玩家的视距设置变化，写成常量反而会与视距设置脱节。

**着色器侧**（`tracer_light.fsh` 的 `const`）—— 形态学，改它等于改衰减曲线本身：

| 常量 | 符号 | 建议初值 | 单位 |
| --- | --- | --- | --- |
| `NEAR_Z` | — | 0.05 | m（原版近平面，与上面两个标定深度无关） |
| `LIGHT_STEPS` | $K$ | 12（仅 S3） | — |

**同名常量不允许同时存在于两处**：一个量只有一个所有者。判据是"改它要不要重编着色器"——要重编的留在 GLSL，不要的留在 Java 并作为 uniform 传入。`NEAR_Z` 与 `CALIB_Z_NEAR` 名字接近、含义无关（前者是剔除下界，后者是深度标定的采样点），不要合并。屏幕半径下限 `MIN_SCREEN_RADIUS_PX` 只在 Java 侧（着色器不需要它，§6.5），而近平面 `NEAR_Z` 只在着色器侧（CPU 侧只剔除 $z_c \le 0$，§4.3 第 3 条）。

两处都不进配置，是为了让观感随版本整体演进；需要暴露时再逐项上提。

# 附录 A · 投影、深度与视空间重建

## A.1 世界坐标 → 视空间

`AFTER_LEVEL` 阶段事件携带的 `getModelViewMatrix()` 是**纯旋转**（不含平移；附录 C10），因此换算分两步：

```text
P_view = R_view · (P_world − C_camera)
```

视空间中 $z$ 为负表示在相机前方。前向深度定义为 $z_c = -P_{view}.z$，取正值。

## A.2 深度线性化

不走"反投影求视空间距离"那条路（需要原版不对外暴露的近/远平面常量），而是用两个标量系数把非线性深度线性化：

$$d_{tex} = \frac{B}{z} - A \qquad\Longleftrightarrow\qquad z = \frac{B}{d_{tex} + A}$$

$A$、$B$ 由两个已知前向深度 $z_{\text{near}}$、$z_{\text{far}}$ 标定：先各投影一次得到 $d_1$、$d_2$，再反解。对任何"深度线性于 $1/z$"的透视投影约定都成立，**不假设深度方向**。

取 $z_{\text{near}} = 1$ m、$z_{\text{far}} = 256$ m。该区间覆盖了本效果所有有意义的衰减距离。

实现见 `BlastProjectionUtil.calibrateDepth`（附录 C5），本文直接复用。

## A.3 屏幕像素 → 视线方向

$$f = \lvert m_{11} \rvert \cdot \frac{H}{2}$$

$H$ 为画面高度（px），$m_{11}$ 取自投影矩阵。对像素 $(p_x, p_y)$：

$$\vec q = \left(\frac{p_x - W/2}{f},\ \frac{H/2 - p_y}{f}\right), \qquad \hat v = \frac{(q_x,\ q_y,\ -1)}{\sqrt{1 + \lvert \vec q \rvert^2}}$$

沿射线的点可参数化为 $t \cdot (q_x, q_y, -1)$，其前向深度恰为 $t$，因此表面点直接写成

$$P_{view} = z_{fwd} \cdot (q_x,\ q_y,\ -1)$$

取 $f$ 时用矩阵元素而不是由 FOV 现算，可以自动跟随望远镜、细雪视效、座舱视角等改变 FOV 的状态（附录 C6）。1080p、FOV 70° 下 $f \approx 770$ px。

## A.4 符号总表

| 符号 | 含义 | 单位 |
| --- | --- | --- |
| $C$ | 光源的视空间位置 | m |
| $R$ | 光源世界半径 | m |
| $P$ | 被照表面的视空间位置 | m |
| $d$ | $\lVert P - C \rVert$，光源到表面的世界距离 | m |
| $z_c$ | 光源的前向深度 $-C_z$ | m |
| $z_{fwd}$ | 本像素的前向深度，由深度纹理还原 | m |

| $r_{px}$ | 光源在屏幕上的投影半径 | px |

# 附录 B · 与爆炸波前折射的逐项对照

两者共用同一条深度通路与同一套标定公式，但几何与语义方向有多处相反。本附录集中列出，避免实现时互相照抄。

| 维度 | 爆炸波前折射 | 本文（曳光光照） |
| --- | --- | --- |
| 几何对象 | **球壳**（薄壳） | **实心球** |
| 核心判据 | 光源到**视线**的垂距落在波前附近（判据区间由壳层厚度参数给出） | 表面点到光源的**距离** $d < R$ |
| 为何如此 | 折射发生在波前所在的壳层，是一条视线掠过球壳 | 光照是体效应，球内任何表面都被照到 |
| 是否需要表面点 | 否，只需判断视线是否掠过壳层 | **是**，$d$ 必须用真实表面点算（§2.2） |
| 背景/远平面 | 场景没有几何体时不发生折射（判据里的背景分支即此意图） | **必须排除，不照亮**（§8.3） |

| 对画面颜色的处理 | 三通道独立采样做色散 | 逐通道 screen 混合，永不削顶（§8.2） |
| 典型并发数 | 个位数（爆炸事件稀疏） | 个位数到十余（§3.2），上界 $N = 16$ |
| 每帧成本与什么相关 | 与爆炸发数无关（摊在同一 pass） | 同左 |
| 每槽 uniform 宽度 | 4 float（视空间 xyz + 半径） | 4 float（同左） |
| 深度来源 | 链内声明的副本目标（`AFTER_LEVEL` 拷入） | 同左：各自声明、各自拷一份（见下方注） |
