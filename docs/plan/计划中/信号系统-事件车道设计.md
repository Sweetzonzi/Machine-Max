# 信号系统-事件车道设计

> **状态**：计划中。设计稿，待审阅；代码中尚无 `onSignalEvent`、`emitSignal`、`broadcastEvent`，也没有 `resolveTargets` 的布尔重载。
> **日期**：2026-11-24
> **范围**：装配体内的信号投递。本设计引入一条"只投递、不写槽"的事件车道，供玩家交互、子系统通知与后续机构使用。
> **源码依赖**：`common/mech/signal/`、`common/mech/part/AbstractPart`、`common/mech/subsystem/SubsystemController`、`common/mech/vehicle/interact/InteractBox`、Spark-Core 动画状态机（`AnimController#triggerEvent`）。

## 1. 现状：只有一条车道，语义是"当前值"

信号系统按"每个发送者一格的最新值"工作。这条车道由四个机制共同定义，缺一个就退化：

| 机制 | 位置 | 语义 |
| --- | --- | --- |
| 投递即写槽（键 = 发送者） | [`ISignalSender#deliverSignal`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L219-L226) | 频道里存的是"这个来源现在是多少" |
| 端口只在值变化时转发 | [`SignalPort#onSignalUpdated`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/SignalPort.java#L64-L121) | 相同值重复发送不产生投递 |
| 值进入部件/装配体的存储表 | [`AbstractPart#onSignalUpdated`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/AbstractPart.java#L1280-L1288)、[`SubsystemController#onSignalUpdated`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/SubsystemController.java#L377-L386) | Molang 的 `local.get` / `global.get` 读它 |
| 清空靠写"无值标记" | [`ISignalSender#resetSignalOutputs`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L161-L170) | `EmptySignal` 表示"来源已连接、当前无值" |

"发生了一次"在这条车道上没有位置。代码里因此有两处绕开它的写法：

1. **交互区的 `global` 频道**：`InteractBox#interact` 不经总线，直接调 `IPartAssembly#broadcastInteractionEvent`，由装配体逐零件调 `triggerInteractionEvent`（[`InteractBox`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/interact/InteractBox.java#L196-L210)、[`VehicleCore#broadcastInteractionEvent`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java#L1694-L1698)）。这是为"一次性通知"专门开的一条方法通道。
2. **弹种切换**：`ammo_switch` 的接收者消费后把该来源的槽值写成 `EmptySignal`（[`consumeAmmoSwitch`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L1150-L1171)），用"槽里不再是可识别的指令"模拟边沿；`EmptySignal` 的语义是"来源仍在、当前没有值"（见 §7）。

结论：系统缺一个"不写槽的投递"原语。把事件补成一条车道，这两处绕行可以收回同一套语义。

## 2. 目标与非目标

**目标**

1. 一次性通知走一条与值车道并行的车道，共用同一张线网（首跳表、端口转译、总线分发、接受条件）。
2. 事件不写槽、不进 `signalStorage`、不参与 Molang、不参与排序、不持久化、不去重。
3. 任何 `ISignalReceiver` 都能接收事件；任何 `ISignalSender` 都能发出事件。接收者不必是总线。
4. 交互区只负责"发出"：每条频道按投递点解析结果决定是否 emit，没有"动画事件专用"的分支。
5. 跨零件的事件投递沿实际接线走：拆件即断线，与值车道同一条约束。
6. 发现能力回答"这条事件频道有没有人去接"，让交互区的激活判据与服务端复核一致。

**非目标**

- 不引入队列、重放、延迟投递、优先级或持久化。错过就是错过，这是事件的语义。
- 不引入 `CONSUME`。事件是广播式投递，多个接收者都要收到；"只能被一个逻辑处理"属于仲裁，归值车道的优先级与三键排序。
- 不引入子系统的事件频道白名单字段。端口转发与总线分发沿用既有的 `getAcceptedChannels()`，声明一次即可。
- 不改动值车道的任何行为：去重、`EmptySignal`、`resetSignalOutputs`、优先级、Molang 存储保持原样。
- 不在本期做服务端→客户端的事件镜像（见 §9 阶段 3 与 [`动画系统-事件触发动画设计`](../进行中/动画系统-事件触发动画设计.md#L164-L169) §6.2 的待办）。

## 3. 车道模型

| | 值车道 | 事件车道 |
| --- | --- | --- |
| 写入 | 槽 + 存储表 | 什么都不写 |
| 去重 | 值不变不转发 | 每次都投递 |
| 读取方 | 子系统读槽、Molang 读存储 | 接收者的回调 |
| 时机 | "当前是多少" | "刚刚发生了一次" |
| 消费 | `CONSUME` / 释放标记 | 无消费、无释放 |
| 典型频道 | `engine_speed`、`crew_driver_move`、`gear` | `interact_hood`、将来的一次性动作指令 |

线网上的节点分三种角色：

| 角色 | 类型 | 事件车道里的职责 |
| --- | --- | --- |
| 传输 | `SignalPort` | 按对侧 `signal_translations` / `signal_targets` 转发，无条件、不看值变没变；自身不是投递点 |
| 传输 + 接收者 | `ISignalBus`（`AbstractPart`、`SubsystemController`） | 自己收，再按接受条件分发给订阅者 |
| 接收者 | 叶子（`AbstractSubsystem`，以及将来任何实现） | 收到就收；默认空实现 |

投递规则一句话：**沿线路走，凡是接收者都收；传输节点额外转发。**

## 4. 接口与投递规则

### 4.1 `ISignalReceiver#onSignalEvent`

```java
/**
 * 事件到达。与 {@link #onSignalUpdated} 并列：一个说"值变了"，一个说"发生了一次"。
 * 不写槽、不返回结果（事件没有消费语义）。
 * <p>调用线程是发送方的线程；触发动画、推进状态机的实现只应在主线程被投递。
 */
default void onSignalEvent(String channelName, ISignalSender sender, Object payload) {}
```

挂在 `ISignalReceiver` 上而不是新接口：它和 `onSignalUpdated` 是同一批接收者的两种输入，默认空实现让"不关心事件"的实现零成本。

### 4.2 `ISignalSender#emitSignal`

三个重载，与 `sendSignalToTarget` / `sendSignalToAllTargets` 并列：

```java
default void emitSignal(String channel, Object payload)                         // 该频道的全部首跳
default void emitSignal(String channel, String targetName, Object payload)      // 该频道的某个首跳
default void emitSignal(String channel, ISignalReceiver target, Object payload) // 已解析的接收者实例
```

重访判定与按角色分派放在 `signal` 包内的包私有类 `EventDispatch`（§4.6）。接口私有方法在子接口与实现类里都不可见，而 `ISignalBus#broadcastEvent` 与 `SignalPort#onSignalEvent` 都需要这条分派，所以它不能放在 `ISignalSender` 内部：

```java
// signal 包内，包私有
final class EventDispatch {
    static void dispatch(ISignalReceiver target, String channel,
                         ISignalSender sender, Object payload) {
        if (!current().visit(target, channel)) return;      // 同一 (接收者, 频道) 只投一次
        if (target instanceof SignalPort port)      port.onSignalEvent(channel, sender, payload);
        else if (target instanceof ISignalBus bus)  bus.broadcastEvent(channel, sender, payload);
        else                                        target.onSignalEvent(channel, sender, payload);
    }
}
```

### 4.3 `ISignalBus#broadcastEvent`

```java
default void broadcastEvent(String channel, ISignalSender sender, Object payload) {
    onSignalEvent(channel, sender, payload);   // 总线自身已由 EventDispatch.dispatch 判重
    for (ISignalReceiver sub : getAllSubscribers()) {
        if (sub.acceptAllBroadcastInput() || sub.getAcceptedChannels().contains(channel)) {
            EventDispatch.dispatch(sub, channel, sender, payload);
        }
    }
}
```

两个覆写：

- `AbstractPart#onSignalEvent` → `triggerInteractionEvent(channelName)`：到达频道就是动画状态机的事件名，本件控制器按 `event.<频道>` 转移。
- `SubsystemController#onSignalEvent` → `assembly.broadcastInteractionEvent(channelName)`：把事件交给装配体广播给全部零件。`SubsystemController` 目前只持有 `level`（[L54-L60](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/SubsystemController.java#L54-L60)），需要补一个可空的 `IPartAssembly` 引用；独立构造的控制器（无装配体）保持只向订阅者分发。

`IPartAssembly#broadcastInteractionEvent` 因此从"交互区的第二套投递路径"变成装配体对 `global` 的实现，接口本身保留，其他宿主可以有自己的实现。

这条零件扇出由装配体自己完成：它逐个零件调 `triggerInteractionEvent`，不经线网，也不计入会话的重访判定。因此 `global` 的发现结果只包含控制器与它的订阅者，零件不在其中——§5 的契约据此限定为"线网上的投递点"。同一条频道同时指向 `local` 与 `global` 时，同一零件会收到两次事件（一次经线网、一次经装配体广播），这种写法由 `checkContent` 在内容层禁止（§9 阶段 2）。

### 4.4 `SignalPort#onSignalEvent`

按对侧端口的 `signal_translations` 得到到达频道，再查对侧 `signal_targets`；对每个接收者先按值车道的同一判据 `acceptAllRoutingInput() || getAcceptedChannels().contains(到达频道)` 过滤，再经 `EventDispatch.dispatch` 继续（含对侧总线）。与值车道一致：**不做值比较**，`signal_targets` 里没有该频道时静默丢弃。过滤这一步不能省——省掉就会把事件送到没有声明该频道的叶子，发现结果与投递结果随即变成两套答案（内容检查见 §9 阶段 2）。

### 4.5 与值车道的关系

- 事件不写 `getSignalInputChannels()`、不写 `getSignalStorage()`，因此不影响 `local.get` / `global.get`。
- 事件不参与 `resetSignalOutputs`：清空值是清空槽，事件没有槽可清。
- 端口对事件的转发规则与对值的转发规则并存：同一条频道可以既有值又有事件，两个方向互不干扰（`SignalPort` 的两张表复用）。
- `Signal` 子类与 `EmptySignal` 都不需要参与事件车道；负载用 `Object`，纯触发传 `null`。

### 4.6 环路与线程

值车道靠"值不变就不转发"天然终止。事件车道用**重访检测**终止：一次顶层 emit 打开一个投递会话，会话记录已投递过的 `(接收者, 到达频道)` 对，重复到达时跳过投递。

会话挂在 `ThreadLocal` 上，按线程常驻、每次顶层 emit 清空：`begin()` 把线程内深度加一，深度由 0 变 1 时清表；`end()` 在 `finally` 里减一，归零时再清一次；容器本身留在线程上复用，因此每次 emit 只做清表、不新建映射。嵌套 emit（接收者在回调里发出另一条频道）深度大于 1，共用同一份 visited：另一条频道照常投递，把同一频道发回上游则被抑制。`current()` 在会话不存在时按需创建，`broadcastEvent` 这类入口即使没有外层 emit 也不会拿到 null。回调抛异常时 `finally` 仍会减深度，下一次顶层 emit 从空表开始，脏数据不跨 emit 存活。

`visited` 的上界是一次 emit 触及的 `接收者 × 到达频道`。到达频道来自翻译表（有限静态映射）与调用方传入的字符串，一条频道能派生出的频道名因此有限，任何环路都会在有限步内重复同一个 `(接收者, 频道)` 对，所以不需要额外的深度上限。被抑制的重访默认静默，只在 `debug` 级留一条。

线程：车道不做线程检查，回调在调用方线程上同步执行。两条限制来自使用方式而不是检查：

- **按名 emit 限主线程**：首跳表由主线程用 `clear()` + `putAll()` 整体替换，物理线程按名读取会读到空表或半张表——与值车道"物理步不按名发送"是同一条纪律。
- **物理步只按实例发给不触碰状态机的接收者**（例如驱动器）。发往 Part 或装配体总线会推进动画状态机，与主线程的 `AnimController#tick` 竞态。

真出现竞态时，在 `AbstractPart#onSignalEvent` 加一次主线程断言，比在车道上逐次判断更窄。

```java
// signal 包内，包私有；键语义与 resolveSignalLine 的 visited 相同
final class EventDispatch {
    private static final ThreadLocal<EventDispatch> CURRENT = new ThreadLocal<>();
    private final Map<ISignalReceiver, Set<String>> visited = new IdentityHashMap<>();
    private int depth;

    static EventDispatch current() { /* 取不到时创建并挂到 CURRENT */ }

    /** 首次到达返回 true；同一 (接收者, 频道) 的第二次到达返回 false。 */
    boolean visit(ISignalReceiver receiver, String channel) {
        return visited.computeIfAbsent(receiver, k -> new HashSet<>(2)).add(channel);
    }
    // begin(): depth++，由 0 变 1 时 visited.clear()
    // end():   depth--，归零时 visited.clear()；调用点包在 try/finally 里
}
```

## 5. 发现：`resolveTargets` 的布尔轴

两条车道共用一套遍历（[`resolveSignalLine`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L90-L120)），差别只有一处：**总线本身算不算终端**。

| 入口 | 语义 |
| --- | --- |
| `resolveTargets(channel)` | 叶子终端，现有语义 |
| `resolveTargets(channel, boolean includeBuses)` | `false` 等价于上一行；`true` 为投递点 |
| `resolveTargets(channel, List<String> firstHopNames)` | 叶子终端 + 首跳白名单，现有语义 |
| `resolveTargets(channel, List<String> firstHopNames, boolean includeBuses)` | 白名单过滤后取投递点 |

- **默认行为是仅叶节点**：现有调用点（驾驶、火控、视点、弹药发现、交互区、GameTest）与既有签名都按"终端 = 执行者"使用，`includeBuses` 缺省为 `false`，它们不受影响。
- 四个入口都是对同一个私有遍历的委托，没有第二份遍历逻辑。白名单轴与布尔轴正交；第四档（白名单 + 投递点）目前没有调用方，随第一个"按控制组查投递点"的需求加入——它只是一段三行委托。
- 重载解析没有歧义：`boolean` 是原始类型，`null` 第二参只匹配 `List` 重载。
- 布尔在调用点不可读，调用方用一个具名局部量或一行注释解决；不为可读性再包一层方法。

写进 Javadoc 的契约：

> `includeBuses = false`：只返回叶子接收者（执行者 / 发现目标），总线只作为分发点被穿过。
> `includeBuses = true`：线网上的投递点，即叶子 + 途经的总线实例本身；端口永远不出现在结果里。两者的差集恰好是总线实例。装配体经 `broadcastInteractionEvent` 做的那次零件扇出不在线网上，也不在发现结果里（§4.3）。

### 现状缺口：`global` 不接受路由输入

`SubsystemController` 没有覆写 `acceptAllRoutingInput()`（默认 `false`），也没有声明接受频道；而端口转发要求 `acceptAllRoutingInput() || getAcceptedChannels().contains(channel)`（[`SignalPort`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/SignalPort.java#L86-L89)）。结果是**经连接点路由到 `global` 的频道今天会被静默丢掉**，只有直接写在首跳表里的 `global` 才可达。`AbstractPart#acceptAllRoutingInput` 返回 `true`（[L1332-L1335](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/AbstractPart.java#L1332-L1335)），两总线应当一致：**总线本身一律接受路由输入，频道筛选交给订阅者**。

这条修正同时让事件车道的 `global` 目标在跨零件时可达，并且改变只读发现：经端口到达 `global` 的频道从"发现不到"变成"展开整车订阅者"。现有内容里没有任何连接点把频道指向 `global`，所以这是新增能力；`AbstractSubsystem#resolveViewpoints`、`AbstractControllableSubsystem` 的控制器发现，以及 `LauncherSubsystem` / `AmmoLoaderSubsystem` / `LoaderRoster` 的弹药发现要随 P2 一起回归。

## 6. 交互区改造

### 6.1 为什么盖板的事件必须跨零件

`JointDriverSubsystem` 在驱动器自己所属的零件上采样本零件的动画姿态：`getLocatorBoneChain` 读本零件模型，`hasAnimationContribution` 要求本零件有覆盖该骨骼链的正在播放的动画，否则 `releaseDrive()`（[L60-L71](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/JointDriverSubsystem.java#L60-L71)、[L116-L140](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/JointDriverSubsystem.java#L116-L140)）。桑塔纳的铰链骨骼 `HoodHinge` / `TrunkHinge` 属于车体，盖板是独立零件，所以点击盖板产生的事件必须到达**车体**的状态机；四扇车门的两端都在车体上，`local` 就够。

一次性事件因此需要"沿接线到达另一个零件"的能力，而不是"广播给全车"或"只能发给自己"。

### 6.2 一次投递点遍历，分成两档

`InteractBox#setTargetFromNames` 重建首跳表后，对每条频道做一次 `resolveTargets(channel, true)`：

- 结果是总线实例 → 这条频道是事件线（点击时 `emitSignal`，并按 §6.3 计入激活判据）；
- 结果是子系统 → 现有逻辑不变（`isInteractable()` 决定能否点，`onInteract` 按声明序尝试，`CONSUME` 结束遍历）。

只对"到达总线"的频道发事件：子系统目标继续走 `onInteract`，不给纯值线附加无意义的投递。

交互区的表现状态只有首跳表与解析结果：`local` 与 `global` 都是首跳表里的条目，构造期不做动画事件分桶。

### 6.3 激活判据

`canInteract()`：门控成立，且

- 至少一条频道到达总线（事件线），或
- 至少一个终端子系统此刻 `isInteractable()`。

这与现状等价：现状是"有 `local`/`global` 动画目标，或任一终端子系统可交互"。差别的来源是事件线现在可以经连接点到达，判据读的是解析结果而不是配置里的字面量。

只作为子系统事件监听者的线不会点亮提示——交互区的点击语义对子系统一直是 `onInteract`。若将来真需要"只靠子系统事件点亮提示"，给交互区加一个显式的 `event_channels` 字段，不为一个尚未出现的需求先造。

### 6.4 内容写法

现状（桑塔纳车体，[hull](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_hull.json#L112-L186)、[hood](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_hood.json#L39-L49)）：

| 部位 | 交互区所在零件 | 铰链骨骼所在零件 | 频道目标 |
| --- | --- | --- | --- |
| 四扇车门 | 车体 | 车体 | `local` |
| 引擎盖、后备箱盖 | 盖板 | 车体 | `global` |

四门与两盖板在事件车道落地后行为不变。两者的频道目标都可以写作"经铰链连接点 + 对侧 `local`"：语义比 `global` 精确，事件沿实际接线走，不惊动无关零件。

同规格重复件的独立交互（一个门变体、N 个实例），用连接点承载实例差异：门侧一个共享频道，车体侧每个铰链各写一条转译与目标。

```jsonc
// 门零件（一个变体，N 个实例共用）
"interact_boxes": { "interact.machine_max.door": {
  "signal_targets": { "interact_door": ["connector.machine_max.axis"] } } }

// 车体（一个变体，每个铰链一段）
"connector.machine_max.left_front_door_axis": {
  "signal_translations": { "interact_door": "interact_door_lf" },
  "signal_targets": { "interact_door_lf": ["local"] } }
```

`signal_translations` 与 `signal_targets` 是连接点条目的顶层字段（[`ConnectorAttr`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/connector/ConnectorAttr.java#L99-L115)），每个连接点各写一份，不需要变体副本，也不需要 `overwrite`。

## 7. `EmptySignal` 的定位

`EmptySignal` 属于值车道：**"这个来源已连接、当前无值"**。座椅无人时发给车控的空信号让该来源的槽从"按住"回到"已释放"，单例与按类型相等的判断在这里是对的——释放之后不该反复转发。

事件车道不产生也不消费它：没有事件就不 emit，负载要空就传 `null`。因此两条车道各有一个"空"，互不重叠：

| | 值车道 | 事件车道 |
| --- | --- | --- |
| 空 | `EmptySignal`：有连接、无值 | 不存在这个概念，没发生就没有投递 |
| 重复 | 相同值不转发 | 每次 emit 都投递 |

文档口径需要一处订正：`signal/AGENTS.md` 的「空信号触发」一条把 `EmptySignal` 描述为"仅用于触发性通知（如开火）"，而开火是按住语义（值车道），一次性指令才走事件车道；同一文件的「执行器读输入槽」一条又说它"表示该来源已释放"。正确的表述是"无值标记：来源仍在、当前没有值"。

## 10. 风险与待定

1. **线程**：车道不做线程检查，回调在调用方线程上同步执行（见 §4.6）。物理步来源的事件只发给不触碰状态机的接收者；出现竞态时把断言加在 `AbstractPart#onSignalEvent`。
2. **环路**：由重访检测终止，键是 `(接收者, 到达频道)`，与只读发现的 visited 同构；菱形接线因此只投递一次。抑制静默、`debug` 级留痕。
3. **总线接受规则变更**：`SubsystemController#acceptAllRoutingInput` 取值 `true` 后，经端口到达该控制器的任意频道都会写入 `global` 存储并向订阅者分发（订阅者仍按自己的频道表筛选）。影响面需要一次回归，尤其是既有的连接点接线。
4. **交互区的子系统事件**：本期点击对子系统只有 `onInteract`。需要子系统从点击里拿到一次性事件时，再加 `event_channels` 字段。
5. **客户端**：事件目前只在服务端产生（与现状一致）。动画状态机的状态在客户端独立推进，盖板这类只有定位器骨骼的动画不影响画面；可见动画的事件镜像属于 P3。
6. **事件频率**：事件车道面向离散时刻（点击、装填阶段切换、开关到位）。逐 tick 的量仍走值车道，避免每个订阅者每 tick 一次回调。
7. **JS hook 契约**：`resolveTargets` 默认只返回叶子，脚本侧行为不变；`includeBuses = true` 作为新入口，既有签名不变。
