# 子系统：下游类型注册开放与内置迁移计划

> 状态：已否决，未实施。本文是 A 路线：保留两张 NeoForge Codec 注册表，MM 与下游各自用 DeferredRegister 向同一对公开 Key 登记。实际落地的方案是同目录 `../已实现/子系统-下游类型注册开放与内置迁移计划-静态表方案.md` 的静态表路线；逐条对比、否决理由与"何时应回到 A"的条件见该文附录 A。
> 版本：v2，审阅后设计草案；日期：2026-11-14。源码核对基线：`444f200c`，正文源码坐标为活引用。
> 目标：MM 的全部可用内置子系统与下游模组使用同一条公开注册路径，下游可以声明自己的子系统类型、属性与实现。

## 1. 范围与交付原则

1. 使用 NeoForge 的 `DeferredRegister`、`DeferredHolder` 与现有自定义注册表。
2. 保留静态定义、安装属性两个 Codec 注册表；类型身份使用带命名空间的 `ResourceLocation`。
3. 全部内置登记迁入公开路径。迁移以真实内置实现及内容包验收，不建设独立示例模组或演示子系统。
4. 保留属性对象的 `createSubsystem(owner,name)` 工厂，以及子系统的信号、能源、伤害、同步、保存和生命周期机制。
5. 内置内容包的类型 ID、型号引用、安装字段和运行行为保持兼容；Java API 的签名变化要求依赖模组重新编译。

本计划不包含轮式／履带动力学、角色代理施力、执行后端切换、汽车控制器的能力接口化、全新推进器实现或子系统线程调度调整。这些功能可以消费本计划开放的注册接口，各自形成独立实现范围。MM 的注册能力验收不等待 ARMS-Core 的轮驱实现。

## 3. 类型、型号与实例身份

| 身份 | 含义 | 目标形态 |
| --- | --- | --- |
| 类型 ID | 一对静态／安装属性 Codec 所代表的子系统种类 | 如 `machine_max:wheel_driver`、`arms_core:character_wheel` |
| 型号 ID | 内容包提供的一份静态参数定义 | 由安装属性的 definition 引用，与类型 ID 独立 |
| 实例名称 | 某个 SubPart 上一项子系统的名字 | 用于已有信号寻址、状态保存和运行期查询 |

**类型身份只从 Codec 登记键派生。** 两个属性基类分别提供目标方法 `public final ResourceLocation getType()`：安装属性在安装 Codec Registry 中对 `codec()` 做 getKey，静态属性在静态 Codec Registry 中对 `codec()` 做 getKey。返回值就是该条目的命名空间 ID；查不到登记实例时报告未注册 Codec 诊断。

具体属性类只声明自己的单例 CODEC，不覆盖 getType，也不另写类型身份常量。静态／安装属性的配对比较两个派生 ID 的值相等；因此下游无法靠覆写 getType 让不同登记 ID 冒充同一类型。这不需要第三张注册表。它要求注册完成后才构造／解码属性，时序见 §4.3。

当前 SubsystemTypes 枚举的各个 getType 覆写从具体属性类中移出。若实施时有真实消费者需要内置 ID 便捷常量，可保留常量集合；它只表达登记名，不能成为第二份身份声明或白名单。常量取值遵守 §5，不以枚举 ordinal、Java 类名或无命名空间字符串表示类型。

注册表的条目是 Codec 单例，运行期子系统实例由安装属性工厂创建。DeferredHolder 持有注册条目，不持有某个机体的子系统实例。

## 4. NeoForge 注册接线

### 4.1 公开注册表 Key 与创建责任

两个注册表 ID 固定为：

```text
machine_max:subsystem_attr_codec
machine_max:subsystem_static_attr_codec
```

MM 公开对应的 `ResourceKey<Registry<MapCodec<…>>>`。Key 放在无事件总线依赖、无注册表创建副作用的常量容器中；建议落点为 `common/registry/MMRegistryKeys`，这是待实施的文件，不是现存声明。

下游只读取 Key 即可声明自己的 DeferredRegister，不必提前求取 Registry 实例，也不必触发 S8 的创建流程。实际 Registry 由 MM 创建一次，沿用 S1 的现有创建接线；下游不调用 makeRegistry 或重复登记同一张表。实现时检查静态初始化链，而非依赖两个模组构造器的偶然执行顺序。

### 4.2 内置与下游使用同一登记机制

MM 为两个 Key 分别声明 DeferredRegister，命名空间为 `machine_max`；下游针对相同 Key 声明 DeferredRegister，命名空间为自己的 mod ID。各 DeferredRegister 在所属模组构造器挂到自己的 mod event bus。

登记条目使用 supplier 提供具体类已有的 CODEC。所有 24 组内置类型走这条路径，双方登记同一类型 ID。条目句柄可以使用 DeferredHolder，具体属性类的 `codec()` 直接返回该已登记的 CODEC 单例。

**实例同一性是强制契约：登记 supplier 交出的 MapCodec 与属性 codec() 返回的 MapCodec 必须是同一个对象。** codec() 不能每次创建一个等价 Codec；同一个 Registry 也不能通过将同一实例重复登记为不同 ID 来表达类型别名。S12 的反查以及 §3 的类型派生都依赖这个契约。

两类通用 dispatch 在选中具体 Codec 后，对解码得到的属性核对 `attr.codec() == selectedCodec`，失败即给出内容诊断。这样下游 Codec 不能把一种登记 ID 解码成报告另一种 Codec 的对象，再借型号配对通过校验。该检查位于两类属性的解码边界，使用已有 Codec 组合操作，不将临时校验适配器登记成新类型。

DeferredRegister 的条目工厂文档给出通用的创建建议，本计划的条目是具备固定身份的 Codec 单例，不能据此将登记与 codec() 分别写成独立的新建表达式。优先沿用各类 static final CODEC；若通过 DeferredHolder 获取实例，属性只在注册完成后返回该 holder 对应的同一个实例。

MMCodecs 的目标职责是持有内置 DeferredRegister 与条目声明，并安装总线监听；S2 中世界效果、制导 Codec 的现有登记保持独立。避免同一子系统条目同时由 RegisterEvent 和 DeferredRegister 登记。

本计划不提供 MM 专属注册事件、成对注册包装器、第三张类型描述符注册表或按宿主替换实现的全局工厂表。两个 DeferredRegister 已能完成所需登记；配对关系由 ID 与加载校验保证。

### 4.3 初始化与同步边界

1. 声明期只创建 Key、DeferredRegister 和条目 supplier；依赖条目的读取在注册完成后执行。
2. 静态初始化期间不调用 DeferredHolder.get() 去完成另一张表的登记、查找型号或构造子系统实例。
3. `MMDataRegistries` 的两个通用 dispatch Codec 使用对应 Registry 查找条目，不枚举内置类型作为白名单。
4. 保留两个 Registry 的 `sync(true)`。这里同步的是注册条目映射，不会把下游 Java 类或 Codec 实现发送给客户端；两端需要安装相容的依赖模组。
5. 未注册类型必须在解码／连接检查中失败，不能静默当成 BASIC、忽略该子系统或清空其安装数据。

工具依据为 [NeoForge 1.21.1 Registries](https://docs.neoforged.net/docs/1.21.1/concepts/registries/)。本机版本 NeoForge 21.1.219 的源码包 `build/moddev/artifacts/neoforge-21.1.219-sources.jar` 已核对 DeferredRegister 的按 Key 创建、条目登记、mod event bus 安装及 makeRegistry API；本计划选用按 Key 创建 DeferredRegister，保留 Registry 创建方。

## 6. 型号绑定、诊断与实例创建

### 6.1 解码构造期完成基础绑定

S4、S11 已经在安装属性构造器中调用 getStaticAttr。型号缺失／类型不匹配可能在 JSON 解码时发生，不是只在出车或物理步暴露。本计划保留这种立即绑定方式，将基础校验明确落在 `AbstractSubsystemAttr.getStaticAttr()`，且使用 PackContentException：

```text
通用 dispatch 按已注册类型选择安装 Codec
  → 安装属性的解码构造器调用 getStaticAttr
  → 定位 definition 对应的静态定义
  → 两侧按 §3 从各自已登记 Codec 派生类型 ID
  → 按 ID 值相等校验，失败报告内容错误
  → 返回已确认类型的静态定义，具体属性执行所需的类型读取
```

getStaticAttr 保留当前两端定义来源的选择口径，是解码与直接 Java 构造共用的基础绑定边界。型号与类型在此立即确认，运行期使用构造时绑定的结果。型号缺失、类型错误及未注册 Codec 使用结构化内容诊断，不抛裸 NPE／ClassCastException，也不回退成 BASIC。

### 6.2 几何校验与发布链

几何引用保持以下已有链路：`SubPartAttr.validate` → `AbstractSubsystemAttr.validate(variant,subPartName,subsystemName)` 的具体实现，外层由 `VariantAttr.validate`、`AbstractPartType.validate` 与 `PartDefinitions.validateAndPublish` 调度。定位器、连接点与需要完整模型的检查继续在这里完成；实现坐标见 S11。

不能仅把型号／类型检查放进空的基类 validate，因为现存多个覆盖方法不调用 super，且构造器已在更早阶段读取静态定义。若未来另作延迟绑定设计，必须同步处理全部构造器读取、字段初始化和覆盖方法；该改造不属于本计划。

PackCodec 在解码阶段保留结构化内容错误，PartDefinitions 在发布校验阶段保留内容错误组件；源码为 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/pack/diagnostic/PackCodec.kt#read`、S11 的发布入口。两条路径均需关联实际内容文件，不能用 Java 类名替代类型 ID。

### 6.3 诊断与翻译交付

| 失败 | 明确落点 | 消息必需信息 |
| --- | --- | --- |
| 型号缺失 | getStaticAttr 的 definition 查找 | definition ID、期望类型 ID |
| 型号类型不匹配 | getStaticAttr 的两侧类型 ID 比较，位于强转前 | definition ID、期望与实际类型 ID |
| 未知 JSON 类型 ID | 两个通用 dispatch 的类型读取／注册表查找边界，位于具体属性构造前 | 未知 ID、静态／安装槽位 |
| codec() 返回未登记实例 | 基类 getType 的反查失败；编码路径也须保留可诊断失败 | 静态／安装槽位、Codec 实例未登记的原因与修复提示；无可反查 ID 时不得伪造 ID |

在 `src/main/java/io/github/sweetzonzi/machine_max/datagen/MMLanguageRegistry.java#MMLanguageRegistry` 交付上述 MM 诊断需要的键及 zh_cn／en_us 文案，模板可参考同文件 `#ERROR_PART_SUBSYSTEM_LOCATOR_NOT_FOUND`。未知类型目前经 PackCodec／DFU 变成内容错误，很多 DFU 消息仍是 literal；本计划若承诺 MM 的未知类型翻译，须在表中指明的类型查找边界产生结构化消息，不能通过解析 DFU 英文字符串或在 getStaticAttr 中处理尚未创建对象的错误。

消息组件使用既有 PackContentException 和加载器的文件关联机制；不另建诊断包装类型。实现验收覆盖解码与直接 Java 构造，错误不会被降级为警告或静默剔除。

### 6.4 实例与生命周期

自定义子系统可以继承 AbstractSubsystem／BasicSubsystem，并通过现有能力接口参与供能或信号。宿主、生命周期调用和保存格式服从 S6、S7；安装属性经 createSubsystem(owner,name) 创建实例，无需在 MM 中逐种增加工厂分支。汽车控制器识别具体轮驱类的限制见 S10，该业务兼容性不由注册成功隐式保证。

## 7. 兼容与内容工具

### 7.1 内容和存档

所有已登记类型 ID、definition 型号引用、实例名称及类型专属字段保持。当前内容包无需为本次注册迁移批量改 JSON，存档恢复也按相同 ID 选择属性 Codec。

注册顺序不构成持久身份；存档／配置使用命名空间 ID，不能把 DeferredRegister 条目顺序或 Registry 整数 ID 当作永久类型编号。2026-11-14 源码盘点没有发现 SubsystemTypes 的 switch／ordinal 消费者，直接类型比较只有 S4 一处；getType 的声明、诊断输出与具体覆写均须随基类调整。实施基线检查应复核这个结论，而不是把 enum 序列当成兼容数据。

### 7.2 Java API 与版本

`getType()` 的目标公共契约是基类 final ResourceLocation 派生方法；具体属性实现 codec 与工厂，类型身份由基类读取。这属于 Java 扩展 API 变更。下游需按发布版本重新编译并声明相应最低 MM 版本。公共文档说明 Key、mod event bus、Codec 实例身份、两类 Codec 的配对要求以及工厂入口。

本计划没有载荷字段改动；是否提升网络协议号按实施时实际产生的网络变化判定，不能仅因 Java 方法签名变化推导出协议字段变化。两端模组与注册项兼容性按 NeoForge 注册同步规则检查。

### 7.3 schema 与文档

基准 schema 位于 `src/main/resources/spark_modules/Machine-Max_Builtin/machine_max/docs/zh_cn/schemas/subsystem/`。当前两份顶层 schema 的 type 枚举各 21 项，缺少已登记的 joint_driver、scriptable、battery；各自 if／then 仅 20 项，basic 已在枚举中但没有接入已存在的 basic 具体 schema。不能把枚举接受、字段分派与 §5 的 24 组登记混为一谈。

目标顶层 type 接受以下两种情况，同时保留逐内置 ID 的 if／then 字段分派：

1. §5 的 24 个完整 machine_max 类型 ID，使用明确枚举校验。
2. 具有合法命名空间与路径、且命名空间不是 machine_max 的外部 ID；由下游 schema 约束其专属字段。

可实现为 type 字符串上的 anyOf：24 项 enum，或匹配 `^(?!machine_max:)[a-z0-9_.-]+:[a-z0-9/._-]+$` 的外部 ID。不能只在保留闭合 21 项 enum 的前提下增加外部分派，也不能放宽成任意 machine_max 前缀字符串；拼错的内置 ID 必须失败。

为 joint_driver、scriptable、battery 补齐静态／安装两侧共六份具体 schema，并把现有 basic_static_attr.schema.json、basic_dynamic_attr.schema.json 接入顶层分派，最终字段分派覆盖到 24 项。这六份 WIP schema 尚待实施，字段约束以已有 CODEC 为准，schema 完整不承诺玩法功能完整。内置具体字段的坏配置不得被宽松外部分支接受；编辑器接受外部 ID 也不表示运行时可以缺少已注册 Codec。

schema 修改按根 AGENTS.md“内容包 schema 同步”执行 syncSchemas／checkSchemas。根 AGENTS 与 subsystem 目录 AGENTS 的计数应区分当前 25 个枚举常量（含占位）、24 组登记及 21 项 schema；实施后的指引按注册条目与 schema 覆盖陈述，不把抽象基类文件数当作类型数量。

配套更新上述两份 AGENTS 的子系统扩展指引、`docs/wiki/5-内容包制作教程/5.5-子系统定义.md` 的类型来源和 WIP 边界。公共接入说明可沿用 `docs/部件公共基础接入.md`“扩展模组的注册和构造”的组织方式，但须给出子系统自己的明确契约。

### 7.4 下游内容资源进入加载器

S13 的 SparkPackResourceLoader 遍历已加载 mod，为各自 jar 的 spark_modules 目录执行自动打包。下游可以按该现有机制分发型号定义与部件内容，目录需要合法 meta.json，是否打包还受 enable_auto_pack 与相关事件控制；不另建 ARMS 专用内容加载器。

SubsystemModule.read 用 namespace 与文件名（去掉 .json）生成型号 ID，中间分类目录不参与身份。下游使用自己的命名空间避免跨模组冲突；同一命名空间中不同子目录的同名文件仍会冲突，不能把移动目录当作隔离型号名的方法。代码类型注册与型号资源加载是两条独立步骤，前者不能被内容包 Java 类声明代替。

## 9. 验收边界

- 内置登记集合与 §5 的迁移基线相符，静态／安装双方配对；测试预期以兼容契约及独立基线为依据，不复制实现生成的结果作为断言。
- 所有已存在的有效内容使用相同 JSON ID 解码、编码并恢复；不把具体包的份数、型号名称或平衡数值写成永久断言。
- 类型身份只取各自已登记 Codec 的 ID，并按 ResourceLocation 值相等配对；没有下游可覆写的第二份身份。dispatch 所选 Codec 与解码对象的 codec() 为同一实例；等价克隆、报告另一 Codec 和未登记实例应失败，编码、保存和蓝图导出也须覆盖。
- 型号缺失／类型不匹配在安装属性解码构造期间通过 getStaticAttr 给出结构化内容错误；未知类型在 dispatch 入口失败，几何引用由现有 validate／发布链检查。消息键、两种语言与文件位置均可验证，没有 BASIC 兜底。
- 公共 Key 的读取不触发未安装总线异常；内置条目 supplier 与 DeferredHolder 的读取遵守注册生命周期。
- 内置真实实例通过通用 createSubsystem 路径构造，生命周期、信号、能源、同步和持久化适用回归通过；不强制测试暂未启用的 WIP 功能。
- 下游可使用标准 DeferredRegister、自己的命名空间、公共基类与工厂，无需编辑 MM 内置列表。该能力由公开类型与入口审查、编译检查覆盖；独立演示模组不列入交付。
- 编辑器覆盖 24 个登记 ID，三个 WIP 类型两侧具体 schema 均存在；未知 machine_max ID 与坏字段失败，合法外部 ID 可进入下游 schema，但运行期仍要求已注册 Codec。
- 专用服务端可加载公共注册类，不引入客户端类描述符或隐含客户端初始化。
