# 武器系统 — 装弹机装填语义与供给绑定重构计划

**状态**：已实施，待实机验收。字段分块、两种输弹粒度、对接状态机与控制器独占绑定都已落到代码（实施记录见 §14）；客户端画面与 HUD 进度环仍需 runClient 核对。

## 2. 现状与问题陈述

### 2.1 四个存储位置被压缩成两个

弹药在运行期实际经过四个位置，当前模型只显式表达了其中三个：

| 位置 | 当前载体 | 是否扣库存 |
| --- | --- | --- |
| 储备（弹仓） | `AMMO_COUNT_ID` + 固定弹链 | 在取走时才扣（C5） |
| 输弹线（在途） | `deliveryLoadedTicks` / `readyConsumers` | 不扣，属于承诺 |
| 膛 | `LauncherSubsystem.chamberedType` | 已在取走时扣过 |
| 弹匣（可替换单元） | **无** | — |

第四个位置没有载体。字段名 `magazine` 同时被用来指「储备」和「可替换的弹匣」，而运行期只有前者。

### 2.2 `reload_time` 一词三义

`RegenLoaderSubsystemStaticAttr` 的注释与 schema 描述（C1）把 `reload_time` 写成三种东西：输送一发弹药给消费者的时间、再生模式下弹药诞生到可用的延迟、以及整匣更换的总耗时。第三义与 `regen_per_minute` 重复——每发诞生延迟由回充速率决定，再给一个独立字段会让两个数互相矛盾。它在代码里的落点是普通装弹机的 `round_by_round`（C15）：一个布尔同时切换 `reload_time` 的量纲，而该布尔至今没有被实现读取。

### 2.3 `regen_round_by_round` 不能承担换匣语义

它描述的是回充曲线：逐发回充，或打空后整批回充。批量分支的总时长是 `容量 ÷ 速率`（C8），与容量成正比。换匣的耗时与装多少发无关——30 发弹匣与 100 发弹链都可能是 4 秒。两者的时间模型不同，不能共用一个字段。

### 2.4 `can_supply_multiple` 的判定粒度错位

字段名与注释都在说「消费者」（C1、C12），实现判的是「有没有一发在途」（C13 的 `occupancyTier`）。后果是一条输弹线可以被两根管同时绑定：两根管的 `currentSupplier` 都指向同一台机器，靠 tick 顺序轮抢每一发。整匣模式下更糟——对接是瞬时的交付，在途几乎观测不到，占用判定形同虚设。

### 2.5 绑定没有代价，路由每 tick 都可能换人

`findSupplier` 与 `isWorthKeeping`（C13）把供给者当成可随时替换的资源，比较维度包括占用档位与装填耗时。换人只释放承诺、不扣弹药（C6），所以这种行为在今天的模型里没有成本，也就没有「换一次弹匣」这件事。

## 3. 目标模型

### 3.1 术语

| 术语 | 定义 |
| --- | --- |
| **装填单位** | 一次输弹操作移动的东西。逐发模式下是一发弹药；整匣模式下是一个弹匣。 |
| **绑定** | 发射器的 `currentSupplier` 指向某台供给者。绑定存在发射器上，由 `cancelRound` 在换人时释放（C6）。 |
| **对接** | 绑定建立后，第一次输弹所付的 `feed.reload_time`。它就是「把弹匣插上」或「把弹链接上」。 |
| **独占绑定** | `feed.can_supply_multiple=false` 的供给者，同一时刻最多绑定一根活跃发射器。 |
| **认领** | 供给者记录的「谁绑着我」的集合（`IAmmoSupplier#getBoundConsumers()`）。独占机器上最多一条，随供给者走，跨控制器共享（§6.2）。 |

### 3.2 字段归属

| 字段 | 归属 | 类型与默认 | 含义 |
| --- | --- | --- | --- |
| `reload_time` | **feed** | number，必填，秒 | 把一个装填单位送进膛的时间。逐发模式：每一发；整匣模式：每次对接 |
| `reload_round_by_round` | **feed** | bool，默认 `true` | `true`：每发都付 `reload_time`；`false`：只在对接时付一次，之后瞬时送达 |
| `can_supply_multiple` | **feed** | bool，默认 `false` | `false`：独占绑定；`true`：允许多根管同时绑定、各自计时 |
| `durability_weight` | **feed** | number，默认 `1.0` | 耐久权重，规则不变 |
| `capacity` | **magazine** | integer，必填，≥1 | 存量上限 |
| `regen_per_minute` | **magazine** | number，默认 `0` | 产出速率，规则不变 |
| `regen_round_by_round` | **magazine** | bool，默认 `true` | 回充粒度：逐发回充 / 打空后整批回充，规则不变 |
| `energy_cost_per_round` | **magazine** | number，默认 `0` | 每产出一发的取电，规则不变 |
| `regen_delay` | **magazine** | number，默认 `0` | 取走一发后暂停产出的时间，规则不变 |
| `durability_weight` | **magazine** | number，默认 `1.0` | 耐久权重，规则不变 |

`reload_round_by_round` 与 `magazine.regen_round_by_round` 只差前缀，问的是两件事：前者是「一次输弹移动几发」，后者是「一次回充补几发」，两者正交。代号随之对齐：`FeedModuleAttr` 的访问器为 `reloadRoundByRound()`，接口方法 `IAmmoSupplier#isRoundByRound`（C12）更名为 `isReloadRoundByRound`，两个实现同步改名；它在当前代码中没有调用方，改名不改变既有行为。普通装弹机静态属性里的 `round_by_round` 是它自己的字段，不在本次改名范围内。

类型级保留 `basic_attr` 与 `sounds`；实例级保留 `projectile_types`、`belt_label`、`discovery_outputs`（C16）。弹链属于装配时给这台机器配的弹种序列，不是模块的属性，因此不进 `magazine`。

两个模块的类注释（C17）随之改写：`feed` 承载的是「怎么送」，`magazine` 承载的是「存多少、怎么长回来」。模块名、关键性、恢复门槛都不变。

### 3.3 两种输弹粒度

逐发（`reload_round_by_round=true`）：

```text
请求 → 起计时器 reload_time → 就绪 → 被取走（扣库存、推进弹链）→ 下一次请求重新起计时器
```

每一发都走这一遍，与当前实现一致。绑定本身不额外收费——第一次输弹就是对接。

整匣（`reload_round_by_round=false`）：

```text
首次请求 → 起计时器 reload_time（对接）→ 就绪 → 被取走并标记已对接
后续请求 → 直接就绪（不再计时）→ 被取走
```

两条路径共用同一个计时器字段与同一套进度/音效口径，区别只在 `startDelivery` 是否因「已对接」而跳过计时（C4）。

### 3.4 对接的建立与解除

| 事件 | 对接标记 |
| --- | --- |
| 该 consumer 的首次取弹成功（整匣模式）：计时完成且那一发被 `consumeReadyRound` 取走 | 置位 |
| 计时完成、那一发尚未被取走 | 不置位 |
| `cancelRound(consumer)`：换供给者、供给者被摘除 | 清除 |
| 库存归零 | **保持**。同一台机器打空再回充，仍是同一个匣 |
| 模块受损、整机停用、整机摧毁 | **保持**。输弹线接口状态不是弹匣内容；`clearDeliveries`（C10）只释放承诺，不动对接 |
| 读档、结构变化后重新握手 | 清除（标记不持久化，见 §7.1） |

逐发模式不读写这个标记。不变量：**已对接 ⇔ 本次绑定成功送达过至少一发**——所以「就绪但还没被取走的那一发被 `clearDeliveries` 清掉」不会留下一个已对接的绑定。

### 3.5 独占绑定

`can_supply_multiple=false` 的供给者，同一时刻最多被一根活跃发射器绑定。武器控制器在候选过滤阶段排除「已被别的活跃发射器绑定」的机器（§6.2），而不是把它排到末位。没有替代品时该发射器的供给者为空，HUD 如实显示无供给者——这是建设不足的信号，不用轮抢掩盖。

`can_supply_multiple=true` 的机器允许多根管同时绑定，各自计时、各自取弹；库存由它们共同消耗。

「谁绑着这台独占机器」记在供给者身上（`IAmmoSupplier#getBoundConsumers()`），而不是各控制器扫自己的发射器表：同一台车上的多个武器控制器共用同一份认领，跨控制器的冲突因此也看得见（§6.2）。

于是路由语义从三种收敛为两种：独占与共享。「可以绑多根但一次只喂一根」这种中间态不进入本期模型。

### 3.6 打空后的行为

补给只来自 `regen_per_minute`（以及将来可能的外部补弹），没有独立的「换匣计时器」。打空后：

- 绑它的那根管继续持有绑定、继续请求；机器回充到一发即可交付，逐发模式下要再付一次输弹时间，整匣模式下因为对接标记保持，回充的第一发瞬时送达。
- 控制器在该机器无法服务的同一 tick 里可能把它换给另一台能给弹的机器（现货优先，不等它回充）；换人付出新机器的 `feed.reload_time`，旧机器的对接标记随 `cancelRound` 清除。
- 车上只有这一台机器时，行为是「按回充速率续射」，不存在额外的换匣惩罚。

### 3.7 与膛的关系

膛（`chamberedType`）独立于绑定：换供给者、供给者打空、机器被摧毁都不动膛内那发（C14）。对接计时只在膛空时才会被发起，因为发射器只在 `chamberedType == null` 时请求（C14 的 `tryLoadChamber`）。这条不需要额外代码，但验收必须覆盖「换绑时膛内那发不被清、按原弹种打出，新供给者的对接在膛空后才开始」（T15）。

### 4.1 definition 形态

```json
{
  "type": "machine_max:regen_loader",
  "basic_durability": 20,
  "pass_damage": false,
  "feed": {
    "durability_weight": 1.0,
    "reload_time": 0.45,
    "reload_round_by_round": true,
    "can_supply_multiple": false
  },
  "magazine": {
    "durability_weight": 1.0,
    "capacity": 74,
    "regen_per_minute": 120,
    "regen_round_by_round": true,
    "energy_cost_per_round": 0,
    "regen_delay": 0.3
  },
  "sounds": { "progress_sounds": { } }
}
```

实例级的 `projectile_types` / `belt_label` 写法不变。

### 4.2 Codec

`FeedModuleAttr` 与 `MagazineModuleAttr` 的 `MapCodec` 扩为完整形态，接收上表各自的字段。`RegenLoaderSubsystemStaticAttr#CODEC`（C1）的顶层只保留 `basic_attr` 与 `sounds`，其余字段全部收进两个块：

- `feed`：`fieldOf`，必填。缺块即解码失败，错误带字段名。
- `magazine`：`fieldOf`，必填。
- 其余顶层字段（`basic_attr`、`sounds`）保持不变。

两个模块的 `DEFAULT` 常量一并删除：块是必填的，兜底实例只会掩盖漏写。

Java 访问器按字段名转驼峰：`FeedModuleAttr#reloadTime`、`#reloadRoundByRound`、`#canSupplyMultiple`；`MagazineModuleAttr#capacity`、`#regenPerMinute`、`#regenRoundByRound`、`#energyCostPerRound`、`#regenDelay`。模块类继续继承 `AbstractModuleAttr`，只保留现有的耐久权重与关键性。

### 4.3 校验

沿用现有 `validateAttributes` 的 `DataResult` 风格（模块化损伤计划 §3.1 已规定错误边界），在装弹机边界的校验集合上增加：

| 规则 | 说明 |
| --- | --- |
| `feed.reload_time` 为有限非负数 | 负值无意义，NaN/∞ 会污染计时器 |
| `magazine.capacity >= 1` | 容量 0 的装弹机不可用，按配置错误拒绝 |
| `magazine.regen_per_minute`、`energy_cost_per_round`、`regen_delay` 为有限非负数 | 同上 |
| 权重与权重合计仍按现有规则 | 不变 |

错误文案带模块名与字段名（`feed.reload_time`、`magazine.capacity`），便于内容包作者定位。

未知字段按 Codec 默认被忽略：把 `reload_round_by_round` 拼成旧名不会报错，只会落回默认值 `true`。因此 T04 必须显式写出该字段并验证行为改变，用行为证明字段名接通；schema 的字段名与 §3.2 逐字一致。

### 4.4 破坏性变更与迁移

顶层写入 `magazine_capacity`、`regen_per_minute`、`regen_round_by_round`、`energy_cost_per_round`、`reload_time`、`can_supply_multiple`、`regen_delay` 不会被读取。因为两个块是必填，未迁移的定义在加载时直接失败并给出字段名，不会静默退化。第一方六份定义在同一个提交里迁移完（§8.1）。

旧存档不涉及静态属性：载具存的是实例的 `projectile_types` 与运行期计数，定义由 jar 提供，因此改字段不需要存档迁移。

## 5. 运行期契约

### 5.1 对接状态

`RegenLoaderSubsystem` 增加一个插入有序的 `Set<IAmmoConsumer> dockedConsumers`，与 `deliveryLoadedTicks`、`readyConsumers` 同处主线程。

| 位置 | 行为 |
| --- | --- |
| `startDelivery(consumer)` | 若 `reload_round_by_round`，或该 consumer 不在 `dockedConsumers`，按 `reload_time` 起计时；否则直接进 `readyConsumers` |
| `onTick` 交付推进 | 计时到位转入 `readyConsumers`；对接标记不在这里置位 |
| `consumeReadyRound(consumer)` 成功取走 | 整匣模式下把该 consumer 放进 `dockedConsumers` |
| `cancelRound(consumer)` | 移除计时、就绪位、音效记录，并移除 `dockedConsumers` |
| `clearDeliveries()` | 只清计时、就绪位、音效记录，**不动** `dockedConsumers` |
| `clearRegenState()` | 不动 `dockedConsumers` |
| 读档 | `dockedConsumers` 保持为空，即所有消费者需要重新对接 |

不变量：**已对接 ⇔ 本次绑定成功送达过至少一发**。`dockedConsumers` 只表达「这次绑定的对接付过了」，不表达弹匣里还有没有弹。

`getReloadTimeTicks()` 返回 `reload_time × 20`，两种模式一致；是否需要计时由 `reload_round_by_round || !docked` 决定，不由这个返回值决定。这样候选排序（§6.3 末段）与进度分母都不用区分模式。

### 5.2 状态与进度

`getStatus` 与 `getReloadProgress`（C9）的分支已经覆盖「交付计时中」「已就绪」「批量回充中」三种情形，对接复用交付计时器，因此不需要新分支：

- 对接进行中：`RELOADING`，进度按对接耗时折算。
- 已对接、库存充足：`READY`。
- 已对接、库存为零：按现有规则报 `EMPTY` 或 `RELOADING`（后者表示正在回充）。

交付计时与整批回充不会同时存在，因此 `getReloadProgress`（C9）先返回批量回充进度这一分支顺序不需要优先级规则：整批回充只在弹仓为零时触发（C8），而库存为零时 `requestRound` 直接拒绝（C3），计时器起不来；反过来，计时器存在意味着弹仓至少有一发，取走最后一发的动作本身就把该消费者的交付结束了。这条互斥在 `can_supply_multiple=true` 时不成立，本期没有内容使用该形态，记入 §12 不交付。

### 5.3 能量

计费点不变：逐发回充在产出一发时扣，整批回充在批次开始时按满容量一次性扣（C8）。对接本身不扣能量——对接换的是容器，不是凭空产出弹药；这一条让「整匣模式比逐发模式更划算」不成立，两种模式的差异只体现在时间结构上。

### 5.4 与模块损伤的交界

| 情形 | 结果 |
| --- | --- |
| 对接计时中 `feed` 被打坏 | `clearDeliveries` 清掉计时；该 consumer 未置位 |
| 计时完成、那一发尚未取走时 `feed` 被打坏 | `clearDeliveries` 清掉就绪位；该 consumer 仍未置位（对接以取走为界），修复后重新按 `reload_time` 计时 |
| `feed` 修好后重新请求 | 此前有一发被取走则瞬时送达；否则重新按 `reload_time` 计时 |
| `magazine` 判毁 | `clearRegenState`；对接标记保留，但供给能力为假，请求一律被拒 |
| 弹仓修复并解除恢复锁存 | 首次请求按绑定状态决定是否计时；库存不因修复变化 |

### 5.5 空库存

`requestRound` 在 `AMMO_COUNT_ID <= 0` 时返回 false（C3），规则不变。绑定由控制器维持（§6.3），不由供给者自动解绑。

### 5.6 拿到下一发还要多久

`IAmmoSupplier#getTicksToNextRound(consumer)` 回答「为这个消费者拿到下一发还要多少 tick」，是控制器保持/换人比较的唯一输入（§6.3）：

| 状态 | 返回值 |
| --- | --- |
| 已为本管备好一发（就绪待取） | `0` |
| 整匣模式、已对接、有余弹 | `0`（后续每一发都是瞬时交付） |
| 正为本管输弹 | `reload_time` − 已输送 tick，钳到 0 |
| 有余弹、未开始输弹 | `reload_time` |
| 无余弹且无在途 | `Integer.MAX_VALUE`（此刻给不出；空匣不被视为合适供给者，见 §6.1） |

最后一行是**现货优先**的直接表达：判据只回答「现在能不能给、给得多快」，不预测回充。空匣的机器即使下一 tick 就会回充出一发，也不参与比较——一发弹药撑不起续航，换到有现货的机器更划算；没有候选时绑定保留（§6.3 的 ④），由它回充后继续供弹。

默认实现读 `isRoundScheduled`、`isRoundReady`、`getDeliveryElapsedTicks`、`hasAmmo`、`getReloadTimeTicks`；`AmmoLoaderSubsystem` 直接继承它（它的计时器是倒计时，`getDeliveryElapsedTicks` 已换算成已走 tick），`RegenLoaderSubsystem` 覆写补上「整匣已对接」一行。方法无副作用：`isRoundReady` 只在已经排上的分支里调用，不会顺手发起新请求。

「已排程」与「已开始供弹」是两件事：`startDelivery` 一落表，`isRoundScheduled` 就为真，但 `getDeliveryElapsedTicks` 可能还是 `0`——这一发只是被认领，输弹还没走一格。第三行读的就是这个差值，因此刚排上的交付剩余正好等于整段 `reload_time`，此刻换人不白扔任何进度。

## 6. 武器控制器契约

### 6.1 总原则

控制器只做三件事：为每根管挑一台能服务且未被别的管独占的供给者；在当前供给者不再合法、或换到候选能更早拿到下一发时换人；换人时付新机器的对接代价。

换人只有一个目的：让下一发更早到手，所以判据是**现货优先**——当前供给者与候选各自按「现在拿到下一发还要多少 tick」计（§5.6），有余弹的那台因此总排在空匣那台前面；判据不预测回充。空匣机器即使马上要回充出一发也不是合适的供给者：一发撑不起续航，此时换到有现货的候选才是正确的。判断顺序固定为：

1. **合法性**（硬条件）：机构可用、弹种被炮闩接受、在选中弹链上。不成立立刻换人（§6.4）。
2. **代价比较**：候选严格更小才换；相等或更大就保持。
3. **没有候选**：保持还合法的那台——有回充能力的机器不该因为一时无弹丢掉绑定。

这条判据覆盖了几种容易写错的形态：整匣模式已对接时下一发是 `0` tick，任何换人都更慢，所以它从不被迁移；逐发模式手上已有一发时也是 `0`，同理；逐发在途时比的是**剩余**而不是整段耗时，刚排上（已输送 0 tick）的交付剩余正好是整段，更快的候选当场接管、白扔的进度不到一个 tick，进度已深则剩余变小、自然守到这一发完成，下一个请求再从更快的机器开始。

### 6.2 独占过滤

「谁绑着这台机器」记在供给者上：`IAmmoSupplier#getBoundConsumers()` 返回当前绑着它的消费者集合，只在主线程由服务端路由写入，不入存档、不参与同步。用集合而不是单个字段表达，是因为 `can_supply_multiple=true` 的机器合法地同时绑定多根管；独占只是对集合大小的一条判据，两种形态共用同一份存储。

`findSupplier` 组装候选时按三条过滤：

1. 弹种被炮闩接受（现 `supplyTypeAccepted`）。
2. 有库存（现 `canSupplyTo` 的 `hasAmmo`）。
3. `canSupplyMultiple()=false` 且集合里已有别的消费者（本文新增）。

集合随供给者走，同一台车上的多个武器控制器看到同一份认领，跨控制器的「两管抢一台」在建绑后立即不可行（§6.6）。失效条件是可验证的：**认领有效 ⇔ 持有者仍在（未摧毁、未失能）且它的 `currentSupplier` 仍指向本机**。供给者的 `pruneGoneConsumers`（C7）按这两条剔除，路由在认领前也按同样条件剔除一次；释放绑定的一方（`assignSupplier`，C14）把本管从旧集合里移除，因此认领集合与 `currentSupplier` 始终同时变化。

第三条接过了占用档位（C13 的 `occupancyTier`）的职责：一台正为别的管装填的独占机器根本进不了候选，空闲的那台才是；多装弹机-多发射器的装配因此仍按先到先得摊开，不需要在候选之间再排档。

保持判据不重复这三条过滤：它只比对两个「拿到下一发的时间」（§6.3 的 ⑤—⑦），候选已经由 `findSupplier` 过滤过。

### 6.3 保持与换人

`routeAmmoToLaunchers` 对每根活跃发射器按名字序执行下面的决策，全部读实时接口：

```text
① 认领检查：当前供给者是独占机器，集合里已有别的活跃消费者
   → 本管置空并退出集合（旧存档的双重绑定由此消解，§6.6）
② candidate = findSupplier(launcher, 选中弹链)
③ candidate == null    → 置空：选中弹链上已无合法供给者
④ candidate == current → 保持：没有更该选的（空匣但健康、兜底分支都走这里）
⑤ 当前不合法           → 换人（硬性失效，见 §6.4）
⑥ candidate.getTicksToNextRound(launcher) < current.getTicksToNextRound(launcher) → 换人
⑦ 否则                 → 保持
```

「合法」= `supplyTypeAccepted` 且当前供给者在选中弹链上。`findSupplier` 的兜底分支会返回当前供给者本身，因此 ④ 必须排在 ⑤ 之前：选中弹链上没有任何能接活的机器时，空匣但健康的那台不会因为「找不到候选」被丢掉绑定。当前供给者为空时 ⑤ 同样成立——没有绑定就谈不上合法，直接改用候选。

「保持」与 ⑥ 的换人都要维护认领集合：保持时把本管写进当前供给者的集合，换人时先退出旧集合再写进新集合，③ 与 ① 只退出。客户端不写（§6.7）。

`isWorthKeeping` 保留方法名，实现 ⑤—⑦：一次合法性判定加一次时间比较。占用档位（C13 的 `occupancyTier`）在目标模型里没有位置——独占机器已被认领集合过滤出候选，不需要再排档；`canServe`（C13）也不再是独立判据，「无弹且无在途」由 `getTicksToNextRound` 的 `MAX_VALUE` 表达，而「已为本管备好一发」由 `0` 表达，两者都在 ⑥ 的比较里。

候选排序保留「`getReloadTimeTicks` 升序 → 供给者身份」（C13 的 `findSupplier`）：它是「没有当前绑定时挑哪台」的依据，身份是稳定决胜键。候选都是未绑定的机器，`getTicksToNextRound` 对它们等于 `getReloadTimeTicks`，排序与比较因此同源。

### 6.4 硬性失效立即换人

⑤ 成立时当场换人，不等在途的那一发。切链与路由在同一 tick 内先后执行（C13 的 `onTick`），若把换人推迟到那一发被取走，发射器会先从旧弹链取到一发与选项卡不符的弹药——这正是「弹链不匹配」必须立即解绑的理由。弹种不再被炮闩接受、供给者机构被打坏同理。

被丢弃的在途交付不损失弹药：交付阶段库存未扣，`cancelRound`（C6）只清计时与就绪位。⑥ 的比较里已经扣掉了已走的进度，「在途被换掉」不是无条件的中断，而是换回来得更早。

### 6.5 释放路径

| 事件 | 处理 |
| --- | --- |
| 发射器被摧毁或失能 | 控制器每 tick 在路由前扫一遍**全部**发射器（含非活跃），对 `getCurrentSupplier() != null` 的非活跃者调用 `setCurrentSupplier(null)` 并从认领集合里移除；整个控制器先被摧毁时由供给者的 `pruneGoneConsumers` 兜底 |
| 发射器换弹种，当前供给者不在新弹链上 | 走硬性失效路径（§6.4）；旧绑定由 `setCurrentSupplier` 释放 |
| 供给者被打坏 | `supplyTypeAccepted` 为假，换人；旧绑定释放 |
| 供给者打空 | 不主动解绑；由绑它的发射器在换人时释放 |

控制器被停用或摧毁不触发释放：绑定在发射器上，路由停摆后那根管仍会照常向供给者要弹（发射器的 `onTick` 在开火指令判定之前就尝试装填，C14），机器确实在被使用；此时释放认领会允许第二根管绑上同一台独占机器，独占因此失效。重新上线的控制器在同一 tick 内经 ① 与 ④ 接管这些仍然有效的绑定与认领。

没有这条释放路径，一台机器会被已摧毁的发射器永久占住。

### 6.6 旧存档的双重绑定

`SUPPLIER_ID` 会持久化（C14），读档后可能两根管都恢复成同一台独占机器。认领集合不入存档，读档后为空；第一次路由按名字序处理发射器：排在前面的那根把机器认领进集合并保持，后面的那根在 ① 发现机器已被占，置空后在同一 tick 里重选。结果与「第一次装配时的先到先得」一致，且不依赖握手顺序——集合只在路由里写，握手只恢复 `currentSupplier` 字段。

跨控制器时「先到先得」由子系统的 tick 顺序决定，而非名字序：两个控制器各管一根管时，先 tick 的那个拿到机器。独占始终成立，差异只在谁拿到（§12）。

### 6.7 客户端

路由只在服务端执行（C13 的 `routeAmmoToLaunchers` 首行即返回），客户端经 `SUPPLIER_ID` 跟随，因此独占判定与保持/换人决策都不需要在客户端重跑；认领集合只在服务端写。客户端自己的 `requestRound → consumeReadyRound` 链只为进度与音效服务，对接标记在两端各自从空开始、各自因换人清除，表现一致。

## 7. 持久化与同步

### 7.1 存档内容

`saveData` / `loadData`（C11）的键集合不变。`dockedConsumers` 不写盘：它是「这次绑定付过对接没有」的会话内状态，写盘需要把消费者身份一起序列化，收益只是省一次 `reload_time`。

认领集合（`getBoundConsumers()`）同样不写盘：它由路由在每 tick 重建，读档后第一次路由即按名字序恢复（§6.6）。

### 7.2 世界重载的影响

读档后 `dockedConsumers` 为空，所有绑定在第一次输弹时重新对接一次。载具新造出来时同样如此——第一发之前会等一个 `reload_time`，这与「装弹机要先接上弹链」一致。

### 7.3 同步协议

没有新的同步值，也没有既有同步值的格式变化：`AMMO_COUNT_ID`、`BELT_INDEX`、`DATA_MODULES_ID`、`SUPPLIER_ID` 的语义与编码都不变。世界同步协议版本（当前 `sync:2.8.0`）不因本文调整。实施时若发现确有编码变化，再按既有规则升版本并在交付报告里写明。

## 9. 普通装弹机的适配边界

`AmmoLoaderSubsystem` 保持 WIP，不做字段拆分、不做模块化。本文只要求它的接口口径与实现一致：

- `isReloadRoundByRound()` 返回 `true`。它的交付路径对每一发都计时（C15），因此它在控制器眼里是逐发机器，适用 §6.3 的逐发规则（在途等取走、之后可被更快的顶替）。
- 其静态属性里的 `round_by_round` 在换匣模式真正实现之前不参与判定；实施时在该字段注释里写明这一点，避免作者以为写了 `false` 就有换匣语义。

普通装弹机将来模块化时，两个模块属性与 `feed`/`magazine` 的字段归属由本文定义，直接复用。

## 11. 验收矩阵

### 11.1 业务契约

| 编号 | 场景 | 预期 |
| --- | --- | --- |
| T01 | 省略 `feed` / 省略 `magazine` / 显式完整块 | 前两者解码失败并报出字段名；完整块按值生效 |
| T02 | `capacity=0`、`reload_time=-1`、`regen_per_minute=NaN` | 该定义不注册，其余定义继续加载 |
| T03 | 逐发模式连续请求 | 每一发都付 `reload_time`；进度按当前耗时折算 |
| T04 | 整匣模式首次请求、取走后再次请求 | 首次付 `reload_time`，之后瞬时；两次的 `RELOADING`/`READY` 正确 |
| T05 | 整匣模式换供给者后再换回 | 每次换人都重新对接 |
| T06 | 整匣模式打空后回充 | 对接标记保持，回充的第一发不重新计时 |
| T07 | 两管对一台独占机器 | 只有先认领的那根有供给者；另一根为 null 且不进入轮抢 |
| T08 | 绑定者被摧毁或失能 | 该机器在下一 tick 可被别的发射器选中 |
| T09 | 当前供给者打空、场上另有空闲机器 | 换人；新机器的首轮（逐发）或对接（整匣）照常计时；旧机器释放 |
| T10 | 当前供给者打空、场上无替代 | 保持绑定，不换人，不重复对接 |
| T11 | 逐发机器在途交付、场上另有更快的同弹链机器 | 进度尚浅时当场换（丢弃的进度小于换人省下的时间）；进度已深时等这一发完成，下一个请求由更快的机器供给 |
| T12 | 对接计时中打坏 `feed`，修复后重新请求 | 计时作废；修复后按绑定状态决定是否重新对接 |
| T13 | 读档后首次请求 | 重新对接一次；膛内那发不受影响，可正常发射 |
| T14 | 旧存档中两根管指向同一台独占机器 | 按名字序保留一根，其余置空并重选 |
| T15 | 换绑时膛内已有弹药 | 换绑不清膛；膛内那发按原弹种打出；新供给者的对接在膛空后首次请求才开始 |
| T16 | 整匣模式打空后整批回充 | 回充期间请求被拒、状态与进度是回充的；回充完成后首次取弹瞬时（对接标记由打空前的最后一发保留） |
| T17 | 两个控制器各管一根管、都能发现同一台独占机器 | 只有先 tick 的那根拿到绑定；另一根为 null，不干扰已绑定者 |
| T18 | 整匣式已对接、场上另有更快的同弹链机器 | 不迁移：已对接的下一发是 0 tick，HUD 供给者不变 |
| T19 | 当前供给者打空、下一 tick 就会回充出一发，场上另有余弹候选 | 仍然换人（现货优先，不等回充）；空匣机器释放 |

### 11.2 测试落点

- 属性解码与校验、对接时序、控制器决策都落在 GameTest：真实 `SynchedEntityData`、真实 `Level` 与子系统编排无法在纯 JUnit 中启动。沿用 `common/gametest/ModularDamageGameTest.java` 的构造方式与独立批次名；两消费者场景用两台真实 `LauncherSubsystem`，与现有 `loader.requestRound(launcher)` 的接线一致。

- 控制器跨 tick 的行为（代价比对、认领、释放）需要多个 tick 的 GameTest，不用单 tick 断言模拟。
- 客户端画面、HUD 进度环与声音必须实机核对；服务端测试通过不替代画面验收。

## 12. 风险与不交付

| 风险 | 处置 |
| --- | --- |
| 独占绑定使「两管一台」的装配少一根管的供给 | §8.2 在 P0 逐台核对；受影响载具每根管配一台装弹机 |
| 对接不持久化，读档后第一枪延后一个 `reload_time` | 接受；§7.2 写明。若实测违和，再讨论按已恢复的绑定播种对接标记 |
| `getReloadTimeTicks` 在两种模式下的含义不同（对接耗时 / 每发耗时） | 保持判据读 `getTicksToNextRound`（§5.6），两种模式都被折算成「拿到下一发还要多久」；`getReloadTimeTicks` 只作为候选择序键，排序时所有候选都未绑定，同一量纲 |
| 认领的有效性依赖「持有者仍在要弹」：无开火指令的管今天仍会取弹，将来若让它停止取弹，绑定会变成无人使用的占位 | §6.5 的失效条件（持有者仍在且仍指向本机）覆盖不了这种情形——届时需要在那条改动里补上控制器停用路径的释放 |
| 跨控制器的认领顺序由子系统 tick 顺序决定，而非名字序 | 独占始终成立，差异只在谁拿到；同一控制器内仍是名字序（§6.6） |
| 换弹种会触发换人与对接，玩家感知为一次明显停顿 | 这是设计意图：换弹种就是换弹匣。数值由内容作者标定 |
| 普通装弹机的 `round_by_round` 字段在实现前具有误导性 | §9 规定返回值恒为 `true` 并在注释里写明 |

本期不交付：

- 手动换装弹机、手动提前换匣、弹匣作为物品或独立子系统。
- 多个 `magazine` 模块、按模块拆分的库存与弹链。
- 模块损伤导致输弹变慢的衰减乘数（`feed` 耐久目前只决定「能送 / 不能送」）。
- 普通装弹机的模块化、物品映射与物流。
- `can_supply_multiple=true` 下交付计时与整批回充并存的进度优先级（§5.2 的互斥只在独占时成立）。
- 新的同步值、新的存档键、世界同步协议升级。

## 14. 实施记录

### 14.1 字段与校验

`FeedModuleAttr` 承载 `durability_weight`、`reload_time`（必填）、`reload_round_by_round`（默认 `true`）、`can_supply_multiple`（默认 `false`）；`MagazineModuleAttr` 承载 `durability_weight`、`capacity`（必填）、`regen_per_minute`、`regen_round_by_round`、`energy_cost_per_round`、`regen_delay`。两个块在 `RegenLoaderSubsystemStaticAttr#CODEC` 里都是必填 `fieldOf`，顶层只剩 `basic_attr` 与 `sounds`。

校验在装弹机属性边界执行：`basic_durability` 有限为正、两个权重有限为正且合计有限、`feed.reload_time` 有限非负、`magazine.capacity` ≥ 1、`regen_per_minute` / `energy_cost_per_round` / `regen_delay` 有限非负。错误文案带模块名与字段名。

六份第一方定义已按 §8.1 迁移。`can_supply_multiple` 五份写 `false`（独占绑定）；`atgm_regen_loader` 写 `true`，K17 炮塔的四根导弹管由这一台装弹机同时供弹，各管独立计时、库存共用。输弹粒度分两类：PKTM、MG34 与 2A42 整匣输弹（换弹链／换弹匣付一次 `reload_time`，之后每发瞬时），其余三份逐发送弹（ATGM 每发 10 秒）。回充粒度也分两类：PKTM 与 MG34 打空后整批回满（整批 10 秒，`regen_per_minute` 因此写 `capacity × 6`），其余四份逐发回充（ATGM 单发 30 秒，即 `regen_per_minute = 2`）：

| 定义 | `reload_time` | `reload_round_by_round` | `capacity` | `regen_per_minute` | `regen_round_by_round` | `regen_delay` |
| --- | --- | --- | --- | --- | --- | --- |
| `2a90_regen_loader` | 0.45 | `true` | 74 | 120 | `true` | 0.3 |
| `2a42_regen_loader` | 4 | `false` | 300 | 100 | `true` | 0.3 |
| `pktm_regen_loader` | 3 | `false` | 2000 | 12000 | `false` | 0 |
| `atgm_regen_loader` | 10 | `true` | 4 | 2 | `true` | 0 |
| `mg34_regen_loader` | 3 | `false` | 150 | 900 | `false` | 0 |
| `kwk39_50mm_regen_loader` | 2 | `true` | 40 | 10 | `true` | 0 |

供给接口的输弹粒度方法为 `IAmmoSupplier#isReloadRoundByRound`（C12 记录的旧名是 `isRoundByRound`）；普通装弹机恒返回 `true`，它的 `round_by_round` 字段在实现换匣语义之前不参与判定，类注释已写明。

### 14.2 对接状态机

`RegenLoaderSubsystem#dockedConsumers` 是会话内集合，`startDelivery` 只在「逐发模式」或「该消费者尚未对接」时起计时，`consumeReadyRound` 在整匣模式下成功取走后置位。`cancelRound` 与 `pruneGoneConsumers` 清除它；`clearDeliveries`、`clearRegenState`、读档都不动它。逐发模式不读写这个集合。

`IAmmoSupplier#getTicksToNextRound` 默认实现读 `isSupplyOperational` / `isRoundScheduled` / `isRoundReady` / `getDeliveryElapsedTicks` / `hasAmmo` / `getReloadTimeTicks`，`RegenLoaderSubsystem` 覆写补上「整匣已对接且有余弹 → 0」。

### 14.3 控制器

`IAmmoSupplier#getBoundConsumers()` 是供给者上的可变集合，由服务端路由写入、`LauncherSubsystem#assignSupplier` 摘除、供给者的 `onTick` 剔除失效条目。`WeaponControllerSubsystem#claimedByOther` 在候选过滤阶段排除已被别的活跃管认领的独占机器；`routeAmmoToLaunchers` 按 §6.3 的七步执行，并在路由前把非活跃发射器的绑定释放掉（控制器自身停用时不释放，理由见 §6.5）。`occupancyTier` 与 `canServe` 已删除。

### 14.4 装配核对

§8.2 的核对结果：除 `ammo_atgm` 外，各弹药频道的机器数都不少于管数——2S38 的 `ammo_2a90` 是 2 机 1 管、`ammo_pktm` 1 机 1 管；K17 的 `ammo_2a42` / `ammo_pktm` 各 1 机 1 管；MTLB 的 `ammo_pktm` 1 机 1 管；Sdkfz234 的 `ammo_50mm` 2 机 1 管、`ammo_7_92mm` 1 机 1 管。K17 的 `ammo_atgm` 是 1 机 4 管，靠 `can_supply_multiple=true` 的一台四发装弹机同时供四根导弹管，不需要多摆机器。因此独占绑定不需要给任何载具加机器。
