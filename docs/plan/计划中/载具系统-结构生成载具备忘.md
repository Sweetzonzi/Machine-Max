# 载具系统-结构生成载具备忘

> 状态：计划中，未细化。本文记录结构生成载具的技术方向与待决问题，供后续形成调查或实施计划；不代表代码已实现。
> 创建时间：2026-11-26
> 相关代码：[VehicleData](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/data/VehicleData.java)、[ObjectManager](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/ObjectManager.java)、[VehicleCore](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java)、[MMDynamicRes](../../../src/main/java/io/github/sweetzonzi/machine_max/external/MMDynamicRes.java)
> 前置设计：[载具系统生命周期与同步设计](载具系统-生命周期与同步设计.md) §3.1、§6。全表登记与物理入世分开，结构生成不要求同一批车辆立即活跃。

## 1. 目标

允许世界结构生成已经组装好的 Machine-Max 载具，例如路边废弃车辆、危险哨站中的炮塔，以及其他由内容包配置的场景载具。载具不要求由玩家放置，也不要求在结构里放置技术性方块作为锚点。

结构配置应能引用 `MMDynamicRes.TEMPLATES` 中的载具模板，并可附带生成位置、朝向和初始状态规则。首批考虑的随机化需求包括整车各部件的随机耐久区间。

## 2. 技术方向

采用数据驱动的自定义 `StructureProcessor` 记录生成请求；不在结构生成期间构造 `VehicleCore`、创建物理体或调用 `ObjectManager.addVehicle`。

候选流程：

1. 结构的 processor 配置声明载具模板 ID、结构内相对生成坐标、朝向规则、随机化规则及可选盐值。
2. Processor 在模板处理阶段根据放置位置、旋转和镜像换算世界坐标，将不可变的待生成记录写入目标区块的可序列化 NeoForge chunk attachment。
3. 服务端运行期只在目标区块进入完整加载状态后读取记录；此时再做模板解析、落点校验和载具实例化。
4. 对载具数据副本应用随机初始状态与目标变换，在 `ObjectManager` 将新建的 `VehicleCore` 登记到载具全表。需要运行时再请求唤醒，物理入世就绪后进活跃表；没有活动需求则保持休眠。客户端按玩家跟踪，不随全表登记广播整车。
5. 兑现结果和载具保存记录一起持久化；待办只有在结果可恢复后才能清理。失败时按失败类型保留并重试，或明确标记为不可重试并记录诊断。

`StructureProcessor` 实例只保存 Codec 解出的配置，不保存跨调用的可变待办队列。生成过程可能并行或重试，状态应落在按目标区块归属、可持久化的数据上。

## 3. Processor 配置草案

字段名与格式尚未定稿，示意如下：

```json
{
  "processor_type": "machine_max:spawn_vehicle",
  "vehicle": "machine_max:example_vehicle",
  "spawn_offset": [0.5, 0.0, 0.5],
  "facing": "structure",
  "random_salt": "roadside_wreck",
  "durability": {
    "min_ratio": 0.15,
    "max_ratio": 0.65,
    "scope": "regular_part"
  }
}
```

- `vehicle` 指向内容包载具模板 ID，而不是把整份 `VehicleData` 内联进结构 JSON。
- `spawn_offset` 相对模板放置原点；其坐标需随结构 rotation / mirror 一起变换。
- `facing` 可选择跟随结构朝向或使用显式偏转；是否支持非 90 度旋转待定。
- 结构 processor list 是否能被目标结构类型引用，需要按所采用的世界生成结构类型确认；jigsaw/template pool 是当前优先调查对象。

## 4. 初始状态随机化

随机范围由 processor Codec 字段定义，抽样应用在 `VehicleData` 的副本上。首版可用均匀分布，耐久比例限制在 `[0, 1]`，并受部件组装进度对应的耐久上限约束。

耐久数据已有两种粒度：共享耐久使用 `RegularPartData.sharedDurabilityRatio`；非共享耐久使用各 `SubPartData.durabilityRatio`。配置中的 `scope` 应明确一次抽样应用于整件 RegularPart，还是分别应用于每个 SubPart。共享耐久类型不能按 SubPart 各自抽样。

抽样种子候选由世界种子、结构放置坐标、载具模板 ID 和配置盐值组合，保证同一世界中的结构生成重试可复现、不同位置或世界可产生不同结果。不能默认把 `StructurePlaceSettings.getRandom(...)` 当作世界种子随机源：其随机源未显式设置时会退回位置种子；种子坐标为空时则使用时间种子。

待定的持久化选择：

- 待生成记录只存随机种子与规则，兑现时重算；记录较小，但数据包或载具模板更新可能改变最终结果。
- 待生成记录存每个部件已抽出的耐久比例，生成结果固定；记录较大，但更符合“区块生成时结果即确定”的预期。
- 是否需要模板版本或数据包重载兼容策略。

## 5. 生命周期与幂等

- Processor 回调发生在结构模板放置流程中，早于全部方块写入完成；该阶段只记录意图，不检查需要完整世界状态的碰撞/支撑条件，也不触碰物理线程。
- 延迟兑现时验证目标区块已完整加载、载具模板存在、生成区域可用，并按载具包围范围检查与地形/结构的冲突。
- 结构可能因区块生成重试而重复处理。请求需使用稳定键去重，候选组成包括维度、世界坐标、模板 ID 与 processor 配置标识。
- 从稳定请求键导出确定性载具 UUID。检查当前车辆用全表，不能查不到活跃车就重建；是否已兑现以持久化结果为准，避免车辆被移走、收纳或合并后重放生成。
- 兑现需覆盖“载具及结果已存，待办仍在”和“载具及结果未存”两种重启窗口；进入活跃表不是成功条件。
- 对越区块的大型载具，待办归属与就绪条件需要覆盖整个载具包围盒，而不只检查锚点坐标所在区块。

## 6. 待细化问题

- 首版只支持 jigsaw/template pool，还是要支持其他结构放置路径？
- 一个模板允许放置一台还是多台载具？多个 processor 是否各自代表一次生成？
- 位置采用结构原点、processor 的局部偏移，还是显式锚点坐标？如何处理地形高度与结构投影？
- 载具初始姿态是跟随结构水平朝向，还是支持倾斜；车辆底面如何贴合地面？
- 结构生成载具采用完整状态、骨架状态，还是独立的 spawn restore mode？随机耐久与已损坏部件是否允许？
- 生成载具是否静止、可立即驾驶，或由炮塔/AI 等后续系统接管？
- 世界重载、数据包重载、模板被删除、缺少部件定义、生成空间不足时分别如何处理？
- chunk attachment 的数据 Codec、写入线程、区块保存时机与重试语义需要通过本地 21.1.219 源码和 GameTest 验证。
- 对结构 generation retry、目标区块延迟加载、跨区块载具、服务器重启和重复兑现建立 GameTest/集成验收。

## 7. 相关现有入口

- `MMDynamicRes.TEMPLATES` 按 `ResourceLocation` 保存载具模板。
- `VehicleData.withNewUUID(...)` 可替换载具身份；随机化前应复制数据，不直接改动注册表中的模板对象。
- `VehicleCore(Level, VehicleData, PartRestoreMode)` 从数据重建载具。
- `VehicleCore.setTransform(...)` 可将结构放置的目标变换应用到整车部件。
- `ObjectManager.addVehicle(...)` 当前把登记、入世、存档快照和客户端广播绑在一起。结构兑现依赖双表设计提供只登记的入口，不直接调用这个组合入口，也不自行加入零件或刚体。
