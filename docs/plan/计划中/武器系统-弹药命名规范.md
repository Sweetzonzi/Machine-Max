**状态**：推荐标准。不是强制约定，内容包作者可以任意命名自己的弹种；本文给出的是"读得懂、不撞车"的推荐写法。
**日期**：2026-10-23
**分支**：1.21.1
**适用对象**：内容包作者、发射器 / 装弹机维护者、武器 HUD 维护者

> **本文自包含**：本文用到的全部标识符、字段与判据都在文内给出，不要求先读其他文档；文中的弹种、标签与展示名均按仓库当前内容包的实际内容列出。

### 1.2 一条 id 承担五种用途

| 用途 | 实现 | 代码位置 |
| --- | --- | --- |
| 注册键 | `ResourceLocation.fromNamespaceAndPath(namespace, fileName.removeSuffix(".json"))` | `common/resource/modules/ProjectileModule.kt:55` |
| 弹链成员 | 部件 JSON 的 `projectile_types` 的键 | `RegenLoaderSubsystemAttr.projectileTypes` |
| 展示名 | `registryKey.toLanguageKey()` → `machine_max.<id>` | `ProjectileType.getDisplayLabel()`（`ProjectileType.java:185`） |
| 模型缺省名 | 无 `visual.model` 时按 id 查 `models/projectile/<id>` | `BallisticProjectile.getDefaultModelIndex()`（`BallisticProjectile.java:421`） |
| 选择态同步 | 弹链编码成 `id1,id2` 字符串 | `WeaponControllerSubsystem.encodeBelt()` |

id 是扁平的单段路径（`ProjectileModule` 只取 `fileName`，忽略 `pathSegments`），因此 id 内不能出现 `/`。

### 1.3 兼容性判据是标签，不是 id

发射器与弹种的匹配是纯标签集合运算，标签名由作者自由定义（`ResourceLocation`，任意 `命名空间:路径`）：

```java
// BreechModuleAttr.isAmmoCompatible(List<ResourceLocation>)
requiredTags  非空 → 必须全部包含
acceptableTags 非空 → 至少包含一个
forbiddenTags  非空 → 一个都不能包含
```

`external.caliber` 不参与匹配，它只用于光效折算与伤害扩展（`MuzzleFlashLight.radiusFor`、`ProjectileTracerLightSource.lightRadius`、`BFDamageExtensions.CALIBER`）。

### 1.4 id 不落盘

`WeaponControllerSubsystem.saveData()` 只写 `target_*`（`WeaponControllerSubsystem.java:1010`），`RegenLoaderSubsystem` 只写 `belt_index`（`RegenLoaderSubsystem.java:790`）；蓝图按 `PartData.registryKey + variant` 重建，放置时以 `readAdditionalData=false` 忽略子系统数据。改 id 不动存档，也不动蓝图。

## 二、命名要解决的四个问题

### 2.1 同一件事有四套写法

以"曳光"为例：

| 层 | 写法 | 位置 |
| --- | --- | --- |
| id 效果段 | `t` | 投射物文件名 |
| 标签 | `ammo/tracer` | 投射物 JSON 的 `tags` |
| 展示名 | `曳光` / `TRACER` | `lang/zh_cn.json`、`lang/en_us.json` |
| 弹链名 | `AP/T` | 部件 JSON 的 `belt_label` |

四套写法各自演化，没有一张表规定对应关系。规范要做的不是把它们合并成一种，而是给出一张**对照表**（§3.3），并让 id 的效果段与 `belt_label` 共用同一套缩写。

### 2.2 缩写没有共享词表就会撞名

同一个 token 在不同领域可以指不同东西。仓库里曾有一个 `7_92mm_smk`：`smk` 指 S.m.K.（Spitzgeschoss mit Kern，硬芯穿甲弹），而 `smk` 在弹药领域是 smoke（烟幕）的标准缩写。一个名字有两种读法，只有标签 `ammo/ap` 能给出唯一答案。

这就是效果词表存在的理由：`smk` 一旦被收进词表并指定为"烟幕"，它就不能再兼任弹种型号。该弹种现名 `7_92x57_ap`，改名理由见 §4.1。

### 2.3 名字、标签、弹道数据可能互相矛盾

三者分处三个文件（文件名、`tags`、`terminal`），没有任何机制保证它们说同一件事。判据取最硬的那个：**穿深**。纯曳光弹的弹头里装了曳光剂，穿深低于同弹壳的穿甲弹是合理的；反过来，一个叫 `_t` 的弹如果穿深不低于同弹壳的 `_ap`，名字就该重新考虑。

仓库里四个 7.62 / 7.92 弹种按这条对过一遍，是自洽的：

| id | `tags` | 穿深 |
| --- | --- | --- |
| `7_62x54r_ap` | `ammo/ap` | 8 |
| `7_62x54r_t` | `ammo/tracer` | 5 |
| `7_92x57_ap` | `ammo/ap` | 5 |
| `7_92x57_t` | `ammo/tracer` | 3 |

两个 `_t` 的穿深都低于同弹壳的 `_ap`，与"纯曳光弹"一致。曾经对不上的只有弹链名，记在 §4.2。

### 2.4 口径当兼容键，默认够用

`required_tags: ["machine_max:caliber/7_62mm"]` 是当前所有发射器的写法。它的代价只有一个：**当同一个包里出现第二种同口径弹壳时，这行标签必须细分**（例如改成 `caliber/7_62x54r`），否则 PKTM 会接受 7.62×39 的弹。

这是作者的选择，不是缺陷：`tags` 可以写到任意粒度，细分只需要改发射器的一行标签，不需要改代码。规范只在"确实要区分"时推荐写法，不强制所有弹种都标弹壳。

## 三、推荐写法

### 3.1 id = `<名称>_<效果>`

```
id := <名称> "_" <效果>
```

- **名称**：作者自定，推荐"在包内足够区分"的最短可读名。常用三类写法见 §3.2。
- **效果**：取自 §3.3 的推荐词表，放在最后一段。这样"按效果分组"、`belt_label`、HUD 缩写、语言键都只需要看末尾。
- 名称段可以带下划线（`7_62x54r`、`sprgr38`），效果段在最后，因此从右往左读第一段就是效果。
- **id 里不用连字符**（`AP-T` 写成 `ap_t`），连字符只出现在展示名与 `belt_label`。

效果段不是必填的教条：当名称本身就是公认型号、且效果唯一（`50mm_pzgr39`、`9m133_kornet`），省掉效果段也读得懂。推荐仍加上，因为它是 HUD 取字与弹链命名的公共来源。

### 3.2 名称段怎么写

| 对象 | 推荐 | 例子 |
| --- | --- | --- |
| 枪弹（同口径多弹壳） | 口径×壳长 | `7_62x54r_ap`、`5_56x45_t`、`7_62x39_t` |
| 枪弹（本包只有这一种，且不打算加同类） | 只写口径 | `7_62mm_ap`、`7_92mm_t` |
| 炮弹 | 只写口径 | `50mm_apcbc`、`120mm_apfsds`、`155mm_he` |
| 炮弹（名称即型号） | 口径 + 型号 | `50mm_pzgr39`、`122mm_of462` |
| 英制火炮 | 磅级 | `25pdr_he`、`17pdr_ap`（数值放标签，§3.4） |
| 导弹 / 特种弹 | 型号 | `9m133_atgm`、`flare_illum` |

第二行是可选写法：仓库当前四个 7.62 / 7.92 弹种都写到了弹壳，因为这两个口径在现实中都有多种互不通用的弹壳（§4.1）。

**炮弹不写壳长。** 炮弹在现实中按口径识别（50mm、122mm、155mm），壳长是枪弹才需要的区分量；分装弹（155mm 榴弹炮）没有固定壳长。同一口径出现多种炮弹时，用型号名区分（`50mm_pzgr39` 与 `50mm_pzgr40`），不用壳长。

**枪弹反过来**：口径常常不够。7.62 在现实中就有 39、51、54R 三种互不通用的弹壳，5.56 与 5.45 也是按弹壳区分的。若预计本包会加第二种同口径弹壳，名称段直接写弹壳（`7_62x54r_ap`），比事后改名便宜——§4.1 记录的四个改名就是按这条做的。

### 3.3 效果词表（推荐）

id 用 token 本身；展示名与 `belt_label` 按下表取。这是**共享词表**，不是强制校验——作者用了表外的写法，引擎照样能跑，只是别的包读不懂。

| id token | 中文 | 英文 | `belt_label` | 说明 |
| --- | --- | --- | --- | --- |
| `ap` | 穿甲 | AP | AP | 泛称，也用于未细分的穿甲 |
| `api` | 穿甲燃烧 | API | API | |
| `t` | 曳光 | T | T | 纯曳光弹 |
| `ap_t` | 穿甲曳光 | AP-T | AP-T | |
| `api_t` | 穿甲燃烧曳光 | API-T | API-T | |
| `apbc` | 被帽穿甲 | APBC | APBC | |
| `apcbc` | 风帽被帽穿甲 | APCBC | APCBC | |
| `apcr` | 硬芯穿甲 | APCR | APCR | |
| `apds` | 脱壳穿甲 | APDS | APDS | |
| `apfsds` | 尾翼稳定脱壳穿甲 | APFSDS | APFSDS | |
| `aphe` | 穿甲爆破 | APHE | APHE | |
| `he` | 高爆 | HE | HE | |
| `he_t` | 高爆曳光 | HE-T | HE-T | |
| `heat` | 破甲 | HEAT | HEAT | |
| `hesh` | 碎甲 | HESH | HESH | |
| `smk` | 烟幕 | SMK | SMK | 只表示烟幕 |
| `illum` | 照明 | ILLUM | ILLUM | |
| `atgm` | 反坦克导弹 | ATGM | ATGM | |
| `sub` | 亚音速 | Sub | Sub | 追加在效果段之后：`ap_sub` |
| `red` | 减装药 | Red | Red | `he_red` |

组合顺序固定为"主效应 → 燃烧 → 曳光"（`ap_t`、`api_t` 即按此序），装药变体追加在最末。同一 `名称_效果` 出现多种装药时，**全部标注**，不要只标非标准的那发——否则"没有后缀"同时意味着"全装药"和"未分类"。

### 3.4 名字里装不下的，一律用标签

规范不规定必须有哪些标签；需要按某个维度筛选的人，自己定义标签并在发射器 / 弹药池里引用即可。常用几类：

| 维度 | 推荐标签 | 备注 |
| --- | --- | --- |
| 口径 | `caliber/<数值>` | 数值用下划线代替小数点：`caliber/7_62mm`、`caliber/87_6mm` |
| 弹壳（需要细分时） | 自定义，例如 `cartridge/7_62x54r` | 只在同口径多弹壳时才有必要 |
| 弹头效应 | `ammo/ap`、`ammo/tracer`、`ammo/he` … | 集合语义，可多写；与效果段同义但不重复 id 的职责 |
| 其它（国别、年代、装药） | 任意命名空间 | 引擎不解释，作者自用 |

两条经验：

- **标签集合按分量写，不写复合词**：穿甲燃烧写 `ammo/ap` + `ammo/incendiary`，让"要任何穿甲弹"用 `ammo/ap` 就能匹配到它。
- **通用族与具体族同时写**：`50mm_pzgr39` 是风帽被帽穿甲，写 `ammo/ap` + `ammo/apcbc`。这条把仓库里已有的 `ap`+`apcbc` 双写从偶然做法变成可预期的写法。

需要按弹壳匹配时，发射器写 `required_tags: ["machine_max:cartridge/7_62x54r"]`；多口径兼容用 `acceptable_tags` 列出全部。**不要**把 `external.caliber` 当兼容依据——它是弹丸口径，次口径弹如 `120mm_apfsds` 写的是 26 mm 弹芯，不是膛口口径。

### 3.5 展示名与 `belt_label`

| 量 | 推荐 |
| --- | --- |
| 弹种展示名 | 语言键 `machine_max.<id>`，取值取 §3.3 的中文 / 英文列 |
| 不带口径 | 展示名里不写口径（`57mm 穿甲弹` → `AP`），口径在弹链详情单独显示 |
| `belt_label` | 只用 §3.3 的 `belt_label` 列，`/` 分隔；**每一段是一种弹**：3 发穿甲 + 1 发曳光写 `AP/T`，穿甲与高爆混装写 `AP/HE`。`AP/AP-T` 读作"穿甲弹 + 穿甲曳光弹"，只在弹链真的同时装了这两种时才用。它是字面文本，不查语言文件，因此只用与语种无关的缩写 |
| 空缺 | 纯弹种弹链不填 `belt_label`（自动取首发弹种的展示名），混装或需区分配比时必填 |

### 3.6 一个实用问题：7.62×54R 有型号名吗

有，但要分清三层，它们的"名字"不是一回事：

| 层 | 现实中叫什么 | 例子 |
| --- | --- | --- |
| 弹壳 | 口径 × 壳长（+ 底缘） | 7.62×54R、7.62×39、7.62×51 |
| 枪弹型号 | 型号代号 | LPS（轻弹钢芯）、T-46（曳光）、B-32（穿甲燃烧）、7N1（狙击） |
| 炮弹 | 口径 + 弹种代号 | 50mm PzGr 39、122mm OF-462 |
| 英制火炮 | 磅级 | 25-pounder（87.6mm）、17-pounder（76.2mm） |
| 导弹 | 型号 | 9M133 |

**`7.62×54R` 是弹壳名，不是弹种名**：同一个弹壳下有 LPS、T-46、B-32、BZT 等多个弹种。所以名称段写哪一层，取决于要区分到哪一层：

| 要区分到 | 名称段写法 |
| --- | --- |
| 只区分"7.62 毫米的穿甲" | `7_62mm_ap` |
| 区分"54R 的穿甲燃烧"（会有 39 的弹时） | `7_62x54r_api` |
| 区分到具体型号 | `lps_ap`、`b32_api`（或 `7_62x54r_lps_ap`） |

名称段写得越细，改起来越贵；推荐写到"包内不会撞"为止，而不是写到史书级别。

## 四、迁移记录

### 4.1 已改名的四个弹种

四个 7.62 / 7.92 弹种按"名称段写弹壳、效果段取词表"改过一次名。旧 id 与新 id 的对应：

| 旧 id | 现 id | 理由 |
| --- | --- | --- |
| `7_62mm_ap` | `7_62x54r_ap` | 7.62 在现实中就有 39、51、54R 三种弹壳并存 |
| `7_62mm_tracer` | `7_62x54r_t` | 与上一行同弹壳；`tracer` 不是词表里 `t` 的写法，一并统一 |
| `7_92mm_smk` | `7_92x57_ap` | `smk` 有两种读法（§2.2），效果段改用 `ap` |
| `7_92mm_tracer` | `7_92x57_t` | 与上一行同弹壳、同一条弹链；`tracer` → `t` |

`tags` 未动：这四个弹种的口径没变，`caliber/*` 仍写 `7_62mm` / `7_92mm`（§1.1）。展示名也未动，仍是 `AP` / `曳光` / `TRACER`。

### 4.2 同一批修掉的弹链名与标签

| 项 | 处理 |
| --- | --- |
| K-17 / 2S38 / MTLB 的 PKTM 弹链名 | `AP/AP-T` → `AP/T`。弹链是 3 发穿甲 + 1 发纯曳光，`AP/AP-T` 字面读作"穿甲弹 + 穿甲曳光弹"（§3.5） |
| Sd.Kfz.234 的 MG34 弹链名 | 补 `AP/T`。此前不带 `belt_label`，弹链名自动取首发弹种的展示名 `AP`，读不出混装 |
| `7_62x54r_ap` 的 `tags` | 去掉 `ammo/api`。该弹是纯穿甲弹，弹头里没有燃烧剂 |

### 4.3 改一个弹种 id 要同步改的位置

| 位置 | 说明 |
| --- | --- |
| `projectiles/<id>.json` | 文件本身就是 id |
| 部件的 `projectile_types` | 弹链成员的键（K-17 / 2S38 / MTLB / Sd.Kfz.234 共 4 处） |
| 模板的 `chambered_type` | 装填态的初值（`k17.json`、`sdkfz234_2.json`） |
| `lang/{zh_cn,en_us}.json` | 语言键 `machine_max.<id>` |
| 文档与 schema 的描述示例 | 全局检索旧 id |

`discovery_outputs` 的键（如 MG34 的 `ammo_7_92mm`）是研究系统的产出通道名，不是弹种 id，改名时不需要跟着改。

### 4.4 可以改但没改的

| 可改可不改 | 说明 |
| --- | --- |
| `30mm_ap` / `30mm_he` → `30x165_ap` / `30x165_he` | 30mm 有多型弹壳，但本包只此一种；什么时候真要加第二种就什么时候改 |
| `50mm_pzgr39` / `50mm_sprgr38` | 型号名已是通行名，可在末尾补 `_apcbc` / `_he` 以便按效果聚合，不补也读得懂 |
| `9m133_kornet` → `9m133_atgm` | 型号名已是通行名；它是模型与文档引用最多的一个，改名收益低 |

| 不用改 | 说明 |
| --- | --- |
| `57mm_ap` / `57mm_he` | 2A90 只有一种 57mm 弹，口径已足够 |
| `120mm_apfsds` | 口径已足够 |
| `155mm_he` | 口径已足够，且分装弹没有固定壳长 |
| `20mm_ap` | 调试弹种 |
| `flare_illum` | 已符合"名称 + 效果" |

`ProjectileTestItem` 与 `FlareTestItem` 的默认值（`20mm_ap`、`flare_illum`）不受改名影响。

### 4.5 没有别名机制

`ProjectileModule` 每个文件只注册一个键，`ProjectileType.setRegistryKey` 对重复注册直接抛异常，因此不存在"新旧 id 并存"的过渡期。若担心第三方内容包引用，可给 `ProjectileModule` 加一个 `aliases` 字段（把旧键同时放进缓存表，约 5 行代码）；否则就是一次改完。

## 六、作者自查清单（可选）

不是加载期校验，供作者在提交前自己过一遍：

1. 文件名（id）能读出"是什么弹"：`<名称>_<效果>`；
2. 效果段在 §3.3 里，且写在最后；
3. 名称段是否已经足以在本包内区分？同口径有多种弹壳时，名称段写到弹壳（`7_62x54r`）而不是口径（`7_62mm`）；
4. 每个弹种的 `tags` 至少一条 `ammo/*`，否则按效应筛选时看不到它；
5. 语言文件里有 `machine_max.<id>` 的键，且不带口径前缀；
6. `belt_label` 的每一段都能在 §3.3 找到，且每段对应弹链里真实存在的一种弹（混装穿甲与曳光写 `AP/T`，不是 `AP/AP-T`）；
7. 名字、标签、穿深三者对得上：叫 `_ap_t` 的弹，穿深不应低于同弹壳的 `_t`。
