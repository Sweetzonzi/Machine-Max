# 载具系统-部件附魔与词条系统备忘

> 状态：计划中，未细化。本文记录方向、已定决策与未决项，供后续展开为实施计划，不是实现计划。

## 1. 目标与边界

让载具部件携带**词条**（rune，对外可称"部件附魔"）。词条在部件受损、装填、开火等时机生效，效果由 Java 实现，条目本身来自 mod 自带数据包。

与装备附魔的差异是设计目标，不是副作用：部件词条应当更贵、更难获得、数量受部件限制，且不通过附魔台随机产出。

边界：

- 载体是 `RegularPart`；`SubPart` 与子系统是效果的落点，不是词条的载体。
- 词条是第一方内容。内容包只能引用已存在的词条 id，不能新增条目（内容包目录是自定义资源包，不是数据包）。
- 不做通用"附魔效果总线"，只开有限的几个 hook。

## 2. 已定决策

| 决策 | 理由 |
| --- | --- |
| 词条寄存在原版 `Enchantment` 注册表 | `Registries.ENCHANTMENT` 由 `RegistryDataLoader` 从 `data/<ns>/enchantment/` 装载，条目只能来自数据包，无法在代码里 `DeferredRegister`；复用注册表可以直接得到 `ItemEnchantments` 存储、tooltip、发光与等级上限 |
| 每条词条一份 JSON，只写名字、可附魔范围与 `max_level` | `effects` 留空；`weight` / `min_cost` / `max_cost` / `anvil_cost` / `slots` 是 `EnchantmentDefinition` 的必填项，填占位值 |
| 效果逻辑写在 Java，按 `ResourceKey<Enchantment>` 分派 | 不注册 effect 组件、不写条件 DSL；词条数量有限且由第一方维护，代码比数据更可控、可单测 |
| 物品层存 `ItemEnchantments`，部件层存 `Map<ResourceLocation, Integer>` | 物品层随 `ItemStack` 自动存档、同步、`copy()`；部件层不依赖 `RegistryOps`，词条被移除时按未知 id 跳过而不是整份存档解析失败 |
| 不采用原版效果组件与 `LootContext` | `LootContextParamSets#register` 是 private，无法注册新参数集；部件不是 `Entity`，`ENCHANTED_DAMAGE` 等既有参数集无法满足 |
| 获取不使用附魔台 | 附魔台的随机性、青金石与等级经济不适配"更贵更难"；由铭文物品与安装交互承担 |
| 蓝图不携带词条 | `BlueprintData` 只存模板引用，天然不复制；打印产物为无词条部件 |

## 3. 数据形态

### 3.1 词条 JSON

```json
{
  "description": { "translate": "enchantment.machine_max.reinforced" },
  "supported_items": "#machine_max:enchantable_parts",
  "primary_items":   "#machine_max:enchantable_parts",
  "weight": 1,
  "max_level": 3,
  "min_cost": { "base": 1, "per_level_above_first": 0 },
  "max_cost": { "base": 1, "per_level_above_first": 0 },
  "anvil_cost": 0,
  "slots": ["any"]
}
```

| 字段 | 用途 | 取值 |
| --- | --- | --- |
| `description` | 显示名与语言键 | 翻译键 |
| `supported_items` / `primary_items` | 哪些物品能带该词条 | 部件物品标签，或填 `[]` 关闭原版途径（`/enchant`、铁砧附魔书）；取舍见 §7 |
| `max_level` | Java 读取它做等级钳制，是 JSON 里唯一承载数值的字段 | 1–3 |
| `weight` / `min_cost` / `max_cost` / `anvil_cost` / `slots` | 附魔台与铁砧使用，本方案不依赖 | 占位值 |

放置位置：`src/main/resources/data/machine_max/enchantment/<id>.json`，与 `data/machine_max/damage_type/` 同级。`effects` 留空是刻意的扩展点：将来若要让某条词条由数据驱动，往同一份 JSON 的 `effects` 里加组件即可，存档与 id 不变。

### 3.2 部件存档

`RegularPartData` 增加可选字段 `runes`（`Map<String, Integer>`，键是词条 id，值是等级），JSON 与固定序 `STREAM_CODEC` 同步修改。字段缺失按空表处理，既有存档不需要迁移。`VehicleData` 聚合 `RegularPartData`，同步随既有载具数据包下发，不新增网络包。

## 4. 代码骨架

**词条行为**：一个接口，每个 hook 一个默认方法（默认原样返回）。每个词条一个实现类，只重写自己关心的 hook。

```java
public interface PartRune {
    default float damageTaken(PartEnchantContext ctx, int level, float amount) { return amount; }
    default float durabilityDamage(PartEnchantContext ctx, int level, float amount) { return amount; }
    default int   reloadTicks(PartEnchantContext ctx, int level, int ticks) { return ticks; }
    default int   projectileCount(PartEnchantContext ctx, int level, int count) { return count; }
    default float spread(PartEnchantContext ctx, int level, float spread) { return spread; }
    default void  onTrigger(PartEnchantContext ctx, int level) { }
}
```

**分派表**：`Map<ResourceKey<Enchantment>, PartRune>`，用 `ResourceKey` 而不是 `Holder` 建表，避免类初始化期访问注册表；运行时用 `registryAccess().lookupOrThrow(Registries.ENCHANTMENT)` 解析。

**上下文**：`PartEnchantContext(RegularPart, SubPart, HitBox, AbstractSubsystem, BFDamageContext, RandomSource)`。不借用 `MMPartEntity` 冒充实体，避免语义错位。

**调度入口**：`PartEnchantHelper` 只开下表的 hook，每个 hook 一处调用点。

| hook | 落点 | 线程 |
| --- | --- | --- |
| `damageTaken` | `SubPart#modifyArmorDamage` 返回前，或 `SubPartDamageEvent.Pre` | 物理线程 |
| `durabilityDamage` | `SubPart#settleAccumulatedDamage` 扣耐久处 | 主线程 |
| `reloadTicks` | `LauncherSubsystem` 创建 `ReloadJob` 处；`AmmoLoaderSubsystem#getReloadTimeTicks` | 主线程 |
| `projectileCount` | `LauncherSubsystem#fireSingle` | 物理线程 |
| `spread` | `LauncherSubsystem#fireSingle`，乘 `horizontal/verticalAccuracyMultiplier` | 物理线程 |
| `onTrigger` | 装填完成、开火、被击穿等离散事件 | 随事件 |

多重射击需要给 `ProjectileType#fire` 增加弹丸数覆盖参数（当前弹丸数来自 `ProjectileType#bulletNum`，`fire` 没有数量入参），并同步处理弹药消耗、后坐力与制导登记，否则会变成免费弹药。

## 5. 生命周期与线程

1. 玩家用铭文物品对部件物品或已装配部件安装词条；服务端校验部件类型、槽位上限、互斥关系与等级范围。
2. 装配时把物品上的 `ItemEnchantments` 抄进 `RegularPart`（`VehicleAssemblyServerHelper#handle` 构造部件的位置），部件实例持有 `Map<ResourceLocation, Integer>`。
3. 存档按 §3.2 写入；读档时逐 id 解析，未知 id 跳过并记一次日志。
4. 反拆（撬棍）把词条写回产出的部件物品；焊枪拆成材料时词条不返还，需在 tooltip 或文档中明示。
5. 物理线程只读。词条集合在装配、拆装、安装时解析成不可变快照（`volatile` 字段或 `AtomicReference`），`RandomSource` 不在线程间共享；概率类效果在主线程或物理线程各自的随机源上掷。

## 6. 代价与获取

| | 装备附魔 | 部件词条 |
| --- | --- | --- |
| 获取 | 附魔台随机 + 青金石 + 等级 | 研究解锁 + 制造材料 + 安装耗时 |
| 上限 | 无硬上限，靠 `exclusive_set` | 每部件 1–3 槽，按吨位或部件等级 |
| 失败与代价 | 随机性 | 安装失败损耗材料；拆卸按比例损耗 |
| 复制 | 铁砧合并、图书 | 蓝图不携带；拆卸返还或降级 |

槽位上限、互斥组、允许的部件类型都写在 Java 表里，与词条 id 同处一张注册表；`Enchantment` 的 `exclusive_set` 保持空，避免冲突规则分散在两处。

## 7. 未决项

- **保护作用面**：一次命中会流经履带装甲层、子系统耐久、`SubPart` 耐久、载具 HP、连接点结构完整性、物理冲量六个出口。词条是保护其中一部分还是全部，需要产品决策；落点不同会改变结构冲击与冲量是否被减免。
- **概率免伤与线性减伤的取舍**：概率免伤是新增语义，原版保护是线性减伤。两者可并存，但要先定主效果。
- **附魔台与铁砧路径**：`supported_items` 填部件标签会同时打开铁砧附魔书路径；是否保留这条获取路径（把附魔书当作铭文载体）未定。`PartItem#isEnchantable` 需要显式覆盖为 false，因为半成品部件物品带 `MAX_DAMAGE`（材料缺口），默认判据会把它当成可附魔物品。
- **拆卸返还策略**：撬棍返还部件物品（词条可写回），焊枪拆成材料（词条消失）。是否在焊枪路径返还附魔书或部分材料，未定。
- **客户端呈现**：原版 tooltip 会列出"名字 + 等级"，是否追加一行计算后的数值（如"受损伤害 −24%"）、是否需要 HUD 标注，未定。
- **词条 id 的稳定性**：id 即存档数据，发布后不能改名；改名需要别名迁移表。是否需要 `/machine_max rune` 调试命令（安装、移除、列出）未定。

## 8. 风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 半成品部件可附魔 | `Item#isEnchantable` 默认要求 `MAX_DAMAGE`，而材料缺口正占用该字段 | `PartItem#isEnchantable` 显式返回 false |
| 数据包重载 | `/reload` 会重载附魔注册表 | 词条随 mod 数据包发布、id 稳定；部件侧未知 id 跳过 |
| `ItemEnchantments` 序列化 | 其 codec 是注册表引用，需要 `RegistryOps` | 部件侧不存 `ItemEnchantments`，只存 id + 等级 |
| 物理线程读词条 | `damageTaken`、`fireSingle` 在物理线程执行 | 主线程解析快照，物理线程只读 |
| 复制与丢失 | 蓝图、反拆、配方产物三条路径都可能复制或吞掉词条 | 蓝图不携带；反拆写回；配方产物不带词条，并在文档中写明 |
| 数值硬编码 | 逻辑在 Java，数值散落在实现类里 | 数值集中在 `MMServerConfig` 或每词条的常量表，便于平衡迭代 |

## 10. 验收与测试

- **纯函数单测**：每个 `PartRune` 实现的 hook 是纯函数（等级 + 输入值 → 输出值），直接用 JUnit 断言等级曲线，不构造世界。
- **GameTest**：词条安装校验、装配快照、存档往返、反拆写回、未知 id 跳过、装填时长、弹丸数、伤害结算。
- **实机**：tooltip 与拒绝提示的文案、安装交互的手感。

## 11. 未来扩展

- **数据驱动效果**：保持 `(id, level)` 存储不变，给对应词条的 JSON 增加 `effects`，`PartEnchantHelper` 先查 `Enchantment#getEffects`，命中走数据、未命中回退到 Java 实现。这是现在就把 `effects` 留空的原因。
- **内容包词条**：需要内容包加载器在注册表冻结前注入数据包条目，属于独立项目；在此之前内容包只能引用 id。
- **词条与子系统/模组配合**：新的 hook 按"一个 hook 一处调用点"的规则增补，不引入通用事件总线。
