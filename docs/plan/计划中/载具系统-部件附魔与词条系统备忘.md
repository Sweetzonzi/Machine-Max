> 状态：计划中，未细化。本文记录方向、已定决策与未决项，供后续展开为实施计划，不是实现计划。

## 1. 目标与边界

载具部件可以携带**词条**：在部件受损、装填、开火等时机生效，效果由 Java 实现，条目定义随 mod 的数据包发布。

玩家拿到的不是随机刷出来的"部件附魔"，而是一枚**铭文**：可交易、可堆叠、可安装的中间物品。铭文由原版（或其它模组）的附魔书在铁砧上**铭刻**而来——书里的附魔按映射表翻译成本项目的词条，等级同时被压缩。附魔书是原料，铭文是产物，载具上跑的始终是本项目的 Java 逻辑。

与装备附魔的差异是设计目标，不是副作用：单价更高（一本书 + 一块铭板 + 经验等级）、上限更低（每部件两槽、词条最高 3 级）、不能沿蓝图复制。

边界：

- 载体是 `RegularPart`；`SubPart` 与子系统是效果的落点，不是词条的载体。
- 词条定义与映射表都随 mod 的数据包发布。词条 id 只能在数据包里登记；映射表是数据包注册表，第三方数据包可以加行（内容包是资源包，不能）。
- 部件物品不进附魔台、不进铁砧；铁砧只承担"书 + 铭板 → 铭文"这一步。
- 不做通用"附魔效果总线"，只开与词条一一对应的少量 hook。

## 2. 已定决策

| 决策 | 理由 |
| --- | --- |
| 词条寄存在原版 `Enchantment` 注册表 | 该注册表是数据包注册表，自带描述、最高等级与客户端同步，并为将来的数据驱动效果留了 `effects` 字段 |
| 每条词条一份 JSON，只写名字、可附魔范围与 `max_level` | `effects` 留空；`weight` / `min_cost` / `max_cost` / `anvil_cost` / `slots` 是 `EnchantmentDefinition` 的必填项，填占位值 |
| 效果逻辑写在 Java，按 `ResourceKey<Enchantment>` 分派 | 不注册效果组件、不写条件 DSL；词条数量有限且由第一方维护，代码比数据更可控、可单测 |
| 铭文是独立物品 `machine_max:rune`，词条身份与等级存在 `machine_max:runes` 组件里 | 需要一个可交易、可存储、可安装的中间物；单原型物品 + 组件与 `part` / `track` / `assembly` 的既有做法一致 |
| 铭刻在铁砧上完成，附魔书放左格、空白铭板放右格 | NeoForge 的 `AnvilUpdateEvent` 能在不改原版菜单的前提下接管产物与成本，产物槽本身就是预览，经验等级是原生成本；不需要新方块，也不需要 Mixin |
| 原版与模组附魔到词条的映射是数据包注册表 `machine_max:rune_conversion` | 附魔 id 是开放集合（模组随时新增），映射必须能增量扩展；注册表带网络编解码器，两端拿到的映射一致，铁砧预览不会与服务端分叉 |
| 等级映射默认 `min(附魔等级, 词条最高级)`，可逐条覆写 | 默认规则让首批 7 行映射里 6 行不必写等级表；覆写留给"高等级书只产出低等级铭文"的例外与"该等级不可铭刻"的封堵 |
| 物品层与部件层都存 `Map<ResourceLocation, Integer>` | 不依赖 `RegistryOps`；词条被移除时按未知 id 跳过而不是整份存档解析失败；反拆写回与装配读写共用同一种形态 |
| 不采用原版效果组件与 `LootContext` | `LootContextParamSets#register` 是 private，无法注册新参数集；部件不是 `Entity`，既有参数集无法满足 |
| 获取不使用附魔台 | 附魔台的随机性、青金石与等级经济不适配"更贵更难"；由铭刻与安装承担 |
| 词条只作用于宿主部件 | 每块装甲各自承担一份成本，收益随车体规模线性增长，不需要额外的全局叠加上限 |
| 蓝图不携带词条 | `BlueprintData` 只存模板引用，天然不复制；打印产物为无词条部件 |

### 2.1 核实依据

| 编号 | 事实 | 位置 |
| --- | --- | --- |
| F1 | `Registries.ENCHANTMENT` 由 `RegistryDataLoader` 从 `data/<ns>/enchantment/` 装载，条目无法在代码里 `DeferredRegister` | 注册表装载清单 |
| F2 | 铁砧在左格非空时经 `CommonHooks#onAnvilChange` 触发 `AnvilUpdateEvent`；事件给出非空产物即跳过原版逻辑 | `AnvilMenu#createResult` |
| F3 | 取走产物时清空左格，按 `repairItemCountCost` 消耗右格；`AnvilUpdateEvent#setMaterialCost` 正是写入该字段 | `AnvilMenu#onTake`、`CommonHooks#onAnvilChange` |
| F4 | 产物可取的前提是 `cost > 0` 且玩家等级足够；创造模式跳过等级检查 | `AnvilMenu#mayPickup` |
| F5 | `AnvilRepairEvent#setBreakChance` 可以把铁砧损耗概率置零 | `CommonHooks#onAnvilRepair` |
| F6 | 数据包注册表用 `DataPackRegistryEvent.NewRegistry#dataPackRegistry(key, codec, networkCodec)` 注册，给出网络编解码器时同步到客户端 | `DataPackRegistryEvent` |
| F7 | 附魔书的附魔存在 `DataComponents.STORED_ENCHANTMENTS`；`EnchantmentHelper.getEnchantmentsForCrafting` 对书取该组件、对其它物品取 `ENCHANTMENTS` | `EnchantmentHelper` |

## 3. 数据形态

### 3.1 词条 JSON

```json
{
  "description": { "translate": "enchantment.machine_max.plating" },
  "supported_items": "#machine_max:enchantable_parts",
  "primary_items": "#machine_max:enchantable_parts",
  "weight": 1,
  "max_level": 3,
  "min_cost": { "base": 1, "per_level_above_first": 0 },
  "max_cost": { "base": 1, "per_level_above_first": 0 },
  "anvil_cost": 0,
  "slots": ["any"]
}
```

| 字段 | 用途 | 取值 |
| --- | --- | --- |
| `description` | 显示名与语言键 | 翻译键 |
| `supported_items` / `primary_items` | 哪些物品能带该词条 | 指向空标签 `#machine_max:enchantable_parts`，关掉原版途径（`/enchant`、铁砧附魔书） |
| `max_level` | Java 读取它做等级钳制，是 JSON 里唯一承载数值的字段 | 1–3 |
| `weight` / `min_cost` / `max_cost` / `anvil_cost` / `slots` | 附魔台与铁砧的原版逻辑使用，本方案不依赖 | 占位值 |

放置位置：`src/main/resources/data/machine_max/enchantment/<id>.json`，与 `data/machine_max/damage_type/` 同级；`supported_items` 引用的标签是 `data/machine_max/tags/item/enchantable_parts.json`，内容为空列表，原版附魔途径因此对任何物品都不成立。`effects` 留空是刻意的扩展点：将来若要让某条词条由数据驱动，往同一份 JSON 的 `effects` 里加组件即可，存档与 id 不变。

### 3.2 铭文与铭板

| 物品 | 属性 | 组件 |
| --- | --- | --- |
| `machine_max:rune`（铭文） | `stacksTo(16).fireResistant()` | `machine_max:runes`，恰好一条 `(词条 id, 等级)` |
| `machine_max:rune_blank`（空白铭板） | `stacksTo(16)` | 无 |

`machine_max:runes` 的值是 `Map<ResourceLocation, Integer>`：持久编码 `Codec.unboundedMap(ResourceLocation.CODEC, Codec.INT)`，网络编码 `ByteBufCodecs.map(..., ResourceLocation.STREAM_CODEC, ByteBufCodecs.VAR_INT)`。铭文恰好一条，部件物品零到两条，两者共用同一个组件与同一套 tooltip 渲染。

铭文 tooltip：词条名 + 罗马数字等级 + 一行按等级算出的效果摘要（如"受损伤害 −12%"）。词条名取 `Enchantment#description`，等级上限取 `Enchantment#getMaxLevel`，两点都从注册表读，不在物品侧另存。

空白铭板配方（起点值，随 M5 标定调整）：2 结构组件 + 2 电子组件 + 1 紫水晶碎片 → 2 块。

### 3.3 映射表

```json
{
  "enchantment": "minecraft:protection",
  "rune": "machine_max:plating",
  "xp": 4
}
```

| 字段 | 必填 | 含义 | 缺省 |
| --- | --- | --- | --- |
| `enchantment` | 是 | 来源附魔 id | — |
| `rune` | 是 | 目标词条 id | — |
| `xp` | 否 | 每级经验等级成本，实际成本是 `xp × 目标等级` | 4 |
| `levels` | 否 | 显式等级映射，下标是附魔等级 − 1；写 0 表示该等级不可铭刻 | `min(附魔等级, 词条 max_level)` |

放置位置：`data/<ns>/rune_conversion/*.json`，注册表键 `machine_max:rune_conversion`，条目 id 由作者自定（推荐 `<附魔命名空间>/<附魔名>`）。装载期校验：

1. `rune` 必须解析到已注册的 `Enchantment`，否则整条丢弃并记一条 error。
2. `xp` 必须非负，`levels` 长度不超过 32、每项落在 `0..max_level`。
3. 同一条附魔被多份映射声明时，按条目 id 字典序取第一条，其余记 error——取第一条而不是后写覆盖，保证两端与服务端重启后的结果一致。

映射表随注册表同步到客户端，因此铁砧预览与服务端判定用的是同一份数据。

### 3.4 部件存档

`RegularPartData` 增加可选字段 `runes`（`Map<String, Integer>`，键是词条 id，值是等级），JSON 放在 `sub_parts` 之后，`STREAM_CODEC` 末尾追加同样的键值表。字段缺失按空表处理，既有存档不需要迁移。`VehicleData` 聚合 `RegularPartData`，同步走既有的载具数据包。

## 4. 玩家流程

### 4.1 铭刻（铁砧）

1. 左格放附魔书、右格放空白铭板。产物槽出现铭文即为预览：名字、等级、效果摘要都在 tooltip 里。
2. 成本 = `xp × 目标等级` 级经验（默认 4 级/级，即 4–12 级），另消耗一块铭板（`materialCost = 1`）。
3. 铁砧不磨损：命中铭刻时把 `AnvilRepairEvent` 的损耗概率置零。
4. 不产出铭文的情形：书里不止一条附魔；没有映射行；`levels` 把该等级写成 0；目标词条解不出来。产物为空，玩家拿不走，也不消耗任何东西。
5. 铭板放在左格不产出。原版取走产物时会清空左格，整叠铭板会一起消失；只有书在左（书不可堆叠）时成本才与数量无关。
6. 两端都执行：`AnvilMenu#createResult` 在客户端也会走一遍，映射表是同步注册表，两端看到的产物与成本相同。经验不足时由原版 `mayPickup` 挡住，创造模式免经验。

### 4.2 安装（右键部件）

对已装配的部件右键（手持铭文），服务端校验通过后写入宿主 `RegularPart`，两端取消原版交互。校验规则：

| 规则 | 判据 | 拒绝反馈 |
| --- | --- | --- |
| 部件已装配 | `part.assembly != null` | actionbar 提示"未装配的部件不能刻写" |
| 同 id 只升不降 | 已有同 id 时，新等级必须更高；写入即覆盖，旧铭文消失 | 提示"已刻写更高或同等级" |
| 有空槽 | 没有同 id 时，已有词条数必须小于 2 | actionbar 提示"铭文槽已满" |
| 等级合法 | `1 <= 等级 <= 词条 max_level` | 拒绝并记日志（正常途径不会出现） |

成功后消耗 1 枚铭文并同步。安装不额外收费：成本已经在铭刻阶段付过。

### 4.3 拆除、替换与损失

- **撬棍拆下部件**：词条随部件物品保留（写进 `runes` 组件），装到另一台车上继续生效。
- **焊枪拆成材料**：词条消失。
- **部件被摧毁 / 载具爆炸**：词条随部件消失。
- **蓝图打印**：产物不带词条。
- **单独取出铭文**：不提供。要换词条只能把部件拆下来，或者用更高等级的铭文覆盖——这本身就是"部件附魔比装备附魔更难反悔"的一部分。

### 4.4 首批映射

| 原版附魔 | 原版最高级 | 词条 id | 名称 | 最高级 | hook | 起点效果（M5 标定） |
| --- | --- | --- | --- | --- | --- | --- |
| `minecraft:protection` | 4 | `plating` | 装甲强化 | 3 | `damageTaken` | 每级 −4%，全伤害类型 |
| `minecraft:blast_protection` | 4 | `blast_structure` | 抗爆结构 | 3 | `damageTaken` | 每级 −8%，爆炸 |
| `minecraft:projectile_protection` | 4 | `interception` | 弹道拦截 | 3 | `damageTaken` | 每级 −8%，投射物 |
| `minecraft:fire_protection` | 4 | `heat_shield` | 耐热装甲 | 3 | `damageTaken` | 每级 −8%，火焰与高温 |
| `minecraft:unbreaking` | 3 | `toughness` | 结构韧性 | 3 | `durabilityDamage` | 每级 −15% 耐久损失 |
| `minecraft:quick_charge` | 3 | `quick_reload` | 速装机构 | 3 | `reloadTicks` | 每级 −10% 装填时间 |
| `minecraft:multishot` | 1 | `salvo` | 齐射 | 1 | `projectileCount` | +1 弹丸 |

等级按默认规则压缩：`protection` IV 产出 `plating` III，III 也产出 III，II 产出 II，I 产出 I。同一部件上的两条词条按乘算叠加（如 `plating` III 与 `blast_structure` III 同时作用于一次爆炸），单条词条的减伤上限与材质减伤的叠加上限在 M5 一并标定。

**候选、需要新 hook 或新语义，不在首批**：荆棘 → 反应装甲（要能追溯到攻击者）、经验修补 → 自修复（要周期 tick）、穿透 → 弹芯（要穿深 hook）、力量 → 增装药（要弹丸初速/伤害 hook）、深海探索者 / 冰霜行者 / 灵魂疾行 → 履带抓地（要牵引 hook）、迅捷潜行 → 静音、水下呼吸 → 两栖密封、引雷 → 电容过载。

## 5. 代码骨架

### 5.1 词条行为

一个接口，每个 hook 一个默认方法（默认原样返回）。每个词条一个实现，只重写自己关心的 hook；`damageTaken` 的四条减伤词条共用一个实现类，按构造参数区分伤害类型与系数。

```java
public interface PartRune {
    default float damageTaken(PartEnchantContext ctx, int level, float amount) { return amount; }
    default float durabilityDamage(PartEnchantContext ctx, int level, float amount) { return amount; }
    default int   reloadTicks(PartEnchantContext ctx, int level, int ticks) { return ticks; }
    default int   projectileCount(PartEnchantContext ctx, int level, int count) { return count; }
}
```

首批只开这四个 hook。新增 hook 的准入是"一条词条 + 一处调用点"成对出现：先有要用它的词条，再加方法，不预留散布、周期触发这类暂时没有消费方的方法。

**分派表**：`Map<ResourceKey<Enchantment>, PartRune>`，用 `ResourceKey` 而不是 `Holder` 建表，避免类初始化期访问注册表；运行时用 `registryAccess().lookupOrThrow(Registries.ENCHANTMENT)` 解析。

**上下文**：`PartEnchantContext(RegularPart, SubPart, HitBox, AbstractSubsystem, BFDamageContext, RandomSource)`。不借用 `MMPartEntity` 冒充实体，避免语义错位。

### 5.2 落点

| hook | 落点 | 线程 |
| --- | --- | --- |
| `damageTaken` | `SubPart#modifyArmorDamage` 返回前，或 `SubPartDamageEvent.Pre` | 物理线程 |
| `durabilityDamage` | `SubPart#settleAccumulatedDamage` 扣耐久处 | 主线程 |
| `reloadTicks` | `LauncherSubsystem` 创建 `ReloadJob` 处，读 `AmmoLoaderSubsystem#getReloadTimeTicks` | 主线程 |
| `projectileCount` | `LauncherSubsystem#fireSingle` | 物理线程 |

多重射击需要给 `ProjectileType#fire` 增加弹丸数覆盖参数（当前弹丸数来自 `ProjectileType#bulletNum`，`fire` 没有数量入参），并同步处理弹药消耗、后坐力与制导登记，否则会变成免费弹药。

### 5.3 铭刻与安装的落点

- 铭刻是 `AnvilUpdateEvent` 的一个订阅者：左格是附魔书且右格是空白铭板时，读 `EnchantmentHelper.getEnchantmentsForCrafting(左格)`，要求恰好一条附魔且映射表命中，算出产物与 `cost`，`setOutput` / `setCost` / `setMaterialCost(1)`。左格是铭板、右格是书时不产出，避免整叠铭板被清空。
- 铁砧损耗在 `AnvilRepairEvent` 里按同一判据置零。
- 安装是 `PlayerInteractEvent.EntityInteract` 的一个订阅者：`MMPartEntity` 给出 `subPart`，按 §4.2 的规则改 `subPart.part`，两端取消原版交互。判据与提示文案在服务端执行一次，客户端只做取消。

## 6. 生命周期与线程

1. 附魔书在铁砧上被铭刻成铭文，铭文是可堆叠物品，可以交易、存放、批量携带。
2. 玩家对已装配部件安装铭文；服务端改部件实例的 `Map<ResourceLocation, Integer>`，随即同步。
3. 装配时把部件物品上的 `runes` 组件抄进 `RegularPart`（`VehicleAssemblyServerHelper#handle` 构造部件的位置）。
4. 存档按 §3.4 写入；读档时逐 id 解析，未知 id 跳过并记一次日志。
5. 反拆（撬棍）把词条写回产出的部件物品；焊枪拆成材料时词条不返还。
6. 物理线程只读。词条集合在装配、拆装、安装时解析成不可变快照（`volatile` 字段或 `AtomicReference`），`RandomSource` 不在线程间共享；概率类效果在各线程自己的随机源上掷。

## 7. 代价对照

| | 装备附魔 | 部件词条 |
| --- | --- | --- |
| 获取 | 附魔台随机 + 青金石 + 等级；或村民与战利品 | 附魔书 + 空白铭板 + 铁砧经验（4 级/级） |
| 材料 | 青金石 | 结构组件、电子组件、紫水晶 |
| 上限 | 无硬上限，靠 `exclusive_set` | 每部件 2 槽，词条最高 3 级 |
| 等级来源 | 附魔台随机抽取 | 映射表压缩（保护 IV → 装甲强化 III） |
| 复制 | 铁砧合并、图书管理员 | 蓝图不带；焊枪拆解即消失 |
| 反悔成本 | 砂轮洗掉，成本低 | 只能拆部件或高等级覆盖，成本高 |

## 8. 未决项

- **保护作用面**：一次命中会流经履带装甲层、子系统耐久、`SubPart` 耐久、载具 HP、连接点结构完整性、物理冲量六个出口。`damageTaken` 作用在哪几个出口需要产品决策；落点不同会改变结构冲击与冲量是否被减免。
- **概率免伤与线性减伤的取舍**：概率免伤是新增语义，原版保护是线性减伤。首批四类减伤按线性做，概率免伤留作后续词条的差异化手段。
- **研发门槛**：当前设计靠材料与经验定价，不设研发前置。若 `plating` 之类的基础词条也要研发，铁砧只能以"产物为空"表达拒绝，玩家读不出原因，需要额外的提示通道或改用专用方块。
- **单独取出铭文**：默认不提供。若后续要做，落点是"撬棍对部件"的第二种交互，代价是按比例损耗或降级。
- **诅咒与多附魔书**：诅咒没有正面效果，不映射；多附魔书直接拒绝。是否需要把多附魔书拆成多枚铭文（按附魔逐条计费）未定。
- **模组附魔的兜底**：未映射的附魔不转化。按 `supported_items` 标签猜类别（护甲 → 装甲强化）的兜底能白送一点兼容性，但会产出语义错位的词条，默认不做。
- **客户端呈现**：铭文 tooltip 的效果摘要是逐词条手写文案，还是按 hook 公式自动生成；HUD 是否需要标注本车已生效的词条。
- **词条 id 的稳定性**：id 即存档数据，发布后不能改名；改名需要别名迁移表。是否需要 `/machine_max rune` 调试命令（发放、安装、移除、列出）未定。
- **铁砧的创造模式与多人一致性**：创造模式免经验，等于无限铭文；是否需要限制（例如创造模式也扣经验）未定。专用服务器上映射表靠注册表同步，客户端未同步完成时铁砧预览会暂时为空，需要确认这期间的交互不会误消耗物品。

## 9. 风险

| 风险 | 说明 | 对策 |
| --- | --- | --- |
| 铁砧左格整叠消耗 | 取走产物时左格被清空，整叠铭板会一起消失 | 只认"书在左、铭板在右"，铭板放左格不产出 |
| 映射表两端不一致 | 客户端拿不到数据包里的映射行时会看到空产物，服务端却能产出 | 映射表走同步数据包注册表；铁砧的产物与成本两端都由同一份注册表算出 |
| 铁砧被其他模组改写 | 改铁砧逻辑的模组（如重写合并规则的）会让事件路径分叉 | 只用 NeoForge 事件，不 Mixin；与其他铁砧模组冲突时优先保证本功能可用 |
| 附魔书经济被改写 | 村民、钓鱼、战利品的书都能换成铭文，书价会被拉高 | 这是有意的联动；用铭板与经验把单枚铭文的成本压在高位 |
| 半成品部件可附魔 | `Item#isEnchantable` 默认要求 `MAX_DAMAGE`，而材料缺口正占用该字段 | 铭文不进原版附魔路径，`PartItem#isEnchantable` 与 `RuneItem#isEnchantable` 都显式返回 false |
| 数据包重载 | `/reload` 会重载附魔注册表与映射表 | 词条 id 稳定；部件侧未知 id 跳过；映射表重载后铁砧预览随之刷新 |
| 物理线程读词条 | `damageTaken`、`fireSingle` 在物理线程执行 | 主线程解析快照，物理线程只读 |
| 复制与丢失 | 蓝图、反拆、配方产物三条路径都可能复制或吞掉词条 | 蓝图不携带；反拆写回；配方产物不带词条，并在文档中写明 |
| 数值硬编码 | 逻辑在 Java，数值散落在实现类里 | 数值集中在 `MMServerConfig` 或每词条的常量表，便于平衡迭代 |

## 11. 验收与测试

- **纯函数单测**：每个 `PartRune` 实现的 hook 是纯函数（等级 + 输入值 → 输出值），直接用 JUnit 断言等级曲线，不构造世界。
- **映射表单测**：等级默认规则、`levels` 覆写、0 封堵、重复条目取字典序第一条、未知词条整条丢弃。
- **GameTest**：铭刻产出与消耗、安装校验、装配快照、存档往返、反拆写回、未知 id 跳过、装填时长、弹丸数、伤害结算。
- **实机**：铁砧预览的可见性、tooltip 与拒绝提示的文案、安装交互的手感。

## 12. 未来扩展

- **数据驱动效果**：保持 `(id, level)` 存储不变，给对应词条的 JSON 增加 `effects`，`PartEnchantHelper` 先查 `Enchantment#getEffects`，命中走数据、未命中回退到 Java 实现。这是现在就把 `effects` 留空的原因。
- **内容包词条**：需要内容包加载器在注册表冻结前注入数据包条目，属于独立项目；在此之前内容包只能引用 id。
- **模组附魔的映射行**：第三方模组可以自带 `data/<ns>/rune_conversion/` 把自家附魔接进来，不需要改本项目的代码。
- **更多 hook**：按"一条词条 + 一处调用点"成对增补，不引入通用事件总线。
- **铭文外观**：单原型物品现在靠名字区分；后续可用 `custom_model_data` 给每类词条换贴图，`CUSTOM_ITEM_MODEL` 与 `CustomModelItemRenderer` 已有基础设施。
- **JEI 展示**：把映射表渲染成铁砧配方页，玩家不必靠试。
