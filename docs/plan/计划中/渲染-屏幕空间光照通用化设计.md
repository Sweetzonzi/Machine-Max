# 第一部分 · 现状与目标

## 1. 目标与范围

### 1.1 要做什么

| 项 | 内容 |
| --- | --- |
| **P1** | **通路通用化**：把现有曳光光照的通用部分（深度快照、链与 pass 生命周期、光源表、uniform 上传、屏幕半径剔除、screen 混合）抽成与光源来源无关的屏幕空间光照；曳光成为它的第一个提交者。**观感与参数一个不动** |
| **P2** | **爆炸火光**：爆炸波前沿用一个球状光源照亮周围，半径随波前长大、强度随年龄衰减 |
| **P3** | **光源上限策略**：槽位抬到 32，引入优先级（常驻灯不被瞬态曳光挤掉），超限时记录日志 |
| **P4** | **载具车灯（球光）**：把 `LightingSubsystem` 的 `POINT` 型灯接成屏幕空间光源 |
| **P5** | **载具车灯（锥光）**：锥形衰减 + 朝向 + S3 逐像素遮挡 + S4 法线响应 |

分期只按"能不能单独验收"划分，与优先级无关；P1 是其余各项的前置。

### 1.2 不做什么

| 不做 | 理由 |
| --- | --- |
| 阴影贴图（从光源视角渲染一遍世界的深度） | 需要一条独立的世界渲染通道，成本与收益不成比例；遮挡由 S2/S3 的屏幕空间手段承担 |
| 修改原版光照等级（方块光照表） | 这正是本方案要避开的东西，理由见 §1.3 |
| 屏幕空间反射、全局光照等其它屏幕空间效果 | 与本文目标无关 |
| 分块光源列表（tiled light lists） | 只有"几百盏灯同屏且都要照亮"成为真实需求时才做；设计与理由见 §5.4 |
| 时间复用地渲染光源子集（每帧只画一部分灯） | 在 60 fps 会话下容量收益为零，且与截图验收冲突；完整算术见 §6 |

### 1.3 为什么不直接用原版光照

原版的光照是**体素化**的：世界里每个方块格存一个光照等级，光按方块逐格传播。它的代价与"光照覆盖多少方块"成正比，而且光源一动就要对周围一大片方块重新传播。给一辆车装两个会移动的车灯，等于每帧改几万个方块格的光照等级——这是本方案要避开的开销。

屏幕空间光照的代价与"**屏幕像素数 × 光源数**"成正比，**与光照覆盖的世界体积无关**：一盏 20 m 半径的爆炸火光和一个 3 m 半径的曳光，只要屏幕投影大小相同，代价就相同。

代价的另一面必须说清楚，它决定了本方案**不能**用于什么：

- **它只改画面，不产生光照等级。** 生物看不见这些光、不影响刷怪、不影响作物生长、不影响任何按光照等级判定的游戏逻辑。
- **别的 mod 也看不见。** 它不写任何共享的光照数据，只把光叠在最终画面上。
- **光影（Iris）会话下依然生效**，但那是叠在光影算出的画面上的一层，两者不做一致性协调。

## 2. 现状：已落地的曳光光照

本节是事实陈述，用于界定"哪些部分已经写好、只是位置不对"。

| 位置 | 内容 |
| --- | --- |
| `client/render/post/TracerLightEffect.java` | 一条完整的 PostChain 屏幕空间光照：链加载与释放、窗口尺寸适配、`AFTER_LEVEL` 取世界深度快照、标量与数组 uniform 上传、`chain.process` 后还原主目标绑定 |

| `shaders/program/tracer_light.{json,vsh,fsh}` | 程序契约与片元本体：天空排除、表面点重建、二次窗衰减、光源级遮挡（S2）、screen 混合 |
| `client/render/post/PostProcessingManager.java` | 唯一的事件订阅点与次序所有者 |
| `client/MMClientConfig.java` | `tracer_light_enabled` 开关与 `tracer_light_intensity` 全局倍率 |
| `common/mech/projectile/ProjectileType.java` | 弹种可选字段 `tracer_light_intensity`（内容包字段，**与上面那个同名的配置键是两回事**） |

**通路与光源在这一个方法里分开**：`TracerLightEffect.render` 内部，前半段（`assemble`，约 70 行）是"遍历投射物的 SoA 数组、门禁、算半径与容差、写进扁平数组"，纯投射物语义；后半段（`ensureLoaded` / `captureWorldDepth` / 上传 uniform / `chain.process` / `bindWrite`）与投射物毫无关系。

**现有的照射半径与遮挡容差都按弹种口径折算**（`R = 3 m + 2 cm × 口径(mm)`，上限 8 m；容差 `0.20 m + 2 mm × 口径(mm)`，上限 1 m）。这两条换算是投射物语义，随 `assemble` 一起搬家，不进通用层。

## 3. 三个用途的差异

这一张表是本文的出发点：**能复用的是通路，不是光源**。

| | 曳光（已实现） | 爆炸火光 | 车灯 |
| --- | --- | --- | --- |
| 形状 | 球，R 3–8 m | 球，R 可到 20 m 以上，随波前长大 | 按子系统配置：球（`POINT`）或锥（`BEAM`） |
| 同屏数量 | 多发、瞬态 | 少 | 每车 1–3 个、**常驻** |
| 寿命来源 | 投射物 `lifetime` | 波前年龄（`BlastFrontVisual` 自带插值半径） | 子系统 `isActive()` |
| 光心可见性 | 常被车体或墙挡住，**S2 有效** | 光心被挡住时整团光被误杀，**S2 不可靠** | 灯装在车头、相机通常看得见，**S2 恒成立 → 必然穿墙** |
| 法线响应的重要性 | 次要（光斑主要靠运动与影读作光） | 次要 | **主要**（近景表面的明暗梯度） |
| 数据来源 | `ProjectileManager` 的 SoA 数组 | `ExplosionManager.visuals()` | `VisualEffectHelper.lightingSubsystems` |
| 遍历是否已存在 | 是（`assemble`） | 否，但 `BlastDistortionEffect` 已在消费同一个列表 | **是**（`LightSourceRenderer` 已有定位器世界变换 + `partialTick` 插值 + 失效清理） |

两条从表里直接读出的结论：

1. **火光与球光车灯不需要新的着色器能力**，只是多两个提交者（外加各自的强度包络）。
2. **锥光车灯需要三样新东西**：锥形衰减、S3、法线。其中 S3 不是"锦上添花"——没有它，车灯会自动穿墙，见 §9.3。

# 第二部分 · 通用化设计

## 4. 通用化架构

### 4.1 类型与职责

| 类型 | 职责 | 是否含 GL 调用 |
| --- | --- | --- |
| `ScreenSpaceLight` | 一次提交的记录：光心（相机坐标系下的位置）、世界半径、颜色、强度、遮挡容差。提交器持有一个实例反复复用，避免每帧分配 | 否，纯 CPU |
| `ScreenSpaceLightPriority` | 优先级的整数常量：载具灯 → 爆炸火光 → 曳光 | — |
| `ScreenSpaceLightBuffer` | 光源表：公共剔除（半径非正、光心在相机背后、屏幕投影过小、超出渲染距离、强度非正）、槽位分配与淘汰、写进扁平数组 | 否，纯 CPU |
| `ScreenSpaceLightSource` | 提交器接口：一个实现负责一类光源的来源、门禁、几何、包络与优先级 | 否，纯 CPU |
| `ScreenSpaceLightEffect` | 通路：链的生命周期、窗口尺寸适配、`AFTER_LEVEL` 深度快照、uniform 上传、`chain.process`、主目标绑定还原 | 是 |
| `ProjectileTracerLightSource` | 曳光的提交器：`ProjectileManager` 遍历 + 口径折算 + 曳光门禁 | 否 |

数据流：`Effect.render()` → 对每个提交器先 `beginSource(priority)` 再 `collect()` → `Effect` 把表的数组一次性上传 → 一次 `chain.process`。

`Effect` 与 `Source` 的关系是**一对多**：`Effect` 在构造时接收一个 `List<ScreenSpaceLightSource>`，按顺序依次 `collect`。顺序无正确性影响（见 §4.2）。

#### 接口形态

```java
public interface ScreenSpaceLightSource {
    /** 本提交器所有光源的优先级：数值越小越不该被淘汰。取常量，不在热路径上计算。 */
    int priority();

    /** 往光源表里写本帧的光源。渲染线程调用；禁止分配对象、禁止 GL 调用。 */
    void collect(Matrix4f modelViewMatrix, Vec3 cameraPos, float partialTick, Level level,
                 ScreenSpaceLightBuffer out);
}
```

```java
public final class ScreenSpaceLightBuffer {
    void beginFrame(float focalPx, float maxDistance, float globalIntensity);
    /** 由 Effect 在每次 collect 之前调用一次，把该提交器的优先级盖在本类光源上。 */
    void beginSource(int priority);
    /** 拷贝记录，按 (优先级, 屏幕投影半径) 决定占用哪个槽位；被剔除或未被接受时不写入。 */
    void submit(ScreenSpaceLight light);
    int count();
    boolean isCapped();
}
```

**优先级放在提交器上，而不是放在每条光源上**：一个提交器产出的就是同一类光源，优先级是这一类的属性。同类的两档（例如车灯里的前照灯与尾灯）拆成两个 `VehicleLightSource` 实例、各带一个构造参数即可，这比给每条光源留一个可变字段更不容易写错。

**优先级用 `int` 常量而不是 `enum`**：它只参与两两比较、不参与序列化；`enum.ordinal()` 在有人重排声明顺序时会静默改变淘汰行为，而 `int` 常量的值就写在声明处，重排不会改变它。

**`priority()` 不做成接口的默认方法**：抽象方法让"新加一个提交器却忘了声明优先级"在编译期被拒绝。若给它一个默认值，忘记声明的提交器会拿到某个值并与车灯抢槽位——那是运行期才看得见、且只在光源超限时才显形的错误。

**字段忘记赋值时的行为**：`ScreenSpaceLight` 的各字段在 `submit` 返回后被重置为 `0`，于是漏填的字段落在"半径 0 / 强度 0 / 容差 0"上，被公共剔除直接丢掉。**错误的表现是"这盏灯不亮"，而不是"亮错了"**——前者一眼可见，后者要看很久。代价是每条被提交的光源多几次写入，与公共剔除自身的十几条指令同量级。

### 4.2 为什么合并成一条链

现在每增加一个屏幕空间光照效果，就多一份深度快照 + 多一次全屏 pass + 多一组数组 uniform。合表后是**一次快照 + 一次 pass**，代价只随光源数增长。

合并不损失任何正确性，因为 screen 混合满足交换律与结合律：

```
out = light + src · (1 - light)
```

连续应用两次的结果是 `1 - (1 - src)(1 - l₁)(1 - l₂)`，与顺序无关。因此"分成几条链、按什么顺序叠"与"合成一条链、数组里排前面还是后面"在数学上完全等价。

这条等价有一个边界：着色器在混合前对累加结果做了一次 `min(light, 1)` 截断。分成多条链是**每条链各自截断后再叠**，合成一条链是**求和后截断一次**。两者只在"总光量超过 1"时不同，且都是各自饱和的合理行为——合并后的行为更接近"总光量饱和"，分开则会让先叠的那条链先饱和。这个差别只在极限亮度下可辨，不构成合并的障碍。

合并还消掉一个脆弱点：现有文档明确要求"一帧内所有深度快照必须在第一个以 `minecraft:main` 为输出目标的 pass 之前取完"，因为任何写主目标的 pass 会清空主目标（连同深度）。屏幕空间光照自身只需要一份快照，因此这条约束在本链内部没有失效空间；跨链的部分仍然存在——折射链的快照依旧必须排在屏幕空间光照的 pass 之前。

**不变的部分**：深度仍取自 `AFTER_LEVEL`；每个需要深度的链仍各自声明并拷贝一份快照；写主目标的 pass 之后不再有深度读取。这三条是硬约束，理由与现状记录见 `client/render/post/AGENTS.md`。

### 4.3 数组 uniform 的容量

数组 uniform 的**长度必须在 JSON 里写死**，且不短于着色器里声明的 `count`——不足时 `Uniform.set` 只打一条 WARN 并整段忽略（静默失效）。现状与目标：

| | 现在（16 槽） | 32 槽 | 64 槽 |
| --- | --- | --- | --- |
| `LightView`（每槽 4 个 float） | 64 | 128 | 256 |
| `LightColor`（每槽 4 个 float） | 64 | 128 | 256 |
| `LightTol`（每槽 1 个 float） | 16 | 32 | 64 |
| 合计 | 144 个 float | 288 | 576 |
| 若加锥光参数（每槽 +5） | — | 448 | 896 |

GL 规范给片元阶段非块 uniform 的分量下限是 1024（见附录 A.2），所以**表的大小不是瓶颈**，32 甚至 64 槽都塞得下。真正的约束是 §5.1 的后两条。

## 5. 光源上限

**槽位**是同一帧里能参与光照的光源个数上限。着色器里的光源数组长度必须是编译期常量，所以这个数字在写程序时就定死、运行期改不了。**它限制的不是"世界里能亮几盏灯"，而是"同一帧被逐像素计算的光源有几盏"**；超出的光源不是变暗，而是完全不参与。

### 5.1 上限由三个约束共同决定

| 约束 | 现在 | 32 槽 | 说明 |
| --- | --- | --- | --- |
| ① 表的大小 | 144 个 float | 288–448 个 float | 规范下限 1024 个分量，**不是瓶颈** |
| ② 每像素的剔除循环 | 16 次/像素 | 32 次/像素 | 每光源约十几条算术指令。一屏 200 万像素 × 32 光源 ≈ 10 亿条指令/帧，独显上"能接受但不免费"，集显上明显 |
| ③ 每个存活光源的深度采样 | S2：1 次 | S2：1 次；S3：K 次（K 取 8–16） | **这里才会失控**：S3 下每像素每存活光源采 K 次深度，量级相当于 K 个全屏 pass |

②和③的数量级差别很大：剔除循环是"不管有没有光源都要跑满"的固定成本，深度采样只在剔除通过后发生。所以：

- **上限应当由实测帧时间决定，而不是由估算决定。** 本文给出的 32 是工程起点，不是物理阈值；落地后要按实际帧时间调，并保留一条触顶日志。
- **S3 必须只对衰减值显著的像素做**，否则它的成本按③的最坏情况结算。这条是 P5 的硬要求。

### 5.2 现在超限会发生什么

现有实现在槽位用满且出现新光源时，会比较所有槽位的屏幕投影半径、替换掉最小的一个；如果新光源比所有已占用的都小，就**直接丢弃且不留任何记录**。

后果是：一场大规模交火里，几盏常驻车灯会稳定占据槽位，瞬态曳光被静默丢弃——玩家看到的是"曳光有时候不发光"，且没有任何线索能追。**这条要在 P1 一并修掉**（只加记录，不改行为）；P3 再抬槽位、并给其余提交器填入优先级。

### 5.3 推荐策略：32 槽 + 优先级淘汰

| 措施 | 内容 |
| --- | --- |
| 槽位 | 16 → 32 |
| 优先级 | 由 `ScreenSpaceLightSource.priority()` 给出，编译期强制每个提交器声明；`Effect` 在每次 `collect` 之前经 `beginSource` 盖到本类光源上。三个常量：载具灯 → 爆炸火光 → 曳光（数值越小越不该被淘汰） |
| 淘汰 | 排序键是 `(优先级, 屏幕投影半径)` 二元组：先淘汰优先级最低者，同级内淘汰屏幕投影半径最小者；被淘汰即记录 |
| 诊断 | 本帧发生淘汰时打一条日志（同一次触顶只打一次，恢复后再触顶再打），内容含本帧光源数、槽位数、被淘汰的优先级与提交器 |
| 配置 | 槽位数是着色器与 JSON 的编译期契约，**不做成玩家配置**；它只在实现时改一次 |

**这个二元组排序键在 P1 就落地**，理由是把接口一次定死、避免 P3 再动提交器的契约。P1 只有曳光一个提交器、只有一档优先级，二元组在只有一档时退化为现状的"按屏幕投影半径淘汰"，与现状逐字一致（§7 的"观感不变"论证因此不受影响）。**P3 要做的事只有两件**：给火光与载具灯两个提交器各自填一个优先级常量、把槽位从 16 抬到 32。

### 5.4 真正的解法：分块光源列表

如果将来"几百盏灯同屏且都要照亮"成为真实需求，正确做法不是抬槽位，也不是 §6 的时间复用，而是**分块光源列表**：

1. 把屏幕切成固定大小的小格（例如 16×16 像素）；
2. 每个光源按它在屏幕上的投影范围，登记进它覆盖的每一个格子；
3. 上传成一张"每格有哪些光源"的索引表；
4. 像素只循环**自己格子里的**那几盏灯。

这样"重叠在同一格上的光源数"取代了全局槽位数成为上限，而实际重叠数远小于总数（远处的小光源只占几格）。代价是多一个分桶步骤和一张索引表。

**现在不做**：它需要一个新的 pre-pass 与一张索引纹理，而当前的真实场景（几辆车 + 若干曳光 + 偶尔的爆炸）用 32 槽加淘汰策略足够。把它记在这里，是为了将来撞墙时不必重新论证。

## 6. 时间复用方案评估：每帧只画一部分光源

**思路**：把光源分成若干组，每帧只画一组，轮流循环，靠人眼的时间积分把亮度补回来。这样单帧的表还是那么小，但"能装"的光源数变成"表大小 × 组数"。

这个思路在实时渲染里是真实存在的技术（随机的光源子集抽样 + 时间累积，属于 stochastic light sampling / temporal reuse 一类）。它值得认真算一遍，结论是**不做**，理由如下。

### 6.1 容量：在 60 fps 下收益为零

设帧率 `F`、槽位 `S`、光源总数 `L`，需要分成 `G = ⌈L / S⌉` 组，于是**每盏灯每 `G` 帧才出现一次**，它的闪烁频率就是 `F / G`。要让人眼看成常亮，这个频率得高于闪烁融合频率（约 50–60 Hz，越亮、越靠视野边缘越高）：

| 帧率 `F` | 槽位 `S` | 分组 `G` | 每盏灯刷新率 `F/G` | 结论 |
| --- | --- | --- | --- | --- |
| 60 | 32 | 1 | 60 Hz | `L ≤ 32`，**与不用这个方案完全相同** |
| 60 | 32 | 2 | 30 Hz | 能装 64 盏，但明显在闪 |
| 120 | 32 | 2 | 60 Hz | 能装 64 盏，不闪 |
| 120 | 32 | 4 | 30 Hz | 能装 128 盏，明显在闪 |
| 240 | 32 | 4 | 60 Hz | 能装 128 盏，不闪 |

关键一行是第一行：**`S = 32` 时"每帧画一组"的刷新率恰好是 60 Hz，因此这个方案在 60 fps 会话下换不来任何额外容量**——格子数和每秒刷新次数此时是同一个数。它只在 120 fps 以上、且超出倍率不超过 2 倍时提供容量。

### 6.2 亮度：可以按 Talbot–Plateau 律补偿

每 `G` 帧亮一次的灯，单帧强度乘以 `G`，时间平均亮度不变（Talbot–Plateau 律：闪烁频率高到看不出来时，感知亮度等于时间平均值）。所以"变暗"不是这个方案的障碍，**闪烁才是**——它没法补偿。

### 6.3 运动光源：跳格

曳光每 `G` 帧才更新一次位置，得到的是**跳格**而不是拖尾。而曳光的全部价值就在于平滑：这条方案恰好作用在最需要平滑的那一类光源上。

### 6.4 不解决 S3 的成本

时间复用只解决"表装不下"。遮挡判定无法跨帧借用：拿第 1 帧的深度去判第 3 帧的光，相机一动，遮挡关系就全错。要跨帧复用深度必须引入历史缓冲与重投影（按相机运动把上一帧的结果搬到这一帧），那是另一套基础设施，工程量远超 §5.3。

### 6.5 与截图验收冲突

本项目所有的视觉验证都靠截图，而任何单帧只含 `1/G` 的光源。可以加一个"调试模式一次画全部光源"的逃生开关来绕，但这也说明它是一个**需要逃生舱**的方案，而它换来的容量在 60 fps 下是零。

### 6.6 结论

**不做。** 理由按重要性排序：① 60 fps 会话下容量收益为零；② 与截图验收冲突；③ 对运动光源的伤害正好落在曳光上；④ 不解决 S3 的成本；⑤ 真正的正规做法（随机子集 + 历史缓冲累积）工程量远大于 §5.4 的分块光源列表，而后者没有任何时间伪影。

**留作后备的一条**：如果将来真的要随机抽样，必须给**每个光源一个固定的随机相位**（而不是每帧随机抽），让误差在空间上打散成噪声、而不是形成有规律的整屏闪烁；而且要配历史缓冲累积才算完整。这条不列入分期。

## 9. 载具车灯

### 9.1 数据已经齐了

`LightingSubsystemStaticAttr` 提供了全部所需字段：`lightType`（`POINT` / `BEAM`）、`range`、`color`、`intensity`、`beamAngle`。`LightSourceRenderer` 已经实现了同一套遍历：从 `VisualEffectHelper.lightingSubsystems` 取列表、跳过未激活的、通过定位器拿世界变换并做 `partialTick` 插值、按 `range` 与渲染距离剔除、在 tick 与 render 两处清理失效项。**这些都不需要重写**，通用化后的车灯提交器与它是并列的第二个消费者。

### 9.2 锥形光需要新写的三件事

| 项 | 内容 | 为什么必需 |
| --- | --- | --- |
| **锥形衰减** | 光源表增加朝向与内外锥角；片元里先判"这个表面点是否落在锥内"，再乘一个内外锥之间的平滑过渡 | 球光是全向的，表达不了"只照亮灯前" |
| **S3 逐像素遮挡** | 每个衰减显著的像素沿屏幕空间直线向光源走 K 步、每步比一次深度 | 没有它必然穿墙，见 §9.3 |
| **S4 法线响应** | 从深度导数重建视空间法线，乘一个 `N·L` 因子 | 没有它，正对光柱的墙与垂直的地面读到同样亮度，近景看起来像贴纸 |

三者的实现顺序有依赖：**S3 必须在 S4 之前**（S4 只是给已通过遮挡判定的像素加梯度；先做 S4 的话，阴影里的像素照样是亮的）。

### 9.3 为什么车灯不做 S3 就一定穿墙

车灯的灯泡装在车头，而相机（第一人称或第三人称）几乎总看得见它。于是 S2 判据——"在光源的屏幕位置采一次深度，比光源更近就说明被挡住"——**永远返回"没被挡住"**。

后果：车灯朝一堵墙照过去时，墙会被照亮（正确），但**墙后面的地面同样会被照亮**（错误），因为对墙后地面上的像素来说，它到灯泡的距离确实在 `range` 以内、也确实落在锥内，没有任何一步能发现中间隔着一堵墙。

这不是调参能解决的问题，是判据本身的适用范围问题：S2 的隐含前提是"光源小到可以当作一个点、且它的可见性等价于整团光的可见性"。**灯泡位置永远可见时这个前提在最关键的方向上失效。** 修复只能靠 S3。

### 9.4 体积光锥的去留

现有 `LightSourceRenderer` 用 `RenderType.dragonRays()` 画一组从灯源到远端圆环的三角形，模拟空气中的光柱。它与本文的屏幕空间光照**不是替代关系**：

- 体积光锥 = 空气中看得见的光柱（介质散射）；
- 屏幕空间光照 = 被照亮的表面。

现实中的车灯两者都有。保留体积光锥、但**调低它的不透明度**，避免两者叠加过亮（`addTriangle` 的 alpha 系数与 `intensity` 都在 `LightSourceRenderer` 里，属可调项）。
