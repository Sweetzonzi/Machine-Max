# 载具系统：生命周期与同步设计

> 状态：计划中。本文定义载具登记、物理运行、玩家跟踪和保存的首版契约。源码基线：Machine-Max `da9ed542`、Spark-Core `187fc4e8`、Minecraft 1.21.1 / NeoForge 21.1.219。证据包括源码核对、裸刚体摘挂探针和内置模板编码实测；尚未实现整车生命周期，也未跑整车联机压测。

## 1. 目标与范围

接入内容包的野外结构载具前，先解决一个问题：**一辆车已经存在、需要参与物理模拟、某个玩家需要知道它的状态，这三件事目前没有分开。** 结构里新生成的车和玩家停在野外的车，都不应仅因为存在就一直模拟、占用区块票并向全维度同步。

### 1.1 要解决的问题

| 问题 | 现状及后果 | 本期目标 |
|---|---|---|
| 停放车一直参与世界运行 | 读档和创建都走入世路径；即使静止无人，载具也占用物理空间和区块票 | 无活动需求的车可停 tick、退出物理空间并释放自己的票；再次需要时恢复同一实例 |
| 客户端没有按玩家跟踪的边界 | 登录和换维拿整维度整车数据，后续状态按维度发；若只给这个协议套上进出范围，每次重入还会重发整车 | 只向订阅者发运行状态；缓存已知结构，倍镜切换不触发重建，真实重入且结构版本命中时只补当前初值 |
| 公里级交战不能绑定原版区块跟踪 | 观察者可能没收到目标区块，目标仍需可见，且被击中时服务端必须已有可供命中的载具 | 用现有地面载具验证数百米至公里级观测和交战；目标区地形由服务端按需准备，跟踪不以观察者是否收到该区块为前提 |
| 保存、登记和入世绑在一起 | 读档逐车重走添加，反复做整维度快照；按活跃表保存又会漏掉休眠车 | 旧存档可读，同一份按 UUID 保存的记录集覆盖活跃车和休眠车，每车一条；野外结构能只登记载具，重试或重启不会重复兑现 |

### 1.2 本期范围

覆盖现有 `VehicleCore` 地面载具及结构中放置的固定装配。**飞行器不在本期范围**：当前没有可供测试的飞行器载具，不设计或验收载具在服务端未加载地形中的飞行。公里级地面交战仍在本期范围。存储后端迁移、远景代理和持续位姿压缩不作为首版交付条件。

### 1.3 目标方案与第一批交付

服务端每维度设**载具全表**和**活跃载具表**，后者只引用全表中可参与世界运行的同一对象；启用按需休眠后，必须确认物理入世才发布为活跃。休眠摘掉物理对象和运行索引，唤醒挂回原 `VehicleCore`。客户端按玩家订阅并缓存网络结构；进入跟踪补齐当前状态基线，持续同步沿用各层增量。存档从全表按车提取 `VehicleData`。结构生成走只登记的路径，需要参与世界运行时再唤醒。具体契约见 §3 至 §6。

**允许先交付架构调整。** 读档可一次性把当前维度全部载具恢复为内存对象，这也是内存休眠方案的组成部分。是否把这些对象全部加入物理世界、是否让每个客户端都建副本，是另外两个决定。P0 保持全量物理入世和现有维度同步，仅拆登记、入世、保存的职责；P1 换单车入场协议和按玩家订阅，服务端仍可全量物理入世；P2 才开启按需休眠和唤醒。野外结构批量生成须等 P2；P0 不宣称已经省掉停放车的模拟或网络开销。实施和验收见 §7。

| 场景 | 服务端载具 | 地形需求 | 客户端 |
|---|---|---|---|
| 无活动需求的停放车辆 | 同一个载具对象留在内存，刚体和约束不在物理空间 | 无载具自持票 | 不发运行流；进入可交战范围前唤醒 |
| 驾驶或参与交战的地面载具 | 完整部件、约束和子系统 | 按整车覆盖和交互需求保活 | 向相关玩家发完整运行流；驾驶或控制会话保持订阅 |
| 无人但有活动任务的载具 | 有明确活动理由，不因无人而休眠 | 按任务所需保活 | 只有相关玩家才收到运行流 |

## 2. 现状与代价

- **存盘。** [ObjectManager](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/ObjectManager.java) `#snapshotVehicles/#saveVehicles/#loadVehicles` 把整维度运行实例重新做成 `Set<VehicleData>`，写入 `MMAttachments.LEVEL_VEHICLES`。物理世界初始化时循环 `FULL_STATE` 重建并走 `addVehicle`；添加、拆分、移除、合并和 Level 保存都可触发全表快照，启动逐车重走添加，快照遍历合计呈二次增长。单表便于维度归属和命令查找，`VehicleData` 已有部件拓扑、位姿、速度和多种子系统状态，可复用；问题是整表失效、必定实体化。恢复失败只记日志，后续若由 live 表覆写，原记录可能丢失。
- **活动与区块。** `ObjectManager` 的 Level tick 和 Physics tick 遍历已注册对象，服务端把 `inLoadedChunk` 置真。[VehicleCore](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java) `#onAddToLevel` 将已有部件和履带加入世界、重建信号表并申请地形保活，`#preTick/#updateVehicleTerrainHold` 按当前整车 AABB（含向下一层支撑）续票。正常有效 AABB 上的远处载具往往不在真正卸载的 MC 区块里，而是反过来让区块保持加载。Bullet 自己睡眠不等于停止 MM tick、移除刚体或释放区块；等 `ChunkEvent.Unload` 再休眠会形成循环依赖。现有做法的价值是支撑和持续模拟直观，玩家离开不会让车辆立即失去地面。
- **同步与显示。** 登录、换维请求下发维度全表和运行字段；创建、删除及姿态/耐久、拓扑、子系统等多条增量按维度发。客户端完整重建；[DistantVehicleRenderer](../../../src/main/java/io/github/sweetzonzi/machine_max/client/render/renderer/DistantVehicleRenderer.java) 遍历 `clientAllVehicles`。原版 `MMPartEntity` 则独立配对，注册为 `.noSave()`，生成数据只负责查找所属部件。现有全量假设让按 ID 寻址和远景简单；原版代理掉出跟踪不代表整棵载具不在客户端。按玩家同步须明确整车的远距可见范围、代理到达顺序和结构关系包的交付。
- **现有入场是两条触发路径。** `ObjectManager#transmitVehicleData` 在服务端登录时推送；客户端 `PhysicsLevelInitEvent` 又可以通过 `ClientRequestVehicleDataPayload` 请求同类快照。两处都先下发 `LevelVehicleDataPayload`，客户端按数量收齐后用 `FULL_STATE` 整维度建车，服务端再发子系统与轮面补包。零辆车时没有数据包；切维清理靠客户端生命周期事件。新协议只保留一个世界就绪触发点，用同一个单车入场流程，见 §4.3.2。
- **运行期间的创建与删除。** `ObjectManager#addVehicle` 向本维度广播 `VehicleCreatePayload`（含 `VehicleData`）并补推运行字段，然后调用 `onAddToLevel`。普通 `removeVehicle` 则广播 `VehicleRemovePayload`，客户端按 UUID 找副本并移除；合并吸收走专用载荷，由客户端重演部件转移。P1 的发包点和收件人见 §4.3.3。

两个现有边界需要先处理：

- Spark `PhysicsChunkManager#holdVehicleChunkTerrain` 用 `addRegionTicket(..., 2, ..., true)`，按块聚合、不分持有者。同块一车退出能摘掉另一车的保活，区块内变化的高度范围也不是按持有者替换。方案按「持有者 → 本轮覆盖」做差量，按区块和 section 汇总，并与投射物预约协调。`DistanceManager#addRegionTicket` 以 `33 - 2 = 31` 给中心块定 `ENTITY_TICKING` 级别；向外传播时票级衰减，这不是一个独立的单块 `FULL` 请求。
- `saveVehicles` 是内存快照更新，不是写盘。此版本 `ServerLevel#save` 先 `saveLevelData`（其中调用 `DimensionDataStorage#save`），后发 `LevelEvent.Save`；`LevelAttachmentsSavedData` 在序列化时取 Level 附件，`SavedData#save` 复制 NBT 后交给 IO worker。在该事件更新附件赶不上同一次序列化；P0 的取样点和落盘验收见 §5、§7.1。

## 3. 生命周期与地形

### 3.1 服务端双表契约

两张表都按 `ServerLevel → (UUID → VehicleCore)` 组织。**载具全表是注册与存在性的权威；活跃载具表是全表中获准参与世界运行的子集。** 同一个 UUID 同时出现在两张表里时，取到的必须是同一个 `VehicleCore` 引用。没有独立的休眠表，也没有第二份部件、库存或拓扑。

| 表 | 包含 | 谁读这张表 |
|---|---|---|
| **载具全表** | 当前维度已登记的所有载具，不论是否已入世 | UUID 存在性、管理查询、`snapshotVehicles` 与关服保存；P2 的休眠候选按 §3.2 的派生索引查找 |
| **活跃载具表** | 已发布为可运行的载具，可以无人订阅 | 服务端 Level tick、物理 tick、驾驶和交互的载具查找、完整运行流的候选（P1 发包另验物理就绪） |

| 操作 | 载具全表 | 活跃载具表 |
|---|---|---|
| 启动读档／首次创建 | 登记 `VehicleCore`；读档沿用 `VehicleData`，新建子零件分配新 ID | P0、P1 对读档车全部请求入世，保留现有运行调度时机；P1 发首包另等物理就绪。P2 按需求请求入世并在确认完成后发布；仍在运动或有未完任务的读档车请求入世 |
| 唤醒 | 不动；保留同一个对象 | 刚体、约束、查询与运行索引就绪后登记，并置 `inLevel = true` |
| 休眠 | 不动；保留同一个对象 | 关闭运行入口、摘出活跃表并置 `inLevel = false`；物理空间及查询快照摘除确认后释放地形票 |
| 真正移除（收纳、永久删除、合并吸收等） | 业务提交时注销身份，后续保存排除该车；已休眠的载具不必先唤醒 | 同一次主线程提交关闭世界参与；尚在排队的入世不得重新发布该车。仅进入摧毁状态但残骸还在，不等于注销 |
| MC 区块卸载／玩家退订 | 不动 | 不直接改表；是否休眠由活动需求决定，退订只结束该玩家的运行流 |
| 整个 `ServerLevel` 卸载／关服 | 按全表取最终保存快照，再清理该维度的内存引用；不是永久删除 | 结束该维度的运行并清理活跃索引 |

**复用 `VehicleCore.inLevel` / `isInLevel()`，不设生命周期枚举。** 存在性查全表；能否参与业务运行查活跃表，`isInLevel()` 是该资格在载具上的镜像；刚体是否已挂载则由物理任务和查询快照确认。`ObjectManager` 是服务端两张表及双端 `inLevel` 的唯一发布点，在主线程提交时一并更新运行资格和相应运行索引。P0 保留当前双端「请求入世即进入运行调度」和服务端待地形冻结逻辑，把 `onAddToLevel`、`onRemoveFromLevel`、分裂等路径的直接赋值收归管理器；P1 给服务端网络入场加物理完成步门槛，客户端按 §4.3.2 在基线填完后发布副本。P2 启用休眠后，未入世而等待地形或物理完成的车保持 `false`；已发布的车行驶中暂遇地形未就绪，仍保持活跃，`waitingForTerrain` 只负责冻结与解冻。

**摘挂是操作，不是业务状态。** 同车只保留一个在途操作句柄，用句柄身份区分本次与过期回调。主线程决定，物理 `PRE` 任务完成整批摘挂、核对实际物理空间成员并回报成功或失败；`submitImmediateTask` 返回仅表示已排队。主线程在 Spark `PhysicsSnapshotReadyEvent` 回调中核对本次成功回报及预期刚体的快照成员资格，需给 `WorldSnapshot` 增加按原刚体查询成员的只读入口。这里的预期刚体只包括应参与 `CollisionGroups.SNAPSHOT_TRACKED`（`PHYSICS_BODY`、`PAWN`、`PROJECTILE`）的对象，载具的 `TRIGGER` 交互体和连接器挂点不在该快照内。入场检查本次对象仍登记且所有应追踪刚体都在；退场等它们全部不在。约束和不参与快照的碰撞对象由 PRE 任务核对实际添加／摘除结果（例如碰撞对象的 `isInWorld`），不用查快照推断。过载可能跳过整个刷新，不能按游戏 tick 数推定完成。失败不发布半辆车，先通过同一操作清掉部分挂载或摘挂残留；重复请求合并，反向请求在完成后按当前需求重判。主线程不阻塞等待；退场提交后，旧查询快照不能绕过活跃资格接收新命中。

| `isInLevel()` 的主要读取方 | 迁移规则 |
|---|---|
| `VehicleCore#onStructureChanged`、同车接合、加件／接合及合并 | 业务编辑要求相关整车已活跃、无在途摘挂；休眠车先唤醒再编辑。未登记的构造期装配仍可接线，但不发布世界事件或物理操作。分裂接管已入世的部件，不对它们重复挂载；结构与部件归属在同一提交发布。 |
| Part 的装配进度、做旧等同步 | 活跃只是可发送的前提，具体玩家由 §4.3.2 的收件人入口选取。 |
| `AbstractPart#setTransform`、整车位置和刚体位姿写入 | 双端用明确的直接写入判据（建议名 `canWriteBodyDirectly`）：独占构造且尚未提交物理挂载，或已经按本节确认完全脱离物理空间，两种情况均须没有在途操作。`!isInLevel()` 本身不足以证明该判据。活跃或摘挂中，把写入与同车物理操作串行。非载具装配体不因此改变自己的生命周期契约。 |

**现有入口映射。** `ObjectManager.levelVehicles` 的服务端维度条目可承担全表，`snapshotVehicles` 按该表保存，服务端世界运行遍历切到活跃表。P0 将 `ScriptablePayload` 的两端查找分开：服务端按发送者所在维度查活跃表，客户端查本地副本，两端查不到对象都跳过载具的子系统分发；完成后可撤掉跨维度镜像 `serverAllVehicles`。`levelDestroyableObjects` 是独立的对象运行与 ID 寻址索引：休眠时撤下该车的子零件，唤醒时以原 ID 挂回；其他可破坏对象继续走各自的生命周期。`isRemoved` 和 `inLoadedChunk` 都不代表双表成员资格。

**休眠和唤醒都不重建对象。** 不经 `VehicleData` 往返，`VehicleCore`、`SubPart`、运行 ID、装配和结构版本保持不变。物理入世和玩家订阅的衔接见 §4.1，保存触发规则见 §5。

### 3.2 物理与地形

**以活动需求决定休眠，不看车自己的区块票。** 首版只休眠持续稳定受支撑、线/角速度低、无乘员、无玩家或其他对象依靠车体支撑、无外部绑定和未结算作业的整车。有销毁倒计时、装填预留、动力、信号或 AI 作业的车先保持活跃，不为休眠重写这些计时。物理接触只能保住已经活跃的车；休眠车没有接触回调。休眠前保留整车 AABB，加入全表车的活动需求判断；服务器按玩家／载具的移动和位置变化重算近场及交战范围，先于玩家能站上车或高速载具能撞到车时请求唤醒。范围外还要经过时间滞回才允许休眠。

**摘出物理空间，不执行游戏内销毁。** 先停业务和新指令，结清或撤销已排队的操作。P2 增加以下同一物理批次内可调用的摘挂能力；不走 `VehicleCore#onRemoveFromLevel`、`DestroyableRigidObject#destroy`、连接器解扣或 `TrackLink#dispose`。世界侧代理、声音和索引单独撤下，按 §3.1 确认快照摘除才释放票。

| 对象 | 摘除与挂回 |
|---|---|
| 连接器 | 摘实际关节和在世挂点，保留配对、安装框架与可复挂的 `joint` 引用；两端刚体挂回后再恢复。 |
| 履带 | 从 `TrackLink` 提取只摘物理约束的入口，停止旧的重建任务，保留成员、配件状态、断带和建造进度。刚体挂回后复用履带的约束重建入口；不要求复用 `GearJoint` 实例。 |
| 子零件与交互体 | 约束摘完才摘刚体。以 Spark `PhysicsWorld.removeCollisionObject/addCollisionObject` 保留车身刚体的 `owner` 并维护 `WorldSnapshot`；不用会清 owner 的 `Level.removePhysicsBody`。不支持复挂的辅助交互体或原版代理可以重建。 |

**唤醒恢复世界参与。** 先预约整车覆盖范围，等地形和支撑可查询，再单独检查原位是否被方块或实体占据。原位受阻就保持休眠，报告受阻并按现有活动需求重试；不强行顶开或自动搬车。就绪时在同一物理批次先加刚体、再加约束，清旧接触和支撑读数；主线程确认查询快照后才发布活跃、控制、命中和状态流。

**交战范围保活优先，弹道预约补边界。** P2 首版让可能参与当前交战的车提前唤醒或继续活跃，不等实际弹道接触。发射和弹道预载重算时，以预测的扫掠范围匹配休眠车 AABB，提交活动需求并预载覆盖地形。可复用 `TerrainPreload` 的窗口与调度，但其 `LEAD_SECONDS`（3 个游戏 tick）是地形参数，不是整车唤醒上限。用实车测从请求到查询可命中的时延，据此设置外侧唤醒距离和提前量。若不能保证在玩家接触或弹道到达前就绪，该场景保持载具活跃；不能把尚未就绪的载具默认为可穿透的目标来通过验收。

**已验证的范围。** 用 Spark-Core 1.0.1041 的 Java 接口与 Windows DpMt 原生库做过一次裸 `PhysicsSpace` 探针。试验摘要：两动态刚体和一个 `New6Dof`，以相同对象循环摘约束、摘刚体、挂刚体、挂约束并步进，共 100 次；观察到脱离时位姿不推进、挂回后恢复步进，owner 与三个原生 ID 不变。探针代码和原始输出未入库，这段摘要只提供可复挂的初步证据，不计入可复跑验收；正式整车用例列在 §7.3。保留刚体和形状也会保留其原生内存，首版不承诺压缩全表的常驻内存。

**地面运行以服务端地形就绪为准。** 分别检查 `LevelChunk` 可用、Spark 碰撞地形就绪，以及需要时的原版实体可用，不能用 `hasChunk` 一个判据代替。客户端是否收到该区块与这些检查无关。

**地形票账本属于 Spark。** P2 在 Spark-Core 的 `PhysicsChunkManager` 实现按持有者替换覆盖范围的接口（建议 `updateVehicleTerrainHold(holder, coverage)`，释放等价于将该持有者的覆盖置空）。Machine-Max 的 `VehicleCore#updateVehicleTerrainHold` 及退场路径只提交本实例的区块与 section 覆盖，持有者身份在本实例内稳定，不以可能被新实例复用的 UUID 作为唯一键。Spark 比较该持有者的新旧覆盖，按区块汇总所有持有者实际需要的 section；一辆车离开只撤其贡献，其他车所需 section 不受影响。现有 `vehicleHeldRanges`、`updateActivation`、`releaseChunkTerrain`、区块卸载、待构建地形与管理器销毁统一依据此账本，并协调已有的地形预约。相同 MC 票键不具有引用计数，最后一个依赖该票的来源退出才撤票；被其他来源使用的碰撞地形也不得卸载。两仓库同步迁移调用方，旧的无持有者整块释放接口不用于新路径；若须保留对外兼容签名，只能代理到独立的 legacy 持有者，不得跨持有者清账。Machine-Max 不另建一套区块票账本。

**休眠车的活动候选查询。** P2 在 `ObjectManager` 按维度维护休眠车整车 AABB 的派生空间分桶索引。每车保留一份 AABB，覆盖到的桶只存 UUID 或对象引用；全表仍是存在性权威，此索引不承担第三种生命周期状态。未入世登记、退场时登记／更新覆盖，唤醒等待及摘挂中保持可查询并合并重复需求；发布活跃、注销或维度卸载时清理。允许修改未入世车辆位置的管理入口必须同步更新覆盖。区域查询先按相关桶取候选并去重，再检查实际 AABB 和业务需求，不每 tick 遍历全表休眠车。按固定局部查询范围测候选数、访问桶数及耗时，桶粒度根据实测选择，不另为 P1 活跃车辆强制引入空间索引。

## 4. 玩家跟踪与同步

### 4.1 跟踪范围与远景

服务端维护玩家到载具、载具到玩家的双向订阅。P1 在服务端 Level tick 按当前玩家位置与载具 AABB 重算，登录就绪、新车就绪和会话变化也触发检查。移动的可以是玩家，也可以是车。满足进入距离和权限即走单车入场；越过较宽的离开距离则只向该玩家停流，缓存结构。撤权或退出会话不等距离滞回；合法乘员和控制会话保留订阅。首版不用区块跟踪事件驱动订阅：`MMPartEntity` 仍由原版独立配对，跨块大车只建立一个副本，远距目标不要求观察者已收到目标区块。

**完整运行流只发给跟踪该活跃车的玩家。** 车辆可以活跃而无人跟踪；对休眠车的观测或交战需求可以请求唤醒，但要等物理入世完成才开放完整运行流和命中。单个玩家退订不直接改服务端两张表；服务端休眠要停掉该车的运行流，但不注销载具或提升结构版本。世界特效和投射物可有独立可见性策略；控制和交互上行仍由服务端校验位置、权限和会话。

**倍镜开关、视锥和遮挡裁剪不直接驱动整车进出。** 对允许公开的目标，按服务端交战／观测范围和会话订阅，距离边界设滞回。首版可在有限的远距范围内复用完整副本与现有频率，先测数百米到公里的交战；若倍镜需要更多细节，只增加必要字段或更新频率。之后才考虑低频代理（UUID、时间戳、整体变换、粗外形／外观），代理不构造客户端物理车，也不订阅子系统。滞回、缓存和远景代理均不能绕过服务器授权。

### 4.2 网络结构与运行状态

网络结构定义运行状态的坐标、字段和寻址。结构和状态都从同一权威载具提取，不维护第二套可写拓扑；网络观察副本与存档恢复使用不同的数据契约。

| 数据 | 包含 | 不包含 |
|---|---|---|
| `VehicleStructure` | 载具 UUID、网络结构版本；按安装序的部件 UUID 与定义/variant；实际存在的子零件及其声明键和服务端 `SubPart.id`；连接边的两端、配对后的局部安装框架；履带成员及顺序、型号、绕向、设计节数 | 当前世界位姿、运动速度、连接完整度、血量、库存 |
| 运行状态（多个同步通道） | 当前各刚体的位置、旋转和必要速度；整车/部件耐久、制造与摧毁状态、连接完整度、履带建造量/断裂扇区/相位、当前涂装、可观察的子系统字段 | 拓扑和 `SubPart.id` 绑定表；只有服务端或授权菜单需要的库存等私有数据 |
| `VehicleData`（存档与模板） | 现有的整车保存格式：装配、可恢复状态及保存所需的私有字段；也用于模板初态、蓝图和载具收纳 | 不作观察者跟踪包；整数 ID 不是跨会话的持久身份 |

判据是：**改动若改变成员、配对、约束参考系、ID 绑定，或改变状态如何解释，就换网络结构版本；若仅改变同一结构下的值，不换版本。** 炮塔转动不换版本，重新安装炮塔而改变安装框架要换；连接完整度降低不换，断开连接或移除零件才换。换贴图只改外观，所以放在低频状态；能影响形状、声明顺序或连接定义的 variant 更换属于结构。

**按车订阅不等于按车打包。** 持续同步沿用整车、Part、SubPart、连接器和子系统各自的字段表、ID 寻址和应用相位；见 §4.5。使用 `packDirty()` 的通道按字段表所有者取一次：整车一份、每个子零件或连接器各一份，子系统仍由控制器收拢成装配体批次。每个结果发给该车的全部适用收件人，不能按玩家重取。不加每 tick 构造的整车运行状态对象，也不要求 ARMS-Core 一类非载具装配体切换协议。含结构信息的包（例如履带全量同步）按结构发布规则处理。

#### 4.2.1 安装框架不是当前相对位姿

现有 [ConnectionData](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/data/ConnectionData.java) 同时存边的端点和 `posRotA/posRotS`。它们取自两端 `actualTransform`，是各自刚体局部坐标里的安装框架。`AbstractConnector#attachJoint` 对两端旋转执行一次固定的轴约定转换，再把它们交给 `New6Dof`；`adjustTransform` 可能在安装时写入额外旋转，`alignActualTransformForJoint` 甚至可以在不移动两刚体的情况下改变局部安装框架。不要用默认 locator 重建这些覆盖，也不要在导出时顺手用当前位姿重算安装框架。

用左乘记号，`W_A/W_B` 是两刚体当前世界位姿，`F_A/F_B` 是已经应用轴约定的有效局部关节框架。两侧关节的世界位姿是 `W_A F_A` 和 `W_B F_B`，当下的关节相对变换是 `D = (W_A F_A)⁻¹ (W_B F_B)`，即 `W_A⁻¹ W_B = F_A D F_B⁻¹`。结构存定义 `F` 的值，状态描述此刻的 `W`，不混用。

- 刚性连接的理想情况 `D` 近似单位变换，但求解误差仍可能让真实相对位姿偏离；炮塔角、悬挂压缩、挂车折角都是真实的 `D` 变化，不改装配边。
- 相同的空间摆姿可以来自焊接、铰接，甚至尚未相连的部件。即使某些边可以用相对位姿视觉重建，也不能凭位姿恢复端点身份、自由度或连接关系。
- `VehicleCore#partNet` 的节点是 Part，允许平行边和自环；跨接与部件内部的物理约束落到具体 SubPart 刚体。两层都不假设是树，不从装配图递推唯一世界位姿。模板可显式保存某一静置或展示摆姿。

#### 4.2.2 基线与持续位姿

沿用 `SubPart.id` 定位世界刚体及其运行数据，不另设稠密序号。**P1 在 Spark `PhysicsSnapshotReadyEvent` 的主线程窗口采样并发送待入场批次。** 此时上一轮物理已完成、查询快照已刷新、下一轮物理未启动。`stateOf().update()` 却还没执行：位置、旋转和需同步的速度在这个窗口从同一轮已完成的刚体直接拷贝，不从 `SubPart.transform` 或旧同步字段凑出基线。只采有待入场或换版的车，同版多名观察者可共享这次物理取样，不为所有车维护第二张逐 tick 快照表。P1 用整车首次挂载或结构修改涉及的物理任务完成回报，加上 `WorldSnapshot` 成员查询（§3.1），确认本次结构可用于入场；只发当前结构版本。刷新跳过就等下一次有效事件。耐久、制造进度和子系统读当前游戏线程字段，不要求和位姿属于同一物理子步。持续位姿沿用逐 `SubPart` 的 `assignValues` 和插值节奏，不为入场重排各运行通道。

相对编码若有需要，使用显式参考刚体 `R`，不把车辆形心当作能提供旋转的坐标系：传 `W_R` 和每个独立刚体的 `L_i = W_R⁻¹ W_i`，客户端用 `W_i = W_R L_i` 恢复。`L_i` 是**运行状态**，不是固定挂点；车体相对地面的移动与内部运动都不会冒充改装。只发送一份世界根姿态不等于只同步根刚体，亦不承诺压包或提高底层物理精度。

首版用逐刚体世界位姿，不为未启用的相对编码新增参考刚体字段，也不将不同类型的约束压成关节角。若引入相对编码，参考刚体才进入结构契约；参考体变化须换版、重发基线并重建插值，不能把新根与未对齐的旧样本当成同一帧。速度若保留世界表示，不能把它当作减过根速度的量。

### 4.3 入场、缓存和交付顺序

观察者需要公开的结构和初值；不要先生成带私有 NBT 的 `VehicleData` 再过滤。可以复用装配构造步骤，但不能把 `FULL_STATE` 的输入删字段就当作等价恢复。

- **结构包携带身份和寻址。** 车 UUID 与部件 UUID 是稳定身份；子零件的结构身份是「部件 UUID + 声明键」。每个子零件条目也带服务端分配的 `SubPart.id`，它是 Machine-Max 对象索引使用的整数，现有 `SubPartData.STREAM_CODEC` 就会发送它。客户端沿用该 ID 和连接器、子系统的声明序号寻址；这些绑定随结构一起缓存，不在每次状态基线里重传。ID 只在活动副本存续时注册到客户端对象索引。
- **运行 ID 按服务端会话分配，客户端缓存按连接隔离。** 新建、内容包生成、蓝图及收纳放置分配新的运行 ID，保证同一 Level 内跨 `levelDestroyableObjects` 的所有类型唯一，不另设载具私有计数器。冷启动不承诺复用整数 ID，内存休眠保留原 ID。缓存按连接、维度和车 UUID 隔离；重连清缓存。P1 不支持服务端世界运行期间、客户端已进入世界后的 Spark 内容包定义热重载，更换定义须退出世界并重新加载内容、重连。实施时在 Spark 的实际内容加载入口加守卫：覆盖 `ReloadPackageCommand`、`SparkPackLoaderApplier` 的重载监听器以及 `SparkPackageReloadPayload` 的已入世客户端处理，须在重置、准备或注入定义之前拒绝在线定义变更；初始加载及入世前的远端内容同步照常完成。原版或纯贴图等不改变定义的资源重载可以继续执行，但不得连带重装 Spark 定义。不在首版用整车增版冒充双端定义更新。
- **缓存不持有客户端运行对象。** 服务端只在同一连接上复用已交付的结构版本；客户端结构缓存和服务端的跨次复用记录都设容量上限，不影响活跃订阅。入场头声明的版本若不在缓存（例如已逐出），客户端不发布副本、不应用该车增量，并发单车补结构请求，字段为当前维度会话、车 UUID、入场头声明的版本。同一入场只请求一次。这不是重发世界就绪请求：服务端校验当前会话、该车流及订阅资格，重新入场时强制发送**当前**结构和新基线。退订或注销后拒绝补取，不重放缺失期间的增量。
- **结构版本约束交付，不要求写进每个增量包。** 服务端在结构切换或停流时清理旧结构的待发状态，客户端按同一顺序应用结构、基线与增量，并清理退出副本的待办和插值。连接只保证到达顺序；主线程或业务阶段延期的应用仍要绑定接收时的副本与结构，不能落到新副本。用这些边界约束现有载荷，不为所有增量统一新增版本头。
- **一条结构变更路径。** 螺栓接入、解扣、拆件、分裂/合并、履带成员和安装框架变更，统一经服务端的装配提交点；一次编辑涉及的成员归属、装配图和引用索引一起提交，同时换结构版本并停止旧版增量。对有相关订阅的玩家，等本次编辑的物理变更就绪再发完整的新结构和同版基线。客户端应用新结构，不重演拆合操作，不接收逐操作拓扑补丁，也不拿编辑前的快照解释新装配图。
- **拆分和合并。** 保持已有原件的持久身份，按接收者可见集合交付受影响的新图和移除/停流，作为一个客户端可见的批次切换。一名玩家可以只见过合并的 survivor、从未见过 donor；新结构和基线必须足以显示结果，不能要求客户端已有 donor。可按稳定部件身份复用未变的运行对象，也可替换受影响对象，但代理、座位和对象索引在提交完成后必须指向新归属。
- **跟踪退出不等于注销。** 玩家退订和服务端休眠都用同一条停止指令撤掉客户端副本并保留结构缓存；真正注销复用该指令并使结构缓存失效，通知范围见 §4.3.3。留在缓存中的结构不证明载具当前存在。公开名册不是同步前置条件。

#### 4.3.1 何时发送全量运行状态

**全量指「单车所有对观察者公开的运行初值」，不是整维度，也不是存档的全部字段。** 每次建立或替换某玩家的运行副本都发一次：登录或换维后的首次订阅、新车对该玩家可见、真退订后重入、休眠唤醒后重新建立流、结构换版，以及发现结构缓存失配后的重新入场。普通位姿变化、数值回到默认值、玩家打开倍镜都走现有增量或表现逻辑，不触发重推；不做定时全量广播。同一辆车只唤醒一次，但给每名需要它的玩家分别建立流；其他车辆不用重同步。

| 所属层 | 入场必需初值 | 取值与交付 |
|---|---|---|
| 整车 | 当前耐久、摧毁标记、可见名称和该副本需要的公开配置 | 读当前业务值或同步字段；耐久、摧毁可复用 `VehicleStatusSyncPayload` 的字段表 |
| Part | 制造进度与制造／摧毁状态、共享耐久（若适用）、涂装和做旧 | 从 Part 读当前值，复用已有专用载荷的字段；检查 `RegularPartData` 构造客户端副本时初始化、没有对应下行字段的必需值 |
| SubPart | 各刚体位姿和消费方需要的速度、非共享耐久，以及适用的轮面支撑 | 位姿来自同一轮完成的物理步（§4.2.2）；可复用 `SubPartSyncPayload` 字段。轮面支撑在该窗口直接读 `SubPart#isWheelSupported()` 的 `completedWheelSupport`，不读 Level Post tick 才写入的同步字段；适用轮面明确发 `true` 或 `false` |
| 连接器与履带 | 连接完整度、履带建造量、断裂扇区和呈现所需的当前相位 | 依入场结构寻址取当前值。完整度复用 `ConnectorSyncPayload` 的字段；履带按同版结构取运行字段，不把带拓扑的全量同步当普通增量 |
| 子系统 | 该副本应获知的所有同步字段，包括停在默认值或长期没有变化的字段 | 复用 `SubsystemController#pushAllTo` 的全量读法：刷新派生同步初值，再读字段。库存等私有值按原授权业务另发 |

现有 `ObjectManager#pushVehicleRuntimeState` 只补子系统和 `true` 的轮面支撑，不能直接当作新协议的基线。实施时按上表清点当前 `VehicleData` 构造副本时带入的字段；以已有载荷表达初值，只给确实缺失的公开字段补编码，不造整车运行态对象。基线只读取当前值，不调用 `packDirty()` 或强制标脏，且必须能覆盖零值、`false` 和空值。客户端以初始化语义写入，不把初始损伤当受击，不把初始位姿当持续插值的多帧样本。

#### 4.3.2 登录、换维与逐车发包

1. **客户端准备好后请求一次。** 登录、换维或实际替换 `ClientLevel` 后先清理旧运行副本、代理关系和排队更新。等当前 `ClientLevel` 已安装到客户端、本地玩家与物理空间都就绪，再从客户端主线程发送游戏阶段的就绪请求，可复用 `ClientRequestVehicleDataPayload` 的入口。请求用维度键＋本连接递增的进入序号标识本次进入。世界入口只由就绪请求触发，服务端换维和离线事件负责清理旧订阅。同一请求重复到达不重建，早于已接收序号的请求丢弃。单纯原地重生且 `ClientLevel` 未变，无需重发。
2. **服务端确认世界并选择车辆。** 主线程处理请求时核对连接和玩家当前维度，替换该玩家的旧订阅上下文，发一条回显本次序号的开始消息，即使候选为零也发。随后从当前维度活跃表应用 §4.1 的距离、权限、乘员／控制规则，逐车入场；等待唤醒或之后才获得资格的车就绪时走同一入口。不以整维度 `packetNum` 形成建车屏障。初次有很多候选时可以分 tick 处理，每辆车发出前重验资格并取当前值。
3. **逐车交付：入场头 → 基线 → 入场结束 → 增量。** 入场头带维度会话、车 UUID 和结构版本，服务端不能复用已交付版本时附上结构。基线可分多条载荷，但整批按 §4.2.2 在同一主线程操作内连续采样并投递，不跨 tick 切开，也不与另一辆车的基线或普通增量交错。入场结束发出后才在订阅表登记该玩家已交付的结构版本。客户端在主线程按下述发布契约完成副本，不等待原版代理，不增加客户端确认往返。
4. **旧世界数据不得落入新副本。** 新 `ClientLevel` 等待匹配维度和进入序号的开始消息；旧流的包即使同维度也不接进来。开始／结束边界和连接有序交付负责划分消息，主线程或业务延期任务须绑定入队时的维度会话和副本。进出、结构切换和停流时丢掉旧待办，不给每条存量增量统一加会话头或版本头。

**客户端发布契约。** 入场头构造未发布的 `VehicleCore`，`inLevel = false`，在本次入场范围内维护车 UUID 与已分配子零件 ID 的查找。基线继续采用各层已有字段及载荷；在入场批次内用该私有查找定位对象，直接调用可复用的字段初始化逻辑，不通过 `getVehicle`、`getDestroyableObject` 的公开索引，也不等正常 tick 消费。常规索引与包括 `clientVehiclesToAdd` 在内的回退查找都不得暴露正在填充的副本。这样既保留现有寻址方式，也避免为让 `SubPartSyncPayload`、`ConnectorSyncPayload`、`SubsystemSyncPayload` 等 handler 查得到对象而提前让未初始化对象参与 tick。收齐并验证必需字段之前，不注册运行 ID、不进入客户端 tick、物理空间或渲染。

入场结束时，`ObjectManager` 在一次主线程提交内将完整副本加入 `levelVehicles` 对应的客户端表、`levelDestroyableObjects` 及 `clientAllVehicles` 等公开索引，置 `inLevel = true`，初始化插值并配对已到达的代理，同时按物理任务规则安排客户端空间挂载；发布只证明基线完整、运行入口已开启，不证明挂载任务已完成。结构切换先撤出受影响旧副本的索引，再发布完整的新副本集合，同一提交不得出现重复 ID；旧副本延期清理只作用于原实例，不按复用的 ID 清理新条目。基线缺失、失配或中途停流就丢弃未发布副本及其私有资源，按当前会话的补取／停流规则处理，不留下公开索引或待挂载物理任务。普通增量在客户端主线程按序使用已发布索引查找并应用，不能在入队前缓存一个尚未发布或已退出的对象；必须延期的应用按本节第 4 条绑定副本与结构。

**统一收件人入口。** 服务端所有依赖载具副本的下行（整车、Part、SubPart、连接器、履带、子系统及车相关脚本消息）通过订阅表解析收件人，不直接广播维度。增量只发给当前会话且已投递本车当前结构版本的玩家；用同一个订阅条目记录已交付版本，不设额外 `ready` 状态。退订先从增量收件人中摘除，再发停流；换版则版本不匹配时自动停发，等新基线投递完成再继续。延迟发送的旧结构样本在发送前丢弃。投射物、世界特效、授权菜单和非载具装配体仍按各自规则。入口只选收件人，不接管各字段表或其采样。

#### 4.3.3 玩家已在世界时的新增与移除

- **新车入世。** 玩家放置、命令创建和结构生成先登记到全表。P1 按现有逻辑全量物理入世，P2 按活动需求入世；仅登记、等待物理时都不发单车入场。`ObjectManager` 在主线程确认全表仍是同一实例、首次挂载和查询快照就绪后，重算该车订阅；P2 在此发布活跃条目。符合 §4.1 且当前世界会话已就绪的玩家走 §4.3.2 单车入场。没人符合便不发；尚未就绪的玩家之后由世界就绪请求补入。登录与新车就绪重叠时，同一玩家与车只建立一条流。唤醒也走这个入口。
- **同一个停流消息，两种缓存处理。** 消息只需当前维度会话、车 UUID 和是否注销。单人退订仅发给该玩家；休眠与注销只发给本次仍持有该车流的玩家（入场头已发但客户端尚未发布副本的也算）。尚未发出入场头的候选直接取消。客户端收到消息后撤掉运行副本或未完成的入场，清理渲染、对象索引、代理关联、插值和待应用更新；延期清理须绑定到被停止的副本或入场批次，重复停止是无操作。退订和休眠保留结构；注销删除当前收件人的结构缓存。已经退订且只留缓存的玩家不用补发删除通知：不能靠缓存自行建车，缓存可正常逐出。若业务后来以曾用 UUID 登记新实例，必须使服务端该身份的缓存命中记录失效、强制发送新结构，不能凭 UUID 和碰巧相同的版本号复用旧内容。
- **真正注销。** 收纳先取得业务所需的 `VehicleData`，合并先改妥部件归属。主线程提交时关闭这辆车的交互和持续发包、撤出活跃表与全表、取消待发入场并清掉旧流的待发增量，然后按上条发注销通知；不等物理摘除完成才让客户端退场。延迟的入世完成回调不得把已注销实例加回活跃表；已经挂上的物理对象仍按 §3.1、§3.2 退场，最后释放其资源和票。下次保存从全表排除该车，不把移除通知当作落盘确认。休眠车可以直接注销；仍存在的残骸按耐久、摧毁状态和结构变化同步。整个维度退出时按会话清理，不逐车广播注销。
- **拆分／合并不是独立的普通创建和删除。** 分裂产生的新车与原车的新版结构一起发布；合并时保留方换版，被吸收方注销，但已经迁移的零件不销毁。都按 §4.3 的接收者可见集合一起切换，不能等客户端自行重演或查到另一辆车。

### 4.4 入场载荷编码实测（2026-11-28）

用 `VehicleData.CODEC` 读入仓库全部 24 份内置模板，再用与创建载荷相同的 `VehicleData.STREAM_CODEC` 编码，读取缓冲区字节数。`Deflater` 列是单独压缩这些字节的参考值，不是抓包；不含维度、协议头、子系统运行状态补推和轮地支撑补包，也不是装满物资、经过改装的实车上限。子零件位姿列为 `PosRotVelVel` 的固定每件 52 B（13 个 float）；NBT 列为将每个子零件的两张 NBT map 置空前后的编码差值，含键名、不含保留的空 map 长度。剩余字节不全是静态结构。

| 内置模板 | 子零件 | `VehicleData` 字节 | 单独 Deflater | 子零件位姿 | 两类 NBT 差量 |
|---|---:|---:|---:|---:|---:|
| `vn` | 3 | 1,770 | 708 | 156 | 596 |
| `ae86` | 9 | 5,713 | 1,704 | 468 | 1,948 |
| `m1a2_sep` | 33 | 6,669 | 1,245 | 1,716 | 0 |
| `2s38` | 28 | 12,781 | 2,783 | 1,456 | 5,773 |

全样本编码范围 1,770–12,781 B；表中四个样本的独立压缩范围为 708–2,783 B。`m1a2_sep` 模板的这两张 NBT map 均为空，不代表实车也为空。实车 `SubPartData(SubPart)` 会逐个调用连接器、子系统的 `saveData`，例如储物箱会把物品一起存进去；`ObjectManager#pushVehicleRuntimeState` 则另发子系统同步字段与部分轮地支撑状态。`VehicleData` 整包不是可缓存的网络结构，删掉私有 NBT 的 `FULL_STATE` 也不等价于正常恢复。

### 4.5 持续流量估算与合包取舍

`VehicleStatusSyncPayload` 按车 UUID 发血量和摧毁状态；`SubPartSyncPayload` 按子零件 ID 发位姿、耐久与轮面支撑等；Part 的制造进度、做旧、涂装使用专用包，通过子零件 ID 找所属 Part。连接器按 `(SubPart.id, 声明序号)` 同步。`SubsystemController#flushSync` 已将子系统变化集合成一份装配体批次，接收端在自身 tick 收尾应用。整车与子系统在 `VehicleCore#preTick` 发，子零件在 `LevelTickEvent.Post` 路径结算伤害后发，各有时序和消费者；没有必要为了新订阅机制改成一个状态对象、一个采样时刻。

高频项是 `DestroyableObject#syncToClient`：即使位姿未变，也为每个参与呈现缓冲的 `SubPart` 补位置和旋转。以 33 个子零件的 `m1a2_sep` 为例，按 20 Hz 算，每名接收者每秒有 660 条常规 `SubPartSyncPayload`，不含维修等额外路径。仅位置和旋转是 28 B；计入数据项标识、子零件 ID、终结符与载荷类型名后，只有位姿时约 75 B/条、49.5 kB/s，作为编码下界。若一条还带线速度与角速度，光这两个向量就多 24 B，连字段开销约 100 B/条；不是每条都带。估算不含帧头、其余字段和压缩，不是实服流量。

优先按车限制收件人，先省掉未订阅者的全部持续流量；入场补齐初值后，持续通道仍按各自所有者发。若实测瓶颈是消息数量或重复头，只把 `SubPart` 更新合批，保留每个子零件每次 `assignValues` 的姿态采样语义。原版 bundle 可组织有序交付，但仍编码每个内包的类型名；要省重复头，需要真正的同类条目批次。若热点主要是远场位姿本体，先评估减少刚体数或采样率；降频要配合改造当前「每 tick 一个样本」的插值假设。不要为了少几个低频包重写整车、Part、连接器和子系统的同步。

## 5. 持久化

首版保留 Level 附件 `LEVEL_VEHICLES` 和 `VehicleData.CODEC`。从全表为每个已登记 UUID 保存一份 `VehicleData`，不分活跃或休眠；活跃表不存盘。保留 `ObjectManager` 的快照和保存加载入口、载具恢复构造函数与模板、蓝图、收纳接口。蓝图等业务可继续用 `VehicleData.STREAM_CODEC`，不把它当成观察者载荷。

- **读档和运行变更。** 读档走只登记／请求入世的批量路径，不为每条读档记录刷新附件。P0 保留运行期间创建、移除、分裂和合并提交后刷新内存附件的行为；休眠和唤醒不触发保存。首次恢复尚未完成时不以空全表覆盖附件，恢复失败的记录按下文隔离保留。
- **正式保存的唯一取样点。** P0 在 `ServerLevel#saveLevelData` 入口加窄注入，主线程调用 `ObjectManager#saveVehicles`，在本次 `DimensionDataStorage#save` 序列化前刷新附件；用这一入口替代 `LevelEvent.Save` 上的取样。自动保存、显式保存、关服走同一路径，不从 `LevelEvent.Save` 再调用一次 `dataStorage.save()`，也不在每次增删时等 IO。保存可以用最近一次已发布的位姿与当前业务字段，不为此等待一个物理步。
- **恢复边界。** 内存登记、收纳成功和发移除通知都不是落盘确认；崩溃可能丢掉上次成功写盘后的多次操作。验收用 `/save-all flush` 后终止进程再重启，检查该次保存实际恢复的车、坐标和状态；同时覆盖正常关服。未完成写盘的操作不承诺恢复，也不承诺玩家物品与维度附件跨文件原子提交。

### 5.1 存储后端取舍

| 方案 | 适用性与取舍 |
|---|---|
| 保留 Level attachment，全量表取整维度快照 | **推荐首版。** 不更换后端即可验收内存休眠；仍是整维度读写，保存频率与磁盘检查点另行测量。 |
| 专用维度 `SavedData`：UUID 记录 + 活动车检查点 + 冷快照 | 如果启动或常驻内存成为瓶颈，可仅加载快照再按需创建车辆；但仍可能读入所有记录、脏时重写整个文件，不等于 I/O 分页。迁移须可重跑，缺定义或无法解码的原始记录须保留。 |
| 按锚点的 chunk attachment 或单个可保存根实体 | 冷数据天然分页，根实体可以借用原版异步实体区域存储。单锚点无法覆盖长车另一端，跨块移动、重复恢复和崩溃仍需自己处理。适合结构待办、固定物件或专门的强区块绑定模式，不建议通用车辆首版。 |
| 小型维度目录 + 地区分片或日志 | 可按需加载冷快照、缩小重写范围；自管跨区迁移、缓存、提交和恢复。仅拆成多个 `SavedData` 不会自动获得有界缓存，因为 `DimensionDataStorage` 自身持有缓存。由压测决定二期。 |

保存和网络入场可以共享一次采样，但不共享数据契约。§3.2 的空间索引属于可重建的内存查询辅助，不进入存档。已解码但实例化失败的 `VehicleData` 按 UUID 隔离，不进入运行表，重写附件时仍带回且不与活车重复；附件解码失败则保留原始存档供恢复，不能用空全表覆写。

## 6. 结构生成接入

本节定义世界生成如何进入载具生命周期；配置草案和耐久随机化见[结构生成载具备忘](载具系统-结构生成载具备忘.md)。

Spark 已证明内置模板能经原版模板管理器加载并放置；动态 worldgen 注册表等仍有待验收项。Machine-Max 的 processor 与真实 jigsaw 放置要独立验证，不在 worker 回调创建物理体或写全局 `ObjectManager`。

1. **按拥有者区块记录不可变待办。** 原版 `StructureStart#placeInChunk` 按块放置；`StructureTemplate#processBlockInfos` 的 `finalizeProcessing` 早于放置盒裁剪和实际落块，且 `SinglePoolElement#place` 对 DATA marker 可再走一次处理。因此回调既不是每个模板只执行一次，也不是结构放置成功确认。按实际放置盒、`WorldGenRegion` 中心块与写入约束筛选；不要为了偏移锚点跨去写未拥有的区块。超出 piece 有效放置范围的锚点首版拒绝或另立设计。
2. **运行时限额兑现。** `ChunkAccess#setData/removeData` 会置脏，原地修改内容则须自己置脏；优先以不可变值替换。此版本的 `ChunkSerializer` 读写附件，`LevelChunk` 晋升构造复制附件。`ChunkEvent.Load` 可能早于完全就绪，只入队；之后在主线程非阻塞检查整车覆盖范围。通过落位校验后，构造一辆 `VehicleCore` 并登记到载具全表。无活动需求时不加入活跃表；需要运行时走 §3 的唤醒步骤，验证当前空间与支撑。
3. **结果持久化，而不只按活车去重。** 稳定键含维度、结构/piece 放置身份、规范化锚点和 slot/盐，导出稳定 UUID。在同一权威存储提交兑现结果与载具记录；权威结果没有保住之前，不能先清块待办。可保留待办并按结果账本短路，或设计真实落盘确认后再清理。只查活动表，甚至只查当前载具 UUID，都挡不住载具移走、被捕获、毁掉或合并后旧请求重放。账本保留期覆盖仍可能重放的请求；两个文件之间不假设原子提交。

## 7. 实施与验收

**基线测量。** 统计存档、活跃和休眠车数、在世刚体及约束、MC 票、活跃地形段、每玩家载具数和字节率、启动与保存耗时、堆和进程内存。分开记入场脉冲与持续开销，包含装满库存的实车。

### 7.1 P0：职责拆分，保持现有加载与发包策略

在 `ObjectManager` 拆登记、发布活跃条目和保存。读档、创建仍请求整车入世，保留运行调度时机，关闭自动休眠；客户端沿用 §2 的全维度快照、运行期间创建和移除广播及装配变更包，不引入过渡协议。验收旧存档、登录和换维、创建、分裂／合并与收纳；每个活跃条目与全表指向同一对象，读档不逐车重做全维度快照。按 §5 覆盖「创建一辆、移动现存车、移除另一辆 → 一次 `/save-all flush` → 终止进程再重启」，确认同一次保存的新增、最新位姿与删除都落盘；另验正常关服保存。P0 不把故障前尚未保存的变更或跨文件收纳当成已持久化操作。

随 P0 迁移直接调用 `onAddToLevel`、`onRemoveFromLevel` 或赋值 `inLevel` 的 GameTest 夹具，实际入世和退场走管理器入口；仅用于独立构造测试的未登记对象用独立的清理入口，不为测试重新开放业务运行资格的直写。覆盖双端运行资格与对象索引的一致性。

### 7.2 P1：单车入场与按玩家订阅，暂不启用自动休眠

按 §4.2.2、§4.3 交付物理快照取样点、统一世界就绪入口、单车入场和停流，以及载具增量统一收件人入口，并提升网络协议版本。服务端继续全量物理入世，不依赖 P2 的摘除或地形票汇总。持续同步保留各层载荷。

- **入场顺序。** 双客户端覆盖登录、空维度、A→B→A 快速切维、重复世界就绪、第一批尚未发完时新增或移除一辆车、以及原版代理先到和后到。确认单车独立发布、不等整维度收齐，旧世界的增量和延期任务不落入新车。
- **客户端发布边界。** 暂停在入场头和结束之间，确认整车及各子零件能接收基线而不出现在公开查找、tick、物理空间和渲染中；结束提交后方可查到、`isInLevel()` 为真、首条增量能应用。覆盖缺必要字段、缓存逐出、中途停流、立即换版及旧副本延期清理，确认无悬空索引、重复 ID 或针对未发布副本的挂载任务。已发布及挂载中的刚体写入须符合 §3.1 的直接写入判据。
- **会话内内容定义固定。** 验证在线 Spark 定义重载在污染现有实例或缓存前被拒绝；初始内容同步仍可完成，纯资源重载不改变声明寻址。
- **跨范围。** 两名玩家留在世界内，一人驾车驶入、驶出再进入另一人的跟踪范围，再以观察者移动重复一次。每次进入只建一次流，跨回滞回区不重建，真正退订后无后续增量，缓存命中重入只补初值；驾驶者自身的流不受第二名玩家退订或补推影响。
- **运行中创建与注销。** 一名玩家有订阅资格，另一名没有：仅登记或物理未就绪不发包；就绪后只有前者收到一次完整入场，注销时只有仍持有流的玩家收到停止指令。覆盖入世前删除、客户端入场待补结构时删除、退订后删除、重复删除及收纳后重新放置；确认停流后没有残余增量或可见副本，成功保存后重启不会恢复已注销的车，退订不影响保存。
- **初值与换版。** 新观察者准确拿到默认值、受损、已改涂装和正在作业的车，初始损伤不触发受击，单人补推不影响另一名观察者的增量。核对 `onStructureChanged` 的接线、轮系和履带路径；安装轴、解扣、缺失子零件、平行边和履带成员变化应增版，炮塔转动、悬挂、拖挂折转、受损和涂装不增版。验证闭环结构和当前位姿往返、仅见合并一方的接收者、退订重入、缓存逐出后补取。
- **地面远距。** 用相距约一公里的地面载具，在观察者未收到目标区块时验证可见、可命中。持续开关镜不产生结构包或整车重建。按实测决定是否值得合批、压缩或远场降频。

### 7.3 P2：启用同实例休眠与唤醒

按 §3 交付非破坏性摘挂、地形票的持有者汇总、停车及唤醒策略；复用 P1 的入场协议。先用可复跑的整车 GameTest（连接器、履带、库存）验证：停放不 tick、不发运行包、不可命中；反复摘挂后载具与子零件对象、ID、结构版本、约束关系和库存不变。覆盖快照刷新跳步、重复及反向摘挂、挂载中注销、摘挂中写位姿、原位堵塞、地形未就绪、休眠时删除保存，以及休眠车须先唤醒才可编辑。唤醒后缓存命中只补基线，旧更新不得串入新流。

- **物理成员。** 带连接器挂点、交互体和履带的整车重复摘挂；分别核对参与 `SNAPSHOT_TRACKED` 的车身刚体在查询快照的成员资格，以及不参与快照的对象、约束在物理空间的实际摘挂结果。不能要求 `TRIGGER` 出现在快照中，也不能只检查车身刚体就认定全部摘挂完成。
- **地形持有。** 两辆车覆盖同一区块的不同高度 section，改变其中一车的覆盖并分别按两种退出顺序释放；另验地形预约与车共用覆盖、释放最后持有者、待构建地形及维度清理。检查 section 需求和 MC 票是否按来源正确保留与释放，而非仅检查区块一时仍处于加载状态。
- **休眠索引。** 覆盖跨桶长车、重复候选、未入世登记、反向请求、注销和维度退出；查询结果与全表 AABB 过滤对照，确保无漏项。固定局部查询范围、活动车和玩家数，分批增加远方休眠车，记录每 tick 候选数、访问桶数、查询耗时和索引内存；候选与查询工作不得随无关休眠车总数线性增加。

再用实车测玩家接近／站车、车辆接近和公里级交战下从唤醒请求到可查询、可命中的时延。尚未验证提前量的场景保持活跃，不开启自动休眠。扩大休眠车数时，活动 tick 和持续网络字节不应同比增长；常驻内存另测。

### 7.4 P3：接真实 jigsaw 生成

测试相邻块顺序、旋转／镜像、重复处理、跨块大车、模板缺失、重启和删除后重放；模拟载具记录已写而待办仍在、以及记录未写两种窗口。没有活动需求时只登记到全表，不批量启动物理或向全维度同步。
