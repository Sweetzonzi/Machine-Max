# 模型表面查询与骨骼贴花实现计划

> **状态**：计划中；设计定稿，功能待实现。适用：Minecraft NeoForge 1.21.1，Spark-Core 的 Bedrock cube / poly_mesh 模型，以及 ARMS-Core、Machine-Max 的模型绘制。
>
> 本文定义两项可复用能力：对可视模型做表面射线查询；把独立纹理投影到模型表面，生成随各自 bone 运动的贴花网格。本文中的“拟建类型”和阶段 P1—P7 均是实现约定，不能作为功能已经存在的证据。

## 1. 目标与已定决策

弹孔需要落在实际模型表面；载具徽章、编号和喷绘需要允许任意位置、角度与尺寸。物理 HitBox 与外观可以使用不同几何，两者通过目标标识与入射几何联系。

| 编号 | 决策 | 契约 |
|---|---|---|
| D1 | 使用表面网格贴花 | 复制并裁剪接收模型的一小部分表面，使用贴花自己的纹理与 UV 绘制 |
| D2 | 贴花与底材分辨率独立 | 贴花清晰度由自身纹理、覆盖尺寸和采样决定，不受底材 UV 密度限制 |
| D3 | 提供通用模型表面射线查询 | 输入可视模型、当前姿态、线段和骨骼黑名单，返回实际表面交点 |
| D4 | 骨骼黑名单排除碰撞箱 | 查询与投影共用同一份过滤结果；工具不猜测骨骼命名、不要求添加接收标记 |
| D5 | 所有接收 bone 在创建时确定 | 射线确定中心落点，投影体积确定全部接收面；跨 bone、跨可动子部件分别建立绑定 |
| D6 | 按接收 bone 保存相对位姿 | 每个绑定保存投影器到该 bone 输入空间的完整仿射矩阵；客户端网格缓存也存于该空间 |
| D7 | 使用本次操作的当前模型姿态 | 求交、收集接收面、局部化在同一次操作内完成；不建立历史姿态快照与回放系统 |
| D8 | 几何缓存按需构建 | 创建或资源失效时裁剪；正常绘制仅使用当前骨骼矩阵变换已缓存片段 |
| D9 | 业务范围由调用方给出 | Spark-Core 接受一组模型接收视图；目标、部件集合与 HitBox 黑名单由宿主提供 |
| D10 | 模型查询服务于表现 | 查询失败不改变物理命中、伤害、穿透或跳弹结算 |
| D11 | 表面未命中则跳过弹孔 | 首版不做最近表面吸附；HitBox 覆盖模型空隙时允许有伤害而无弹孔 |
| D12 | 首版处理颜色与透明混合 | 使用实体光照与雾；法线贴图、粗糙度、金属度、真实凹陷和穿孔属于独立扩展 |
| D13 | 后添加的贴花在上层 | 同一 receiver 的绘制范围按唯一的 `creationSequence` 从小到大绘制；上传阶段关闭距离排序；跨 SubPart 的边界见 §7.2 |
| D14 | 首版由代码创建与删除 | 优先接入弹孔；交付模型查询、投影、容器与绘制 API，测试夹具和命中处理器直接调用 |
| D15 | 弹孔复用投射物命中包 | 扩展现有批量命中条目的可选模型定位数据，客户端一并处理，不单设弹孔载荷或发送队列 |
| D16 | 弹孔采用一个固定样式 | 游戏命中统一使用一张贴图和默认尺寸；口径推断、每弹种贴图 RL 与样式同步不属于首版 |

首版接收对象是具有几何表面的装甲、机体和普通模型面。贴花自身支持 alpha。接收底材的逐像素 alpha 镂空、折射玻璃、屏幕空间遮挡投影、多权重蒙皮及纹理烘焙不属于首版验收范围。包含这些材质的骨骼可由调用方加入黑名单；同一 bone 内混合了实面与透明孔洞时，首版不能保证逐像素镂空一致。

首版的业务交付是代码驱动的会话内弹孔。玩家交互编辑、贴纸编辑命令／界面、撤销操作、编辑上行载荷、持久涂装与蓝图存储属于后续产品功能，不列入 P1—P7。后续功能可利用查询结果、投影器和完整 bone 绑定；首版不为它们预建未消费的编辑或存档接口。

### 2.3 几何正确性的实施前置项

`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/model/origin/OPolygon.kt#normal` 是每次求值都调用 `direction.step()` 的 getter，构造期对 `normal` 的乘法作用于临时向量。`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/model/origin/OVertexSet.kt#verticesForQuad` 会在镜像时交换 ±X 面，faceUV 还会交换 ±Y 面。由此，镜像面最终顶点绕序与当前法线属性可能反号。

P1 的 Spark 前置修正是把 `OPolygon.normal` 固化为初始化后的值：对非扁平且含 inflate 后各轴跨度为正的 cube，以最终面顶点绕序的归一化叉积定义外向光照法线。负跨度与扁平 cube 的光照法线及 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/model/origin/OCube.kt#fixInvertedFlatCube` 处理保留，资源入口不得因负跨度或零跨度拒绝加载。查询侧对非零体积 cube 的绕序叉积乘 `sign(sx·sy·sz)`，其中各轴跨度 `s = size + 2×inflate`；这消除负跨度反射造成的绕序反向，使几何法线朝向盒外。跨度含零的扁平 cube 按有面积的面分别求交，不使用零乘积作法线因子，只跳过零面积面。调用方按只读属性使用法线，临时运算使用副本或单独的输出向量。完整几何法线规则见 §4.2，光照法线读取面属性，两者各有明确消费方。

`OPolygon.normal` 的四个消费模块是 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/model/origin/OCube.kt#renderVertexes`、`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/compat/accelerated_rendering/ARBoneRenderer.kt#render`、`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/compat/accelerated_rendering/ARCubeRenderer.kt#render` 和 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/compat/sodium/SodiumCompat.kt#renderCube`（该模块的 bone 路径也读取同一属性）。P1 的修正同时影响基础模型普通与加速路径的镜像面光照，须在阶段内验证所有已启用路径。对含 inflate 后各轴跨度为正的非退化 cube，非镜像六面的绕序叉积方向均等于 `direction.step()`，法线方向的修正只影响镜像面；退化面的方向按本节定义单独断言。

资源依据：第一方模型目录的 65 份 JSON 共含 16914 个 cube。负 size 分量只有 1 个，位于 `src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/models/part/wine_fox/wine_fox.geo.json` 的 `eyes2` bone，`cubes[0].size[2] = -0.252`。按 `size + 2×inflate` 计算，实际零跨度的扁平 cube 有 44 个；原始 size 含零轴的共有 53 个，其中 9 个经正 inflate 形成厚度。因此负跨度与扁平面加载是既有内容约束，P1 夹具应直接覆盖这些资源形态。

`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/model/origin/OMesh.kt#renderVertexes` 当前逐面直接提交原始顶点；在 QUADS 通道中，三角面与非四边形面会跨面拼装。查询的权威拓扑是 §4.2 的逐多边形扇形三角化。P4 同步接入这份拓扑到普通与加速 mesh 绘制：保留 QUADS 接口时，每个扇形三角形独立发出 `(v0,v1,v2,v2)` 退化四边形；不允许把相邻多边形的顶点拼成一个 quad。Machine-Max 第一方内容包 `src/main/resources/spark_modules/` 中模型目录的 `poly_mesh` 条目数为 0，已有内容不能替代三角面、四边面、五边面的合成测试与视觉夹具。

## 3. 坐标、位姿与单位

### 3.1 空间定义

采用列向量，`T_AB` 表示把 B 空间变换到 A 空间；矩阵相乘顺序与 JOML `mul` 一致。

| 符号 | 定义 |
|---|---|
| R | 本次操作的公共参考空间；推荐取目标附近的部件局部空间，避免巨大世界坐标转 float |
| M_i | 第 i 个接收视图的模型根输入空间 |
| B_ij | 该视图内第 j 个 bone 的几何输入空间：已应用 cube 自身变换、尚未应用骨骼链 |
| D | 贴花投影器空间，中心为原点，+X 向右、+Y 向上，沿 −Z 投影 |
| `T_RM_i` | 调用方提供的实际绘制根变换在 R 中的表达 |
| `T_M_iB_ij(t)` | 由当前姿态与同一个 partialTick 求得的完整骨骼链 |
| `T_RB_ij(t)` | `T_RM_i × T_M_iB_ij(t)` |

这里的 B 是渲染器接受的骨骼输入域。Bedrock 顶点可以使用绕 pivot 变换的模型原始坐标；不能假设把坐标减去 pivot 就得到了 B。几何提取与绘制均遵循 §2.1 的矩阵链。

坐标长度使用 Minecraft 方块单位；通常 1 方块按 1 m 解释。已解析的 Spark 顶点直接使用运行时数值。宽、高、深度单独存储，均在 D 中定义。旋转角、纹理像素数和几何长度不得混用。

### 3.2 每 bone 的创建与绘制

创建时，对每个实际接收面所属 bone 求：

```text
T_BD = inverse(T_RB(t_create)) × T_RD
p_D  = inverse(T_BD) × p_B
```

绑定保存 `T_BD`。骨骼链含非均匀缩放时，矩阵可能含剪切，因此使用完整仿射矩阵；不得仅保存位置和四元数后丢掉其余分量。运行时描述保存 3×4 仿射部分，最后一行隐含为 `(0,0,0,1)`。

裁剪后的顶点缓存为 `p_B`，绘制时：

```text
p_R(t) = T_RB(t) × p_B
```

贴花 UV 在创建或从绑定重建网格时确定。骨骼运动时使用缓存 UV；跨关节的片段各随自己的骨骼，关节张开后图案可以分离。

绘制每个 bone 的片段前，复用 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/renderer/ModelRenderHelper.kt#render` 的可见性判据：自身或任一父链的当前 `getLocalScale` 满足该绘制入口的近零缩放条件时，跳过整组片段，不提交退化顶点。P1 将该判据集中为底模型与贴花共用的函数；独立的矩阵可逆性检查负责拒绝不能求逆的候选。

位置使用仿射变换；方向不带平移；法线使用对应线性部分的逆转置并归一化。近零缩放造成矩阵不可逆时跳过该 bone，并累加按宿主／bone 分类的 debug 诊断计数；需要定位时限频输出日志。查询结果的返回类型只有交点或空值；诊断不经返回类型表达，由分类计数与限频日志承担。

### 3.3 当前姿态的一致性

一项创建操作在客户端主线程／渲染线程串行完成，固定本次 partialTick 与根矩阵，内部惰性缓存各 bone 的当前矩阵。求交和投影共用这个操作上下文，结束即释放。

该上下文只避免一次操作内重复取矩阵，不保存过去 tick 的骨骼姿态，不进行时间回溯。创建完成后的附着数据是 §6 的运行时绑定。若请求因预算推迟，则整项操作在处理时读取当前姿态，不把不同帧的半成品拼起来。

## 4. 通用模型表面射线查询

### 4.1 拟建接口与结果

以下类型名为拟建接口；签名表达职责，Java / Kotlin 互操作形式在 P1 固定。

```text
ModelSurfaceView
  receiverKey       // 宿主提供的稳定接收视图标识
  model             // 同一个 ModelInstance；origin / pose / index 均由它派生
  includedBones     // 本视图实际绘制的 bone 集合
  modelToReference  // 与正式绘制对应的 T_RM

ModelSurfaceQuery.raycast(views, context, fromR, toR, excludedBones)
    -> SurfaceHit?  // 沿线段最先命中的合格正面；无交点返回空

SurfaceHit
  receiverKey, modelIndex, boneName
  primitiveId       // geometryFingerprint + bone + cube/mesh、面、三角形索引
  segmentFraction   // 原始 fromR→toR 的 [0,1] 参数
  positionB, geometricNormalB, shadingNormalB
  barycentric       // 插值交点与光照法线
```

`../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/model/ModelInstance.kt#origin` 与 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/animation/model/ModelInstance.kt#pose` 是视图几何与姿态的唯一来源；视图不接受外部单独传入的 origin 或 pose。操作开始时读取该实例的原始几何，资源发布与本次操作串行，不跨资源更新混用骨骼 pivot 和动画。

`receiverKey` 至少区分宿主实例与可独立运动的模型片段；Machine-Max 可由零件 UUID 与子部件名组合。共享 `ModelInstance` 的不同 SubPart 可以有不同绘制根矩阵，不能只用模型对象或 bone 名作为实例身份。

黑名单按 bone 名精确匹配，空集合表示无额外排除；不隐式排除后代。调用方若需要排除一棵子树，先显式展开其所有 bone 名。查询、投影与资源重建必须共用这项语义。按整个目标收集多个 SubPart 时，将它们配置中的 HitBox 骨骼名合并进入集合。

这要求被排除的碰撞骨骼与可见装甲分开建模；如果同一个 bone 同时承载这两种几何，黑名单会连同外观一起排除。内容验收应确认目标资源满足这一前提，不能把该排除结果归因于射线算法失败。

### 4.2 几何提取与查询步骤

1. 按 `geometryFingerprint` 缓存各 bone 的三角形、几何法线、光照法线与局部包围盒。指纹与 primitive 标识定义见 §6.1。
2. cube 从实际 `polygonSet` 提取，应用 cube 自身矩阵；四边形取 `(v0,v2)` 对角线，拆成 `(v0,v1,v2)` 与 `(v0,v2,v3)`，两个三角形共用原多边形绕序。UV 全零且底模型按规则跳过的面不进入接收几何。
3. poly_mesh 按每个多边形的顶点序生成 `(v0,vi,v(i+1))`，`i=1..n−2`；这是三角形、四边形及凸 n 边形查询的权威定义。凹多边形不在首版支持范围，资源入口应报出模型与面索引，不凭 QUADS 通道的实际拼装结果猜测拓扑。
4. 根据 `includedBones`、黑名单与 §3.2 的共用可见性判据筛选候选。对 B 内每个非退化三角形先算 `n = normalize((v1−v0) × (v2−v0))`。cube 的三个有效跨度为 `sx,sy,sz = size + 2×inflate`：三者均非零时，`geometricNormalB = sign(sx·sy·sz) × n`；存在零跨度时，保留有面积面的 n，两侧共面面片各自按朝向参与查询。poly_mesh 的几何法线直接取 n。普通及 mirror cube 的全正跨度因子为 +1；奇数个负跨度的因子为 −1，六面一并修正。几何法线负责背面排除、贴花朝向与投影面向门限；cube 的 `shadingNormalB` 取应用 cube 法线矩阵后的 `OPolygon.normal`，mesh 则取顶点法线插值，仅负责光照。两种法线不互相代替；骨骼负缩放时在 B 中判断几何正反面，法线向外部空间传播使用逆转置。
5. 将线段两个端点用 `inverse(T_RB)` 转到 B。保留端点差，不重新归一化；这样仿射换基后线段参数仍是同一个 `[0,1]`，可跨 bone 比较。
6. 先测 bone 的局部包围盒，再做双面三角形精确求交。排除零面积三角形和超出线段的结果，再用修正后的几何法线与入射方向的点积筛选正面。不能先用仅依赖原始绕序的 Front 求交函数剔除，否则负跨度的近侧面会在法线修正前丢失。
7. 按 `segmentFraction` 取最小值；共边、共面等同距情况按稳定的接收键与 primitive 索引打破平局。容差按候选局部尺度计算并集中定义。
8. 返回实际表面位置、两种法线与重心坐标。原始底材 UV 不进入查询结果、裁剪属性或贴花缓存；逐像素继承底材 alpha 的材质扩展需另行定义其消费链。

初始实现使用每 bone 包围盒与线性三角形查询；接口允许替换成 bone 内静态 BVH。是否加入 BVH 依据 P7 压测，不能为普通动画每帧重建完整世界空间三角形。

### 4.3 物理命中到模型表面的适配

弹孔适配器从已确定的物理命中取得点 h 与入射方向 d，在目标外观范围内查询：

```text
from = h − a·d
to   = h + b·d
a >= 0，b >= 0，a+b > 0
```

`a`、`b` 由宿主依据目标范围提供，覆盖 HitBox 与外观可能存在的前后偏差，且不能无限延伸到其他目标。先从入射侧向前找正面，防止命中点位于外壳内部时误选出口。入射方向取碰撞响应之前的速度；跳弹后的新速度不能用于入射定位。

模型交点为空时返回空值，跳过本次弹孔。无交点、退化面与不可逆 bone 的分类仅进入 debug 计数／限频日志。内部子系统命中是否在外壳留痕，由业务层选择的接收视图范围及命中事件决定；通用工具不根据 HitBox 名猜测外壳。

## 5. 投影器与表面裁剪

### 5.1 投影定义

投影器拥有 `width`、`height`、`depth`、面向阈值、颜色与纹理。尺寸必须有限且大于零。投影盒以 D 原点为中心：

```text
−width/2  <= x_D <= width/2
−height/2 <= y_D <= height/2
−depth/2  <= z_D <= depth/2
u = x_D / width + 0.5
v = 0.5 − y_D / height
```

纹理作者约定图像顶部对应投影器 +Y；上式据此翻转 V。图集只在求出 `[0,1]` 贴花 UV 后映射到图集区域；图集区域需有防串色边距。

弹孔中心取 `SurfaceHit` 的落点，+Z 取外向几何法线，沿 −Z 投影。用与法线不平行的参考轴建立右手正交基，再绕 +Z 施加随机角度；随机种子由命中事件给出。代码调用方也可直接提供投影器位姿，无需先发射射线。

接收面的几何法线变到 D 后，与 +Z 的点积必须达到 `minFacingCos`；该判定不读取光照法线。参数在 `[0,1]` 内，首版默认 `0.1`，用于排除背面与几乎沿面投影的退化情况；内容可显式调整。首版默认值是视觉参数，不代表真实弹道或装甲判据。

### 5.2 创建算法

1. 固定本次 `T_RD`、尺寸、接收视图与骨骼黑名单。
2. 遍历投影体积可能相交的所有合格 bone；射线命中的 bone 只提供中心，不能作为完整接收集合。
3. 为每个候选 bone 算 `T_BD`，通过 `inverse(T_BD)` 把表面三角形送入 D。
4. 用面向阈值排除不合格表面；对每个剩余三角形依次按投影盒六个平面做 Sutherland–Hodgman 裁剪。
5. 交点属性按同一个边参数插值：D 位置、B 位置、光照法线；面向判定沿用源三角形的几何法线，最终光照法线归一化。禁止只检查原三角形顶点是否在盒内，否则会漏掉顶点全在盒外、面却横穿盒子的情况。
6. 裁剪多边形按稳定顺序扇形三角化，丢弃退化输出，按 §5.1 生成贴花 UV。
7. 只有产生非退化三角形的 bone 才建立绑定。结果按 `receiverKey + boneName` 分组，全部成功后原子发布到贴花容器。

投影深度、面向阈值和显式接收范围共同限制穿透。首版的语义是“投影盒内所有合格接收面”，没有“投影方向上只接收第一层”的遮挡保证。盒内叠着两块同向装甲时两块都可能接收；需要限定外壳范围或缩短深度。相机深度测试负责观察时的遮挡，不能提供投影器自身的首层判定。

平面投影在斜面上产生拉伸，在折角处受投影方向影响；这是本方案的图案映射定义。要求沿任意曲面保持图案测地尺寸的涂装，应作为曲面参数化功能另行设计。

## 6. 贴花描述、缓存与生命周期

### 6.1 拟建数据模型

```text
DecalDescriptor
  decalId: UUID
  texture: ResourceLocation        // 代码直接给出贴花纹理；游戏弹孔使用固定资源
  width, height, depth, minFacingCos
  colorRgba, creationSequence
  bindings: List<BoneDecalBinding>

BoneDecalBinding
  receiverKey, modelIndex, geometryFingerprint
  boneName
  projectorToBone: affine3x4        // §3.2 的 T_BD

DecalMeshCache                       // 客户端派生产物，不发包、不保存进存档
  key: (decalId, geometryFingerprint)
  fragments[receiverKey, boneName]
    positionsB, normalsB, decalUvs, triangleIndices
```

`DecalDescriptor` 是会话内贴花附着数据的权威形式，首版仅存于客户端内存。跨多个 bone 的一张贴花只有一个 `decalId`，每个 bone 都有独立绑定；不得仅存中心 bone 和一个世界位姿。

`geometryFingerprint` 根据标准化几何、骨骼静态定义与拓扑确定，不包含每帧动画或底材像素内容。`primitiveId` 的有效域就是这一指纹内的 bone、几何种类、面与扇形三角索引；资源变化不能把旧索引套到不同指纹上。

缓存失效只使用 `(decalId, geometryFingerprint)`。跨不同模型几何的绑定分别落入对应指纹的缓存项，同指纹的多个 receiver 由片段分组区分。描述与缓存只在当前客户端进程内存在；代码删除一项时释放该 id 的全部缓存，进程结束后全部释放。同几何资源重载与几何变化分别遵循 §6.2，首版不设置进程内恒定的算法版本字段或相关失效分支。

`creationSequence` 由客户端容器在一次新建成功发布时从自己的单调计数器分配；命中处理器与开发夹具都调用同一 create，不传入外部添加序号。同一宿主容器的全部 receiver 共用这个计数器，重复 id 不消耗序号。网络只传命中身份与定位信息，客户端按命中条目顺序调用 create；不同客户端的序号数值可以不同，契约是各自容器内实际添加的先后顺序。`decalId` 只作身份、去重与随机种子，不能参与层次比较。

### 6.2 重建与回收

- 首次创建：按 §5.2 收集所有接收 bone，同时产生描述与网格。
- 动画与宿主运动：更新绘制矩阵，复用描述和网格。
- 单项删除：按 id 移出描述并释放所有片段；需要另一种图案或位姿时，由代码创建一个新 id 与新序号的贴花。
- 同一 id 的重复创建：返回既存项，不重新裁剪、不分配新层次、不修改其描述。
- 贴花纹理资源重载：按材质引用刷新纹理；UV 使用归一化坐标，纹理分辨率可以改变。
- 相同几何的资源重载或缓存回收：对描述里已经保存的每个绑定，在 B 内用固定的 `T_BD` 重建网格，不重新发现邻近 bone，不按当前关节姿态重新分配接收集合。
- 模型几何指纹变化或 bone 缺失：该绑定判为失效，丢弃失效片段，不自动吸附到其他 bone。
- 目标移除、客户端换维度或连接断开：释放宿主对应的描述、网格和待处理请求。

这里保存的是每个接收 bone 的相对投影位姿；资源重建不依赖创建时的整具模型姿态。

### 6.3 容器与预算

客户端容器由代码直接调用，最小操作集为：

```text
create(decalId, views, context, projector, texture, colorRgba=WHITE)
    -> DecalDescriptor?              // 完整生成后发布；无接收面或超限则为空
remove(decalId) -> boolean           // 单项摘除，并释放该 id 的全部片段
clear()                             // 宿主卸载与连接结束时释放全部项
```

`create` 先在临时变量中准备完整描述与网格，然后一次性发布；生成失败不改变已有项。同一 id 按 §6.2 去重。`remove` 只影响指定 id；不通过清空并重加其他贴花实现单项删除。创建与删除的正式消费方是客户端命中处理器及宿主生命周期代码，P4／P5 的测试夹具直接调用同一 API，不交付独立玩家调试命令或编辑界面。

游戏弹孔的贴图资源为拟新增的 `machine_max:textures/decal/bullet_hole.png`；首版默认宽、高均为 0.05 方块，投影深度为 0.04 方块，普通光照、白色 tint 与贴图 alpha。样式常量由 Machine-Max 客户端适配器持有，不挂到投射物类型、不由口径推导、不进入网络字段。通用投影器与材质参数供代码调用和几何夹具使用，不要求为游戏弹孔建立材质预设注册表。

宿主传入数量、三角形和生成工作量预算，可按寿命主动调用 `remove`。贴花超限按创建序号淘汰最早项；单项生成超出面数限制时整体失败，不保留任意一半的跨 bone 图案。预算初值由 P7 的测量确定，不在通用几何函数中硬编码游戏寿命或显存配额。

## 7. Minecraft 绘制接入

### 7.1 绘制状态

首版使用独立的贴花 `RenderType`：

| 项目 | 约定 |
|---|---|
| 顶点 | `DefaultVertexFormat.NEW_ENTITY`，贴花独立 UV，插值并归一化后的光照法线 `shadingNormalB`，动态光照与 overlay；提交时按当前法线矩阵变换，几何法线只用于求交与投影判定 |
| 拓扑 | `VertexFormat.Mode.TRIANGLES`，与实际缓存索引一致 |
| 剔除 | `NO_CULL`；提交的三角形绕序不代替 §4.2 的几何正反面判据，扁平面与反射几何均可显示 |
| 着色 | 自定义贴花 RenderType 采用普通实体半透明 shader 与 alpha 混合，保留光照、雾和宿主 tint；排序配置由自定义类型明确设置 |
| 混合 | 标准 source-alpha 混合，贴花纹理颜色按非预乘 alpha 资源约定处理 |
| 深度 | 开启 `LEQUAL`，只写颜色，使用专用 `LayeringStateShard` 的 polygon offset；不得关闭深度测试来隐藏闪烁 |
| 表面偏移 | 首版保留贴合位置，通过渲染状态偏置解决共面竞争；不按骨骼缩放随意增大物理间距 |
| 层次 | 仅按 `creationSequence` 升序提交，后添加的后画；`sortOnUpload=false`，删除一项不改变其他项的次序 |
| 光照 | 由宿主当前绘制传入，不烘焙进几何；普通弹孔不因接收 bone 为发光件就自动满亮 |

构造形态固定为：

```java
RenderType.create(name, DefaultVertexFormat.NEW_ENTITY,
        VertexFormat.Mode.TRIANGLES, size,
        false, false, state); // affectsCrumbling=false，sortOnUpload=false
```

复用的是实体半透明 shader 与混合状态，不能直接使用 `RenderType.entityTranslucent(texture)`：`net.minecraft.client.renderer.RenderType#ENTITY_TRANSLUCENT` 的 `sortOnUpload=true`，会触发 `net.minecraft.client.renderer.MultiBufferSource#endBatch` 的上传阶段排序。贴花类型即使使用同一张纹理也必须与底材 RenderType 分开；缓存 RenderType 按纹理复用，不为每张贴花创建一种类型。

原版 `net.minecraft.client.renderer.RenderType#ENTITY_DECAL` 使用深度相等测试，不能承担任意投影、裁剪和 bone 绑定。`net.minecraft.client.renderer.RenderStateShard#POLYGON_OFFSET_LAYERING` 硬编码 `(-1.0F,-10.0F)`，直接引用它无法调参。贴花自建 `LayeringStateShard`，启用时调用 `RenderSystem.polygonOffset(factor,units)` 与 `enablePolygonOffset()`，退出时复位数值并禁用；初始测量值取 `(-1.0F,-10.0F)`，由 P4 / P7 的薄板、远距读数确定常量。所有叠加层使用同一偏置，层次由添加序号表达。

### 7.2 实际提交顺序

底模型和贴花使用同一个 `MultiBufferSource`。1.21.1 原版 `BufferSource` 的实体底材与本计划贴花类型均走共享缓冲；`getBuffer` 切换到不同的非 fixed RenderType 时会冲刷 `lastSharedType`。因此，在基础模型顶点之后请求贴花类型即可形成原版提交边界，无需另建贴花 BufferSource，也无需每个 bone 手工刷新世界缓冲。

每个绘制入口只提交它负责的 receiver 范围：先按 `creationSequence` 升序遍历贴花，提交这张贴花在该范围内的全部 bone 片段，再处理下一张，不能先按 bone 分组打乱覆盖关系。只能对这个序列中连续的同材质片段合批，例如纹理顺序 A、B、A 必须保留三段，不能合并两个 A 绕过 B。材质切换由同一共享缓冲自然提交，同类型批次由 `sortOnUpload=false` 保留写入顺序。

近距模型按 SubPart 的绘制入口分次提交，跨 SubPart 不承诺按添加序号叠加；真实表面的前后遮挡由深度测试决定。精确共面的跨 SubPart 重复表面没有全局序号覆盖保证，P5 的多 SubPart 接入以此为边界。

添加顺序定义的是同一表面的图案覆盖关系。前后不同的真实表面以及其他世界几何保持深度遮挡；贴花不写深度，不能通过关闭深度测试把后加入的图案强制画到前景物体上。删除只摘除对应 id；代码创建的新 id 使用新序号，位于同一 receiver 的既存图案上层。

AR／Sodium 等可能替换 consumer 或延后提交的管线属于 P4 / P7 的兼容项：必须证实基础几何先提交、同批贴花不被重排、输出目标与深度缓冲一致；需要显式 flush 或降级时仅在对应适配器中处理。底材为真实半透明面时适用 §1 的首版边界。

### 7.3 宿主接入位置

| 宿主 | 已有入口 | 接入要求 |
|---|---|---|
| ARMS 机体 | `../ARMS-Core/src/main/java/io/github/sweetzonzi/arms_core/client/MechaPlayerRenderer.java#renderModel` | 使用当前实体绘制原点、朝向、模型空间矩阵及相同 partialTick 生成查询视图；基础模型顶点写入后，使用同一缓冲源请求贴花类型 |
| Machine-Max 近距模型 | `src/main/java/io/github/sweetzonzi/machine_max/client/render/renderer/PartEntityRenderer.java#renderTextured` | 接收范围取当前 SubPart 实际骨骼；模型根取正式绘制矩阵；线框／装配中未形成的表面跳过贴花 |
| Machine-Max 远距模型 | `src/main/java/io/github/sweetzonzi/machine_max/client/render/renderer/DistantVehicleRenderer.java#renderSubPart` | 与近距共用同一描述和网格；复用该入口的 model-view、根矩阵与光照，相机位置只扣除一次 |

## 8. 代码调用与弹孔接入

### 8.1 首版消费方与阶段归属

| 入口 | 创建方式 | 数据寿命 |
|---|---|---|
| 弹孔 | 已成立的物理命中 → 当前模型射线 → 投影盒 → 每 bone 绑定 | 客户端瞬时记录，受宿主预算控制 |
| 代码测试夹具 | 代码直接给出射线或投影位姿 → 调用 §6.3 的 create／remove | 当前测试场景，由夹具负责清理 |

代码 API 及生命周期属于 P3，ARMS 贴花夹具在 P4 接入，Machine-Max 贴花夹具在 P5 随载具适配接入，真实弹孔命中处理在 P6 接入。P1 先提供基础模型光照夹具，执行形态与贴花夹具相同。夹具直接构造图案并删除指定 id，不注册按键、命令或编辑界面。

夹具的执行形态固定如下：

1. 宿主仓库建立独立的 `decalFixture` 开发源集，源文件放 `src/decalFixture/java/`，夹具模型／贴图放对应开发资源目录。main 源集不引用该源集，发布 jar 的输入只含 main，不能把夹具或其调用点打进发布产物。
2. 仅显式指定 Gradle 项目属性时，执行 `neoForge.mods.named(project.mod_id) { sourceSet(sourceSets.decalFixture) }`，把夹具并入宿主 mod 的扫描数据，使 `@EventBusSubscriber` 可以注册；同时在该仓库的 `neoForge.runs.named('client')` 上用 `systemProperty` 转发同名 JVM 属性，属性值为 case。Machine-Max 使用 `-PmmDecalFixture=<case>`，ARMS 使用 `-ParmsDecalFixture=<case>`；默认 runClient 不加载夹具。不能用 `runClient.classpathProvider`、`runtimeOnly` 或 `<run>AdditionalRuntimeClasspath` 代替 mod 源集挂载，夹具不是一个自带 mods.toml 的独立 mod。
3. 夹具自己的客户端 tick 订阅者检查开发环境、启用属性、单人本地会话和目标模型就绪。目标按宿主已有生成流程准备；首次就绪时自动构造一次测试场景，初始化状态按当前 Level 持有，卸载时清理。发布代码没有对夹具的条件调用；多人远程服务器会话不运行夹具。
4. case 至少包含 `lighting`、`overlap`、`delete` 与 `vehicle`。`lighting` 验证 P1；`overlap` 自动放置同表面叠层，供观察者移动相机；`delete` 在首次构造后的第 200 个客户端 tick 删除中间项、第 400 tick 新建一项，并打印阶段标记；`vehicle` 在现有载具目标上执行同类代码调用。所有创建使用正式容器的序号计数器，可与单人会话中的真实弹孔共存。

实施后的启动方式为：

```powershell
# Machine-Max 的开发夹具；进入本地测试世界并准备载具目标后自动执行
.\gradlew --offline -PmmDecalFixture=overlap runClient

# 在 ARMS-Core 根目录启动基础模型光照夹具
.\gradlew --offline -ParmsDecalFixture=lighting runClient
```

P4／P5 的验收须检查：未带属性的开发客户端没有夹具调用，带属性的本地客户端能自动构造场景，发布 jar 不含该源集的类、资源或调用点。这是开发期代码调用的执行载体，不是玩家功能。

### 8.2 瞬时弹孔同步

首版复用 `src/main/java/io/github/sweetzonzi/machine_max/network/payload/projectile/ProjectilesHitPayload.java#HitEntry`。它已有投射物状态、世界命中点和响应后的 `newVel`；P6 在条目末尾追加一个 presence 位和可选的模型贴花数据段，不新建 CustomPacketPayload、注册项或外观命中队列。

该可选段只包含：

| 字段 | 用途 |
|---|---|
| `decalId: UUID` | 真实模型命中时一次生成，随同一个待发送条目传递，用于客户端去重并作为随机转角种子；夹具的图案也使用独立 UUID |
| `targetSubPartId` | 现有对象表中的目标参考 SubPart 标识；客户端由目标取得所属零件、接收范围和黑名单 |
| `hitPointLocal` | 命中时换算到该参考 SubPart 刚体坐标的命中点 |
| `incomingDirectionLocal` | 碰撞响应前的入射方向，在同一参考坐标中表达；不能用条目的响应后 newVel 代替 |

贴图 RL、口径、尺寸、材质／预设 id 和添加序号均不进入该段。贴图与弹孔尺寸取 §6.3 的固定值，前后搜索长度由已加载目标的模型边界推导。地形、普通实体和仅用于状态校正的命中条目不携带该段；后续为其他模型宿主接入定位属于单独扩展。

物理线程在真实目标命中点冻结局部位置与响应前方向，把可选段放入 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/projectile/ProjectileManager.java#PendingHitSync`；不能在主线程发包时用已经运动后的目标位姿重新换基。复用 `src/main/java/io/github/sweetzonzi/machine_max/common/mech/projectile/ProjectileManager.java#flushPendingHitSyncs` 现有队列和 postTick 批次，将同一份不可变可选数据写入 HitEntry。投射物创建包与命中包沿用原发送顺序。

接收范围沿用 `src/main/java/io/github/sweetzonzi/machine_max/network/payload/projectile/ProjectilesHitPayload.java#broadcast` 的维度内广播；首版不增加“仅目标追踪者接收”的第二条路由。客户端仅对已存在且模型可用的目标生成网格，目标暂未就绪时进入有界短期队列，过期跳过。远距代理若持有目标与模型也可消费这段信息，是否追踪其原版代理实体不是额外门槛。P7 单独记录可选段带来的字节数和广播开销，不承诺全维度内每个客户端都生成网格。

在 `src/main/java/io/github/sweetzonzi/machine_max/network/payload/projectile/ProjectilesHitPayload.java#handle` 中，模型段消费的首版门限为 `pm != null && idx >= 0`，其中 idx 是处理该条目时客户端投射物数组的索引。保留入口处 pm 为空即返回的行为；idx 缺失时只跳过贴花，不改变该条目已有的粒子／声音等处理。不补建 ProjectileManager，不请求补发投射物，不为缺失投射物数据做重建或补同步。已有索引的停止、销毁或穿透命中可在本次条目处理后创建弹孔，模型段入队资格在处理条目时确定。

基础字段的 isFinite 与模型段校验独立；模型段数值无效、目标缺失或查询失败仅跳过贴花，不能阻止有效条目的弹道、粒子或镜头表现。处理器不把完整客户端模型类型暴露到共通方法描述符，使用客户端适配入口完成生成。§8.2 的目标模型就绪队列仅等待已经通过投射物数据门限的本地任务，不承担投射物同步恢复。

局部射线经目标的实际模型根换基进入 §3 的 R 空间，客户端查询当前模型、确定投影器并调用 create；容器统一分配添加序号。各客户端按命中条目顺序调用，对同一目标的待处理项按原入队顺序消费，允许姿态与加载时点导致的外观差异。已有弹孔在当前会话内随目标运动并按预算回收；加入会话不补发历史弹孔。

### 8.3 首版协议与扩展边界

Machine-Max 在 `src/main/java/io/github/sweetzonzi/machine_max/network/MMPayloadRegistry.java#register` 的 S2C `sync` 组扩展既有 ProjectilesHitPayload 的 STREAM_CODEC。本文核对的组版本为 `sync:2.8.0`，P6 目标为 `sync:2.9.0`；可选段属于线格式的一部分，版本号必须与字段同提交提升。解码检查集合长度、目标标识、可选段数值有限性与方向有效性；默认贴图和尺寸由客户端代码提供。

载荷使用 `MainThreadPayloadHandler`，版本串、注册项、字段编解码和对应网络文档在同一次实现提交中更新，遵循 `src/main/java/io/github/sweetzonzi/machine_max/network/AGENTS.md`「约定」。若实施时该组已发布其他版本，则在届时版本上递增，不能把版本号写回较小值。首版没有贴花编辑上行包，也不改零件／蓝图存档格式，因此不为贴花升级 `input` 或 `misc` 组。

完整 bone 绑定与独立投影器可被后续涂装功能使用；交互工具、描述持久化和跨会话恢复需要独立的产品与协议计划。首版不实现编辑请求、完整描述同步或存档 Codec。ARMS 的独立网络适配若在后续增加载荷，提升 `../ARMS-Core/src/main/java/io/github/sweetzonzi/arms_core/network/ARMSNetwork.java#PROTOCOL_VERSION`；涉及实体同步字段时遵循 `../ARMS-Core/docs/ArmsCore双端权威与网络同步实现计划.md` §2.2 的末尾追加规则。

## 10. 验收与测试

### 10.1 表面查询：纯逻辑用例

| 用例 | 必须满足的判据 |
|---|---|
| HitBox 与外观大小不一致 | 前后搜索覆盖时，交点位于实际外观三角形；碰撞箱骨骼无结果 |
| 黑名单精确匹配 | 同名排除生效，未列出的子骨骼按正常资格处理；查询与投影一致 |
| HitBox 覆盖模型空隙 | 返回空，不凭物理命中强造表面 |
| cube 自身旋转、pivot、inflate | 与按正式矩阵变换后的预期表面相交，不能用未旋转 AABB 当最终结果 |
| 负跨度 cube | 资源入口正常接收；`size=(1,1,-0.252)` 与 eyes2 资源的六面均能从盒外命中近侧面，几何法线朝外；射线不能穿过近侧面而选中对侧内壁。光照法线按 §2.3 保留，±Z 标签交换带来的既有光照方向不由查询修正 |
| 扁平 cube | 资源入口正常接收，光照法线与扁平面处理符合 §2.3；零跨度不使全部面失效，有面积的两侧面可求交，零面积面跳过，不计算零乘积法线因子 |
| 父链、非均匀缩放、可逆负缩放 | 与 B 内三角形和完整仿射换基的等价求交结果一致；两类法线分别遵循 §4.2 |
| cube 的 mirror，含 boxUV／faceUV | ±X 面必须可从外侧命中且 `geometricNormalB` 朝外；faceUV 的 ±Y 面同样成立；背面与 `minFacingCos` 使用几何法线，光照法线单独核对 |
| poly_mesh 三角／四边／凸五边 | 分别得到 1／2／3 个扇形三角形，面内与共边命中正确，不与相邻多边形拼装 |
| 视图几何与姿态来源 | 唯一输入为 ModelInstance，origin／pose 均从它派生，API 不接受异源组合 |
| 多视图共享模型、不同根矩阵 | 结果返回正确 receiver；不能混用子部件根矩阵 |
| 线段端点、共边、近平行 | 无 NaN／Infinity，端点规则与稳定平局规则一致 |
| 隐藏、零缩放、空模型 | 安全跳过；不可逆矩阵不进入求逆后续计算，raycast 的返回值只有交点或空值；跳过的 bone 由分类计数定位 |
| 大世界坐标 | 用目标附近的双精度换基后求交，与原点附近等价场景在规定容差内一致 |

### 10.2 投影与描述：纯逻辑用例

| 用例 | 必须满足的判据 |
|---|---|
| 三角形贯穿盒子、顶点全在盒外 | 产生盒内交片；输出所有点符合六面约束 |
| 无交集、相切与退化输入 | 返回空或有效非退化片段，不产生不定数和零面积堆积 |
| 贴花纹理分辨率变化 | 几何与归一化 UV 不变；底模型纹理与 UV 不被修改 |
| 跨两 bone 与两个可动视图 | 一张贴花保存全部绑定；各片段用自己的根矩阵与 bone 矩阵运动 |
| 创建后改变骨骼姿态 | 由当前骨骼矩阵变换缓存 p_B，UV 与描述不被重写 |
| 从描述重建 | 不提供创建时整具模型姿态；同几何指纹下输出与首次生成在容差内一致 |
| 仿射绑定往返 | 非均匀缩放形成的矩阵分量完整保留，运行时 3×4 表示恢复的矩阵与重建结果一致 |
| 模型实例共享原始几何 | 给一个实例添加／删除贴花不改变另一实例和 OModel |
| 添加序号与代码删除 | 后加贴花的序号较大；删除指定 id 不影响其他项及其次序，新 id 创建取得新序号 |
| 同 id 重传与缓存 | 重复创建返回既存项，不重新裁剪或改变次序；删除后该 id 的描述和缓存全部释放 |
| 资源失效 | 仅以几何指纹匹配；绑定按 §6.2 处理，primitive 索引只用于匹配的指纹；进程结束后描述和缓存全部释放 |
| 统一添加序号 | 命中处理器与夹具混合调用同一 create，成功新建的序号严格递增，重复 id 不分配新序号，调用方不传入外部序号 |

测试位置在 Spark-Core 测试源码集的模型／几何包；ARMS 与 Machine-Max 的宿主适配测试留在对应测试包，测试类禁止进入 Mixin 独占包。数学测试覆盖不变量与跨坐标等价性，不以复述循环和字段赋值作为主要断言。

### 10.3 游戏内视觉验收

P1 的基础模型光照阶段门：在固定光照下使用 boxUV／faceUV 的 mirror 与非镜像 cube 夹具，对照普通与所有已启用加速路径；非镜像面的法线值应等于其 `direction.step()`，镜像对应外向面的光照应与同向对照面一致。该验收在 P1 完成，贴花综合画面验收在 P4／P5 执行；不能以数学用例通过替代基础模型光照验收。

1. 平板、斜板、折角、薄板和同向叠层各放一张贴花，验证 §5 的接收定义及穿透边界。
2. 低分辨率底材上显示高分辨率弹孔，确认贴花细节独立；旋转视角检查 Z-fighting、边缘浮起和远距偏置。
3. 机体四肢、炮塔与多块装甲运动；同一贴花跨 bone 后分别附着，隐藏 bone 的贴花同步隐藏。跨 SubPart 验收各 receiver 内部的图案顺序与真实表面遮挡，排序保证采用 §7.2 的范围。
4. 改变世界光照、进入雾、触发宿主 tint／受击 overlay，检查贴花与宿主表现；验证近距、远距和加速路径。
5. 在模型前放遮挡物，弹孔必须被遮住；玻璃、底材 alpha 镂空按 §1 明确标记为首版边界，不把穿帮认作通过。
6. 统计动画帧的几何提取与裁剪计数：未发生创建或失效时为零；允许正常提交缓存顶点。
7. 代码创建两张共面贴花覆盖同一区域，平移／旋转视角后覆盖次序始终是后加在上。再使用 A、B、A 三张纹理顺序复验，防止跨材质合批改序；代码删除中间一张时其余项的顺序保持，新建图案位于同一 receiver 的上层。核实 RenderType 的 TRIANGLES 与 `sortOnUpload=false`，并分别测试普通缓冲与加速 consumer。
8. 使用 mirror cube 的 ±X 面与 faceUV 的 ±Y 面，以及单独的三角、四边、凸五边 mesh 夹具核验交点、投影和显示；几何外向法线与光照方向分别检查。现有第一方内容无 poly_mesh，不能用载具既有画面替代该夹具。

### 10.4 联机与生命周期验收

- 同维度两个具有对应投射物条目且目标模型可用的客户端处理同一命中：按 `decalId` 只创建一次，图案和默认尺寸相同，使用正确目标与响应前方向；本地添加序号不要求数值相等，允许 §8.2 的姿态与加载时点差异。
- 同一 tick 集中产生多次命中：沿用现有 ProjectilesHitPayload 批次，不产生额外弹孔包；基础字段与带／不带可选模型段的编解码往返正确，条目顺序保持。
- pm 为空或 idx 缺失的客户端不创建该次弹孔，也不发起补同步；已有索引的正常终止命中可创建。地形条目无可选段，坏模型段或缺失目标不阻止有效基础字段的弹道更新、粒子与镜头表现。
- 单人开发世界同时启用夹具并产生真实弹孔：同一容器共用添加计数器，不因来源不同占用同一序号；远程会话、无属性的开发启动和发布 jar 均没有夹具执行。
- 客户端命中处理器使用同一 create API；按 id 的重复通知不重建，代码删除和预算淘汰释放全部片段，连接结束后会话内弹孔清空。
- 目标暂未加载、移除、换维度与断线：队列有界且能结束，缓存无悬挂宿主引用。
- 纹理重载、同几何模型重载、几何变化与 bone 缺失：分别走 §6.2 的定义路径。
- 对比开启／关闭弹孔表现时的伤害、穿透与跳弹结果，必须一致。
