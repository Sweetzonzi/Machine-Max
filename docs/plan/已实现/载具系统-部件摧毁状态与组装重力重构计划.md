# 载具系统：部件摧毁状态与组装重力重构计划

> **状态**：已实现并完成实机验收（提交 `2d7c4da9`、`b1d667e4`；2026-10-29 客户端实测通过 §9 五条）
> **适用版本**：NeoForge 1.21.1 · Machine-Max 1.0.3-beta.6
> **编写日期**：2026-10-29
> **本文自包含**：不要求读者先读其他文档或本文的旧版本。文中每个符号都给出路径与职责；「改动前的基线」一节记录本次改动前的代码事实（保留为缺陷根因与验收基线），「实现模型」及之后各节描述当前代码形态。

## 一、要解决的问题

四项彼此关联的问题，根因都在「部件状态」这一层：

1. **重进存档后部分零件零重力**：加载后的重力初始化只覆盖「进度满」和「进度 0 且处于组装态」两种状态，其余状态没有任何一处写入重力，而刚体关闭了世界重力来源，于是永久零重力。
2. **同部件不同子零件的销毁倒计时不同步**：倒计时按子零件各自持有、各自推进、各自加速，没有部件级权威值。
3. **已摧毁状态不存盘**：`destroyed` 与剩余倒计时都不进存档，重进后倒计时重置；配合第 1 条，残骸还会悬空。
4. **摧毁判定与移除时机不清**：部件在「第一个子零件倒计时结束」时就被移除，其余子零件的时间窗口被截断；整件摧毁音的播放点落在客户端的整车批量标记里，同一时刻连响 N 声。

## 二、改动前的基线（缺陷记录）

本节记录本次改动之前的代码事实，作为四项缺陷的根因证据与验收基线；同样的类与字段现在已经是「三、实现模型」描述的形态。

### 2.1 组装状态与重力

- `RegularPart.renderWireframe`（`common/mech/vehicle/RegularPart.java`，字段在 `:45`，构造期默认 `true`）是一个**状态位**，表示部件仍处于组装形态；渲染器用它决定是否画线框（`client/render/renderer/PartEntityRenderer.java:83`，同时要求 `assemblingProgress < functionalThreshold`）。名字与「渲染线框」这个表现动作混淆。
- 存档键 `render_wireframe`（`common/mech/vehicle/data/RegularPartData.java:42`）的默认值是 `true`；17 个模板 JSON 中有 12 个显式写 `false`，共 123 处（例如 `spark_modules/Machine-Max_K17/machine_max/templates/k17.json:4`），另外 5 个不写该键。模板里同时存在「进度 0.2826 + 非组装态」的部件（同文件 `:754-763` 的 `machine_max:k17_wheel`），因此**组装进度与组装态是两个独立字段，不能互相推导**。
- 组装进度的派生规则在 `RegularPart.recomputeAssemblyFromDurability()`（`:395-425`）：取各子零件耐久比例的最大值；有手工配方时再受材料档位限制。
- 子零件刚体在构造时设置 `setProtectGravity(true)`（`common/mech/vehicle/SubPart.java:137`）。该调用的语义是「不采用物理空间重力、空间重力变化时也不覆盖自身值」，因此**每个子零件的重力必须由代码显式写入；没有写入等于零重力**。
- 全项目只有三处写入重力：
  - 恢复构造器 `RegularPart(...)`（`:71-81`）：仅当 `assemblingProgress == 0 && renderWireframe` 时写世界重力的 10%；
  - `RegularPart.setAssemblingProgress`（`:453-464`）：同一条件写 10%，否则写满重力并激活刚体；
  - `SubPart.preTick`（`:275-280`）：`part.usesFullGravity()` 为真且恰在第 10 tick 时写满重力；`RegularPart.usesFullGravity()` 的判据是 `getAssemblingProgress() >= 1f`（`:120-126`）。
- 结果是加载后零重力的状态是「进度在 `(0,1)`」与「进度为 0 且不在组装态」，包括「已摧毁」（伤害会把进度归 0，组装态在越过工作阈值时早已关闭）和「受损未摧毁」。`(1, true)` 会在第 10 tick 由 `usesFullGravity()` 拿到满重力，`(0, true)` 在恢复构造器与 `setAssemblingProgress` 里拿到 0.1g。
- 线框低重力的设计口径写在 `docs/plan/已实现/制造蓝图-配方与物品拆分设计.md`：线框 = 组装进度为 0 的零件形态，重力为正常值的 10%。

### 2.2 摧毁与倒计时

- 每个 `SubPart` 自己持有 `DESTROY_TIME_ID`（`common/mech/DestroyableObject.java:52`，默认值为 `subpart_destroy_min_ticks`，`:69`）。
- 初值来自 `DestroyableObject.getInitialDestroyTimeTicks()`（`:131-134`）：`max(round(耐久上限 × subpart_destroy_ticks_per_durability), subpart_destroy_min_ticks)`，两个参数定义在 `common/MMServerConfig.java:46-55`。
- 计时在 `DestroyableObject.postTick()`（`:84-95`）推进：服务端每 tick 对每个已摧毁对象 `tickDestroyTimer(1)`，归零后 `destroy()`。该推进来自 `ObjectManager.onPostTick` 的逐对象遍历（`common/mech/ObjectManager.java:294-302`），与区块是否加载无关。
- 追加伤害的加速在 `SubPart.settleAccumulatedDamage()`（`:979-987`）：只推进**本次被命中的那个**子零件，且保留最后 20 tick。
- 部件级移除判据在 `AbstractPart.onTick()`（`common/mech/part/AbstractPart.java:340-350`）：遍历子零件时第一次迭代就 `break`，实际只看 `subParts` 的第一个元素；`VehicleCore.preTick()`（`common/mech/vehicle/VehicleCore.java:486-490`）见到 `part.isDestroyed()` 就 `removePart`。
- 子零件被摧毁时的副作用在 `SubPart.setDestroyed()`（`:996-1013`）：停用全部子系统，并在客户端播放 `part.destroyed` 音效。客户端音效的门控是 `level.isClientSide && !isDestroyed()`，而该方法在同步回调里进入时标志已置真，因此**单个子零件死亡实际无声**；真正连响 N 声的是客户端 `VehicleCore` 收到 `DATA_DESTROYED_ID` 后调用 `markDestroyed()`，它在同一帧里对全部子零件批量调用 `setDestroyed()`。
- `VehicleCore.markDestroyed()`（`:408-418`）只置 `DATA_DESTROYED_ID` 并把 HP 归零，**不写子零件耐久**；因此这样摧毁的部件`getAssemblingProgress()` 可能仍是 1。
- 不同步来源（按当前代码逐条）：
  1. 初值口径：子零件取自己的 `getMaxDurability()`。`share_durability` 默认 `true`（`RegularPartType.CODEC`，`:42`），第一方内容包全部使用共享耐久，此时每个子零件的上限都是共享上限、归零与标记在同一 tick 发生，**初值一致**；非共享耐久的部件会从初值就分叉。
  2. 追加伤害只加速被命中的子零件（共享耐久部件同样会被这一条拉开）。
  3. 部件移除只看第一个子零件，导致「部件消失时刻」与其余子零件的倒计时无关，其余子零件的时间窗口被截断。
  4. 重新加载世界时全部计时从头开始，每次加载后的分叉形态不同。

### 2.3 存盘与回收

- `SubPartData`（`common/mech/vehicle/data/SubPartData.java:21-36`）只有 `id`、`durabilityRatio`、位姿、连接点 NBT 与子系统 NBT，没有摧毁标记与倒计时。
- `RegularPartData`（`common/mech/vehicle/data/RegularPartData.java:26-45`）只有组装进度、材料进度、组装态标志等，同样没有摧毁状态。
- 维度内存档在 `ObjectManager.saveVehicles`（`common/mech/ObjectManager.java:362-368`）遍历 `levelVehicles` 打包 `VehicleData`；`VehicleCore.getPartData()`（`:1444-1448`）遍历 `partNet` 的节点，因此摧毁倒计时中的部件会被原样存盘，但状态字段缺失。
- 撬棍（`common/item/prop/CrowbarItem.java:54-123`）对已连接部件在生存模式下只做「断开连接 / 攻击」；只有通过「无外部连接」判定后才走整体拆卸并生成零件物品（`:92-117`）：
  - 组装进度 ≥ 1 → 满耐久零件物品（`:98-99`）；
  - 组装进度 < 1 且配方有非空材料清单 → `createDamagedPartItemStack`（`:219-229`），`materialCap` 取清单长度、`materialGap` 取缺口，缺口等于总量时物品耐久为 0；
  - 无配方、或材料清单为空 → 不产出物品（`:100-109` 的 `itemStack` 保持 `null`）。
- 0 耐久零件物品的放置：`VehicleAssemblyServerHelper.restoreAssemblyStateFromDamage`（`:196-212`）先按 `cap - damage` 反推进度（`:208`），再把全部子零件耐久写满（`:209-211`）；而耐久写入按 `durabilityLimitRatio() = max(progress, 0.05)` 钳制（`RegularPart.java:108-110`、`SubPart.java:1292-1295`），所以「全部材料缺失」的物品放下来是**进度 0、耐久为设计上限 5% 的骨架**。配方为空时该方法提前返回，部件保持构造时的进度 1。
- 焊枪（`common/item/prop/WeldingTorchItem.java:81-111`）把「已摧毁」与「潜行」并列为拆解分支：已摧毁部件无论是否潜行都落入该分支，进度大于 0 时按 `part.disassemble` 返还材料，进度为 0 时直接 `removePart` 且不产出物品——与撬棍并存构成第二条移除路径。
- 相关测试：`RegularPartDataContractTest`（`src/test/java/io/github/sweetzonzi/machine_max/part/RegularPartDataContractTest.java`，`:41` 断言 `render_wireframe` 缺省为真、`:53-64` 逐字段读二进制并以 `readableBytes() == 0` 收尾）；`PartAssemblyProgressSyncPayloadTest`（`src/test/java/io/github/sweetzonzi/machine_max/network/PartAssemblyProgressSyncPayloadTest.java`，断言 13 字节）。

## 三、实现模型

### 3.1 状态与不变量

部件（Part）只有四种状态：

| 状态 | 判据 | 物理 | 子系统 | 重力 |
| --- | --- | --- | --- | --- |
| 组装中（骨架） | `assembling == true && progress == 0` | 可动 | 按进度门控 | 世界重力 × 0.1 |
| 部分组装 / 完整 | 未摧毁，且不是骨架 | 可动 | 按进度门控 | 世界重力 |
| 已摧毁（倒计时） | `isDestroyed()`，即全部子零件已摧毁 | 可动、保留碰撞与关节 | 全部停用 | 世界重力 |
| 已移除 | 倒计时归零后从载具拓扑移除 | 刚体销毁 | 拆离 | — |

不变量：

- **I1**：只有处于「组装中（骨架）」的部件使用 10% 重力；其余一切状态（含部分进度、完整、已摧毁）使用世界重力。任何一个分支都必须写出重力，不存在「不写」的路径。
- **I2**：子零件被打到 0 耐久时只标记该子零件摧毁，刚体、关节与连接点全部保留；部件仍是组装基本单位。
- **I3**：倒计时只有一个权威值，属于 Part；子零件上的 `DESTROY_TIME_ID` 只是它的网络镜像。
- **I4**：全部子零件都摧毁时部件进入倒计时；倒计时结束部件才从载具移除并销毁全部子零件。
- **I5**：`destroyed` 与剩余倒计时进存档；重进后从剩余值继续，不重置。
- **I6**：倒计时期间可用撬棍把部件整体回收为零件物品，产物按部件自身的材料进度换算——被打光耐久的部件给出 0 耐久物品，整车摧毁而零件耐久完好的部件给出满耐久整件；同一部件也可以用焊枪按既有拆解规则熔回材料。两种工具产物不同，各自沿用进入摧毁状态之前的规则。

### 3.2 组装状态位改名

- `RegularPart.renderWireframe` → `assembling`；`shouldRenderWireframe()` → `isAssembling()`（`AbstractPart` 的默认实现返回 `false`，`RegularPart` 返回 `assembling`）。
- 存档键 `render_wireframe` → `assembling`，同时改名 `RegularPartData.renderWireframe` 与 `PartAssemblyProgressSyncPayload.renderWireframe`（网络载荷字段位置不变，仍是 13 字节）。
- 存档键默认值为 `false`：没有该键即表示「这份数据没有记录过组装形态」，按已定型部件处理。字段 `RegularPart.assembling` 的构造期默认值仍是 `true`，因为新建部件以 `progress = 1` 出生、由 `RegularPart.onTick()`（`:169-172`）在越过工作阈值后关闭；而「构造后立刻置进度 0」的路径（零件物品放置、`STRUCTURE_ONLY` 恢复、维修尝试）必须在同一 tick 内保留组装态以便拿到 0.1g，所以字段不能默认 `false`。两种默认值服务的是不同时点，注释里写明。
- 渲染器继续自行决定「是否画线框」：`part.isAssembling() && progress < functionalThreshold`。
- 内容包迁移：12 个模板 JSON 中 123 处 `"render_wireframe": false` 全部删除（该值等于 `assembling` 的默认值，写明只是冗余），其余 5 个模板不含该键；`docs/wiki` 的《5.7-模板、蓝图与装配体》字段表与示例同步改用 `assembling`，并写明默认 `false`。
- 不做旧键回退。旧存档里缺失 `assembling` 的部件读成 `false`，与「模板中进度 0.28 但非组装态」这一既有合法状态同形，因此不会误画线框；仍在组装的旧部件失去线框外观与 0.1g，但保留进度与耐久，可继续组装或维修。

### 3.3 重力

- `AbstractPart` 增加 `usesReducedGravity()`（默认 `false`）；`RegularPart` 返回 `assembling && getAssemblingProgress() == 0f && !isDestroyed()`。
- 重力写入收敛为一个入口 `AbstractPart.applyGravity()`（构造期可直接调用；运行期经 `submitImmediateTask(PPhase.PRE, ...)`）：目标值 = 世界重力 ×（`usesReducedGravity()` ? 0.1 : 1），写全部子零件，非低重力时 `activate()`。
- 调用点：
  - 恢复构造器（保留现有行为：骨架在入世前拿到 0.1g）；
  - `setAssemblingProgress`（替换现有内联循环）；
  - `setAssembling`（新：状态位翻转时重算）；
  - `SubPart.preTick` 的第 10 tick（替换 `usesFullGravity()`：无条件写一次目标值，作为入世次序的兜底；保留这段延迟的原因见 §8）。
- 删除 `AbstractPart.usesFullGravity()`。

### 3.4 Part 级倒计时

- `AbstractPart` 持有：`protected int destroyTime`（剩余 tick，服务端权威）、`protected boolean destroyCountdownStarted`（是否已经进入倒计时）、`isDestroyed()`（全部子零件 `isDestroyed()`，空子零件集合返回 `false`）、`getDestroyTime()`（服务端返回字段；客户端返回根子零件的镜像值）、`allSubPartsDestroyed()`、`tickDestroyState()`、`advanceDestroyTimer(int)`、`applyRestoredDestroyState()`。
- 初值 `AbstractPart.getInitialDestroyTicks()`：`max(round(getTotalMaxDurability() × ticksPerDurability), minTicks)`；新增 `getTotalMaxDurability()` = 各子零件 `getSharedMaxDurability()` 之和（共享耐久部件下等于现有 `getSharedMaxDurability()`，因此第一方内容的窗口长度与现状一致；非共享耐久部件也有确定口径）。
- 启动（两条入口，都在部件被标记摧毁的同一 tick）：`SubPart.setDestroyed()` 在服务端通知所属部件，`VehicleCore.markDestroyed()` 在整件标记后显式调用一次，两者都落到 `AbstractPart.startDestroyCountdown()`：写入初值、置 `destroyCountdownStarted`、播放一次部件摧毁音效并写镜像。`tickDestroyState()` 里的同名分支只是兜底，供「已摧毁但尚未开始」的中间状态收敛；当 tick 不扣减。在同一 tick 启动的好处是存档不会写出「`destroyed = true` 且 `destroy_time = 0`」这种载入即移除的组合。初值为 0（配置允许 `subpart_destroy_min_ticks = 0` 且耐久上限为 0）时按立即移除处理。
- 推进：`tickDestroyState()` 在倒计时已开始后每 tick 减 1，并把当前值写入**全部子零件**的 `DESTROY_TIME_ID` 作为镜像；归零后由 `VehicleCore` 移除部件。
- 追加伤害：`SubPart.settleAccumulatedDamage()` 在 `part.isDestroyed()` 时调用 `part.advanceDestroyTimer(round(drained × subpart_destroy_advance_ticks_per_damage))`，按 `subpart_destroy_advance_ticks_per_damage` 折算并保留最后 20 tick 的下限；同一 tick 内多个子零件各自结算时按各自伤害累加。
- 驱动位置：`VehicleCore.preTick()` 的部件循环（服务端）调用 `part.tickDestroyState()`；归零后调用现有 `removePart(part)`。该循环不受 `inLoadedChunk` 门控，与现状「区块未加载也走计时」一致。
- 客户端不推进计时，也不执行部件移除；移除统一由 `PartRemovePayload` 驱动。`VehicleCore.preTick` 的移除分支只在服务端执行，客户端通过全部子零件的同步标志推导 `isDestroyed()`。
- `SubPart` 不自行销毁：`DestroyableObject` 增加 `protected boolean removesOnCountdownExpiry()`（默认 `true`），`SubPart` 返回 `false`，`DestroyableObject.postTick()` 据此跳过 `tickDestroyTimer` 与 `destroy()`；`SubPart` 不覆写 `tickDestroyTimer`，`BallisticProjectile` 保留自己的覆写。

### 3.5 子零件摧毁后的表现

- 保留刚体、关节、碰撞与 `MMPartEntity`；只停用子系统、把 `DATA_DESTROYED_ID` 置真。
- 渲染继续按子零件读 `isDestroyed()` 与 `getDestroyTime()`：倒计时镜像对全部子零件一致，因此黑化与最后 1 秒淡出同步；`client/render/renderer/DistantVehicleRenderer` 的同一读取无需改动。
- `AssemblyHud3D`（`client/render/gui/hud3d/AssemblyHud3D.java:169-178`）的倒计时读部件状态（经 `subPart.part` 取 `isDestroyed()` 与 `getDestroyTime()`）：部件已摧毁时显示秒数；只有子零件被摧毁而部件尚未进入倒计时时显示无秒数的「已损毁」，文案键为 `MMLanguageRegistry.HUD_WARN_SUBPART_DESTROYED`。
- 已摧毁子零件仍可被命中：命中会推进部件倒计时（§3.4）。
- `VehicleInspectorRenderer` 用 `!subPart.isDestroyed()` 跳过内构绘制（`:132`、`:154`）。子零件在整段倒计时里留在世界，内构视图会提前看不到它，这是 §5 记录的表现变化。

### 3.6 存盘

`RegularPartData` 增加两个字段（JSON 键与 `StreamCodec` 同序）：

| 字段 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `destroyed` | boolean | `false` | 部件是否处于摧毁倒计时 |
| `destroy_time` | int | `0` | 剩余 tick |

- 恢复入口：在恢复构造器里、`restoreState(data, mode)` 之后调用 `applyRestoredDestroyState()`，一次覆盖所有 `FULL_STATE` 落点（`VehicleCore` 构造器的批量恢复，以及 `PartFactory.restoreRegular` 的单独重建，后者见 `ConnectorAttachPayload.handle` 的 `:62`）。两条子顺序约束：钳制上限取 `getInitialDestroyTicks()`，依赖 `restoreState` 写好的耐久上限；停用子系统要等子系统存在，而子系统在 `initializeStructure()` → `createSubParts()` → `createSubsystems()`（`AbstractPart.java:499-510`、`:722`）里创建，早于 `restoreState`。`SubsystemController.initAllSubsystems()`（`:78-82`）只重建能源路径、订阅并调用 `onAttach`，不写 `DATA_ACTIVE_ID`，因此不会把停用状态翻回来；`AbstractSubsystem` 的 `DATA_ACTIVE_ID` 构造期默认 `true`（`:71`），停用必须由恢复逻辑显式执行；`isActive()` 又含 `!subPart.isDestroyed()`（`:256-261`），重复停用是幂等保险。
- `FULL_STATE` 恢复：写入 `destroyed`/`destroyTime`，把全部子零件标记为摧毁，并把倒计时镜像给子零件。
- `STRUCTURE_ONLY`（蓝图路径，`VehicleBlueprintItem.restoreMode()`，`:58-62`）：忽略这两个字段，`destroyed = false`、`destroy_time = 0`。收纳物品走 `FULL_STATE`（`AssemblyItem`，`:51-55`），因此从收纳物品取出的载具按 I5 继续倒数。
- 恢复时把 `destroy_time` 钳制到 `[0, getInitialDestroyTicks()]`；`destroyed == true` 且 `destroy_time == 0` 的部件在载入后的第一次 `tickDestroyState()` 里立即移除，用于处理倒计时恰好归零时保存的存档。
- 旧档没有这两个字段：按默认值读成「未摧毁」；耐久为 0 的子零件仍会在加载后的第一次结算里被重新标记，整部件随之进入倒计时，不会复活成可用状态。
- `SubPartData` 保持现有字段：子零件的摧毁状态由「耐久为 0」或「部件摧毁」推导。

### 3.7 音效

- 部件首次进入摧毁状态时，由服务端在 `tickDestroyState()` 启动分支里调用一次 `Level.playSound(null, ...)`（原版会把声音广播给范围内玩家）。
- 删除 `SubPart.setDestroyed()` 中按子零件播放的客户端音效。
- 客户端 `VehicleCore.markDestroyed()` 不播音：它只是把同步来的整车状态铺到各子零件，声音的唯一播放点是服务端启动倒计时。

### 3.8 回收

两种工具各自沿用进入摧毁状态之前的规则，不因「已摧毁」改道；它们的产物不同，由玩家自己选：

- **撬棍**（`CrowbarItem.use` 的 `else` 分支，`:92-117`）：整体拆卸，产物完全由部件自身的材料进度决定。生存模式下只有「无外部连接」才进这个分支（`:71` 的条件是 `hasConnection && (player.isCrouching() || !player.isCreative())`）；创造模式未潜行时可以把带连接的部件直接带走，代价是触发既有的分裂逻辑。整车 HP 归零不改子零件耐久（`VehicleCore.markDestroyed()`），因此一辆被炸毁的车上完好的零件回收后仍是满耐久整件：零件能不能救回来取决于零件自己挨了多少伤害，而不是载具怎么死的；被逐个打光耐久的部件则给出 0 耐久物品。
- **焊枪**（`WeldingTorchItem.onUseTick`，`:102-112`）：按既有拆解把零件熔回材料——进度大于 0 时 `part.disassemble` 返还材料并在进度归零时停手，进度已是 0 时再操作一次就 `removePart`。已摧毁部件同样适用，因为它产出的从来不是零件物品，而是材料；这条路径不需要为「已摧毁」加门控。无配方部件到不了最后一步：`disassemble` 在 `getRecipe() == null` 时直接返回 `false`（`:273-275`），进度停在原处，因此这类部件只能走撬棍。用焊枪把残骸拆掉会让部件提前离开拓扑，倒计时随之中止，这与撬棍回收一样是玩家主动移除。
- 分裂是既有规则，本轮不加新旁路：断开连接点走 `VehicleCore` 的 `partNetSpiltCheck()` → `serverHandleSpilt()`（`:1131-1149`），单连接点的部件（轮、灯、加装件）一旦断开就是独立载具。撬棍自身的 `removePart` 只在无连接时可达，因此不会再撕一次图；焊枪的 `removePart`（`:110`）不做连接判定，带连接时会触发同一套分裂逻辑——这是既有行为，本轮不改动，也不为撬棍复制它。
- 无配方或材料清单为空的部件，撬棍仍不产出（`:100-109` 的 `itemStack` 保持 `null`）：这类部件没有「材料缺口」这个概念，而给出整件会被放置路径还原成进度 1 的完整件，与 `docs/plan/已实现/制造蓝图-配方与物品拆分设计.md:553-555` 的既有口径一致。
- 提示文本：撬棍对已摧毁部件的交互语义未变，沿用现有提示键；HUD 的「已损毁（无秒数）」需要一条新翻译键，加到 `MMLanguageRegistry` 的枚举（`zh_cn`/`en_us` 内联），再跑 `runData` 刷新 `src/generated/resources/assets/machine_max/lang/*.json`。

## 五、影响面与需要复核的交互

- **履带**：`TrackLink` 的多处判据已经检查 `subPart.isDestroyed()`；子零件在部件移除之前一直留在世界，成员集合更稳定，但 `TrackLink.onMemberDestroyed` 的调用点只剩部件移除路径，需要在实机上确认断带/解体的时序不变。
- **连接点**：已摧毁子零件的连接点保持不变，`connector.destroy()` 只在部件整体移除时调用，因此部件不会因为单个子零件死亡而脱落。这是 I2 的直接结果。
- **座位 / 控制 / 武器**：所有 `subPart.isDestroyed()` 门控保持不变；区别只在于「已摧毁但部件未全毁」的窗口变长，玩家会看到受损但仍在车上的部件。
- **物理**：已摧毁子零件继续参与碰撞与求解；车辆冻结（`freezePhysicsForTerrainWait`）与运动学禁令不受影响。
- **内构视图**：`VehicleInspectorRenderer` 按 `!subPart.isDestroyed()` 跳过绘制，而子零件在整段倒计时里仍在世界，两者叠加的结果是内构里提前看不到该部件。
- **HUD**：`AssemblyHud3D` 是子零件作用域（`:150-178` 用 `subPart.part` 取部件），部件级判据经 `subPart.part` 读取，无秒数文案走 `HUD_WARN_SUBPART_DESTROYED`。
- **蓝图 / 收纳**：`STRUCTURE_ONLY` 不读取摧毁状态；`VehicleData.rebased()` 需要随字段改名同步。恢复模式的分工是 `AssemblyItem` = `FULL_STATE`（`AssemblyItem.java:53-55`）、`BaseVehicleItem` 与 `VehicleBlueprintItem` = `STRUCTURE_ONLY`（`BaseVehicleItem.java:79`、`VehicleBlueprintItem.java:61`），因此把一辆正在倒计时的车装进收纳物品再取出，会按 I5 继续倒数。
- **Lombok**：`AbstractPart` 类级 `@Getter`（`:78`）会为新字段生成 `getDestroyTime()` 等访问器；`RegularPart` 的类级 `@Getter` 会为 boolean `assembling` 生成 `isAssembling()`。手写 `@Override` 版本时 Lombok 检测到同名方法会跳过生成，不要同时保留两处声明。
- **测试**：`PartFoundationGameTest`、`PartAssemblyProgressGameTest` 读写 `assembling`，并已随改名更新；`PartAssemblyProgressSyncPayloadTest` 只按字段位置与 13 字节总长断言，不引用组件名，改名后无需修改；`RegularPartDataContractTest` 逐字段读二进制，字段序含 `destroyed` 与 `destroy_time`，缺省断言为 `false` 与 `0`。

## 八、风险与取舍

- **入世稳定性**：第 10 tick 的重力写入是现有行为，用来避免部件在关节与地形就绪前被重力拉走。保留这段延迟，第 10 tick 无条件写入一次目标值；不要在构造期给完整部件直接写满重力。
- **同步量**：倒计时镜像每次写入都会标脏，同步量约为每 tick、每已摧毁部件 N 条（N 为子零件数），与逐子零件计时的做法同阶；如后续需要压缩，可只写根子零件并在客户端读取部件级值，本轮不做。
- **已摧毁子零件保留碰撞**：这是「Part 是基本单位」的必然结果；如果实机发现残骸碰撞造成异常冲量，再单独评估「摧毁后关闭接触响应」，不属于本轮范围。
- **两种工具的分工**：撬棍取整件、焊枪熔材料，产物不同但不互为替代，已摧毁部件对两者都不设额外门控。零件物品的耐久只表达「材料缺了多少」，不表达「这件零件挨了多少打」，因此整辆载具被炸毁时耐久尚存的零件仍会以满耐久整件回收——这与拆卸、维修用的是同一套材料进度，没有新增例外。两条路径在已摧毁部件上执行的是与摧毁前同一段代码，且摧毁本身会让 `recomputeAssemblyFromDurability()`（`RegularPart.java:395-425`）把材料档位下调，不会凭空多出材料；先熔一部分材料再取零件，得到的也是按剩余材料缩水的物品。
- **存档不兼容**：存档键与协议版本都是破坏性变更，旧客户端无法连接；缺少 `assembling` 键的部件读成已定型，期间仍在组装的部件失去线框外观与 0.1g，进度与耐久保留。
- **回收窗口受连接判定限制**：生存模式下撬棍只在无外部连接时整体拆卸，仍在车上的已摧毁部件要先断开连接点；而断开连接点这一步本身就按既有规则分裂（单连接点的部件断开后成为独立载具）。创造模式未潜行时可以直接带走带连接的部件，同样走既有分裂。撬棍不新增绕过连接判定的分支；焊枪的带连接强制移除是既有行为，本轮不改动。

## 九、验证

- **GameTest（新增 `PartDestroyStateGameTest`）**
  1. 多子零件部件：只摧毁一个子零件，断言部件 `isDestroyed()` 为假、未从拓扑移除。
  2. 摧毁全部子零件：断言部件 `isDestroyed()` 为真、`getDestroyTime()` 等于按 `getTotalMaxDurability()` 计算的初值。

  6. `FULL_STATE` 恢复：断言子零件全部被标记、倒计时保留；`STRUCTURE_ONLY` 恢复：断言两项归零。

  2. 同一部件用准星扫过不同子零件：HUD 秒数一致；淡出同时开始。
