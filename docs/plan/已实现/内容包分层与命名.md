# 内容包分层与命名

**状态**：已实施 · 2026-10-23
**范围**：`src/main/resources/spark_modules/` 下第一方内容包的划分、命名、依赖与迁移；兄弟仓 `Machine-Max_BlockbenchPlugin` 的配套改动。
**本文自包含**：不要求先读其它文档。文中给出的路径与数量都可以在仓库里直接复核。

---

## 1 结论

内容包按**三层**组织，层与层之间用硬依赖串联：

```
L0  Machine-Max_Builtin                引擎基元 + 新人货架 + 题材无关的独立成品件
        ▲ hard
L1  Machine-Max_<范围>_Basic_Kit        型谱层：可被多辆载具复用的真实型号
        ▲ hard
L2  Machine-Max_<车族>                  载具层：几何、挂点、接线、模板、蓝图、配方、HUD
```

一条包内约定同时成立：**包名说归属，目录说品类**。九个第一方包的目录名统一 `Machine-Max_` 前缀，包内内容目录统一 `machine_max/`。

## 2 归属判据

判据问的是「这个定义是不是一个独立于某辆车的实体」，不是「它被几辆车引用」。

| 判据 | 落点 | 例子 |
| --- | --- | --- |
| 抽象档位，无型号名、无原产国 | L0 builtin 货架 | `light_car_engine`、`standard_front_wheel`、`default_seat` |
| 有型号名、有原产国（或明确谱系） | L1 对应 kit | `2a42_launcher`、`k17_composite_armor`、`9m133_kornet` |
| 只在这辆车上成立：几何、挂点位置、信号频道接线、动画名、涂装、HUD 布局 | L2 车包 | `sdkfz234_hull`、`k17_weapon_tubes` |
| 与题材无关、民用包也会用 | L0 builtin 货架 | 座椅、储物、瞄具基类、火控、灯光、连接器基元、材质、通用音效 |
| 自带几何、不引用包外定义、不绑定题材的独立成品件（货箱、拖钩、天线、油箱） | L0 的 `parts/prop/` | `container_16x16x8`、`golden_closestool` |
| 可加装到多辆车上、但几何取自某一车包的加装件（枪塔、外挂件） | 该车包的 `parts/` | `pkt_turret`（几何是 MT-LB 模型的 `PKTTurret` 骨骼组） |

三条配套规则：

1. **一件器材只有一个归属**，借用方通过硬依赖取得，禁止复制定义。
2. **上层包不重复定义下层包的 id**；要改数值用 `{"type":"override"}` 显式声明，使「谁覆盖了谁」写在 meta 里可查。
3. **载具包只依赖最具体的那一册**，链上的定义自动带入。

最后一条判据把「题材无关」与「几何独立」分开：`pkt_turret` 能被任何带同型座圈的车挂上，但它的模型与贴图是 MT-LB 的；放进型谱包会让型谱包依赖某个车包，因此归 MT-LB 车包，其它车通过跨包引用使用它。

**集合包**是第三种角色：13 款民用载具属于同一条产品线，一起维护、不需要单独发布，逐车拆包只增加包数与维护面。`civilian` 不建 kit —— 民用车的动力总成是逐车调校的，没有跨车复用的真实型号。

### 3.2 builtin 的货架使用情况

57 型子系统里，被其它包引用的是 17 型：`default_seat`、`default_passenger_seat`、`default_3rd_seat`、`default_3rd_passenger_seat`、`default_trunk`、`glove_box`、`default_glass`、`gunner_sight`、`commander_sight_dual_stb`、`main_weapon_controller`、`secondary_weapon_controller`、`basic_azimuth_driver`、`basic_elevation_driver`、`beam_light`、`dummy_light`、`track_controller_standard`、`track_drive_heavy`。

其余 40 型是货架件：5 台发动机、6 个变速箱、5 个传动、10 个轮端驱动、3 个电机、`basic_launcher`、`point_light`、两种瞄具变体、`targeting_pod`、`default_car_controller`、`default_motorbike_controller`，以及 `parts/prop/` 的 4 型储物 / 座椅型号。它们服务的是「内容包初级作者不写子系统定义也能把车跑起来」这个场景，判据不是「被官方载具引用」。

由此确定 builtin 的定位：**新人闭环** —— 只装 builtin（编辑器侧由插件内置快照提供），就能从零搭出一辆能开的车。型谱包是它之上的**扩展**，不是替代。

### 3.3 builtin 收编的 5 个独立成品件

这 5 件只依赖 builtin 的 `structural_steel` 材质与 `fixed_*` 连接器，任何题材的载具都能挂，因此归 builtin。一个「件」由七部分组成，成对迁移——漏一项就会出现「有零件没配方」「有物品没名字」「有模型没图标」：

| 组成 | 数量 | 落点 |
| --- | --- | --- |
| 零件定义 | 5 | `machine_max/parts/prop/` |
| 子系统型号 | 4（3 个 `item_storage` + 1 个 `seat`） | `machine_max/subsystems/item_storage/` 与 `subsystems/seat/` |
| 模型 | 4（`reinforced_container_16x16x8` 复用 `container_16x16x8.geo`） | `machine_max/models/part/` |
| 零件贴图 | 5 | `machine_max/textures/part/` |
| 物品图标 | 5 | `machine_max/textures/icon/` |
| 配方 | 10（`recipe/part_fabricating/` 与 `recipe/research/` 各 5） | 同名目录 |
| 语言键 | 19（物品名、研发条目、交互区、子系统名） | `machine_max/lang/` |

`golden_closestool` 是 `seat` 类型而不是 `item_storage`：它的子系统定义带 `views`、`allow_use_items` 与 `passenger_scale`，装配体里表现为一个可坐的调侃件。判据问的是「是否绑定题材与载具」，不问「是否实用」，所以它与货箱一起进 builtin。

三个货箱型号的槽位分别是 1×9、2×9、4×9；`reinforced_container_16x16x8` 复用 1×9 型号，只是零件更硬。

## 4 命名规则

| 对象 | 规则 | 例 |
| --- | --- | --- |
| 文件夹 | `Machine-Max_` + 标题式范围名 | `Machine-Max_Soviet_Basic_Kit` |
| 包 id | `machine_max:<范围>`，范围一到两个词，下划线分词、全小写 | `machine_max:soviet_basic_kit` |
| 内容 namespace | 第一方统一 `machine_max`；第三方用自己的 namespace | `machine_max:2a42_launcher` / `author:t34_engine` |

命名理由：

- **文件夹与 id 的形式刻意不同**。文件夹用 `Machine-Max_` 前缀、标题式；id 用 `machine_max:` 前缀、全小写。两者差得远，把文件夹名误写进 `dependencies[].id` 不会静默生效——`ResourceLocation` 会把 `Machine-Max_K17` 解析成 `minecraft:…`，随后 `SparkPackGraph` 报「缺少硬依赖」，一眼看出是分隔符写错。
- **不带版本号**。`SparkPackResourceLoader` 用目录名生成 `<gamedir>/spark_modules/<目录名>.zip`，目录名一变，旧 zip 不会被覆盖，于是同一个 `meta.id` 同时来自旧 zip 与新 zip；`SparkPackGraph` 以 id 为键、后写入者覆盖前者，而 `Files.list` 的顺序不保证，实际生效的那份因此不确定。版本写在 `meta.json` 的 `version` 里。
- **不用点号**。资源包、数据包那一层名字只给人看（大小写、空格、版本都行），但 `spark_modules/` 这层的名字同时是 zip 的缓存键，且包内还有一层同名的 `machine_max/` 内容目录——`machine_max.builtin/machine_max/…` 会把同一个词写两遍，而点号形式与 id 只差一个字符。
- `_basic_kit` 的 `basic` 修饰的是 **kit**，表达「这包是给载具包垫在下面的基础套件」，不表达内容质量。`_basic` 单独使用会被读成「简化版」。
- `basic` 固定指**第一层、不带时代限定**的那一册；时代或专题册写 `<范围>_<时代>_kit`，两者在依赖链上是两层。
- 包名表达**范围**，不承诺完整性。某个 kit 只覆盖当前已实现的型号，这件事由 `meta.description` 与 wiki 说明，不由名字表达。
- `soviet` 按「苏联系，含苏联与俄罗斯继承型号」理解，覆盖 `2S38`（俄）与 `MT-LB`（苏）同册。

**尚不建立的包**：跨籍经典器材（如 M2HB、12.7×99）目前没有第一方载具使用，先不建空壳包；它们将来落在其原产范围的 kit 里，借用方跨 kit 依赖。`flare_illum`（信号弹）与题材无关，属于 builtin 货架的候选。

## 5 包内目录约定

| 层 | 目录 |
| --- | --- |
| 型谱包 | `subsystems/`（武器按 `subsystems/weapon/` 分）、`projectiles/`、`materials/`、`models/`、`textures/`、`lang/` |
| 载具包 | `parts/`、`connectors/`、`subsystems/`、`models/`、`textures/`、`animations/`、`control_groups/`、`fittings/`、`templates/`、`blueprints/`、`assemblies/`、`hud_layouts/`、`huds/`、`documents/`、`recipe/`、`lang/` |
| builtin | 在型谱包目录之外还有 `parts/prop/`、`connectors/`、`control_groups/`、`materials/`、`sounds/`、`particles/`、`fittings/`、`docs/` |
| 全部 | `docs/`（`docs/<lang>/schemas` 的副本，见 §6） |

**模块目录名固定**：`SparkPackLoader` 用模块 id 取目录名（`parts`、`subsystems`、`connectors`……），子目录只作为 `pathSegments` 透传。因此「加装件」放在 `parts/` 下的子目录里，不新建模块目录。

**内容 id 的取法分两类**：

| 取法 | 模块 | 结果 |
| --- | --- | --- |
| 取文件名，子目录不进 id | parts、subsystems、connectors、materials、colors、control_groups、assemblies、blueprints、templates、projectiles、fittings | `parts/prop/foo.json` → `machine_max:foo` |
| id 含路径 | huds、hud_layouts、documents、models、textures、particles、animations | `hud_layouts/foo.json` → `machine_max:foo`；`hud_layouts/sub/foo.json` → `machine_max:sub/foo` |

第一类在同一命名空间下**不许同名**，跨包同名会互相覆盖。迁移与新增内容后按附录 B 的清单核对一次。

## 6 机制依据

拆分与改名依赖以下既有机制，均可在仓库内核对。

| 机制 | 行为 | 对方案的约束 |
| --- | --- | --- |
| 内容 id 生成 | `PartModule` / `SubsystemModule` 等取 `ResourceLocation(namespace, 文件名去扩展名)`，路径中的子目录不进 id | 跨包移动文件不改变 id，存档、蓝图、配方、研发进度不受影响 |
| 跨包引用 | 每个模块先遍历所有包读完，再调用 `onFinish` 统一注册 | 车包可以引用 kit 包与 builtin 的定义，不声明依赖也能解析；依赖只影响加载顺序与同 id 覆盖 |
| 语言文件 | `LangModule` 把不同包的同一 `namespace:lang/xx.json` 按键合并，后加载的包覆盖同键 | 语言键可以分散在各包；同一个键只在最低层定义一次 |
| 音效 | `SoundModule` 把不同包的 `sounds.json` 按键合并；`.ogg` 的缓存键**只取文件名** | 音效事件名可分散；`.ogg` 文件名必须全局唯一 |
| 粒子 | 粒子 id 含子目录路径 | 可按 kit 分目录隔离 |
| 模型 / 贴图 | 模型在**所有包**的 `models/<namespace>/` 下按名搜索；贴图按路径进合并后的客户端资源包 | 共享模型贴图可以放 kit 包；同名文件后者覆盖前者，需要范围前缀 |
| 弹种与炮的匹配 | 炮的 `breech.required_tags` 与弹的 `tags` 按字符串集合匹配，不经过注册表 | 新增口径（如 125mm）是纯数据，不需要改 Java |
| 包加载 | 启动时每个包目录被 zip 到 `<gamedir>/spark_modules/<目录名>.zip`，按 `meta.id` 建图并按依赖 DFS 排序 | 目录名是 zip 的缓存键，必须跨版本稳定；退役名的副本由 `MMRetiredPackCleanup` 删除 |
| `$schema` | 只在编辑器里生效，加载器不读取；取值是相对当前文件所在目录的路径 | 每个包自带 `docs/<lang>/schemas` 副本后，包内层级不变即可原样保留 |
| 覆盖开关 | 两层：每包 `meta.json` 的 `enable_auto_pack` 为 false 时，`SparkPackResourceLoader` 在发出 `SparkContentPackAutoPackEvent.Pre` 之前就把 `shouldPack` 置为 false；`auto_override_official_pack` 关闭后，处理器对命中的包调用 `setShouldPack(false)` | 单个包的 `enable_auto_pack` 优先级更高，配置项只会在它之上再关一层、不会重新打开；配置项只覆盖 `civilian` 与四个车包，`builtin` 与两个 `*_basic_kit` 始终跟随 jar，下层定义过期会让依赖它的车包报「缺定义」 |
| schema 副本 | `./gradlew syncSchemas` 从 builtin 逐语言复制，`checkSchemas` 校验 | 副本不手改；新增第一方包登记进 `syncTargets` 才有副本 |

## 7 迁移做法

### 7.1 只用三种操作

1. **`git mv` 搬文件**：内容 JSON、模型、贴图、语言文件都以文件为单位移动，字节不变。git 会把它们记成重命名。
2. **解析 JSON 后写新文件**：只用于两类目标——按包拆开的 `lang/<lang>.json`，以及新增的 `meta.json`。写完立刻用同一个解析器重读校验，并核对键的总数守恒。
3. **`./gradlew syncSchemas` 生成 `docs/` 副本**：schema 是纯 JSON 且由脚本单向生成，不手写。

### 7.2 内容 JSON 不解析、不重写

`spark_modules/` 下的内容 JSON 是 **JSONC**：文件里带 `//` 注释、`$schema` 常写在末尾、键的缩进也不统一。任何「读进来再写出去」的脚本都会丢注释或生成非法 JSON，进而让整个包加载失败。

由此定下纪律：**迁移只搬文件，不改内容**。需要在文件里改的东西只有三样，且都不属于内容 JSON：

- 新增 `meta.json`（新文件，脚本生成）；
- 语言文件拆成每包一份（纯 JSON，可安全解析）；
- 需要改路径的硬编码（PDA 原型页、配置常量）用文本替换完成。

### 7.3 迁移批次

| 批 | 内容 | 验收口径 |
| --- | --- | --- |
| 1 | 解散 `sdkfz`：建六个包，按 §3.1 搬迁文件，写 6 份 `meta.json` | 六个包的零件与子系统数量之和与 §3.1 一致；零件、子系统、连接器的 id 全部不变 |
| 2 | `official → civilian`、模板包保留原目录名、`MMCommonConfig` 的第一方包判定、`schema-sync.gradle`、`MMRetiredPackCleanup`、PDA 原型页图标路径 | `./gradlew build`（含 `checkSchemas`）通过；在留有旧 zip 的 gamedir 上启动，日志中不出现同一件零件两处定义 |
| 3 | builtin 收编 5 个独立道具（§3.3）：零件、子系统、模型、贴图、图标、配方、语言键成对迁移；同步插件 `src/builtin/` 快照 | 创造模式零件总数不变（这 5 件由 builtin 提供，排在零件栏前部）；货箱可装可开、配方可造、物品有名字与图标 |
| 4 | wiki 5.1 增分层与 kit 约定；`AGENTS.md` 的包名与示例 id 口径更新；插件仓同步 | `./gradlew checkSchemas` 通过；插件仓 `node scripts/sync-schemas.js --check` 无漂移 |

### 7.4 迁移中遵守的四条

1. **文件名不随包改名**：`sdkfz234_2.geo.json`（模型）与 `sdkfz234_2.json`（装配体 / 蓝图 / 模板）保持原名——内容 id 由文件名决定，改名会同时改掉模型索引、蓝图 id 与模板 id，而包 id 与它们无关。
2. **`$schema` 原样保留**：每个包都有 `docs/<lang>/schemas` 副本，相对路径在包内层级不变时自动成立。
3. **语言键按归属拆开**：键取自零件 JSON 内的 `sub_part.*` / `connector.*` / `subsystem.*` / `interact.*`，以及由文件名推出的 `machine_max.<零件名>`、`machine_max.research.<id>`、`research.machine_max.<id>_blueprint.desc`、`machine_max.fitting.<id>`、`controlGroup.*`。被多个包引用的键放在最低层：builtin（39 个通用实例名，例如车轮挂点、座椅、炮塔轴），或 civilian（5 个跨包通用键：`engine`、`gearbox`、`transmission`、`car_controller`、`sub_part.main`，值与其它包一致）。
4. **`docs/` 由脚本生成**：builtin 的 `machine_max/docs/` 是唯一手写源，其余八个包的 `docs/<lang>/schemas` 由 `./gradlew syncSchemas` 复制。`.md` 教程只在 builtin 与 civilian、template 保留。

### 7.5 遗留

## 9 风险与不做的事

| 项 | 结论 |
| --- | --- |
| 存档、蓝图、研发进度 | 不受影响：内容 id 全部不变 |
| 内容 namespace 按包区分（每包用自己的 namespace） | 不做。会改掉所有物品 id、语言键与引用，收益只是 id 更自解释 |
| 民用包逐车拆分 | 不做，理由见 §3.1 |
| 部件变体独立成包 | 不做。变体内联在零件 JSON，第三方只能整文件 `override` |
| 第三方包只依赖 builtin | 保持可用：builtin 已有 id 冻结，不从 builtin 迁出内容 |
| kit 链过深 | 控制在 2 层（`车 → kit → builtin`）；要加时代册时先处理 §8.3 的插件递归 |
| PDA 原型页的硬编码路径 | 用 `spark_modules/<包目录>/…` 直接指向图标文件；图标迁进 builtin 后路径随之更新 |
| 创造模式零件栏顺序 | 零件栏按包加载顺序插入，builtin 在最前，因此 5 个道具排在栏目前部。不影响可用性 |
| 旧 gamedir 的重复定义 | 由 `MMRetiredPackCleanup` 一次性清理；清理只按目录名命中，不动第三方包 |
| builtin 的座位型号引用 `machine_max:seat_dashboard` | 该布局文件在 `Machine-Max_Civilian` 的 `hud_layouts/`，也就是 L0 引用了集合包的一个 HUD 布局。把它移进 builtin 的 `hud_layouts/` 不改 id（布局 id 不含子目录），但会改变 builtin 公开的内容面，需要单独决定，本次未动 |
| builtin 的道具复用 civilian 的通用语言键 | `sub_part.machine_max.main`、`connector.machine_max.up` 等 5 个通用键按 §7.4 留在 civilian。civilian 随 jar 发布，实际总会加载；若将来有人单独禁用 civilian，builtin 的道具名会退回原始键 |

## 10 已定的选择

1. **`soviet` 而非 `soviet_russian`**：前者按「苏联系，含俄罗斯继承型号」理解，`meta.description` 与 §4 都写明这一点。
2. **kit 链上限 2 层**：插件当前的依赖解析实现够用，不引第三层。
3. **`civilian` 不建 `civilian_basic_kit`**：等出现跨车复用的民用总成再议。
4. **builtin 的 schema 示例保留跨包 id**：`launcher`、`regen_loader`、`seat` 三份 schema 的 `examples` 引用了 `machine_max:2a42_launcher`、`machine_max:2a42_regen_loader`、`machine_max:k17_vehicle_hud`，它们随 `soviet_basic_kit` 与 `k17` 一起发布。builtin 的货架里没有 `regen_loader` 型号，也只有一个 `weapon_live` HUD 布局，改引「builtin 自家 id」需要先给 builtin 补这两类型号，属于扩充货架的新工作。
5. **每个第一方包带自己的 schema 副本**：包数多了会重复约 140 个 JSON 的字节，换来的是包内 `$schema` 相对路径自洽、编辑器在每个包里都能补全。
6. **目录名带 `Machine-Max_` 前缀**：`spark_modules/` 是玩家目录，前缀让第一方包在文件管理器里连成一组，也避免与第三方包的目录重名。id 保持 `machine_max:` 短形式。
