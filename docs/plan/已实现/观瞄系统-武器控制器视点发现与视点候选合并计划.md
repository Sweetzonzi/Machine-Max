## 一、问题

本节记录改动之前的状态与它带来的四个问题；落地后的契约与实现见 §三—§八，内容迁移见 §6.3。

### 1.1 起点：视点发现只有座椅一个来源

座椅在构造时读自己的发现表（[SeatSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/SeatSubsystem.java#L89)），`resolveCameras()` 在 attach 与结构变化时把表中的频道解析成视点实例（[AbstractControllableSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/AbstractControllableSubsystem.java#L118)）。首跳表由装配体统一重建：`addPart` 在子系统挂上控制器之前建一次（[VehicleCore.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java#L859)），运行期结构变化由 `rebuildSignalTargets()` 覆盖全部部件与端口（[VehicleCore.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java#L366)），两处都早于子系统的结构变化回调。切控制组只重建武器控制器发现（[AbstractControllableSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/AbstractControllableSubsystem.java#L286)），不重建视点列表。

因此一辆车长席能切到的镜头，等于它 JSON 里写死的那一列，与当前在控制哪门武器无关。武器控制器自身只有命令输出表 `control_outputs`：`handShake()` 用它发现炮塔驱动与发射器（[WeaponControllerSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L1228)），视点不在它的发现范围内。

### 1.2 五个读点共用同一份静态列表

| 读点 | 改动前的行为 |
| --- | --- |
| [AbstractControllableSubsystem#onTick](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/AbstractControllableSubsystem.java#L56) | 视点来源（`viewSourcePart` / `viewSourceName`）不在列表里就 `clearInputSignals()`；判定含四条件：同装配体、`isActive()`、未摧毁、宿主子零件未移除。手上只有 `(子零件 ID, 名字)`，没有实例 |
| [CameraController#tick](../../../src/main/java/io/github/sweetzonzi/machine_max/client/input/CameraController.java#L172) | 活动视点不在列表里、或失活/摧毁时退回座椅观察 |
| [CameraController#switchCamera](../../../src/main/java/io/github/sweetzonzi/machine_max/client/input/CameraController.java#L489) | 循环列表就是这份静态列表（再按 `isActive()` / 未摧毁 / `allowCycle` 过滤） |
| [ViewInputPayload#serverHandler](../../../src/main/java/io/github/sweetzonzi/machine_max/network/payload/ViewInputPayload.java#L105) | 服务端拒绝不在列表里的视点来源；判定同样是那四条件 |
| [CameraController#updateFixed](../../../src/main/java/io/github/sweetzonzi/machine_max/client/input/CameraController.java#L266) | 固定炮镜的机构几何取“第一台主 WC”，与这台镜头属于哪门武器无关 |

“只在 `switchCamera` 里合并”会漏掉另外四个读点：客户端能切进去，座椅 tick 与服务端却认为该视点无效，于是每 tick 清输入或直接丢弃瞄准包，表现为“视角在动、武器不动”。

五个读点的判定强度不同：座椅 `onTick`（[:56-59](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/AbstractControllableSubsystem.java#L56)）与服务端 `ViewInputPayload`（[:103-108](../../../src/main/java/io/github/sweetzonzi/machine_max/network/payload/ViewInputPayload.java#L103)）各查满四条（同装配体、`isActive()`、未摧毁、宿主子零件未移除）；`CameraController#tick`（[:172-174](../../../src/main/java/io/github/sweetzonzi/machine_max/client/input/CameraController.java#L172)）与 `#switchCamera`（[:494-495](../../../src/main/java/io/github/sweetzonzi/machine_max/client/input/CameraController.java#L494)）只查“在列表里 + 未失活 + 未摧毁”三条，不查宿主子零件是否已移除。

### 1.3 内容里的具体形态

以 M1A2 SEP 为例，改动前的形态是：

- 车长席在迁移前静态声明三组镜头：`gunner_sight`（炮手镜）、`commander_citv`、`sight_rws`（[m1a2_turret.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/parts/m1a2_turret.json#L326)）。炮手镜是一台 `machine_max:camera`（`subsystem.machine_max.gunner_optics`），不是固定炮镜。
- 车长席基础组的**瞄准**频道只有 `crew_any_aim` 与 `crew_commander_aim_citv`；同一份预设另有移动、常规与副武器开火三张表，RWS 的开火走 `crew_commander_secondary_fire` / `crew_any_secondary_fire`（[m1a2_commander.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/control_groups/m1a2_commander.json#L5)）。
- 三条火控的接收频道互不相同：RWS 火控收 `crew_commander_aim` / `crew_any_aim`（[rws_controller.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/subsystems/rws_controller.json#L8)），车长周视镜火控只收 `crew_commander_aim_citv`（[citv_controller.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/subsystems/citv_controller.json#L8)），主炮火控只收 `crew_gunner_aim` / `crew_commander_aim`（[main_weapon_controller.json](../../../src/main/resources/spark_modules/Machine-Max_Builtin/machine_max/subsystems/weapon_controller/main_weapon_controller.json#L7)）。因此车长的基础组把 **{RWS 火控, 周视镜火控}** 算作活动集合，主炮只在 `commander_override` 组里进入（[m1a2_commander.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/control_groups/m1a2_commander.json#L62)）。
- 每一路视点都有一台负责转动它的火控（五台视点、五套火控）：炮手镜归 `main_controller`（[m1a2_turret.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/parts/m1a2_turret.json#L369)）；车长周视镜由 `citv_controller` 转，与 `citv_optics` 同在周视仪那个子零件，但这个视点仍归车长席发现，见上一条；RWS 镜归 `rws_controller`（[m153_crows.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/parts/m153_crows.json#L81)，与 [rws_sight](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/parts/m153_crows.json#L166) 同属 `m153_crows` 这个 Part 的两个子零件），装车时还有一台可加装的终端火控 `rws_terminal_controller` 在另一个 Part（[m153_crows_terminal.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/parts/m153_crows_terminal.json#L29)）；并列机枪镜归 `loader_mg_controller`；尾部机枪镜归 `aa_controller`。后两台的型号是 `port_mg_controller` / `aft_mg_controller`，各收一条设备频道（`crew_loader_aim_port_mg` / `crew_gunner_aim_aft_mg`）。
- 视点列表与这条接线无关：车长在基础组里同样能把画面切进炮手镜，而那时主炮并不接收他的瞄准。
- 周视镜是车长席位自己的观察设备，不是某门武器的镜头：它是 `machine_max:camera`（双轴稳定、方向行程 360°），由视点自己声明接受频道 `commander_citv`（[m1a2_commander_citv.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/subsystems/m1a2_commander_citv.json#L15)）；它的火控 `citv_controller` 只负责转方向机（`aim_drive_citv`），不参与“这个视角归谁”的判定。
- 遥控武器站在模板与实机里都是独立零件，经一对连接点挂在炮塔上（炮塔侧 `connector.m1a2_sep.turret_rws` 是简单连接点，武器站侧 `connector.m1a2_sep.rws_turret` 是高级连接点，[M1A2MountWiringGameTest.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/M1A2MountWiringGameTest.java#L337) 按同样的方式搭夹具）。也就是说“火控在炮塔、镜头在武器站”是一类现成的跨 Part 形态，不只出现在同一 Part 的两个子零件里。
- 三台固定炮镜的稳定配置决定了它们对机构几何的依赖：RWS 镜双轴稳定（[rws_sight.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/subsystems/rws_sight.json#L5)），并列机枪镜与尾部机枪镜双轴无稳（[port_mg_sight.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/subsystems/port_mg_sight.json#L5)、[aft_mg_sight.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/subsystems/aft_mg_sight.json#L5)）。装填手席与高射席的控制组没有主武器频道，`getActiveMainWeaponController()` 对它们返回 `null`，`updateFixed` 因此拿不到机构几何；对无稳镜头，`send()` 在 `aimTarget` 为空时直接早退（[CameraController.java](../../../src/main/java/io/github/sweetzonzi/machine_max/client/input/CameraController.java#L244)），这两台镜的瞄准输入一条都发不出去。
### 1.4 由此产生的四个问题

| 编号 | 问题 | 后果 |
| --- | --- | --- |
| P1 | 加装件的镜头必须在每台宿主车的座位上重复接线 | 换一辆车装同一个武器站，宿主座位没写 `sight_rws` 就没有这个视角，且没有任何日志 |
| P2 | 视点候选与控制组/当前武器无关 | 能在未控制某门武器时切进它的镜头；画面归属与瞄准归属分离 |
| P3 | 多武器共席时机构配对取“第一台主 WC” | 固定炮镜的几何与限位可能来自另一门武器；没有主武器频道的座位（装填手、高射）配不到任何控制器，无稳炮镜连瞄准输入都不发 |
| P4 | 服务端与客户端各自只认静态列表 | 任何只在客户端侧做的候选合并都会造成两端结论不一致 |

## 二、目标与非目标

### 2.1 目标

| 编号 | 目标 |
| --- | --- |
| G1 | 武器控制器能声明“我负责哪些视点”，发现结果随武器本体走：加装件换车不需要改宿主座位 |
| G2 | 座椅的视点候选 = 静态列表 ∪ 当前活动武器控制器发现的视点，按实例去重，顺序稳定 |
| G3 | 五个读点统一读同一份候选，客户端与服务端由同一段共通代码各自算出同一结论 |
| G4 | 固定炮镜的机构采样按“该镜头所属的武器控制器”配对，取不到时回落到现行主 WC 口径 |

### 2.2 非目标

- **不改瞄准路由**：鼠标目标仍由座椅当前控制组的视点频道决定，`setViewInputSignal` 的行为不变。本计划只解决“视角能不能进”，不解决“目标发给谁”。
- **不删座椅静态列表**：没有火控的观察设备（驾驶员潜望镜一类）只能由座位声明；静态声明始终是合法写法，迁移按车逐台进行。
- **不迁车长周视镜**：它是车长席位自己的观察设备，由座位静态声明；`citv_controller` 只负责转它的方向机。
- **不改选轴与正解的口径**：`aimJoints` 的选轴规则与 `JointAimGeometry.sample` 的正解不在本次范围。单连接点双自由度（一颗关节两轴、可能只有一台驱动器）这类形态已经走它们的“一体关节”分支，本计划的配对只决定“哪台控制器”，不假设两轴分属两个连接点。
- **不迁移 M1A2 SEP 以外的第一方载具**：迁移改变的是可切换的镜头集合，每台车要各自做画面验收。其余载具保留现有座位声明，行为不变。
- **不改 HUD 候选语义**：`CustomHud` 在炮镜视角的宿主集合与 `getHudWeaponCandidates()` 的取法不在本次范围。
- **不加网络字段，不改协议版本**：候选由内容与活动组索引两端各自推出。
- **不做视点观察角同步**：仍按观瞄方案的后续 TODO 处理。
- **不改 `handShake()` 的执行器发现**：炮塔驱动与发射器的绑定量不变。

## 三、数据契约

### 3.1 武器控制器的发现表

安装属性 `WeaponControllerSubsystemAttr` 增加一个可选字段：

```json
"subsystem.m1a2_sep.rws_controller": {
  "type": "machine_max:weapon_controller",
  "definition": "m1a2_sep:rws_controller",
  "control_outputs": {
    "aim_drive_rws": ["subsystem.m1a2_sep.rws_azimuth_driver",
                      "subsystem.m1a2_sep.rws_elevation_driver"],
    "weapon.mg.m2hb": ["subsystem.m1a2_sep.rws_launcher"]
  },
  "camera_discovery_targets": {
    "sight_rws": ["subsystem.m1a2_sep.rws_sight"]
  }
}
```

| 属性 | 约定 |
| --- | --- |
| 字段名 | `camera_discovery_targets`，与座位同名同义 |
| 类型 | `Map<String, List<String>>`，复用 `AbstractSubsystemAttr.SIGNAL_TARGETS_CODEC`，缺省空表 |
| 键 | 首跳表的频道键。广播目标（`local` / `global`）与连接点目标都要过接收侧的接受频道，视点必须在 `discovery_inputs` 里声明同一频道（连接点还可能经 `signal_translations` 换成另一个名字）；只有子系统名目标不走这层过滤，频道写什么都解析到那台视点（见 §5 R11） |
| 值 | 子系统名、连接点名、`local`、`global`。同一 Part 内一律具名直连（跨子零件也可以，上例即跨两个子零件）；跨 Part 的三种写法见下表 |
| 语义 | 只读发现。解析走 `resolveTargets`，不写任何信号槽，也不获得对镜头的控制权 |
| 合并 | 并入 `getTargetNames()`（[WeaponControllerSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L1263)），由 `setTargetFromNames()` 构建首跳表 |

发现频道不复用 `control_outputs`：那张表是命令输出，混入只读发现会让“输出”和“发现”共用一张表，`content-check` 也无法分开核对。

跨 Part 的三种写法：

| 情形 | 写法 | 理由 |
| --- | --- | --- |
| 同一 Part（含跨子零件） | 子系统名 | 名字在 Part 内全域可达，不需要对侧任何配置 |
| 跨 Part，两侧内容都归本作者维护（吊舱、通用炮塔、货架上的武器站） | 连接点名 | 只沿那条关节到对侧。同一型号装两台时，每台火控按自己的关节取自己那一台，不会像按频道广播那样两台一起拿。对侧连接点在 `signal_targets` 里声明该频道（必要时配 `signal_translations`），视点接受转译后的频道 |
| 跨 Part，对侧属于宿主或外来内容（通用加装件、独立终端件） | `global` | 对侧连接点的两张表不归本件维护；按频道广播只要求视点自己声明 `discovery_inputs` |

连接点名的代价在可观测性：`SignalPort` 用**对侧**连接点的 `signal_targets` 与 `signal_translations` 解析（[ISignalSender.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L95)：先取 `getAttachedPort()`，再按对侧的转译表查 `other.getTargets()`），对侧没配这条频道时发现结果为空且没有日志，见 §5 R12。

简单连接点同样带 `SignalPort`——每个连接点在构造时就建一份（[AbstractConnector.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/connector/AbstractConnector.java#L72)），只是简单连接点的两张表按定义为空。所以“火控在高级连接点那一侧、视点在简单连接点那一侧”就能用：首跳落在简单连接点这一侧的端口上，解析时读的是对侧（视点所属零件）连接点的表。连接点名不要求两侧都是高级连接点；M1A2 这一对就是一个简单、一个高级，把两端都换成高级会牵动零件几何与自动配对。

### 3.2 视点候选

座椅多一个派生查询；`discoveredCameras` 只表达内容声明的静态发现，候选由新方法给出：

```java
public record ViewCandidate(AbstractViewpointSubsystem viewpoint,
                            @Nullable WeaponControllerSubsystem controller) {}

public List<ViewCandidate> getViewCandidates();

/** 按实例判定，服务端校验与切换路径用它。 */
public boolean hasViewCandidate(AbstractViewpointSubsystem viewpoint);

/** 按结构地址判定，供只记录 (子零件 ID, 名字) 的读点使用。 */
public boolean hasViewCandidate(int subPartId, String name);

/** 该视点在候选里的配对控制器；不在候选或没有活动控制器发现它时为 null。 */
@Nullable
public WeaponControllerSubsystem getViewCandidateController(AbstractViewpointSubsystem viewpoint);
```

| 规则 | 定义 |
| --- | --- |
| 构成 | 静态 `discoveredCameras` ∪ 每个活动武器控制器的发现结果 |
| 活动集合 | `getActiveWeaponControllers()`（base ∪ 当前子组，[AbstractControllableSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/AbstractControllableSubsystem.java#L227)），**不是** `getActiveMainWeaponControllers()`——遥控武器站一类设备走副武器线 |
| 过滤 | 视点四条：与座椅同装配体、`isActive()`、`!isDestroyed()`、`!getSubPart().isRemoved`；武器控制器：`isActive()`、`!isDestroyed()`、宿主未移除。这四条是五个读点判定的**并集，也就是其中最严的一份**，而不是与每个读点逐条相同（§1.2：`CameraController#tick` 与 `#switchCamera` 只查三条）。候选统一到四条，等于给这两处补上“宿主子零件已移除”的守卫：被拆下的子零件上的视点不该还留在切换列表里。这是有意的收紧，不是等价重构 |
| 去重 | 按实例身份（`IdentityHashMap` 语义），首次出现的位置保留 |
| 顺序 | 静态发现顺序在前；随后按活动集合顺序（base → 子组），每个控制器内按自己的发现顺序 |
| 配对 | `controller` 取首次发现该视点的活动控制器；静态列表里的视点若同时被某个活动控制器发现，同样填该控制器，否则为 `null` |
| 重新计算 | 每次调用按当前控制组现算，不缓存到结构变化点。活动组索引两端已同步，因此两端结果一致。`onTick` 那条读点只在 `viewSourcePart >= 0` 时查询，空座不构造候选表 |

两个 `hasViewCandidate` 重载共用上面这张过滤表：实例版本按 `viewpoint` 比身份，结构地址版本按 `(子零件 ID, 名字)` 比现行 `onTick` 的两个字段。`getViewCandidateController` 只服务固定炮镜的机构配对（§4.4 第五条读点）。`ViewCandidate` 的两个字段都有读点：`viewpoint` 用于循环、有效性与服务端校验，`controller` 用于机构采样配对。这与「中间对象只在跨边界冻结数据时出现」不冲突——它不是把已有对象的字段搬一遍，而是把“哪台视点属于哪台武器”这一发现结果固定成一次读取的值。

### 3.3 不需要同步

发现解析在两端都跑：内容由内容包加载，活动组索引由 `ViewInputPayload` 与座位同步维护。候选集是这两份输入的纯函数，所以不加字段、不改 `input` / `sync` 协议版本。

### 3.4 配对的机构前提：两种安装形态

配对只决定“这台镜读哪台控制器的机构”；能不能读出**正确**的几何还取决于关节与视点的相对位置。现有 `aimJoints`（[WeaponControllerSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L1019)）与 `JointAimGeometry.sample`（[JointAimGeometry.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/control/aim/JointAimGeometry.java#L29)）支持两种安装形态，满足条件不同：

| 形态 | 关节与驱动器 | 视点在哪 | 满足条件 |
| --- | --- | --- | --- |
| 拆分式：两条连接点、两台驱动器（M1A2 的并列机枪镜、尾部机枪镜、遥控武器站镜） | 方向机 + 高低机，两轴各一台 | 高低机的从动体 B 一侧 | 方向机 A=中间体、B=基座；高低机 A=中间体、B 是视点的支承链一侧；两条高级连接点与两台驱动器都声明在中间体那个子零件下 |
| 一体式：一条连接点、一颗双轴关节（车体航向机枪、架设式重机枪这类） | 一颗关节带两轴；一台同时配置 `yaw` 与 `pitch` 的驱动器，或两台各驱动一条轴但落在同一颗关节上 | 关节的主动侧 A 一侧 | 基座是 B、视点在 A 一侧；高级连接点落在带视点的那个子零件上；`sample` 走 `integrated` 分支 |

“视点在 B 一侧”不等于“视点与关节端点同体”：`sample` 每次按实际姿态把光轴相对端体的偏移算进去（[JointAimGeometry.java:22-23](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/control/aim/JointAimGeometry.java#L22) 的注释写明炮镜可位于从动体的固定后代、甚至带后坐行程的子部件）。`aimJoints` 里 `bodyB == sight.body` 只是选轴时的**优先匹配**（[:1024-1028](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L1024) 的比较器把它排在前面的驱动器优先），匹配不上不报错、退到排在最前的那台高低机。所以表格里的条件是“视点跟着 B（或 A）走”，不是“视点与连接点同子零件”。

`bodyA` / `bodyB` 是哪一侧是确定的：接线调用点都写成 `advancedConnector.attach(simpleConnector)`（[VehicleCore.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java#L1000)、[:1033](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java#L1033) 的跨载具接线、[:1176](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java#L1176)、[AbstractPart.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/AbstractPart.java#L903)），`attachJoint` 以 `this.subPart.body` 为 A、对侧为 B（[AbstractConnector.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/connector/AbstractConnector.java#L263)），所以 A 恒为高级连接点所在子零件、B 恒为简单侧。

两种对不上都是静默的，没有一条会抛异常。`sample` 里确有一条 `yaw.getBodyA() != pitch.getBodyA()` 的防御（[:43](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/control/aim/JointAimGeometry.java#L43)），但它在现行路径上不可达：`aimJoints` 选方向机时本身就按 `bodyA == pitchJoint.getBodyA()` 过滤（[:1030-1034](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L1030)），不相等时返回 `yaw = null`，而 `sample` 只有一个调用点（[:992](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L992)）。于是方向机对不上只会退成单轴：`yaw == null` 时快照仍非空，偏航限位被锁在零位（[:57](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/control/aim/JointAimGeometry.java#L57)）；视点不在被驱动的一侧时轴数照旧是两轴，只是该轴不跟随。两者都只能按“角度是否跟随”发现，验收项 T09 就是按这个写的；不要为 `sample` 的这条防御写期望抛异常的用例。

第一方内容目前只有拆分式（装填手机枪的两条高级连接点都在 `sub_part.m1a2_sep.loader_mg_azimuth`，视点在 `loader_mg_elevation`），一体式还没有内容使用。本计划的配对改动不假设两轴分属两个连接点：它只决定“哪台控制器”，选轴与正解仍走上面这两处代码，因此新增一体式机构不需要改本计划引入的任何代码。这一节只约束固定炮镜：视点若做成可转镜头（`machine_max:camera`），它不走 `updateFixed` 与 `sampleAimGeometry`，与这里的两行无关。

## 四、实现

### 4.1 共用解析口

`AbstractControllableSubsystem#resolveCameras` 自己遍历频道；武器控制器继承的是 `BasicSubsystem`，够不到这段代码。把“按发现表解析视点”上提到 `AbstractSubsystem`：

```java
protected List<AbstractViewpointSubsystem> resolveViewpoints(Map<String, List<String>> discoveryTargets);
```

行为：遍历 `discoveryTargets.keySet()`，对每个非空频道调 `resolveTargets(channel)`，筛出 `AbstractViewpointSubsystem` 且与发送者同装配体（`getSubPart().getPart().assembly` 相等）的终端，按实例去重并保持首次出现顺序，返回不可变列表。

放在 `AbstractSubsystem` 的理由：两个调用方都是子系统，而端口、交互区与总线不需要这个查询；放进 `ISignalSender` 会让每个发送者都多一个没人用的默认方法，而这些非子系统发送者的发现语义各有各的（端口转发、交互区只发不收、总线广播）。

### 4.2 武器控制器侧

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| 属性字段 | `WeaponControllerSubsystemAttr` | 字段、`CODEC`（`optionalFieldOf(..., Map.of())`）、构造器形参；字段位置放在 `control_outputs` 之后 |
| 构造签名 | `WeaponControllerSubsystemAttr` | 构造器多一个 `Map<String, List<String>> cameraDiscoveryTargets` 形参。[ViewpointGameTest](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/ViewpointGameTest.java#L142) 有三处直接 `new WeaponControllerSubsystemAttr(...)`（[:286](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/ViewpointGameTest.java#L286)、[:356](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/ViewpointGameTest.java#L356)），三处各补一个 `Map.of()` |

### 4.4 五个读点

| 读点 | 目标行为 |
| --- | --- |
| 座椅 `onTick` 的视点来源校验 | 读 `hasViewCandidate(subPartId, name)`；来源是武器控制器发现的视点时保持输入信号 |
| `CameraController#tick` 的退回判据 | 读 `hasViewCandidate(viewpoint)`；所属控制器离开活动集合、或宿主子零件被移除时退回座椅观察 |
| `CameraController#switchCamera` | 候选来自 `getViewCandidates()`，保留 `allowCycle` 过滤；越过边界回座椅的行为不变 |
| `ViewInputPayload#serverHandler` | 读 `hasViewCandidate(viewpoint)`；其余来源、乘客、控制关系、控制组校验不变 |
| `CameraController#updateFixed` | `setAimController` 取该视点候选的 `controller`；为 `null` 时回落到现行 `getActiveMainWeaponController()`。配对的实际效果在下一环：`SightSubsystem#onPostPhysicsTick` 用这台控制器采样机构几何（[SightSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/SightSubsystem.java#L38)），于是“配对”决定的是这台镜此后读哪一套关节几何 |

`CameraController#updateFixed` 是客户端代码，GameTest 覆盖不到它。它的可验证部分在两处：配对决定就在 `getViewCandidates()` 的返回值里，采样链的落点是 `SightSubsystem#onPostPhysicsTick`——两者都在 `src/main` 的公共代码里，T09 用它们把“配给谁”与“几何从哪来”钉住；`updateFixed` 里那一行赋值本身由 runClient 的画面验收确认。

`CameraDiscoveryGameTest` 与 `SignalPipelineGameTest` 断言的是 T-90A 座位经 `global` / 具名直连的静态发现（[CameraDiscoveryGameTest.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/CameraDiscoveryGameTest.java#L43)、[SignalPipelineGameTest.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/SignalPipelineGameTest.java#L243)）。本计划的迁移范围是 M1A2 SEP，T-90A 的座位声明不动，两条断言因此保持原义、期望值不变。把某台车的镜头迁到火控之后，该车座位的 `getDiscoveredCameras()` 只剩没迁走的那几条（M1A2 的车长席保留周视镜）；迁移那台车时要按迁移后的静态列表改断言，全部迁走时改读 `getViewCandidates()`，否则测试会以“发现列表变了”变红，而那正是迁移的预期结果。

### 4.5 生命周期

- 结构变化：武器控制器的视点快照与座椅的静态列表同时重建，候选随之更新。
- 切控制组：候选即时缩回或扩大；活动视点若因此离开候选，`CameraController#tick` 的退回判据会在同一 tick 把它踢回座椅。
- 武器控制器失活/摧毁：其发现的视点离开候选。静态列表里的视点不受控制器状态影响。
- **镜头随所属火控一起失效是有意的**：火控失活（宿主子零件被摧毁）或被摧毁时，它声明的视点跟着离开候选，乘员失去这台武器的视角——这台武器连同它的瞄准链已经不可用。要让某个视角不随火控存亡变化，就把它写回座位的静态声明；车长周视镜按这条处理（§6.3、§5 R14）。
- **该控制器失效时的清档是全清**：坐在它发现的视点里、控制器失活或摧毁，座椅 `onTick` 判出来源无效并调用 `clearInputSignals()`（[AbstractControllableSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/AbstractControllableSubsystem.java#L355)），油门与扳机一并置空。这是“视点设备失效”档，与换视点、换主 WC 的 `clearViewSignals()` 不同档；按 `signal/AGENTS.md` 的口径这是预期行为，不是回归。
- 服务端：`ViewInputPayload` 的校验与客户端读同一套候选，不会出现“客户端能进、服务端拒收”。

## 五、边界与已知风险

| 编号 | 事项 | 处理 |
| --- | --- | --- |
| R1 | 活动集合必须含副武器控制器 | 用 `getActiveWeaponControllers()`；遥控武器站挂在副武器线上，按主轴筛会漏掉 |
| R2 | 门控精度等于频道接线精度 | 某武器只要接受 `crew_any_*`，所有用该频道的座位都会把它算进活动集合，其镜头随之可见。要真正分开，内容得给该设备单独的设备频道（如 `crew_commander_aim_rws`）。本计划不把候选集当权限边界 |
| R3 | 静态列表保留 | 没有火控的观察镜只能由座位声明；静态声明不受控制器活动集合影响，也不会被候选过滤掉 |
| R4 | 跨 Part 的三种写法 | 同一 Part 用子系统名；两侧内容都归本作者维护的跨 Part 配对用连接点名（按关节限定，同一型号装两台也不会串台）；对侧属于宿主的加装件用 `global`。选择依据见 §3.1 |
| R5 | 发现频道不是命令频道 | 单独成表，不并进 `control_outputs` |
| R6 | 切组到服务端处理完成的窗口 | 客户端切组后、服务端处理完切组前，带新组索引的瞄准包会被 `controlGroup` 校验丢弃，下一次照常发送。这与现行切组行为同源，不额外处理 |
| R7 | 每个业务 tick 现算候选 | 列表规模是个位数，`getActiveWeaponControllers()` 一次分配；`onTick` 那条读点沿用现成的 `viewSourcePart >= 0` 门，空座不分配。先按现算实现，剖析显示热点再按（结构代次、活动组索引）缓存 |
| R8 | 配对只影响机构采样 | 不影响瞄准投递；车长超控与越级优先级的语义保持原样 |
| R9 | 不改变 HUD | 炮镜视角的宿主仍是活动视点；武器元素仍按 `getHudWeaponCandidates()` 建立 |
| R10 | 发现频道与输出表共用一张首跳表 | 座位的发现表经 `setUpTargets` 并进输出目标表（[AbstractControllableSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/AbstractControllableSubsystem.java#L304)），空座 `onTick` 的 `resetSignalOutputs()`（[SeatSubsystem.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/SeatSubsystem.java#L123)）会按这张表给每台被发现视点的发现频道写一条 `EmptySignal`。视点不消费这条频道，写入无副作用；契约只承诺“解析本身不写槽”，不承诺“槽永远不存在”。武器控制器在 attach 之后不调用 `resetSignalOutputs()`，它的发现频道不会出现这种槽 |
| R11 | 子系统名目标的频道不参与过滤 | 子系统名直连不走接收侧接受表——端口与总线两条分支各按接受频道筛，最后一行才是“直接当终端收下”（[ISignalSender.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L119)），所以频道写错也照样解析到那台视点。这条线路的风险在目标名（解析不到会记错误日志），不在频道名；频道名在 `global`、`local` 与连接点这三条线路上都是契约 |
| R12 | 连接点目标的对侧无法离线校验 | 连接点名只保证“这条关节存在”，对侧的 `signal_targets` / `signal_translations` 与视点声明的接受频道决定能不能到达。对侧内容静态不可知（连接点在装配时才配对），没配时发现结果为空且没有日志。`checkContent` 能拦的是连接点名本身不存在于安装块所在 Part（§6.2 判据 1）；对侧接线靠内容作者按连接点规则自查，或由实机验收发现 |
| R13 | 配对的前提：视点要跟着被驱动的那一侧走 | 配对成功只说明找到了“哪台控制器”；视点不在被驱动的一侧、或轴连接点不在它的支承链上时，几何照不出来而且不报错（快照仍非空，轴数甚至仍是两轴，只是该轴不跟随）。两处对不上都不抛异常——`sample` 里那条 `bodyA` 校验被 `aimJoints` 的方向机过滤挡在前面、不可达（§3.4）。拆分式与一体式各自要满足什么见 §3.4，验收按“角度是否跟随”写（T09）。第一方内容目前都是拆分式并满足条件 |
| R14 | 迁移后镜头随所属火控失效 | 火控被打掉或被拆时它声明的视点离开候选，乘员失去这台武器的视角。这是有意的取舍：这台武器连同瞄准链已不可用。要保留一个不随火控存亡变化的视角，就把它写回座位的静态声明——车长周视镜按这条处理（§6.3） |

### 6.1 schema

- 源：`weapon_controller_dynamic_attr.schema.json` 的 `zh_cn` 与 `en_us` 两份手写稿各加 `camera_discovery_targets`：`$ref` 到 `../base/signal_targets.json`、`default: {}`、说明写“本火控负责的视点发现表”。字段说明的写法与座位同名段保持一致（[seat_dynamic_attr.schema.json](../../../src/main/resources/spark_modules/Machine-Max_Builtin/machine_max/docs/zh_cn/schemas/subsystem/dynamic/seat_dynamic_attr.schema.json#L33)）。
- 两份都要改：`syncSchemas` 按语言各自复制副本（`zh_cn` 另有一份技能快照），只改一种语言会让另一种落后。
- 副本：运行 `./gradlew syncSchemas` 生成其余内容包与技能快照；`./gradlew checkSchemas` 校验。

### 6.2 `checkContent`

补一条通用判据，座位与武器控制器两处共用，三条：

1. **取值域**：按名字前缀分类，两条分支用同一个作用域——安装块所在变体的 `sub_parts`，也就是运行期这一个 Part 实例（`setTargetFromNames` 扫的就是 `owner.part.subParts`，[ISignalSender.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L255)）：`subsystem.` 必须在该变体内解析到一台 camera / sight，`connector.` 必须存在于该变体；`local` / `global` 走第 2 条；其余写法（交互区名、拼错的类别前缀）判失败。跨 Part 只能写连接点名或 `global`。两条分支的作用域必须一致：按整个文件或兄弟变体扫会放过只存在于兄弟变体里的名字，而运行时的 Part 实例里没有它，线路只会在建表期记一条“未在部件内找到”并留下空发现。
2. **广播目标的频道**：值为 `local` / `global` 时，频道必须出现在至少一份 camera / sight 静态定义的 `discovery_inputs` 里——这两条线路由接收侧按自己的接受频道过滤，频道不在任何视点声明里就永远命中不了。
3. **禁用 `camera_sight`**：它是每台视点未声明时的默认接受频道（[CameraSubsystemStaticAttr.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/attr/static_attr/CameraSubsystemStaticAttr.java#L41)），写在发现表里等于“全车所有视点”；要表达“这台视点归谁”，频道名必须是内容自己的设备词（`sight_rws`、`sight_port_mg` …）。第一方内容当前没有使用它。

第 1 条里“必须解析到一台 camera / sight”这一层是必要的：名字解析对不存在的名字会记错误日志（[ISignalSender.java](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L275)），但“解析到了另一类子系统”不会报错，只表现为发现结果为空。连接点目标的频道不在离线核对范围内：它要过对侧连接点的 `signal_targets` 与视点的接受频道，而连接点在装配时才配对（§5 R12）。

连接点这条线路已经有一半在核对，不要为它再写一条判据：对侧连接点在 `signal_targets` 里声明了该频道时，现有的连接点信号表判据会按目标子系统的接受频道核对到达频道（[content-check.gradle](../../../content-check.gradle#L1488)），而视点类型的接受频道字段就是 `discovery_inputs`。所以上面三条只补两件事——发送侧的名字取值域与广播频道，以及“对侧压根没声明这条频道”这半个缺口（§5 R12）。

`acceptedChannelFields` 那张表不动：它只服务连接点 `signal_targets` 的到达频道核对，且 `install` 分支只认 List 型字段（[content-check.gradle](../../../content-check.gradle#L1147)），Map 型的发现表落进去是空操作；发现表的核对全部走上面三条。

实现落点：三条判据在 [content-check.gradle](../../../content-check.gradle) 的第 16 节，与既有的名字取值域、交互区目标检查同处一个「按变体遍历」的循环里，作用域就是该变体的 `sub_parts`。第 2 条的频道并集在扫描前一次性建好：遍历全部包的全部子系统型号，只取 `type` 为 `machine_max:camera` / `machine_max:sight` 的 `discovery_inputs`。通过数量计入汇总行（`N 条视点发现目标`）。

本计划只迁 M1A2 SEP，其余载具保持现状。

迁移的判据是“这个镜头归武器还是归席位”：跟着武器走、随武器一起存亡的镜头（炮手镜、机枪镜、遥控武器站镜）由该武器的火控声明；本身是某个岗位的独立观察设备、不该随某门武器的火控存亡变化的镜头（车长周视镜）由座位的静态声明保留。

迁移前后 `checkContent` 都必须通过；迁移只改安装块的字段，不动蓝图、模板与存档键。

putAll(重建结果)`（[ISignalSender.java:271](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L271)），装配体级重建会把手工条目抹掉——“清空后为空”会空转（通过的原因是重建抹的，不是夹具清的），而“注入之后补一次重建让端口重新解析”会让命中阶段直接变红。探针火控不在 `part.getAllSubsystems()` 里（那里只汇总各子零件的 `ownSubsystems()`，[AbstractPart.java:681](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/AbstractPart.java#L681)），`rebuildSignalTargets()` 不会碰它，它只能在结构变化回调里重解析，所以步骤 ② 要把它加进 `SubsystemController`。探针火控在 `attach` 之前那一刻读到的是空快照（§4.2），命中与为空都在 ③④ 里判。炮塔侧是简单连接点，照样有 `SignalPort`（§3.1），发现靠对侧高级连接点的表，夹具不改零件几何与配对类型 |
| T14 | 候选过滤的四条件 | 装配体归属之外的任一条不成立（失活、摧毁、宿主子零件被移除）时，它同时从候选、客户端切换列表与服务端校验里消失 |

**T09 的夹具。** 用 M1A2 SEP 炮塔的并列机枪镜（`subsystem.machine_max.loader_mg_sight`，宿主子零件 `sub_part.m1a2_sep.loader_mg_elevation`，与 `loader_mg_azimuth` 同属一个 Part）＋一台探针火控：`control_outputs` 指 `loader_mg_azimuth_driver` 与 `loader_mg_elevation_driver`，发现表写 `{"sight_port_mg": ["subsystem.machine_max.loader_mg_sight"]}`，造法同 T13。装填手席的活动集合里再放一台不发现任何视点的探针火控并排在前面：`getActiveWeaponControllers()` 先取 base 再取子组，“取了活动集合第一台”这类错误会让判据 A 直接红；`controller` 恒 `null` 的错误则由判据 B 抓住——`null` 回落到 `getActiveMainWeaponController()`，装填手席上它同样是 `null`，这台镜就没有几何。这条用例在迁移前后都能跑：迁移前座位仍静态声明 `sight_port_mg`，静态条目同样按发现结果填上控制器（§3.2 的配对规则），判据 A 的结论不变。

判据 B 不跑求解器，但整段仍在物理步回调里执行：把机枪俯仰体绕高低机轴转 +10°、用 `PhysicsBodyExtensionKt.stateOf(body).update()` 刷新相关子零件的缓存位姿（[:374-376](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/ViewpointGameTest.java#L374) 的写法是遍历全部子零件各更新一次；视点夹具不把刚体加入物理世界，[:373](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/ViewpointGameTest.java#L373) 的注释写明这一点，[:379](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/ViewpointGameTest.java#L379) 就是直接转机体），再走上文的采样链；`connector.joint` 为空时按 [:302](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/ViewpointGameTest.java#L302) 的写法补一颗 `New6Dof`。这几步都是物理线程口径（`setPhysicsRotation`、`getAngles` 读活体刚体），必须像 [:365](../../../src/main/java/io/github/sweetzonzi/machine_max/common/gametest/ViewpointGameTest.java#L365) 那样放进 `physics(controller, () -> …)` 的 `PPhase.PRE` 回调：“不跑求解器”只说明不需要物理世界与步进，不表示可以在主线程转刚体。`New6Dof#getAngles` 的原生实现先调 `calculateTransforms()`、再把两端刚体的当前变换换算成角度，所以关节角跟随手工旋转，不需要物理世界与求解器（[Libbulletjme 的 `New6Dof_getAngles`](https://github.com/stephengold/Libbulletjme/blob/master/src/main/native/glue/com_jme3_bullet_joints_New6Dof.cpp)）。主炮高低机停在零位，两套机构的角度因此不同；发 `RotationSignal` 等伺服追上去的写法要把物理世界与求解器补进夹具，成本高于断言本身，不采用。

直接调 `sampleAimGeometry(sight)` 不构成判据：这条路径本次不改，传哪台控制器它就用哪台，断言它“跟着机枪走”等于自证。轴数同样不是判别据：主 WC 的回落也给出两轴齐的快照——`aimJoints` 不排除不在支承链上的驱动器，高低机匹配不到时仍取第一台（[WeaponControllerSubsystem.java:1024](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L1024)），方向机只要求 `bodyA` 与高低机相等，而 M1A2 主炮的两条高级连接点都声明在炮塔那个子零件上（[m1a2_turret.json](../../../src/main/resources/spark_modules/Machine-Max_M1A2_SEP/m1a2_sep/parts/m1a2_turret.json#L225)），这个条件成立，两轴的限位因此都是 `AimAxisLimit.CONTINUOUS`（[JointAimGeometry.java:57](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/control/aim/JointAimGeometry.java#L57)）。回落分支另判：`controller` 为 `null` 时走 `getActiveMainWeaponController()`，无稳镜头因 `aimTarget` 为空而不发瞄准输入，双稳镜头照常发世界点。
