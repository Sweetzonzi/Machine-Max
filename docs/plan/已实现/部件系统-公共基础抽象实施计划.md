> **创建日期**：2026-10-23。
> **范围**：Machine-Max 的公共部件基础、普通部件实现、类型分派与兼容管线；ARMS-Core 仅作为扩展接入方说明。

## 1. 目标与产品边界

公共部件基础负责可复用的机械结构，具体部件类型负责各自的装配、交互与数据规则。Machine-Max 提供 `AbstractPart` 与 `RegularPart`；ARMS-Core 在公共抽象上实现 `BodyPart`。MM 的运行时依赖中不得出现 ARMS 类。

### 1.1 三种装配体

| 装配体 | 接受的部件 | 控制与生命周期职责 |
| --- | --- | --- |
| 普通 MM 载具 `VehicleCore` | `RegularPart` | VehicleCore 管理拓扑、HP、保存、同步、实体与分裂；车辆控制子系统处理输入 |
| 可驾驶机甲，继承 `VehicleCore` | `RegularPart` | `MechaControlSubsystem` 持有并驱动 MechaControl；装配、HP、保存、同步与分裂由 VehicleCore 管理 |
| 机娘／外骨骼 `ArmsCore` | `RegularPart`、`BodyPart` | ArmsCore 管理身体装配，直接持有 MechaControl，生命周期与宿主关联 |

可驾驶机甲通过普通机械模块、关节与控制子系统工作，不依赖 BodyPart。`MechaControlSubsystem` 是后续 ARMS 任务，不属于本计划的实现交付物。此处的角色控制器指 ARMS 当前的 MechaCharacter 动态刚体实现；本计划不变更其力学方案。

`RegularPart` 表示普通机械模块，能够成为载具结构或机娘的武器、推进器、装甲等装备。`BodyPart` 表示使用身体槽位、身体属性与骨骼绑定规则的模块。核心身份是 BodyPart 内的角色，不是第三种 MM 部件类型。

### 1.2 本轮交付

1. 公共实例、公共定义与必要的公共保存数据契约。
2. 完整承接现有 MM 功能的 RegularPart 分支。
3. `type` 缺省为 `regular` 的定义 Codec，以及外部类型注册、创建与恢复入口。
4. VehicleCore 的 RegularPart 接纳规则，以及公共 SubPart／Connector／动画／子系统调用面。
5. 普通物品、工具、制造、创造栏、保存与网络管线的类型边界。
6. 旧普通部件定义、存档和蓝图的兼容性验证，以及外部类型的最小扩展验证。

### 1.3 后续任务

下列内容由 ARMS 后续实施，本轮仅保留接入能力：BodyPart 的正式内容格式、身体核心与槽位校验、默认肉腿、基础生命与动作能量、关节姿态驱动、身体伤害与宿主绘制、ArmsCore 的完整装配同步、MechaControlSubsystem。

本轮不要求把所有载具设施泛化为通用装配体设施。例如 MMPartEntity 的载具绑定、载具蓝图格式、履带与 VehicleCore 的关系可以保持载具专用。

## 3. 目标对象与职责

### 3.1 类型结构

以下为目标结构，Body 分支由扩展模组提供：

```text
MM                                 ARMS
AbstractPart
  ├─ RegularPart
  └─────────────────────────────── BodyPart

AbstractPartType
  ├─ RegularPartType
  └─────────────────────────────── BodyPartType

AbstractPartData（公共实例状态契约）
  ├─ RegularPartData
  └─────────────────────────────── 身体专属数据，按实际字段需要定义
```

公共类放在 `common/mech/part/` 域。RegularPart／RegularPartType 位于 `common/mech/vehicle/`，RegularPartData 位于其 `data/` 子包；不以移动全部物理、连接器或渲染文件作为验收要求。本文不承诺 Java API／二进制兼容；依赖 MM 的源码项目需要一起编译适配。内容包与保存数据兼容规则见 §4。

### 3.2 实例与定义的分工

| 能力 | 公共层 | Regular 分支 |
| --- | --- | --- |
| 身份与归属 | UUID、名称、Level、定义 ID、变体、装配体引用 | 使用公共身份 |
| 机械结构 | SubPart、连接点、子系统、骨骼切分及按名索引 | 使用公共结构 |
| 表现 | 模型、动画控制器、涂装、动画推进与公共查询 | 组装线框及材料进度显示 |
| 信号 | 部件级存储、local/global 路由、生命周期接入 | 使用公共信号能力 |
| 质量与耐久 | 实际质量查询、共享耐久机制、损伤通知 | 材料完成度对质量、耐久及维修上限的影响 |
| 工作许可 | 提供子系统可工作的统一查询 | 使用组装进度与 functionalThreshold 实现 |
| 制造与材料 | 不要求存在制造配方或材料进度 | getRecipe、assemble、disassemble、材料进度与同步 |
| 装配体伤害 | 上报来源、有效伤害及需要的传递结果 | 保持 vehicle_damage_rate 等现有 JSON 字段及载具折算行为 |
| 载具 HP 贡献 | 不强制定义 | 保持 vehicle_durability_rate 与现有 HP 汇总 |

公共定义包含模型／变体等通用结构与共享属性。图标、堆叠上限可作为通用物品展示数据使用，但存在定义不等于一定生成 MM 物品。Body 分支需要的核心参数、默认肢体和身体属性留在扩展定义中。

第一轮复用 VariantAttr／SubPartAttr，不为全部属性类机械地建立对应子类。某个字段确实具有类型专属语义时，通过专属定义或组合配置承载。

### 3.3 构建与恢复

目标入口区分“新建部件”与“恢复部件”，共同经过定义对应的工厂：

```text
定义 ID → 本逻辑侧的定义注册表 → 类型描述与工厂
  新建：定义 + 变体 + 创建上下文 → 部件实例
  恢复：公共状态 + 专属状态 + 恢复上下文 → 部件实例
```

恢复上下文必须显式指定状态策略。以下名称对应 PartRestoreMode 的两个枚举值：

| 状态策略 | 调用场景 | 必须应用的内容 | 必须忽略的内容 |
| --- | --- | --- | --- |
| `FULL_STATE` | 存档加载、客户端完整重建、收纳物品放置 | 输入数据的材料／组装进度、耐久、涂装、连接器动态状态与子系统保存状态 | 不因恢复额外生成默认配装或资源 |
| `STRUCTURE_ONLY` | 蓝图放置 | 部件与 SubPart 结构、变体、相对位姿、连接关系及结构所需的身份引用 | 不读取保存的材料／组装进度、耐久比例、涂装选择、连接器动态状态或子系统保存状态 |

Regular 的 `STRUCTURE_ONLY` 使用材料进度 0、组装进度 0、线框开启、变体默认涂装，以及现有骨架构造规则产生的初始耐久／子系统状态。电量、库存、装填等必须采用该状态策略下的初始化结果，不能导入输入数据中的储存资源。该策略保留结构，并按未组装状态初始化部件。

`VehicleData.normalized()` 不能代替状态策略：其结果中可以包含原实例的材料、耐久与子系统数据，工厂必须依据上下文决定是否读取。结构校验、类型接纳与错误处理在两种策略下均执行。收纳物品与蓝图必须显式传递不同策略，工厂不得用缺省的完整恢复吞掉这一区别。扩展工厂应实现并遵守所支持的策略；不支持某种策略时，明确拒绝该调用。

- Codec 解析配置或保存数据，不负责把刚体／约束直接加入物理世界。
- 公共构建过程负责结构初始化；扩展字段初始化完成后才能调用依赖它们的构建钩子，避免父构造器调用未初始化子类状态。
- 恢复的身份与结构引用按加载／放置上下文保持一致；完整状态或骨架状态由显式策略决定。新建使用新身份，默认配装不在恢复公共钩子中生成。
- 工厂失败时不得留下已注册子系统、半连接图、实体或世界中的约束。类型接纳与可纯数据完成的校验尽量在 native 对象分配前执行。
- 只有内存结构准备完毕后，由现有物理任务机制完成入世。加约束时两端刚体已经入世；移出刚体前摘除引用它的约束。

## 4. 定义、保存数据与网络兼容

### 4.1 定义 type 分派

在现有 `parts` 定义入口增加可选字段 `type`，缺省值是 `regular`。类型分派表可由模组注册；MM 注册 Regular，ARMS 注册自己的类型。不得在 MM 的 switch 中直接引用 BodyPart 类。

| 输入 | 规则 |
| --- | --- |
| 不含 type | 采用 RegularPartType 的字段与默认值 |
| type 为字符串 regular | 采用 RegularPartType |
| type 为已注册扩展 ID，例如 arms_core:body | 采用该扩展的定义 Codec |
| 未注册 ID、空字符串、非字符串或 null | 返回带定义 ID／字段信息的错误 |
| 已识别类型的专属字段无效 | 返回该类型的解码错误，不尝试按 Regular 解码 |

只有字段确实缺失才采用缺省值。不能用“尝试 Body 失败后再尝试 Regular”的无条件 Codec.either 作为类型识别，避免显式扩展定义被错误降级。

Regular 编码可以省略默认 type；扩展类型编码必须保留类型标识与专属字段。兼容目标是字段语义往返一致，不要求 JSON 的字段顺序、缩进、注释或显式默认值写法保持原文。

### 4.2 内容包加载与重载

PartModule 使用公共分派 Codec，维护一份本逻辑侧的已发布定义表；Regular 查询为该表的筛选视图或受控查询，避免维护两份可独立修改的权威定义。候选定义暂存区只服务本轮读取和校验，不是运行时权威表，也不对工厂开放。

保持现有文件名到定义 ID 的规则，以及 Regular 的字段名、默认值、variants 简写／完整映射行为。类型描述注册表与内容定义表分别管理：前者来自模组注册，后者随内容包重载。

模型、连接器与子系统定义按依赖关系准备；跨部件默认连接等扩展引用在全部定义加载后校验。双端清理的时点与缓存失效必须覆盖全部类型，不能让某个类型在重载中被另一个模块单独清空。

**发布契约采用“暂存 → 校验 → 计算有效集合 → 发布”：**

1. `onStart` 为当前逻辑侧建立本轮暂存区，并使该侧运行时定义查询在本轮发布前返回空集合；派生的 Regular 查询、创建缓存和制造查询同步失效。上一轮同名定义不能作为本轮无效定义的回退。
2. `read` 仅写入暂存区。跨部件引用通过校验上下文访问候选集合，不能为了方便解析而把候选对象提前放入权威表。
3. 全部候选读取完成后执行局部约束和跨部件引用校验。显式配置的默认连接对象，其 ID、变体和目标连接点都必须有效。类型校验器需提供依赖关系及错误归属，不能只抛出无法定位对象的汇总异常。
4. 先标记直接失败的定义，再沿必需依赖关系传播无效状态，直到集合稳定。若 A 默认连接 B、B 默认连接 C，而 C 无效，A、B、C 均不能发布；无关且有效的定义可以发布。依赖环的合法性由类型校验器判断，不能仅用“被遍历过”视为验证成功。
5. 有效集合中的每条必需引用都解析到同一集合内的有效目标后，才一次性发布该集合的只读快照并重建派生视图。运行时读者只能看到空集合或已经验证的集合，不能看到逐项填充的半成品。发布前发生未处理异常时，本轮保持空集合。
6. 按 ID 查定义、创造栏、制造索引与新建／恢复工厂都只使用已发布集合。工厂即使收到调用方持有的定义对象，也要确认它属于当前已发布集合；暂存对象、验证失败对象及失效缓存不能绕过检查创建实例。

Spark 的 onFinish 异常捕获只提供诊断，不提供回滚（S17）。校验器可以报告失败并发布有效的依赖闭合集合；无法完成校验时不发布候选内容。该规则由 PartModule 的发布实现保证，不依赖异常向加载器外层传播。失败诊断需列出直接错误与依赖失败链。

此处约束运行时定义查询和新创建行为。已经存活的实例如何处理内容重载，由既有实例生命周期或专门迁移规则决定，不能把阻断无效定义误实现为销毁所有活实例。

### 4.3 保存数据

公共状态包含定义 ID、UUID、名称、变体、涂装、SubPart 状态及共享耐久等机械状态；材料进度、组装线框等进入 Regular 专属状态。字段的最终归属按阶段 P1 的调用审计确认。

- RegularPartData 的 JSON 编码保持现有 PartData 的字段布局、名称与缺省值；Java 类名调整不要求修改磁盘字段。
- VehicleData 中只保存 RegularPartData；ArmsCore 的混合部件数据由 ARMS 后续定义。
- 现有 `registry_key` 能定位定义及工厂，不要求给每条历史实例数据再补一个 type。
- 若扩展专属状态的解析需要逻辑侧注册表，使用明确的第二阶段恢复入口；不得依赖全局“当前世界”或在 Codec 中访问客户端单例。
- 公共数据复制／坐标变换保留类型专属状态。VehicleData 的 Regular 专用复制路径可以继续使用明确的 RegularPartData。
- 保存数据保真与实例恢复策略分别验证：同一份数据可供完整恢复或骨架恢复，不能靠预先清空模板 DTO 才满足蓝图规则；恢复操作也不修改共享输入 DTO。
- 定义缺失、变体缺失、定义类型与容器不匹配时明确失败；不能创建普通部件替代未知身体部件。
- 同一个定义 ID 在一个加载结果中对应一种类型。定义 ID 的类型属于持久化契约，跨类型修改需要显式数据迁移，不受“type 缺省兼容”保证。

### 4.4 网络

先列出实际调用链，再决定是否改变二进制格式。PartType 的手写 STREAM_CODEC 与 JSON type 分派分别审计；不能因为 JSON 有默认值就认为二进制自动兼容。

- 普通载具数据、载具创建与载具蓝图载荷可以只接受 Regular 数据。
- 公共身份、SubPart ID、部件 UUID 等既有定位字段尽量保持含义与顺序。
- 纯 Java 类型提取不要求提升协议；线上字段、顺序或分派标识改变时，提升涉及的 MMPayloadRegistry registrar 版本。
- PartAssemblyProgressSyncPayload 可保持 Regular 专用。Regular 装在外部装配体时，需要由装配体解析入口或外部适配器找到同一部件，不能向载具注册表写入伪载具。
- 载具附件、模板、蓝图文件与网络数据都需要验证，不能只测试直接调用一个 Codec。

## 5. 装配体与公共物理调用面

### 5.1 类型接纳

IPartAssembly 的部件参数使用 AbstractPart，并提供类型接纳查询供 UI 和服务端使用。VehicleCore 的部件表与拓扑图使用 RegularPart；公共入口对参数校验后才进入 Regular 实现，避免在每个热路径反复强转。

载具构造、存档恢复、物品新建、连接导入、跨载具合并均校验 Regular 类型。批量恢复或合并应在写图、迁移子系统、产生物品消耗前验证所有候选部件；失败不留下部分变更。

外部装配体接受哪些类型，由其实现决定。通过装配体类型检查后，还须通过连接点标签、变体与接口匹配检查。MM 服务端不根据客户端提供的 type 决定允许安装什么，而是读取权威定义。

### 5.2 通用结构

SubPart、Connector、命中记录、通用渲染视图使用公共部件引用。RegularPart 保持现有根 SubPart 选择与坐标口径；身体核心语义由 ARMS 确定，不能通过质量最大或耐久贡献最多来推断。

现有碰撞、扫掠、关节约束、能源网格与按名索引尽量保留实现。连接器条件检查仅依赖公共定义提供的标签与变体视图。身体专用 Connector 工厂与动画驱动不在本轮实现。

### 5.3 生命周期与损伤

公共部件提供 tick／物理步前后推进、子系统挂接／摘除及功能许可。Regular 的材料完成度留在其许可实现内；公共 AbstractSubsystem 不直接读取 Regular 字段。

损伤先形成有效命中记录，再执行部件类型的局部状态变化与装配体上报。Regular 保持正常／已毁两档传递率、跨越耐久零点时的分段折算及材料进度联动。身体受损后的属性或宿主伤害由扩展处理。

共享耐久状态只有一个权威写入路径。信号与子系统仍按既有顺序注册／注销；通用控制器可使用已有 Level 构造器，不要求 VehicleCore 身份。

## 6. 工具、物品、制造与 UI 边界

### 6.1 工具许可

公共实例提供 `crowbarRemovable` 布尔，Regular 普通构造默认 true，外部构造上下文可设置 false。该值表达撬棍许可，不表达战斗无敌、不可维修或不可被销毁。

新建与恢复必须通过同一套上下文规则确定该值。若实施引入运行时可修改的许可，则把修改值持久化；不能让重登或客户端重建重置已保存的许可。仅由构造上下文确定的规则无需增加内容包字段。

| 操作 | Regular 行为 | 外部部件边界 |
| --- | --- | --- |
| 撬棍断连、拆卸冲击、取下与物品化 | 操作入口先检查撬棍许可，通过后保持普通行为 | 不调用类型不支持的物品生成逻辑 |
| 焊枪组装／材料拆解／零进度取下 | 仅对 Regular 或明确提供对应能力的对象执行 | 不以强转失败、空配方或固定进度 1 模拟拒绝 |
| 维修 | 保持材料上限与普通子系统维修 | 独立的维修能力或明确拒绝；撬棍布尔不代替维修许可 |
| 喷漆 | 使用公共涂装能力 | 定义存在相应涂装时可复用 |

Regular 装在 ArmsCore 上时仍保有 Regular 类型；是否允许工具操作还可受装配体规则约束。本轮只定义公共入口，ARMS 的改装工作站规则由后续任务实现。

### 6.2 物品、制造与展示

MM 的普通零件物品、PDA 装配请求及制造蓝图只解析 Regular 定义。服务端在创建实例前检查定义类型，避免人为构造的数据组件绕过创造栏筛选。

| 入口 | 本轮规则 |
| --- | --- |
| MM 零件创造栏 | 仅列出允许展示的 Regular 定义 |
| MM 制造蓝图创造栏 | 仅列出有有效制造配方且允许展示的 Regular 定义 |
| 两个创造栏图标 | 使用与对应列表相同的有效候选集，空集使用占位图标 |
| 普通制造索引 | 仅接纳 Regular；显式引用扩展类型时给出可定位错误 |
| 身体物品／培养／身体制造 | 由 ARMS 提供，本轮不自动为扩展类型生成 MM 物品 |

### 6.3 HUD、研发与预览

公共 HUD 可显示名称、耐久、质量和通用子系统状态。材料条、材料列表、研发装配门禁及线框提示仅对 Regular 显示与执行。Body 的健康、槽位和培养状态由 ARMS 界面提供。

PartAnimatable 可复用公共模型／变体结构；VehicleAnimatable 保持 Regular 载具预览。Tooltip、PDA、部件模型元素与蓝图库校验分别使用所需的通用或 Regular 查询。不能为了让 UI 编译，给所有外部部件返回虚假的材料数与制造配方。

## 7. 动画与实体代理

### 7.1 动画所有权

AbstractPart 持有一套动画控制器与共享 ModelPose。IAnimatable 的泛型以公共部件类型为基准；子类不能再以另一个泛型重复实现同一接口。MechMolangContext 使用公共部件查询，保留 local/global 的已有含义，扩展查询通过上下文扩展点提供。

装配体负责安排部件动画 tick。每个部件每个适用物理步只混合一次，每个主线程发布相位只发布一次；Regular 装入外部装配体时也遵守此规则。公共抽象不创建第二套实体动画体。

### 7.2 实体代理由装配体决定

SubPart 的实体自动创建逻辑增加装配体策略门。VehicleCore 选择 MMPartEntity，外部装配体可选择宿主绘制／交互代理。该策略适用于该装配体中的两种部件，不能简单按 Regular／Body 决定是否生成实体。

MMPartEntity 的 ObjectManager 载具绑定可以保持载具专用。选择宿主代理的装配体不触发它的自动补建；销毁、换绑与入世检查也必须遵守相同策略。外部实体查找与绘制由扩展提供，不要求在本轮建立统一的全局装配体注册表。

| 定义 Codec | 缺省 type 与显式 regular 等价；扩展定义往返保留类型与专属字段；null、未知类型及错误专属字段明确失败 |
| 定义发布 | 读取阶段候选不对工厂可见；构造 A→B→C 的必需依赖链，令 C 的默认连接目标／变体／连接点无效，验证三者均不可查询、制造或创建，无关有效定义可用；捕获 onFinish 异常后也无候选泄漏 |
| 定义重载 | 首轮有效、次轮同 ID 校验失败时，上一轮查询结果及缓存不能用于新建／恢复；下一轮修复后可正常发布；重复执行校验不会把失败对象带入权威表 |
| Regular 数据 | 材料进度、组装进度、共享耐久、UUID、变体、涂装与子系统状态往返一致 |
| 恢复策略 | 同一份含材料进度、损伤、非默认涂装及子系统资源的数据，收纳物品走 FULL_STATE，蓝图走 STRUCTURE_ONLY；前者恢复状态，后者仅保留结构且进度为 0、不导入保存资源；输入 DTO 与 normalized 结果中的动态字段不因实例恢复被改写 |
| 蓝图复制 | rebased 只改变规定的位姿／速度；normalized 的 HP 处理符合现有规则；连接与履带引用有效 |
| 容器与工厂 | VehicleCore 拒绝扩展类型；新建与恢复选择正确工厂；失败不消费物品、不注册半成品 |
| 损伤与维修 | 正常／已毁传递率及跨零点折算一致；Regular 材料上限有效；公共部件不被强加材料状态 |
| 工具与展示 | 撬棍被禁时无断连／冲击／取下／物品产出；非材料类型不执行焊枪材料拆解；列表与图标候选一致 |
| 公共能力 | 子系统许可、local/global 信号、供弹引用与涂装保持可用；每相位动画推进／发布次数正确 |
| 代理与网络 | 外部装配体可关闭自动实体；数据提前到达或延迟到达时绑定正确；改动的实际载荷完成编码解码验证 |

纯 Codec／数据测试只构建配置和 DTO，不为测试解码创建 native 刚体。工厂、代理与动画相位等运行行为按需要使用真实环境验证。测试扩展类型可置于测试源码集，不要求正式 BodyPart 功能作为前置。

### 10.2 实施时执行的命令

所有 Gradle 命令使用仓库包装器与离线解析：

```powershell
# Machine-Max 仓库
.\gradlew --offline test
.\gradlew --offline checkSchemas
.\gradlew --offline build

# 修改 builtin Schema 后生成派生文件
.\gradlew --offline syncSchemas

# ARMS-Core 仓库，验证复合构建和接口适配
.\gradlew --offline test
.\gradlew --offline build
```

运行验收使用 `runServer` 和 `runClient`：服务器启动到可用状态，核对内容解码与注册；客户端验证装配、断连、撬棍、焊枪、喷漆、存取、蓝图预览、进出区块和重连。涉及拓扑与 native 生命周期时增加对应物理探针。MM 的 `PartFoundationGameTest` 提供两条构造／恢复探针，运行命令为 `runGameTestServer`，具体覆盖与边界见 `docs/部件公共基础接入.md` 的“验证方式”。

线程与物理纪律沿用仓库约束：主线程与物理线程通过规定任务／快照接口交互，JME／JOML 通过 Spark 转换，保留 updateLock，子系统按生命周期调用父实现。验证中不通过把关节刚体切成运动学来冻结它们。

## 11. 范围控制与后续对接

- BodyPart 的正式定义由 ARMS 注册，核心标记、基础血量、默认连接对象及身体驱动不进入 MM 的 Regular 字段。
- 可驾驶机甲继承 VehicleCore 且仅用 RegularPart；MechaControlSubsystem 后续接入公共动画／关节／作动器契约，不要求 VehicleCore 支持 BodyPart。
- ArmsCore 后续接受两种部件。其混合装配保存、宿主伤害和身体核心唯一性不套用 VehicleData 的载具规则。
- 仅为公共参数签名而改动 ARMS 占位代码时，不把该修改报告为身体功能已经接入。
- 新功能需求若要求身体制作、通用装配体蓝图库或统一对象管理器，另行定义实现范围；本轮交付以 §9 和 §10 的判据为准。
