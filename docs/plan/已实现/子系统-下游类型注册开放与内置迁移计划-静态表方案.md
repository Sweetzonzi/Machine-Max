# 子系统：下游类型注册开放与内置迁移计划（静态表方案）

> 状态：已实现（2026-11-14）。子系统类型登记使用 MM 自有的静态表 `SubsystemKinds`，一条登记同时给出该类型的安装属性 Codec 与静态属性 Codec；类型身份由登记表派生。交付范围见 §8，验收记录见 §9。
> 版本：B 方案（静态表），源码核对基线：`444f200c`，正文源码坐标为活引用。
> 对照：`../计划中/子系统-下游类型注册开放与内置迁移计划.md` 用两张 NeoForge Codec 注册表完成同一目标，已否决。附录 A 给出该路线的摘要、逐条对比与否决理由；正文与附录 A 都自带所需事实，不要求先读那份文件。

## 1. 范围与交付原则

1. 子系统类型登记放进 MM 自有的静态登记表。表的当前源码形态见 §2 S1：两张 NeoForge Codec 注册表。
2. 一条登记同时绑定一个类型的安装属性 Codec 与静态属性 Codec，两侧配对由数据结构保证，不靠两次同名。
3. 类型身份从登记表派生，使用带命名空间的 `ResourceLocation`；具体属性类不声明第二份身份。
4. 全部可用内置类型迁入该表。迁移以真实内置实现及内容包验收，不建设独立示例模组或演示子系统。
5. 保留属性对象的 `createSubsystem(owner,name)` 工厂，以及子系统的信号、能源、伤害、同步、保存和生命周期机制。
6. 内置内容包的类型 ID、definition 引用、安装字段和运行行为保持兼容；Java API 的签名变化要求依赖模组重新编译。
7. 表在内容包装载开始时封表；封表后的登记立即失败，不静默生效。

本计划不包含轮式／履带动力学、角色代理施力、执行后端切换、汽车控制器的能力接口化、全新推进器实现或子系统线程调度调整。这些功能可以消费本计划开放的登记接口，各自形成独立实现范围。MM 的注册能力验收不等待 ARMS-Core 的轮驱实现。

## 3. 类型、型号与实例身份

| 身份 | 含义 | 目标形态 |
| --- | --- | --- |
| 类型 ID | 登记表的一项，同时代表安装属性 Codec 与静态属性 Codec | 如 `machine_max:wheel_driver`、`arms_core:character_wheel` |
| 型号 ID | 内容包提供的一份静态参数定义 | 由安装属性的 definition 引用，与类型 ID 独立 |
| 实例名称 | 某个 SubPart 上一项子系统的名字 | 用于已有信号寻址、状态保存和运行期查询 |

**类型身份只从登记表派生。** 两个属性基类分别提供 `public final ResourceLocation getType()`：返回值是 `SubsystemKinds.nameOf(codec(), 槽位)`，即该 Codec 实例在登记表里的命名空间 ID。反查按引用比较（`==`）遍历登记项，语义是实例身份而不是 `equals`，与 S12 描述的注册表行为一致；登记项最多 21 条，调用点在解码与编码路径上，不另建反向索引。查不到登记实例时抛出「未登记 Codec」诊断（§6.3），不伪造 ID、不返回 null。

具体属性类只声明自己的单例 CODEC，不覆写 `getType`，也不另写类型身份常量。型号绑定时比较两个派生 ID 的值相等，因此下游无法靠覆写 `getType` 让不同登记项冒充同一类型，也不需要第三张注册表。它要求登记先于解码，时序见 §4.3。

类型集合就是登记表本身：具体属性类只声明自己的 Codec 单例、工厂与几何校验，没有类型常量、没有 `getType()` 覆写。原来的 `SubsystemTypes` 枚举按项目「没有消费方的类型与分支不写」的准入直接删除——S3 之外没有消费者：全仓库无 switch、无 ordinal、无序列化。若将来出现真实消费者（例如某个 HUD 或脚本接口需要内置 ID 常量），可以加一个只表达登记名的常量集合，取值遵守 §5，不能成为第二份身份声明或白名单。

登记表的条目是 Codec 单例，运行期子系统实例由安装属性工厂创建。表不持有任何机体的子系统实例。

## 4. 登记表与分派

### 4.1 表的形态与公开入口

`common/mech/subsystem/attr/SubsystemKinds.java`，形态与 `PartKinds` 同构：

```java
public final class SubsystemKinds {
    public record Kind(MapCodec<? extends AbstractSubsystemAttr> installCodec,
                       MapCodec<? extends AbstractSubsystemStaticAttr> staticCodec) {}

    public enum Slot { INSTALL, STATIC }                          // 反查与诊断指明查的是哪一侧

    public static void register(ResourceLocation id, Kind kind);  // 重复 ID 或重复 Codec 实例抛异常
    public static Kind get(ResourceLocation id, Slot slot);       // 未登记抛异常，不回退
    public static ResourceLocation nameOf(MapCodec<?> codec, Slot slot); // 引用比较反查，未登记抛异常
    public static void seal();                                    // 内容包装载开始时调用
}
```

一条登记写入后，同一 Codec 实例不能出现在第二条登记里：类型 ID 靠实例反查，共用实例会让 ID 不唯一，因此`register` 在生效时校验并拒绝。

- **内置登记写在 `SubsystemKinds` 的静态初始化里**，共 21 条，与 `PartKinds` 把 `regular` 放静态初始化同一做法。这样单元测试解析部件定义时无需任何模组初始化，S15 描述的假总线依赖随之消失。
- **下游登记是一行直接调用**：`SubsystemKinds.register(TYPE_ID, new Kind(installCodec, staticCodec))`，在模组初始化阶段执行（`FMLCommonSetupEvent` 的 `enqueueWork` 可用，与 ARMS-Core 的 `BodyParts.register()` 同法），必须早于内容包装载。不需要公开 `ResourceKey`、不挂 mod event bus、不需要 DeferredRegister。
- **两侧配对由数据结构保证**：同一条登记同时给出两个 Codec，写不出「安装侧叫 A、静态侧叫 B」这种错。
- **内容包只能选择已登记类型**，不能自带 Java 实现。这与 `PartKinds` 对部件种类的边界完全一致，公共文档按同一句话写。

### 4.2 分派 Codec

`common/mech/subsystem/attr/SubsystemCodecs.java` 提供 `INSTALL_CODEC` 与 `STATIC_CODEC` 两个手写 `Codec`，形态照 `PartKinds.CODEC`（S16）：

1. 读 JSON 顶层的 `type` 字段。子系统没有默认类型：字段缺失、显式 null、空串、非字符串都失败。
2. `SubsystemKinds.get(id)` 取登记项；未登记这里抛出 §6.3 的「未知类型 ID」诊断，携带未知 ID 与槽位（安装／静态）。该诊断是 `PackContentException` 加 `MMLanguageRegistry` 组件，不落到 DFU 的英文 literal（S12）；解码期从构造器或 Codec 抛内容异常是本项目既有路径（S17）。
3. 把整个对象交给登记项的对应 Codec 解码。
4. 解码完成后核对 `attr.codec() == 登记项.codec()`，不一致即失败：下游不能把一种登记 ID 解码成报告另一种 Codec 的对象，再借型号配对通过校验。
5. 编码时用 `SubsystemKinds.nameOf(value.codec())` 取权威 ID 写入 `type`，并核对登记项的 Codec 与该对象是同一实例；未登记实例必须失败，不能静默写出别的 ID。

**类初始化顺序约束**：`SubsystemCodecs` 的静态初始化只构造 Codec 对象，lambda 体内才引用 `SubsystemKinds`；`SubsystemKinds` 的静态初始化可以引用具体属性类。这个方向保证任何入口先加载哪个类都不成环——属性类静态初始化引用 `SubsystemCodecs`，登记表静态初始化引用属性类，两者不会互相等待。若把两个职责写进同一个类，会形成「表初始化 → 属性类 → 表」的环。

### 4.3 时序与封表

1. 表与分派 Codec 都不接触 `MachineMax.REGISTER`：解码路径不要求事件总线已安装（S15 的耦合在本方案里不存在）。
2. 内置登记随 `SubsystemKinds` 类初始化完成；下游登记在模组初始化阶段完成。两者都必须早于内容包装载。
3. `SubsystemModule.onStart` 首次执行时调用 `seal()`（该回调位于包装载开始、任何子系统文件被读取之前，S13）。封表后 `register` 抛 `IllegalStateException`，不静默生效：登记窗口是确定的，迟到登记会让装载失败而不是让后面的文件悄悄生效。
4. 表按进程保留，内容包 reload 不清表；型号表（`MMDynamicRes.STATIC_SUBSYSTEM_ATTRS`）仍按轮清空，二者职责不同。
5. 静态初始化期间不读型号、不构造子系统实例：登记只交 Codec 单例。

## 6. 型号绑定、诊断与实例创建

### 6.1 解码构造期完成基础绑定

S4、S11 表明具体安装属性在构造器里调用 `getStaticAttr`。型号缺失与类型不匹配因此在 JSON 解码时暴露，不在出车或物理步才暴露。本计划保留这种立即绑定方式，把基础校验明确落在 `AbstractSubsystemAttr.getStaticAttr()`：

```text
分派 Codec 按已登记类型选择安装 Codec
  → 安装属性的解码构造器调用 getStaticAttr
  → 定位 definition 对应的静态定义
  → 两侧按 §3 从登记表派生类型 ID
  → 按 ID 值相等校验，失败报告内容错误
  → 返回已确认类型的静态定义，具体属性执行所需的类型读取
```

这里的比较是**内容级**检查：安装属性的类型 ID 与该 definition 的类型 ID 必须相同，即「这份型号属于这类子系统」。登记级的配对已由 §4.1 的数据结构保证，两者不是同一件事。

`getStaticAttr` 保留当前两端定义来源的选择口径（先查客户端表、再查服务端表），是解码与直接 Java 构造共用的基础绑定边界，诊断消息携带命中哪一级来源，便于区分「这一端没有加载该型号」与「型号确实不存在」。型号缺失、类型错误与未登记 Codec 使用结构化内容诊断，不抛裸 NPE／ClassCastException，也不回退成 BASIC。

### 6.2 几何校验与发布链

几何引用保持以下已有链路：`SubPartAttr.validate` → `AbstractSubsystemAttr.validate(variant,subPartName,subsystemName)` 的具体实现，外层由 `VariantAttr.validate`、`AbstractPartType.validate` 与 `PartDefinitions.validateAndPublish` 调度。定位器、连接点与需要完整模型的检查继续在这里完成，坐标见 S11。

不能仅把型号／类型检查放进空的基类 validate：8 个现存覆盖方法都不调用 super，且构造器已在更早阶段读取静态定义（S11）。若未来另作延迟绑定设计，必须同步处理全部构造器读取、字段初始化和覆盖方法；该改造不属于本计划。

### 6.3 诊断与翻译交付

| 失败 | 明确落点 | 消息必需信息 |
| --- | --- | --- |
| 型号缺失 | getStaticAttr 的 definition 查找 | definition ID、期望类型 ID、命中哪一级来源 |
| 型号类型不匹配 | getStaticAttr 的两侧类型 ID 比较，位于强转前 | definition ID、期望与实际类型 ID |
| 未知 JSON 类型 ID | `SubsystemCodecs` 的 `type` 读取与登记查找边界，位于具体属性构造前 | 未知 ID、安装／静态槽位 |
| codec() 返回未登记实例 | 基类 getType 的反查失败；编码路径同样失败 | 槽位、Codec 实例未登记、修复提示；无可反查 ID 时不得伪造 ID |
| 封表后登记 | `SubsystemKinds.register` | 类型 ID、封表已被触发的说明 |

上表的诊断键登记在 `src/main/java/io/github/sweetzonzi/machine_max/datagen/MMLanguageRegistry.java#MMLanguageRegistry`，格式参照同文件 `#ERROR_PART_SUBSYSTEM_LOCATOR_NOT_FOUND`（`zh_cn` 与 `en_us` 两份文案、`%1$s` 序号参数），组件取 `MMLanguageRegistry#component`。键名为 `error.machine_max.subsystem.` 下的 `type_invalid`（`type` 缺失、非字符串、空串或非法资源名，参数是看到的原值）、`type_unknown`（未登记 ID 与槽位）、`definition_not_found`（型号 ID 与期望类型）、`definition_type_mismatch`（型号 ID、期望与实际类型）、`codec_unregistered`（槽位）、`kind_sealed`（类型 ID），最后一项以 `IllegalStateException` 抛出，其余是 `PackContentException`。按 `datagen/AGENTS.md` 的纪律，后续新增或修改文案仍需逐条与维护者确认。

未知类型的诊断在 `type` 查找边界直接产出，可翻译、可带参数，不经过 DFU 的英文 literal（S12）。消息组件仍走既有 `PackContentException` 与加载器文件关联机制，不另建诊断包装类型。

### 6.4 实例与生命周期

自定义子系统可以继承 `AbstractSubsystem`／`BasicSubsystem`，并通过现有能力接口参与供能或信号。宿主、生命周期调用和保存格式服从 S6、S7；安装属性经 `createSubsystem(owner,name)` 创建实例，MM 中不逐种增加工厂分支。汽车控制器识别具体轮驱类的限制见 S10，该业务兼容性不由注册成功隐式保证。

## 7. 兼容与内容工具

### 7.1 内容和存档

所有已登记类型 ID、definition 型号引用、实例名称及类型专属字段保持。当前内容包无需为本次注册迁移批量改 JSON，存档恢复也按相同 ID 选择属性 Codec。

表的实现形态不构成持久身份：存档／配置使用命名空间 ID，不能把登记顺序或任何整数编号当作永久类型编号。2026-11-14 源码盘点没有发现 `SubsystemTypes` 的 switch／ordinal 消费者，直接类型比较只有 S4 一处，实施时复核结果一致；枚举序列因此不是兼容数据。

### 7.2 Java API 与版本

`getType()` 的目标公共契约是基类 final 的 `ResourceLocation` 派生方法；具体属性实现 codec 与工厂，类型身份由基类读取。这属于 Java 扩展 API 变更，下游需按发布版本重新编译并声明相应最低 MM 版本。公共文档说明登记入口、Codec 实例身份、两侧 Codec 的同项要求、封表时机与工厂入口。

本计划没有载荷字段改动：`network/` 下对两个属性基类零引用，两张表的数字 ID 也从未上线缆（S14）。是否提升网络协议号按实施时实际产生的网络变化判定，不能仅因 Java 方法签名变化推导出协议字段变化。

### 7.3 schema 与文档

基准 schema 位于 `src/main/resources/spark_modules/Machine-Max_Builtin/machine_max/docs/zh_cn/schemas/subsystem/`，英文副本在同级 `en_us/`。顶层 `type` 接受两种情况：

1. 21 个已开放的完整 `machine_max` 类型 ID，使用明确枚举校验，并各自对应一条 if／then 字段分派。
2. 具有合法命名空间与路径、且命名空间不是 `machine_max` 的外部 ID，由下游 schema 约束其专属字段。

实现为 `type` 字符串上的 `anyOf`：21 项 enum，或匹配 `^(?!machine_max:)[a-z0-9_.-]+:[a-z0-9/._-]+$` 的外部 ID。不能把闭合 enum 放宽成任意 `machine_max` 前缀字符串；拼错的内置 ID 必须失败。内置具体字段的坏配置不得被宽松外部分支接受；编辑器接受外部 ID 也不表示运行时可以缺少已登记类型。

`joint_driver`、`scriptable`、`battery` 三个类型的字段契约未定稿、登记被注释掉（§5），因此不提供具体 schema，也不进 enum：编辑器与运行时对它们的判断一致，都按未知类型拒绝。`basic` 的具体 schema 已接入分派，字段分派覆盖 21 项。

schema 修改按根 AGENTS.md「内容包 schema 同步」执行 syncSchemas／checkSchemas。根 AGENTS 与 subsystem 目录 AGENTS 的计数按「21 个已开放类型 + 3 个开发中未登记类型」陈述，不把抽象基类文件数当作类型数量。

配套更新上述两份 AGENTS 的子系统扩展指引、`docs/wiki/5-内容包制作教程/5.5-子系统定义.md` 的类型来源与 WIP 边界。公共接入说明沿用 `docs/部件公共基础接入.md`「扩展模组的注册和构造」的组织方式：同一套六步清单（定义子类 → 声明 Codec → 初始化期登记 → 几何校验 → 专属查询/实例工厂 → 保存恢复），并写明「内容包只能选择已登记类型，不能自带 Java 实现」。

### 7.4 下游内容资源进入加载器

S13 的 `SparkPackResourceLoader` 遍历已加载 mod，为各自 jar 的 `spark_modules` 目录执行自动打包。下游按该现有机制分发型号定义与部件内容，目录需要合法 `meta.json`，是否打包还受 `enable_auto_pack` 与相关事件控制；不另建专用内容加载器。

`SubsystemModule.read` 用 namespace 与文件名（去掉 .json）生成型号 ID，中间分类目录不参与身份。下游使用自己的命名空间避免跨模组冲突；同一命名空间中不同子目录的同名文件仍会冲突，不能把移动目录当作隔离型号名的方法。代码类型登记与型号资源加载是两条独立步骤，前者不能被内容包或 Java 类声明代替。

## 9. 验收边界

- 已开放的内置登记集合与 §5 的基线相符（21 个类型），每个类型同时带安装与静态 Codec；`joint_driver`、`scriptable`、`battery` 以同样的断言固定为未登记。断言只统计 `machine_max:` 命名空间，探针使用 `machine_max_test:`（与 `PartFoundationGameTest` 的既有做法一致），测试预期以兼容契约及独立基线为依据，不复制实现生成的结果作为断言。
- 所有已存在的有效内容使用相同 JSON ID 解码、编码并恢复；不把具体包的份数、型号名称或平衡数值写成永久断言。
- 类型身份只取登记表派生的 ID，并按 `ResourceLocation` 值相等配对；没有下游可覆写的第二份身份。分派所选 Codec 与解码对象的 `codec()` 为同一实例；等价克隆、报告另一 Codec 与未登记实例应失败，编码、保存与蓝图导出同样覆盖。

- 封表生效：首次内容包装载之后的登记抛异常；封表不阻断 reload 期的型号表清空与重读。
- 解码不依赖事件总线：JUnit 可直接解析含子系统安装项的部件定义，无需 `MachineMax.REGISTER.register(...)`（S15 的回归项）。
- 内置真实实例通过通用 createSubsystem 路径构造，生命周期、信号、能源、同步和持久化适用回归通过；不强制测试暂未启用的 WIP 功能。
- 下游可使用 `SubsystemKinds.register`、自己的命名空间、公共基类与工厂，无需编辑 MM 内置列表、无需公开 Key 与 DeferredRegister。该能力由公开类型与入口审查、编译检查覆盖；独立演示模组不列入交付。
- 编辑器覆盖 21 个已开放 ID，三个开发中类型不在 `type` 枚举里；未知 `machine_max` ID 与坏字段失败，合法外部 ID 可进入下游 schema，但运行期仍要求已登记类型。
- 专用服务端可加载公共登记类，不引入客户端类描述符或隐含客户端初始化。

## 11. 附录 A：被否决的 A 方案（NeoForge 双 Codec 注册表）

### A.1 该方案的形态

- 保留两张 NeoForge 自定义 Codec 注册表（S1），另建一个只含两个 `ResourceKey<Registry<MapCodec<…>>>` 的公开常量容器，读取 Key 不触发注册表创建。
- MM 与下游各自用 `DeferredRegister` 向同一对 Key 登记，各自挂自己的 mod event bus；内置 48 项登记改为 DeferredRegister 条目，条目 supplier 交出各属性类的 CODEC 单例。
- 类型身份由 `registry.getKey(codec())` 派生，同样不设第二份声明；解码后核对分派所选 Codec 与 `attr.codec()` 同一。
- 型号绑定同样落在 `getStaticAttr`，几何校验仍在既有的 `validate`／发布链。

### A.2 逐条对比

| 判据 | A：NeoForge 双注册表 | B：静态表（本文） | 依据 |
| --- | --- | --- | --- |
| 表的必要性 | 注册表只被 `byNameCodec` 使用，数字 ID、Holder、同步均无消费者 | 普通映射即可承载同样的解码行为 | S14 |
| 初始化耦合 | 表创建挂在 `lateinit` 总线上，任何触达属性类的路径都要求总线已装 | 表与 Codec 都不接触事件总线 | S8、S15 |
| 单元测试 | 解析含子系统字段的部件定义前必须自建总线 | 直接解析，无需模组初始化 | S15 |
| 下游接入步骤 | 公开 Key + 自己的 DeferredRegister + 条目惰性 + 实例同一性 + 静态初始化禁令 | 一行 `register(TYPE_ID, new Kind(两侧 Codec))` | S16、§4.1 |
| 两侧配对 | 两条登记写同名；需要一致性断言 | 同一条登记内两列，结构上写错不了 | §4.1 |
| 未知类型诊断 | `byNameCodec` 抛英文 literal，只能在外层补结构化消息 | 分派入口直接抛可翻译的内容异常 | S12、S17 |
| 封表 | 注册表 bake 后自动拒绝新增 | 需自行 `seal()` | §4.3 |
| 手写代码量 | 少：两行 dispatch 组合 | 多：约 50 行分派 Codec（已有 `PartKinds` 可对照） | S16 |
| 线缆 | `sync(true)` 同步一张没有消费者的映射 | 无 | S14 |
| 与既有扩展面一致性 | 部件走静态表、子系统走注册表，同一问题两个答案 | 两者同形 | S16 |

### A.3 否决理由

1. **没有消费方的抽象**：两张注册表唯一被用到的能力是名字↔值查找，普通映射等价。NeoForge 注册表提供的数字 ID 同步、Holder、数据包注册与标签在本场景都没有调用方（S14）。
2. **把生命周期带进解码路径**：表的创建依赖模组总线，导致纯解码的单测必须自建总线（S15），并让「属性类静态初始化」与「注册表创建」纠缠。B 方案没有这条链。
3. **双表配对是人为约束**：A 需要「两个登记名相同」这条契约与对应断言；B 把两侧 Codec 放进同一条登记，约束消失。
4. **诊断被迫绕过框架**：A 的未知类型消息只能来自 DFU 英文 literal，要做可翻译诊断就得在外层再包一层；B 的分派 Codec 本身就可以产出结构化消息（S17 的既有路径）。

### A.4 保留 A 的条件

出现下列任一需求时，应重新评估并可能回到 A：

1. 子系统类型需要以数字 ID 进线缆（例如按 ID 同步「本机安装了哪些子系统类型」且不依赖模组列表）。
2. 需要数据包驱动的类型注册，即内容包可携带新的类型实现而非只选已登记类型。
3. 决定把 MM 的全部 Codec 表（含世界效果与制导）统一迁到 NeoForge 注册表，以换取单一机制。

### A.5 迁移成本

两张表没有下游消费者：ARMS-Core 对 `MMDataRegistries`／`MMCodecs`／`SubsystemTypes`／`AbstractSubsystemAttr` 的引用为零。类型 ID 是名字，切换表实现不改任何内容包 JSON、存档、蓝图或载荷。因此从 A 改到 B 只影响 MM 内部代码与本计划文本。
