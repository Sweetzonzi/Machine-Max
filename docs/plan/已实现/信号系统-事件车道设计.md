## 1. 背景：值车道只有一种语义

信号系统按"每个发送者一格的最新值"工作。这条车道由四个机制共同定义，缺一个就退化：

| 机制 | 位置 | 语义 |
| --- | --- | --- |
| 投递即写槽（键 = 发送者） | [`ISignalSender#deliverSignal`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L322-L326) | 频道里存的是"这个来源现在是多少" |
| 端口只在值变化时转发 | [`SignalPort#onSignalUpdated`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/SignalPort.java#L65-L121) | 相同值重复发送不产生投递 |
| 值进入部件/装配体的存储表 | [`AbstractPart#onSignalUpdated`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/part/AbstractPart.java#L1401-L1409)、[`SubsystemController#onSignalUpdated`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/SubsystemController.java#L388-L397) | Molang 的 `local.get` / `global.get` 读它 |
| 清空靠写"无值标记" | [`ISignalSender#resetSignalOutputs`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L194-L203) | `EmptySignal` 表示"来源已连接、当前无值" |

"发生了一次"在这条车道上没有位置。两处一次性通知因此各有自己的处理：

| 场景 | 处理方式 | 本设计的选择 |
| --- | --- | --- |
| 交互区的 `global` 频道 | 零件扇出走方法通道：装配体逐零件调 `triggerInteractionEvent`（[`VehicleCore#broadcastInteractionEvent`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/VehicleCore.java#L1801-L1806)），不经线网 | 事件从 `emitSignal` 进装配体总线，扇出仍由 `IPartAssembly#broadcastInteractionEvent` 承担，成为总线实现的一部分（§4.3、§6） |
| 弹种切换 `ammo_switch` | 在值车道里模拟边沿：接收者消费后把该来源的槽值写成 `EmptySignal`（[`consumeAmmoSwitch`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/WeaponControllerSubsystem.java#L1150-L1171)），用"槽里没有可识别的指令"表达已消费 | 保留：它是乘员输入线上的一条指令值，释放语义由值车道承担（§7） |

结论：系统缺一个"不写槽的投递"原语。补上之后，一次性通知有统一出口，值车道的去重、释放与排序语义保持原样。

## 2. 目标与非目标

**目标**

1. 一次性通知走一条与值车道并行的车道，共用同一张线网（首跳表、端口转译、总线分发、接受条件）。
2. 事件不写槽、不进 `signalStorage`、不参与 Molang、不参与排序、不持久化、不去重。
3. 任何 `ISignalReceiver` 都能接收事件；任何 `ISignalSender` 都能发出事件。接收者不必是总线。
4. 交互区只负责"发出"：每条频道按投递点解析结果决定是否 emit，没有"动画事件专用"的分支。
5. 跨零件的事件投递沿实际接线走：拆件即断线，与值车道同一条约束。
6. 发现能力回答"这条事件频道有没有人去接"，让交互区的激活判据与服务端复核一致。

**非目标**

- 不引入队列、重放、延迟投递、优先级或持久化。错过就是错过，这是事件的语义。
- 不引入 `CONSUME`。事件是广播式投递，多个接收者都要收到；"只能被一个逻辑处理"属于仲裁，归值车道的优先级与三键排序。
- 不引入子系统的事件频道白名单字段。端口转发与总线分发沿用既有的 `getAcceptedChannels()`，声明一次即可。
- 不改动值车道的任何行为：去重、`EmptySignal`、`resetSignalOutputs`、优先级、Molang 存储保持原样。
- 不做服务端→客户端的事件镜像。事件车道只在单端内投递（§10.5）；需要另一端看到的事件由消费方自己同步——走既有载荷、子系统同步值或各自的动画包。

## 3. 车道模型

| | 值车道 | 事件车道 |
| --- | --- | --- |
| 写入 | 槽 + 存储表 | 什么都不写 |
| 去重 | 值不变不转发 | 每次都投递 |
| 读取方 | 子系统读槽、Molang 读存储 | 接收者的回调 |
| 时机 | "当前是多少" | "刚刚发生了一次" |
| 消费 | `CONSUME` / 释放标记 | 无消费、无释放 |
| 典型频道 | `engine_speed`、`crew_driver_move`、`gear` | `interact_hood`、将来的一次性动作指令 |

线网上的节点分三种角色：

| 角色 | 类型 | 事件车道里的职责 |
| --- | --- | --- |
| 传输 | `SignalPort` | 按对侧 `signal_translations` / `signal_targets` 转发，无条件、不看值变没变；自身不是投递点 |
| 传输 + 接收者 | `ISignalBus`（`AbstractPart`、`SubsystemController`） | 自己收，再按接受条件分发给订阅者 |
| 接收者 | 叶子（`AbstractSubsystem`，以及将来任何实现） | 收到就收；默认空实现 |

投递规则一句话：**沿线路走，凡是接收者都收；传输节点额外转发。**

## 4. 接口与投递规则

### 4.1 `ISignalReceiver#onSignalEvent`

```java
/**
 * 事件到达。与 {@link #onSignalUpdated} 并列：一个说"值变了"，一个说"发生了一次"。
 * 不写槽、不返回结果（事件没有消费语义）。
 * <p>调用线程是发送方的线程；本方法不做线程切换，需要主线程的实现由调用方保证（§4.6）。
 */
default void onSignalEvent(String channelName, ISignalSender sender, Object payload) {}
```

挂在 `ISignalReceiver` 上而不是新接口：它和 `onSignalUpdated` 是同一批接收者的两种输入，默认空实现让"不关心事件"的实现零成本。

### 4.2 `ISignalSender#emitSignal`

三个重载，与 `sendSignalToTarget` / `sendSignalToAllTargets` 并列：

```java
default void emitSignal(String channel, Object payload)                         // 该频道的全部首跳
default void emitSignal(String channel, String targetName, Object payload)      // 该频道的某个首跳
default void emitSignal(String channel, ISignalReceiver target, Object payload) // 已解析的接收者实例
```

重访判定与按角色分派放在 `signal` 包内的包私有类 `EventDispatch`（§4.6）。接口私有方法在子接口与实现类里都不可见，而 `ISignalBus#broadcastEvent` 与 `SignalPort#onSignalEvent` 都需要这条分派，所以它不能放在 `ISignalSender` 内部：

```java
// signal 包内，包私有；实现见 EventDispatch.java
final class EventDispatch {
    static void dispatch(ISignalReceiver target, String channel,
                         ISignalSender sender, Object payload) {
        if (!current().visit(target, channel)) return;      // 同一 (接收者, 频道) 只投一次
        if (target instanceof ISignalBus bus) bus.broadcastEvent(channel, sender, payload);
        else                                  target.onSignalEvent(channel, sender, payload);
    }
}
```

端口不需要单独一条分支：`SignalPort#onSignalEvent` 是它自己的覆写，虚拟调用即可到达（§4.4）。

### 4.3 `ISignalBus#broadcastEvent`

```java
default void broadcastEvent(String channel, ISignalSender sender, Object payload) {
    EventDispatch session = EventDispatch.current();
    session.begin();                                  // 自身是顶层入口：没有外层 emit 也从空会话开始
    try {
        onSignalEvent(channel, sender, payload);      // 总线自身已由 EventDispatch.dispatch 判重
        for (ISignalReceiver sub : getAllSubscribers()) {
            if (sub.acceptAllBroadcastInput() || sub.getAcceptedChannels().contains(channel)) {
                EventDispatch.dispatch(sub, channel, sender, payload);
            }
        }
    } finally {
        session.end();
    }
}
```

`begin`/`end` 把它包成一次独立投递：直接调用 `broadcastEvent`（不经过 `emitSignal`）时，会话仍从空表开始、结束时清空，不会复用上一次调用留下的 visited。从 `emitSignal` 进入时深度已经不为零，这次 begin/end 只是加深再退回深度，不清表，嵌套因此共享同一份 visited。

两个覆写：

- `AbstractPart#onSignalEvent` → `triggerInteractionEvent(channelName)`：到达频道就是动画状态机的事件名，本件控制器按 `event.<频道>` 转移。
- `SubsystemController#onSignalEvent` → `assembly.broadcastInteractionEvent(channelName)`：把事件交给装配体广播给全部零件。控制器持一个可空的 `IPartAssembly` 引用（[构造器](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/SubsystemController.java#L63-L71)），独立构造的控制器（无装配体）保持只向订阅者分发。

`IPartAssembly#broadcastInteractionEvent` 是装配体对 `global` 的实现：事件从总线进来，由控制器转给宿主，宿主再逐零件扇出；接口本身保留，其他宿主可以有自己的实现。

这条零件扇出由装配体自己完成：它逐个零件调 `triggerInteractionEvent`，不经线网，也不计入会话的重访判定。因此 `global` 的发现结果只包含控制器与它的订阅者，零件不在其中——§5 的契约据此限定为"线网上的投递点"。同一条频道同时指向 `local` 与 `global` 时，同一零件会收到两次事件（一次经线网、一次经装配体广播），这种写法由 `checkContent` 在内容层禁止（§8 的 `checkContent` 行）。

### 4.4 `SignalPort#onSignalEvent`

按对侧端口的 `signal_translations` 得到到达频道，再查对侧 `signal_targets`；对每个接收者先按值车道的同一判据 `acceptAllRoutingInput() || getAcceptedChannels().contains(到达频道)` 过滤，再经 `EventDispatch.dispatch` 继续（含对侧总线）。与值车道一致：**不做值比较**，`signal_targets` 里没有该频道时静默丢弃。过滤这一步不能省——省掉就会把事件送到没有声明该频道的叶子，发现结果与投递结果随即变成两套答案（内容检查见 §8）。

端口因此与值车道共用同一套表，只是第二个入口：值车道的入口在 `onSignalUpdated` 里比较槽值后传播，事件车道的入口不读槽、直接转发。两条车道在端口上并存，同一条频道可以既有值又有事件。

### 4.5 与值车道的关系

- 事件不写 `getSignalInputChannels()`、不写 `getSignalStorage()`，因此不影响 `local.get` / `global.get`。
- 事件不参与 `resetSignalOutputs`：清空值是清空槽，事件没有槽可清。
- 端口对事件的转发规则与对值的转发规则并存：同一条频道可以既有值又有事件，两个方向互不干扰（`SignalPort` 的两张表复用）。
- `Signal` 子类与 `EmptySignal` 都不需要参与事件车道；负载用 `Object`，纯触发传 `null`。

### 4.6 环路与线程

值车道靠"值不变就不转发"天然终止。事件车道用**重访检测**终止：一次顶层 emit 打开一个投递会话，会话记录已投递过的 `(接收者, 到达频道)` 对，重复到达时跳过投递。

会话挂在 `ThreadLocal` 上，按线程常驻、每次顶层 emit 清空：`begin()` 把线程内深度加一，深度由 0 变 1 时清表；`end()` 在 `finally` 里减一，归零时再清一次；容器本身留在线程上复用，因此每次 emit 只做清表、不新建映射。嵌套 emit（接收者在回调里发出另一条频道）深度大于 1，共用同一份 visited：另一条频道照常投递，把同一频道发回上游则被抑制。`current()` 在会话不存在时按需创建，`broadcastEvent` 这类入口即使没有外层 emit 也不会拿到 null。回调抛异常时 `finally` 仍会减深度，下一次顶层 emit 从空表开始，脏数据不跨 emit 存活。

`visited` 的上界是一次 emit 触及的 `接收者 × 到达频道`。到达频道来自翻译表（有限静态映射）与调用方传入的字符串，一条频道能派生出的频道名因此有限，任何环路都会在有限步内重复同一个 `(接收者, 频道)` 对，所以不需要额外的深度上限。被抑制的重访默认静默，只在 `debug` 级留一条。

线程：车道不做线程检查，回调在调用方线程上同步执行。两条限制来自使用方式而不是检查：

- **按名 emit 限主线程**：首跳表由主线程用 `clear()` + `putAll()` 整体替换，物理线程按名读取会读到空表或半张表——与值车道"物理步不按名发送"是同一条纪律。
- **物理步只按实例发给不触碰状态机的接收者**（例如驱动器）。发往 Part 或装配体总线会推进动画状态机，与主线程的 `AnimController#tick` 竞态。

真出现竞态时，在 `AbstractPart#onSignalEvent` 加一次主线程断言，比在车道上逐次判断更窄。

```java
// signal 包内，包私有；键语义与 resolveSignalLine 的 visited 相同
final class EventDispatch {
    private static final ThreadLocal<EventDispatch> CURRENT = new ThreadLocal<>();
    private final Map<ISignalReceiver, Set<String>> visited = new IdentityHashMap<>();
    private int depth;

    static EventDispatch current() { /* 取不到时创建并挂到 CURRENT */ }

    /** 首次到达返回 true；同一 (接收者, 频道) 的第二次到达返回 false。 */
    boolean visit(ISignalReceiver receiver, String channel) {
        return visited.computeIfAbsent(receiver, k -> new HashSet<>(2)).add(channel);
    }
    // begin(): depth++，由 0 变 1 时 visited.clear()
    // end():   depth--，归零时 visited.clear()；调用点包在 try/finally 里
}
```

## 5. 发现：`resolveTargets` 的布尔轴

两条车道共用一套遍历（[`resolveSignalLine`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/ISignalSender.java#L121-L152)），差别只有一处：**总线本身算不算终端**。

| 入口 | 语义 |
| --- | --- |
| `resolveTargets(channel)` | 叶子终端，现有语义 |
| `resolveTargets(channel, boolean includeBuses)` | `false` 等价于上一行；`true` 为投递点 |
| `resolveTargets(channel, List<String> firstHopNames)` | 叶子终端 + 首跳白名单，现有语义 |
| `resolveTargets(channel, List<String> firstHopNames, boolean includeBuses)` | 白名单过滤后取投递点 |

- **默认行为是仅叶节点**：现有调用点（驾驶、火控、视点、弹药发现、GameTest）与既有签名都按"终端 = 执行者"使用，`includeBuses` 缺省为 `false`，它们不受影响。
- 四个入口都委托给同一个私有遍历，没有第二份遍历逻辑。白名单轴与布尔轴正交；第四档（白名单 + 投递点）目前没有内容侧调用方，它只是一段三行委托。
- 重载解析没有歧义：`boolean` 是原始类型，`null` 第二参只匹配 `List` 重载。
- 布尔在调用点不可读，调用方用一个具名局部量或一行注释解决；不为可读性再包一层方法。

写进 Javadoc 的契约：

> `includeBuses = false`：只返回叶子接收者（执行者 / 发现目标），总线只作为分发点被穿过。
> `includeBuses = true`：线网上的投递点，即叶子 + 途经的总线实例本身；端口永远不出现在结果里。两者的差集恰好是总线实例。装配体经 `broadcastInteractionEvent` 做的那次零件扇出不在线网上，也不在发现结果里（§4.3）。

### 总线一律接受路由输入

`SubsystemController` 覆写 `acceptAllRoutingInput()` 返回 `true`，与 `AbstractPart` 一致。端口转发要求 `acceptAllRoutingInput() || getAcceptedChannels().contains(channel)`（[`SignalPort`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/signal/SignalPort.java#L86-L89)）。总线本身没有排他性的接受列表，它的职责是把频道交给订阅者、由订阅者各自的声明决定收不收，因此**总线一律接受路由输入，频道筛选交给订阅者**。

由此，事件车道的 `global` 目标在跨零件时可达；只读发现里经端口到达 `global` 的频道也展开成整车订阅者（缺这一条时该频道在发现侧表现为不可达）。现有内容里没有任何连接点把频道指向 `global`，这条能力随本设计一起可用；`AbstractSubsystem#resolveViewpoints`、`AbstractControllableSubsystem` 的控制器发现，以及 `LauncherSubsystem` / `AmmoLoaderSubsystem` / `LoaderRoster` 的弹药发现随之回归。

## 6. 交互区改造

### 6.1 为什么盖板的事件必须跨零件

`JointDriverSubsystem` 在驱动器自己所属的零件上采样本零件的动画姿态：`getLocatorBoneChain` 读本零件模型，`hasAnimationContribution` 要求本零件有覆盖该骨骼链的正在播放的动画，否则 `releaseDrive()`（[L60-L71](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/JointDriverSubsystem.java#L60-L71)、[L116-L140](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/subsystem/JointDriverSubsystem.java#L116-L140)）。

桑塔纳的四个车门与两个盖板都是独立零件：交互区在门/板零件上，`signal_targets` 只写一个 `interact` 频道、目标写门轴与锁扣两个连接点；铰链骨骼（`LeftFrontDoorHinge`、`HoodHinge`、`TrunkHinge`）与六台 `joint_driver` 都在车体（[hull](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_hull.json#L240-L288)、[door](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_door.json#L36-L46)、[hood](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_hood.json#L50-L60)、[trunk](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_trunk_door.json#L50-L60)）。交互区不知道、也不需要知道自己会让车体切哪一段动画：含义由对侧连接点的两张表解释——门轴连接点把 `interact` 转译成与控制器事件名逐字相同的到达频道、目标写 `local`，事件因此交给车体的动画状态机；锁扣连接点不转译，到达频道就是 `interact`，目标写 `*_coupler` 子系统，由 `onInteract` 解扣。所以点击门/板产生的事件必须到达**车体**——`local` 只到交互区所属的那一件，交互动作用不上。

门/板零件没有显式声明 `animations` / `controllers`，两者缺省与模型同名，因此它们也绑定了同一套动画与控制器；但那些铰链骨骼属于车体的切片，视觉与物理都由车体的状态机经驱动器决定。接线只把事件送到车体，门/板零件自己的状态机不参与，`global` 的整车扇出因此不是这条链路的一部分。

一次性事件因此需要"沿接线到达另一个零件"的能力，而不是"广播给全车"或"只能发给自己"：对侧连接点把到达频道转译成控制器里的 `event.<名>`、目标写 `local`，事件就交给对侧零件自己的状态机；状态机在别的零件上时目标写 `global`（装配体广播给全部零件）。事件名与控制器转移的对应关系是内容契约：`checkContent` 核对落到总线上的到达频道能在某份动画控制器里找到同名 `event.<名>`，没对上时这条线静默无效。

### 6.2 一次投递点遍历，分成两档

`InteractBox#setTargetFromNames` 重建首跳表后，对每条频道做一次 `resolveTargets(channel, true)`：

- 结果里有总线实例 → 这条频道是事件线（点击时 `emitSignal(频道, null)`，并按 §6.3 计入激活判据）；
- 结果是子系统 → 计入交互目标表（`isInteractable()` 决定能否点，`onInteract` 按声明序尝试，`CONSUME` 结束遍历）。

只对"到达总线"的频道发事件：子系统目标走 `onInteract`，不给纯值线附加无意义的投递。一条频道两档都命中时两档都生效——事件先投，`CONSUME` 不吃掉它。

交互区的表现状态只有首跳表与解析结果：`local` 与 `global` 都是首跳表里的条目，构造期不做分桶。

### 6.3 激活判据

`canInteract()`：门控成立，且

- 至少一条频道到达总线（事件线），或
- 至少一个终端子系统此刻 `isInteractable()`。

判据读解析结果而不是配置字面量：`local` / `global` 只是首跳表里的名字，跨零件的事件线只要接上了就算数，没接上就不亮提示。

只作为子系统事件监听者的线不会点亮提示——交互区的点击语义对子系统一直是 `onInteract`。若将来真需要"只靠子系统事件点亮提示"，给交互区加一个显式的 `event_channels` 字段，不为一个尚未出现的需求先造。

### 6.4 内容写法

交互区统一只发一个 `interact` 频道，目标写该件自己的两个连接点；含义由车体侧的两张表给出（[hull](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_hull.json#L240-L288)、[door](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_door.json#L36-L46)、[hood](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_hood.json#L50-L60)、[trunk](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/santana/santana_trunk_door.json#L50-L60)）：

| 部位 | 交互区所在零件 | 频道目标 |
| --- | --- | --- |
| 四扇车门（四个变体各一个交互区） | 车门零件 | `"interact": ["connector.machine_max.axis", "connector.machine_max.lock"]` |
| 引擎盖、后备箱盖 | 盖板零件 | `"interact": ["connector.machine_max.axis", "connector.machine_max.lock"]` |

```jsonc
// 门/盖零件：频道里不含位置信息，同一份变体可以插到不同位置
"interact_boxes": { "interact.machine_max.door": {
  "signal_targets": { "interact": ["connector.machine_max.axis", "connector.machine_max.lock"] } } }

// 车体门轴：把 interact 转译成控制器事件名，交给车体自己的状态机
"connector.machine_max.left_front_door_axis": {
  "signal_translations": { "interact": "interact_left_front_door" },
  "signal_targets": { "interact_left_front_door": ["local"] } }

// 车体锁扣：到达频道就是 interact，不需要转译
"connector.machine_max.left_front_door_lock": {
  "signal_targets": { "interact": ["subsystem.machine_max.left_front_door_coupler"] } }
```

两条线各走各的：门轴侧转译后的到达频道等于控制器事件名、目标 `["local"]`，事件因此交给车体状态机；锁扣侧到达频道就是 `interact`、目标 `["subsystem.…coupler"]`，解扣由车体锁扣子系统的 `onInteract` 执行。点击时事件线整条频道按名投递一次，两个分支互不影响。解扣断开的是锁扣边，门轴边保留，所以关门那一次点击仍能切动画；锁扣已经不在线上，因此不在点击目标表里——同一套解析在下次结构变化时自然得出这个结果。

事件名只出现在车体侧（连接点表与动画控制器），门/盖零件因此不必知道自己在车上会触发哪个控制器，一份变体可以服务多个位置、多台车。`signal_translations` 与 `signal_targets` 是连接点条目的顶层字段（[`ConnectorAttr`](../../../src/main/java/io/github/sweetzonzi/machine_max/common/mech/vehicle/attr/connector/ConnectorAttr.java#L94-L115)），每个连接点各写一份，不需要变体副本，也不需要 `overwrite`。

### 6.5 两种接线形状：直连与透传

按拓扑选形状，两条形状都能用同一套检具核对：

| 形状 | 判据 | 发送侧 | 接收侧 |
| --- | --- | --- | --- |
| 直连 | 交互区有自己的连接点对（门/盖各自的轴与锁扣） | `interact` | 门轴转译成事件名（交本件状态机时落 `local`，状态机在别的零件时落 `global`）；锁扣/座位直接收 `interact` |
| 透传 | 多个交互区共用一对连接点，对侧要按名分发 | 各自的具名频道 | 中间件 `signal_targets` 按名路由，叶子再转译成 `interact` |

透传形状的实例是 AE86：车壳与车架只有一对连接点，四个上座区共用它（[ae86_hull.json#L36-L64](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/ae86/ae86_hull.json#L36-L64)），车架按频道名把它们分发到三个座位连接点（[ae86_chassis.json#L133-L143](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/ae86/ae86_chassis.json#L133-L143)），座位零件再把名字转译成 `interact`（[ae86_seat.json#L44-L59](../../../src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/ae86/ae86_seat.json#L44-L59)）。一个连接点的信号表是「到达频道 → 目标」的一张映射：发送侧若统一成 `interact`，四条线在这一颗连接点上就会合流、分不出是谁点的，所以透传形状必须保留发送侧的名字。`checkContent` 因此核对两件事：同一变体内多个交互区送往同一个连接点的频道不得重名；落到总线上的到达频道必须能对上某份动画控制器的 `event.<名>`。

## 7. `EmptySignal` 的定位

`EmptySignal` 属于值车道：**"这个来源已连接、当前无值"**。座椅无人时发给车控的空信号让该来源的槽从"按住"回到"已释放"，单例与按类型相等的判断在这里是对的——释放之后不该反复转发。

事件车道不产生也不消费它：没有事件就不 emit，负载要空就传 `null`。因此两条车道各有一个"空"，互不重叠：

| | 值车道 | 事件车道 |
| --- | --- | --- |
| 空 | `EmptySignal`：有连接、无值 | 不存在这个概念，没发生就没有投递 |
| 重复 | 相同值不转发 | 每次 emit 都投递 |

`signal/AGENTS.md` 的「无值标记」一条按这个口径写：`EmptySignal` 表示"该来源仍在、当前没有值"，座椅无人、按键松开、执行器被释放都写它；事件车道不产生也不消费它——没有事件就不 emit，负载要空就传 `null`。

## 10. 风险与待定

1. **线程**：车道不做线程检查，回调在调用方线程上同步执行（见 §4.6）。按名 emit 限主线程（首跳表由主线程整体替换）；物理步只按实例发给不触碰状态机的接收者。出现竞态时把断言加在 `AbstractPart#onSignalEvent`。
2. **环路与会话**：由重访检测终止，键是 `(接收者, 到达频道)`，与只读发现的 visited 同构；会话按线程常驻、深度计数、`finally` 清表，菱形接线因此只投递一次。抑制静默、`debug` 级留痕。
3. **总线的接受语义**：`SubsystemController#acceptAllRoutingInput` 为 `true`，经端口到达该控制器的任意频道都会写入 `global` 存储并向订阅者分发（订阅者仍按自己的频道表筛选）；只读发现也会把"经端口到 `global`"展开成整车订阅者。回归面见 §5。
4. **交互区的子系统事件**：本期点击对子系统只有 `onInteract`。需要子系统从点击里拿到一次性事件时，再加 `event_channels` 字段。
5. **单端边界**：事件车道只在同一进程内投递——`emitSignal` 不产生网络包，也不读另一端的任何状态。两端各自跑自己的生产者：

   - **交互**：客户端点击只发包（`LivingEntityEyesightAttachment#clientInteract` 不本地执行），服务端 `handle` 之后把同一个包（带上触发者 id）转发给维度内所有客户端，各客户端在主线程重放 `InteractBox#interact`；服务端即使因判定过期提前返回，包仍会被转发（既有行为）。
   - **载具物理与关节**：两端各自步进，各自产出。

   两端因此可能分叉，**这由消费方负责**：需要两端一致的量，消费方自己同步（既有载荷、子系统同步值，或 `SubPartHitEffectPayload` 那类专用包）。框架不提供镜像，也不替消费方决定哪一端权威。不做镜像的理由是它要一套负载码表与落点寻址，还要与输入重放划定互斥边界；而消费方最清楚自己要同步的是哪几个量，不是哪些事件。
6. **事件频率**：事件车道面向离散时刻（点击、装填阶段切换、开关到位）。逐 tick 的量仍走值车道，避免每个订阅者每 tick 一次回调。
7. **既有签名**：`resolveTargets` 默认只返回叶子，现有调用点与签名都不变；`includeBuses = true` 是新入口。
