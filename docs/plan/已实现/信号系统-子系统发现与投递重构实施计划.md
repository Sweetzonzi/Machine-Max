# 信号系统子系统发现与投递重构实施计划

**状态**　已实现；服务端与 GameTest 验收通过，客户端实机验收待完成。§1 与 §5 的「改造前」指本次重构的基线。

本文以 Machine-Max 为实施仓库。「内置」指本仓库 Java 实现的子系统与控制器。源码坐标以仓库根为准，`<mech>` 代表 `src/main/java/io/github/sweetzonzi/machine_max/common/mech`。终端查询由 `ISignalSender` 提供默认实现，供子系统构建绑定。发送沿用现有方法名，增加接收者实例重载。

## 1. 现状与目标

握手的发起者需要知道配置线路能到达哪些子系统。改造前的实现通过 `sendSignalToAllTargetsWithCallback` 发送空信号或控制组名，接收者在同一调用栈内向发起者的 `callback` 频道写回数据，发起者再从 `onSignalUpdated` 提取结果。普通信号的输入槽也会被这次发现写入。单目标发送已经有同步返回值 `SignalResult`，它表达本次更新的处理结果。

| 改造前入口 | 要保住的业务契约 |
| --- | --- |
| `<mech>/signal/ISignalSender.java#sendSignalToTarget`、`#sendCallbackToListener`、`<mech>/signal/ISignalReceiver.java#respondCallbackToSender` | 同一频道按发送者实例分槽。按名发送可以写入 Part 或总线提供的 MoLang 存储。车控借用 `sendCallbackToListener` 给已知实例下发实时命令。 |
| `<mech>/signal/SignalPort.java#onSignalUpdated`、`#respondCallbackToSender`、`<mech>/subsystem/SubsystemController.java#respondCallbackToSender` | 端口按对侧配置转译频道，总线按订阅展开。改造前的回调穿透跳过端口接收筛选，并向下一跳传源频道。多跳与转译场景需要以实际接线测试固定语义。 |
| `<mech>/vehicle/interact/InteractBox.java#interact`、`<mech>/subsystem/AbstractSubsystem.java#onSignalUpdated` | 交互区按配置目标顺序尝试。收到 `CONSUME` 时结束，`PASS` 和 `FAIL` 继续。接收者可在当前调用栈内处理 `InteractSignal`。 |
| `<mech>/subsystem/AbstractControllableSubsystem.java#discoverWeaponControllersForGroup`、`#setUpTargets`、`<mech>/control/ControlGroupSet.java#getAllMainWeaponTargets`、`#getMergedMainWeaponTargets` | 同类输出跨组聚合目标，跨输出类别的 `putAll` 可能覆盖同名条目。活动组的合并接口返回同名覆盖后的列表，整频道发送实际只取频道名。§4.1 统一同名线路的规则。 |
| `<mech>/subsystem/AbstractGroundControllerSubsystem.java#handShake`、`<mech>/subsystem/WeaponControllerSubsystem.java#handShake`、`<mech>/subsystem/AmmoLoaderSubsystem.java#handShake`、`<mech>/subsystem/RegenLoaderSubsystem.java#handShake` | 车控与火控发现执行器，装弹机发现消费者并反向登记。绑定属于当前装配体，结构变更会使旧绑定失效。 |
| `<mech>/subsystem/SubsystemController.java#initAllSubsystems`、`#onVehicleStructureChanged` | 初装先订阅再 attach。结构变更先让全部子系统预清理，再进入发现。发射器清理供给者与装弹机登记依赖此顺序。 |

完成后的调用流程是「读配置接线 → 同步拿到终端 → 调用方建立绑定」。油门、按键、交互、反馈都通过运行时发送入口投递。现有内容包的接线字段、存档中的装配信息和网络载荷是本次兼容契约。P0 核对本仓库的发送者、接收者、代理覆写与使用旧方法的调用方。

## 2. 首跳、终端与发送入口

`getTargets().getOrDefault(channel, Map.of()).values()` 给出该发送者在这个频道上配置的**第一跳实例**，供按名发送和端口转发寻址。`resolveTargets(outputChannel)` 给出从该输出频道可达的**全部终端**，供镜头、车控、火控和装弹机构建绑定。直连时首跳就是终端。遇到 `global` 总线或 `SignalPort` 时继续展开，走到普通接收者即结束该分支。

在 `<mech>/signal/ISignalSender.java` 提供落地方法 `default Map<String, List<ISignalReceiver>> resolveTargets(String outputChannel)`。它从 `this.getTargets()` 取首跳，按 §3.1 展开总线和配对端口。同步返回按**到达频道**分组的结果。端口可能改频道名，所以绑定时使用结果的键。用 `Collections.unmodifiableMap(new LinkedHashMap<>(...))` 和 `List.copyOf` 冻结容器与顺序，终端元素是已有对象引用。子系统用 `instanceof` 挑自己的业务目标。装配、接线变更或控制组编辑时在两端各自的主线程解析。

| 随包样例 | 第一跳和业务终点 |
| --- | --- |
| T-90A 车体的履带控制器 | `car_control` 直接列出发动机、变速箱和左右履带。查一层目标表就能绑定。见 `src/main/resources/spark_modules/Machine-Max_T90A/t90a/parts/t90a_hull.json` 中 `subsystem.t90a.track_controller`。 |
| T-90A 炮手席的镜头发现 | `gunner_sight` 指向 `global`。第一跳是装配体的 `SubsystemController`，实际镜头声明订阅 `gunner_sight`。见 `src/main/resources/spark_modules/Machine-Max_T90A/t90a/parts/t90a_turret.json` 中 `subsystem.t90a.gunner_seat`，以及同包 `t90a/subsystems/t90a_gunner_sight.json` 的 `discovery_inputs`。 |
| 大运车体的车控 | `car_control` 指向 `connector.machine_max.chassis_axis`。对接的底盘端口将该频道指向发动机、变速箱和车轮。见 `src/main/resources/spark_modules/Machine-Max_Civilian/machine_max/parts/dayun/dayun_hull.json` 中 `subsystem.machine_max.car_controller`，以及同目录 `dayun_chassis.json` 中 `connector.machine_max.hull_axis` 的 `signal_targets`。 |

同一发送者内，同名输出频道表示同一条共享线路，按 §4.1 的顺序合并目标并去重。控制组选择启用哪些频道，按组发现火控时只需对该组的频道调用 `resolveTargets(outputChannel)`。例如同一座位的可切换子组 A 声明 `aim → 火控 A`，子组 B 声明 `aim → 火控 B`，任一组启用 `aim` 都能发现两台火控。独立操控两台火控应声明两个频道。不同发送者各有自己的目标表。`<mech>/signal/ISignalBus.java#getTargets` 返回空表，`global` 作为线路中的目标时通过订阅扇出。

单目标继续用 `sendSignalToTarget(channel, targetName, value)`。它写入接收方输入槽，返回 `SignalResult`。油门或 GUI 操作可以忽略结果，交互区根据结果决定是否试下一个目标。`PASS` 表示接收者没有即时接管，值可能已进入输入槽。批量发送继续逐个投递并返回 `void`。

车控已持有发动机、电机、车轮和履带的引用，使用同名重载 `SignalResult sendSignalToTarget(String channel, ISignalReceiver target, Object value)`。调用处传终端的输入频道和对象引用。按名发送先查首跳，再共用写槽和通知步骤。发送者由 `this` 提供，端口与总线保留原始发送者。主线程普通发送在两个重载中共用存储写入与同步处理结果。物理线程使用实例重载的范围见 §4.2。结构变化后，发送者必须先重新解析并保存接收者引用，再继续发送；旧引用在同一轮结构变化后失效。火控的目标角、开火请求与执行器自身状态之间的边界见 §4.3。

### 2.1 回调各自承担的工作

| 改造前机制 | 迁移后的归属 |
| --- | --- |
| `respondCallbackToSender` 向发起者的 `callback` 频道回送频道名或原值 | 内置握手通过 `resolveTargets` 取得终端。即时处理结果走 `SignalResult`。 |
| `sendCallbackToListener` 向已绑定实例写命令 | 走 `sendSignalToTarget` 的实例重载。 |
| `callbackTargets` 提供批量发送和重置目标 | 内置控制器按自身绑定表下发。结构变动时装配体清空信号槽并重建绑定。P5 清理使用这些表的代理方法。 |
| `onSignalUpdated` 处理接收方输入更新 | 发送链继续调用。它是接收端处理入口，返回本次处理结果。 |
| 转速、车速和履带受力等运行时反馈 | 按普通配置频道发送。履带速度与受力在 `<mech>/subsystem/TrackDriveSubsystem.java#onPostPhysicsTick` 采样、由本端主线程 `onTick` 投递，§4.2 定义这两个相位。 |

## 3. 查询如何走接线

### 3.1 走线规则

1. **取得首跳。** 按输出频道读发送者的 `getTargets()`。首跳表由 `<mech>/signal/ISignalSender.java#setTargetFromNames` 从配置构建，寻址范围是发送者所在 SubPart，`local` 指 Part 自身。显式直连按配置定位到对象，接收频道筛选只适用于下述端口与总线转发。空频道、空列表或未接通的端口可返回空结果。
2. **跨连接器。** 从 `<mech>/signal/SignalPort.java#owner` 取连接器，读 `<mech>/vehicle/connector/AbstractConnector.java#attachedConnector` 指向的对侧端口。用对侧端口转译频道，再从其目标表取接收者。按端口的接收规则检查 `acceptAllRoutingInput()` 与 `getAcceptedChannels()`。下一次递进使用转译后的频道，例如 `aim → mount_aim → traverse` 的终端结果是 `traverse`。
3. **展开 `global`。** 用 `<mech>/signal/ISignalBus.java#getAllSubscribers` 取订阅者，按 `acceptAllBroadcastInput()` 或已声明频道筛选。显式列表保序。内置广播候选按部件 UUID、SubPart 名、接收者寻址名排序，避免由订阅集合的迭代顺序决定业务选择。
4. **结束。** 访问集与终端去重均以「对象引用身份、频道」为键，可用 `IdentityHashMap<ISignalReceiver, Set<String>>` 记访问状态。同一对象可以在不同频道出现。各频道按首次出现顺序处理，频道内保留终端到达顺序。断开的端口只终止自身分支。

合并与分裂后的目标表重建涵盖子系统、交互区和端口，顺序见 §4.1。业务绑定校验双方属于同一有效装配体。对象类型、损坏、激活、电力、库存等资格由消费方判定。查询只读配置与连接状态，禁止调用发送、输入槽创建、MoLang 写入和处理回调。

### 3.2 频道与优先级

- 查询按一条输出线路返回各终端实际到达的频道。已绑定发送、炮塔目标和发射器开火的频道键都取该终端频道。
- 某执行器经不同线路可达多个输入时，查询保留每个可达输入。控制器若只对同一实例发一份命令，普通控制按 `<mech>/signal/ISignalReceiver.java#getAcceptedChannels` 的顺序选，目标角和开火请求按实际读者的声明顺序选，见 `<mech>/subsystem/TurretDriverSubsystem.java#getTargetAngle` 和 `<mech>/subsystem/LauncherSubsystem.java#getActiveFireCommand`。没有声明优先级时，按确定的遍历顺序选取。跨输出频道汇总时，频道字典序只用作平局规则。
- 改造前的握手回传源频道，端口运行时投递使用到达频道。P0 须逐项核对第一方转译接线以及发射器的 `ammo_inputs`、`control_inputs`。遇到结果变化时，用真实输入声明决定预期并留夹具。保留频道配置格式，别名语义只由端口转译表决定。
- 发现器展开的是终端集合。普通发送、交互顺序、端口对相同值的传播条件、总线存储和结果汇总沿用运行时入口。共用的规则限于首跳解析、转译和接收资格，按具体使用点提取。

## 4. 结构变动与运行边界

### 4.1 结构变化与控制组编辑

**各子系统自行解析并拥有业务绑定。** 座位管理镜头和分组候选，车控和火控管理执行器，装弹机负责发现消费者，发射器拥有供给者登记。以 `<mech>/subsystem/SubsystemController.java#initAllSubsystems`、`#addSubsystems` 和 `#onVehicleStructureChanged` 为生命周期入口，`SubsystemController` 负责生命周期顺序与订阅表。两端各在自己的主线程完成发现，客户端的 HUD 和镜头直接读本地结果。

1. `VehicleCore` 完成加件、拆件、连接、合并或分裂，按新归属和配对连接器建表。清理与重建范围包括合并的双方、分裂的原装配体和所有分支，以及本次退出的部件。首次构造和存档恢复从空的运行状态建立。
2. 主线程重建全部首跳表和订阅，先向所有子系统调用 `onVehicleStructurePreChanged`（清空信号槽与拓扑缓存），再统一调用 `onVehicleStructureChanged`（按新拓扑调用 `resolveTargets` 并建立绑定）。绑定表按不可变快照发布，物理线程只读。每个子系统恰好触发一次 `onAttach`：构造与存档恢复的初始批量由 `initAllSubsystems` 统一订阅并 attach，初始化后的后加零件由 `addSubsystems` 在加入时先订阅再 attach；结构变化仍按上面的两阶段重新发现。
3. 装弹机向发射器登记的先后见 §4.4。装配体结构事件发生时，主线程发现和登记已经完成。主线程按 §4.3 清空信号槽后，物理线程按已发布的绑定快照继续推进。

**首跳表刷新。** `<mech>/vehicle/VehicleCore.java#addPart` 已经遍历子系统、交互区和端口来建表，复用这条遍历覆盖受影响装配体。合并、分裂后 `global` 从当前装配体解析。服务端接收编辑的入口在 `src/main/java/io/github/sweetzonzi/machine_max/network/payload/ControlGroupSetEditPayload.java`，客户端也可本地编辑。两端最终经过 `<mech>/subsystem/AbstractControllableSubsystem.java#setControlGroupSet`，包括无预设的脚本子系统首次编辑。归属尚未建立时只存配置。改变接线的在世编辑走全量清理与重建。单纯切换活动组按 `<mech>/subsystem/AbstractControllableSubsystem.java#clearInputSignals` 清除当前输入并使用已算好的候选。

`<mech>/signal/ISignalSender.java#setTargetFromNames` 先在局部有序表完成解析，再在主线程对现有 `targets` 执行 `clear()` 和 `putAll()`。查表发送、端口转发、查询和刷新都在本端主线程执行，见 §4.2，读者因此只看到完整的表。频道删空时也执行替换。

`<mech>/subsystem/AbstractControllableSubsystem.java#setUpTargets` 汇集各类输出时，同频道的目标名取有序并集。同一频道以单条目标列表的顺序、base 到子组的顺序以及各类输出和按键绑定、GUI 的固定遍历顺序决定优先顺序。频道键来自 `ControlGroup` 中的 `Map.copyOf`，其迭代顺序无配置语义。base 与活动组决定整频道发送所启用的频道，`sendSignalToAllTargets` 投递给该频道的全部首跳，组内火控发现也读取这张表。显式按名发送只送指定目标。同类输出跨组并集已有实现，P2 固定的是跨类别同名也取并集。

### 4.2 线程、信号槽与反馈

跨线程的独立信号值沿用 `ConcurrentMap`。`<mech>/signal/SignalChannel.java` 已是 `ConcurrentHashMap`，每个接收频道按原始发送者存值。独立频道和同频道的不同来源可并发读写。入表值应为不可变对象或写入后的独立副本。每次读取取一次槽值，按读到的结果处理，避免一次逻辑中两次查询同一槽得到两个时刻的值。

| 路径 | 线程和写入边界 |
| --- | --- |
| 按名发送、批量发送、端口和总线转发 | 本端主线程。查目标表，写来源槽与现有 MoLang 存储，再同步执行 `onSignalUpdated`。输入、GUI 操作、座位交互和信号触发的脚本 Hook 在这一线程处理。座位立即拿到 `SignalResult`。 |
| 车控向已知发动机、电机、车轮、履带发送 | 物理步允许调用实例重载，使用业务绑定中选定的实例和实际输入频道。只允许数值及控制状态等载荷和经过核对的内置接收者。其通知路径只读并发槽并返回，接收端在物理步读取槽值。P0 检查继承的 `onSignalUpdated` 与 `getSignalStorage`，以实际发送目标为准。物理步使用的目标须能在此契约内工作。 |
| 火控向炮塔、发射器发送 | 物理步下发目标角和开火请求。执行器在自己的 tick 读取当前输入，按声明的频道优先级执行。结构变动只清空信号存储，输入请求与业务状态的边界见 §4.3。 |
| 物理步计算、由配置线路输出的反馈 | 物理线程发布最近值，本端主线程的 `onTick` 通过普通发送入口投递。已发布的标量直接复用，多个独立动态频道可共用发送者的最新值并发 Map。主线程读取值后发送，采样槽允许被下一次物理采样覆盖。涉及按目标名称输出的反馈保留配置的命名投递方式。 |

反馈迁移至少核对 `AbstractGroundControllerSubsystem#onPostPhysicsTick` 的油门、刹车、手刹，`EngineSubsystem#onPrePhysicsTick`、`MotorSubsystem#onPrePhysicsTick` 的转速，以及 `TrackDriveSubsystem#onPostPhysicsTick`、`WheelDriverSubsystem#onPostPhysicsTick`、`JointDriverSubsystem#onPostPhysicsTick`、`TurretDriverSubsystem#onPostPhysicsTick` 的速度、受力或姿态。`GearboxSubsystem#switchGear` 可由物理步内的车控触发，挡位变化的普通线路投递归其主线程 `onTick`；`switchGear` 内的直接发送同步移除。按 P0 搜索补齐实际入口，更新 `<mech>/signal/AGENTS.md` 的线程约定。

在启用主线程整表清理前，迁完物理路径对首跳表的访问。特别是 `AbstractGroundControllerSubsystem#onPrePhysicsTick` 在停用时会调用 `resetSignalOutputs`。绑定命令在物理侧释放，按配置线路的状态复位由主线程消费停用状态。先确定复位与反馈的先后，停用后的主线程投递以释放值为准。

在收发两侧都正常推进时，连续命令与反馈允许在接收侧接下来一至两个活跃 tick 可见。物理接收方按物理子步计，主线程接收方按游戏 tick 计。最近值可以覆盖未读取的中间采样。按键脉冲、交互和开火或释放等离散处理按其业务入口保证顺序，座位与 GUI 的即时处理保持同步。结构变动后的信号读取与缺输入行为见 §4.3。

周期发送保持在各自的 `onTick`；乘员信号、开关状态等需要跨结构变化保留的状态型输出由所有者在 `onTick` 周期发送，清空后的值由下一次 `onTick` 补回，不另设重发阶段。

### 4.3 信号清理与子系统状态

结构变动按受影响装配体清空信号存储，包括普通输入频道、Part 和总线的临时信号存储、端口缓冲及用于投递的最近反馈。首跳、订阅、镜头、分组候选、执行器、供给者登记及与接线有关的几何从当前结构完整建立。清空写在预清理阶段，重新解析和绑定写在发现阶段；顺序保证新绑定面对的是清空后的槽。受影响范围内接线相同的线路也从空信号槽开始。

炮塔目标角和锁止角、车控输入锁存及平滑量、发射器与其他子系统的业务状态由各自维护。结构回调只清空信号槽和重建派生接线。下一次业务 tick 从当前容器读输入，由子系统按已有规则决定跟随、保持或释放。炮塔在没有有效目标时可锁定当前关节角，见 `<mech>/subsystem/TurretDriverSubsystem.java#onPrePhysicsTick`。车控按自己的输入采样与平滑逻辑运行，见 `<mech>/subsystem/AbstractGroundControllerSubsystem.java#onPrePhysicsTick`。单次结构变化本身不代表归中指令。

火控改造前的 `setTargetAngle` 和 `setFireCommand` 会把请求写到普通信号容器之外。P3 让执行器判断请求是否存在时读取当前信号容器，复用已有目标角和 `FireCommand` 载荷及频道优先级。炮塔读不到请求时由自身规则处理目标与锁止状态。发射器按本次有效开火请求决定是否继续发射，已经受理的发射按既有生命周期完成。执行器自行处理缺输入，结构回调无需逐项调用旧目标上的释放 setter。

信号槽在本端主线程清空：`signalInputChannels`、Part 与总线的临时存储、端口缓冲都从当前结构重新建立；`SignalChannel` 是 `ConcurrentHashMap`，清空与并发读写安全。发送者的业务绑定表按不可变快照整体替换，物理线程只读取已发布快照，不原地清空正在遍历的 `HashMap`。结构变化后新发起的发送必须先重新解析并保存绑定；结构变化发生时已经在途的一个物理步允许按旧快照完成，之后必须使用新快照。几何在物理相位按新接线采样。物理步与正常发送照常运行。

端口连接和断开由全量清理收尾。`<mech>/signal/SignalPort.java#onConnectorAttach` 的缓存重放和 `#onConnectorDetach` 的逐接收者清理退出结构变动路径。新线路从下一次正常输入、物理采样和主线程反馈填充。结构变动只需清空当前结构的信号槽并重建绑定。

`<mech>/signal/ISignalSender.java#resetSignalOutputs` 用于座位释放、停用等日常动作，按发送者自己的输出复位。物理侧停用释放已知实例的命令，主线程复位配置线路。销毁和构建失败清空运行状态，失败清理入口见 `<mech>/subsystem/SubsystemController.java#discardUninitialized`。

Spark 的 `../Spark-Core/src/main/kotlin/cn/solarmoon/spark_core/physics/level/PhysicsLevel.kt#prePhysicsTick` 先发布 Pre 事件，再处理该相位任务。信号槽清理在本端主线程完成，不额外提交物理任务；刚体与关节的结构变更仍按现有物理相位任务执行。动力图同期实施时对齐 [动力图与支路控制实施计划 §6.1](../计划中/动力系统-动力图与支路控制实施计划.md#61-结构变化的发布边界) 的物理边界。

### 4.4 弹药登记和同步

结构变化的预清理阶段由发射器清空自己的供给者登记。随后两类装弹机从各自的 `discovery_outputs` 查询并通过发射器的现有登记入口填入结果。初装从空表开始。登记按「消费者实例、到达频道、供给者实例」去重，发射器只接受 `ammo_inputs` 中声明的到达频道，声明外的登记拒绝，不建对应列表。火控只设置建池脏标记，在本轮结构变化完成后的首个主线程 `onTick` 建池，空结果也替换弹药池。服务端通过现有供给者切换入口释放已离线的当前供给者，以处理未交付弹药和占用。膛内弹、当前弹链、独占分配、库存和再生行为按既有业务规则核对。

本地登记是从装配结构得到的结果。选中弹链与当前供给者的同步值可能先于本地登记到达。保留待解析的标识，在完整登记和弹药池就绪后重试。只在测试区分「拓扑已齐但无有效弹链」与「同步对象尚不可解析」后收敛 `<mech>/subsystem/WeaponControllerSubsystem.java#onTick` 中因等待握手登记而存在的轮询。损伤恢复、内容变化和真实网络先后顺序分别验收。

供给者指认与释放入口见 `<mech>/subsystem/LauncherSubsystem.java#assignSupplier`，装填语义见 [装弹机装填语义与供给绑定重构计划 §6](武器系统-装弹机装填语义与供给绑定重构计划.md#6-武器控制器契约)。
