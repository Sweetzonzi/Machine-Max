# 命令：载具召唤（`/mm vehicle summon`）

> **状态**：已实现（`VehicleCommand#summon`）；十五条人工验收待完成。
> **日期**：2026-11-29
> **相关**：[载具系统-放置旋转与结构生成复用计划](../进行中/载具系统-放置旋转与结构生成复用计划.md)（§3.5 定义了本命令调用的无玩家实例化入口）。

## 1. 目标

1. 一条命令按内容包模板 id 在指定坐标召唤一台可直接行驶的载具，供调试、验收与服务器管理使用。
2. 召唤走与物品放置完全相同的几何、碰撞与入世路径，不另开一条「直接 `new VehicleCore` + 手动登记」的旁路。
3. 不带 `Player`、`ItemStack`、准星与交互距离也能执行（控制台、命令方块、`/execute`）。
4. 落点被拒时说明是**哪一条**条件没过，而不是一句笼统的「空间不足」。
5. 管理员可以显式要求忽略落点校验强制放置（`force`），并被告知跳过了什么。

## 2. 非目标

- 不做骨架（蓝图语义）召唤的可选参数；本命令固定完整状态。
- 不支持任意 pitch / roll，朝向只取世界竖直轴 yaw。
- 不实现「按 id 查找 / 移除单台载具」「复制在场载具」的配套命令。
- 不做客户端预览、不发送专用网络包。
- 不做「省略坐标时按视线取点」（理由见 §11）。
- 不做「按原因选择性忽略」（例如只跳过占位、仍要求区块已加载）；`force` 只取全跳与全不跳两档。

## 3. 语法

```
/mm vehicle summon <template> <pos> [<yaw>] [force]
```

| 参数 | 类型 | 语义 |
| --- | --- | --- |
| `template` | `ResourceLocationArgument.id()`，带补全 | 内容包模板 id，即 `templates/<文件名>.json` 的 `<命名空间>:<文件名>`。必须是完整 id（§3.2）。示例：`m1a2_sep:m1a2_sep`、`2s38:2s38`、`machine_max:santana`。 |
| `pos` | `Vec3Argument.vec3(false)` | 接地锚点（定义见 §4）。坐标按字面值使用，不做块心补偿；`~` 相对执行者。必填。 |
| `yaw` | `AngleArgument.angle()` | 参考根子零件的世界朝向，单位度；按 §3.4 的约定解释，`~` 相对执行者当前 yaw。省略时取执行者 yaw，控制台为 `0`。不要求 90° 的倍数。可选。 |
| `force` | 字面量 | 跳过全部落点校验强制放置（§3.5）。可选，写在 `pos` 之后或 `yaw` 之后都可以。 |

示例：

```
/mm vehicle summon m1a2_sep:m1a2_sep ~ ~ ~12
/mm vehicle summon 2s38:2s38 100 64 -200 90
/mm vehicle summon machine_max:van ~ ~ ~10 ~
/mm vehicle summon m1a2_sep:m1a2_sep ~ ~ ~6 force
/mm vehicle summon m1a2_sep:m1a2_sep ~ ~ ~6 180 force
/execute as @p at @s run mm vehicle summon k17:k17 ~ ~2 ~
```

`force` 与 `yaw` 互为可选且互不依赖，四种组合都注册成独立节点：

```
summon <template> <pos>                     → 默认 yaw，校验
summon <template> <pos> force               → 默认 yaw，跳过校验
summon <template> <pos> <yaw>               → 指定 yaw，校验
summon <template> <pos> <yaw> force         → 指定 yaw，跳过校验
```

命令树里 `force` 字面量与 `yaw` 参数是同一层的两个可选节点：输入非数字的 `force` 由字面量接住，输入数字由 `AngleArgument` 接住，两种输入互不干扰。字面量写在参数之前，只是让每个待匹配节点的尝试顺序确定下来。

### 3.1 自动补全

`ResourceLocationArgument` 本身不带补全，参数节点上挂一个 `suggests` 回调，把 `MMDynamicRes.TEMPLATES` 的键交给原版的资源补全器：

```kotlin
Commands.argument("template", ResourceLocationArgument.id())
    .suggests { _, suggestions ->
        SharedSuggestionProvider.suggestResource(
            MMDynamicRes.TEMPLATES.keys.sortedWith(ResourceLocation::compareTo), suggestions)
    }
```

`SharedSuggestionProvider#suggestResource` 的过滤规则（1.21.1 源码）：输入不含冒号时，对**命名空间**与**路径**分别做分段前缀匹配，命中即列出完整 id；输入含冒号时对完整 id 做同样的匹配。匹配按 `.` 与 `_` 切段，所以 `van` 命中 `machine_max:van`、`fox` 命中 `machine_max:wine_fox`、`m1a2` 命中 `m1a2_sep:m1a2_sep`；在补全列表里选中哪一条，填进输入框的就是那一条的完整 id。

三点实现细节：

- 补全在服务端算，客户端按 `ServerboundCommandSuggestionPacket` 取结果；模板表本来就只在服务端有数据（`TemplateModule` 只在 `fromServer` 时填充），不需要给客户端补一份。
- `TEMPLATES` 是 `ConcurrentHashMap`，键序不稳定，补全前用 `ResourceLocation::compareTo` 排序，与 `list_templates` 的顺序一致。
- `PhysicsTestCommand` 是手写 `builder.suggest(path.toString())` 循环；本命令的参数是资源 id，`suggestResource` 直接给出「命名空间或路径命中 → 完整 id」的过滤，不需要手写这段匹配。

### 3.2 模板 id 必须是完整 id

`TEMPLATES` 以 `ResourceLocation` 为键，键本身唯一，`machine_max:van` 与 `2s38:2s38` 是两个不同的条目，不存在「同一个 id 对应多份数据」的情况。问题出在参数解析这一侧：`ResourceLocationArgument.id()` 走 `ResourceLocation.read` → `bySeparator`，输入不带冒号时补成 `minecraft:<路径>`。所以 `van` 会被解析成 `minecraft:van`，在模板表里查不到。

命令按解析结果**精确查表**，没有按路径反查的回退：裸写路径必然查不到，报「未知模板」，该消息的文本本身就说明 id 要写成 `命名空间:路径` 并指向 `list_templates`。补全（§3.1）只吐完整 id，正常操作不会手打短名。

### 3.3 缺参数与错误输入由原版给出

`<template>` 与 `<pos>` 是必填节点，缺参数时原版负责提示，命令不需要写：

- 输入过程中，客户端 `CommandSuggestions#updateUsageInfo` 用 `CommandDispatcher#getSmartUsage` 在补全区下方显示用法行（`/mm vehicle summon <template> <pos> [<yaw>] [force]`）；
- 执行不完整的命令时，Brigadier 抛 `dispatcherUnknownCommand` / `dispatcherUnknownArgument`，由 `Commands#finishParsing` 转成失败消息并补一行 `command.context.here` 的插入符定位。

命令自己只产出「解析通过、执行期才失败」的消息：未知模板、模板数据损坏、落点被拒、强制放置时跳过了哪一条。

### 3.4 朝向角的两套约定

`yaw` 参数按 **Minecraft 的 yaw 约定**解释：`0` 指向 +Z（南），数值增大对应俯视顺时针。这样 `~` 取得的是执行者当前 yaw，F3 界面里的朝向读数可以直接复制过来用，省略 `yaw` 与显式写同一个数字等价。

载具放置内部用的是 **JME 四元数**：`Quaternion#fromAngleNormalAxis` 绕世界 +Y 按右手法则旋转，正角在俯视下是逆时针，与 Minecraft yaw 反向。两者之间的换算只有一步取反：

```kotlin
private fun placementRotation(yaw: Float): Quaternion =
    Quaternion().fromAngleNormalAxis(Math.toRadians(-yaw.toDouble()).toFloat(), Vector3f.UNIT_Y)
```

`yaw = 0` 表示参考根朝向与模板的作者朝向一致（与世界轴对齐），数值增大表示俯视顺时针转过相应角度。物品放置路径的朝向是相对量——每次按键把预览转动 ±90°——不构成一套可比的绝对角度，因此命令给出的是与 Minecraft yaw 同一空间的绝对角度：`~` 与手写数字可以互换，面朝西（yaw 90）时写 `~` 与写 `90` 等价。

### 3.5 `force` 的语义与代价

落点校验拆成五条互不依赖的判定（§5.2），`force` 把它们**全部**跳过。以下是它换来的东西和它的代价，逐条对应：

| 跳过的那条 | 强制放置后发生什么 |
| --- | --- |
| 世界边界越界 | 载具在边界外的位置入世，物理照常模拟；世界边界只约束玩家与方块，不约束载具。 |
| 建造高度越界 | 落点在建造范围之外，脚下没有地形，物理体不受支撑会持续下坠，直到被下方地形或维度底部挡住。 |
| 区块未加载 | `VehicleCore#onAddToLevel` 会为载具 AABB 覆盖的区块申请保活（`updateVehicleTerrainHold` → `holdVehicleChunkTerrain`），地形随后异步构建；就绪前刚体被钉住，就绪或超时（`TERRAIN_WAIT_TIMEOUT_TICKS`）后解除。这是唯一一条「强制放置后系统会自己补齐前提」的拒绝原因。 |
| 落点与方块重叠 | 载具与方块互相侵入，物理求解会把载具挤出去；挤不动时载具卡在方块里，需要拆方块或再挪一次。 |
| 落点被玩家或载具占用 | 与实体重叠，物理冲量会把双方推开；玩家可能被顶飞或卡住。 |

命令在强制放置成功时额外回一条「已忽略落点校验: <原因>」，让执行者知道这次是靠 `force` 才成立的。这条判定在**入世之前**取值——载具一旦进世界，它自己的物理体会让占位检查对它自己成立。

`force` 只跳过落点校验，不跳过载具数据的预检：模板损坏仍然走 `failed`，构造器抛出的异常照样透出。

## 4. 坐标语义

`pos` 是**接地锚点**，不是载具实例中心，也不是旋转后世界 AABB 的底心：

- XZ 对齐「参考根子零件局部坐标系下整车物理碰撞 AABB 的底心」的水平投影；
- Y 是整车最低碰撞边界的目标高度，落地高度由此反推。

参考根取总质量最大的普通部件的 `rootSubPart`（同质量按部件 UUID 自然顺序决胜）。这套语义由 `VehiclePlacementService` 实现，命令只负责把参数传给 `instantiateAndAdd`，不自行换算。

因为 Y 是接地高度而不是实体中心，`pos` 用 `Vec3Argument.vec3(false)`：坐标按字面值使用，输入的 `y` 就是整车最低碰撞边界的目标高度（`100 64 100` 表示底部贴住 `y=64`）。`Vec3Argument.vec3()` 的块心补偿会给写成整数的每一轴加 `+0.5`（含 Y），用在这里会让载具在输入高度上方悬空半格。想要水平对齐块心时把 XZ 写成 `100.5`。

站在落点上用 `~ ~ ~` 会让载具碰撞 AABB 与执行者包围盒重叠，落点校验按「被占位」拒绝；这是预期行为，调试时用 `~ ~ ~8` 之类的前方坐标，或者加 `force` 硬放。

## 5. 执行流程

全部在主线程、服务端执行；命令只在服务端被调度，不存在客户端分支。

1. `source.getLevel()` 取 `ServerLevel`；`source.getRotation().y` 供 `yaw` 省略时取值。
2. `ResourceLocationArgument.getId(ctx, "template")` 取模板 id，在 `MMDynamicRes.TEMPLATES` 里精确查找。缺失 → 「未知模板」。
3. `new VehiclePlacementService(level, template)`：选定参考根并合成局部碰撞 AABB。模板损坏时构造器与后续合成会抛 `IllegalArgumentException` / `NullPointerException`，整段包在 `try/catch (Exception)` 内，把异常消息回给执行者，不让异常冒到命令调度器。
4. `yaw` → `placementRotation(yaw)`（§3.4）。
5. `anchor = Vec3Argument.getVec3(ctx, "pos")`；`bounds = placement.boundsAtOrigin(rotation).move(anchor)`。
6. `force` 为真时，先把 `placement.findRejection(bounds)` 的结果存下来（用于事后回报），然后**无条件**继续；否则跳过这一步。
7. `placement.instantiateAndAdd(PartRestoreMode.FULL_STATE, anchor, rotation, force)`。返回 `null` 表示落点校验没过。
8. 返回 `null` 时用 `placement.findRejection(bounds)` 取具体成因，回一条「落点校验未通过: <原因>」并附 AABB，返回 0。
9. 非空即已登记进 `ObjectManager`。若第 6 步存下的成因非空，先回一条「已忽略落点校验: <原因>」。
10. 成功消息：模板 id、实例 UUID、部件个数、接地锚点；`sendSuccess(..., true)` 广播给其他 op。返回 1。

### 5.1 服务端权威事项

- 新实例 UUID 由 `VehiclePlacementService#createInstanceData` 生成，命令不指定；
- 模板对象不被修改：`createInstanceData` 产出新的 `VehicleData` 副本，`parts` 的键与部件 UUID 沿用模板（与物品放置一致），实例身份靠载具 UUID 区分；
- 恢复模式固定 `FULL_STATE`：模板是内容包里已组装、满耐久的成品，召唤的用途是立刻能开。`STRUCTURE_ONLY` 是蓝图语义（进度归零、线框、履带 0/N），留给未来的骨架参数。

入世后的地形保活、地形未就绪时的冻结等待、创建包广播与运行时状态补推都在 `VehicleCore#onAddToLevel` 与 `ObjectManager#addVehicle` 内完成，命令不介入。

### 5.2 落点校验的拆分

`VehiclePlacementService#findRejection(AABB)` 按固定顺序返回第一个不满足的条件，`canPlace` 退化为 `findRejection(bounds) == null`：

| 顺序 | `PlacementRejection` | 判定 |
| --- | --- | --- |
| 1 | `OUT_OF_BORDER` | 整车碰撞 AABB 越过世界边界 |
| 2 | `OUTSIDE_BUILD_HEIGHT` | 越过建造高度下限或上限 |
| 3 | `CHUNKS_UNLOADED` | AABB 覆盖的区块没有全部加载 |
| 4 | `BLOCK_COLLISION` | 与方块碰撞形状重叠（`Level#noBlockCollision`） |
| 5 | `OCCUPIED` | 与玩家或在场载具的物理体接触（`contactTest`，PAWN 与 PHYSICS_BODY） |

判定的区分粒度按「执行者能采取的处置」定：前两条是坐标要挪，后三条是现场要清。区块判定与方块判定共用同一份收缩后的 AABB（`interiorOf`：每轴收缩 1e-4，避免把恰好贴着的区块或方块算进去），所以「贴着边界放着」不会被误判。

判定用的是整车 AABB，而不是逐个子零件的碰撞形状：斜停的长车在窄巷里会被按外接盒高估体积，明明塞得下也会被拒。这是这套校验天然偏严的那一面，也是 `force` 存在的直接原因之一（§3.5）。

## 6. 失败情形与消息

| 情形 | 判定点 | 消息键 | 参数 |
| --- | --- | --- | --- |
| 未知模板 | 模板查找 | `unknown_template` | 模板 id |
| 模板数据损坏 | 放置服务构造 / 碰撞合成抛异常 | `failed` | 异常消息；空消息回退为异常类型名 |
| 落点被拒 | `instantiateAndAdd` 返回 `null` | `rejected` | 原因文案、目标 AABB |
| 强制放置时跳过了校验 | `force` 且 `findRejection` 非空 | `force_ignored` | 原因文案 |
| 成功 | 返回非空 | `success` | 模板 id、实例 UUID、部件个数、接地锚点 |

原因文案本身是四条键（边界与建造高度共用一条，处置方式相同；取不到成因时用第五条兜底）：

| 枚举 | 标签 | zh_cn | en_us |
| --- | --- | --- | --- |
| `OUT_OF_BORDER`、`OUTSIDE_BUILD_HEIGHT` | `…summon.reason.out_of_bounds` | 落点超出世界边界或建造高度 | outside the world border or build height |
| `CHUNKS_UNLOADED` | `…summon.reason.chunks_unloaded` | 目标区块未加载 | target chunks are not loaded |
| `BLOCK_COLLISION` | `…summon.reason.block_collision` | 落点与方块重叠 | overlaps solid blocks |
| `OCCUPIED` | `…summon.reason.occupied` | 落点被玩家或在场的载具占用 | occupied by a player or an existing vehicle |
| （成因取不到） | `…summon.reason.unknown` | 落点不合适 | the spot is not usable |

全部键登记到 `MMLanguageRegistry`，经 `runData` 生成语言文件，命令里不写裸字符串：

| 枚举常量 | 标签 | zh_cn | en_us |
| --- | --- | --- | --- |
| `COMMAND_VEHICLE_SUMMON_SUCCESS` | `command.machine_max.vehicle.summon.success` | 已召唤 %1$s（%2$s），%3$s 个部件，落点 %4$s | Summoned %1$s (%2$s), %3$s parts at %4$s |
| `COMMAND_VEHICLE_SUMMON_UNKNOWN_TEMPLATE` | `…summon.unknown_template` | 未知载具模板: %1$s；模板 id 需写成 命名空间:路径，完整列表见 /mm vehicle list_templates | Unknown vehicle template: %1$s; ids are namespace:path, see /mm vehicle list_templates |
| `COMMAND_VEHICLE_SUMMON_REJECTED` | `…summon.rejected` | 落点校验未通过，无法在 %2$s 召唤: %1$s | Placement check failed, cannot summon at %2$s: %1$s |
| `COMMAND_VEHICLE_SUMMON_FORCE_IGNORED` | `…summon.force_ignored` | 已忽略落点校验: %1$s | Placement checks ignored: %1$s |
| `COMMAND_VEHICLE_SUMMON_FAILED` | `…summon.failed` | 召唤失败: %1$s | Summon failed: %1$s |

消息经 `MMLanguageRegistry#component` 构造：带 `en_us` 兜底，专用服务器与命令方块的日志里也能读到正文而不是裸键。

坐标与 AABB 的文本格式在命令内联（`String.format(Locale.ROOT, "%.1f, %.1f, %.1f", …)`，AABB 用 `→` 连接最小角与最大角），不占用翻译键：它们是数字，与语言无关。

## 7. 基础设施确认

本命令不引入新的载具构造、入世或同步逻辑，全部复用现有实现。逐项核对结果：

| 能力 | 现状 | 结论 |
| --- | --- | --- |
| 命令挂载 | `MMCommands.reg` 把 `VehicleCommand().create(buildContext)` 挂在 `/mm` 下；`VehicleCommand` 继承 Spark-Core 的 `BaseCommand("vehicle", 4)`，已有 `clear`、`list_templates` | 在 `putExecution` 里加一条 `literal("summon")` |
| 模板注册表 | `MMDynamicRes.TEMPLATES`（`ConcurrentMap<ResourceLocation, VehicleData>`），由 `TemplateModule` 在服务端装载 `templates/*.json` 时填充；`list_templates` 已在用 | 够用；键是唯一 id |
| 模板有效性 | `VehicleData#validate(Level)` 给蓝图口径的问题列表；`VehicleCore(Level, VehicleData, PartRestoreMode)` 构造期自带型号 / 身份 / 连接引用预检并抛 `IllegalArgumentException`；`findPlacementReferenceRoot` 对无可用参考根抛 `IllegalArgumentException` | 命令只捕获并透出；不先跑 `validate` |
| 放置几何 | `VehiclePlacementService#boundsAtOrigin(Quaternion)` 用「参考根局部 AABB 底心 + 目标朝向最低 Y」求接地盒，结果按朝向缓存 | 直接调用 |
| 落点判定 | `VehiclePlacementService#findRejection(AABB)` 返回 `PlacementRejection` 枚举（边界 / 建造高度 / 区块 / 方块 / 占位）；`canPlace` 是它的判空形式 | 命令读枚举，据此给出具体原因 |
| 入世 | `VehiclePlacementService#instantiateAndAdd(PartRestoreMode, Vec3, Quaternion, boolean force)`：校验通过（或 `force`）后构造 `VehicleCore` 并 `ObjectManager.addVehicle`，返回 `VehicleCore` 或 `null`；在客户端世界调用会抛异常 | 这是唯一的调用入口；三参重载等价 `force = false`，物品放置路径未变 |
| 入世后处理 | `VehicleCore#onAddToLevel` 做区块保活、地形未就绪时冻结等待；`ObjectManager#addVehicle` 落盘维度数据、广播 `VehicleCreatePayload`、补推运行时同步字段 | 命令不需要额外收尾；`force` 落进未加载区块时靠这里自愈（§3.5） |
| 补全 | `SharedSuggestionProvider#suggestResource(Iterable<ResourceLocation>, SuggestionsBuilder)` 可直接用；`PhysicsTestCommand` 有手写 `builder.suggest` 的先例 | 一行挂到参数节点上 |
| 缺参数提示 | 客户端 `CommandSuggestions#updateUsageInfo` 走 `getSmartUsage` 显示用法行；执行期由 Brigadier `dispatcherUnknownCommand` / `dispatcherUnknownArgument` 出提示，`Commands#finishParsing` 附插入符 | 命令不写缺参数消息 |
| 参数原语 | `ResourceLocationArgument.id()`（缺命名空间补 `minecraft`）；`Vec3Argument.vec3(boolean)`（`centerCorrect` 控制字面值是否 `+0.5`，命令取 `false`）；`AngleArgument.angle()` + `AngleArgument.getAngle`（`wrapDegrees`，`~` 相对执行者 yaw） | 三个都是 1.21.1 现成 API，已核对源码 |
| 语言键 | `MMLanguageRegistry` + `runData` 生成 `src/generated/resources/assets/machine_max/lang/*.json` | 按 §6 登记九条 |
| 线程 | 命令在主线程执行；物理体登记由 `VehicleCore` / 连接器内部经 `submitImmediateTask` 完成 | 无额外约束 |

### 7.1 缺口

| 编号 | 缺口 | 本设计的处理 |
| --- | --- | --- |
| G1 | 物品预览的绿 / 红框只读 `canPlace` 的布尔结果，界面上不显示拒绝原因 | 命令按 `findRejection` 的枚举给原因；物品预览只用布尔结果。要让预览也显示原因，把 `BaseVehicleItem#updateBoundingBoxPreview` 的入参换成枚举即可，不需要新实现 |
| G2 | 权限粒度：`BaseCommand` 把 `requires { hasPermission(permissionLevel) }` 钉在 `vehicle` 节点上，子命令无法单独放宽（Brigadier 沿路径 AND 各级 `requires`） | 沿用 4 级，与 `clear` 一致。要让召唤降到 2 级需改 `BaseCommand` 的用法或换掉基类，不在本设计范围 |
| G3 | 没有「按 id 查找 / 移除单台载具」，`clear` 只能清空整个维度 | 成功消息给出实例 UUID 便于排查；配套命令留作后续 |

## 8. 设计决定

**D1 `id` 指内容包模板 id，不是装配体 / 蓝图 id，也不是载具实例 UUID。**
`AssemblyItem` 与 `VehicleBlueprintItem` 都是用 `AssemblyData#getTemplate` / `BlueprintData#getTemplate` 取到模板 id，再经 `MMDynamicRes.TEMPLATES` 拿 `VehicleData`；装配体与蓝图 id 本身不携带可实例化的几何。在场载具的身份是 `VehicleCore` 的实例 UUID，与内容包 id 不是同一个命名空间，召唤不使用它。

**D2 `pos` 必填。**
坐标是接地锚点，缺省值只能是「随便找个地方」或「执行者视线前方」，前者不可控，后者要在执行期区分不同来源并额外产出一条语义错误消息（原版只负责缺参数，不负责这种语义约束）。`~ ~ ~8` 已经把「在身前召唤」写起来很短，所以不做省略形式。

**D3 `pos` 的语义对齐现有放置服务，不自创。**
命令不自行把世界 AABB 底心当落点，也不按载具 `min/max` 缓存算高度，避免同一台模板在物品放置与命令召唤下落地高度不一致。

**D4 恢复模式固定 `FULL_STATE`，`yaw` 不吸附 90°。**
90° 吸附是物品放置路径的输入约束（`BaseVehicleItem#handlePlacementRequest` 校验 `yaw % 90 == 0`），命令直接给角度更有用（斜停测试、精确对齐）。朝向角的取值约定见 §3.4：命令侧按 Minecraft yaw 取参数，构造四元数时取反。

**D5 模板 id 精确查表，不按路径回退。**
键唯一，回退只会引入「裸名命中谁」的第二套语义与歧义分支；补全已经把完整 id 送到手边，裸写路径的失败由「未知模板」一条消息说明写法即可。

**D6 落点判定拆成枚举，`canPlace` 退化为它的判空形式。**
五条判定彼此独立、处置方式不同，合成一个 `false` 会让执行者只能盲试。枚举由放置服务拥有（一份实现），命令只读它决定文案；`canPlace` 保留为布尔入口，物品预览与既有调用方的签名不变。判定不为每条原因各建一个异常类型——它们都不是异常，是常规的「这里不行，换个地方」。

**D7 `force` 跳过全部判定，但回报跳过了什么。**
落点校验的价值在于「系统替你把明显的错误挡掉」，调试时它挡住的往往正是想复现的东西（墙里的载具、悬空测试、未加载区块的入世行为）。`force` 用一条消息说明跳过了哪条，比静默强制更容易追溯；判定取值在入世之前完成，否则载具自己的物理体会让占位检查成立。不提供按原因选择性忽略：多一档开关就多一组组合，而 `force` 加换坐标已经覆盖了全部用法。

## 10. 验收

首版只有手工验收：命令类逻辑目前没有 GameTest 覆盖，后续如需固化，再按 `runGameTestServer` 里 `performPrefixedCommand` 的形态补一份。

1. `/mm vehicle summon m1a2_sep:m1a2_sep ~ ~ ~12`（玩家朝地面）→ 生成完整载具，满耐久，焊接进度满，能直接开动。
2. 补全：输入 `/mm vehicle summon ` 后按 TAB 列出现有全部模板 id（第一方内容 24 个），按 id 排序；输入 `van` 命中 `machine_max:van`，输入 `fox` 命中 `machine_max:wine_fox`，输入 `m1a2` 命中 `m1a2_sep:m1a2_sep`；补全结果是完整 id。
3. 同一模板连续召唤两次 → 两台载具、两个不同实例 UUID、可独立开动；模板 JSON 与物品蓝图未被改写。
4. `/mm vehicle summon 2s38:2s38 100 64 -200 90`（控制台）→ 底部对齐 `y=64`，朝向 90°。
5. `/mm vehicle summon van ~ ~ ~5` → 「未知模板」，消息说明 id 要写成 `命名空间:路径` 并指向 `list_templates`。
6. 在未加载的远处坐标召唤 → 「落点校验未通过: 目标区块未加载」并附 AABB，且不产生任何载具（`/mm vehicle clear` 计数为 0）。
7. 朝墙召唤（锚点在墙体内）→ 「落点校验未通过: 落点与方块重叠」；清空后重试成功。
8. 站在落点上用 `~ ~ ~` → 「落点校验未通过: 落点被玩家或在场的载具占用」，换成 `~ ~ ~6` 成功。
9. 跨多区块的大型载具：只有 AABB 覆盖的区块全部加载时才成功。
10. 缺参数：`/mm vehicle summon` 与 `/mm vehicle summon m1a2_sep:m1a2_sep` 分别给出原版的错误提示与用法行，命令自身不产出消息。
11. 非 op 执行 `/mm vehicle summon ...` → 权限拒绝（4 级）。
12. 三种 `force` 写法都进同一个执行体：`... ~ ~ ~6 force`、`... ~ ~ ~6 180 force`，以及补全列表里 `force` 出现在 `pos` 与 `yaw` 之后。
13. 朝墙加 `force`：载具出现在墙里，先回「已忽略落点校验: 落点与方块重叠」再回成功消息；随后物理把载具挤出墙体（拆掉方块后能开动）。
14. 未加载区块加 `force`：载具立刻出现在目标坐标，且目标是「区块随后被加载」——观察载具先悬停后落地（地形就绪即解除钉住），不出现坠穿。
15. 边界外 / 建造高度外加 `force`：载具确实入世，并且在建造高度外时看得见持续下坠。

编译期与数据期已过的部分：`compileJava` / `compileKotlin` 通过，`gradlew --offline test` 全绿，`runData` 生成两条语言文件；第 2、5 项的补全过滤与 `minecraft:` 补全行为按 `SharedSuggestionProvider` / `ResourceLocation#read` 源码核对，第 10 项按 `Commands#finishParsing` 源码核对，第 12 项的节点解析按 Brigadier 的逐节点尝试规则核对。第 1、3、4、6–9、11、13–15 项需要进游戏确认。
