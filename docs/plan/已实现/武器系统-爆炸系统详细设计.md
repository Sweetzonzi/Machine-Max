**量类速查**：$A_{pen}$ 是**强度量**（不乘面积）；$D$、$J$ 是**广延量**（随目标迎流面积缩放）；$I$ 是无量纲的局部量，只驱动强度。

> **关键约定：本模型里能量是无量纲的（总爆炸能量 $\equiv1$，§6.3）。因此 $\Delta E$、$\mathfrak{E}$ 无量纲，它们的"单位"被 $\Phi_0$ 吸收（$\Phi_0$ 的 $\mathrm{m^{-2}}$ 就是"每平方米的参考能量"在无量纲化之后的残留）。**
>
> 照此做量纲自检：$\Delta E/\Phi_0$ 得到的正是 $\mathrm{m^2}$，而 `base_damage` 的单位是 伤害·$\mathrm{m^{-2}}$，两者相乘恰好是伤害点数：
>
> $$\underbrace{\frac{\Delta E}{\Phi_0}}_{\text{无量纲}\div\mathrm{m^{-2}}=\ \mathrm{m^2}}\times\underbrace{base\_damage}_{\text{伤害}\cdot\mathrm{m^{-2}}}=\text{伤害}$$

# 第一部分 · 基础规则

## 一、背景与动机

现有投射物系统只支持纯动能弹，引信与战斗部已在 `武器系统-组件化投射物与类型体系设计.md` 中设计，但战斗部**具体如何实现爆炸尚无设计**。原版爆炸有三条硬伤，都不能接受：

| 问题                            | 后果                                           |
| ----------------------------- | -------------------------------------------- |
| 只作用于原版生物与方块                   | 完全无法与 Bullet 刚体（载具、零件、抛射物）互动，只能靠代理 Entity 转发 |
| 瞬发（单次 `explode()` 内算完全部破坏与伤害） | 大范围爆炸产生性能尖峰；破坏与掉落逐方块触发邻居更新                   |
| 无传播过程                         | 无掩体削弱、无暴露面积概念，伤害与遮挡只能靠特例分支近似                 |

同时爆炸**不应只服务于弹头**：弹药架被击穿后的殉爆、油箱起火、子系统摧毁都需要同一套能力。因此爆炸必须是**独立的通用服务**，而不是投射物包里的一个 Effect 实现。

### 1.1 一句话模型

**爆炸是一团随时间向外扩张的"能量场"，用一组确定性射线去采样这个场。**

- 射线是**采样探针**，不是能量包：每条射线占一个固定的立体角份额，负责在它经过的地方报告"那里的场强是多少"。
- 射线**维护的是能量**：初始为 1.0，沿途只因穿透而折减。
- **强度** **$I$** **是派生量**：需要判断穿深、伤害、冲量时，由射线的剩余能量与几何量现算。
- 射线数因此退化为**纯采样参数**——它改变估计的方差，不改变期望（§4.6）。

## 二、核心设计决策

| 决策        | 内容                                                                              |
| --------- | ------------------------------------------------------------------------------- |
| **判定归属**  | 爆炸的几何遍历与伤害结算全部在**主线程**；物理线程只接收已结算的冲量批次                                          |
| **地形判定**  | 主线程直接读区块数据的 **3D DDA 体素遍历**，不经物理引擎                                              |
| **刚体判定**  | 读 `PhysicsWorld.worldSnapshot`（主线程可读的物理快照），射线**可穿透**刚体                          |
| **两通道**   | `rayTest` 只可能返回刚体（地形刚体不在快照里，§3.5）；地形**只走 DDA**                                  |
| **单次检测**  | 每射线每 tick **只做一次** `rayTest`，覆盖本 tick 的推进段，**不做逐格检测**（§4.3）                     |
| **传播模型**  | **逐段推进**：按 `front_speed / 20`（主线程 tick 率）前进；越出 `max_radius` 结束，能量低于阈值则只停止交互          |
| **本征量**   | 射线维护**剩余能量比例** **$E_r$**（初始 1.0）；场强比 $I$ 是派生量（§3.1）                             |
| **两段式执行** | 推进阶段**只登记**原始命中数据；所有射线推进完毕后才结算强度、伤害、冲量与摧毁（§4.5、§7.4）                            |
| **穿透判据**  | 由 $I$ 导出有效穿深；**BF 目标（刚体/实体）交目标侧 `resolvePenetration`，方块由爆炸侧自比 $A_{block}$**，均为二值（拦下 / 穿透） |
| **伤害判据**  | 基准伤害 $D=base\_damage\times\dfrac{\Delta E}{\Phi_0}$；**最终值再由目标侧材料修正**（方块 `blockDamageFactor`／刚体 `modifyDamage`／实体原版链条）（§7.2） |
| **冲量**    | $J=base\_impulse\times\sum_r A_r\sqrt{I_r}$，广延量；逐射线求和，$A_r=\Delta\Omega\,d_r^{2}$       |
| **近场平台**  | $d<near\_radius$ 时 $I$ 钳到 1，贴脸不再发散（§6.4）                                        |
| **施加纪律**  | 每个**去重键**（命中区域）每 tick 至多结算一次伤害与一次冲量；同 tick 内先累积、后统一施加（§9.5）                     |
| **摧毁判据**  | **看伤害，不看能量**；只要被摧毁必然是被击穿过（§9.2、§7.3）                                            |
| **掩体削弱**  | 由穿透折减自动产生，**与是否摧毁解耦**；关掉地形破坏后穿透折减照常发生（§十一）                                      |
| **摧毁执行**  | 静默标记，本 tick 结算末尾统一执行，杜绝遍历顺序依赖（§9.2）                                             |
| **线程协作**  | 冲量经 `ctx` 的 `IMPULSE` 扩展随伤害一并交给刚体侧，爆炸侧不另建投递队列（§10.3）                                       |
| **服务化**   | 爆炸是独立服务，投射物/子系统/指令只是它的三种调用方                                                     |

## 三、线程与时间基准

### 3.1 本征量与派生量

**射线维护的能量是本征量；场强比是派生量。**

| <br /> | 量             | 含义            | 初始值   | 被谁改变                                  |
| ------ | ------------- | ------------- | ----- | ------------------------------------- |
| **本征** | $E_r\in[0,1]$ | 该射线**剩余能量比例** | $1.0$ | 只被穿透折减（§五）                            |
| **派生** | $I\in(0,1]$   | 该点的**归一化场强比** | —     | 由 $E_r$、$d_r$ 现算（§6.1）                  |

两者分工要写清楚，否则会写出"逐条射线算一个 $I$ 再相加"这类错误：

- $E_r$ 是**射线的状态**，是广延量的累积对象；
- $I$ 是**某一点的场强**，是穿透与伤害判据的输入；
- $\lambda_r=\Delta\Omega/4\pi=1/rayCount$ 是**全局常数**，不随距离变、不随遮挡变。它只以**能量份额**的身份出现（$E_r\lambda_r$ 才是该射线占爆炸总能量的比例）；**通量里不含它**（§6.1），这正是结果不随 `rayCount` 变的原因（§4.6）。

> **为什么不做亚步长位置外推**：快照每主线程 tick 只刷新一次，物理每 tick 推进 `dynamicRepeat` 个子步（默认 5，`PhysicsLevel.kt:65`），因此快照可落后 0\~5 个子步。200 m/s 的飞行器在 5 个子步内位移可达 10 m。但爆炸是一个跨多 tick 扩张的波前，这个量级的初始位置误差对它没有意义；强行外推反而引入"应当外推到哪个时刻"的额外语义。正确做法是：**用最新快照判定，并把那一刻登记为起爆时刻。**

### 3.2 介质交互的三个通道

| 目标         | 通道                                      | 为什么                                 |
| ---------- | --------------------------------------- | ----------------------------------- |
| **方块（地形）** | 主线程 **3D DDA** 读区块数据                    | 地形刚体**不在快照里**，且为一次爆炸唤起地形构建不划算       |
| **快照中的刚体** | 快照粗筛 + `rayTest` + `triangleIndex → HitBox` | 已在快照中，且能拿到精确命中几何。**内容不纯，须按 `owner` 分派** |
| **其余实体**   | 主线程 AABB 相交，取进入 t 作 hitFraction              | 不在快照里（如 `PAWN` 组），不拦下射线、只被登记（§4.4、§8.4） |

**三条通道的结果必须合并成同一条按距离排序的序列**，否则地形遮挡会被绕过（§4.4）。

> 各通道的碰撞组归属、快照实际内容清单、`owner` 分派规则，见 **附录 A.1、A.2**。

### 3.3 主线程 tick 的真实时序
依据 Spark-Core `PhysicsLevelApplier` 与 `PhysicsLevel.requestStep()`：

```text
LevelTickEvent.Pre
  ├─ [HIGHEST] ObjectManager.onPreTick()          ← 本项目 preTick 在此
  ├─ [HIGH]    PhysicsLevelApplier.mcLevelTask()
  │              └─ requestStep()
  │                   ├─ worldSnapshot.syncStructure()   ← 结构同步（仅 dirty 时）
  │                   ├─ worldSnapshot.syncTransform()   ← 位置同步（每 tick）
  │                   ├─ worldSnapshot.update(...)       ← 仅维护 AABB
  │                   └─ 唤醒物理线程执行本 tick 的 5 个物理步
  └─ 其余 Pre 监听器
LevelTickEvent.Post
  ├─ [HIGH]    PhysicsLevelApplier.mcLevelTask()  ← 仅处理 POST 阶段任务
  └─ [NORMAL]  ObjectManager.onPostTick()          ← 本项目 postTick 在此
```

**两条必须遵守的结论：**

**① 爆炸的推进必须排在** **`ObjectManager.onPreTick`** **之后。**

`ObjectManager.onPreTick` 是 `HIGHEST`（`ObjectManager.java:206`），而快照刷新发生在 Spark 的 `HIGH` 处理器内（`PhysicsLevelApplier.kt:60-66` → `PhysicsLevel.kt:240-243`）。`HIGHEST` 先于 `HIGH` 触发，因此**在本项目现有的 preTick 中读快照会拿到刷新前的旧值**。放在 `LevelTickEvent.Post` 则快照已经刷新完毕。

**② 快照延迟的常态是一个物理步，不是一整个 tick。**

```text
Post 阶段读取到的状态 = 物理步 (t−1) 结束时的位置
冲量实际生效时刻       = 物理步 t 的 PPhase
```

冲量投递相位建议用 `PPhase.ALL`（每个子步开头抽干，`PhysicsLevel.kt:393`），使延迟收敛到 1 个物理步；若用 `PPhase.PRE`，由于 `requestStep()` 已在 Pre 阶段唤醒物理线程、PRE 队列可能已被抽干，冲量会落到下一个物理步，延迟翻倍为 2 个物理步。**这个差别是 10 ms 与 20 ms 的差别，属于手感量级，务必在实现时确认。**

### 3.4 逻辑时间基准

**爆炸管理器只订阅一个事件，且只在这个事件里推进。** 该事件必须满足一个语义要求：**只在快照真的刷新时触发**。

```java
/// 主线程；在 worldSnapshot.syncTransform() 之后、下一轮物理步唤醒之前触发。
/// ★ 触发条件：本 tick 的快照确实完成了刷新（requestStep 未因 RUNNING 提前返回）。
public class PhysicsSnapshotReadyEvent extends Event {
    PhysicsLevel getPhysicsLevel();
    long getPhysicsStep();     // 快照步号（主线程 tick）：事件丢失的诊断
}
```

**"事件即一步"**：收到一次，推进一次推进距离。所以

- **不需要"剩余待排队步数"计数器**——事件的触发频率就是推进节奏，没有需要补偿的时间轴；
- **不需要 `isSnapshotFresh()`**——新鲜度由"事件是否触发"本身承载。若事件在空转时也触发，就必须再筛一次；把触发点收紧到"确实刷新"之后，这个字段就是多余的；
- **不需要关心 `dynamicRepeat`**——快照刷新发生在主线程 tick 上（20 tps），与物理子步数（100 tps）无关；物理负载导致快照被跳过时，事件率与推进同步下降，爆炸扩散以主线程 tick 为节拍。

> **实例年龄 `tickCount`**：每个爆炸实例自带一个从 0 开始的计数器，每次推进自增；`frontRadius` 与寿命都由它给出（§4.3、§4.8）。它与 `PhysicsLevel.tickCount` 同名但无关（后者按物理子步自增，不参与爆炸的任何计算），也不同于上面否掉的"待排队步数"计数器——那个用于补偿时间轴，这个只记录"已经推进了几步"，因此不依赖任何全局时钟。

**事件丢失时的行为**：物理线程过载 → 快照刷新变稀 → 事件变稀 → 爆炸扩散变慢。这是本设计唯一的降级路径，且**只影响表现节奏，不影响任何判定结果**——每步的推进距离、$I$、伤害都不变，只是发生的次数少了。

> **这条路径只由物理线程触发。** 主线程自身变慢不会让快照停止刷新（tick 被拖长时物理线程反而更从容），因此爆炸侧不设主线程方向的限流：单个爆炸的规模由 §4.7 的射线数自适应约束，并发规模由 §12.4 的最大实例数约束。

> **口径说明（贯穿全文）**：爆炸的推进单位是"**一次快照就绪事件**"。正常运行时一个主线程 tick 恰好对应一次推进，因此下文为便于叙述，凡称"每 tick"处均指**每次推进**；只有在物理线程过载、快照被跳过时二者才会分叉，而那时的行为已由本节规定（扩散变慢，判定不变）。

> **实现要求（给 Spark-Core）**：事件的 post 点必须放在 `requestStep()` 内部走完 `syncStructure` / `syncTransform` / `update` 之后，**不能**在 `mcLevelTask(LevelTickEvent.Pre)` 里无条件 post。原文那句"在 `syncTransform()` 之后触发"已经蕴含这一点，但接口上若再挂 `isSnapshotFresh` 字段，容易被实现成无条件触发。
>
> **不可替代性**：`PhysicsLevel.tickCount` 已存在且 `@Volatile` 主线程可读（`PhysicsLevel.kt:105-106`），在 `repeat(dynamicRepeat)` 内自增（`:156-158`），可作为步号使用；但它是 `Int`。既有的 `PhysicsLevelTickEvent.Post` **不是**等价钩子——它由 `PhysicsLevel.physicsTick` 触发（`PhysicsLevel.kt:405`），跑在**物理线程**、每子步一次（默认每 tick 5 次），且语义上与快照刷新无关。
>
> 该事件同时是未来"瞬时判定的光束"所需要的同一挂载点，属于一次性投入。

> **注意区分两件事**：上面的简化只涉及**逻辑时间**（不需计数、不需新鲜度标志）。§4.3 的**浮点累计推进距离**属于**几何**量，必须保留——每步推进 `advancePerStep`，跨体素时推进 DDA 游标。`advancePerStep` 与体素尺度只决定每 tick 跨几格（默认 `front_speed = 20 m/s`、20 tps 时为 1 m，约一格；低速爆炸或斜向射线则不足或超过一格）；若把它一并省掉，波前将无法按几何跨格推进。

### 3.5 快照的性质（对爆炸的三条含义）

`WorldSnapshot` 是一个**只读、主线程专用**的物理空间，内容为碰撞组落在 `CollisionGroups.SNAPSHOT_TRACKED` 中的已注册 `PhysicsRigidBody`；该集合当前为 `setOf(PHYSICS_BODY, PROJECTILE)`（`CollisionGroups.kt:72`）。对爆炸而言只有三条含义：

1. **地形永远不在里面。** 这不是缺陷而是前提：地形 section 的刚体只在"附近有刚体"时才激活并懒构建，而构建要付一次完整的体素形状化代价。为一次爆炸去唤起整片地形的构建，是"为了拿一个 `BlockState` 而付一整个形状化的钱"。区块 DDA 只触碰射线路径上的体素，成本低两个数量级。
2. **两个通道因此彻底解耦。** 对快照的 `rayTest` / `contactTest` 永远不会返回地形，成本是加法关系，不是每格都付两份钱。
3. **但"在快照里"不等于"是载具零件"。** 候选集里还会有实体刚体（其默认碰撞组就是 `PHYSICS_BODY`）与投射物的运动学触发体（碰撞组 `PROJECTILE`，属主是 `ProjectileHitBox`）。**必须按 `owner` 分派**（附录 A.2）。

> 完整的碰撞组归属表与 `owner` 分派规则见 **附录 A.1、A.2**。

### 3.6 地形读取的硬性约束

**主线程禁止使用 `terrainManager.getBlockSnapshotAt()` / `getSectionForBlockPos()`。** 主线程读方块只能走 Minecraft 自身的数据路径：

```text
ServerLevel → getChunk(x, z) → LevelChunk.getSection(yIdx) → LevelChunkSection.getBlockState(...)
```

这条路是安全的，因为**主线程就是区块数据的唯一所有者**。宽限期内未加载的区块视作空气。

> 为什么禁用那两个 API（以及为什么现有代码里的用法是错的），见 **附录 A.4**。

# 第二部分 · 传播模型（射线怎么走）

## 四、传播

### 4.1 一条射线 = 一份立体角

爆炸被离散为 `rayCount` 条从爆心射出的射线，方向用**种子决定的 Fibonacci 球**生成（确定性，客户端可复现）。每条射线的立体角份额固定为

$$
\lambda_r=\frac{\Delta\Omega}{4\pi}=\frac{1}{rayCount}
\qquad\Longrightarrow\qquad
\Delta\Omega=\frac{4\pi}{rayCount}
$$

**射线维护的是剩余能量比例** **$E_r$（初始 1.0），不是能量、也不是"每单位立体角的能量"。**

| 量              | 含义                    | 初始           |
| -------------- | --------------------- | ------------ |
| $E_r$          | 该射线**剩余能量比例**（相对自身初始） | $1.0$        |
| $\lambda_r$    | 该射线**占全空间的立体角份额**     | $1/rayCount$ |
| $E_r\lambda_r$ | 该射线**占爆炸总能量的比例**      | $1/rayCount$ |

$$
\sum_{\text{全部射线}}E_r\lambda_r=1
$$

**分工**：折减只碰 $E_r$，几何只碰 $\lambda_r$ 与 $d_r$，三者互不干涉。把两者压进一个数里（例如 $\varepsilon_r$）会立即产生"折减的到底是哪个量"的歧义，拆开写之后这个歧义不存在。

$\lambda_r$ 是**全局常数**（不随距离、遮挡、时间变化），因此**不需要存进射线对象**，只在需要它的那一个公式里现算（§8.2）。

抖动：方向用种子生成小幅抖动，避免出现对称的"星形"破坏图案（原版亦如此处理）。抖动必须在**推进之前**固定，不得在推进过程中重新随机，否则同一发爆炸不可复现。

### 4.2 射线状态

```java
/// 跨 tick 持久存在的传播射线
public final class BlastRay {
    // ===== 能量（本征量）=====
    float energy;                // E_r，剩余能量比例，初始 1.0；只被穿透折减

    // ===== 推进线索 =====
    float px, py, pz;            // 当前波前位置
    float dx, dy, dz;            // 单位方向（构造后不变）
    float distance;              // d_r，已飞行距离
    VoxelCursor cursor;          // DDA 游标：当前体素、下一跨越参数、步进符号、最近跨越面轴
                                 // （独立成小类，因为遍历器要与光束共享，见 §14.2）

    // ===== 交互 =====
    boolean interacting;         // false = E_r 低于 interactionCutoff，只推进、不再判定
    boolean alive;               // false = 越界或已被拦下，彻底结束

    // ===== 去重（生命周期级，不清空）=====
    // 混装三类目标标识，各用其自然键（见下文）：
    //   零件 HitBox → PenetrationKey(subPart, hitBoxId)   值语义
    //   方块        → BlockPos                            值语义
    //   一般实体    → Entity                              UUID 值语义
    Set<Object> struck;
}
```

**去重的粒度是"命中区域"，不是"零件"。** 同一个 `SubPart` 上的不同 `HitBox` 是**彼此独立的目标**——这是既有设计的原话：

```java
// SubPart.java:836-838
/**
 * 将三角形索引（碰撞检测结果）映射到对应的 HitBox id。
 * 不同 HitBox 具有独立穿透判定——击穿外装甲后仍可命中内部引擎等。
 */
```

因此一条射线可以在同一次爆炸里连续命中同一个 `SubPart` 的外装甲与内部引擎，两次独立判定、独立结算、独立折减。**这与 §9.5 的"每个去重键每 tick 至多一次"是同一件事**，不冲突。

**零件侧复用** **`PenetrationKey`**（`data class PenetrationKey(val owner: PhysicsHost, val zoneId: String?)`，`PenetrationKey.kt:17-20`）：`SubPart` 覆写 `getPenetrationZoneId()` 返回 `hitBox.getAttr().getId()`（`SubPart.java:842-845`），因此键天然落在 HitBox 粒度上。`hitBoxes` 是按名字索引的 `ConcurrentHashMap`（`SubPart.java:94`、`:827`），实例在一次运行内稳定，键的相等性可靠。

> **不要用** **`HitBox`** **本身当键**：`HitBox` 只有 `@Getter`、没有 `equals`/`hashCode`（`HitBox.java:12-13`），是 identity 语义，也无法令identifier相同的HitBox避免被重复判定。用 `PenetrationKey` 才是值语义。

**方块与实体不套** **`PenetrationKey`**：`PenetrationKey.owner` 是 `PhysicsHost`，而 `BlockPos` 不可能是 `PhysicsHost`——现有地形去重只能把方块坐标**冒充** `zoneId` 字符串塞进去（`ProjectileManager.java:1007`）。爆炸侧地形只走 DDA、不产生刚体，没有理由继承这个妥协，直接用 `BlockPos`（record）与 `Entity`（UUID）即可。

**去重的作用域是射线的整个生命周期**，不是单个 tick——这一点与投射物侧**完全一致**：现有实现的注释就写着"同一次飞行中，同一 (owner, zoneId) 不会被重复判定"（`ProjectileManager.java:138-140`），集合在投射物销毁时才清除（`:1794-1795`），`pendingPenKeys` 只是"命中帧无法确认结果"时的异步暂存（`:142-147`）。

> **为什么这里必须点名生命周期而不是"每帧"**：波前每 tick 前进 `advancePerStep`（= `front_speed / 20`），当它小于一个体素时（`front_speed < 20 m/s`），跨过一个方块要**若干个 tick**——同一个方块会在连续的 tick 里被同一条射线反复遇到。若把键只按"本帧命中"清除，同一个方块就会被重复结算数次，而结算次数取决于 `front_speed` 与 `voxelSize` 的比值；于是"方块受到的伤害"变成了表现层旋钮的函数。生命周期去重把这个依赖彻底切断。（投射物 200 m/s 时一帧就跨过 1 m 以上，同一个方块在生命周期内本就只会遇到一次，所以两种说法在投射物侧看不出差别，在爆炸侧才有差别。）

> **生命周期持有引用的代价**：`Set<Object>` 会跨 tick 钉住 `SubPart` / `Entity` 实例。爆炸寿命是秒级，可接受；但爆炸结束时必须随射线一并释放——射线组由 `ExplosionInstance` 持有（§14），`struck` 不得放进 `ExplosionManager` 级的容器。

### 4.2.1 关于 `struck` 的一个已知放宽

去重键以 `PenetrationKey` 为准，而它的 zoneId 是 **HitBox id**，比三角形索引粗。也就是说：同一条射线在板甲上擦过两个不同三角形仍算一次命中。

对本设计这是**刻意选择**——爆炸是广域效应，逐三角形区分没有物理意义，而且会让同一块装甲被波前反复"数"出多次命中，重新把结果绑到采样密度上。**投射物侧也是同样的粒度**，两侧一致。

### 4.3 推进规则

```text
advancePerStep = front_speed / 20          // 米/主线程 tick，默认 20/20 = 1.0 m
```

**每次推进同时把实例的 `tickCount` 自增 1**（§3.4）；`frontRadius` 与寿命都由它推出（§4.8）。

**每次快照就绪事件（§3.4）对每条 `alive` 射线推进一步：**

```text
起点 = (px, py, pz)
终点 = 起点 + 方向 × advancePerStep
distance += advancePerStep

若 distance > max_radius：alive = false，结束

若 interacting：
    ① 从当前 DDA 游标出发，遍历 [起点, 终点] 段内的体素
       遇到实体方块 → 登记（§六 的介质交互）
    ② 对 [起点, 终点] 段做一次快照 rayTest        ← 每 tick 一次，不是每格一次
       命中刚体 → 登记
    ③ 把 ① 与 ② 的结果合并成一条按距离升序的序列，顺次消费
       每消费一项：判定它是否拦下本射线
         被拦下 → alive = false，结束
         穿透   → 按 §八 折减 energy
    ④ 若 energy < interactionCutoff：interacting = false
否则：
    仅按方向推进位置（纯视觉，无 DDA、无 rayTest）
```

**为什么是"每 tick 一次 rayTest"而不是"每格一次"**：`rayTest` 是 native 调用，成本与"调用次数 × 空间遍历量"大致成正比。逐格调用会把调用次数放大到 `rayCount × advancePerStep` 倍而每次并不省多少。一次覆盖整段的调用在几何上是等价的（段是直的），而调用次数与体素步数解耦。**这条纪律是性能预算的前提**（§15.2）。

**合并与去重**：射线穿过一个 section 时，DDA（逐方块）与 `rayTest`（section 作为一个刚体、且地形不在快照里所以不会命中）可能对同一目标双重报告。合并序列时必须按 `BlockPos` / `HitBox` 去重，否则同一目标会被扣两次能量。

**裁剪范围**：`rayTest` 的段**必须裁剪到本 tick 的推进区间**，不能从爆心一路 cast 到 `max_radius`——否则会判定"波前还没到"的目标，语义就错了。

**要记的一条**：`interactionCutoff` 用**相对量**（$E_r$ 相对其实例初值），因此是**纯性能旋钮**，不参与任何平衡。

> **推进过程中只登记、不施加**：DDA 与快照判定产生的原始命中数据进入累加器，真正算出 $I$、施加伤害与冲量、以及摧毁方块都发生在"本 tick 所有射线推进完毕"之后（§7.4、§9.5）。这条时序是确定性与"每个去重键每 tick 至多一次"的前提。

### 4.4 介质交互总则

三条通道（§3.2）在一个 tick 内**并行收集、统一合并**：

```text
本 tick 对每条 interacting 射线：
    seq = merge_sort(
        DDA_voxels(seg),      // 地形：逐方块，携带精确 hitFraction 与面法线
        rayTest(seg),         // 快照刚体：已按 hitFraction 升序返回
        entityAabb(seg)       // 一般实体：AABB 与射线段求交，取进入 t 作为 hitFraction
    )
```

`CollisionSpace.rayTest` 返回**全部命中并已排序**（`CollisionSpace.java:553-560`：清空列表 → `rayTestNative` → `results.sort(hitFractionComparator)`），因此合并只需一次归并。

**必须保序**：地形与刚体在同一个 `hitFraction` 轴上竞争。若不合并、而是分两轮消费（先处理所有地形命中、再处理所有刚体命中），则"墙后的车"会先被刚体轮次命中、完全绕过地形的遮挡。这是本设计最容易写错的一处。

**实体通道同样要保序。** 一般实体（`PAWN` 等，不在快照）用 AABB 与射线段求交，取**进入 t** 作为 `hitFraction` 并入同一序列；实体不消耗射线能量、也不拦下射线（§8.4），因此只是序列里的“软目标”——若其前方已有方块/刚体把该射线拦下，序列消费到那里就终止，实体自然不会被结算。

**粗筛（性能）**：先排除"本 tick 根本够不到任何刚体"的射线，只有通过粗筛的射线才调用 `rayTest`。

```text
每 tick 每爆炸一次（主线程，直接查询快照）：
    球 = 以爆心为心、半径 = frontRadius + advancePerStep
    快照 contactTest(球, listener)            → 候选刚体集合 K
    把 K 各体的 AABB 读进 Java 侧缓存

逐射线（纯 Java 算术，无 native 调用）：
    射线段 AABB × K 中各体 AABB
    通过者才调用 快照 rayTest(本 tick 段)
```

**四条要点：**

1. **查询打在快照世界，不是主物理世界。** 快照对主线程是只读且独占的，直接调用即可，不需要 `submitImmediateTask` 排队。
2. **半径取当前传播距离 `frontRadius`，不是 `max_radius`。** 取 `max_radius` 会在候选集里塞满波前够不到的东西，粗筛就白做了。建议留 `advancePerStep` 的余量对冲快照滞后一步。
3. **逐射线粗筛必须是纯 Java 算术。** 若每条射线都回引擎查一次，等于把成本搬了个家——粗筛的价值就在于它每爆炸每 tick 只查一次。
4. **候选集不是同质的。** 里面可能是 `SubPart`，也可能是实体刚体或交互区。**必须按 `owner` 分派，不能假定是 `SubPart`**（附录 A.2）。

**粗筛只做排除，不做判定。** 我们手上只有一个个 AABB，没有引擎的 broadphase 结构，无法在 Java 侧复刻一次射线树遍历——因此"通过粗筛的射线，其射线-刚体求交仍交给 `rayTest`"。

> 为什么用快照的 `contactTest` 而不是 `PhysicsGhostObject` 的重叠列表，以及它的固有代价（会跑 narrow phase），见 **附录 A.3**。

### 4.5 逐段推进的登记时序

**推进期只登记，不施加。** 本 tick 全部射线推进完毕后，才进入结算：

```text
tick 开始
  ├─ 推进期：DDA + rayTest → 只往累加器里登记（谁、在哪个距离、E_r 多少）
  ├─ 结算期：算出每个目标的 I，施加伤害、冲量，标记待摧毁方块
  └─ 执行期：统一摧毁方块（§9.2）
tick 结束
```

这条时序同时保证三件事：确定性（不受遍历顺序影响）、"每个去重键每 tick 至多一次"、以及摧毁与世界修改的解耦。

### 4.6 射线数与物理无关（采样分辨率）

均匀方向集下，各射线的立体角份额为 $\lambda_r=1/rayCount$。在距离 $d$ 处穿过面积 $A$ 的目标时命中条数为 $rayCount\cdot A/(4\pi d^2)$，而单条射线的权重为 $1/rayCount$，两者相消：

> **$\mathbb{E}[\hat\Phi]=\Phi_{true}$，对任意** **`rayCount`** **成立。**

`rayCount` **只决定采样分辨率（几何与视觉精度）与性能开销，不参与物理平衡**。调它不会牵动数值：改变条数只改变估计的方差。这是爆炸系统最重要的一条工程性质——性能压力可以用一个纯性能参数缓解。

> **该性质成立的前提是"不做跨 tick 的时间积分"**：§9.2（摧毁）与 §9.5（施加）都按"每 tick 独立结算"设计，因此不存在"调慢波前 → 照射 tick 数变多 → 破坏更强"的隐藏通道。

### 4.7 射线数自适应

采样精度只需在**内半径附近**达标：那里是 `base_*` 的标定位置、也是效果最强的区域；远处效果本来就弱，稀疏采样的绝对误差可以忽略。因此自适应公式锚定 `near_radius` 而非 `max_radius`。

**但标定位置必须真的采得动。** 一个迎流面积为 $A$ 的目标在距离 $d$ 处的期望命中条数是

$$
\mathbb{E}[n]=rayCount\cdot\frac{A}{4\pi d^{2}}
$$

若要求"参考半径处 $1\ \mathrm{m^2}$ 的目标至少有 10 条射线命中"（否则 $n$ 太小，$1/\sqrt n$ 的涨落会让同一发爆炸的结果不可预期，且可能出现 $n=0$ 即"完全没记上伤害"）：

$$
rayCount\ \ge\ 10\cdot 4\pi\,near\_radius^{2}\ \approx\ 126\,near\_radius^{2}
$$

```text
rayCount = clamp(round(126 * near_radius^2), MIN_RAYS, MAX_RAYS)

near_radius = 2  →  504
near_radius = 3  →  1134
near_radius = 4  →  2016
```

> **射线数不可配置。** 它只由上式导出（`MIN_RAYS` / `MAX_RAYS` 是代码常量），内容包 JSON 里没有这个字段；客户端按同一公式重算即可，无需随包同步。

对照：在 `near_radius` 处一条射线占据的波前面积约为 $\pi\ \mathrm{m^2}$（射线间距约 1.8 m）。**"间距 ≈ 1 格"是个次要指标——真正要锚定的是"参考点处一个典型目标收到多少条射线"，因为那才是** **$I$** **的方差来源。** 前者只是后者的几何后果。

> **`n=0`** **不是"精度不够"而是一个真实漏洞**：此时 $\Delta E=0$，该目标本 tick 完全不吃伤害。舱盖铰链、天线、螺栓这类小件在参考距离处以相当高的概率长期零命中。提高 `rayCount` 是唯一的结构性解法。

> **射线数在生成时固定、终生不变。** 在爆炸生命周期内抽稀射线数会让同一发爆炸给出不同的破坏结果（§4.6）。

### 4.8 与视觉的耦合

`frontRadius(t)` 由已推进的距离换算，是逻辑层的直接产物：

```text
frontRadius = 已推进距离        // 或逐射线的统计中位数，视表现需要
```

客户端可仅凭 **起爆点 + 种子 + 参数集** 复现整条时间线，**无需逐条射线同步**——波前年龄由客户端自己从 0 起算。网络同步只发生在起爆事件本身。

# 第三部分 · 场的计算（$I$ 等于几）

## 五、能量在介质中的折减

### 5.1 介质消耗 $\eta$

$\eta$ 是**沿单条射线路径的传输效率**：方块用爆炸侧的 $A_{block}$ 公式（§8.2），刚体用 BF 送入的 $effPen$ 与 $rha$（§8.3）。两者各自逐段连乘到 $E_r$ 上：

$$
\eta\in(0,1],\qquad E_r\leftarrow E_r\times\eta
$$

- 真空中 $\eta\equiv1$；
- $\eta$ **只承担介质消耗，不承担几何衰减**（几何在 §6.2 的权重里）；
- 折减的对象是 $E_r$，而 $E_r$ 是**射线自身的状态**，因此它不影响"本方块处"的强度——只影响下游（§6.5）。

介质消耗的能量去向：$1-\eta$ 的部分被该方块/刚体吸收，以发热、变形与结构振动形式耗散，**不进入伤害判据**；伤害只由"该目标是否被击穿"以及击穿射线的能量之和决定（§7.2、§9.1）。

### 5.2 几何衰减与介质消耗是两个来源（不得叠加）

| 来源       | 承载者                 | 表现                               |
| -------- | ------------------- | -------------------------------- |
| **几何扩散** | $I$ 表达式里的 $d_r^{2}$ | 显式 $(near\_radius/d)^{2}$，可预期、可调 |
| **介质消耗** | $E_r$ 的连乘           | 墙后、板后、土中目标被削弱                    |

**两者各自只由一个因子承担，不得重复叠加。** 这是本设计最容易出错的纪律：把 $1/d^2$ 同时写进"逐射线的距离因子"和"命中条数"会让距离指数变成 4，且这种错误会随射线数变化而不易察觉。

## 六、场强折算

### 6.1 强度比 $I$：单条射线在自己命中点处的强度

爆炸系统对外的强度量只有一个——**归一化场强比**：

$$
\boxed{\ I=\frac{\Phi_{eff}}{\Phi_0}\in(0,1]\ }
\qquad
\Phi_0=\frac{1}{4\pi\,near\_radius^{2}}
$$

$\Phi_0$ 是该发爆炸**总能量**在 `near_radius` 处的场强；本设计把总能量固定为 $1$（§6.3），故它有上面这个数值。

$I$ 的语义是\*\*"相对于参考条件，这一点还剩下百分之多少的威力"\*\*：参考条件下 = 100%，12 米空旷处（`near_radius = 3`）≈ 6%，3 米处隔一道吃掉 60% 能量的墙 = 40%。

**它是逐射线求值的**：一条射线在它的命中点处的强度，由它自己的剩余能量与自己的命中距离给出（§3.1 的派生关系）：

$$
\Phi_r=\frac{E_r}{4\pi\,d_r^{2}}
\qquad\Longrightarrow\qquad
\boxed{\ I_r=\frac{\Phi_r}{\Phi_0}=E_r\left(\frac{near\_radius}{d_{eff,r}}\right)^{2}\ }
\qquad
d_{eff,r}=\max(d_r,\ near\_radius)
$$

**通量里没有 $\lambda_r$**：一条射线携带能量份额 $\lambda_r$，但它占据的立体角恰好是 $\Delta\Omega=4\pi\lambda_r$，在距离 $d_r$ 上摊开的面积是 $\Delta\Omega\,d_r^{2}=4\pi\lambda_r\,d_r^{2}$，两者相除得到 $\Phi_r=E_r/(4\pi d_r^{2})$——与如何离散无关。这既是 §4.6 要求的"不随 `rayCount` 变"，也是 §7.1.1 里那条射线足迹的来源。

**验算（$\Phi_0$** **的选取依据）**：取 $E_r=1$、$d_r=near\_radius$、`near_radius = 3`，

$$
I_r=1\cdot\left(\frac{3}{3}\right)^{2}=1\ \checkmark
$$

自由场里 $E_r\equiv1$，于是 $I_r=(near\_radius/d_r)^{2}$ 对任意 `near_radius` 都成立——**这同时说明了近场平台（$d_{eff,r}$ 的钳制）不是额外规则，而是这个式子的自然截断。**

### 6.2 逐射线求值：先各算各的，再求和

**一条射线命中一个目标时，先算它自己在命中点处的强度**——用自己的剩余能量 $E_r$ 和自己的命中距离 $d_r$：

$$
\Phi_r=\frac{E_r}{4\pi\,d_r^{2}}
\qquad\Longrightarrow\qquad
\boxed{\ I_r=E_r\left(\frac{near\_radius}{d_{eff,r}}\right)^{2}\ }
\qquad
d_{eff,r}=\max(d_r,\ near\_radius)
$$

$I_r$ 是**这一条射线**在该命中点处的相对强度，与命中条数无关。穿透判定用它（§8.1）。

**目标的总能量是所有命中射线各自的能量之和**：

$$
\Delta E=\sum_{r\,\text{被击穿}}E_r\,\lambda_r
\qquad\Longrightarrow\qquad
D=base\_damage\times\frac{\Delta E}{\Phi_0}
$$

（伤害公式里不出现面积：$\Delta E$ 是击穿该目标的射线能量之和，已随目标面积缩放，§7.2。迎流面积 $A$ 另由射线足迹给出，只服务于冲量，§7.1.1。）

**顺序为什么不能颠倒**（先把逐射线的几何与能量各自汇总成一个"目标平均强度"，再乘总面积）——三点理由：

**① 不同射线的命中距离不同。** $d_r$ 是射线自己的量，同一块大装甲板上，近侧的射线与远侧的射线 $d_r$ 可以差出好几倍。先把 $d_r^{2}$ 求和成一个总面积，等于假设板上所有点都在同一个半径上。

**② 不同射线的介质消耗不同。** 掩体把一部分射线吃掉、另一部分没吃到（§5.1），于是即使命中距离相同，$E_r$ 也不一样。**衰减本来就是逐射线的**，把 $E_r$ 先求和会把"谁被挡了"这件事抹平。

**③ 两者相乘的后果不是小误差。** 命中距离的跨度是"目标尺度 / 爆心距离"，衰减的跨度是"挡与没挡"。对一块斜置或部分被遮挡的大目标，只算一个平均 $I$ 会同时错在这两处。

> **穿透尤其必须逐射线。** 一块装甲的近侧与远侧应当给出不同的穿深，被遮挡的部分与暴露的部分更应当给出不同的穿深。**用一个全目标平均的 $I$ 去判穿透，会让"同一次爆炸打在板上的每一处穿深相同"** ——这与"斜置板被射线覆盖的投影面更小、沉积能量更少、伤害更低"（§7.1.1、§7.2）自相矛盾。
>
> **注意这不是"逐条相加 $I_r$"**：$I_r$ 只在**单条射线内部**使用（判穿透、算 $\eta_r$），永远不以 $\sum_r I_r$ 的形式进入任何判据。广延量求和的对象是**能量**，不是强度。

**为什么求和不改变"结果不随射线数变"这条性质**：`rayCount` 翻倍时每条 $\lambda_r$ 减半，而命中条数翻倍，$\mathbb{E}[\Delta E]$ 因此不变（§4.6、§4.7）。**逐射线求值反而让这条不变性更容易检验**——每个求和项都是显式的，没有藏在中间的除式里。

#### 6.2.1 遮挡直接由分子承担

$D=base\_damage\cdot\Delta E/\Phi_0$ **只有一个能量项，没有需要配平的面积分母**，因此遮挡的处理是直接的：

| 情形 | 该射线对 $\Delta E$ 的贡献 |
| --- | --- |
| 射线到达并**击穿目标** | $E_r\lambda_r$（该射线的入射能量份额） |
| 射线到达但**没打穿目标** | $0$（不计入，§7.5） |
| 射线被**更靠前的掩护**吸收、没到达目标 | 不登记（无命中），即 $0$ |
| 射线没朝这个目标去 | — |

被掩护吃掉的射线本来就不该贡献伤害，不登记即可。**伤害对遮挡因此单调递减**，不存在"多挡一层反而更疼"的退化——因为未被击穿的射线根本不计入 $\Delta E$（§7.5），遮挡只会减少"能击穿目标的射线"。

> **边界情形**：两条等能量、等距离的射线命中同一个 $1\ \mathrm{m^2}$ 目标（$A=1\ \mathrm{m^2}$），其中一条的路径上有一块掩护、另一条畅通。取 $d=near\_radius$，则目标应收的总能量为 $\Phi_0$，两条射线各占一半 $\Phi_0 A/2$；被掩护的那条几乎被吃光（$E_r\to0$）而无法击穿，故只有畅通的一条计入，$\Delta E=\Phi_0 A/2$：
>
> $$D=base\cdot\frac{\Phi_0 A/2}{\Phi_0}=0.5\,base$$
>
> 与"一半暴露"完全一致。

### 6.3 模型是标度无关的

**把一发爆炸的所有射线能量同时乘任意常数** **$\lambda$，模型的任何输出都不变。** 因为：

- $\eta$ 的折减是**比例式**（§8.2 的 $(A_{pen}/(A_{pen}+A_{block}))^2$）、不是减法式，因此与绝对能量无关；
- $I$ 是比值：$\Phi_0$ 就是**该发爆炸总能量**在参考距离处的场强，与分子中的能量同标度，因此公共缩放被约掉；
- 唯一会拿绝对能量做比较的是射线失活阈值。本设计把它定义为**相对于射线初值的比例**（§4.3 的 `interactionCutoff`），因此这个阈值是纯性能旋钮，不参与平衡。

所以绝对能量在模型里处处被约掉。本设计据此把它固定：**总爆炸能量** **$\equiv1$，即** **$E_r$** **的初值为** **$1.0$、全部射线满足** **$\sum E_r\lambda_r=1$。** 由此得到三个好处：

1. **内容包参数里没有任何能量量纲**。作者只需给四个数：`base_damage`（单位面积伤害）、`base_penetration`（mm）、`base_impulse`（单位面积冲量）、`near_radius`（m）。全部是可直觉校验的量（注意 `base_penetration` 是**强度量**，不带"每单位面积"，见 §7.1）。
2. **弹种不必"先想清楚装药多少焦耳"**。真实的焦耳数在游戏里从来没有可观测量与之对应，硬填只会制造"这个数该填多大"的伪问题。
3. **"衰减快慢"不是爆炸侧的旋钮**。直觉上它像是该跟"爆炸当量"放在一起，其实它属于材料侧（方块护甲 / 刚体 RHA 与爆压的比值）——那才是它该在的地方。

> **物理注脚**：§6.6 的 $r\approx1.6\sqrt{W[\mathrm{MJ}]}$ 给出的是 `near_radius` 应取 2–4 m 的**依据**，而不是一个要填进 JSON 的字段。想标注真实当量的作者可以写进 `tooltip`，它不影响任何计算。

### 6.4 近场平台

$d_r\to0$ 时 $I_r=(near\_radius/d_r)^{2}$ 会发散（贴脸 0.5 m 就是 36 倍），必须钳制。由 §6.1 的闭式，钳制就是取

$$
\boxed{\ I_r=E_r\left(\frac{near\_radius}{d_{eff,r}}\right)^{2}\ }
\qquad
d_{eff,r}=\max(d_r,\ near\_radius)
$$

等价写法更好读：**内半径以内，该射线给出的强度恒等于参考值（在无介质消耗时）**。

**平台是逐射线的，各自用自己的 $d_r$。** 这很重要：同一个目标上不同射线的命中距离不同（§6.2 理由①），若共用一个平台因子，就会把"近侧已进入平台、远侧还没进入"这种情形抹平。

**平台只作用在几何上，不作用在** **$\eta$** **上。** $\eta$ 已经在 $E_r$ 里了，照常逐段累乘；钳制只改分母的 $d_r$。因此**内半径以内隔着钢板的目标依然只拿到衰减后的能量**——这是掩体在近场仍然生效的原因，也是最容易漏掉的一处。

`min(1,·)` 的代价是"贴脸引爆"不会比站在 `near_radius` 上更疼。这是刻意的取舍：

- 平方反比在 $d_r\to0$ 时发散，若不加钳制，贴脸目标会吃到天文数字的伤害；
- 现实中近场本来就是"爆轰产物直接作用"而非冲击波，与远场不是同一套机制：理想气体关系 $\Delta p\approx(\gamma+1)\Phi$ 的前提是强激波且 $\gamma$ 恒定，而贴脸时激波还在爆轰产物里传播、$\gamma$ 在变、甚至尚未形成激波。**用平台截断比硬算发散值更接近实际**；
- 从游戏性看，内半径范围内伤害基本一致也让"近距离命中"有确定的手感预期，而不是对距离极其敏感。

若将来要让近场更狠，把 $\max(d_r,near\_radius)$ 换成带宽限的连续函数（例如 $\max(d_r,\ near\_radius\cdot d_r/(d_r+r_0))$）即可，不影响其他部分。

### 6.5 强度在哪个时刻取值（避免循环）

**$I_r$** **用射线传播到命中点时的条件计算，不受本次穿透结果影响。**

折减作用在"穿过之后"的能量上（下游会看到更低的 $E_r$），但不会回头改变"进入时"的 $I_r$——否则会形成"折减多少取决于折减多少"的循环。这与物理一致：作用在该目标上的爆压由它**入射侧**的场强决定。

对方块而言，$I_r$ 取射线进入该方块**入射面处**的值；折减产生的 $E_r$ 下降只对下游生效。

### 6.6 物理注脚：为什么爆炸的穿深不该给大

按真实爆轰的数量级校核，取理想气体近似 $\Delta p \approx (\gamma+1)\Phi$（$\gamma = 1.4$），则 50% 致死超压（约 0.35 MPa）对应

$$
\Phi_{50\%} \approx \frac{0.35\ \mathrm{MPa}}{2.4} \approx 1.46\times10^5\ \mathrm{J/m^2}
$$

即 $0.146\ \mathrm{J/mm^2}$——而 20 mm RHA 的破碎阈值恰好在 $0.14$–$0.28\ \mathrm{J/mm^2}$ 量级。由此得到裸装药的装甲破坏半径

$$
r \approx 1.6\sqrt{W[\mathrm{MJ}]}\ \text{米}
$$

3 MJ → 约 2.8 m，8 MJ → 约 4.5 m。这与"高爆弹只在极近距离靠爆压伤甲、更远处靠破片"的现实一致，也解释了为什么 `near_radius` 取 2–4 m 量级是有物理依据的——**`near_radius`** **就是"爆压还能伤甲"的那个界限**，而 `base_penetration` 就是这条界限上的穿深。

**给内容包作者的直觉**：不要在爆炸上填几百毫米的穿深。爆炸的穿甲能力天生很短程，远距离的杀伤应当由破片战斗部（后续设计）承担，而不是把爆压穿深调大。

> 注意：本节的 $\Phi$ 是**真实能量密度**（$\mathrm{J/m^2}$），而 §6.1 的 $\Phi_0$ 在"总能量 $\equiv1$"的归一化下是 $\mathrm{m^{-2}}$ 量级。两者只差一个总当量因子，本节的换算给出的是 `near_radius` 的取值依据，不进入任何公式（§6.3）。

### 6.7 采样方差（已知代价）

伤害的**期望正确，但存在方差**。方差有两个来源：

**① 不同射线到达目标时其剩余能量 $E_r$ 的差异。** 每条射线沿途经过的掩护不同，$E_r$ 是各自折减后的结果；遮挡得越碎，参与采样的射线之间 $E_r$ 差别越大。真空中所有 $E_r$ 相同，结果逐次精确——**爆炸在空旷处的表现是可预期的，不会出现"同一发炸同一点伤害不同"的抖动**。

**②** **$n$** **太小时的方差。** 逐射线的 $I_r$ 与每条射线携带的能量都无偏（§4.6），$\mathbb{E}[\Delta E]$ 也不随 `rayCount` 变；$n$ 小的问题是**方差**——估计值在 $0$ 与数倍均值之间摆动，$n=0$ 时该目标本 tick 完全不吃伤害。

因此**不要指望通过跨 tick 积分来降方差**：§9.2 与 §9.5 都按"每 tick 独立结算"设计，一个去重键在波前扫过的若干个 tick 里会各自独立地结算一次。**提高** **`rayCount`** **是唯一的解法**，而 §4.7 的公式已经按"参考半径处 $\mathbb{E}[n]\ge10$"标定过。

# 第四部分 · 终点效应

## 七、终点效应总则

### 7.1 三个量的量类

| 终端     | 公式（大小）                              | 量类      | 乘面积吗 |
| ------ | ----------------------------------- | ------- | ----- |
| **穿深** | $A_{pen}=base\_penetration\times I_r$ | **强度量** | ❌     |
| **伤害** | $D=base\_damage\times\dfrac{\Delta E}{\Phi_0}$ | 广延量     | ✅     |
| **冲量** | $J=base\_impulse\sum_r A_r\sqrt{I_r}$，$A_r=\Delta\Omega\,d_r^{2}$ | 广延量     | ✅     |

其中 $A_r=\Delta\Omega\,d_r^{2}$ 是**单条射线的足迹**、$A=\sum_rA_r$ 是总迎流面积（§7.1.1，仅冲量使用），$A_{pen}$ 是**有效穿深**（mm），$\Delta E$ 是被击穿射线的沉积能量之和，$I_r$ 是该射线在自己命中点处的强度（§6.1），$D$ 是伤害，$J$ 是冲量大小。

> **伤害的"✅ 乘面积"由 $\Delta E$ 承担，不由公式里的因子承担。** $\Delta E$ 是击穿该目标的射线能量之和，目标迎流面积翻倍它就翻倍，所以 $D$ 随之翻倍，公式里不需要（也不允许）再出现面积项。理由见 §7.2。

**三者的求值顺序不同，这不是笔误**：

- **穿深逐射线算**，用的是**这条射线自己**的 $I_r$（§6.1）；
- **伤害与冲量按去重键汇总**，用的是**全部命中射线**的能量之和。

理由见 §6.2：不同射线的命中距离与介质消耗都不同，把强度平均掉会同时错在这两处。三个量各自怎么落到具体目标上，见 §八\~§十。

**标定条件就是** **$I=1$**：在 `near_radius` 处、无介质消耗、射线群完整覆盖目标，且目标**被完全击穿**。三个终端的标定量共用这一条约定，这一句把全部标定收在一处。

> **"每单位面积"只属于伤害与冲量，不属于穿深。** 穿深是**强度量**：能不能打穿一块钢板取决于作用在它上面的压强，与钢板多大无关（把钢板扩大十倍，穿深不变）。所以 `base_penetration` 的单位就是 **mm**。

| 字段                 | 语义                                                           | 量类  | 建议默认     |
| ------------------ | ------------------------------------------------------------ | --- | -------- |
| `base_penetration` | `near_radius` 处、无介质消耗时的穿深（mm）                                | 强度量 | 必填       |
| `base_damage`      | `near_radius` 处、无介质消耗时、**每** **$1\ \mathrm{m^2}$** 迎流面积被完全击穿时所受到的伤害 | 广延量 | 必填       |
| `base_impulse`            | `near_radius` 处、无介质消耗时、**每** **$1\ \mathrm{m^2}$** 迎流面积受到的冲量 | 广延量 | 必填       |
| `near_radius`      | 参考距离，三个标定量的公共参考点；**同时是近场平台半径**                               | —   | 建议 2–4 m |
| `max_radius`       | 硬截断半径（射线推进终点）                                                | —   | 必填       |
| `front_speed`      | 波前推进速度（m/s）                                                  | —   | **20.0** |

### 7.1.1 迎流面积是逐射线足迹之和

冲量逐射线用到每条射线的足迹 $A_r$，它们的总和就是迎流面积：

$$
A_r=\Delta\Omega\,d_r^{2}=4\pi\lambda_r\,d_r^{2},
\qquad
A=S_w=\sum_rA_r
$$

$A_r$ 是一条射线携带的立体角 $\Delta\Omega$ 在距离 $d_r$ 处摊开的面积，只由该射线自己的 $d_r$ 给出；因此 $A$ 是射线推进的副产物，不需要从 `HitBox` 或 AABB 另推截面（§10.1 会逐项用到 $A_r$）。伤害完全不使用面积（§7.2）。

理由有两条：

**① 它就是能量真正穿过的那个面积。** 一条射线携带能量份额 $\lambda_r$，摊在面积 $\Delta\Omega\,d_r^{2}$ 上（§6.1）；把命中射线的足迹求和，得到的正是"这些射线共同覆盖了多大一片迎流面"。

**② 它的物理含义正对。** 射线自爆心向外，因此 $S_w$ 就是目标**朝向爆心的投影面积**——目标截面积为 $A_t$、法线与爆心方向成 $\theta$ 角时 $S_w=A_t\cos\theta$（正面命中即 $A_t$）。几何估算（从 `HitBox` 或 AABB 推一个截面）不仅麻烦，而且算出来的是另一个量（法向截面），在斜置目标上会有系统性偏差。

**由此，三类目标的面积取法完全一致**，差别只剩"怎么发现被命中"：

| 目标 | 怎么发现命中 | 单条射线的足迹 |
| --- | --- | --- |
| 方块 | 3D DDA 逐体素 | $A_r=\Delta\Omega\,d_r^{2}$（正面命中一个方块面时 $\sum_rA_r\approx1\ \mathrm{m^2}$） |
| 快照刚体 | 粗筛 + `rayTest` | **同左** |
| 一般实体 | AABB 相交 | **同左** |

> **伤害不使用面积。** 伤害公式 $D=base\_damage\cdot\Delta E/\Phi_0$ 里没有面积项（§7.2）；面积只服务于 §十 的冲量，而且是**逐射线**使用 $A_r$，不需要先求总和。
>
> **一条射线都没命中时** $\Delta E=S_w=0$，不产生伤害与冲量（§4.7）。

### 7.2 伤害是能量比，不乘也不除面积

`base_damage` 的完整读法是：**参考内半径处、无遮挡、参考面积 $1\ \mathrm{m^2}$ 的板被完全击穿时所受到的伤害**。它不是"爆炸的基础伤害"，也不是某个目标的伤害值。

$$
D=base\_damage\times\underbrace{\frac{\Delta E}{\Phi_0}}_{\text{能量比}}
$$

$$
\Delta E=\underbrace{\sum_{r\,\text{被击穿}} E_r\lambda_r}_{\text{击穿该目标的射线能量之和}},
\qquad
\Phi_0=\underbrace{\frac{1}{4\pi\,near\_radius^{2}}}_{\text{每 }1\ \mathrm{m^2}\text{ 的参考能量}}
$$

**面积已经含在 $\Delta E$ 里**：$\Delta E$ 是击穿该目标的射线能量之和，命中面积越大、能击穿的射线越多，它就越大；在射线群完整覆盖且全部击穿的极限下等于 $\Phi_{local}\cdot A$，因此 $\Delta E/\Phi_0=I\cdot A$——面积只通过 $\Delta E$ 出现这一次。

**量纲自检**：能量在本模型里无量纲（$\equiv1$，§6.3），所以 $\Phi_0$ 带的是 $\mathrm{m^{-2}}$，$\Delta E/\Phi_0$ 是**以平方米为单位计的能量**；`base_damage` 的单位是 伤害·$\mathrm{m^{-2}}$，两者相乘正是伤害点数：

$$
\underbrace{\frac{\Delta E}{\Phi_0}}_{\mathrm{m^2}}\times\underbrace{base\_damage}_{\text{伤害}\cdot\mathrm{m^{-2}}}=\text{伤害}
$$

**$\Delta E$ 自带面积，所以公式里不出现 $A$。** 击穿能量随目标面积缩放：面积翻倍 ⇒ 命中条数翻倍 ⇒ $\Delta E$ 翻倍，于是 $D$ 也翻倍——伤害是广延量：

$$
\text{面积翻倍}\Rightarrow\Delta E\text{ 翻倍}\Rightarrow D\text{ 翻倍（总伤害翻倍）}
$$

反过来说，再把 $A$ 乘进去就重复计了面积，再除以 $A$ 又把面积抵消掉，两者都不是期望行为。这正是 §7.1 表格里"伤害是广延量"的实现方式。

**`rayCount` 不进入结果。** $\mathbb{E}[\Delta E]$ 与射线数无关（§4.6）——每条射线各自无偏，命中概率恰好补偿了它携带的份额 $\lambda_r$：

$$
\mathbb{E}[\Delta E]=\sum_r\frac{1}{rayCount}\cdot\frac{A\cos\theta}{4\pi d^{2}}=\frac{A\cos\theta}{4\pi d^{2}}
$$

采样稀疏影响的是**方差**与 $n=0$ 的概率（§4.7），不是 $\Delta E$ 的期望，因此 `rayCount` 保持为纯性能旋钮。

**标定**：在 `near_radius` 处、无介质消耗、参考面积 $1\ \mathrm{m^2}$ 的板被射线群完整覆盖并**完全击穿**时（$\cos\theta=1$、所有命中射线 $E_r\equiv1$），$\Delta E=\Phi_0$，于是 $D=base\_damage$。

三条必须记住的性质：

1. **先求和再相除**。$\Delta E$ 是求和，除以 $\Phi_0$ 才是与标定口径一致的量；
2. **强度量不带面积、广延量带面积**。$A_{pen}$ 不含 $A$（把钢板放大十倍不会更难击穿）；$D$ 与 $J$ 随面积缩放，其中 $D$ 的面积由 $\Delta E$ 自带，$J$ 则显式乘 $A$（§10.1）；
3. **$n$** **足够大时能量比收敛到连续值** $\Phi_{local}/\Phi_0$，离散采样的作用只是估计这个比值。

**作者手上的三个旋钮各管一件事，互不干扰：**

| 想改什么        | 改哪个参数                                                        |
| ----------- | ------------------------------------------------------------ |
| 伤害高低        | `base_damage`（直接线性）                                          |
| 击退强弱        | `base_impulse`（直接线性）                                                |
| 能击穿多厚的装甲    | `base_penetration`                                           |
| **穿墙后还剩多少** | **不改爆炸，改材料**——$\eta$ 由爆压与护甲的比值决定（§8.2），因此这是方块护甲 / 刚体 RHA 侧的事 |

这正是"能量不直接决定伤害"这句话的极端形式：**这个模型里根本没有能量这个旋钮。**

### 7.3 为什么摧毁必然伴随击穿

穿透是伤害的**门控**：只有击穿才进入伤害结算。因此

> **只要方块被摧毁，必然是被击穿过。**

这条是**结构性**的，不需要额外写一条规则来保证穿透判据与摧毁判据一致。

### 7.4 统一登记 → 结算 → 施加

```text
推进期   对每个命中：把 (去重键, 射线, 命中点, 法线) 登记进累加器
         去重键 = 零件的一个 HitBox ／ 一个方块 ／ 一个一般实体（§4.2）
         同一射线对同一去重键只登记一次（生命周期去重，§4.2）

结算期   对每个去重键：                        ← 顺序不可颠倒
         ① 逐射线求各自命中点处的强度
                I_r = E_r · (near_radius / d_eff,r)²   §6.1
         ② 逐射线判穿透并折减
                A_pen = base_penetration × I_r
                方块：与 A_block 比较；BF 目标：调 resolvePenetration(ctx)
                拦下则该射线终止；击穿则该射线按 η_r 折减（§八）
         ③ 汇总，得到广延量
                ΔE  = Σ_击穿 E_r·λ_r                 // 伤害的分子（被击穿射线的能量和）
                A_r = ΔΩ · d_r²                       // 单条射线的足迹
                D   = base_damage × ΔE / Φ_0
                J   = base_impulse × Σ_全部命中 A_r·√I_r        §10.1（逐射线求和）
         ④ 施加：每个去重键调一次 BFDamageApi.hurt（D 作 ctx.baseDamage、J 作 IMPULSE；D=0 时也调用以投递冲量）

执行期   统一摧毁被标记的方块（§9.2）
```

**第 ①② 步逐射线、第 ③ 步按去重键汇总**——这个分工是 §6.2 那三条理由（命中距离不同、介质消耗不同）的直接结果，不是为了性能。

> 同一个 `SubPart` 的多个 HitBox 会产生**多条独立记录**，各自结算——这正是"击穿外装甲后仍可命中内部引擎"所要求的（§4.2）。

### 7.5 未击穿目标的处理

| 被拦下的射线 | 处理                                        |
| ------ | ----------------------------------------- |
| 能量去向   | **全额沉积在该目标上**（$E_r\to0$）。判据已是二值的，沉积也应是二值的 |
| 伤害     | **不产生**（未击穿 = 没有伤害，§7.3）                  |
| 冲量     | **照常产生**。被拦下时能量几乎全部转为板的动能，这恰好就是 $J$       |
| 射线     | `alive = false`，终止                        |

> **为什么冲量与是否击穿无关**：若按是否击穿切换冲量公式，会在穿透阈值处产生**冲量不连续**（阈值一侧突然降档），这是必须避免的非物理跳变。统一的代价是击穿时略微高估板的冲量——可接受的近似。
>
> 注意"全额吸收"与"不产生伤害"并不矛盾：被拦下的能量去了发热、变形与结构振动，**不计入 $\Delta E$**（$\Delta E$ 只累加被击穿射线的能量，§9.1），因而不进入 §九 的伤害结算。

## 八、穿深

### 8.1 通用规则

**穿透判定是二值的，且逐射线进行。两条判定通道：**

```text
A_pen = base_penetration × I_r        // 有效穿深，强度量（I_r 是该射线自己的命中点强度）

方块    ：A_pen 与 A_block 比较                          → 爆炸侧自管（方块不是 BFHurtTarget，§8.2）
BF 目标 ：ctx.penetration(A_pen) → resolvePenetration(ctx) → PENETRATED / BLOCKED / RICOCHET（§8.3）
```

- **逐射线判**：每条射线用**自己的** $I_r$（自己的 $E_r$、自己的 $d_r$，§6.1）。一块装甲的近侧与远侧、被遮挡处与暴露处因此会得出不同结论——这正是物理上应有的行为（§6.2）。
- **BF 目标不自行比对装甲**：判定权归目标侧的 `resolvePenetration`（它内部才调 `modifyPenetration` / `getRHA` 与跳弹判定）。爆炸侧只负责把 $A_{pen}$ 写进 `ctx.penetration` 并读取结果。
- 这个判据**不会变成采样密度的函数**：$I_r$ 由几何与局部场强决定，与有多少条射线命中无关；`rayCount` 变化时改变的只是“目标上被采样了多少个点”，不是每个点上的强度值。
- **保守截断**：一条射线被某目标拦下即终止，不做“绕射”或“部分穿透”。这保证“掩体能不能挡住这次爆炸”是确定的，玩家可以建立可靠直觉。
- **纯判定，无副作用**：`resolvePenetration` 只读 `ctx`，因此“逐射线判定”不会与 §9.5“每去重键每 tick 一次施加”冲突；施加仍走一次 `BFDamageApi.hurt`（§9.3）。

> **残余能量 $\eta$ 仍由爆炸侧给出**：BF 只回答“穿没穿”，不回答“还剩多少”。方块用 §8.2 的 $A_{block}$ 式，刚体用 §8.3 的 $effPen/rha$ 式。两者都是**连续折减**，与判定结果正交——BLOCKED / RICOCHET 的射线直接终止（$\eta$ 用不到），PENETRATED 的射线按对应 $\eta$ 折减 $E_r$ 供下游。

### 8.2 方块

**方块不是 BFHurtTarget，因此判穿与折减都由爆炸侧自管。** 方块护甲 $A_{block}$ 复用 `ArmorUtil.getBlockArmor` 的公式形状（已配平，无需重新拟合）：

```text
材料因子   M = 100 · log10(爆炸抗性 + 1) · log10(硬度 + 1.001)

方块护甲   A_block = k_armor · M
```

（实现即 `ArmorUtil.java:105` 的原式，只是乘一个爆炸侧系数。）

保留同一形状的理由：

1. 它**只对"会挡住东西的方块"产生非零值**——空气与无碰撞形状的方块会被射线遍历直接跳过，不参与判定，因此"抗性 0 → 护甲 0"这个边界不需要额外处理；
2. 形状已配平，内容包现有数值不用重做；
3. 它同时含爆炸抗性与硬度——挡不挡得住本来就同时取决于"多难炸"与"多硬"。

**能量折减**：爆压对材料的作用本质是**法向压力**，不存在斜入射跳弹，因此方块护甲的等效入射角恒为 0（垂直于面，§8.3），等效因子恒为 1：

$$
\boxed{\ \eta=\left(\frac{A_{pen}}{A_{pen}+A_{block}}\right)^{2}\ }
$$

| $A_{pen}/A_{block}$ | $\eta$ | 破折点式 $1-A_b/A_p$ |
| ------------------- | ------ | ---------------- |
| 0.1（护甲远强）           | 0.8%   | —                |
| 1.0（临界）             | 25%    | 0                |
| 10                  | 83%    | 90%              |
| 100                 | 98%    | 99%              |

三条性质：

- **护甲够不到 → 比值趋近 0 → 剩余能量趋近 0**，射线自然终止。这正是"拦下"的物理表达；
- **护甲很小（泥土、沙、树叶）→ 剩余能量几乎全额**，波前基本不受影响；
- **穿深远超护甲 → 折减很小**；**刚好超过护甲 → 折减很大**，符合"刚好击穿"的物理行为。

> **为什么用这个形式而不是** **$\eta = 1 - A_{block}/A_{pen}$**：后者是破折点形式，在 $A_{pen}$ 略大于 $A_{block}$ 时给出"剩余能量 ≈ 0"，即**刚好击穿的一瞬间射线反而几乎过不去**，数值上出现凸起。上面的形式单调、平滑、无凸起，且在 $A_{pen}\gg A_{block}$ 时展开为 $1 - 2A_{block}/A_{pen}$，与破折点形式**一阶一致**。

**$k_{armor}$** **待标定**：`getBlockArmor` 的返回值是配平在"投射物穿深（mm）"尺度上的（石头约 105，黑曜石约 209）。爆炸侧要与 `base_penetration`（mm，默认量级几十）比较，因此 $k_{armor}$ 会是一个远小于 1 的系数。标定目标：**石头应当挡住中等装药的爆炸、泥土应当被穿透**。

### 8.3 刚体

**判定交给 BF，爆炸侧不自行比对装甲。**

```text
A_pen = base_penetration × I_r
ctx.penetration(A_pen); ctx.hitNormal(射线方向的反向); ctx.hitVelocity(射线方向)   // 入射角恒 0
result = subPart.resolvePenetration(ctx)                                // PENETRATED / BLOCKED / RICOCHET
eta    = (effPen / (effPen + rha))²
         effPen = subPart.modifyPenetration(ctx)                        // 内含 hitBox.modifyPiercing
         rha    = subPart.getRHA(ctx)                                   // HitBox.getRHA，只含耐久衰减
```

- **入射角恒为 0。** 爆压对装甲是法向压力，无斜入射跳弹。实现上把 `ctx.hitNormal` 取射线方向的反向、`ctx.hitVelocity` 取射线方向（非零模长），于是 `SubPart.resolvePenetration` 中的 `impactAngleDeg = acos|n·v| = 0`，`ArmorUtil.shouldRicochet` 在 ≤45° 直接返回 false——**跳弹恒不发生且结果确定**（`Math.random` 分支不可达），护甲侧无需改动。
- **`HitBox.getRHA` 只含耐久衰减项**（`HitBox.java:85-89`）：
  ```java
  rhaCoeff = decay_rha + (rha − decay_rha) · durabilityRatio^decay_power
  return thickness · rhaCoeff
  ```
- **命中框靠扩展传递。** `SubPart.findHitBox(ctx)` 先读 `MMDamageExtensions.HIT_BOX`（`SubPart.java:613-618`），读不到才回退“最厚装甲”。逐射线判定时必须把该射线的命中框写进扩展，否则会命中错误区域。
- **三角形索引 → HitBox**：`SubPart.getHitBox(int)`（`SubPart.java:811-822`）/ `getHitBox(long)`（`:824-832`）。其参数是**子形状序号**而非三角形序号，对简单凸包形状两者一致。**去重键的生成走 `PenetrationKey.fromCollision`（§4.2），两者不要混起来**。
- **能量折减**：判定为 PENETRATED 的射线按 $E_r\leftarrow E_r\times\eta$ 折减后继续传播；BLOCKED / RICOCHET 直接终止。$\eta$ 用上面的 $(effPen/(effPen+rha))^{2}$，与方块式同形，只是输入换成 BF 的两个真实量。
- **不施加入射角修正**：按 `ArmorUtil.getEquivalentArmor` 的定义角（速度方向与装甲法线夹角）衡量等效入射角恒为 0，故不乘 $1/|\cos\theta|$。斜置装甲被射线覆盖的投影面已随 $\cos\theta$ 缩小（§7.1.1），这份倾角效应在 $\Delta E$ 里已经计入（§9.3）——再乘 $1/|\cos\theta|$ 属于重复计入，且方向相反（把斜置板算得更硬）。
- **两个未接线 API 与爆炸无关**：`ArmorUtil.getEquivalentArmor(armor, angle)`（`ArmorUtil.java:93-96`）与 `HitBox.hasAngleEffect()`（`HitBox.java:119-121`）**全仓库无调用点**；项目中入射角效应的实际落点在投射物管线层（`BallisticProjectile.java:1104-1110` 的 LOS 视厚度、`MMPartEntity.java:269`），爆炸路径不调用这两者。
- **法线来源**：`rayTest` 返回的 `getHitNormalLocal`，或 DDA 跨越面轴（`lastNormalAxis`）；但**逐射线判定时统一覆盖为射线方向的反向**（见上），真实几何法线只用于冲量的“法线均值”（§10.3）。

### 8.4 一般实体

生物/玩家（`PAWN`）不在快照里，用主线程 AABB 相交发现命中（§3.2）；命中点取 AABB 与该射线段求交的**进入 t**，并入与 DDA / `rayTest` 同一条按 `hitFraction` 排序的序列（§4.4）。

**穿透与伤害都交给 BF**，爆炸侧不自行计算等效装甲：

```text
ΔE = Σ_到达该实体的射线 E_r·λ_r        // 实体不延续传播，故按“到达”计，不按“击穿”计
D  = base_damage × ΔE / Φ_0
BFDamageApi.hurt(entity, ctx)          // D 作 ctx.baseDamage
```

- **普通实体（非协议感知）**：BF 走原版分支，直接 `entity.hurt(source, D)`，护甲、附魔、药水效果由原版链条处理——因此不需要 `k_entity_armor / k_entity_toughness` 之类的等效装甲。
- **戴 BF 护甲的实体**：BF 走 adapter 分支，按护甲侧规则判穿与定稿。
- **实体不延续射线传播**：折减不作用于实体（$E_r$ 的折减只对下游方块/刚体有意义），因此 $\Delta E$ 对实体按“到达”计。
- **命中遮挡**：实体命中必须在序列里按 $t$ 排序消费——若其前方已有方块/刚体把该射线拦下，则该实体不计入（§4.4）。

> **TODO（未来）**：实体应当能阻挡爆炸——穿深不足的射线被实体吞掉，从而削弱其身后的目标。本阶段刻意不做：实体不在快照里（只有 AABB 求交），要做到这一点需要给实体一套等效装甲（投射物侧的 `computeEntityEffectiveRha` 是形状参考），并把实体从"序列里的软目标"改成能终止射线的目标；届时应连同 §4.4 的保序消费与 §9.5 的施加纪律一起改。

## 九、伤害

### 9.1 通用规则

**伤害是广延量**，三个目标类型共用同一个基准伤害 $D$：

$$
\boxed{\ D=base\_damage\times\frac{\Delta E}{\Phi_0}\ }
\qquad
\Delta E=\sum_{r\,\text{被击穿}}E_r\,\lambda_r
$$

**逐射线求值、按去重键汇总**（§6.2）：每条被击穿的射线贡献其入射能量份额 $E_r\lambda_r$，求和即该去重键收到的总能量 $\Delta E$；再除以参考场强 $\Phi_0$，得到与标定口径一致的伤害。目标面积对伤害的影响已经含在 $\Delta E$ 里（§7.2），不需要单列面积因子。

| 目标           | 怎么发现命中        | 穿透判定                              | 最终伤害                                          |
| ------------ | ------------- | --------------------------------- | --------------------------------------------- |
| 方块           | 3D DDA 逐体素   | 爆炸侧比 $A_{block}$                  | $blockDamageFactor\times D>\texttt{getMaxBlockDurability}$（§9.2） |
| 刚体 `SubPart` | 粗筛 + `rayTest` | `subPart.resolvePenetration(ctx)` | `BFDamageApi.hurt` → `hitBox.modifyDamage`（§9.3） |
| 一般实体         | AABB 相交       | BF / 原版                           | `BFDamageApi.hurt` → 原版减伤链（§9.4）                |

**三者共用同一个基准 $D$**，$\Delta E$ 的求法一致（§7.2）；**最终伤害再由目标侧材料修正**——方块乘 `blockDamageFactor`、刚体过 `hitBox.modifyDamage`、一般实体交原版/BF 护甲链。差别只在**怎么发现被命中与怎么定稿**。

**伤害随迎流面积缩放是物理正确的**：薄壳结构按**单位面积**的应力破坏，不是按总能量。总能量翻倍、摊在两倍面积上，应力不变——所以**强度判据（$I$）不含面积，而总伤害含面积**。若让伤害也不含面积，大零件会在耐久上"免费"获得优势。

### 9.2 方块

```text
对该方块上每条被击穿的射线：
    A_pen = base_penetration × I_r           // 逐射线判穿透，§8.1
    击穿 → 计入 ΔE += E_r·λ_r
D  = base_damage × ΔE / Φ_0
若 D × blockDamageFactor > Θ_block → 标记摧毁
   其中 Θ_block = DamageUtil.getMaxBlockDurability(level, state, pos)
```

**方块不需要写死 $1\ \mathrm{m^2}$。** 正面命中一个方块面时，该方块收到的 $\Delta E$ 天然落在 $1\ \mathrm{m^2}$ 的标定口径上（$D=base\_damage$）；只有一条射线命中这类稀疏采样时 $\Delta E$ 更小、伤害更低，与刚体侧一致。

**判据复用既有实现的两个函数，不新造材料映射**：

- `Θ_block` 取 `DamageUtil.getMaxBlockDurability(level, state, pos)`（`util/mechanic/DamageUtil.java:33-51`）——已含材质分档（泥土/雪/沙 200、羊毛 200、树叶 10、粘性方块 1000、一般 100）与**方块体积修正**（`:47-49`，按碰撞形状包围盒体积缩放）。因此半砖、楼梯这类非满方块的耐久天然更低，**不需要在爆炸侧另做体积处理**；
- `blockDamageFactor` 沿用投射物侧 `ProjectileType` 的既有字段，语义与 `BallisticProjectile.java:737` 完全一致（那里是 `getProjectileType().getBlockDamageFactor() * damage > blockDurability`），只是一个按弹种给出的方块破坏倍率。

**由此，方块不需要自己的任何阈值参数**——直接复用投射物侧已配平的一套材料映射，不必再引入 `k_durability`、方块强度阈值之类的新参数。

**每方块每 tick 一次结算。** 同一 tick 内多条射线穿过同一方块时，它们各自先判穿透（用各自的 $I_r$），被击穿的那些再汇入 $\Delta E$。

**不做跨 tick 累积。** 这意味着：

- 不需要持久累积表，不需要"跨爆炸清零"的讨论；
- 摧毁结果与 `front_speed` 无关（波前慢只改变判定发生的时刻，不改变判定用的值）；
- 手感上仍等价于"一发轰不碎的墙第二发也轰不碎"——因为每 tick 用的是同一批射线、同一批判定结果。

### 9.3 刚体

```text
per-去重键（每 tick 汇总一次，tick 末统一施加）：
    逐射线：result = subPart.resolvePenetration(ctx_ray)   // 判定（纯，无副作用）
            PENETRATED → ΔE += E_r·λ_r；E_r ← E_r·η（供下游）
            否则       → 该射线终止
    D = base_damage × ΔE / Φ_0
    每键一次：BFDamageApi.hurt(subPart, ctx_agg)
```

- **判定逐射线、施加每键一次**：`resolvePenetration` 只读 `ctx`，可安全地逐射线调用；聚合后每个 HitBox 只 `hurt` 一次（§9.5）。
- **`ctx_agg` 的构造**：
  ```java
  BFDamageContext ctx = BFDamageContext.builder()
          .source(爆炸伤害源)                 // machine_max:blast
          .baseDamage(D)                     // 爆炸侧基准伤害（可为 0）
          .penetration(A_pen_代表值)          // 见下
          .hitVelocity(负法线均值).hitNormal(法线均值)   // 入射角 0；均值定义见 §10.3
          .hitPoint(命中点均值)
          .build();
  ctx.extensions().set(MMDamageExtensions.HIT_BOX, hitBox);  // 该 HitBox
  ctx.extensions().set(BFDamageExtensions.IMPULSE, J);       // 合冲量（§10.3）
  BFDamageApi.hurt(subPart, ctx);
  ```
- **代表穿深取该 HitBox 上所有命中射线中最大的 $A_{pen}$**：聚合后的 `hurt` 会二次判定（入射角恒 0，`resolvePenetration` 无随机，判定幂等），只有传最大穿深才能保证“至少一条击穿 ⇒ 仍判 PENETRATED”，避免把 $D$ 清零。
- **$D=0$ 时也调用**：§7.5 要求未击穿仍产生冲量，因此即使 $\Delta E=0$（全部被拦下或一条未命中），也要调用一次以经 `IMPULSE` 扩展投递冲量。
- **最终伤害由护甲侧定稿**：`SubPart.calculateFinalDamage` 对 PENETRATED 走 `hitBox.modifyDamage(source, ctx.baseDamage())`。只有“至少一条击穿”才会把 $D>0$ 传进去，未击穿时 $D=0$，钝伤分支取 0——与 §7.5“未击穿不产生伤害”一致，不需要额外开关。
- **不经过** `MMPartEntity.hurt()` 中的 `DamageSource.EXPLOSION` 分支（`MMPartEntity.java:191-224`）——语义为“最近 SubPart + 最厚装甲”，粒度过粗。**因此绝不能使用原版 `minecraft:explosion` 伤害类型。**

### 9.4 一般实体

生物侧的护甲、附魔、药水效果仍由原版减伤链条处理（戴 BF 护甲的实体由 adapter 处理），本系统只负责给出基准伤害并调用一次：

```text
ΔE = Σ_到达该实体的射线 E_r·λ_r
D  = base_damage × ΔE / Φ_0
BFDamageApi.hurt(entity, ctx)     // D 作 ctx.baseDamage；去重键 = 该 Entity
```

用爆炸类 `DamageSource`（新增 `machine_max:blast`）施加。**不复用原版的方块破坏路径**——破坏集合完全由本系统决定。

> 与刚体侧唯一的差别是**怎么发现命中**：实体不在快照里，用主线程 AABB 相交（§3.2）。一旦确认命中，$\Delta E$ 的求法与伤害公式与刚体一致。

### 9.5 结算节奏与施加纪律

**每个去重键每 tick 至多施加一次。**（去重键的定义见 §4.2：零件的一个 HitBox、一个方块、或一个一般实体。）同一 tick 内所有命中**同一去重键**的射线**先累积后统一施加**，不允许逐条直接造成伤害或冲量。理由有三条，缺一不可：

1. **性能**：`rayCount` × 命中次数会产生成千上万次微小的伤害与冲量调用；聚合后每个键每 tick 各一次，即使 `rayCount` 上千也恒定。
2. **阈值可达性**：破坏与穿透阈值必须在"目标尺度"上判定，而不是在"单条采样射线"尺度上判定——否则阈值会变成采样密度的函数。
3. **物理正确性**：冲量本就应当以合矢量、合作用点一次性施加；连续施加微冲量会让约束求解器反复重算。

**注意粒度**：同一个 `SubPart` 的**不同 HitBox** 是不同去重键，因此同一 tick 内可以各结算一次——击穿外装甲与命中内部引擎是两次独立事件，各自带自己的 `hitBox`、$A_{pen}$、$rha$。这正好对应 `BFDamageApi` 的形状：`MMDamageExtensions.HIT_BOX` 本来就是逐次 `hurt` 设置的（`MMPartEntity.java:210/221`）。

**判定是逐射线的，施加是每键一次的**：对刚体，逐射线只调 `resolvePenetration`（纯判定，无伤害/音效/物理任务），真正的 `BFDamageApi.hurt` 每个去重键每 tick 只调一次（§9.3）。因此“逐射线判定”与本节纪律不冲突。

**跨 tick 不再累积**（§9.2）。一个去重键在波前扫过的过程中会被连续结算若干个 tick，每次独立；这是"波前依次到达"的自然结果，不是积分。

## 十、冲量

### 10.1 通用规则

$$
\boxed{\ J=base\_impulse\sum_r A_r\sqrt{I_r}\ }
\qquad
A_r=\Delta\Omega\,d_r^{2},
\qquad
base\_impulse=\text{`near\_radius` 处、无介质消耗、单位迎流面积受到的冲量}
$$

**逐射线求和，与伤害同一条纪律（§6.2）。** 每条射线用自己的足迹 $A_r$ 与自己的强度 $I_r$（§6.1）算出它那一份冲量 $base\_impulse A_r\sqrt{I_r}$，再相加。**面积在这里逐射线使用，不需要先求总和**——$A=\sum_rA_r$ 只是顺带得到的（§7.1.1）。

> **近似闭式（供参考，不是定义）**：若目标在几何上足够紧凑、各条射线的 $d_r$ 与 $I_r$ 接近，则
> $$J\approx base\_impulse\,A\sqrt{\frac{\mathfrak{E}}{A\,\Phi_0}},\qquad \mathfrak{E}=\sum_{\text{全部命中}}E_r\lambda_r$$
> 由 Cauchy–Schwarz，右端是逐射线求和的**上界**：$\sum_rA_r\sqrt{I_r}\le\sqrt{A\,\mathfrak{E}/\Phi_0}$，射线间 $d_r\sqrt{E_r}$ 越分散、高估越多。所以它只是"目标够紧凑"时的速算，不能当定义。

**为什么对面积是一次、对强度是平方根**：冲量 = 压力 × 面积 × 时间，是一次的**力累积**，因此面积进一次。强度一侧取平方根，落点在**比冲量的距离衰减**：$\sqrt{\cdot}$ 给出每平方米冲量 $\propto1/d$，若改成线性（$J\propto\mathfrak{E}/\Phi_0$）则 $\propto1/d^2$，远距离击退会衰得太快。这与 §6.6 的 $\Delta p\propto\Phi$ 不冲突——那里是**瞬时超压**，这里是**冲量** $\int\Delta p\,dt$（还要乘正相持续时间），两者随距离的幂次本就不同。该形式同时保证"大目标吃到更大击退"与"远距离击退正确衰减"两条。

> **冲量是唯一必须显式携带面积的终端量。** 伤害把面积吃进了 $\Delta E$（§7.2）；而冲量的每一份贡献是"足迹 × 压强因子"，足迹 $A_r$ 无法由该射线的能量 $E_r$ 单独给出（它由立体角与距离决定），所以必须逐射线带上。这个 $A_r$ 就是 §7.1.1 的逐射线足迹，不是另行测量的迎流截面。

- **掩体削弱自动进入冲量**：被墙折减能量的射线，其 $I_r$ 随之下降，$\sqrt{I_r}$ 直接反映到那一份冲量上，不需要为冲量单独写一套衰减。
- **冲量与是否击穿无关**（§7.5）。
- **不引入装甲面密度与比破碎能**。本设计刻意不做弹道极限级别的物理化：`HitBoxAttr` 已同时具备 `thickness`（`:29`）、`rha()`（`:296`）、`unpen_power()`（`:304`），因此**未来若需要把穿深判定换成** **$v_{50}=\sqrt{2e_{frag}}$** **的物理式，材料是齐备的**，但那属于后续精化，本阶段不做。

> 注意：`MaterialAttr`（`MaterialAttr.java:17-20`）**没有 density 字段**，质量来自 `subPart.body.getMass()` 与 `MassUtil` 的实体硬编码，不经过材质属性。上句"材料是齐备的"只对 `HitBoxAttr` 成立。

> **已知偏差：薄件的冲量可能超过"全转动能"上限。** 本公式是"单位面积冲量 × 面积"的**压强模型**：$J\propto A$，与目标质量无关。而一个物体能拿到的动量受其动能上限约束——收到入射能量 $E$ 时 $J\le\sqrt{2m\eta E}$（$m$ 为质量、$\eta$ 为热效率），且 $E\propto A$，所以该上限 $\propto\sqrt m\propto\sqrt A$。两者之比只取决于材料的**面密度** $\sigma=m/A$ 与参考点的**真实**能量密度 $\Psi_0=W/(4\pi\,near\_radius^{2})$（$W$ 为总当量，$\mathrm{J}$）：
>
> $$\frac{J_{\text{本模型}}}{J_{\text{能量上限}}}=\frac{base\_impulse}{\sqrt{2\sigma\,\eta\,\Psi_0}}$$
>
> 目标大小与距离都约掉了。当 $\sigma< base\_impulse^{2}/(2\eta\Psi_0)$ 时本模型偏大：按 $base\_impulse\approx300\ \mathrm{N\cdot s/m^2}$、$\Psi_0\approx1\times10^{5}\ \mathrm{J/m^2}$、$\eta=0.1$ 估算，阈值约 $4.5\ \mathrm{kg/m^2}$（≈0.6 mm 钢）——**只有天线、薄蒙皮、铰链盖这类轻件会被吹得偏狠（约 1.5× 量级），装甲件不受影响**。（$\sigma$ 只在这一估算里出现，不是模型输入。）
>
> **本设计接受这一偏差**，换来三条性质：公式有界（$J\propto A$，不随质量发散）、与质量无关、参数表不含任何能量量纲（§6.3）。若要消除它，就得逐刚体取 $\min\!\big(\text{本模型},\ \kappa\sqrt{m\eta\mathfrak E}\big)$，代价是内容包必须新增真实总当量 $W$。

### 10.2 方块

**方块不吃冲量。** 方块的响应是"碎或不碎"（§9.2），没有刚体意义上的动量传递。若将来需要"爆炸把方块震落"之类的效果，属于独立机制。

### 10.3 刚体
```text
J = base_impulse × Σ_全部命中 ( A_r × √I_r )      // 逐射线求和；A_r = ΔΩ·d_r²，I_r 见 §6.1
   近似闭式（§10.1，仅供速算）：J ≈ base_impulse × A × √( 𝓔 / (A·Φ_0) )
   其中 A = Σ A_r、𝓔 = Σ_全部命中 E_r·λ_r   （入射能量，与是否击穿无关）

n̄  = normalize( Σ (E_r·λ_r)·n̂_r )          // 能量加权的法线均值；n̂_r 取该命中点“朝爆心”的法线
p̄  = Σ (E_r·λ_r)·p_r / Σ (E_r·λ_r)          // 能量加权的命中点均值
```

- **逐刚体（`SubPart`）累积，不给整车一个冲量。** 逐刚体施加后，连接器关节自动把载荷传遍整车，同时“爆炸撕掉零件”的行为直接交给既有连接器完整性系统。
- **注意与伤害的口径差别**：伤害只对**被击穿**的射线求和（$\Delta E=\sum_{r\,\text{被击穿}}E_r\lambda_r$）；冲量对**全部命中**的射线求和（每条贡献 $A_r\sqrt{I_r}$，与是否击穿无关，§7.5）。两者共用同一套逐射线登记，只是求和范围不同。
- **方向与作用点**：方向取**能量加权的法线均值** $\overline n$，作用点取能量加权的命中点均值 $\overline p$（权重都是 $E_r\lambda_r$，与 §6.2 同一条纪律）。作用点不落在质心，因此力矩自然产生（扭转、抬头、甩尾），不需要额外规则。

**投递：复用 $`SubPart.hurt` 的 `IMPULSE` 通路，爆炸侧不另建队列。**

```text
ctx.hitNormal   = n̄        // 法线均值（朝爆心）
ctx.hitVelocity = -n̄       // 入射角 = acos|n̄·(-n̄)| = 0；冲量方向 = normalize(hitVelocity) = -n̄
ctx.hitPoint    = p̄
IMPULSE         = |J|
```

- `SubPart.hurt` 用 `ctx.hitVelocity` 的归一化方向作为冲量方向、`ctx.hitPoint` 作为作用点、`IMPULSE` 作为大小，因此上面四个字段一次写对即可同时满足“入射角 0”与“推离爆心”（冲量沿 $-\overline n$，即爆炸能量的传播方向）。
- `SubPart.hurt` 在**没有** `IMPULSE` 扩展时会回退到伤害基公式（`Math.log10(...)·250`）。爆炸源不是 `PART_COLLISION`，所以**必须显式写入 `IMPULSE`**（即使为 0）来抑制回退，避免额外击退。
- **相位**：`SubPart.hurt` 用 `PPhase.PRE` 提交物理任务（`SubPart.java:547`）；若希望延迟收敛到 1 个物理步可改为 `PPhase.ALL`（每个子步开头抽干，`PhysicsLevel.kt:393`）。该改动落在 `SubPart.hurt`，不在爆炸侧。

> 若后续确需爆炸侧自行投递物理任务：必须用 `PhysicsLevel.submitImmediateTask`（`SparkLevel` 的那套在主线程 `PhysicsLevelApplier` 抽干），且严禁在投递的 lambda 里再投同一 phase（`TaskSubmitOffice.kt:67-77` 是 `while(isNotEmpty) poll→invoke`，自重投会活锁）。

### 10.4 一般实体

按 $\vec J$ 直接施加击退冲量（`entity.push(...)` 或 `addDeltaMovement`）。原版爆炸会额外放大爆炸类击退，本系统保持一致：**冲量公式只有一个**（§10.1），放大通过 `base_impulse` 表达。

### 10.5 内部二次传播（不在本阶段）

**冲击在载具内部的传播**（连接器节点承受冲击、子系统间接受损、殉爆触发）是另一个问题，不应塞进爆炸射线模型。本阶段只保证"命中谁就给谁正确的强度、方向与作用点"，内部传播交由既有的连接器完整性与子系统损坏机制。详见 `子系统-模块化损坏与子模块设计.md`。

# 第五部分 · 外围

## 十一、掩体削弱

### 11.1 削弱来自穿透折减，与摧毁解耦

削弱发生在 §8.2 的**穿透折减**这一步——射线穿过一个方块时按该方块的护甲折算能量损失。它与"这个方块是否被摧毁"**没有关系**：

> **只要不摧毁方块，掩体作用自动成立，不需要额外写"掩体模式"。**

这给出了本项目最想要的一条性质：管理员关闭地形破坏后，**穿透折减照样发生**，因此墙后的目标仍按被吃掉的能量受损——掩体作用与"方块碎不碎"互不影响。

由于场强是"命中该点的射线集"的统计量（§6.2），被墙挡住的方向不参与计算，**遮挡天然是方向相关的**：同一发爆炸对墙后的两个目标可以给出不同的 $I$。这是特性而非缺陷——它正是"掩体"这个词的物理含义。

### 11.2 配置项

| 配置项                                     | 作用                   | 语义                  |
| --------------------------------------- | -------------------- | ------------------- |
| `explosionBlockDamage`                  | 全局 / 按维度总开关          | 关 → 只折减能量、不摧毁方块     |
| `explosionTerrainDamageMultiplier`      | 对地形的破坏力倍乘            | `0.0` = 只留掩体不破坏地形   |
| `destructionSourceFilter`               | 按来源放行                | 例如允许殉爆破坏地形、禁止普通炮弹破坏 |
| `frontSpeedDefault`                     | 默认波前速度               | JSON 可覆盖            |
| `interactionCutoff`                     | 射线累积传输效率的失活阈值        | `0.01`；纯性能旋钮，不参与平衡  |
| `k_armor`                               | 材料因子 → 方块护甲          | 待配平（§8.2）           |

`explosionBlockDamage` 与 `explosionTerrainDamageMultiplier` 合起来正好覆盖"既需要掩体作用、又不想破坏地形"的需求，且这是模型结构自带的，不是补丁。

**配置优先级（必须明确定义，否则多处开关会打架）：**

```text
1. 全局总开关 explosionBlockDamage = false     → 一律不摧毁（能量折减照旧）
2. destructionSourceFilter 不放行本次来源      → 不摧毁（能量折减照旧）
3. 本次爆炸的 JSON destroy_blocks = false      → 不摧毁（能量折减照旧）
4. 以上都放行                                   → 摧毁，并受下列倍率影响
   a. 命中方块时乘以 explosionTerrainDamageMultiplier
   b. drop_items 决定是否掉落
```

**三条“不摧毁”路径都不影响穿透与折减**——这是 §11.1 那条性质的实现保证。

## 十四、模块布局

爆炸是独立模块，**不放在** **`projectile`** **包内**（它要服务于投射物之外的来源）：

```text
common/mech/explosion/
├── ExplosionManager.java          ← 每 Level 单例：活跃实例表 + tick 驱动
├── ExplosionInstance.java         ← 一次爆炸的聚合根：射线组 + 去重集 + 本 tick 累积（跨 tick 存活）
├── ExplosionParams.java           ← 传播与映射参数（JSON Codec）
├── BlastRay.java                  ← 持久传播射线（§4.2）
├── BlastRayGenerator.java         ← Fibonacci 球 + 种子抖动，确定性方向集
├── BlastField.java                ← 场强折算（无状态静态）：近场平台、唯一的 I 出口（§六）
└── BlastFrontVisual.java          ← 波前半径与视觉数据（双端）
```

**切分依据是状态归属，不是阶段。** 独立成类的只有两类：有自己生命周期的对象（`ExplosionManager` 持有的活跃实例、`ExplosionInstance`、`BlastRay`）与无状态的纯函数库（`BlastField`、`BlastRayGenerator`）。推进（DDA + 快照 `rayTest`）、本 tick 累积、对目标施加这三个阶段，是**同一次爆炸在同一次 tick 内顺序执行的连续步骤**，共享 `ExplosionInstance` 的状态，因此实现为它的方法与字段——三者之间没有需要隔离的状态，各立一个类型只会把同一份状态在多个对象间来回传递。

> **接口签名另见**《武器系统-爆炸系统接口设计.md》。那份文档单向引用本文（本文不引用它），本文因此仍可独立阅读与评审。

### 14.1 三种调用方共享同一入口

调用方只需要给出四个量（起爆点、参数集、归属、种子），`ExplosionManager` 收到后创建对应的 `ExplosionInstance` 并纳入活跃表，其余全部由它承担。三个入口是：

| 调用方         | 入口                                                                                                                          | 本阶段状态                        |
| ----------- | --------------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| **指令 / 脚本** | 直接调用 `detonate(...)`                                                                                                     | ✅ 可独立实现，调试与管理用               |
| **子系统殉爆**   | 子系统损坏 → 调用 `detonate(...)`                                                                                               | ✅ 可独立实现，**需 §12.4 的环路保护**    |
| **弹头起爆**    | `Fuze`（引信，投射物侧设计）→ `WorldEffect`（通用世界效果抽象）→ `WorldEffect` 的 `machine_max:blast` 实现，把 `EffectContext` 翻译成 `detonate(...)` 的入参 | ⚠️ **依赖上游尚未实现的通用 Effect 体系** |

投射物侧只需保留一个薄适配层：

```text
projectile/component/effect/
├── WorldEffect.java               ← 通用效果 Codec 抽象（上游设计）
├── EffectContext.java             ← 展平的命中上下文（上游设计）
├── EffectExecutor.java            ← 主线程执行器（上游设计）
└── ExplosionWorldEffect.java      ← 本设计：把 EffectContext 翻译成 detonate 的入参
```

> **现状提示（重要）**：`common/mech/explosion/` 已按本设计实现（§十七 阶段 A–J），因此指令/脚本与子系统殉爆这两个调用方可以直接调用 `detonate(...)`。`Fuze`、`WorldEffect`、`EffectContext`、`EffectExecutor` **目前在仓库中不存在**，只作为设计存在于上游文档 `武器系统-组件化投射物与类型体系设计.md`，因此 §十七 的阶段 K 依赖该文档的阶段 F。

**两条实现纪律**（写进类注释，它们是本设计唯一容易写错的地方）：

1. **归一化只做一次，且只在 `BlastField` 里做。** `ExplosionInstance` 的推进步骤只允许更新 $E_r$ 与 $d_r$，**不得**乘任何含距离的因子——几何衰减已经由 $d_r^{2}$ 在算 $I_r$ 时显式给出，再乘一次会把距离指数变成 4（§5.2）。反向的错误同样要防：**不得跳过 $I_r$ 把 $E_r$ 直接当强度用**（$E_r$ 是无量纲比例，进不了任何以 mm 或伤害为量纲的判据）。
2. **只有累积表记录命中，只有施加步骤产生副作用。** 推进期只往累积表写入，结算完成后由施加步骤统一对外调用——每个去重键每 tick 至多一次伤害、一次冲量。

### 14.2 共享 DDA 工具

**需新写**，不能直接从 `ProjectileManager` 提取。现有实现是：

```java
private static List<BlockHitEntry> walkBlocksAlongRay(
        Vector3f rayFrom, Vector3f rayTo, PhysicsChunkSection terrain)   // :1593
```

它与爆炸的需求有三个不可调和的差异：

1. **要求一个已经构建好的物理地形 section**——它用 `terrain.getSectionPos()`（`:1596-1603`）、`terrain.getBlockSnapshot(bp)`（`:1688`）、`terrain.getPhysicsLevel().getBlockShapeManager().getBlockAabbs(state)`（`:1692`），且 `getBlockSnapshot` 在 section 未构建完时返回 `null`（`PhysicsChunkSection.kt:381-384`）；
2. **方块数据来自构建期从 MC 区块拷贝的副本**（`SectionSnapshot.snapshotFromChunk`，`SectionSnapshot.kt:33-81`，且过滤掉空气/无碰撞方块），**不是** **`LevelChunk`** **本体**——而 §3.6 要求爆炸走 MC 自身的数据路径；
3. **裁剪到单个 16³ section**（`:1609-1646`），不携带跨 tick DDA 游标（§4.2 需要 `voxelX/Y/Z`、`tMax`、`step`、`lastNormalAxis`）。

因此正确的做法是：**新写一个跨 section、直接读** **`LevelChunkSection.getBlockState`、携带跨 tick 游标的全局体素遍历**，只共享 Amanatides-Woo 的步进算术。

**必须处理的退化情形：起点在实心方块内部。** 现有代码在调用方处理它（`ProjectileManager.java:1039-1069`），注释写明 *"Bullet 的 GJK/SubSimplex 算法声明'起点不应在凸体内部，否则结果未定义'"*，且探测手段用了 §3.6 禁止的 API。爆炸侧：

- **DDA 侧**：首次跨越参数初始化为 0，使起始体素本身参与判定（§4.3 的"先步进后判定"会让起点体素永不被判定，必须显式处理）；
- **快照 rayTest 侧**：爆心落在装甲凸体内部时同样命中该未定义行为，需要显式检测并回退。

该类位于 `util/mechanic/`（与 `ArmorUtil` 同目录），因为它同时被爆炸与光束使用——两者都在主线程，共享的是 Amanatides–Woo 步进算术与跨 section 的区块读取路径；投射物侧仍走它自己的物理地形 section。

## 十五、性能预算

### 15.1 两个通道的成本

| 通道                        | 单位成本      | 每 tick 次数                      | 与地形有关               |
| ------------------------- | --------- | ------------------------------ | ------------------- |
| **DDA 体素遍历**              | 纯数学，极低    | `rayCount × advancePerStep`    | 是                   |
| **快照 `contactTest`（粗筛）**   | 1 次 native 查询 + narrow phase | **1（每爆炸每 tick 一次，§4.4）**       | **否**（快照不含地形） |
| **快照 `rayTest`（粗筛后）**      | native 调用   | 仅"本 tick 够得到的刚体附近"的射线          | **否**               |
| 逐射线 AABB 粗筛               | 纯 Java 算术  | `rayCount × 候选刚体数`             | 否                   |

**关键：粗筛把 `rayTest` 的调用次数从"全部射线"降到"确实靠近刚体的射线"，而 `contactTest` 本身只付一次。** 三道防线依次是：`contactTest`（每爆炸一次）→ 逐射线 AABB（纯 Java）→ `rayTest`（仅幸存者）。

以 20 Hz 主线程、`rayCount = 1024` 折算。每 tick 的 DDA 体素步数只由 `front_speed` 决定（`advancePerStep = front_speed / 20`，体素 1 m 见方）：

| 场景                                 | DDA 体素步数/tick | 量级       |
| ---------------------------------- | ------------- | -------- |
| `front_speed = 20 m/s`（默认） | ≈ 1024 | 数十 µs |
| `front_speed = 40 m/s` | ≈ 2048 | 数十 µs |
| `front_speed = 100 m/s` | ≈ 5120 | 开始有意义 |
| `front_speed = 200 m/s` | ≈ 10240 | 开始有意义 |

> 注意射线数由 `near_radius` 决定（§4.7），与 `max_radius` 解耦——所以"增大爆炸半径"只增加推进总步数与寿命，不增加每 tick 的采样成本；而 `front_speed` 只改变这些步数摊在多少个 tick 上（寿命 = `max_radius / front_speed` 秒）。

### 15.2 真正需要监控的是 rayTest 次数

`rayTest` 是 native 调用，且 `CollisionSpace` 的实现会遍历空间的 broadphase（`CollisionSpace.java:557`）。纪律是：

1. **每 tick 每射线一次**，覆盖本 tick 的推进段（§4.3），绝不逐格调用；
2. **粗筛**：按 §4.4 的候选带排除"本 tick 够不到任何刚体"的射线，只有通过粗筛的射线才调用 `rayTest`；
3. **每个去重键每 tick 一次**施加纪律（§9.5），把伤害与冲量的调用次数压到与射线数无关。

**结论：只要把** **`front_speed`** **作为调参量（几十 m/s 量级），逐段推进在主线程完全无压力。** 真实爆轰波前速是 km/s 量级，但视觉化的扩散反而更好读，也更适合游戏节奏。

> 顺带一提：**地形不进快照这件事让两个通道彻底解耦**（§3.5）。DDA 的成本只与体素步数有关，`rayTest` 的成本只与刚体数有关，`rayCount` 是两者唯一的公共乘数——而它已经是纯性能旋钮（§4.6）。这是本设计在性能上最干净的一条性质。

## A.2 候选刚体的分派规则

`contactTest`（§4.4）与 `rayTest`（§4.3）的候选集**不是同质的**，必须按 `owner` 分派：

| `owner` | 来源 | 爆炸的处理 |
| --- | --- | --- |
| `SubPart` | 载具零件 | **完整通路**：`triangleIndex → HitBox` 取命中框与 $rha$，交 BF 判定后结算伤害与冲量 |
| 实体（`RigidBodyEntity` / `CollisionObjectEntity` 子类） | Spark 的物理实体 | 走 §8.4/§9.4 的一般实体通路；**去重键用该 `Entity` 本身** |
| `InteractBoxes` | 载具交互区 | **跳过**。它是交互判定用的 `TRIGGER` 体，即使将来换了碰撞组也不该被爆炸当装甲 |
| `ProjectileHitBox` | 投射物的运动学触发体（碰撞组 `PROJECTILE`） | **跳过**：属主是 `ProjectileHitBox` 而非 `SubPart` / `Entity`，落进下面的 `else` 分支 |
| `PhysicsChunkSection` | 地形 | **跳过**（防御性分支） |
| `null` | 未设 owner 的刚体 | 跳过并记一条 debug 日志，便于发现新的注册来源 |

```java
Object owner = PhysicsBodyExtensionKt.getOwner(body);
if (owner instanceof SubPart subPart)        { /* 完整通路 */ }
else if (owner instanceof Entity entity)     { /* 一般实体通路，去重键 = entity */ }
else                                          { /* 跳过 */ }
```

**为什么写成防御性分派而不是"只处理 `SubPart`"**：`PHYSICS_BODY` 是 `CollisionObjectEntity` 的**默认**碰撞组，任何新增的物理实体都会自动落进快照。硬编码假定会在将来某次改动后静默失效——而且症状是"爆炸对某些东西没反应"，很难定位。

**既有代码的两段式先例**（`EntityMixin.java:139-144`）：

```java
int group = pco.getCollisionGroup();
if (group != CollisionGroups.PHYSICS_BODY) continue;
if (!(PhysicsBodyExtensionKt.getOwner(pco) instanceof SubPart subPart)) continue;
```

> **碰撞组是筛选门槛，`owner` 才是分类依据。**

## A.3 粗筛查询的实现细节

### A.3.1 为什么打在快照世界

| | 主物理世界 | **快照世界** |
| --- | --- | --- |
| 归属线程 | 物理线程 | **主线程专用** |
| 调用方式 | 需 `submitImmediateTask` 排队 | **直接调用** |
| 并发风险 | 与物理步进竞争 | 无 |
| 内容 | 全部刚体 + 地形 section | **只有 `SNAPSHOT_TRACKED` 组（`PHYSICS_BODY` / `PROJECTILE`）** |

`WorldSnapshot` 是独立的 `PhysicsSpace`（`WorldSnapshot.kt:22-28`），类注释写明"用于主线程进行 rayTest / sweepTest / **contactTest**"。其 `needsCollision` 覆写返回 `false`（`WorldSnapshot.kt:129-131`），地形 section 的 `btCollisionObject` 根本不会进来——**不需要额外写碰撞掩码滤地形**。

### A.3.2 `contactTest` 走的是树遍历

```cpp
// btCollisionWorld.cpp:1232-1239
void btCollisionWorld::contactTest(btCollisionObject* colObj, ContactResultCallback& resultCallback) {
    btVector3 aabbMin, aabbMax;
    colObj->getCollisionShape()->getAabb(colObj->getWorldTransform(), aabbMin, aabbMax);
    btSingleContactCallback contactCB(colObj, this, resultCallback);
    m_broadphasePairCache->aabbTest(aabbMin, aabbMax, contactCB);
}

// btDbvtBroadphase.cpp:300-308
void btDbvtBroadphase::aabbTest(const btVector3& aabbMin, const btVector3& aabbMax, ...) {
    m_sets[0].collideTV(m_sets[0].m_root, bounds, callback);   // 动态集
    m_sets[1].collideTV(m_sets[1].m_root, bounds, callback);   // 静态集
}
```

### A.3.3 它的固有代价：会跑 narrow phase

`btSingleContactCallback` 对每个 AABB 候选调用 `contactPairTest` → `findAlgorithm(..., BT_CLOSEST_POINT_ALGORITHMS)`，**建立完整接触流形**，且 native 侧对每个重叠体回调一次 Java 监听器（JNI 往返 per body）。

我们只需要"哪些刚体在附近"，不需要接触点，因此拿到的能力有一大半是浪费的。用快照世界把候选集限制在 `SNAPSHOT_TRACKED` 组之后处于可接受范围。

### A.3.4 为什么不用 `PhysicsGhostObject`

`btPairCachingGhostObject` 的重叠列表来自 broadphase 的**配对缓存**，而 Bullet 的 DBVT broadphase 会跳过已 deactivated 的刚体、其配对不再更新。**停放中的载具正是会休眠的**——一旦漏掉它，"炸停在原地的车"就会完全无效，这是最不能接受的失败模式。

`contactTest` 没有这个问题：它走树遍历（A.3.2），睡眠 proxy 仍在树中。**这是选择它而非 ghost 的主要理由——正确性上的，不是性能上的。**

顺带也省掉了维护一个物理对象（建 ghost、每 tick 移动、维护形状与 AABB 更新时机）的全部麻烦。

API 备查：`PhysicsGhostObject`（`Spark-Core/src/main/java/com/jme3/bullet/objects/PhysicsGhostObject.java:66`）提供 `getOverlappingObjects()`（`:130-137`，返回内部复用列表，内部先 `clear()`）、`getOverlappingCount()`（`:118-123`）、`getOverlapping(int)`（`:108-111`，**必须先调 `getOverlappingObjects()`**）。

### A.3.5 快照滞后的余量

`syncTransform()` 在 `LevelTickEvent.Pre` 阶段刷新（`WorldSnapshot.kt:100-105`），因此快照位置滞后一个物理步。查询球半径取 `frontRadius + advancePerStep` 可以避开"波前刚好够到、快照里却还在外面"的边界漏判。

## A.4 地形读取的硬性约束

**主线程禁止使用 `terrainManager.getBlockSnapshotAt()` / `getSectionForBlockPos()`。**

理由要写准确（不是"物理线程在改它"）：

- `PhysicsChunk.sections` 是普通 `mutableMapOf`（`PhysicsChunk.kt:22`），**非并发**；
- 它的**写者是 `PhysicsChunk.load()` / `unload()`，全部在主线程**；`updateActivation()` 从不增删 `sections`；
- 而**读它的却包含物理线程**（`CollisionHandler.java:492`、`SubPart.java:398/414`）；
- 现有 `ProjectileManager.java:1047/1049` 在主线程读它，是一条真实的 `ConcurrentModificationException` 通路。

真正的竞争方向是"主线程写、物理线程读"，与直觉相反。

## A.5 介质交互通道的完整清单

| 目标 | 通道 | 成本 | 与地形有关 |
| --- | --- | --- | --- |
| 方块（地形） | 主线程 3D DDA，直接读 `LevelChunkSection.getBlockState` | 纯数学，极低 | 是 |
| 快照中的刚体 | 快照 `contactTest` 粗筛 → 纯 Java AABB → 快照 `rayTest` | native 调用 | **否** |
| 其余实体（`PAWN` 等） | 主线程 AABB 相交 | 纯数学 | 否 |

三条通道的结果必须合并成同一条按距离排序的序列（§4.4）。
