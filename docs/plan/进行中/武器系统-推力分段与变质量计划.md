## 一、v1 基线（历史对照）

> **本节记录的是段表落地前的形态**，只作为差距对照保留：内容包侧的 `ThrustProperties` 对象与弹道库侧的单窗口 `ThrustProfile` 都已不存在，现行形态见 §零、§三与 §4.1。

投射物的推进段由两个独立的类型各表达一次，中间是一次一对一折算：

| 位置 | 类型 | 字段 | 说明 |
| --- | --- | --- | --- |
| 内容包 | `BallisticProjectileType.ExternalProperties.ThrustProperties` | `force` / `duration` / `ignition_delay` | 作者侧形态，`spark_modules/**/projectiles/*.json` 的 `external.thrust` |
| 弹道库 | `io.github.sweetzonzi.ballistics_framework.api.trajectory.ThrustProfile` | `force` / `startSeconds` / `endSeconds` | 求解器与积分器读的形态；窗口 `[start, end)` |

折算在 `BallisticProjectileType#getThrustProfile()`：`start = ignition_delay`、`end = ignition_delay + duration`，结果按弹种惰性缓存一次。

三个消费方共用同一条积分式 `TrajectoryStep#step`（服务端趟一、客户端外推、地形预载视界行走），因此"预测与模拟同式"由构造保证。仓库内 15 个弹种定义里只有 `9m133_kornet.json` 配了 `thrust`：

```json
"thrust": { "force": 2600.0, "duration": 2.5, "ignition_delay": 0.1 }
```

推力沿**速度矢量**施加，只增速率、不改方向；质量取 `BallisticConfig.mass()`，燃烧期恒定。`HudBallisticTable` 对 `hasThrust()` 的弹种返回空表，即带推力的弹种不出弹道标定分划。

## 二、v1 形态的两处缺口（历史动机）

> **本节记录段表落地前的问题与当初的量级评估**，是 §三 的设计依据；现行形态见 §零与 §三。文中"v1 形态"指只支持单窗口、燃烧期质量恒定的那一版。

### 2.1 只能点火一次

双脉冲（第二脉冲在飞行中段点火）、火箭增程弹、筒式发射弹的"弹射 + 续航"两段，都需要不止一个燃烧窗口。v1 形态用一个 `force` 与一个窗口表达，能表达的只有"一次恒力点火 + 出膛速度"这一种组合。

### 2.2 燃烧期质量恒定

v1 形态里推进剂烧掉后质量不变，于是段内加速度恒为 `F/m₀`，而真实加速度随质量下降单调上升。以 9M133 的配置做量级参考（26 kg、2600 N、2.5 s，取排气速度 2354 m/s 即 Isp 240 s，反推装药 2.76 kg 占总质量 10.6%，用同一条半隐式欧拉、dt = 0.01 s）：

| 场景 | 燃尽速度 | 45° 射程 | 10° 射程 |
| --- | --- | --- | --- |
| 常质量（不写 `propellant_mass`） | 283.7 m/s | 8530 m | 1402 m |
| 变质量 | 297.9 m/s | 9352 m（+9.6%） | 1476 m（+5.2%） |
| 变质量且把 `force` 反标定到 2473 N | 284.4 m/s | 8544 m（+0.2%） | 1373 m（−2.1%） |

读法有三条：

- **速度增量改变**。总冲不变而分母变小，`Δv` 从 250 m/s 升到 264 m/s（+5.7%）。
- **单点反标定只能对上一种射击**。把 `force` 调到 2473 N 能让 45° 复原，10° 反而短 2%——变质量把加速后置（段初加速度低、段末高），浅角射击对速度形状更敏感。
- **阻力项使结论偏乐观**。上表用 9M133 的 `drag_factor = 0.0025`，300 m/s 时阻力加速度只有 0.08 m/s²，因此差别几乎全是纯火箭效应；阻力若按真实量级取值，燃尽后质量更低会使减速度更大，抵消一部分增益。

积分误差不是问题：同样的比对在 dt = 10 ms 下，常质量与变质量相对各自 0.2 ms 参考解的位置差都是米级（1.6 m 与 1.4 m，O(dt) 同阶），质量流失不劣化误差阶。

### 2.3 本文不承担的部分

- **推力曲线 / 任意函数**：固体发动机的实际剖面是"平台 + 尾段爬升"，2~4 个分段点足够；采样曲线没有消费方，且给内容作者增加无收益的负担。
- **分级分离**：真正的多级有级间分离、质量跳变与迎风面积跳变。段表给的是"多次点火"，不含分离事件。
- **推力方向**：沿速度矢量是质点模型下的既定近似，制导转弯由指令加速度承担。

## 三、目标形态：段表

`external.thrust` 是一个段数组，缺省或空数组表示无推力：

```json
"thrust": [
  { "force": 2600.0, "start": 0.1, "duration": 2.5 },
  { "force": 1800.0, "start": 8.0, "duration": 1.2, "propellant_mass": 0.9 }
]
```

| 字段 | 类型 | 缺省 | 语义 |
| --- | --- | --- | --- |
| `force` | number > 0 | 必填 | 推力（N） |
| `start` | number ≥ 0 | 必填 | 点火时刻（s），自发射瞬间起算 |
| `duration` | number > 0 | 必填 | 燃烧时长（s）；窗口 `[start, start + duration)` |
| `propellant_mass` | number ≥ 0 | `0` | 本段全程烧掉的推进剂（kg）；0 = 本段质量恒定 |

**装药按段记录，不设剖面级总量。** 每段自带推进剂，于是每段有自己的排气速度（助推药柱与续航药柱本就不是同一配方），也不必强行为全剖面假设一个 Isp。质量按段内匀速消耗：

```text
mdot_i        = propellant_i / duration_i                          （kg/s）
consumed_i(t) = clamp(t − start_i, 0, duration_i) · mdot_i         （kg）
m(t)          = max(m_base + Σ (propellant_i − consumed_i(t)), ε)   （kg）
```

`m_base` 就是 `external.mass`（**弹体基础质量，不含推进剂**），所以出膛质量 `m(0) = m_base + Σ propellant_i`，越过全部窗口后回落到 `m_base`。阻力与推力加速度共用这个 `m(t)` 作分母；`ε` 是防除零下限（弹道库里是 1e-6 kg），不是可用配置。排气速度 `ve_i = force_i / mdot_i` 是派生量，不进 JSON，也不作为作者参数。

**校验分两层，各管一段**：

- **解码期**（内容包加载期报错，带文件路径）：`propellant_mass ≥ 0`；`Σ propellant_mass < external.mass`。前者防"负装药让整段被判无效、推力一起消失"，后者防燃尽时质量归零。实现在 `ExternalProperties#CODEC` 的 `flatXmap`。
- **折算期**（弹道库的构造器）：`force > 0` 且 `duration > 0` 的段才进剖面，其余丢弃；段之间不得重叠（允许空隙，空隙即无推力滑行），重叠抛 `IllegalArgumentException`，MM 侧转成点名弹种的 error 并按无推力处理。

## 四、BallisticsFramework 侧

已随 `1.0.0.alpha.15` 落地。本节只留 Machine-Max 需要知道的能力边界；API 细节、段窗口判定与质量公式归该仓库的 `docs/推力分段与燃烧质量流失-实施计划.md` §二–§四，不在这里复制。

### 4.1 `ThrustProfile`

```java
public record ThrustProfile(List<Segment> segments) {
    public record Segment(float forceN, float delaySeconds, float durationSeconds, float massKg) {}

    public static final ThrustProfile NONE = new ThrustProfile(List.of());
    public static ThrustProfile of(float forceN, float delaySeconds, float durationSeconds);  // 单段、恒质量

    public boolean isActive();
    public float forceAt(double seconds);                    // 段外与空隙返回 0
    public float massAt(double seconds, float baseMass);     // 段质量为 0 时逐位返回 baseMass
    public float startSeconds();                             // 首段点火时刻
    public float endSeconds();                               // 末段熄火时刻
    public float burnDuration();                             // Σ 段时长
    public ThrustProfile remainingSince(double elapsedSeconds);
}
```

三点与 Machine-Max 的写法直接相关：

- **第三个参数是持续时长，不是熄火时刻**。内容包的 `duration` 可以 1:1 填入；要表达"熄火于 T"就写 `T − start`。
- **时间参数是 `double`、段边界是 `float`**。查询时传同一个 `float` 值最稳：double 字面量 `0.1` 比 `float` 的 `0.1f` 略小，会落在窗口之前。
- **规范化在构造器里**：丢弃无效段 → 按点火时刻排序 → 拒绝重叠（抛 `IllegalArgumentException`）。MM 侧不重复判据。

段表以发射瞬间为原点的消费方（Machine-Max 的三处）不需要 `remainingSince`：`forceAt` / `massAt` 以调用方给出的时刻为唯一时基。

### 4.2 `RealisticTrajectory` 接线

三个推力积分器每步取 `forceAt(步初时刻)` 与 `massAt(步初时刻, config.mass())`，`aT` 与阻力共用当步质量。分派门禁是「段表非空」，因此空隙步也走推力积分器——它与无推力外推是同一离散格式的两份实现，差在浮点表示（§4.3）。

### 4.3 Machine-Max 依赖的三条不变式

- **单段恒质量剖面与单窗口形态逐位一致**：`forceAt` 在窗口内返回同一个 `float`，`massAt` 无装药时逐位返回 `baseMass`。9M133（单段、不写装药）的弹道因此与"只有一个燃烧窗口"的写法逐位相同。
- **段表非空时一律走推力积分器**，包括段间空隙；非推力退化路径永远见不到变质量，继续用常量 `config.mass()`。
- **段窗口判定取步初时刻**，左闭右开。

BF 侧 T1–T17 见该仓库计划 §五（T10 是"单段剖面复现单窗口算术"的逐位基线）。Machine-Max 侧的对应覆盖在 §0.1 的用例行：`TrajectoryStepTest` 的逐步比对覆盖单段、双段与变质量三种剖面，空隙步另有逐位断言。

## 五、Machine-Max 侧

### 5.1 数据形态

`ExternalProperties` 的 `thrust` 字段是 `List<ThrustSegment>`，不保留包装 record，也没有对象/数组的形态分派：

```java
public record ThrustSegment(float force, float start, float duration, float propellantMass) {}
```

`propellant_mass` 是数组元素上的可选字段，缺省 `0` 表示该段质量恒定，因此不写它的内容包与"没有这个字段"时的行为一致。

`CODEC` 为 `Codec.list(ThrustSegment.CODEC).optionalFieldOf("thrust", List.of())`。`ExternalProperties` 的整组 codec 再套一层 `flatXmap` 承接跨字段校验（装药非负、合计小于 `mass`），失败返回 `DataResult.error`，由 `PackCodec` 转成一条带内容包路径的内容错误，而不是堆栈。

### 5.2 折算

`ExternalProperties#toThrustProfile()` 把段表逐项映射为 `ThrustProfile.Segment`，`propellantMass` 原样进入 `massKg` 后一次构造；`BallisticProjectileType#getThrustProfile()` 按弹种惰性缓存，并在 `setRegistryKey()` 里先折算一次——重叠段属于内容包错误，加载期就要点名弹种。`hasThrust()` 取折算后剖面的 `isActive()`，与积分侧同源。

### 5.3 积分

`TrajectoryStep#step` 每步先算一次当步总质量 `mass = thrust.massAt(burnTime, cfg.mass())`，再把它同时用作阻力与推力加速度的分母：`forceN = thrust.forceAt(burnTime)`，`forceN > 0` 时推力加速度为 `forceN / mass`。函数签名不变，三个消费方零改动；无装药时 `massAt` 逐位返回 `cfg.mass()`，既有弹道逐位不变；空隙步的推力项为 0。

阻力与推力共用分母是物理口径而不是实现细节：`external.mass` 是弹体基础质量，未燃尽的装药属于同一发弹丸的质量，拆成两个分母会让"变轻"只作用在推力项上。

### 5.4 内容包

`9m133_kornet.json` 的推进段写成一段的数组，不写 `propellant_mass`——保持常质量，弹道与单窗口形态逐位一致（依据见 §六）：

```json
"thrust": [ { "force": 2600.0, "start": 0.1, "duration": 2.5 } ]
```

### 5.5 schema 与同步

`projectile.schema.json` 的 `thrust` 是 `array`，元素 `additionalProperties: false`，不含对象形态；元素的 `propellant_mass` 说明"窗口内匀速消耗，全部段的合计必须小于 `external.mass`"，`external.mass` 自身的说明写明"不含推进剂"。改完 schema 后执行 `./gradlew syncSchemas`，把其余十个包的副本、技能快照与 `bundle-manifest.json` 放在同一个提交。

### 5.6 不改动的部分

| 组件 | 原因 |
| --- | --- |
| `HudBallisticTable` | 带推力的弹种继续返回空表；分划表的前提（射程上界取初速、飞行时间上限）对助推弹不成立 |
| `ProjectilesSpawnPayload`、`sync` 协议版本 | 推进段全部是弹种常量，无需逐发同步 |
| `ProjectileManager` 的 SoA 数组 | 质量由 `burnTime` 与段表解析得到，不需要新状态 |

### 5.7 文档

## 六、验收

**门槛**（三条全绿才算"行为保持 + 接线正确"）：

1. `ProjectileThrustCodecTest` 十二条用例全绿——缺省 / 空数组 / 字段映射 / 按序保留 / 整表折算与空隙 / 重叠拒绝 / 对象形态报错 / 无效段丢弃 / 装药解码与质量下降 / 装药缺省 / 装药合计上限（含分段合计）/ 负装药拒绝；
2. `TrajectoryStepTest` 六条用例全绿，其中「双段 + 空隙」既做逐步比对，也对空隙步做逐位断言；「变质量」既逐步比对，又用"两个步初时刻的速度增量之比等于质量反比"钉住分母口径（若阻力仍用 `cfg.mass()`，比值会偏出 1e-2 量级，而逐步比对的 1.0 m/s 容差看不出来）；
3. `./gradlew checkSchemas` 通过——builtin 与其余十个包的副本、技能快照、`bundle-manifest.json` 一致。

**9M133 不动的依据**：它只有一段、不写装药 ⇒ `massAt` 逐位返回 `cfg.mass()`，`forceAt` 在窗口内返回同一个 `float`，阻力与推力的分母因此都是同一个常量，`TrajectoryStep` 的算术与单窗口形态逐位相同。BallisticsFramework 侧的 T10 用冻结基线钉住同一件事。

**命令**：`./gradlew --offline test`、`./gradlew checkSchemas`；实机用 `runClient` 发射一发 9M133 确认弹道与画面无变化。

## 七、明确不做

- **指令触发（飞行中点火）**。它的引入方式是在段上加一个可选的 `ignition` 枚举（`timed` / `commanded`）；数组元素增加可选属性属于兼容的 schema 变更，不产生迁移成本。届时才需要引入"每发解析后的剖面"与一条点火同步载荷，而当前没有消费方（没有火控会下发这个指令），因此不进本期。
- **对象形态不保留**。`external.thrust` 只接受数组：仓库内只有 9M133 一处，它写成数组。第三方包若沿用了对象写法，会在加载期以"期望列表"失败，属于响亮的失败而非静默降级。
- 推力曲线、分级分离、推力方向，见 §2.3。

## 八、风险

| 风险 | 处置 |
| --- | --- |
| 段间空隙使推力积分器承接了"无推力滑行"的步 | 由 §4.3 的不变式保证等价；MM 侧空隙步另有逐位断言（§六 第 2 条） |
| 重叠段/无序段被内容作者写出 | 弹道库构造期规范化与拒绝重叠，加载期由 `setRegistryKey()` 折算时记 error 并按无推力处理，不做隐式覆盖 |
| 装药写多了，燃尽时质量归零 | 解码期拒绝"合计 ≥ `external.mass`"（§三 校验、§5.1）；库侧另有 1e-6 kg 防除零下限 |
| 负装药让整段被判无效 | 解码期拒绝负值（§三 校验），避免"没推力"这种无从排查的失败 |
| 阻力与推力共用当步总质量作分母 | 与"只按 `cfg.mass()` 算"相比，只在写了 `propellant_mass` 时两者不同；无装药时 `massAt` 逐位返回 `cfg.mass()`，既有弹道逐位不变（§六 依据） |
| 变质量移动既有弹道 | 只在写了 `propellant_mass` 时发生；9M133 不写，现有弹道不变 |
| schema 破坏性变更影响第三方内容包 | 对象形态→数组那一轮是破坏性的（仓库内仅一处配置受影响）；`propellant_mass` 是可选新增，不写它的配置照常解码 |
| 两个仓库的提交顺序 | BallisticsFramework 先合入并升到 `alpha.15`；Machine-Max 的 `gradle.properties` 在同一次提交里跟上，否则复合构建会解析到旧版本 |
