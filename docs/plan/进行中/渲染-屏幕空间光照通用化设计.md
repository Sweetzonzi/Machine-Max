# Machine-Max 渲染 — 屏幕空间光照通用化设计

> **状态**：设计已完成首轮源码审阅与用户讨论；**P1（通用通路、光源表、曳光来源）、P2（独立可配置的爆炸火光）与枪口火光（P1 通路上的第三类来源）已落地，P3–P5 尚未实现**（2026-10-17）。当前实现是「来源 → 光源表 → 效果」三层：`ScreenSpaceLightEffect` 按 `ScreenSpaceLightSource` 列表采集，`ScreenSpaceLightBuffer` 做校验、影响体剔除与容量选择，来源有曳光（`ProjectileTracerLightSource`）、爆炸火光（`ExplosionLightSource`，状态在 `ExplosionLightState`）与枪口火光（`MuzzleFlashLightSource`，状态在 `MuzzleFlashLightState`）。本文其余章节规定载具球光与锥光的接入。
>
> **已确认的范围**：接受屏幕空间遮挡近似，按当前画面中有深度证据的遮挡验收；爆炸火光独立配置半径、强度、寿命，未填写时采用统一默认值，各弹种可以覆盖；枪口火光按弹种配置、默认开启，半径按口径折算（§2.4）。具体默认数值见 §8.1，已作为内容包缺省值落地，仍属待客户端标定。P1 的等价验收由用户在主视图实机目视完成，不建立数组级或逐像素的自动断言。
>
> **本文自包含**：结论、字段语义与验收条件在本文给出。源码路径以 Machine-Max 仓库为基准：`client/`、`common/`、`network/` 分别指 `src/main/java/io/github/sweetzonzi/machine_max/` 下同名目录，`shaders/` 指 `src/main/resources/assets/machine_max/shaders/`。这些是路径缩写，不是另一个源码树。P1/P2 的类型、资源与接线已在仓库落地（§2.1、§2.3、§2.4）；P3–P5 的类型、配置与阶段验收都是提案，未据此声称已经实现或运行通过；当前事实的坐标集中在附录 B。

**术语**：S2 = 在光心的屏幕投影位置采深度，判断光源自身是否可见，决定该光源的**表面项与星芒**是否参与（空气散射光晕不走这条判定，它按逐像素深度截断）；S3 = 对受光表面点到光源的线段做屏幕空间遮挡检测；S4 = 从深度重建表面法线并计算朝向响应。S2 与 S4 已实现（S4 见 §9.4），S3 未实现。P1–P5 是实施阶段，不是遮挡算法等级。

## 1. 目标与范围

### 1.1 要做什么

| 阶段 | 内容 |
| --- | --- |
| P1 | 通用通路、CPU 光源表、提交器接口与诊断；曳光首先接入，保持 §7 列出的参数、剔除、插值和混合算法 |
| P2 | 独立可配置的爆炸火光；包含内容包解码、起爆包同步和独立客户端寿命 |
| P3 | 实测 16/32 槽的容量与成本，确定 32 槽是否适合作为默认容量；优先级比较与超限计数在 P1 建立 |
| P4 | 载具 `POINT` 灯接入；统一体积光几何与光照链的调度次序，核验近裁面与相机背后光源 |
| P5 | 载具 `BEAM` 灯、S3 与 S4；球光车灯也使用 S3，遮挡策略不由球/锥形状决定 |

P1 是其余阶段的前置。P2/P4 的球光可以独立展示亮度与生命周期，但其无逐像素遮挡的阶段能力必须明确标注；它们不能提前通过 P5 的遮挡验收。

### 1.2 不做什么

| 范围外 | 边界 |
| --- | --- |
| 阴影贴图、世界空间遮挡结构 | 本期接受屏幕空间信息缺失导致的漏光；不能承诺所有视角都有完整阴影 |
| 修改原版方块光照等级 | 本效果只改客户端画面，不影响刷怪、作物或任何读取光照等级的逻辑 |
| HDR 光照、材质 BRDF、与光影包统一曝光 | 本链在已经渲染的颜色上合成，没有独立反照率、材质、曝光输入 |
| 全局光照、反射 | 与光源表通用化无关 |
| 分块光源列表、光源子集时间累积 | 记为后续扩展方向，见 §5.4、§6 |
| 检查器/CCTV 离屏视角 | 本期只处理主视图；离屏目标需要各自的矩阵、深度与效果实例 |

### 1.3 成本与表现口径

本方案不触发体素光照传播。CPU 成本来自候选光源遍历与选取；GPU 成本来自有效像素、入选光源数、覆盖面积与遮挡步数。世界半径通过剔除、投影面积和步进长度间接影响成本，不能仅由半径或指令数量估算帧时间。

Iris 会话是单独的兼容验收场景。主目标中可取得的深度、实际投影和最终颜色必须匹配；只有通过 §10 矩阵的组合才算支持，不据现有曳光链的存在推断所有光影包都兼容。

### 2.2 P1 保留的口径与算法

| 保留项 | 现位置 |
| --- | --- |

### 2.3 火光的落地形态与现行值（2026-10-17）

爆炸火光的配置、同步与生命周期按 §8 落地：内容包可选子对象 `light` 由 `common/mech/explosion/ExplosionLightParams.java` 解析，随 `ExplosionParams` 的网络 codec 进入起爆包（registrar `sync:2.2.0`），客户端由 `client/render/post/ExplosionLightState.java` 按维度登记、由 `client/render/post/ExplosionLightSource.java` 采集。

| 现行值 | 数值与语义 |
| --- | --- |
| 缺省颜色 / 半径 / 辐照度 / 寿命 | 橙黄 `[255,180,100]` / 8 m / 166 / 6 tick；内容包未写 `light` 时整份取它，只写部分字段时逐字段回落 |
| 字段边界 | 半径 `(0, 64]` m、辐照度 `[0, 4096]`、寿命 `[1, 200]` tick；越界或非有限值在内容包加载期带字段路径报错 |
| 强度包络 | `I(t) = 配置辐照度 × (1 - u²(3 - 2u))`，`u = t/T`；起爆立即到峰值，结束时平滑归零，半径固定不扩张 |
| 遮挡策略 | `SOURCE_DEPTH`，绝对容差 1.0 m：爆心贴地、贴墙、夹在自己的火球里是常态，容差太小会整盏误杀；墙或车体挡在光心前面时跳过表面项与星芒。光晕不受这条判定影响（逐像素 `t_hit`），见 §8.5 |
| 强度合成 | 辐照度（1 m 处）× 时间包络 × 火光类别倍率 × 全局倍率；全局倍率由光源表统一乘一次 |
| 时钟 | 关卡的 `getGameTime()`（20 tick/s）；暂停冻结，渲染侧另加帧间插值量 |
| 配置键 | `screen_space_light_enabled` / `screen_space_light_intensity`（总开关/总倍率）、`explosion_light_enabled` / `explosion_light_intensity`（火光类别） |

这些数值是首轮标定起点，仍未在客户端实测标定；改动它们不需要重编着色器。

### 2.4 枪口火光的落地形态与现行值（2026-10-17）

枪口火光是 P1 通路上的第三类来源：它不改变容量、数组契约与链，只是在 `ScreenSpaceLightSource` 列表里多一个实现。内容包字段挂在弹种的 `visual` 块下、按弹种配置——发射器只提供 locator 与开火动画名，真正的尺度由装药量决定，而口径（`external.caliber`）是它在数据里的唯一载体。设计取舍见 §8.6。

| 现行值 | 数值与语义 |
| --- | --- |
| 内容包字段 | `visual.muzzle_flash` 子对象，整块可缺省；只写部分字段时逐字段回落（`enabled` / `radius` / `color` / `intensity` / `glow` / `glare` / `duration_ticks`） |
| 缺省颜色 / 辐照度 / 寿命 | 暖白 `[255,200,120]` / 90 / 6 tick（≈300 ms） |
| 缺省半径 | 按口径折算 `min(2 m + 15 cm × 口径mm, 48 m)`：口径 7.62 mm → 3.1 m、20 mm → 5.0 m、30 mm → 6.5 m、50 mm → 9.5 m、120 mm → 20 m、155 mm → 25.3 m；次口径弹按弹芯口径折算，见下 |
| 字段边界 | 半径 `-1`（按口径折算）或 `(0, 64]` m、辐照度 `[0,4096]`、光晕与星芒倍率非负（无上界）、寿命 `[1,40]` tick；越界或非有限值在内容包加载期带字段路径报错（`muzzle_flash.radius` 等） |
| 强度包络 | `I(t) = 配置辐照度 × (1 - u)²`，`u = t/T`：开火瞬间到峰值，随后二次衰减 |
| 遮挡策略 | `SOURCE_DEPTH`，绝对容差 0.75 m：枪口贴着自己的炮管与炮口制退器，容差小了会在自己开火时整盏误杀；车体或墙挡在光心前面时跳过表面项与星芒。光晕不受这条判定影响（逐像素 `t_hit`） |
| 触发 | 发射器 `onTick` 的客户端分支与两个调试物品的 `use`，经 `MuzzleFlashLight#emit` 登记；同一 tick 至多一条，强度不按发数累加 |
| 时钟 | 关卡的 `getGameTime()`（20 tick/s）；暂停冻结，渲染侧另加帧间插值量 |
| 优先级 / 来源 | `MUZZLE_FLASH = 15`（爆炸火光 10 之后、曳光 20 之前）；来源 ID `machine_max:muzzle_flash` |
| 配置键 | `muzzle_flash_light_enabled` / `muzzle_flash_light_intensity`（类别开关 / 倍率） |
| 同步 | 不同步：两端各自加载同一份弹种数据，客户端按本机数据推导，不占载荷版本 |

`intensity` 是枪口光源在 1 m 处的辐照度（绝对量，不是叠加倍率），半径只决定照到多远。仓库内的 13 个弹种都按 `external.caliber` 写入了显式值（7.62 mm → 9.9、20 mm → 25、30 mm → 42.3、50 mm → 90.3、120 mm → 400、155 mm → 638），首轮锚点与反解方法见 `docs/plan/进行中/渲染-屏幕空间光照物理化设计.md` §4.2；想关掉某个弹种写 `"muzzle_flash": {"enabled": false}`。字段与折算式在 `common/mech/projectile/ProjectileType.java#MuzzleFlash` 与 `common/mech/projectile/MuzzleFlashLight.java#radiusFor`；改动它们不需要重编着色器。

**次口径弹的折算偏差**：`external.caliber` 对 120mm APFSDS 是 26 mm 的弹芯，按它折算出的枪口焰只有 5.9 m，而按炮口口径会得到 20 m。要按炮口表达，就在该弹种写显式 `radius`——`120mm_apfsds` 就配了 `"radius": 20.0`；折算式只认口径这一个量，不区分它是炮口还是弹芯。

## 3. 光源差异与遮挡策略

| 属性 | 曳光 | 爆炸火光 | 枪口火光 | 车灯 |
| --- | --- | --- | --- | --- |
| 形状 | 球 | 球 | 球 | `POINT` 球 / `BEAM` 锥 |
| 几何与寿命 | 投射物插值位姿、口径与剩余寿命 | 起爆点、独立 `light` 配置、独立计时 | 枪口 locator 位姿、弹种 `muzzle_flash` 配置、独立计时 | 子系统激活状态、定位器位姿与静态属性 |
| P1/P2/P4 遮挡 | S2，保留现有行为 | S2，绝对容差 1.0 m | S2，绝对容差 0.75 m | `NONE`，接受漏光 |
| P5 遮挡 | 保留 S2，升级另行验收 | 可单独评估 S3，不作为 P5 的必要范围 | 可单独评估 S3，不作为 P5 的必要范围 | `POINT` 与 `BEAM` 均用 S3 |
| 法线响应 | 启用（共享着色器，权重 0.5） | 启用（权重 0.5） | 启用（权重 0.5） | P5 逐盏 `normalWeight` |
| 光心可见性的含义 | S2 是现有启发式，可能误杀/漏判 | 爆心贴地、贴墙或夹在火球里，靠 1 m 容差避免误杀 | 枪口贴着自己的炮管与制退器，靠 0.75 m 容差避免误杀 | 灯泡可能离屏、被车身挡住或在相机背后 |

**S2 与 S3 是可选择的策略，不能先用 S2 否决整盏灯再执行 S3。** 相机看不见灯泡时，相机可见的另一块表面仍可能被照亮。形状、遮挡、法线响应是三个独立维度。

**S2 只否决表面项与星芒，不否决光晕。** 空气散射光晕有逐像素的 `t_hit` 截断（沿视线取到第一个表面），它比"在光心投影处采一次深度"精确：光源被挡住、而光晕球有一半没被挡住时，逐像素截断会画出露出的一半，S2 会整片抹掉。星芒则相反，它是镜头内的成像，只有光源自身可见才有意义，所以只认光源级判定。

## 4. 通用化架构

### 4.1 类型与提交契约

| 类型 | 职责 |
| --- | --- |
| `ScreenSpaceLight` | 可复用的可变提交载体；完整设置一条光源，提交时立即复制数值 |
| `ScreenSpaceLightPriority` | 明文整数常量：车灯 0、火光 10、枪口火光 15、曳光 20；数值越小越优先 |
| `ScreenSpaceLightBuffer` | 数值校验、公共几何剔除、容量选择、扁平数组与诊断计数；无 GL 调用 |
| `ScreenSpaceLightSource` | 提供稳定的来源 ID、优先级和采集函数；采集只读渲染所需状态，不操作 GL |
| `LightFrameContext` | 本次主视图的只读借用上下文：Level、相机位置、视图/投影矩阵、目标尺寸、焦距、渲染距离、游戏时间插值量 |
| `ScreenSpaceLightEffect` | 采集编排、链加载/释放、尺寸与深度格式检查、uniform 上传和绘制 |
| 四个来源实现 | `ProjectileTracerLightSource`、`ExplosionLightSource` 与 `MuzzleFlashLightSource` 已落地，`VehicleLightSource` 是 P4 的提案 |

```java
public interface ScreenSpaceLightSource {
    ResourceLocation id(); // 构造期创建，用于来源统计，不在逐光源路径上创建
    int priority();        // 必须显式声明
    void collect(LightFrameContext frame, ScreenSpaceLightBuffer out);
}

public final class ScreenSpaceLightBuffer {
    void beginFrame(LightFrameContext frame, float globalIntensity);
    void beginSource(ScreenSpaceLightSource source);
    SubmitResult submit(ScreenSpaceLight light); // ACCEPTED / INVALID / CULLED / UNSUPPORTED / CAPACITY_REJECTED
    void endFrame();                             // 统计各来源最终入选数，并按限频发汇总日志
    int count();
    int capacity();
    boolean isCapped();
    float[] positionRadius();        // capacity * 4：视空间光心 xyz + 半径
    float[] colorIntensity();        // capacity * 4：线性颜色 rgb + 辐照度（已乘全局倍率）
    float[] sourceDepthTolerance();  // capacity：S2 的绝对容差
    float[] occlusion();             // capacity：遮挡策略编码，0 = 不做遮挡判定，1 = S2
    void resetDiagnostics();         // 退出世界时清空触顶状态
}
```

这些签名在 `client/render/post/` 的同名文件里落地。`SubmitResult` 区分接收、数值非法、几何剔除、阶段未支持与容量拒绝；发生槽位置换时额外统计被挤出的来源。

`occlusionMode` 逐盏编码进 `LightOcclusion`：`NONE` 编成 `0`、`SOURCE_DEPTH` 编成 `1`。片元只在编码为 `1` 时执行 S2，因此同一帧里曳光与火光可以各自使用自己的策略。S2 判为不可见时只跳过表面项与星芒，空气散射光晕仍按逐像素深度截断求值。`SCREEN_RAY` 在提交处按 `UNSUPPORTED` 拒绝，没有编码值。

`Effect` 在构造期持有来源列表，每帧依次调用 `beginSource` 与 `collect`。来源 ID 与优先级由 `beginSource` 盖到条目上；同一来源需要不同优先级时拆成两个实例。不要依赖 enum 声明顺序确定优先级。

**每条光源的完整字段与单位：**

| 字段 | 契约 |
| --- | --- |
| `positionView` | 视空间米制位置；前方为负 Z。世界位置先减相机位置，再乘视图旋转；不重复减相机 |
| `radius` | 有限影响半径（m），大于 0；点到光心距离达到半径时贡献严格为 0 |
| `color` | 非负 RGB，通道归一化到 `[0,1]`；沿用现有颜色通道口径，不引入 gamma 转换 |
| `intensity` | 非负有限峰值系数，乘来源包络与类别倍率；全局倍率只由 Buffer 乘一次 |
| `shape` | `POINT` 或 `SPOT`；未实现的形状必须报告不支持，不能按球光悄悄渲染 |
| `directionView`、`cosInner`、`cosOuter` | 锥光必填；方向单位向量，从灯指向照射方向；`cosInner >= cosOuter` |
| `occlusionMode` | `NONE` / `SOURCE_DEPTH`（S2）/ `SCREEN_RAY`（S3）；未实现模式不能默认为已生效。当前 GPU 编码只有前两者的逐盏开关 |
| `sourceDepthTolerance` | S2 绝对容差（m），允许 0；S3 的起点偏置和厚度使用独立参数 |
| `normalWeight` | `[0,1]`，0 表示不乘法线响应，1 表示完整 Lambert 项 |

为避免漏填与残值，提供一次写齐必填量的 `setPoint(...)` / `setSpot(...)` 方法；它们同时覆盖模式、颜色和强度，并置 `configured`。`submit` 在所有返回路径清除 `configured`，未配置便再次提交时计为非法。字段不公开逐个写入；Buffer 必须独立检查 NaN/Infinity、半径/强度和锥角关系。**零位置、零容差都是合法值，不能靠“提交后全部清零”证明完整性。**

渲染线程拥有 Context、Buffer 与 scratch；来源不得保存借用的 Context/矩阵，也不得在物理线程写入提交记录。避免为每盏灯创建新记录和集合；现有定位器/位姿 API 的内部对象分配单独量测，不能把“采集函数绝对零分配”作为已有事实。

CPU 提交契约已经写全；GPU 打包按阶段扩展，当前只支持球光与 `NONE`/`SOURCE_DEPTH` 两种遮挡策略。接口完整不等于已经支持 S3 或锥光。

### 4.2 合并链的数学口径

每像素每个入选光源产生非负 RGB 贡献 `l_i`，目标算法是：

```text
e = sum(color_linear_i * I_i * w(d_i) / max(d_i², d_min_i²))   // 逐通道求和
C = srgb_to_linear(src.rgb)
C_out = 1 - (1 - C) / (1 + e * (C + β(1 - C)))
out.rgb = linear_to_srgb(C_out)
out.a = 1
```

这就是 `shaders/program/screen_space_light.fsh#main` 的累加与合成形态（`β = 0.03`，算子推导见 `docs/plan/进行中/渲染-屏幕空间光照物理化设计.md` §3）。光源在同一张表里求和，数学结果与排列无关；浮点求和允许末位差异。

**把光源拆到多条链分别合成，不等于合成一次。** 合成曲线对 `e` 不可加：同一像素先后经过两条链、每条只算一部分 `e`，与把两部分求和后映射一次的结果不同。合成必须在一次 pass 内完成。

合并的理由是共享一次光照深度快照、一份候选表和一条链。链包含一次光照 pass 与一次颜色回写 pass；每个用途分别建同类链则会重复这些步骤。折射链有独立深度目标，见 §4.4。

### 4.3 公共剔除与近裁面

公共层负责有限数检查、非正半径/强度、距离、投影覆盖与容量。具体剔除口径如下（前四行已落地，实现位置是 `client/render/post/ScreenSpaceLightBuffer.java#commit`）：

| 来源 | 规则 |
| --- | --- |
| 曳光特有 | `frontDepth <= 0`、光心距离大于渲染距离、`focalPx * radius / frontDepth < 4 px` 三条留在来源内，见 `client/render/post/ProjectileTracerLightSource.java#collect` |
| 火光/车灯 | 用影响体判定：`distanceToCenter > renderDistance + radius` 才按距离剔除；光心在相机背后不能直接剔除 |
| 穿越近裁面的影响球 | 只在整个球位于近裁面后方时剔除；与近裁面相交时保守保留，不用接近零的光心深度作除数 |
| 完全离屏 | 按影响球与视锥是否相交判定；光心投影离屏不等于影响范围离屏 |
| 排序半径 | 影响球与近裁面不相交时使用投影半径；相交时采用有限的屏幕对角线作为保守评分，避免 Infinity |

视锥侧平面直接由投影矩阵的 `m00` / `m11` 与 `w = -z` 给出，因此自动跟随 FOV、视口比例与任何改变投影的状态；球与平面相交判定用未归一化法线比较，省掉逐盏开方。

曳光的特有剔除留在来源里，公共的影响体剔除按影响球判定，二者不得被一条不区分来源的“背后光心即丢弃”规则混用：影响体剔除只会移除整球都不可能贡献的条目，腾出的槽位可能让同一帧里排序更后的低优先级光源入选。P5 锥光可以先用同半径球保守包围，再在片元判锥角。

### 4.4 帧次序、深度与生命周期

P1 保持 `client/render/post/PostProcessingManager.java#onRenderLevelStage` 的顺序：折射深度快照 → 光照深度快照 → 光照链；`onRenderLevelLast` 执行折射、过载、失色。光照没有候选时跳过本链快照与绘制，不能跳过独立需要深度的折射链。

**P4 必须统一体积光与本链的调度。** 当前 `LightSourceRenderer` 与 `PostProcessingManager` 独立订阅同一事件，代码没有表达两者的明确相对次序。目标次序由 Manager 显式调用，体积光只保留 tick 清理订阅：

1. `AFTER_LEVEL` 世界几何完成，冻结本次 FrameContext 并采集光源。
2. 完成折射与光照所需的深度快照。
3. 绘制并提交体积光几何；此时主目标深度尚完整。
4. 执行光照链，随后还原主目标绑定。
5. 进入手部阶段，再执行 `RenderLevelLastEvent` 的后处理链。

`dragonRays` 只写颜色（`net.minecraft.client.renderer.RenderType#DRAGON_RAYS`，本地 NeoForge sources jar）；本设计会让表面光照也合成到包含体积光的颜色上。体积光透明度需在 §9.4 的组合验收中标定。若要求体积光完全不受此合成，需要额外合成层，非本期默认方案。

每个需要深度的链在首个写主目标的 pass 前取好自己的快照；链尾颜色回写会清主目标深度，事实与诊断见 `client/render/post/AGENTS.md`「为什么：主目标的深度什么时候还有效」。本期保留这一行为，并显式记录对光影会话手部遮挡的影响（§13）。

资源规则：首次有效帧懒加载；尺寸变化时调整链目标并复核深度格式；缺 uniform、尺寸不匹配、加载失败时跳过本效果并限频报告；所有可能改变 FBO/深度掩码的路径包括异常路径都恢复状态。退出世界释放 GPU 资源与来源状态。当前实现资源重载不重建链，着色器验收需退出再进入世界；自动重载支持另列后续项，不声称已经具备。

FrameContext 的投影必须与该深度快照一致。P1 使用现有事件投影与 `BlastProjectionUtil`；P5 在 FOV、屏幕比例、相机震动与 Iris 场景核验重建。若焦距标量无法表达实际投影，则需传完整投影/逆投影矩阵，不能沿用错误的重建结果调遮挡容差。

### 4.5 uniform 容量与上传

| 每槽布局 | 16 槽 | 32 槽 | 64 槽 |
| --- | --- | --- | --- |
| 已落地：位置/半径 4 + 颜色/强度 4 + S2 容差 1 + 遮挡策略 1 + `d_min` 1 | 176 | 352 | 704 |
| P5 预算：上述 11 + 锥光方向/角度 5 + 形状编码 1 + 法线权重 1 | 288 | 576 | 1152 |

数字是 float 分量预算，不含公共 uniform；具体 GPU 编码在对应阶段固定并校验。OpenGL 3.2 的片元 uniform 分量下限是 1024，**64 槽的 P5 完整预算（1152）已经越过下限，因此 64 槽不是可承诺可移植的配置**；32 槽的 P5 预算（576）仍在下限之内，但同样须查询实际能力并检查链接结果，不能把表格当成性能结论。依据：[OpenGL 3.2 Core §3.9.1、表 6.43](https://registry.khronos.org/OpenGL/specs/gl/glspec32.core.pdf)。

Java 数组长度、程序 JSON `count` 和 GLSL 展开后的标量数量必须一致。`com.mojang.blaze3d.shaders.Uniform#set` 的 `float[]` 重载在数组过短时仅 WARN/忽略，过长时可能越过内部 FloatBuffer 容量；“大于等于 count 即可”不是安全契约。加载时核验，提交时全量上传。`LightCount` 保持 float，因为现有 `PostChain#setUniform(String,float)` 走浮点 setter。

## 5. 光源上限与诊断

### 5.1 成本模型

槽位数是编译好的 shader 容量 `Nmax`；运行时有效数 `N <= Nmax`。片元循环按 `N` 执行，不是无论有没有光源都跑满容量。无候选时本链没有 GPU 工作，但 CPU 来源遍历存在。

S2 最坏约 `有效像素 × N` 次光心深度采样；S3 还受每盏灯覆盖面积、提前命中与步数 K 影响。缓存、分支分歧和 GPU 架构使它不能换算成“K 个全屏 pass”。以隔离计时为准。

P3 测 16 与 32 槽；P5 测 K=4/8/16。固定分辨率、相机、光源数据、光影开关和 GPU，预热后采 300 帧，报告本效果 GPU 时间与整帧 p50/p95。VSync 关闭；GPU timer query 异步读结果，避免为计时强制同步。无 GPU 计时条件时注明只能看到整帧结果。

### 5.2 选择规则

保留固定容量的最优候选，排序键为 `(priority 升序, radiusPx 降序)`。同键按先到先留处理；来源注册顺序固定，来源内部尽量稳定。`VisualEffectHelper.lightingSubsystems` 当前是并发 Set，不能假定它提供跨帧稳定顺序（`common/visual/VisualEffectHelper.java#lightingSubsystems`）。

优先级不是保留名额：若 32 盏车灯占满 32 槽，全部火光、枪口火光与曳光都可能被排除；同优先级的近邻光源也可能在边界处跳换。首期接受严格优先级方案，不承诺每类至少有一盏。只有实测出现不可接受的跳换/饿死，再讨论配额或跨帧迟滞。

曳光只有一档优先级：光源表按 `(优先级升序, 投影半径降序)` 选择，同键先到先留，与落地前曳光链的「较大半径才替换」在单一优先级下等价。火光、枪口火光与车灯在各自来源接入时就使用既定优先级，不等 P3 才补。

### 5.3 可观测性

每帧按来源计：提交数、非法数、几何剔除数、通过剔除的候选数、最终入选数、容量拒绝数与被置换数。`isCapped` 表示有效候选超容量，直接拒绝也算，不能只统计实际置换。几何剔除数包含数值上合法但不产生贡献的条目（零半径/零强度）与影响体剔除（距离、近裁面、视锥）。

日志在开始触顶时记录，连续触顶按最多每 5 秒一条汇总，恢复时一条；日志含容量、来源优先级和上述计数。短暂不触顶不能绕过频率限制。0 候选、关闭效果、退出世界时重置本帧计数；容量日志与非法数据日志分开。不得逐光源逐帧刷日志。

容量仍是程序、JSON 和 Java 的共同常量，P1/P3 不开放任意数值的玩家配置；未来可以用固定编译变体提供档位。

### 5.4 分块光源列表的触发条件

分块方案按光源投影包围范围，把光源索引登记到屏幕小格（例如 16×16 像素），片元只遍历本格候选。它减少的是不相关光源的循环，不消除同格重叠光源的成本，也需要定义索引表溢出行为。

CPU 分桶并上传索引纹理是一种实现方式，**不必然需要额外几何 pre-pass**。只有持续容量不足、或剔除循环成为可测瓶颈时再做；“必须到几百盏才值得做”不作为硬阈值。

## 6. 时间复用评估

本期不采用每帧只画一组灯、直接让显示帧轮换的方案；也不建设历史缓冲累积。

若分 G 组、帧率 F，每灯的更新频率为 `F/G`：60 fps 两组为 30 Hz，120 fps 两组为 60 Hz，240 fps 四组为 60 Hz。**这个算式不能证明“不闪”**；显示方式、对比度、运动与观看条件都会改变可见闪烁，不能用统一 50–60 Hz 门槛承诺容量收益。

强度乘 G 也不能保证输出亮度相同。本链把逐光源辐照度求和后经有界曲线映射（`1 − (1 − C)/(1 + e·q)`，对 `e` 非线性），把一帧拆成 G 组轮流点亮同一盏灯不会得到同样的亮度：黑底上 `e = 0.8` 的一帧与 `e = 0.4` 的两帧并不等价。移动光源还会出现间歇光斑；单张截图无法验收时间稳定性。

真正的时间累积需要历史颜色/深度、重投影、遮挡变化拒绝、移动光源有效性判断，以及不受错误历史污染的当前帧估计。它是独立工程范围，不能用固定随机相位代替。容量问题先按 §5 实测与空间剔除处理；任何后续时间方案都要同时做截图和连续帧验证。

## 7. 曳光提交器与 P1 兼容基线

`ProjectileTracerLightSource` 承接落地前曳光链（§2.2）的投射物语义：类型/对象门禁、`tracer_alpha > 0`、光源半径与颜色（缺省回到口径折算与 `tracer_color`，可由内容包字段显式覆盖）、剩余寿命淡出与世界位姿采样。**不按 `alive` 剔除**：保留条目这一帧可能还要画曳光。对照 `client/render/renderer/ClientProjectileRenderer.java#render`，使用相同对象矩阵与游戏时间插值量。

曳光固定：16 槽、4 px 下限、光心距离/背后剔除、同键先到先留、S2 判据与容差、有限支撑窗、先求和后一次有界映射、alpha=1，以及现有客户端曳光配置的生效语义。内容包字段的语义见 `docs/plan/计划中/武器系统-投射物曳光光照设计.md` §11.1、§15.6。

光源表的影响体剔除（§4.3）对曳光同样生效，但它只移除整球都不可能贡献的条目；排序半径的保守分支覆盖“影响球与近裁面相交”，厚半径的近距曳光因此用屏幕对角线而非投影半径参与容量排序。这两条不改变任何像素的贡献，只改变容量吃紧时谁占槽位。

| 验收 | 判据 |
| --- | --- |
| 观感等价 | 固定世界、相机、弹种与输入，由用户在主视图目视验收曳光光照（保留口径见 §2.2）；覆盖 0、1、16、17 盏与同键候选，比较被照区与完整画面，差异需定位后才放行 |
| 空候选 | 本光照链 depth-copy/pass 计数均为 0；CPU 采集允许发生 |
| 门禁/淡出 | 保留死亡条目、剩余寿命边界、alpha=0、视锥边缘分别覆盖 |
| 触顶 | CPU Buffer 用容量 1 验证拒绝/置换；GPU 场景提交 17 盏验证 16 槽，避免只改 Java 常量造成 uniform 契约不一致 |
| 会话/生命周期 | 原版与目标 Iris 组合、窗口 resize、退出/重进世界、禁用/启用、加载失败均可恢复 |

## 8. 火光类来源：爆炸火光与枪口火光

### 8.1 爆炸火光的内容包字段（已落地）

在每份爆炸参数对象中增加可选子对象 `light`。所有使用该爆炸参数的弹种/世界效果可以分别覆盖；它不改变伤害、冲量、波前速度、起火或粒子参数。**缺省策略已确认：统一默认半径、强度与寿命，各内容项按需覆盖。**

```json
"light": {
  "enabled": true,
  "color": [255, 180, 100],
  "radius": 8.0,
  "intensity": 166.0,
  "glow": 1.0,
  "glare": 1.0,
  "duration_ticks": 6
}
```

上述数值是首轮标定起点，已作为内容包缺省值落地（`common/mech/explosion/ExplosionLightParams.java#DEFAULT`），仍不是实测标定后的最终默认值。

| 字段 | 单位/范围 | 缺省与语义 |
| --- | --- | --- |
| `enabled` | boolean | true；false 完全禁用该爆炸火光 |
| `color` | 三个整数 `[0,255]` | `[255,180,100]`；颜色，不作为额外 alpha |
| `radius` | m，有限，`0 < R <= 64` | 8；固定照射半径，独立于 `max_radius` 与 `front_speed` |
| `intensity` | 无量纲，有限，`[0,4096]` | 166（1 m 处辐照度）；起爆时峰值，0 不产生光照 |
| `glow` | 无量纲，有限，非负、无上界 | 1；空气散射光晕的倍率，同时缩放阈值半径与亮度，0 关闭该光源的光晕（物理化设计 §3.6） |
| `glare` | 无量纲，有限，非负、无上界 | 1；十字炫光的倍率，同时缩放臂根亮度与臂长，0 关闭该光源的星芒（物理化设计 §3.7） |
| `duration_ticks` | 整数 `[1,200]` | 6；按 20 TPS 游戏时间计的总寿命，暂停时冻结 |

`light` 缺省时用完整默认对象；只填部分字段时逐字段回落。非法值在内容包加载时带字段路径报错（codec 校验），运行时提交器再做有限性守卫（紧凑构造器收敛区间，非法条目由光源表统计并限频报告）。64 m、辐照度 4096、200 tick 是内容边界，随默认数值标定时复核；不复用曳光 8 m 上限。全局/类别客户端开关不改变该内容包对象。

### 8.2 强度包络

设连续游戏年龄为 `t`、持续时间 `T`，定义 `u=clamp(t/T,0,1)`：

```text
radius(t) = configuredRadius
I(t) = configuredIntensity * (1 - u*u*(3 - 2*u))
```

起爆时立即达到峰值，结束时平滑到 0；不除以波前半径，避免年龄为 0 时除零，也不把冲击波传播解释成火球扩张。空间衰减用整条链统一的 `w(d)/max(d², d_min²)`（`w = (1 − (d/R)⁴)²`，`d>=R` 时为 0；爆炸火光的 `d_min = 0.75 m`），算子见 `docs/plan/进行中/渲染-屏幕空间光照物理化设计.md` §3.2。有效辐照度再乘客户端火光倍率与全局倍率，落地形态是 `client/render/post/ExplosionLightSource.java#collect`。

首期配置固定半径；扩张半径、色温变化与多段包络不列为必填字段。若需要这些表现，后续增加可选项，不借用波前参数充当隐式火光曲线。

### 8.3 独立客户端生命周期

不能直接在 `ExplosionManager.visuals()` 中逐帧借用 `BlastFrontVisual` 作为唯一火光来源：`BlastFrontVisual.java#isFinished` 与 `ExplosionManager.java#tick` 会在波前结束时移除条目，火光寿命可能更长。

火光列表由客户端 `client/render/post/ExplosionLightState.java` 持有。起爆包在主线程被接受后，通过客户端接线钩子（`ExplosionManager#setLightSink` 注入，`client/MachineMaxClient.java` 安装）登记一次：起爆点、不可变 light 参数、接收时的连续游戏时间。列表按自己的 `duration_ticks` 结束，tick/渲染使用同一游戏时钟与插值口径；不用墙钟，也不每帧重复从波前表重建。独立保留 `Level`/维度归属，退出、换维度或世界卸载时清理。

开关关闭与容量拒绝只影响本帧提交，年龄照常推进；再次启用不会把已结束火光从头播放。波前与火光的计时互相独立，但来自同一次起爆通知；§10 验收两种寿命大小关系。

### 8.4 参数同步与服务器隔离

`common/mech/explosion/ExplosionParams.java#MAP_CODEC` 负责内容包、`ExplosionParams.java#STREAM_CODEC` 负责网络，`network/payload/explosion/ExplosionDetonatePayload.java#handle` 是客户端起爆入口。`light` 参数同时有 JSON 解码与网络编解码，客户端使用服务端发来的解析值，不重新读内容包。

载荷线格式变化同步提升了其所属 registrar 的版本：`network/MMPayloadRegistry.java#register` 把起爆包注册在 `sync:2.2.0` 下，让带 `light` 字段的线格式与旧端在握手阶段即被判定不兼容，而不是解出一包错位的参数集。`light` 里的 `glow` 与 `glare` 各占一个 float，两次字段扩充都抬了版本号。通用参数记录不含 Minecraft 客户端类型，客户端登记通过 client 包接线的回调完成，避免共通载荷/参数类在专用服务器校验时解析客户端类。

### 8.5 遮挡

火光使用 S2，绝对容差 1.0 m：爆点贴地、贴墙、夹在自己的火球与烟尘里是常态，容差太小会把整盏光判死；墙或车体明显挡在光心前面时，表面项与星芒跳过，不再照亮相机看不到的那一侧。这条判定是启发式而不是火光阴影——它只在光心投影处采一次深度，"爆心被挡住但某块可见表面仍被照到"与"光心可见但表面被挡住"两种情形都不精确，S3 未实现。

**光晕不走这条判定。** 它按逐像素 `t_hit` 截断，爆心被挡住而光晕球露出一半时只画露出来的那一半；套上 S2 会把那一半一起抹掉。火光的亮度与寿命验收不宣称已经完成火光阴影。

### 8.6 枪口火光：按弹种配置、按开火登记

枪口火光走与爆炸火光相同的通路，但有三个不同点：**配置挂在弹种上、参数不进网络、触发点是开火而不是起爆**。

| 维度 | 爆炸火光 | 枪口火光 |
| --- | --- | --- |
| 配置载体 | 爆炸参数的可选子对象 `light` | 弹种的可选子对象 `visual.muzzle_flash` |
| 参数来源 | 服务端解析后随起爆包同步 | 两端各自解析；客户端按本机弹种数据推导，不联网 |
| 触发 | 起爆包被接受 | 发射器 `onTick` 的客户端分支与调试物品的 `use`，经共通侧 `MuzzleFlashLight#emit` |
| 状态 | `ExplosionLightState` | `MuzzleFlashLightState` |
| 包络 | `1 - u²(3 - 2u)`：先亮住再收 | `(1 - u)²`：瞬间峰值、二次衰减 |
| 优先级 | 10 | 15 |

字段语义、缺省值与边界见 §2.4；缺省值在 `common/mech/projectile/ProjectileType.java#MuzzleFlash`，折算式在 `common/mech/projectile/MuzzleFlashLight.java#radiusFor`。

**为什么不同步。** 弹种数据两端各自加载且必须一致，客户端已经持有 `ProjectileType.get` 的同一条记录；再走一遍网络只会多一个包，并让 registrar 版本跟着一次纯表现改动漂移。代价是这一帧的闪光不由服务端授权——它与开火音效、枪口粒子同属一条客户端表现链，服务端不结算它们中的任何一个。

**为什么按弹种而不是按发射器。** 枪口粒子（`visual.fire_particles`）与开火音效（`sounds.fire_sounds`）已经按弹种配置，发射器只提供 `locator` 与 `fire_animation`，其属性里没有口径——而口径是"装药量有多大"在数据里的唯一载体。按弹种配置是唯一能按口径折算半径的落点；"同一种弹、不同枪的焰不一样"当前不表达，需要时给发射器加覆盖字段，而不是把整块搬到发射器上。

**每 tick 至多一条，强度不按发数累加。** 同一 tick 的多发落在枪口同一点，视觉无法区分（与 `LauncherSubsystem#playFireAnimation` 同粒度）；若按发数累加，实际亮度会随射速漂移，内容包的 `intensity` 就不再是一个可调的量。高射速下枪口焰靠"寿命覆盖射击间隔"表现为连续光，而不是靠叠加变亮。

**遮挡用 S2、容差 0.75 m。** 光心就在炮口，紧贴自己的炮管与炮口制退器——沿视线看过去它们比枪口本身近几十厘米是常态，容差小了会在自己开火时把这一发判死；车体或墙挡在光心前面时深度差是米级，判定成立，表面项与星芒整盏跳过，不再"隔着自己的车体发光"。光晕不受这条判定影响（§8.5）。

**状态上限 128 条/维度。** 正常负载是"每台发射器每 tick 至多一条 × 寿命窗口"，远低于上限；上限只兜异常输入（大量发射器同帧开火、调试物品连点），超出时丢最旧的一条——枪口焰是可丢弃的短命表现。

## 9. 载具车灯

### 9.1 数据与坐标

字段来自 `common/mech/subsystem/attr/static_attr/LightingSubsystemStaticAttr.java#CODEC`：`light_type`、`range`、`color`、`intensity`、`beam_angle`。激活/维度/刚体在世、定位器存在性与位姿插值复用 `client/render/renderer/LightSourceRenderer.java#render`、`LightSourceRenderer.java#isRenderable` 的口径；实施时提取共享采样帮助函数，避免两条消费者各自复制一套门禁。

失效清理只由明确的生命周期所有者执行，采集过程不为第二个消费者再修改共享集合。定位器方向取局部 **-Z**，与 `LightSourceRenderer.java#renderBeamLight` 一致，转到世界再转到视空间并归一化。

### 9.2 锥形衰减

`beam_angle` 在当前几何代码中是**全角（度）**，因为圆环半径按 `tan(beam_angle/2)*range` 计算。表面光采用外半角 `thetaOuter=beam_angle/2`，内半角初值 `thetaInner=0.8*thetaOuter`。设方向 D 从灯指向前方、受光点 P、光心 C：

```text
mu = dot(normalize(P-C), D)
cone = smoothstep(cos(thetaOuter), cos(thetaInner), mu)
```

内外角相等时用明确阶跃分支，不能调用边界相等的 smoothstep；`beam_angle=0` 作为退化灯禁用并诊断。距离小于数值 epsilon 时避免 normalize(0)。

`range` 在表面光中定义为到光心的欧氏支撑半径，锥光被同半径球截断。体积光几何现有 `range` 是轴向长度，宽锥边缘的两种距离不相同；P5 需核验边界观感，不能把二者描述为严格相同的照射体。

### 9.3 S3：可见深度中的近似遮挡

**已确认只要求屏幕空间近似。** 单层深度不含离屏几何和被前景完全盖住的表面，也不含未写入该深度目标的透明层。即使灯本身是点光，S2 的“相机到灯”判定也不等于“受光点到灯”的判定；这与灯泡是否总在视野内无关。

每个贡献显著的表面点 P，向光心 C 做有限线段检测。工程契约：

1. 距离/锥角/强度先筛掉无贡献像素，再做昂贵步进。阈值以未乘可见性的 RGB 最大分量定义，初值 `1/255`，需核验多弱光叠加时是否有可见损失。
2. 对线段做近裁面与视口裁剪，避免 `w=0`。从 P 朝 C 偏移起点，灯端也留小段排除区以减轻自遮挡；两者用米制参数，与 S2 的光心容差分开。
3. 屏幕步进必须透视正确：沿屏幕线段插值 `Q/w` 与 `1/w`，除回得到视空间深度；不能线性插值两个端点的米制深度。
4. 深度采用有限厚度区间，检查当前步覆盖的射线深度区间与场景表面厚度是否相交；不能把“射线在可见表面之后”一概视为命中，否则前景会产生过长的假阴影。
5. 结果区分 `HIT`、`NO_HIT` 与 `UNKNOWN`。离屏/近裁面裁断的未检测部分、预算耗尽、无有效深度等属于不完整证据。未得到命中的像素允许发光；这是减少误杀、接受漏光的明确策略，不等同于证明全线段无遮挡。
6. K=4/8/16 是质量/成本候选。必须记录步长、覆盖距离与预算耗尽率；步数增加可能改变采样位置，**不承诺图像误差单调下降**。没有历史累积时首期不用逐帧随机抖动掩盖条带。

方法依据：[McGuire 与 Mara，Efficient GPU Screen-Space Ray Tracing，§1–§4](https://jcgt.org/published/0003/04/04/paper.pdf)。上述命中/未知处理是本项目的设计选择。

验证场景必须让受光地面与遮挡墙同时出现在主视图，且墙在光线投影路径上留有足够宽的深度记录；普通“隔着实墙看墙后地面”的相机摆法没有可供验收的可见受光像素。实体与地形适用同一条深度判据，只要写入快照就可参与，不能声称 S3 天然排除实体遮挡。薄片、画外墙、被前景掩住的墙单列为局限用例。

### 9.4 S4 与体积光

S4 的目标系数为 `mix(1, max(dot(N, normalize(C-P)),0), normalWeight)`。法线从视空间重建点求得，方向统一朝相机；深度不连续处必须做边缘保护，不把跨物体的导数当成平面法线。无可信法线时回落为不乘法线项，避免整圈轮廓异常变黑。

这条系数已在共享片元着色器里实现（`screen_space_light.fsh` 的 `viewNormal`，取侧规则与回落条件见 `docs/plan/进行中/渲染-屏幕空间光照物理化设计.md` §3.5），因此曳光、爆炸火光与枪口火光同样接受朝向响应。权重由客户端配置 `screen_space_light_normal_weight` 给出，缺省 0.5，落地形式是 `o = max((1 − w) + w·cos, 0)`：掠射面保留 `1 − w` 的底，背光面仍为 0。P5 需要新增的是车灯侧的逐盏 `normalWeight` 字段，而不是响应本身。

若用 `dFdx/dFdy`，在所有相关片元一致执行的路径上先求导，再做逐像素早退/光源分支；分歧分支中的导数没有定义。当前实现走另一条路：显式取四邻域深度做差分，代价是每像素 4 次深度采样，与光源数无关。依据：[GLSL 1.50 §8.8](https://registry.khronos.org/OpenGL/specs/gl/GLSLangSpec.1.50.pdf)。

S3 与 S4 可独立实现、分别开关核验；不存在“S3 必须先实现，S4 才能工作”的算法依赖。完整车灯效果验收同时覆盖二者。

`LightSourceRenderer.java#renderBeamLight` 的三角光锥与 `LightSourceRenderer.java#renderPointLight` 的光晕承担空气中可见光形，表面光承担受光面。分别保存“只体积/只表面/两者同时”的对照，再标定体积 alpha；不得在 P1 顺手调低它，也不把这组几何称为物理体积散射解。

## 10. 分期与验收矩阵

| 阶段 | 实施范围 | 必须通过 |
| --- | --- | --- |
| P1（已落地） | 提取通路/光源表/曳光来源；完整 CPU 提交契约；来源优先级与诊断；16 槽 | §7 的目视观感对照、空候选、同键/溢出、生命周期；NaN/Infinity 与未配置条目被拒绝 |
| P2（已落地） | `light` 可选配置、网络同步、独立客户端火光状态、火光来源与阶段遮挡策略；光源表的影响体剔除 | 缺省/部分覆盖/禁用/非法字段；JSON 与网络往返；火光寿命短于及长于波前两种场景；暂停与换维度；起爆峰值到末尾零亮度；折射同屏正常 |
| P3 | 16/32 槽实测并固定默认 | 多来源争抢按优先级；同级按投影半径；拒绝和置换都计数；16/32 成本报告；编译/上传数组一致 |
| P4 | POINT 来源、共享门禁/定位器采样、体积光的显式调度 | 开关灯、失活/卸载、相机在影响球内、光心背后但球内表面可见、灯离屏但光斑入屏；深度快照不含后处理清屏结果 |
| P5 | SPOT、车灯 S3/S4、对应 GPU 字段 | 全角/半角与 -Z 轴正确；灯心不可见但表面受光；可见墙/车体遮挡；未知区域按约定漏光；法线平面/轮廓稳定；K=4/8/16 成本与误差对照 |

枪口火光不属于 P1–P5 的任一阶段：它复用 P1 的通路与 P2 的表现模式，是同一来源列表上的第三类实现，不改变容量、数组契约与优先级规则（§2.4、§8.6）。它的验收是目视：夜战开火时，枪口周围的地面与车体应随每一发闪一下，高射速下表现为连续光而不是逐发频闪。

共用矩阵：无光影/目标 Iris 版本与光影包、至少两种分辨率、FOV 改变、resize、暂停、退出重进、加载失败恢复。记录版本、GPU、分辨率、相机、场景与调试输入，不能只写“开光影测试过”。

遮挡量化：固定灯/相机，标注可见受光区域中的被挡 ROI 与未挡 ROI；以同场景关灯帧为基线，分别比较开灯 S3 开/关的 RGB 增量。排除轮廓一个像素带后，测试中已检测命中的像素应无该灯贡献；未挡区域不得整片误杀。另输出命中/未知掩码、漏光面积比例。最终容差和帧时间预算随实测记录确定，不编造已通过数字。

纯 CPU 选择、配置解码与包络属于可自动断言的范畴，需要另建测试载体；P1 的等价验收按 §7 由用户实机目视完成，P2 的火光亮度与寿命、枪口火光的强度与寿命同样按目视验收，都不依赖该载体。GL 状态、遮挡、光影兼容和 GPU 时间需客户端验证。本次设计审阅没有执行这些未来实现的验收。

## 11. 配置与兼容迁移

曳光的现有配置键 `client/MMClientConfig.java#TRACER_LIGHT_ENABLED` 与 `client/MMClientConfig.java#TRACER_LIGHT_INTENSITY` 保留其曳光语义，用户已经调整的值继续生效。通用总开关与总倍率、火光与枪口火光的类别键都在 `client/MMClientConfig.java` 落地，各类别键互相独立：

| 配置 | 语义与默认 |
| --- | --- |
| `screen_space_light_enabled` / `screen_space_light_intensity` | 所有表面光照总开关 true / 全局倍率 1（已落地） |
| `tracer_light_enabled` / `tracer_light_intensity` | 曳光类别开关/倍率，沿用现有用户值（已落地） |
| `explosion_light_enabled` / `explosion_light_intensity` | 火光类别开关 true / 倍率 1（已落地） |
| `muzzle_flash_light_enabled` / `muzzle_flash_light_intensity` | 枪口火光类别开关 true / 倍率 1（已落地） |
| `vehicle_light_enabled` / `vehicle_light_intensity` | 车灯表面光类别开关 true / 倍率 1；P4 接入 |
| 弹种 `tracer_light_intensity` / `tracer_light_radius` / `tracer_light_color` / `tracer_light_enabled` | 每种弹的光源强度、半径、颜色与独立开关，与客户端同名键处于不同数据域；语义见 `docs/plan/计划中/武器系统-投射物曳光光照设计.md` §11.1 |
| 弹种 `visual.muzzle_flash.*` | 每种弹的枪口火光参数（开关、半径、颜色、强度、寿命），两端各自解析、不同步；语义见 §2.4、§8.6 |
| 爆炸参数 `light.*` | §8 的每次爆炸表现参数，服务端内容包解析并同步 |

每条光源最终辐照度为 `内容辐照度（1 m 处）× 时间包络 × 类别倍率 × 全局倍率`（曳光另含自身 alpha），每项只乘一次。总开关关闭时跳过全部来源采集与本光照链工作；瞬态状态的年龄维护照常。类别开关不控制体积光、起爆粒子或折射。

这是兼容保留类别键并增加总开关的方案，**不把玩家的曳光设置重命名成总设置、也不丢弃已有值**。所有内容包字段均可缺省，不增加必填项。

## 13. 已定事项、风险与待测项

| 类别 | 内容 | 处理 |
| --- | --- | --- |
| 用户已定 | 接受屏幕空间遮挡近似 | 可见深度内验收；离屏/隐藏几何列为能力边界，不承诺全视角阴影 |
| 用户已定 | 火光独立配置，缺省统一数值、按弹种覆盖 | §8；不从波前大小或伤害推导默认光照 |
| 用户已定 | 枪口火光按弹种配置、默认开启、半径按口径折算 | §2.4、§8.6；内容包不写 `muzzle_flash` 也能用（缺省辐照度 90），需要关掉时写 `muzzle_flash.enabled = false` |
| 用户已定 | P1 等价验收由用户在主视图实机目视完成 | §7 的观感等价行；不建立数组级或逐像素自动断言 |
| 设计建议 | 严格类别优先级、保留曳光配置并增加总开关 | §5.2、§11；容量饿死与配置语义明确可见 |
| 待标定 | 火光默认颜色/半径/辐照度/寿命及字段边界 | §8.1 的数值已作为缺省值落地（§2.3），客户端标定后记录最终值 |
| 待标定 | 枪口火光默认颜色/半径/辐照度/寿命及字段边界 | §2.4 的数值已作为缺省值落地（`ProjectileType.MuzzleFlash#DEFAULT`），客户端标定后记录最终值 |
| 待实测 | 32 槽、S3 步数/厚度/偏置、帧时间预算 | P3/P5 分别给出测量，不能据 uniform 余量推断性能 |
| 已知近似 | LDR 已着色画面上叠光，透明/粒子颜色可能对应背景深度 | 不声称材质正确或每一透明层独立受光 |
| 已定 | 表面光照算子取物理形状 + 有界合成：`color · I · o · w(d) / max(d², d_min²)` 求和、经 `1 − (1 − C)/(1 + e·q)` 映射，线性空间、逐通道；`o` 是朝向响应（S4，权重可配置），仍无 albedo | 方案、标定与分阶段计划见 `docs/plan/进行中/渲染-屏幕空间光照物理化设计.md`；本文 §2.2、§8.2 与 §9.4 的算子描述与它一致 |
| 已知近似 | 火光遮挡是 S2（容差 1.0 m）：只判定光心，不判定受光表面；爆心被挡住而可见表面仍被直接照到时判定站在"挡住"一侧 | §8.5；不声称火光阴影已完成，S3 不作为 P5 的必要范围 |
| 已知近似 | 枪口火光遮挡是 S2（容差 0.75 m）：容差为炮管与制退器留出余量，因此枪口紧贴车体侧面时可能仍然漏一点光 | §8.6；不声称枪口焰有阴影，容差是要与人眼观感一起调的 |
| 已知行为 | 链尾回写清主目标深度，Iris 手部可能失去世界遮挡 | `client/render/post/AGENTS.md` 的次序记录；P1 保持，P4 保证体积几何在清除前画完 |
| 生命周期风险 | 瞬态光源在关效果、超容量、换世界时残留 | 独立年龄推进、按 Level 清理；不能依靠是否入选决定寿命 |
| 容量风险 | 高射速武器持续开火时枪口火光长期占用一个槽位（优先级 15，排在曳光之前） | P3 实测多来源争抢；若曳光显著缺失，先调 `MUZZLE_FLASH` 常量而不是改选择规则 |
| 范围外 | 离屏 FBO、资源自动重载、完整阴影、时间累积 | 需要独立实施与验收，不能由主视图链自动获得 |
