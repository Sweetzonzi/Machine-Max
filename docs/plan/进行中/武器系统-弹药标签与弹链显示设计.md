## 一、要解决的问题

### 1.1 现象

武器状态 HUD 需要显示弹种与弹链，但界面上出现的是内部标识符：

```
machine_max:50mm_pzgr39
```

设计目标是把同一处显示为：

```
AP
```

### 1.2 根因

投射物定义里**已经**写着弹种标识（`registryKey`），但没有任何代码把它映射成玩家可见的文本——没有 API，语言文件里也没有对应的键。以 120mm 尾翼稳定脱壳穿甲弹为例：

```json
// 注册键 = machine_max:120mm_apfsds
"tags": ["machine_max:caliber/120mm", "machine_max:ammo/apfsds"]
```

`tags` 字段的语义是**发射器弹药兼容性匹配**（与 `required_tags` / `acceptable_tags` / `forbidden_tags` 比对），其中的 `ammo/*` 项同时充当了弹种分类。

本设计的做法是让显示文本取自**弹种自己的翻译键**：`registryKey` 经 `ResourceLocation.toLanguageKey()` 得到 `machine_max.120mm_apfsds`，由该弹种所属的内容包在自己的 `lang/<locale>.json` 里给出文本（§3.5）。语言文件按命名空间跨内容包合并（§3.5.1），因此同一个命名空间下的多个包各自补自己的键即可，不需要约定"谁独占哪个键"。

`tags` 继续以完整列表参与兼容性比对，显示逻辑不读它（§3.3）。

### 1.3 已声明但未接线的方法

`IAmmoSupplier` 已经声明了一个明确标注为 HUD 用途的方法：

```java
/** HUD 弹种标签 */
String getLabel();
```

两个实现类（`RegenLoaderSubsystem`、`AmmoLoaderSubsystem`）都返回资源标识符字符串：

| 实现 | 返回值 |
| --- | --- |
| `RegenLoaderSubsystem` | `attr.projectileTypes.get(归一化指针).toString()`，即 `machine_max:50mm_pzgr39` |
| `AmmoLoaderSubsystem` | 有弹药时 `getSuppliedType().getRegistryKey().toString()`；无弹药时 `empty` |

本次落地前，全库检索 `getLabel` 只有上述三处：一处声明、两处实现，零调用点——因此这次改动是把既有声明接到 HUD 上，而不是改动既有行为。落地后它由两个位置取值：`RegenLoaderSubsystem` 把它实现为转发 `getBeltLabel()`（§4.2），HUD 在供给者不是再生装弹机时退回调用它（§6.2.5）。

`AmmoLoaderSubsystem`（物品弹药装填机）尚在实现中：它不被 `WeaponControllerSubsystem.rebuildAmmoPool()` 收集（该方法只收 `RegenLoaderSubsystem`，见 `WeaponControllerSubsystem.java:294`），内容包里也还没有装配实例。本设计只约束 `RegenLoaderSubsystem` 一侧；`AmmoLoaderSubsystem.getLabel()` 待其完工后按 §4.3 对齐。

### 1.4 由此引出的界面缺口

武器状态 HUD 期望按弹链列出余量（每条弹链一个选项卡，显示该弹链的剩余发数），需要三类文本：

| 文本 | 取数性质 | 用途 | 示例 |
| --- | --- | --- | --- |
| **弹种展示名** | 弹链**外**的独立量 | 单个弹种的展示名，不依赖任何弹链上下文 | `APFSDS`、`HE`、`ATGM` |
| **当前弹种** | **膛内态**（空膛时退回**指针态**：随弹链指针逐发变化） | 弹种槽 | `AP` → `HE` → `AP` … |
| **弹链名** | **弹链态**：整条弹链的展示名 | 弹链选项卡 | `穿甲`、`曳光`、`AP/HE` |

后两者是**不同的语义层**，服务于 HUD 上两个不同的槽位：同一弹链内射击时指针改变而弹链名不变；替换弹链时弹链名改变而指针归位。

### 1.5 现有 HUD 与原型 HUD 的差异

当前装备的简易 HUD（`AmmoHud`，Java 逐行绘制）按武器控制器分组，每个发射器渲染一个**两行组**，并在组前先画一行控制器标题（子系统名走语言键）：

```
<武器控制器名>
  <弹种名>  <当前>/<总量>          ← 当前 = 该发射器供给者的余量；总量 = 弹药池中选中弹链的聚合余量
  <装填进度条 + 百分比 / READY / EMPTY>
```

总计量的 `∞` 分支（供给者无容量概念时）与 `EMPTY` / `READY` 状态尾标也都由该实现绘制。

此外该实现有一处口径不一致：两行都归属"发射器"，但**第一行的分子取单一供给者、分母取池级聚合**（`AmmoHud.java:108-118`），两个数在"同一条弹链配了多个弹仓"时并不同源。本设计的正式页不沿用这种分子分母不同源的写法：弹种槽的计数与上限都取**供弹弹链在弹药池里的全部装弹机**（§4.5），与选项卡的余量同源。

**该实现在任何位置都不显示弹链名**——它只有"弹种"这一个文本量，取自发射器当前弹种。

原型 HTML HUD 在此之上增加了弹链选项卡一层：

```html
<span class="w-ammo">APFSDS</span>          <!-- 弹种槽 -->
<span class="w-count">24<span class="w-cap">/30</span></span>
...
<div class="w-tabs">
  <span class="tab is-on">ATGM <b>4</b></span>   <!-- 弹链选项卡：弹链名 + 该弹链余量 -->
  <span class="tab">HE <b>8</b></span>
</div>
```

因此**本设计要补的是"弹链名"这个量本身**，并明确它与弹种槽是两个独立的量：简易 HUD 只有前者，原型同时需要两者。

这意味着标签体系需要分别提供两处文本，且**两处的取数规则相互独立**——不是一条规则的两个出口。

阶段三摘除 `ammo_hud` 图层注册后，AUI 正式页是唯一在绘制的武器状态 HUD；`AmmoHud` 类文件保留在仓库中作为回退（§6.3）。本节描述的差异因此读作两个页面的对照，而不是两处在同时显示。

### 1.6 页面结构与现有数据模型的映射

HUD 的**一个武器块对应一个武器控制器**（`WeaponControllerSubsystem`）。块内的两组元素各有独立口径：

| 元素 | 口径 | 取数 |
| --- | --- | --- |
| 选项卡 | 条数 = 该控制器**可选弹链数** | 弹链名（链 C） + 该弹链在弹药池中的聚合余量 |
| 装填条 | 段数 = 该控制器下的**发射器数** | 一段 = 一根管：膛内有弹取**膛内态**（常亮），空膛取该管供给者的 `getStatus()` / `getReloadProgress()` |
| 弹种槽 | 单值，**膛内态**；空膛时退回**指针态** | 第一根膛内有弹的管的膛内弹种；都没有膛内弹时取供给者的指针态那一发（链 B） |

一个武器控制器同时只有一条选定弹链，由 `selectedBelt` 表示；`.is-on` 即标记当前**负责供弹**的那一条。控制器建起弹药池后总会选中一条：建池时默认选中排序第一条（按第一发弹种的资源地址升序），选中的链随结构变化消失时改选，因此 `selectedBelt` 只在弹药池为空时为 `null`（那时没有可选的链，路由落到无弹链的兜底供给者）。HUD 直接读 `selectedBelt`；它取不到值只发生在弹药池尚未建起的窗口（刚载入、握手未完成），此时取 `getAvailableBelts()` 的第一条兜底。**高亮因此恒定恰好落在一条选项卡上**，不会出现一条都不亮的情形。

三处口径互不推导：可切换的量是**弹链**（`selectedBelt`），装填状态是**发射器态**（一段一根管），弹种槽是**膛内态**（空膛时退回指针态）。同一控制器下的不同发射器可以装填不同弹种，因此弹种槽与服务多管的装填条必须分别取数；弹种槽只有一个，取显示顺序里第一根有膛内弹的管。

**本设计只定义"每条弹链叫什么"与"当前弹种是什么"，不定义选项卡与装填条的分组与渲染**。它们的取舍属于 HUD 的数据装配，见 §6.2.5 的槽位取法。

## 二、术语与既有数据模型

本文使用以下符号。全部为代码中已存在的实体。

| 符号 | 含义 |
| --- | --- |
| `ProjectileType` | 投射物类型抽象基类，对应一个 `projectiles/*.json` 文件 |
| `ProjectileType.tags` | `List<ResourceLocation>`，该投射物的标签列表，JSON 中的 `"tags"`。**只参与发射器兼容性匹配，不参与显示** |
| `ProjectileType.registryKey` | 该投射物的注册键，如 `machine_max:50mm_pzgr39`。经 `toLanguageKey()` 得到弹种展示名的语言键 |
| `RegenLoaderSubsystem` | 再生装弹机子系统，弹药的供给方 |
| `attr.projectileTypesMap` | `Map<ResourceLocation, Integer>`，JSON 中的 `projectile_types`，键为弹种、值为条数 |
| `attr.projectileTypes` | `List<ResourceLocation>`，由 `projectileTypesMap` 逐项按条数展开得到的**展平弹链** |
| `attr.beltLabel` | 装弹机实例上的可选字段 `belt_label`，弹链名的作者声明值 |
| `ammo_count` | 装弹机的**单一**弹药计数，整条弹链共用 |
| `belt_index` | 弹链指针，指示下一发从展平弹链的哪一位取出 |
| `selectedBelt` | `WeaponControllerSubsystem` 当前选中的弹链（展平列表），同时只有一条；弹药池非空时总有一条被选中（建池时默认选中排序第一条） |
| `WeaponControllerSubsystem` | 武器控制器，负责弹链选择与弹药路由。HUD 的一个武器块对应一个控制器 |
| `ammoPool` | `Map<List<ResourceLocation>, List<LoaderEntry>>`，按**展平弹链**分组的弹药池 |

### 2.1 弹链是"有序循环的弹种引用序列"

展平规则为逐项按条数展开，例如：

```
{7_92mm_smk: 3, 7_92mm_tracer: 1}  →  [smk, smk, smk, tracer]
```

发射时按指针顺序取用并循环推进，因此**混装弹链是真实存在的**，K-17 炮塔就配了三条：

| 装弹机 | `projectile_types` | 展平弹链 |
| --- | --- | --- |
| 2A42 机关炮 | `{30mm_ap: 1, 30mm_he: 1}` | `[ap, he]` |
| PKTM 机枪 | `{7_62mm_ap: 3, 7_62mm_tracer: 1}` | `[ap, ap, ap, tracer]` |
| ATGM 管 ×4（四条独立弹仓，构成相同） | `{9m133_kornet: 1}` | `[kornet]` |

### 2.2 弹药计数是弹链级的，不分弹种

`ammo_count` 是整条弹链共用的一个数。混装弹链不存在"每个弹种各自剩几发"这种量——弹种由指针顺序决定，不由库存决定。

**由此确定的设计判据：显示单位是弹链，不是弹种。** 混装弹链只报告"这条弹链剩 N 发"。按弹种分解余量不在本设计范围内；弹药池在"同一条弹链配了多个弹仓"时的聚合口径见 §8.1。

### 2.3 `ammoPool` 以展平弹链为身份

`WeaponControllerSubsystem.rebuildAmmoPool()` 以 `attr.projectileTypes`（展平列表）作为弹药池的键。**构成相同 = 同一条弹链身份**，因此：

- 四个 ATGM 装弹机（弹链全同）合并为一个弹药池条目，各自通过 `LoaderEntry.channel` 区分；
- 构成不同即为不同条目，互不影响。

这条性质是本节全部设计的前提：**弹药池的键是展平弹链，不含 `belt_label`，因此弹链名不参与弹链身份。**

## 三、标签设计

### 3.1 三条解析链

三条链各自**取第一个非空结果，命中即停**，且**互不推导**。

**A. 弹种展示名**（`ProjectileType` 提供）：

```
① 弹种自己的翻译键
       → Component.translatable(键).getString()，键 = registryKey.toLanguageKey()，如 machine_max.50mm_pzgr39
② 语言文件中没有该键 → Component.translatable 原样返回键字符串，如 machine_max.50mm_pzgr39
```

链 A 只有一个层级，层级 ② 不是预设的兜底分支，而是"键缺失时 `Component.translatable` 的返回值"这一事实（§3.4）。内容包必须为自己的每个弹种补键——这条是作者侧约定，见 §3.7。

**B. 当前弹种**（`RegenLoaderSubsystem` 提供）：

```
① 弹链指针所指的那一发，取其弹种展示名（即链 A）
② 弹链为空或该发尚未解码为投射物类型时 → 取该资源的 path
```

链 B 是**指针态**：指针逐发推进，返回值随弹链构成循环。

指针的取值载体是 `SynchedEntityData` 的 `BELT_INDEX`，不得读普通字段 `projectileTypeIndex`——两者在客户端不一致，§3.9 给出机制与修法。**该读取方式是链 B 的组成部分，不是可选的实现细节。**

**C. 弹链名**（`RegenLoaderSubsystem` 提供）：

```
① attr 的 belt_label 字段非空   → 原样返回，不走语言文件
② 弹链首发的弹种展示名（即链 A） → 委托给 ProjectileType
③ 首发尚未解码为投射物类型时    → 取该资源的 path
④ 弹链为空                     → 返回 "---"
```

链 C 是**弹链态**：不读指针，同一弹链的返回值恒定。

链 A 与链 C 的层级 ② 取的是同一个量——弹种的展示名。二者仍要分成两条链，因为链 B 引入了指针，链 C 引入了 `belt_label` 与空链兜底。

### 3.1.1 为什么链 C 不自动推导

链 C 的层级 ② 取"首发弹种的展示名"是一个**简化**，不是精确描述。作者用 `belt_label` 覆盖它。

曾考虑让链 C 遍历弹链、把各发弹种名去重后拼接（`[ap, he]` → `AP/HE`），该方案被否决，理由是**推导出的名字无法承担区分的职责，而名字的职责是给玩家读**：

| 弹链 | 拼接推导结果 | 问题 |
| --- | --- | --- |
| `[ap, he]` | `AP/HE` | 可读 |
| `{ap:3, tracer:1}` | `AP/曳光` | 可读 |
| `{ap:1, tracer:3}` | `AP/曳光` | **与上一行完全相同** |

两种配比对玩家意味着完全不同的武器行为（以穿甲为主 vs 以曳光为主），推导结果却一致；反过来，若把配比也编进名字（`AP×3/曳光`），名字就不再是玩家用语。

**因此推导不解决问题，只是把"名字不精确"从显式字段挪到了隐式规则里。** 判据是：

- 自动值只需**可读且不误导**——首发弹种的展示名满足这两点（弹链以穿甲弹开头，叫它 `AP` 不构成错误陈述）；
- 需要精确时由 `belt_label` 显式给出，此时它是作者的声明而非代码的推断；
- **两条弹链显示同一个名字不是缺陷**：它们本就该叫同一个名字时，同名才是正确结果。选项卡的重名由选中态（`.is-on`）与各自余量区分，不依赖名字唯一。

### 3.1.2 两层在 2A42 混装弹链上的对照

以 K-17 的 2A42 装弹机（`{30mm_ap: 1, 30mm_he: 1}`）为例：

| 槽位 | 取链 | 连续射击时的取值 |
| --- | --- | --- |
| 弹种槽 | **膛内态**（空膛的那一两 tick 退回 B 的指针态） | `AP` → `HE` → `AP` → `HE` … |
| 弹链选项卡 | C（弹链态） | 恒为 `AP`；作者填 `"belt_label": "AP/HE"` 后恒为 `AP/HE` |

若只提供链 B（即现有简易 HUD 的形态），选项卡没有可取的值；若只提供链 C，弹种槽无法随指针变化。两个槽位的差异是本设计提供两条链的原因。

### 3.2 明确排除的候选

以下候选**不采用**。

| 排除项 | 理由 |
| --- | --- |
| 用 `tags` 里的 `ammo/*` 当展示文本的来源 | `tags` 是兼容性标签表，聚合了许多弹种共有的分类（`ap` 覆盖 5 个弹种）。把它当展示来源会引入一个与弹种并行的键空间，且该键空间由多个内容包共享（§3.5.1）。展示文本改为直接取弹种自己的翻译键。 |
| 兜底到 `tags` 的第一条（`caliber/*`） | 标签列表的书写顺序是 `caliber/*` 在前、`ammo/*` 在后（全部 12 个投射物定义均如此）。取第一条会得到 `machine_max:caliber/120mm`，语言文件中通常不存在对应键，界面会显示 `machine_max.caliber.120mm`。口径是第二个文本量（弹链详情），不属于弹种展示名。 |
| 弹链名由构成自动推导 | 推导结果无法承担区分职责：`{ap:3, tracer:1}` 与 `{ap:1, tracer:3}` 推导结果相同，而两者对玩家意味着不同的武器行为。详见 §3.1.1。 |
| 每个弹种一个可选的"每发子标签" | 没有消费场景：弹种展示名与弹链名已覆盖"弹种槽"与"弹链选项卡"两处显示，中间层无位置可放。 |
| 标签中带格式化参数（`%s`） | 会把标签变成模板，随之需要定义参数从何而来。统一使用无参 `getString()`。 |

### 3.3 `tags` 只参与匹配

`tags` 字段继续以完整列表参与发射器的兼容性比对（`caliber/*` 与 `ammo/*` 同样参与），**显示逻辑一律不读它**：

- **禁止**修改 `ProjectileType.getTags()` 的返回值；
- **禁止**让显示路径依赖 `tags` 的顺序或内容。

违反这两条会把"显示"与"口径匹配"耦合成一处：前者需要改标签，后者会因此改坏。`ammo/*` 在内容包里继续充当作者的分类体系（例如按 `ammo/ap` 归拢各型穿甲弹），界面上的文本不取自它。

### 3.4 空串与语言键缺失的行为

| 输入 | 行为 |
| --- | --- |
| `belt_label` 为空串 | 视为**未填写**，落到链条下一层 |
| 弹种的语言键缺失 | `Component.translatable` 返回键字符串本身，即界面显示 `machine_max.120mm_apfsds` |
| 语言文件中该键的值是空串 | 视为空，落到链条下一层 |
| 投射物定义不存在（内容包缺失/解码失败） | 弹种展示名的来源本就是注册键，不受影响；链 B / 链 C 落到层级 ②③，返回该资源的 path，如 `7_92mm_tracer` |
| 弹链为空 | 链 C 返回 `---`（链 B 无取值，弹种槽留空） |

**语言键缺失时显示键本身是刻意的**（fail-visible）：内容包作者漏写语言键时，界面直接暴露缺失的键，比显示空白更容易定位。

### 3.5 语言键与语言文件

弹种展示名的语言键由 `ResourceLocation.toLanguageKey()` 生成，格式为 `<namespace>.<path>`，其中 `/` **保留不替换**（该方法只做命名空间与路径的拼接，不替换路径里的任何字符）：

| 资源标识符 | 语言键 | 归属 |
| --- | --- | --- |
| `machine_max:50mm_pzgr39` | `machine_max.50mm_pzgr39` | 该弹种所在的内容包 |
| `machine_max:ammo/apfsds` | `machine_max.ammo/apfsds` | 假设的弹种：路径含 `/` 时键里同样含 `/` |

现有 12 个弹种的路径都是扁平的（`120mm_apfsds`、`7_62mm_ap` 等），因此实际弹种键里不出现 `/`。§3.5.2 的通用分类键是**手写键**，不是从任何注册键推导出来的，与这条拼接规则无关。

键写在内容包的 `lang/<locale>.json` 里，路径为：

```
spark_modules/<内容包>/<命名空间>/lang/<locale>.json
```

`<locale>` 取 `zh_cn`、`en_us`、`zh_tw`、`zh_hk` 等标准语言代码，文件名即语言代码。

#### 3.5.1 多个包写同一命名空间时的合并规则

语言文件**按键合并，不按文件覆盖**。Spark-Core 的资源模块按 `命名空间:lang/<locale>.json` 为身份收集所有内容包的贡献，再按**内容包依赖拓扑序**逐份合并进同一张表：

| 环节 | 规则 |
| --- | --- |
| 收集身份 | `命名空间:lang/<locale>.json`，与内容包目录名无关 |
| 合并顺序 | 内容包依赖图的拓扑序：被依赖者先入表 |
| 同名键 | **依赖序靠后的包覆盖靠前的包** |
| 中文变体 | `zh_cn` / `zh_tw` / `zh_hk` 之间互相补足缺失键 |
| 英文兜底 | 中文表缺失的键再用 `en_us` 表补足 |
| 生效范围 | 仅客户端（`LangModule.mode = CLIENT_LOCAL_ONLY`）：外部包的语言表只在客户端注入 |

由此得到两条对内容包作者的直接影响：

- **基础键放 `builtin` 包最合适**：该包不依赖任何包，其余内容包都依赖它，所以它的键天然是最底层、可被任意包覆盖；
- **同一个命名空间下的多个包不会互相抹掉键**：各自补自己的弹种键即可，只有**同名键**才会区分先后。

#### 3.5.2 通用分类键放 `builtin` 包

`builtin` 包（`spark_modules/machine_max.builtin/machine_max/lang/`）提供一套**通用分类键** `machine_max.ammo.*`，覆盖常见弹种缩写。两个用途：

- 第三方内容包可以借用通用键来表达分类，例如给自己的 `belt_label` 抄一份短名，或在自己的弹种名里引用同一套措辞，从而不必为每种弹重写一遍；
- `builtin` 是依赖图的最底层，因此它是唯一适合承载"全库共用的键"的位置（§3.5.1）。

通用键是**可选的便利层**，不是显示链的一环：链 A 不查它，包不借用它就完全用不到；键名是手写的，不与任何注册键的拼写规则挂钩（§3.5）。建议的键与取值：

| 键 | `zh_cn` | `en_us` |
| --- | --- | --- |
| `machine_max.ammo.ap` | `AP` | `AP` |
| `machine_max.ammo.apfsds` | `脱穿` | `APFSDS` |
| `machine_max.ammo.heat` | `破甲` | `HEAT` |
| `machine_max.ammo.he` | `HE` | `HE` |
| `machine_max.ammo.tracer` | `曳光` | `TRACER` |
| `machine_max.ammo.atgm` | `ATGM` | `ATGM` |

### 3.6 `belt_label` 的定位

`belt_label` 是**可选**字段，用于给弹链起一个比自动值更准确的名字。链 C 的层级 ② 只取首发弹种的展示名，因此任何"弹链不止一种弹"或"弹链可用更贴切的名字描述"的情形都由该字段表达：

```jsonc
// 混装弹链：自动值会是 "AP"，作者声明它叫什么
{ "belt_label": "AP/HE", "projectile_types": { "machine_max:30mm_ap": 1, "machine_max:30mm_he": 1 } }

// 配比不同、自动值无法区分的一对：靠显式名字区分
{ "belt_label": "穿甲", "projectile_types": { "machine_max:7_62mm_ap": 3, "machine_max:7_62mm_tracer": 1 } }
{ "belt_label": "曳光", "projectile_types": { "machine_max:7_62mm_ap": 1, "machine_max:7_62mm_tracer": 3 } }
```

**该字段按字面返回，不查语言文件**：填什么就显示什么，因此它不受玩家语言影响。需要多语言时把弹链名交给层级 ②（弹种展示名走语言键），或按 §3.5.1 的合并规则给各语言各写一份定义——弹链定义属于内容包数据，可以按包分发。

**两条弹链显示同一个名字不构成缺陷。** 名字是给玩家读的语义标签，不是弹链的唯一键。选项卡的重名由选中态与各自余量区分（§3.1.1）。

**该字段只影响链 C，不影响链 B。** 弹种槽始终报告指针所指的真实弹种，不会因为作者给弹链起了别名而改变——`belt_label: "穿甲"` 的混装弹链，其弹种槽仍会在 `AP` 与 `HE` 之间切换。

**该字段不参与弹链身份。** 它不进入 `ammoPool` 的键，因此改动它不会影响弹药池分组、路由或已装填载具的状态。这一条是本设计可以安全增量落地的依据。

### 3.9 弹链指针的唯一载体是 `SynchedEntityData`

链 B 取"指针所指的那一发"，因此它的正确性取决于**客户端能否读到服务端的指针**。本节是链 B 的前置条件，落地于阶段一（§6.1 第 5 项）。

指针存在 `RegenLoaderSubsystem` 的 `SynchedEntityData` 访问器 `BELT_INDEX` 里，服务端与客户端读同一个来源：

| 环节 | 写入 |
| --- | --- |
| 每发推进（`consumeReadyRound()`） | 把 `(当前指针 + 1) % 弹链长度` 写入 `BELT_INDEX`，双端都写 |
| 读指针（`normalizedBeltIndex()`） | 读 `BELT_INDEX`；越界时把 `Math.floorMod` 折回后的修正值写回该访问器，下次保存即为合法值 |
| 存档恢复（`loadData()`） | 把 NBT 的 `belt_index` 写入 `BELT_INDEX` |
| 存档写出（`saveData()`） | 从 `BELT_INDEX` 取值写进 NBT |

服务端写入该访问器后，按 `AbstractSubsystem.onTick()` 的增量推送自动送达客户端，客户端因此不需要自行从 NBT 恢复起点；服务端从存档恢复时同样经由该访问器，读到的就是存档里的真实指针。

**为什么必须单一载体**：普通字段与访问器并存时，普通字段由 `loadData()` 从 NBT 恢复、访问器由服务端每发写入，而客户端只有访问器这条路径（装弹机的 `onTick()` 与发射器的开火循环双端都执行，`consumeReadyRound()` 在客户端也会推进）。两条载体各自独立推进且无对账机制，首发射击起即错位，表现是弹种槽的文本停留或漂移在弹链首位附近。因此指针的读写全部经由 `BELT_INDEX`：两端都以它为准，指针不会各自走偏。

`normalizedBeltIndex()` 的折回修正因此也写进访问器，而不是写进一个普通字段：越界只可能来自"改内容包后弹链变短而存档指针仍指向旧位置"，修正值写回访问器后才会随存档保存。

链 C（弹链名）不受本节影响：它取首发而非指针位置。

## 四、API 契约

### 4.1 `ProjectileType`

| 方法 | 返回 | 契约 |
| --- | --- | --- |
| `getDisplayLabel()` | `String` | §3.1 链 A。取 `registryKey.toLanguageKey()` 对应的文本。**该方法的返回值不保证唯一**，不得用于比对或查找。 |

弹种展示名是**单发**语义：它只描述一个弹种，不知道任何弹链上下文。弹链相关文本由 `RegenLoaderSubsystem` 提供。

`getDisplayLabel()` 可能在客户端被每帧调用（HUD 刷新），实现内部不做缓存：一次 `toLanguageKey()` 加一次 `Component.translatable(...).getString()`，两者都是廉价操作。

**只在客户端调用**：文本取自客户端的语言表；专用服务器的语言表只加载原版 `en_us`，内容包的键在服务端取不到取值（`Component` 原样返回键名），因此服务端逻辑（Jade 服务端侧、AI、命令输出）不要用它——需要弹种标识时用 `registryKey`。该方法属于共通包，客户端调用不会引入分发问题。

### 4.2 `RegenLoaderSubsystem`

| 方法 | 返回 | 契约 |
| --- | --- | --- |
| `getCurrentRoundLabel()` | `String` | §3.1 链 B。读**指针所指的那一发**。 |
| `getBeltLabel()` | `String` | §3.1 链 C。不读指针，同一弹链的返回值恒定。弹链为空时返回 `---`。 |
| `getLabel()` | `String` | `IAmmoSupplier` 的既有方法，实现为转发 `getBeltLabel()`。 |

`getCurrentRoundLabel()` 的指针来源是 `SynchedEntityData` 中的 `BELT_INDEX`，这是弹链指针的唯一载体（§3.9）。该取值方式使本方法在客户端可用。

两个方法在纯弹种弹链上返回同一个字符串（首发＝指针所指的唯一弹种），除非作者填了 `belt_label`；在混装弹链上，`getCurrentRoundLabel()` 随指针变化而 `getBeltLabel()` 恒定。两者服务于 HUD 的两个槽位，不是彼此的冗余实现。

`getStatus()` / `getReloadProgress()` 对"弹仓空了但正在逐发再生"的型号报**装填中 + 再生进度**：按 `regen_per_minute` 产弹的型号（`reload_time=0`）没有输送计时器，若照"没弹就是 `EMPTY`"报，打空后的整段再生时间在 HUD 的装填条上是一片熄灭，看不出它正在回弹。批量再生（`regen_round_by_round=false`）的型号本来就在冷却期间报 `RELOADING` 与冷却进度，两者口径一致。

### 4.3 `AmmoLoaderSubsystem`

物品弹药装填机尚在实现中（§1.3）：它不进 `ammoPool`，内容包里也没有装配实例，因此本阶段的 HUD 取数不经过它。

待其完工后，其 `getLabel()` 应对齐同一套文本规则：有弹药时取 `getSuppliedType().getDisplayLabel()`，无弹药时的返回值另定（不沿用裸字符串 `empty`，那会绕过语言文件）。

### 4.4 `IAmmoSupplier`

`getLabel()` 的 Javadoc 写明两点：

- 返回值**仅供显示**，不得用于比对、查找或路由；
- **只在客户端调用**（§4.1）。

`IAmmoSupplier` 的其他成员（`getSuppliedType()`、`getRemainingCount()`、`getStatus()`、`getReloadProgress()`）承载全部功能性语义。

**理由**：标签只描述"这是什么弹"，不承载"这是哪条弹链"的信息。两条不同弹链可以合法地显示同一个名字（§3.1.1），任何以标签为键的逻辑都会把它们混为一谈。需要标识弹链时用展平弹链列表，需要标识弹种时用 `getSuppliedType()` 返回的 `ProjectileType` 实例。

### 4.5 调用方

武器状态 HUD 的文本与计数槽位分别取：

| 槽位 | 取法 |
| --- | --- |
| 弹种槽 | 第一根膛内有弹的管的膛内弹种（`getDisplayLabel()`）；都没有膛内弹时退回 `getCurrentRoundLabel()`（指针态） |
| 弹种槽计数 | **供弹弹链**在弹药池中全部条目的 `getRemainingCount()` / `getCapacity()` 之和（容量为负时显示 `∞`） |
| 弹链选项卡 | `getBeltLabel()`（弹链态），余量取弹药池中该弹链的聚合值（与上一行同一个来源） |
| 装填条分段 | 一段 = 一根管：膛内有弹 → 常亮；空膛 → 该管供给者的 `getStatus()` / `getReloadProgress()`；无供给者 → 熄灭 |
| 武器名 | 子系统名，走既有的语言键 |

两个计数（弹种槽与选项卡）读的是同一份数据：**供弹弹链在弹药池里的全部装弹机**。因此"选项卡上的数"与"弹种槽里的数"在供弹那条上必然相等——K-17 的 ATGM 是四根管各配一台容量 1 的装弹机，弹种槽因此显示 4 发总量（打掉一发后 3/4），而不是其中一根管的 1 发。

**取池，而不是取"当前被发射器绑定的那几台"**：绑定是每 tick 都可能变的运行态——只有一台有余弹时多根管会一起挤到它上面，余弹归零的管又会短暂无主——按绑定求和会让同一批弹药显示成 1/1，而弹链池是 4 发。池是按弹链建立的快照，与路由无关。**池本身按实例去重**（`rebuildAmmoPool()` 用 `visited` 去重），因此 `getRemainingCount()` / `getCapacity()` 这两个**装弹机**属性不会被同一台重复计入。弹药池里没有这条弹链时（物理弹仓的 `AmmoLoaderSubsystem` 不进池）回退到该控制器已绑定供给者的合计，回退路径按实例去重。

标签与计数的口径不同：弹种槽的文字是**膛内态**（膛内那发已经压好，与装弹机里还剩什么无关），计数是**弹链池的和**。两者在一管一弹仓的武器上同步；不一致本身有信息量——膛内那发不属于当前供弹弹链时（例如刚轮切了弹链），弹种槽挂 `is-mismatch` 染成警示黄，提示"这一发打出去的不是选项卡上写着的那种弹"。

保留在仓库中的 `AmmoHud` 在读取弹种时使用两处返回 `ProjectileType` 的方法——`LauncherSubsystem.getCurrentAmmoType()` 与 `IAmmoSupplier.getSuppliedType()`——并对结果取 `getRegistryKey().getPath()`；AUI 正式页的弹种槽走"膛内态优先、指针态兜底"（§6.2.5 的槽位表），不经过这两处。

**弹种槽可用的三个来源不等价**，差异如下：

| 来源 | 语义 | 客户端可用性 |
| --- | --- | --- |
| `getChamberedType()` | 膛内已装填的弹种 | 可用，但它是**本机那条链**的结果：起点由载具数据里的 `chambered_type` 播种（`loadData()`），此后由客户端自己的 `requestRound → consumeReadyRound` 链推进（同一条链也是本机开火特效与装填进度的来源）。不是服务端推送的权威值，见 §8.2 |
| `getCurrentRoundLabel()` | 弹链指针当前指向的弹种 | 可用（读 `SynchedEntityData`） |
| `getSuppliedType()` | 供给者下一发将交付的弹种 | 可用，但受 §3.9 影响 |

三者都取 `getDisplayLabel()` 作为文本。**弹种槽优先取 `getChamberedType()`**：它回答的是"这根管现在打出去的是什么"，而玩家按下扳机打出的正是膛内那发；膛内为空时退回 `getCurrentRoundLabel()`（下一发是什么），此时与"还没开始装填"的状态对应。

## 五、数据模型与作者可见改动

### 5.1 装弹机实例 JSON

新增一个可选字段，默认值为空串。**它与 `projectile_types` 写在同一处**——即部件 JSON 里引用装弹机的那个块：

```jsonc
// parts/...json → subsystem.<名字>
{
  "type": "machine_max:regen_loader",
  "definition": "machine_max:2a42_regen_loader",

  "projectile_types": {
    "machine_max:30mm_ap": 1,
    "machine_max:30mm_he": 1
  },

  // 整条弹链的名字。留空则取首发弹种的展示名（见 §3.1 链 C）。
  // 弹链不止一种弹、或自动值不够准确时填写。
  "belt_label": "AP/HE",

  "discovery_outputs": {
    "ammo_2a42": ["global"]
  }
}
```

字段名与 Java 侧的对应关系：JSON 的 `belt_label` ↔ `RegenLoaderSubsystemAttr.beltLabel`。它与 `projectile_types` 同属装弹机的动态属性，由同一个 `CODEC` 读出（§6.1 第 2 项）。

**`belt_label` 必须与 `projectile_types` 同层，不能写进 `subsystems/` 下的定义文件。** 定义文件（`spark_modules/<包>/<命名空间>/subsystems/<分类>/<名字>.json`）承载的是弹仓容量、再生速率、音效这类**按型号共享**的静态属性，同一型号的定义会被多个装弹机实例引用；而 `projectile_types` 与 `belt_label` 都是**逐实例**的——四条 ATGM 管各写各的 `projectile_types`，因此弹链名也必须写在实例上。

由此得到一条内容包写作推论：**同一个型号定义下要挂多条不同构成的弹链时，各弹链的 `belt_label` 只能靠"命名空间 + 实例"分散表达，定义文件无法为它们分别命名。** K-17 与 sdkfz234 的现状是每条弹链一个实例，因此不需要额外处理；若某个内容包想让同一型号定义服务多条互不相同的弹链，就需要按弹链拆成多个定义（每个定义一份静态属性），或接受自动值。

### 5.4 JSON Schema

`projectile_types` 与 `belt_label` 都是**子系统实例**字段（§5.1），因此它们的说明落在描述实例字段的那份 schema 里。各内容包新增一份

```
spark_modules/<内容包>/<namespace>/docs/<locale>/schemas/subsystem/dynamic/regen_loader_dynamic_attr.schema.json
```

并在同目录的 `subsystem_dynamic_attr.schema.json`（按 `type` 分派实例 schema 的总表）中把 `machine_max:regen_loader` 加入 `type` 枚举、加一条指向新文件的 `allOf` 分支——与既有的 `machine_max:launcher` 分支同一写法。要点为：

- 弹种展示名取 `registryKey.toLanguageKey()`，由该弹种所属的内容包在自己的 `lang/<locale>.json` 提供；
- 输入一个未知弹种时，语言键缺失会让界面直接显示键名本身（§3.4），这是刻意的定位手段；
- 留空 `belt_label` 时弹链名取弹链首发弹种的展示名（§3.1 链 C），填写时**按字面**使用所填字符串、不查语言文件；该字段只影响弹链名，不影响弹种槽；改动它不影响弹药池分组与已装填载具的状态。

按型号共享的字段（弹仓容量、再生速率等）留在 `subsystem/static/regen_loader_static_attr.schema.json`，该文件的描述里加一句指向实例 schema，以免作者把 `projectile_types` / `belt_label` 写进定义文件。若后续希望弹链名也走语言文件，可在 `belt_label` 上支持「以 `#` 开头的键引用」写法。

`<locale>` 取 `zh_cn` 或 `en_us`。涉及的内容包与命名空间：`Machine-Max_Official_Pack/machine_max`、`sdkfz/machine_max`、`machine_max.builtin/machine_max`、`Machine-Max_Pack_Template/namespace`。

#### 6.2.2 文档与文字

正式页的文案全部由 Java 写入，因此语言切换在下一次刷新时即生效：固定文案每 tick 取当前语言的文本写进叶子元素，语言一变，写入的文本就变（文本未变时 AUI 自身不做任何事，见 §6.2.4），不需要重开界面或重建文档。

固定文案（角色标签、组名、就绪 / 空弹尾标）走 `Component.translatable(...).getString()`，键以 `gui.machine_max.weapon_hud.` 开头，与项目其他界面文案一起写在 `MMLanguageProvider` 里：

| 键 | `zh_cn` | `en_us` |
| --- | --- | --- |
| `…role.tag.primary` / `…role.tag.secondary` | `主` / `副` | `PRI` / `SEC` |
| `…role.title.primary` / `…role.title.secondary` | `主武器` / `副武器` | `Main Weapon` / `Secondary Weapon` |
| `…ready` / `…empty` | `就绪` / `空弹` | `READY` / `EMPTY` |

弹种槽与弹链选项卡的文本取自运行期数据（膛内弹种或指针态，以及弹链态）与弹种的语言键，同样由 Java 写入。

AUI 的 `<translation>` 元素可以达到同样的效果（取值同样是 `Component.translatable(...).getString()`），但它的取值时机取决于元素文本何时被重新解析；正式页的文案已经统一由 Java 写入，因此不使用该元素。该元素的勘误见 §6.2.1。

| 条件 | 由谁处理 | 机制 |
| --- | --- | --- |
| 有 Screen 打开 | AUI（`Client.drawOverlay`） | `Minecraft.getInstance().screen != null` 时整段跳过 |
| F1 隐藏 HUD | AUI（同一方法） | `options.hideGui` 时提前返回 |
| 未乘坐座椅、座椅未激活、或该座椅没有激活的武器控制器 | `WeaponHudOverlay` | 取数即得空表，生成结果为空串，此时面板整体隐藏 |
| 炮镜模式 | `WeaponHudOverlay` | `CameraController.isCameraMode()`：AUI overlay 不走 `RenderGuiLayerEvent` 黑名单，不自行判断就会浮在瞄具分划之上 |

此外需要两处显式处理：

- **不参与输入**：文档**不得**声明 `<meta name="aui-mouse-events">`。该 meta 缺失时 AUI 不拦截鼠标事件，鼠标滚轮与快捷栏按键照常由原版处理。
- **文档生命周期**：首次需要显示时创建，退出世界时 `remove()`。参考实现是 `PdaHotbarOverlay`（`document()` / `dispose()` / `ClientPlayerNetworkEvent.LoggingOut` 订阅）。

#### 6.2.4 刷新策略

AUI overlay 每帧绘制，本 HUD 每客户端 tick 刷新一次内容。刷新路径按 AUI 1.2.7 对三类写入的不同处理方式分工：

| 写入 | AUI 的处理 | 本 HUD 的做法 |
| --- | --- | --- |
| 叶子元素的 `innerText` | `Element.tick()` 每帧比对新旧文本，只有变化才清文本缓存并标脏（`Element.java` 的 `tick()`） | 每 tick 无条件赋值：未变时只有一次字符串比较 |
| 类名 token（`getClassList().add/remove`） | `DOMTokenList` 在 token 集合未变时不写回、不触发样式重算（`Element.java` 的 `updateTokens()`） | 状态类各记一个"上一次写过的 token"，未变时不调用 |
| `setInnerHTML` / `setAttribute` | 两者都没有内容比较：前者拆掉全部子节点并重新解析（`Element.setInnerHTML()`），后者无条件排一次子树样式重算（`Element.setAttribute()` → `StyleScope.requestRecalc()`） | 都不放在每 tick 路径上 |

因此**元素结构只在形状变化时重建**（`clearChildren()` + `createElement()` + `append()`），属性只在建结构时写；此后每 tick 只改取值。

**形状**由角色、武器块数、每块的发射器数、是否有装填条、选项卡条数组成。这些量决定要建哪些元素；名称、弹种、计数、状态与选中态都写在已有元素上，它们变化不会触发重建。装填条的填充比例按 10% 一档量化（对应样式表的 `fill-0` ~ `fill-100`），把连续变化的进度收敛到 11 个取值。

**"是否有装填条"取静态判据**：多管控制器一定出现（一段一管，它是唯一能表达"哪根管空了"的槽位）；单管控制器只在弹药池里任一装弹机的 `getReloadTimeTicks() > 0` 时出现。判据取弹药池而不是当前供给者——供给者会随弹链切换瞬时为空，用它判定会让装填条在结构未变时忽现忽隐（§6.2.5 的槽位规则）。

#### 6.2.5 页面结构与槽位取数

页面按**三级结构**组织：角色（主 / 副）→ 武器控制器 → 发射器，武器块与控制器一一对应。角色层取 `AbstractControllableSubsystem.getActiveWeaponControllersByRole()`：它与 `getActiveWeaponControllers()` 取同一批控制器，只是按角色分组。槽位取数按 §4.5：

| 槽位 | 取法 |
| --- | --- |
| 武器名 | 控制器对应的子系统名，走语言键 |
| 弹种槽 | **第一根膛内有弹的发射器**（按显示顺序，HUD 侧按子系统名排序）的膛内弹种 `getDisplayLabel()`；膛内都没有弹时退回第一根有供给者的发射器的 `getCurrentRoundLabel()`（指针态）。膛内弹种不属于供弹弹链时给 `.w-ammo` 挂 `is-mismatch` |
| 弹种槽计数 | **供弹弹链**在弹药池中全部条目的 `getRemainingCount()` / `getCapacity()` 之和（容量为负时显示 `∞`）；弹药池里没有这条弹链时退回该控制器下已绑定供给者之和，按**实例**去重 |
| 弹链选项卡 | 每条可选弹链一个选项卡，文本取该弹链在弹药池中首个条目的 `getBeltLabel()`，余量取该弹链全部条目的 `getRemainingCount()` 之和；`is-on` 标在**负责供弹**的那一条上（§1.6：取 `getSelectedBelt()`，它只在弹药池为空时为 `null`，此时取 `getAvailableBelts()` 的第一条兜底） |
| 装填条 | 该控制器下每个发射器一段：膛内有弹 → 常亮（这段现在就能打）；空膛 → 该管供给者的 `getStatus()` / `getReloadProgress()`；无供给者 → 熄灭。**多管时一定出现，单管时只在确有装填机制时出现**（见下） |
| 尾标 | 空弹全灭时取 `…empty`，否则任一发射器装填中时取最慢一段的剩余时间（无装填耗时概念的型号改用百分比；逐发再生的装弹机 `reload_time` 为 0，因此走百分比），其余取 `…ready` |

**选项卡的条数与该控制器下的发射器数无关**：一个控制器可以只有一个发射器而有多个可选弹链（原型用例 A），也可以有多个发射器而只有一条弹链（原型用例 B/D）。两者是独立的两组元素。

**需要逐 tick 改写的文本槽位都是叶子元素**：计数拆成 `.w-cur` + `.w-cap`，选项卡名与计数拆成 `.tab-label` + `.tab-count`。AUI 只渲染无子节点元素上的 `innerText`（`InnerText.appendChildren()` 在元素有子节点时不再取 `innerText`），带子元素的槽位写 `innerText` 不会显示。

##### 角色从哪来

控制组 JSON 的 `main_weapon_targets` / `secondary_weapon_targets` 的目标名统一写 `["global"]`（信号发到装配体再广播给控制器），因此**角色不能从控制组的条目反查控制器**。角色在武器控制器发现握手里记录：`AbstractControllableSubsystem` 逐频道发送握手，事先记下该频道属于主武器表还是副武器表，回调（同步完成）里据此把控制器写进 `weaponControllerRoles`。主、副武器频道都握到手时记主武器；只经由瞄准、移动或绑定频道发现的控制器不入表，查询侧归入主武器。

这一判定与开火指令的走线同源（两者都看“该控制器接受哪一类武器频道”），因此角色的含义就是“哪个扳机打得响它”。

##### 弹种槽在多发射器控制器下的归属

装填条按发射器分段（一段一管），而弹种槽是单值。弹种槽取**第一根膛内有弹的发射器**：按下扳机打出的正是这根管里的那一发，因此槽里写的就是"这一发是什么"。其余发射器若装填其他弹种，其弹种不在本槽位体现；膛内那发与供弹弹链不符时由 `is-mismatch` 标出——切换供给者不改变膛内那发（§4.5），所以轮切弹链后弹种槽会短暂显示旧链的弹，那一发被击发后槽位就回到指针态。

##### 槽位的出现规则

以下四条是设计约束，正式页必须延续：

| 规则 | 内容 |
| --- | --- |
| 插槽的**有无**由静态结构决定 | 发射器数、可选弹链数、是否有装填机制。三者都取自载具结构，因此同一载具的 HUD 高度恒定。是否有装填机制判据是该控制器弹药池里任一装弹机的 `getReloadTimeTicks() > 0`（内容包现状：只有 sdkfz234 的 50mm 装弹机满足，机关炮与机枪的 `reload_time` 均为 0）。 |
| 插槽的**内容**由运行态决定 | 就绪 / 装填中 / 空弹只改变填充比例与尾标，**不增删槽位**。这条直接对应原型的 `is-ready` / `is-reloading` / `is-empty` 三个类：它们只改颜色与尾标文案。 |
| 装填条一段 = 一发射器 | 段的段数等于该武器控制器下的发射器数。**多管控制器一定出现**：每根管的"有弹 / 空弹 / 装填中"互不相同，这是唯一能表达它的槽位（K-17 的 ATGM 控制器下是四根管，每根管一台 `reload_time` 为 0、按 `regen_per_minute` 逐发再生的装弹机；膛内有弹的段常亮，空膛的段按该管装弹机的再生进度涨，因此四段读得出"哪根管现在能打"）。**单管控制器**只在弹药池里任一装弹机的 `getReloadTimeTicks() > 0` 时出现；否则一段的填充只等于弹种槽的计数、没有额外信息，该插槽整体不出现（原型用例 C 的弹链机枪）。 |
| 弹种选项卡仅在可选弹链数 > 1 时出现 | 单弹链武器不渲染 `.w-tabs`。 |

**空弹不删行**：弹链耗尽的武器保留其槽位，只把状态类切到 `is-empty`。这是"高度恒定"的一部分，也是原型用例 F 的存在理由。

被摧毁或未激活的发射器不占槽位、被摧毁或未激活的武器控制器不占武器块：它们的弹药已无意义，且载具受损本身已经改变结构。运行态中只有就绪 / 装填中 / 空弹三种不改变槽位数量。

##### 默认用例清单

原型头部的 A~F 六例是实例化默认页时要覆盖的组合，不是验收用例（验收见 §7.2）：

| 用例 | 组合 | 覆盖的插槽 |
| --- | --- | --- |
| A | 单管 · 三弹种 · 装填中 | 多弹种选项卡 |
| B | 双联装 · 两弹种 · 就绪 | 分段装填条（全满） |
| C | 单管 · 单弹种 · 无装填机制 | 弹链机枪：无装填条、无选项卡 |
| D | 双管 · 两弹种 · 一管就绪一管装填 | 分段体现每管独立 |
| E | 单管 · 单弹种 · 装填中 | 单段装填条 |
| F | 单管 · 单弹种 · 空弹 | 空态保留槽位、不删行 |

### 6.3 阶段三 — 切换与收尾

阶段三只做一件事：摘除 `ammo_hud` 图层注册，让 AUI 正式页成为唯一在绘制的武器状态 HUD。

| # | 事项 | 说明 |
| --- | --- | --- |
| 1 | 摘除 `AmmoHud` 的注册 | `MMGuiManager.registerHud` 里删掉 `event.registerAboveAll(id("ammo_hud"), new AmmoHud())`，并在原处留一行注释说明武器状态 HUD 现由 AUI overlay 承载 |
| 2 | 保留 `AmmoHud` 类文件 | 类本身留在仓库中作为回退：AUI 侧若出现绘制问题，恢复那一行注册即可，不必重写 |

**保留类文件、只摘注册**的理由是回退成本：重新注册是一行改动，而重写一个逐行绘制的 HUD 不是。待 AUI 版 HUD 稳定一个版本后再删除该类。

`AmmoHud` 是 Java 逐行绘制（`GuiGraphics.fill` / `drawString`），其代码不产出可复用的片段，因此阶段二不读取它的任何实现；两处的显隐条件各有各的处理者（§6.2.3）。

`AmmoHud` 的隐式信息来源在 AUI 侧都成了显式契约：炮镜模式的隐藏由 `MMGuiManager` 的图层黑名单完成，而 AUI overlay 不走 `RenderGuiLayerEvent`，因此这一条写进了 `WeaponHudOverlay` 的自查条件，否则炮镜分划会被 HUD 遮挡。

## 八、本设计之外的相关缺口

以下两项在本次讨论中定位到，但**不属于**标签设计的范围。记录在此以免后续重复排查。

### 8.1 弹药池按弹链分组，装弹机与武器控制器无绑定

两项性质，均非缺陷但需知晓：

**其一，同构成即同一条目。** `ammoPool` 的键是展平弹链，因此构成完全相同的多个装弹机会合并为一个条目（K-17 的四个 ATGM 装弹机即如此），由 `LoaderEntry.channel` 区分。这是聚合多个弹仓的正确行为。

**其二，每装弹机只有一个弹链指针，而弹药池按武器控制器建立。** 弹链指针（`BELT_INDEX`）与 `ammo_count` 都是装弹机级状态。若内容包让一个装弹机向多个武器控制器的发射器供给，则两个控制器会共用同一个弹仓与同一个指针，一方的射击会推进另一方的取弹位置。

当前内容包不触发这种情形，因为 `discovery_outputs` 的频道把武器隔开了（`ammo_2a42` 只喂 2A42、`ammo_pktm` 只喂 PKTM）。**该隔离是内容包约定，代码未做强制。**

**弹链级余量聚合**：HUD 的弹种槽与选项卡读的是同一个量——该弹链在弹药池中的聚合余量（同一弹链的多个装弹机求和）。没有"当前弹仓余量"这样一路按绑定关系取数的写法，聚合值因此与"此刻哪几台被发射器绑定"无关（§4.5）。

### 8.2 膛内弹种只在本机那条链上有值

弹种槽与装填条的一段都要读"这根管膛内有没有弹、是什么弹"，而 `LauncherSubsystem.chamberedType` 不是同步值：它的起点由载具数据里的 `chambered_type` 播种（`loadData()`），此后由客户端自己那条 `requestRound → consumeReadyRound` 链推进——发射器在客户端同样跑这条链（它也是本机开火特效与装填进度的来源）。两端的膛内态因此来自**同一套输入**，而不是同一份推送。

这与 `SUPPLIER_ID`（供给者指认：服务端单方面决定，经 `SynchedEntityData` 推送，客户端只跟随）不同——指认是路由决策，只能有一个权威；膛内态是发射器自己的状态机，两端各跑一遍。若日后要求弹种槽逐 tick 与服务端一致，照 `SUPPLIER_ID` 的做法把膛内弹种的注册键也做成一个 `SynchedEntityData`（服务端在 `chamberedType` 的每个写入点顺带写一次）即可，HUD 侧的取数口径不变。
