# 履带系统：内容包模块与类型注册设计

> **状态：** 决策已定，待实现。本文固定 Module 层、目录、注册表、类型分派与数据链路接口；履带字段集合由[数据模型设计](履带系统-数据模型设计.md)定义。
> **日期：** 2026-10-22
> **关联：**
>
> - [履带系统：数据模型设计](履带系统-数据模型设计.md)：`TrackAttr` / `FittingVisual` 字段、材料复用、音效与渲染口径
> - [履带系统：物理实现设计文档](履带系统-物理实现设计文档.md) §2.4（轮面半径与厚度）、§4.4（张力）

> - `PartType` / `PartModule`：内容包类型注册与双端注册表的现有模式

## 1. 范围

### 1.1 本文解决

- 固定内容包目录、模块 id、注册表、schema 文件名与 JSON 类型分派字段，使首个数据驱动履带版本只实现履带，未来增加挂件 / 装甲板时**不迁移已有内容包文件**。
- 固定“物品 → 型号 → `TrackLink` → 存档 / 网络 / 蓝图”的接口。
- 固定 `FittingType` 与 `TrackType` 的类关系。
- 固定型号缺失、材料缺失与协议版本变化的处理规则。

### 1.2 本文不解决

- `TrackAttr` / `FittingVisual` 的字段集合、材料复用、音效与渲染口径——由[数据模型设计](履带系统-数据模型设计.md)定义。
- 履带物品的经济模型（一件物品对应一条带，还是按节消耗）。
- `Fitting` 运行时对象、装甲板、装饰物、两点放置、`SubPartData.attachments`。
- 距离 LOD、多骨骼模型合批；远处渲染使用程序化履带。

### 1.3 术语

| 术语 | 含义 |
| -- | -- |
| 型号 / type id | 内容包定义的一条记录，id 为 `namespace:filename`，如 `machine_max:default` |
| 种类 / kind | JSON 的 `"type"` 字段，首版只有 `"track"` |
| `FittingType` | 所有载具挂件型号的基类；首版只有 `TrackType` |
| `TrackType` | 履带型号；持有 `TrackAttr` 与 `FittingVisual` |
| `Fitting` | 未来用于单 SubPart 刚体挂件的运行时对象；首版不实现 |

## 2. 现状

- `TrackAttr` 是 record，`TrackAttr.DEFAULT` 是硬编码常量；`TrackLink.assemble`、`TrackLink.fromData`、`ItemInteractHandler` 直接读取它。
- `TrackLinkData` 持久化主动轮、成员、当前耐久、断带状态与铺设绕向，**没有型号字段**。
- `TrackItem` 是写死的测试物品，注册名为 `machine_max:test_track`，`stacksTo(1)`；交互流程在 `ItemInteractHandler`。
- `TrackRenderer` 的节贴图、节颜色、节宽度是类内常量；节长与节厚来自 `TrackAttr`（目标字段 `length_per_link` / `thickness_mm`）。
- 内容包模块的现有模式：`ProjectileModule` 读取 `projectiles/` 目录，`ProjectileType.CODEC` 用 `Codec.STRING.dispatch("type", ...)` 分派；当前 `"type"` 只有 `"ballistic"` 一个取值，未知取值抛出异常并由模块记为内容包错误。
- `MMDynamicRes` 为每类内容维护客户端 / 服务端两张注册表。

## 4. 为什么模块层现在固定

### 4.1 内容包迁移成本高于代码成本

内容包作者写的是文件路径、型号 id、配方与物品引用。目录一旦发布为 `tracks/`，未来增加挂件 / 装甲板时只有两种选择：

- 永久保留两套目录（`tracks/` 与 `fittings/`），模块与文档长期分叉；
- 要求所有内容包把文件迁到 `fittings/`，并同步修改引用。

两者都比现在多写一个基类贵。首个数据驱动版本还没有外部内容包依赖，是固定路径成本最低的时刻。

### 4.2 `ProjectileType` 已经证明单分支 dispatch 不是过度设计

`ProjectileType` 的 `CODEC` 是 `Codec.STRING.dispatch("type", ...)`，当前只有 `"ballistic"` 一个分支，注释明确写着未来增加 `"pulse"` / `"beam"` 时在同一个 `switch` 里加分支。履带采用同一模式，首版只有一个 `"track"` 分支，后续增加 `"prop"` / `"plate"` 只加分支和子类。

### 4.3 基类只承载公共字段

`FittingType` 持有所有挂件共有的 `FittingVisual`（模型与贴图，定义见[数据模型设计](履带系统-数据模型设计.md) §4）与注册键；履带专属字段留在 `TrackType`，未来挂件专属字段留在各自的子类。基类不预设履带字段，也不承担运行时职责。

### 4.4 命名

目录名、模块 id、注册表名、schema 文件名与 `FittingType` 类名在本文一次定死。推荐 `fittings`：

- 中性，覆盖履带、装甲板、玩偶等“挂在载具上的硬件 / 配件”；
- 不与 NeoForge 的 `Attachment`（实体数据附件）撞名；
- 与 `FittingType` / `FittingModule` 一致。

备选名称为 `equipment`（更泛）、`mounts`（容易与骑乘混淆）、`accessories`（偏装饰）。如果项目内部更习惯其中某个词，应在实现前替换本文所有命名；实现开始后再改即是本文要避免的迁移。

## 5. 模块与注册表

### 5.1 目录与 id

```text
src/main/resources/spark_modules/<pack>/<namespace>/fittings/<name>.json
```

- 型号 id 为 `namespace:<name>`，与文件所在子目录无关。
- `FittingModule.id = "fittings"`；`SparkPackModule` 的 `id` 就是资源包内的子目录名。
- 不设 `tracks/` 目录；履带定义写在 `fittings/` 下。

### 5.2 注册表

```java
public static ConcurrentMap<ResourceLocation, FittingType> FITTING_TYPES = new ConcurrentHashMap<>();
public static ConcurrentMap<ResourceLocation, FittingType> SERVER_FITTING_TYPES = new ConcurrentHashMap<>();
```

- 双端各自加载：客户端需要型号做渲染与反序列化，服务端需要型号做物理与持久化。
- 提供与 `PartType.get(Level, ResourceLocation)` 相同的读取入口，按 `level.isClientSide()` 选择注册表。
- 注册键由模块在加载时写入 `FittingType.registryKey`；未注册就读取注册键应抛出明确异常，便于定位内容包问题。

### 5.3 加载生命周期

`FittingModule` 与 `ProjectileModule` 同构：

- `onStart(isClientSide, fromServer)`：`fromServer` 为真时清空对应侧注册表，并打印开始日志。
- `read(...)`：用 `PackCodec.read(FittingType.CODEC, content)` 解析，写入注册键，放入对应侧注册表；解析失败时只记录内容包错误，不写入注册表、不设置注册键。
- `onFinish(...)`：打印加载数量。
- 在 `MMPackModuleRegistries.reg` 中注册 `FittingModule()`，位置在 `MaterialModule()` 之后、`PartModule()` 之前。`TrackAttr` 在构造时解析材料，材料表必须先就绪。

重复 id 的现有行为是后加载者覆盖先加载者；`FittingModule` 在此基础上加一条 warn，保留来源信息。内容包诊断依赖 `PackCodec` 的错误通道，未知 `type`、字段错误与材料缺失都记为内容包错误，不让服务器启动失败。

## 6. 类型与 Codec

### 6.1 `FittingType` 基类

包路径：`io.github.sweetzonzi.machine_max.common.mech.vehicle.fitting`。

```java
public abstract class FittingType {
    private final FittingVisual visual;
    private ResourceLocation registryKey;

    protected FittingType(FittingVisual visual) {
        this.visual = visual;
    }

    public abstract String getSerializedName();

    public FittingVisual visual() { return visual; }

    public ResourceLocation getRegistryKey() {
        if (registryKey == null) throw new IllegalStateException("FittingType not registered");
        return registryKey;
    }

    public void setRegistryKey(ResourceLocation key) {
        if (this.registryKey != null) {
            throw new UnsupportedOperationException("FittingType already registered as " + this.registryKey);
        }
        this.registryKey = key;
    }

    public static final Codec<FittingType> CODEC = Codec.STRING.dispatch(
            "type",
            FittingType::getSerializedName,
            name -> switch (name) {
                case "track" -> TrackType.MAP_CODEC;
                default -> throw new IllegalArgumentException("未知载具配件类型: " + name);
            }
    );
}
```

- `getSerializedName()` 是 JSON `"type"` 的取值，也是 dispatch 的路由键。
- 具体类型的 `MAP_CODEC` 是 `MapCodec`，不写 `"type"` 字段；dispatch 负责读写 `"type"`。
- `FittingVisual` 的字段、Codec 与模型约定见[数据模型设计](履带系统-数据模型设计.md) §4；本文只使用它。
- `TrackType` 的字段与 `"visual"` 同级，不包 `"track"` 对象。

### 6.2 `TrackType`

`TrackAttr` 的字段组由[数据模型设计](履带系统-数据模型设计.md) §3.2 定义，包含 `MAP_CODEC`。

```java
public class TrackType extends FittingType {
    private final TrackAttr attr;

    public TrackType(FittingVisual visual, TrackAttr attr) {
        super(visual);
        this.attr = attr;
    }

    @Override
    public String getSerializedName() {
        return "track";
    }

    public TrackAttr attr() {
        return attr;
    }

    public static final MapCodec<TrackType> MAP_CODEC = RecordCodecBuilder.mapCodec(instance -> instance.group(
            TrackAttr.MAP_CODEC.forGetter(TrackType::attr),
            FittingVisual.CODEC.fieldOf("visual").forGetter(FittingType::visual)
    ).apply(instance, (attr, visual) -> new TrackType(visual, attr)));

    public static final Codec<TrackType> CODEC = MAP_CODEC.codec();
}
```

- `TrackAttr.MAP_CODEC.forGetter(TrackType::attr)` 把履带字段平铺到型号 JSON 顶层；`FittingVisual.CODEC.fieldOf("visual")` 增加一个 `"visual"` 对象。
- `TrackType.CODEC` 只用于需要独立 `Codec` 的调用点；dispatch 使用 `MAP_CODEC`。
- `TrackType` 不承担运行时职责；它只提供数据。

### 6.3 分派与错误

- JSON 的 `"type"` 只接受 `"track"`。其他取值在 `FittingType.CODEC` 的 `switch` 中抛出 `IllegalArgumentException`，由 `PackCodec` 捕获并记为内容包错误。
- 未知字段由 Codec 忽略，schema 负责提示；字段类型错误由 Codec 报错，同样走内容包错误通道。
- 客户端与服务端各自加载同一份内容包。

## 7. JSON 外壳与 Schema

### 7.1 文件路径与 id

```text
fittings/default.json          -> machine_max:default
fittings/track_wide.json       -> machine_max:track_wide
```

一个文件对应一个型号；同一个包可以定义多个型号。型号 id 不包含 `fittings/` 前缀。

### 7.2 首版 JSON 外壳

```json
{
  "type": "track",
  "material": "machine_max:track_steel",
  "thickness_mm": 50.0,
  "durability_per_link": 20.0,
  "length_per_link": 0.2,
  "tension": {
    "enabled": true,
    "stiffness": 12000.0,
    "damping": 900.0,
    "preload": 0.0,
    "slack": 0.015,
    "max_force": 800.0
  },
  "sounds": {
    "hit_un_pen": { "sound_id": "machine_max:part.collision.terrain.hard_metal", "range": 64 },
    "hit_pen":    { "sound_id": "machine_max:part.collision.terrain.hard_metal", "range": 64 }
  },
  "visual": {
    "model": "machine_max:track_link",
    "texture": "machine_max:textures/part/track_link.png"
  }
}
```

- `"type"` 由 `FittingType.CODEC` 分派；其余字段由 `TrackType.MAP_CODEC` 解析。
- 字段语义、单位、默认值与材料示例见[数据模型设计](履带系统-数据模型设计.md) §9。
- 首版内置 `machine_max:default` 是字段齐全的联调 fixture，数值取[数据模型设计](履带系统-数据模型设计.md) §5.1 的首版标定；该型号的字段值由 `fittings/default.json` 本身决定。

### 7.3 Schema

- 文件名固定为 `fitting.schema.json`，放在 builtin 内容包的 `docs/<lang>/schemas/` 下，随 `gradlew syncSchemas` 分发到官方包、模板包与技能快照。
- 首版 schema 约束 `"type": { "const": "track" }`、`material`、`thickness_mm`、`durability_per_link`、`length_per_link`、`tension`、`sounds`、`overwrite`、`visual`；字段细节见[数据模型设计](履带系统-数据模型设计.md)。
- `overwrite` 按 `HitBoxAttr.OverwriteAttr` 的字段组声明；schema 描述注明 `overwrite.sounds` 对履带不生效。
- 字段已定稿，schema 按最终字段收紧；后续字段扩展走 schema 版本更新。
- `checkSchemas` 会校验副本一致性，schema 改动与副本放在同一个提交里。

## 8. 物品、持久化与网络

### 8.1 物品与数据组件

- `MMDataComponents` 增加 `FITTING_TYPE`（`ResourceLocation`），与现有 `PROJECTILE_TYPE` / `PART_TYPE` 同构：

```java
public static final DeferredHolder<DataComponentType<?>, DataComponentType<ResourceLocation>> FITTING_TYPE =
        COMPONENTS.register("fitting_type", () -> DataComponentType.<ResourceLocation>builder()
                .persistent(ResourceLocation.CODEC)
                .networkSynchronized(ResourceLocation.STREAM_CODEC)
                .cacheEncoding()
                .build());
```

- 正式物品 `machine_max:track`：`TrackItem`，`stacksTo(1)`，读取 `FITTING_TYPE`；组件缺失时回落到 `machine_max:default` 并打 warn。
- `machine_max:test_track` 保留为开发 / 测试物品，内容包只使用 `machine_max:track`。
- 型号到物品的入口是配方产物组件：`result.components` 写 `machine_max:fitting_type`，示例见[数据模型设计](履带系统-数据模型设计.md) §9.3。`machine_max:fabricating` 与标准合成配方都使用 `ItemStack.CODEC`，支持该写法；履带使用前者，不走 `PartFabricatingRecipe` 的 `PART_TYPE` 注入。
- `ItemInteractHandler` 在开始铺设时读取手持物品的 `FITTING_TYPE`，解析为 `TrackType` 写入 `TrackDraft`；闭合时把 `TrackType` 传给 `VehicleCore.createTrack`。
- 同一个型号可以由多条配方产出；配方不改变型号数据，只写组件。
- 首版物品图标可以共用一张；按型号换图标留到内容包美术接入时处理。

### 8.2 `TrackLinkData`

```java
public record TrackLinkData(
        TrackMemberRef sprocket,
        List<TrackMemberRef> members,
        float durability,
        boolean broken,
        boolean clockwise,
        ResourceLocation trackType
) { ... }
```

- JSON 字段名为 `"track_type"`，避免与内容包 JSON 的 `"type"`（种类）混淆。
- `CODEC` 使用 `optionalFieldOf("track_type", DEFAULT_TYPE)`；旧存档没有该字段时回落到 `machine_max:default`。
- `STREAM_CODEC` 写入 / 读取 `ResourceLocation`；`normalized()` 保留型号，只重置耐久与断带。
- 加入 `track_type` 会改变 `TrackLinkData` 的线格式。`VehicleData` 同时被 `sync` 组的 `TrackLinkSyncPayload` / `LevelVehicleDataPayload` 与 `misc` 组的 `BlueprintExtractLocalPayload` 使用，两个协议版本都要提升：`sync` 与 `misc`。发布说明同时注明。

### 8.3 运行时 `TrackLink`

- `TrackLink` 持有 `TrackType type` 与原始 `ResourceLocation typeId`；`attr()` 委托到 `type.attr()`，现有的物理 / 渲染 / 装甲调用点不需要改签名。
- `TrackLink.MIN_MEMBERS = 2` 是结构常量；型号不提供最低成员数。成员 = 主动轮 + 至少 1 个负重轮。
- `TrackLink.assemble(vehicle, sprocket, wheels, type)` 与 `VehicleCore.createTrack(..., type)` 增加型号参数，返回类型为 `@Nullable TrackLink`。成员少于 `MIN_MEMBERS`、或 `thicknessMeters()` 不小于任一成员轮半径时返回 `null`，不注册、不建约束；`createTrack` 在 `assemble` 返回 `null` 时直接返回 `null`。
- `removeMember` / `refreshMembers` / `onMemberDestroyed` / `fromData` 四处都以 `MIN_MEMBERS` 判定；成员低于该值时解散（`fromData` 丢弃并清理反向引用）。判定不依赖包络返回 `null`。
- `ItemInteractHandler` 在闭合处检查 `createTrack` 的返回值；`null` 时给出失败消息并保留草稿，不调用 `link.members()`。
- 装配与载入都校验 `type.attr().thicknessMeters()` 小于每个成员轮的有效半径；不满足时闭合被拒绝，载入中的履带按无效成员处理并丢弃，日志给出成员名与两侧数值。
- `TrackLink.fromData` 先解析型号，再推导节数与最大耐久：

```java
TrackType type = resolveTrackType(level, data.trackType());
if (type == null && fallbackToDefault) {
    type = resolveTrackType(level, DEFAULT_TYPE);
}
if (type == null) {
    MachineMax.LOGGER.warn("履带型号 {} 不存在或不是履带类型，已跳过", data.trackType());
    return null;
}
```

`resolveTrackType` 查对应侧注册表；型号不存在或不是 `TrackType` 时返回 `null`。

- 服务端 `VehicleCore.fromData`（存档加载）调用 `fromData(..., false)`：型号缺失、型号不是 `TrackType`、默认型号缺失，都丢弃该条履带并 warn；成员轮仍留在原 Part 上。
- 客户端 `VehicleCore.applyTrackLinkData`（应用同步）调用 `fromData(..., true)`：先查原始型号，再回退 `machine_max:default`；两步都失败时丢弃。回退成功时 `typeId` 仍是原始 id。
- `TrackLinkData` 是型号的唯一持久化载体；`TrackLink` 不把 `TrackType` 对象写进存档。`toData()` 写 `typeId`，不写回退得到的默认 id。

### 8.4 网络与客户端

- `TrackLinkSyncPayload` 的载荷结构只含履带列表；型号字段在 `TrackLinkData.STREAM_CODEC` 内，因此 `sync` 与 `misc` 协议版本都要提升。
- 客户端收到型号 id 后从 `FITTING_TYPES` 解析；缺失时按 §8.3 回退默认视觉并打 warn，渲染用默认型号的 `FittingVisual` 与 `TrackAttr`。
- 客户端不参与履带型号的物理判定；型号只影响渲染、音效查询与本地显示。服务端物理以服务端注册表为准。
- 客户端回退只影响本地表现；下一次服务端同步或保存时仍携带原始 `typeId`。

## 9. 兼容与错误处理

| 场景 | 处理 |
| -- | -- |
| 旧存档没有 `track_type` | 回落 `machine_max:default`；默认型号缺失时丢弃该条履带并 warn |
| JSON `"type"` 未知 | 内容包错误；该文件不进入注册表 |
| JSON 字段类型错误 | 内容包错误；该文件不进入注册表 |
| `material` 缺失或不在材料表 | 内容包错误；该型号不注册 |
| 型号 id 重复 | 后加载者覆盖，warn 记录来源 |
| 客户端缺少型号 | 回退默认型号视觉，保留原始 id，warn；不阻断载具加载 |
| 客户端连默认型号也缺失 | 丢弃该条履带，warn；载具其余部分正常加载 |
| 服务端缺少型号 | 丢弃该条履带，warn；成员轮保留 |
| `TrackAttr` 静态默认实例 | 不提供；默认型号由 `fittings/default.json` 提供 |
| 闭合成员不足 | `createTrack` / `assemble` 返回 `null`；草稿保留，提示补轮；不调用 `members()` |

## 12. 开放问题

`TrackAttr` / `FittingVisual` 的字段、材料复用、音效边界与 JSON 平铺方式已由[数据模型设计](履带系统-数据模型设计.md)定义。模块层仍需决定：

1. 物品经济：一件物品对应一条带，还是可堆叠的“单节履带板”，按包络节数消耗。
2. 正式物品是否按型号切换 2D 图标。
3. 重复型号 id 的最终策略：覆盖、拒绝后者，还是按包优先级。
4. 未来 `prop` 类型的公共字段与 `FittingVisual` 的边界。

蓝图携带履带的策略已定：`VehicleData` 的 `trackLinks` 与 `TrackLinkData.normalized()` 都保留履带，蓝图因此携带成员引用与型号；放置时按当前载具拓扑重新解析成员，失效成员丢弃。

## 13. 风险

| 风险 | 影响 | 缓解 |
| -- | -- | -- |
| 目录 / 模块命名反复 | 内容包迁移，正是本文要避免的成本 | 实现前一次定死；本文列出的备选名只在实现前可换 |
| 履带字段与 schema 反复 | 内容包作者反复改文件 | 本文只定外壳；字段由数据模型文档一次定稿 |
| 协议版本遗漏 | `sync` 或 `misc` 未提升时，旧客户端解析新 `TrackLinkData` 失败 | 两个版本同时提升并写发布说明 |
| 模块顺序错误 | `FittingModule` 先于 `MaterialModule` 时型号全部记为材料缺失 | 注册顺序固定为 `MaterialModule` → `FittingModule` |
| 客户端缺包 | 型号缺失导致渲染或反序列化异常 | 默认型号视觉回退 + 保留原始 id；服务端权威 |
| 过早引入 `Fitting` 运行时 | 复杂度翻倍，偏离首版目标 | 本文明确不做；未来另开文档 |
| 材料缺失静默回退 | 作者以为型号生效，实际走了默认材质 | 材料必填；缺失即内容包错误且型号不注册 |
