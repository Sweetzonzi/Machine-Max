## 一、概述

三项改动：

1. **结算相位前移**：部件累积伤害的结算点从 `LevelTickEvent.Pre` 移到 `LevelTickEvent.Post`，使"该 tick 内已入队的伤害"在 tick 末尾统一结算。
2. **逐次折算，并以子系统事件的最终金额为准**：结算时对批次内**每一次命中**各自折算载具伤害；参与折算与耐久扣减的金额是该次命中的 `SubPartDamageEvent.Pre` 最终金额，因此**子系统对伤害的截断会传导到零件耐久与载具伤害**（§3.4，本次唯一的预期数值变更）。
3. **通告携带完整批次**：装配体收到的通告从"零件 + 一个 float"变为"零件 + 本次结算的全部命中记录"，每条记录携带该次命中的协议上下文。
本次重构只交付到**通告**为止：装配体是否把伤害投递给承载实体、是否按来源或零件归并、在哪个相位扇出，都由 `IPartAssembly` 的实现决定（§5.5 与 §七）。协议侧的承载者投递入口 `BFDamageApi.deliverTo` 由 BallisticsFramework 侧同步交付。

改动集中在四处代码文件：`common/mech/DestroyableObject.java`、`common/mech/vehicle/SubPart.java`、`common/mech/vehicle/IPartAssembly.java`、`common/mech/vehicle/SubPartHitDamage.java`（新增）；另需同步若干文档与 Javadoc（§六）。不触碰 `BallisticProjectile` 的结算位置、不改变子系统事件契约、不改变装甲与穿甲判定。

## 二、现状锚点

本节描述**改动前**的结算链路，即这次改动要修正的形态；改动完成后的形态见第五节。

### 2.1 结算调用链

```text
LevelTickEvent.Pre  → ObjectManager.onPreTick（HIGHEST）
                        → ProjectileManager.preTick()
                        → levelVehicles.forEach(v -> v.preTick())
                        → levelDestroyableObjects.forEach(o -> o.preTick())
                            → DestroyableObject.preTick
                                ├─ tickCount++
                                ├─ hurtTime--
                                ├─ handleAccumulatedDamage()     ← 伤害结算
                                └─ checkDestroyed() → setDestroyed()
                            → SubPart.preTick
                                └─ 装配进度满 10 tick 时写入刚体重力

物理线程（异步，与主线程并行）→ PhysicsLevelTickEvent.Pre / Post

LevelTickEvent.Post → ObjectManager.onPostTick（NORMAL）
                        → levelDestroyableObjects.forEach(o -> o.postTick())
                            → DestroyableRigidObject.postTick
                                └─ 刚体状态写入同步数据 → super.postTick()
                            → DestroyableObject.postTick
                                ├─ tickDestroyTimer(1)
                                └─ syncToClient()             ← 本 tick 的同步
                            → SubPart.postTick
                                ├─ 连接点 mcTick
                                ├─ 刷新实体代理与包围盒
                                └─ collisionHandler.effectManager.tick()
                        → ProjectileManager.postTick()
```

坐标：`common/mech/ObjectManager.java#onPreTick`、`#onPostTick`、`#onPrePhysicsTick`；`common/mech/DestroyableObject.java#preTick`、`#postTick`；`common/mech/DestroyableRigidObject.java#postTick`；`common/mech/vehicle/SubPart.java#preTick`、`#postTick`。

物理步的调度：Spark-Core 在 `LevelTickEvent.Pre` 内请求一次物理步（`requestStep()`），物理线程接到请求后与主线程**并行**推进约一个主线程 tick 的物理量；单线程物理模式（`SparkCoreConfig.SINGLE_THREAD_PHYSICS`）下该步进同步完成。

### 2.2 伤害入队与结算

伤害从任意线程进入部件：

```java
// common/mech/DestroyableObject.java#accumulateDamage
protected ConcurrentLinkedQueue<Pair<Float, BFDamageContext>> accumulatedDamage = new ConcurrentLinkedQueue<>();

public void accumulateDamage(float damage, BFDamageContext ctx) {
    if (damage > 0) { hurtTime = hurtDuration; accumulatedDamage.add(Pair.of(damage, ctx)); }
}
```

入队金额由 `SubPart.hurt(DamageSource, float)` 给出：它先广播一次 `SubPartDamageEvent.Pre` 并取用事件的最终金额，再 `accumulateDamage(amount, ctx)`。

结算一次抽干队列：

```java
// common/mech/vehicle/SubPart.java#handleAccumulatedDamage（摘录）
float totalDamage = 0;
while (!accumulatedDamage.isEmpty()) { ... totalDamage += damage; }
if (totalDamage > 0) {
    float remainingDurability = Math.max(0f, getDurability());
    setDurability(Math.clamp(getDurability() - totalDamage, 0, getMaxDurability()));
    part.recomputeAssemblyFromDurability();
    if (part.assembly != null) {
        float vehicleDamage;
        if (isDestroyed())              vehicleDamage = totalDamage * part.type.vehicleDamageRateDestroyed;
        else if (totalDamage > remainingDurability)
            vehicleDamage = part.type.vehicleDamageRate * remainingDurability
                          + part.type.vehicleDamageRateDestroyed * (totalDamage - remainingDurability);
        else                            vehicleDamage = totalDamage * part.type.vehicleDamageRate;
        part.assembly.onPartDamage(part, Math.max(0f, vehicleDamage));
    }
    ...
}
```

### 2.3 装配体通告

```java
// common/mech/vehicle/IPartAssembly.java#onPartDamage
void onPartDamage(Part part, float damage);

// common/mech/vehicle/VehicleCore.java#onPartDamage
public void onPartDamage(Part part, float damage) { this.applyVehicleDamage(damage); }
```

装配体只拿到一个 float。传参里不包含命中位置、命中法线、命中速度、穿深、伤害来源，也不包含"本批由哪几次命中构成"。

### 2.4 结算公式里的两个传递率

`part.type.vehicleDamageRate` 与 `part.type.vehicleDamageRateDestroyed` 是零件类型上的两个**常量**传递率：`PartType`（`common/mech/vehicle/PartType.java`）的 `final` 字段，取值来自零件类型 JSON 的 `vehicle_damage_rate`（默认 1.0）与 `vehicle_damage_rate_destroyed`（默认 0.1），运行期不随耐久变化。

| 符号 | 含义 | 取值来源 |
| --- | --- | --- |
| `r` | `part.type.vehicleDamageRate` | JSON `vehicle_damage_rate`（默认 1.0） |
| `r_d` | `part.type.vehicleDamageRateDestroyed` | JSON `vehicle_damage_rate_destroyed`（默认 0.1） |

`Part.recomputeAssemblyFromDurability()` 只重算组装进度与材料进度上限（两者都取自子零件耐久比例），不写入这两个字段；耐久对伤害的影响发生在命中时、入队之前：`HitBox.getRHA` / `getEffectiveDmgResist` / `getEffectiveDmgMult` 都按子零件当前耐久比例衰减。

因此"本批是否跨过摧毁阈值"只由**累计伤害与剩余耐久的相对大小**决定。记本批开始前的耐久为 $R$、本批累计伤害为 $D$：

$$V(D) = \begin{cases} D \cdot r & D \le R \\ R \cdot r + (D - R) \cdot r_d & D > R \end{cases}$$

零件已处于摧毁状态时整批按 $D \cdot r_d$ 折算。$V$ 是 $D$ 的**分段线性函数**，拐点在 $R$。

### 2.5 子系统对伤害金额的截断在改动前的落点

结算过程中，结算代码按每次命中构造一个 `SubPartDamageEvent.Pre` 并直接交给命中判定的 `HitBox` 所属子系统（不经事件总线），子系统可以下调金额（`event.setDamageAmount`）。`AbstractSubsystem.onHurt` 用该金额扣减子系统自身耐久；`BasicSubsystem` 与 `ModularSubsystem` 在静态属性 `limit_damage` 打开时把它截到子系统剩余耐久（语义即该属性在 schema 中的描述："限制伤害传递值不超过子系统剩余耐久度。例如 40 伤害、剩余 20，则只传递 20"）。

改动前的实现随后累加的是**入队原值**：

```java
// common/mech/vehicle/SubPart.java#handleAccumulatedDamage（摘录）
totalDamage += damage;            // 入队原值：不含子系统对事件的截断
```

于是子系统对金额的截断只作用于子系统自身耐久，被截掉的部分仍然全额扣减零件耐久并折算载具伤害。

## 三、问题

### 3.1 结算相位使"本 tick 的伤害何时生效"不确定

结算发生在 `Pre`。同一 tick 内，`Pre` 之前的物理步产生的伤害算本 tick，`Pre` 之后的整个 tick（含方块与实体 tick、以及随后的物理步）产生的伤害只能落到**下一个 tick 的 `Pre`**。同样是"这个 tick 打出的伤害"，生效时刻相差一个 tick，且取决于伤害进入物理空间与结算点的先后。

物理步在独立线程上与主线程并行，因此**任何主线程相位都不是跨线程的屏障**：结算点选在 `Post` 时，"本 tick 已入队的伤害"指 `Post` 排空前进入队列的伤害；`Post` 之后由物理步入队的伤害仍落下一 tick。单线程物理模式下不存在该窗口（物理步在 `Pre` 内同步完成）。

宿主实体的生命值只能在主线程扣除，因此"装配体在同一 tick 内投递"是同一问题的另一半：若投递发生在某个部件的 `postTick` 里，而 `onPostTick` 是对每个对象**依次**调用的，那么部分零件尚未结算就会先投递。

### 3.2 批次聚合丢弃逐次信息

`totalDamage` 把整批伤害求和后丢弃每一次的 `BFDamageContext`。母舰/机娘这类"以实体为承载者"的装配体需要把伤害继续投递给宿主，而投递需要：伤害来源（用于承载实体侧的原版判定与第三方监听）、命中几何（用于表现与方向性判定）、以及（需要时）按来源归并的能力。这些在 `onPartDamage(Part, float)` 的通告里全部不可得。

### 3.3 逐次折算与整批折算在传递率恒定时数值等价

§2.4 的 $V$ 是 $D$ 的分段线性函数，因此逐次求和与整批求值恒等：

$$\sum_i \left[V(D_i) - V(D_{i-1})\right] = V\!\left(\sum_i D_i\right)$$

数值例（$R = 5$、$r = 1.0$、$r_d = 0.1$）：三次 2 点得 $2.0 + 2.0 + 1.1 = 5.1$；一次 6 点得 $5 \times 1.0 + 1 \times 0.1 = 5.1$。

所以逐次折算的价值不在数值，而在**粒度**：装配体拿到逐条命中而不是一个求和值（§3.2），每条记录可以携带它生效时刻的上下文。数值上的差异来自 §3.4。

### 3.4 子系统对伤害的截断被丢弃

按 §2.5，子系统把一次命中的金额截到自身剩余耐久后，零件耐久仍按入队原值扣减，`limit_damage` 描述的行为没有落到零件上。截断本应表达"这部分伤害由子系统挡住、不再向零件内部传导"，例如子系统剩余耐久 10、命中 15 时，零件承受的是 10 而不是 15。

## 四、意义

1. **时序确定**：结算点落在 tick 末尾的 `Post`，同一 tick 内已入队的伤害（不论来自方块 tick、实体 tick 还是并行物理步）在该相位统一结算——这消除了"伤害落在 `Pre` 前后差一个 tick"的分裂。
2. **信息不丢**：装配体拿到每次命中的完整上下文，按来源归并、方向性防护、表现层后效所需的信息都在手上，无需再去反查。
3. **折算忠实**：每次命中以它生效时刻的事件最终金额参与零件耐久与载具伤害的计算，子系统对伤害的截断因此真正生效。
4. **为承载者投递铺路**：装配体投递到宿主实体的入口是协议侧的承载者投递（`BFDamageApi.deliverTo`，由 BallisticsFramework 侧同步交付），它要求调用方持有一次可归属的协议上下文——这正是本计划第 3 项交付的东西。

## 五、方案

### 5.1 结算相位迁到 `Post`

`DestroyableObject.preTick` 保留 `tickCount++`、`hurtTime--`、客户端 `clientSyncPose()`；把**伤害结算**与**摧毁判定**迁到 `postTick`：

```java
// common/mech/DestroyableObject.java
public void preTick() {
    if (isRemoved) return;
    tickCount++;
    if (hurtTime > 0) hurtTime--;
    if (level.isClientSide()) clientSyncPose();     // 客户端同步位姿；结算只在服务端
}

public void postTick() {
    if (!level.isClientSide()) {
        settleAccumulatedDamage();                  // 结算（服务端）
        if (checkDestroyed()) setDestroyed();       // 摧毁判定必须紧跟结算
        if (isDestroyed()) tickDestroyTimer(1);
        syncToClient();                             // 必须晚于结算，否则本次耐久变化延后一 tick 同步
    }
    if (isDestroyed() && getDestroyTime() <= 0) this.destroy();
}

protected abstract void settleAccumulatedDamage();
```

`handleAccumulatedDamage` 更名为 `settleAccumulatedDamage`，以反映"结算"语义并避免与"累积"混淆。`DestroyableRigidObject.postTick` 先把刚体状态写入同步数据再调用 `super.postTick()`，因此"刚体回写 → 结算 → 同步"这一相对顺序与改动前相同。

`SubPart` 覆写该方法并被基类 `postTick` 调用；`BallisticProjectile` 覆写了 `preTick`/`postTick` 并在自己的 `preTick` 里直接调用该方法（`common/mech/projectile/BallisticProjectile.java#preTick`），因此其结算位置保持不变——投射物没有需要继续投递的承载者，其摧毁判定与自身生命周期绑定。

### 5.2 批次记录类型

```java
// common/mech/vehicle/SubPartHitDamage.java
/**
 * 一次命中在零件层的结算结果。
 *
 * @param damage        子系统事件之后、未被取消的该次命中伤害（≤ 0 的命中不产生记录）
 * @param vehicleDamage 按传递率折算后的装配体伤害
 * @param ctx           该次命中的协议上下文，携带伤害来源与命中几何
 * @param part          产生该次结算的零件
 */
public record SubPartHitDamage(float damage, float vehicleDamage, BFDamageContext ctx, Part part) {}
```

`part` 字段与通告入参看起来重复，它的作用是让承载者侧的**扁平批次**（把多个零件的记录汇总成一个列表）自带来源信息，无需再按零件分组嵌套。

不携带子系统引用：需要子系统时可由记录的 `ctx` 反查——`ctx.extensions().get(MMDamageExtensions.HIT_BOX)` 给出命中框，再经 `HitBox#getSubsystem()` 取到子系统；扩展缺失时按 `findStrongestHitBox()` 的回退规则取框。

### 5.3 逐次折算

```java
// common/mech/vehicle/SubPart.java#settleAccumulatedDamage（重构后的关键段）
float remaining = Math.max(0f, getDurability());   // 本批开始前的耐久
float drained = 0f;                                // 本批此前已结算的量
List<SubPartHitDamage> hits = new ArrayList<>();
while (!accumulatedDamage.isEmpty()) {
    Pair<Float, BFDamageContext> pair = accumulatedDamage.poll();
    float damage = pair.getFirst();
    BFDamageContext ctx = pair.getSecond();
    if (damage <= 0f) continue;                    // 滤掉非正伤害
    SubPartDamageEvent.Pre event = new SubPartDamageEvent.Pre(this, ctx, damage);  // 构造后直接交给子系统，不经事件总线
    HitBox hitBox = findHitBox(ctx);
    // findHitBox 声明 @NotNull，但无命中框时 findStrongestHitBox 返回 null：守卫必须保留
    if (hitBox != null && hitBox.getSubsystem() != null) hitBox.getSubsystem().onHurt(event);
    if (event.isCanceled()) continue;              // 被子系统取消的命中不产生记录
    NeoForge.EVENT_BUS.post(new SubPartDamageEvent.Post(this, ctx, damage));

    // 子系统可以下调本次金额：事件最终金额是零件耐久与载具伤害的唯一输入
    float effective = Math.max(0f, event.getDamageAmount());
    if (effective <= 0f) continue;
    float leftBefore = Math.max(0f, remaining - drained);
    float vehicleDamage;
    if (isDestroyed()) {
        vehicleDamage = effective * part.type.vehicleDamageRateDestroyed;
    } else if (effective > leftBefore) {
        // 本次命中跨过摧毁阈值：承受住的部分用当前传递率，溢出部分用摧毁传递率
        vehicleDamage = part.type.vehicleDamageRate * leftBefore
                      + part.type.vehicleDamageRateDestroyed * (effective - leftBefore);
    } else {
        vehicleDamage = effective * part.type.vehicleDamageRate;
    }
    drained += effective;
    if (vehicleDamage > 0f) hits.add(new SubPartHitDamage(effective, vehicleDamage, ctx, part));
}
if (drained > 0f) {
    setDurability(Math.clamp(getDurability() - drained, 0, getMaxDurability()));
    part.recomputeAssemblyFromDurability();
}
if (!hits.isEmpty() && part.assembly != null) part.assembly.onPartDamage(part, List.copyOf(hits));
// 每点伤害额外推进的摧毁倒计时仍在此处，基数取 drained；
// syncToClient() 由基类 postTick 在结算之后统一调用；本方法内不发送同步包
```

性质说明：

- **耐久读取**：`remaining` 是整批开始前的一次读取，批内沿用该值；`getDurability()` 在 `shareDurability` 为真时映射到零件的共享耐久池，写入发生在整批结束之后，因此批内读数稳定。
- **`remaining` 与 `drained` 的关系**：`leftBefore = max(0, remaining - drained)` 表达的切段点是"这批累计伤害跨过剩余耐久"的位置，与 §2.4 的 $V$ 拐点一致；传递率恒定时逐次求和与整批求值数值相同（§3.3）。
- **金额来源**：`effective` 是事件最终金额，子系统对伤害的截断在此生效；被截掉的部分不计入 `drained`，也不折算载具伤害（§3.4）。`extraAdvance` 同样以 `drained` 为基数。
- **零值**：`damage <= 0` 的入队项与金额被下调到 0 的命中都不产生记录、不扣耐久。
- **`isDestroyed()` 在整批期间取值不变**（摧毁标记只在 `checkDestroyed` 里写），因此不需要在循环内重查。
- **`part.recomputeAssemblyFromDurability()` 在整批结束后调用一次**，调用次数与位置同 §2.2。
- **`SubPartDamageEvent.Post` 仍以入队原值发布**：`damage` 是队列里的金额，`effective` 是事件最终金额；两个值各自服务既有监听（记账用前者）与零件结算（用后者）。
- **通告一次**：每个 `SubPart` 每次结算至多通告一次，`hits` 为空时不通告。

### 5.4 通告接口

```java
// common/mech/vehicle/IPartAssembly.java
/** Part 受到伤害后向装配体顶层上报，由实现者决定如何折算到装配体的 HP */
void onPartDamage(Part part, float damage);

/**
 * 一次结算的通告：携带本零件本次结算产生的全部命中记录。
 * <p>
 * 与 {@link #onPartDamage(Part, float)} 的差别只在粒度——后者只有一个折算后的总量，
 * 前者还带有逐次命中的金额与协议上下文（伤害来源、命中几何），
 * 供需要把伤害继续投递给承载实体的装配体使用。
 * 记录里的零件字段让"把多个零件的记录汇总成一个扁平列表"的场景自带来源信息。
 * 通告发生在结算过程中（{@code LevelTickEvent.Post} 内），若实现要把伤害投递给承载实体，
 * 必须自行推迟到全部零件结算之后。
 * </p>
 * <p>默认实现把记录折算为总量后调用 {@link #onPartDamage(Part, float)}，因此只实现该重载的装配体照常工作。</p>
 */
default void onPartDamage(Part part, List<SubPartHitDamage> hits) {
    float total = 0f;
    for (SubPartHitDamage hit : hits) {
        total += hit.vehicleDamage();
    }
    if (total > 0f) onPartDamage(part, total);
}
```

`VehicleCore` 保留 `onPartDamage(Part, float)`（其实现 `applyVehicleDamage(damage)` 不变），并继承默认的批次通告，因此载具产品线本次不改变行为。承载者产品线（宿主实体的生命值在机体装配体之外）覆写批次通告以接收逐条记录。

### 5.5 通告的相位与投递约束

通告发生在结算过程中，即 `LevelTickEvent.Post` 内的 `ObjectManager.onPostTick`；该方法对每个对象依次调用 `postTick`，因此装配体在收到通告时，其他零件可能尚未结算。

由此得到一条约束：

**若装配体要把伤害交给承载实体，投递必须晚于全部零件的结算。**

投递的实现方式由装配体决定（是否投递、是否按来源或零件归并、在哪个相位扇出），本文不引入投递接口，也不改动 `ObjectManager`。两条可供实现选择的落点：以更低优先级订阅同一个 `LevelTickEvent.Post`（NeoForge 的 `EventBus` 按 `EventPriority` 由 `HIGHEST` 到 `LOWEST` 派发、同优先级按注册顺序），或在下一个 tick 的 `Pre` 投递。

## 七、非目标

- **不改变子系统事件契约**：`SubPartDamageEvent.Pre` / `Post` 的签名与语义不变（`Pre` 可取消、可用 `setDamageAmount` 下调金额，`Post` 以入队原值发布），事件的产生方式也不变：`SubPart.hurt` 向事件总线广播一次 `Pre` 并取用其最终金额入队；结算阶段按每次命中构造一个 `Pre` 直接交给子系统（不经事件总线），通过后再广播一次 `Post`。结算点迁到 `Post` 相位只改变后一个构造与广播发生的相位。
- **不改变 `VehicleCore` 的伤害行为**：它继续把折算结果累加到载具自身的生命值体系，不涉及承载实体投递。
- **不规定投递**：装配体是否投递、如何把结果交给宿主实体（护甲层是否参与、是否按来源归并、无敌帧是否被完全格挡的伤害消耗、在哪个相位扇出）属于承载者产品线的设计，本文只交付通告与"投递晚于结算"这一约束，见 `../BallisticsFramework/docs/BFDamageApi-deliverTo投递计划.md` 与宿主侧文档。
- **不改变装甲与穿甲判定**：本计划只动"结算之后怎么通告"，不动"命中时怎么判定"。
- **不改动 BallisticsFramework**：承载者投递入口 `BFDamageApi.deliverTo` 由该仓库侧同步交付。

## 八、影响与风险

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 子系统截断传导（预期变更） | 子系统把事件金额截到自身剩余耐久后，零件耐久与载具伤害都按截断后的值结算；截掉的部分不传导 | 设计意图，与 `limit_damage` 的 schema 描述一致；需在改动说明中标注为数值变更 |
| 逐次折算的数值 | 传递率为常量时逐次折算与整批切段公式恒等（§3.3） | 无需平衡性说明；验证逐次与整批结果相同 |
| 相位窗口内物理线程读到旧状态 | 结算点从 `Pre` 中段移到 `Post`，本 tick 的物理步（`HitBox.getRHA` 的耐久衰减、`AbstractConnector.handleAccumulatedImpact` 的 `isDestroyed()` 分支）读到的是结算前的耐久与摧毁标记 | 差异为一个物理步量级；需要"结算后立刻生效"的链路应改用事件结果而非 `getDurability()` |
| 异步物理步跨越 `Post` | `Post` 的排空不是跨线程屏障：其后入队的伤害在下一 tick 结算；单线程物理模式下不存在该窗口 | 契约限定为"该 tick 的 `Post` 之前入队的伤害在本 tick 结算"，不承诺跨线程严格同 tick |
| 结算与同步的顺序被写反 | 若先 `syncToClient` 再结算，本 tick 的耐久变化要下一 tick 才可见 | §5.1 的顺序是硬约束，需在代码注释中标注 |
| 摧毁倒计时推进的时机 | `tickDestroyTimer` 在 `postTick`，`checkDestroyed` 迁入后必须在它之前 | 同 §5.1 |
| 客户端同步 | 结算只在服务端；客户端按同步数据更新耐久与摧毁标记（`DestroyableObject#onSyncedDataUpdated`） | `syncToClient` 与结算同处一个 `postTick`，客户端可见时机不变 |
| 上下文引用被长期持有 | `SubPartHitDamage` 携带 `BFDamageContext`，其 `extensions()` 为可变容器 | 装配体只在本次 `Post` 内消费；需要跨 tick 保留时应先复制扩展容器（`BFDamageExtensions#copy`） |
| 通告按 SubPart 粒度触发 | 同一 Part 的多个 SubPart 在同一 tick 各自通告一次，装配体因此收到多条通告 | 归并与去重由装配体实现决定（记录自带来源零件，可直接汇总） |
| 投射物结算位置 | `BallisticProjectile` 有自己的结算入口，不随基类迁移 | §5.1 已限制只改基类链路 |

## 九、验证

本仓库没有 `src/test/` 目录，以下断言需以 `runServer` / `runClient` 手工构造场景，或用临时调试代码打印断言。

1. **相位**：单 tick 内构造两次命中，断言两次都在**同一 tick 的 `Post`** 完成结算、耐久一次写入、装配体收到**一条**含两条记录的通告。
2. **折算恒等**：$R = 5$、$r = 1.0$、$r_d = 0.1$ 时，"三次 2 点"与"一次 6 点"的载具伤害同为 5.1；逐次求和与整批求值在传递率恒定时相同。
3. **子系统截断**：子系统剩余耐久 10、`limit_damage` 打开、命中 15 → 零件耐久减少 10、载具伤害按 10 折算；同一 batch 内两次 15 → 零件耐久共减少 10（第二次被截到 0）。对照参考：`limit_damage` 关闭时零件耐久按入队原值扣减。
4. **信息完整性**：通告中每条记录的 `ctx` 非空，且 `ctx.source()` 与发起伤害时传入的对象是同一个引用；`SubPartDamageEvent.Post` 的金额等于入队原值。
5. **零值与取消**：`damage <= 0` 的命中不产生记录；被子系统取消的命中不产生记录，且不影响同批其他命中；金额被下调到 0 的命中不产生记录。
6. **同步顺序**：断言耐久变化在**同一 tick** 的同步包中可见（不含延迟一 tick 的现象）。
7. **回归**：投射物命中、爆炸、零件摧毁倒计时、下车候选搜索与连接点伤害分配的行为与改动前一致。

## 十、修订记录

- 更正结算公式中两个传递率与耐久的关系（常量的 JSON 取值），并给出"逐次折算与整批折算恒等"的结论。
