# 子系统机制与信号传输

本教程目标：
- 讲清子系统如何赋予零部件“实际功能”。
- 讲清信号如何在子系统、交互区、连接点、vehicle 之间传递。
- 教你在内容包层（JSON）创建“自己的子系统型号”（复用现有 type）。


---

## 1. 子系统由谁创建

在 `parts/*.json` 的 `sub_parts -> subsystems` 中配置后：
1. 系统读取每个子系统条目（名称 -> 动态属性）。
2. 通过 `type + definition` 找到对应逻辑与静态参数。
3. 运行时创建具体子系统实例并挂到 subpart。

源码锚点：
- `AbstractSubsystemAttr`：动态属性基类，负责 `createSubsystem`。
- `Part.createSubsystems()`：把 JSON 条目实例化并放入 `subPart.subsystems`。
- `AbstractSubsystem`：生命周期、耐久、信号接收与输出。

---

## 2. `type + definition` 的职责分离

- `type`：选择“行为类别”（例如 `machine_max:item_storage`、`machine_max:engine`）。
- `definition`：选择该类别下的“具体型号参数”。

可把它理解为：
- `type` = 类
- `definition` = 配置化实例模板

示例：

```json
"subsystems": {
  "subsystem.machine_max.trunk": {
    "type": "machine_max:item_storage",
    "definition": "machine_max:default_trunk"
  }
}
```

---

## 3. 如何创建“自己的子系统”（内容包层）

这里的“自己的”指：
- 不写 Java 新类型；
- 通过新建 definition 文件，产出你自己的型号。

步骤：
1. 在 `machine_max/subsystems/` 下复制一个接近的官方定义。
2. 改名并调整参数（容量、功率、曲线、耐久、音效等）。
3. 在 part 的 `subsystems` 中用原有 `type` 引用你的新 `definition`。
4. 进游戏验证功能与交互。

高频错误：
- `definition` 路径存在但 `type` 不匹配。
- 名称空间写错导致找不到定义。

---

## 4. 信号通路总览

信号核心接口：
- 发送：`ISignalSender`
- 接收：`ISignalReceiver`
- 存储频道：`SignalChannel`
- 跨连接点转发端口：`SignalPort`

源码锚点：
- `ISignalSender.sendSignalToTarget/sendSignalToAllTargets`
- `ISignalReceiver.getSignalChannel/onSignalUpdated`
- `SignalPort.onSignalUpdated`（跨部件连接后转发）

---

## 5. `signal_targets`：把信号送给谁

`signal_targets` 可出现在：
- 交互区（interact box）——只发不收，语义是"点击后由谁接管"，见 §5.1
- 连接点（connector）
- 某些子系统动态配置（取决于具体 type）

信号线的目标名可指向：
- 某子系统名
- 某连接点名（端口）
- `local`
- `global`

名字的作用域是发送者所在的**整个 Part**：子系统名、交互区名、连接点名三类共用一套命名空间，跨子零件
也能解析。所以同一个 Part 内的连线一律直接写目标名（子系统名），不要绕经连接点——见 §6。

### 5.1 交互区的目标是"谁来接管这次点击"

交互区不是信号接收者。它的 `signal_targets` 在结构变化与载具入世时被解析成终端子系统（跨零件时沿连接点
到达对侧的座位；模板车的接线发生在入世之前，所以入世那一次才是第一次完整解析），点击时按声明序逐个调
目标的 `onInteract`：`CONSUME` 结束，`FAIL`（座位已被占）与 `PASS`（目标不处理）都继续试下一个。
因此交互区的目标只能写子系统名或连接点名；`local`、`global` 与另一个交互区都解析不出可交互的终端，
装载期就报错。

交互区挂在哪个零件上，只决定"它随谁一起消失"，不决定玩家能不能碰到它：`fast` 是玩家包围盒与交互区
体积的接触判定，`accurate` 是射线命中交互区体积，两者都只看交互区的世界位置。所以门框完全可以写在
座位所在的车体里，从而把目标写成同零件的子系统名，省掉跨零件的到达频道表；反过来，把门框写在可被打掉
的车壳里，就得到"车壳没了、门也就点不了"的效果，代价是每次装车都要配对侧那张表。

```json
"interact_boxes": {
  "interact.machine_max.trunk": {
    "bone": "TrunkInteractZone",
    "signal_targets": {
      "trunk_interact": ["subsystem.machine_max.trunk"]
    },
    "interact_mode": "accurate",
    "condition": "local.subsystem_active('subsystem.machine_max.engine') == 0"
  }
}
```

交互区只在三件事同时成立时激活（提示亮、射线选得中）：解析出的终端表非空、`condition` 门控成立、
至少一个终端子系统报告 `isInteractable()`（座位看"空且完好"，储物箱看"还在工作"）。提示与点击共用
这三条，内容里不需要再把占用状态"报"给交互区。

## 6. `signal_translations`：跨连接点改频道名

只有**跨 Part** 的信号才走连接点：名字解析到 Part 边界为止，零件 B 的子系统没法被零件 A 的
`signal_targets` 直接点名。同一个 Part 内部（包括标了 `"internal": true` 的内部连接点）不写这两张表，
直接写子系统名即可——内部连接点只表达机械关节，表写在上面会被 `checkContent` 拦下：端口要靠两端
几何自动配对才能对接，配不上时整条线静默断开。

端口转发用的是**接收侧**的表：信号到达端口 P 后，`SignalPort` 取 P 的对接口 Q，先用 Q 的
`signal_translations` 转译频道，再按 Q 的 `signal_targets` 找接收者。两张表都写在"要接收信号的那一半"
连接点上，描述的是本零件收什么频道、收下之后送给谁。投递前还会核对接收者声明的接受频道（座位的
`interact_inputs`、引擎与变速箱的 `control_inputs` 等），不在表里的接收者被直接跳过。

使用场景：
- A 零件内部叫 `interact_left_door`，
- B 零件希望接收 `interact`（门的编号与座舱无关）。

可在接收侧的连接点配置里写：

```json
"connectors": {
  "connector.machine_max.seat_mount": {
    "locator": "AttachPoint",
    "definition": "machine_max:fixed_front",
    "signal_translations": {
      "interact_left_door": "interact"
    },
    "signal_targets": {
      "interact": ["subsystem.machine_max.seat"]
    }
  }
}
```

机制要点：
- 频道转译在 `SignalPort` 层完成，只改频道名，不改信号值。
- 转译后的频道必须在本连接点的 `signal_targets` 里存在，否则不会被消费。
- 座位默认只接受 `interact`。门送进来的若是不带转译的 `interact_left_door`，要么在接收侧连接点上
  把它转译回 `interact`，要么在座位安装块里补 `interact_inputs`（与型号的 `interact_inputs`、
  `loader_discovery_inputs` 取并集）；只在连接点上写了目标、座位没声明接受，这条信号会在端口转发
  时被丢掉，日志里没有任何痕迹。

## 7. 完整最小链路示例

**交互链路**（玩家点击）不经过信号槽：

1. `interact_boxes` 里的一条目标：`"trunk_interact": ["subsystem.machine_max.trunk"]`。
2. 结构变化与载具入世时交互区解析出终端子系统；零件单独摆放、跨零件没接上，或对侧没配到达频道时
   终端为空，交互区不激活（提示不亮、射线也选不中）。
3. 玩家点击 → `InteractBox#interact` 按声明序调 `onInteract`，第一个 `CONSUME` 结束本次交互。

跨部件时，目标写成自己零件上的那个对接连接点；交互区沿连接点找到对侧零件上被本连接点
`signal_targets` 点名、且声明接受该频道的子系统（转译规则见 §6）。

**信号链路**（状态与指令）走频道：

1. 发送方把值写进某个频道，目标写在自己的 `*_outputs` 里。
2. 同零件具名直连；跨零件写连接点名，由接收侧的 `signal_translations` 与 `signal_targets` 定位。
3. 子系统在 `onSignalUpdated` 或内部逻辑中处理。

两类链路的区别值得记住：交互是一次性事件（`CONSUME` 之后没有残留状态），信号是持续状态（槽里
留着最后一条值，接收者每轮读取）。

---

## 8. 调试顺序（强烈建议）

1. 先确认子系统本体工作（不跨连接点）。
2. 再让交互区指向该子系统，确认提示与点击生效。
3. 最后再引入 connector 转发与频道翻译。

每次只新增一段链路，避免一次性排查过多变量。

## 9. 高频问题排查

### 问题 A：子系统完全无反应

检查：
- `type` 与 `definition` 是否匹配。
- 子系统名字是否与 `signal_targets` 目标名完全一致。

### 问题 B：跨部件后信号丢失

检查：
- 连接点是否真的处于连接状态。
- `signal_translations` 映射后的频道名，是否被对侧 `signal_targets` 监听。
- 接收者是否声明接受这个（转译后的）频道：座位看 `interact_inputs`，引擎、变速箱、车轮驱动看
  `control_inputs`，武器控制器看 `aim_inputs` / `fire_inputs`。未声明的接收者在端口转发时被跳过，
  既不写输入槽也不打日志。

### 问题 C：频道名看起来对，但仍不触发

检查：
- 大小写与下划线是否完全一致。
- 是否在错误对象上配置了 `signal_targets`（例如写在了不消费该频道的对象上）。

---

## 10. 能力边界

JSON 层可以完成：
- 子系统型号扩展（新 definition）。
- 信号路由与频道翻译。
- 交互到功能的多数常见玩法。

若你要新增“全新 type 语义”（即全新运行逻辑），需要 Java 扩展（本文不展开）。
